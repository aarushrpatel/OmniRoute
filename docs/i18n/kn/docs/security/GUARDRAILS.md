> **ಸತ್ಯದ ಮೂಲ:** `src/lib/guardrails/`
> **ಕೊನೆಯ ನವೀಕರಣ:** 2026-08-29 — v3.8.51 (Video Bridge ಪ್ರತಿಲೇಖದ ಮೂಲವನ್ನು ಕರೆಮಾಡುವವರು ಘೋಷಿಸುತ್ತಾರೆ,
> ಸರ್ವರ್ ಇನ್ನೂ ಅದನ್ನು ಪರಿಶೀಲಿಸುವುದಿಲ್ಲ — #11661 ಪ್ರಕಾರ ಸ್ಪಷ್ಟಪಡಿಸಲಾಗಿದೆ)

Guardrails, OmniRoute ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಪೂರೈಕೆದಾರರ ನಡುವಿನ ಗಡಿಯಲ್ಲಿ ಸುರಕ್ಷತೆ,
ನೀತಿ ಮತ್ತು ವಿಷಯ ರೂಪಾಂತರಗಳನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ. ಪ್ರತಿಯೊಂದು guardrail ವಿನಂತಿಯ
ಪೇಲೋಡ್ಗಳನ್ನು (`preCall`) ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು (`postCall`)
ಪರಿಶೀಲಿಸಬಹುದು (ಮತ್ತು ಐಚ್ಛಿಕವಾಗಿ ತಿರಸ್ಕರಿಸಬಹುದು, ರೂಪಾಂತರಿಸಬಹುದು ಅಥವಾ ಟಿಪ್ಪಣಿ ಸೇರಿಸಬಹುದು).

ಈ ವ್ಯವಸ್ಥೆಯು **fail-open** ಆಗಿದೆ: ಕಾರ್ಯಗತಗೊಳ್ಳುವಾಗ guardrail ದೋಷವನ್ನು ಎಸೆದರೆ,
registry ಆ ದೋಷವನ್ನು ದಾಖಲಿಸಿ, ವಿನಂತಿಯನ್ನು ವಿಫಲಗೊಳಿಸುವ ಬದಲು ಮುಂದಿನ guardrail
ಜೊತೆಗೆ ಮುಂದುವರಿಯುತ್ತದೆ. ನಿರ್ಬಂಧಿಸುವುದು ಸ್ಪಷ್ಟ ನಿರ್ಧಾರವಾಗಿದೆ (`block: true`),
ಎಂದಿಗೂ ಆಕಸ್ಮಿಕವಲ್ಲ.

## ಅಂತರ್ನಿರ್ಮಿತ ಗಾರ್ಡ್ರೇಲ್ಗಳು

ಆಮದು ಮಾಡುವಾಗ ರಿಜಿಸ್ಟ್ರಿಯು ಆದ್ಯತೆಯ ಕ್ರಮದಲ್ಲಿ ಆರು ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಲೋಡ್ ಮಾಡುತ್ತದೆ
(`registry.ts` → `registerDefaultGuardrails()` ನೋಡಿ):

| ಆದ್ಯತೆ | ಹೆಸರು               | ಹಂತ(ಗಳು)       | ಫೈಲ್                  |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

ಕಡಿಮೆ ಆದ್ಯತಾ ಸಂಖ್ಯೆಗಳು **ಮೊದಲು** ರನ್ ಆಗುತ್ತವೆ.

### ವಿಷನ್ ಬ್ರಿಡ್ಜ್ (`visionBridge.ts`) — ಮೊಡಾಲಿಟಿ ಬ್ರಿಡ್ಜ್ PR-1

**ವಿಷನ್ ಬೆಂಬಲಿಸದ ಮಾದರಿಗಳಿಗೆ** ಗುರಿಪಡಿಸಿದ, ಚಿತ್ರಗಳನ್ನು ಒಳಗೊಂಡ ವಿನಂತಿಗಳನ್ನು ಮಧ್ಯದಲ್ಲಿ ತಡೆದು, ಸಂಪೂರ್ಣ ವಿನಂತಿಯನ್ನು ವಿಷನ್-ಸಾಮರ್ಥ್ಯವಿರುವ ಮಾದರಿಗೆ ಮರುಮಾರ್ಗಗೊಳಿಸುತ್ತದೆ ಅಥವಾ ಅಪ್ಸ್ಟ್ರೀಮ್ ಕರೆಗೆ ಮೊದಲು ಚಿತ್ರದ ಭಾಗಗಳನ್ನು ಸಂರಚಿಸಬಹುದಾದ ವಿಷನ್ ಮಾದರಿಯಿಂದ ರಚಿಸಲಾದ ಪಠ್ಯ ವಿವರಣೆಗಳೊಂದಿಗೆ ಬದಲಾಯಿಸುತ್ತದೆ. ಇದರಿಂದ ಪಠ್ಯ-ಮಾತ್ರದ ಪೂರೈಕೆದಾರರು ಮಲ್ಟಿಮೋಡಲ್ ಪೇಲೋಡ್ಗಳನ್ನು ಪಾರದರ್ಶಕವಾಗಿ ನಿರ್ವಹಿಸಬಹುದು.

ಹರಿವು:

1. ಗುರಿ ಮಾದರಿಯು ಈಗಾಗಲೇ ವಿಷನ್ ಅನ್ನು ಬೆಂಬಲಿಸುತ್ತಿದ್ದರೆ ಬಿಟ್ಟುಬಿಡಿ (ಅದು ಬಲವಂತದ-ಬ್ರಿಡ್ಜ್ ಪಟ್ಟಿ `isVisionBridgeForcedModel`ಯಲ್ಲಿ ಕಾಣಿಸಿಕೊಳ್ಳದ ಹೊರತು).
2. `extractImageParts(messages)` ಮೂಲಕ ಚಿತ್ರದ ಭಾಗಗಳನ್ನು ಹೊರತೆಗೆಯಿರಿ
   (`visionBridgeHelpers.ts`), ಇದು `open-sse/utils/mediaParts.ts`ನಲ್ಲಿರುವ **ಏಕೀಕೃತ ಮೀಡಿಯಾ ಪತ್ತೆಕಾರಕ** `detectMediaParts()`ಗೆ ನಿಯೋಜಿಸುತ್ತದೆ — ಇದು ಕಾಂಬೊ ಹೊಂದಾಣಿಕೆ ಫಿಲ್ಟರ್ನೊಂದಿಗೆ ಹಂಚಿಕೊಳ್ಳಲಾದ ಏಕೈಕ ಸತ್ಯದ ಮೂಲವಾಗಿದೆ.
   ಹೊರತೆಗೆಯುವಿಕೆಯನ್ನು `replaceImageParts` ಮರಳಿ ಸೇರಿಸಬಹುದಾದ ಆಕಾರಗಳ ಮೇಲ್ಮಟ್ಟದ ಭಾಗಗಳಿಗೆ ಅನುಮತಿ ಪಟ್ಟಿಯ ಮೂಲಕ ಸೀಮಿತಗೊಳಿಸಲಾಗಿದೆ (ಹೊರತೆಗೆಯುವಿಕೆ↔ಬದಲಿಸುವಿಕೆ ಒಪ್ಪಂದ): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, ಮತ್ತು Responses API `input_image`. ನೆಸ್ಟೆಡ್ ಹೊಂದಾಣಿಕೆಗಳು ಮತ್ತು ಸೂಚಕ-ಮಾತ್ರದ ಆಕಾರಗಳು ಕಾಂಬೊ-ಫಿಲ್ಟರ್ಗೆ ಸಂಬಂಧಿಸಿದವು ಮತ್ತು ಅವುಗಳನ್ನು ಎಂದಿಗೂ ಹೊರತೆಗೆಯಲಾಗುವುದಿಲ್ಲ.
   ಯಾವುದೂ ಕಂಡುಬರದಿದ್ದರೆ ಬಿಟ್ಟುಬಿಡಿ.
3. `resolveVisionBridgeRuntimeSettings()` ಮೂಲಕ ರನ್ಟೈಮ್ ಸಂರಚನೆಯನ್ನು ನಿರ್ಧರಿಸಿ
   (`src/shared/constants/modalityBridgeDefaults.ts`): ಹೊಸ `modalityBridge*`
   ಸೆಟ್ಟಿಂಗ್ಗಳ ಕೀಗಳು ಆದ್ಯತೆ ಪಡೆಯುತ್ತವೆ; ಹಳೆಯ `visionBridge*` ಕೀಗಳು **ಒಂದು-ಚಕ್ರದ
   ಫಾಲ್ಬ್ಯಾಕ್** ಆಗಿ ಉಳಿಯುತ್ತವೆ (ರೋಲ್ಬ್ಯಾಕ್ ವಿಂಡೋ). ಬ್ರಿಡ್ಜ್ ನಿಷ್ಕ್ರಿಯವಾಗಿದ್ದರೆ ಯಾವುದೇ ಮೀಡಿಯಾ ಟ್ರಾವರ್ಸಲ್ಗೆ ಮೊದಲು ಬಿಟ್ಟುಬಿಡಿ.
4. ಮೋಡ್ ಆಯ್ಕೆಕಾರಕ (`modalityBridgeVisionMode`, ಕೆಳಗಿನ ಕೋಷ್ಟಕವನ್ನು ನೋಡಿ) ಮರುಮಾರ್ಗಗೊಳಿಸುವಿಕೆ ಅಥವಾ ವಿವರಣೆಯ ನಡುವೆ ನಿರ್ಧರಿಸುತ್ತದೆ. ಮರುಮಾರ್ಗಗೊಳಿಸುವಿಕೆಯು `model` ಅನ್ನು ಮಾತ್ರ ಬದಲಾಯಿಸಿದ `modifiedPayload` ಅನ್ನು, ಜೊತೆಗೆ `{ rerouted, fromModel, toModel, imagesKept }` ಮೆಟಾವನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ.
5. ವಿವರಣೆ ಮಾರ್ಗ: ಚಿತ್ರಗಳ ಸಂಖ್ಯೆಯನ್ನು `maxImages`ಗೆ ಸೀಮಿತಗೊಳಿಸಿ, ಕಾರ್ಯ-ಅರಿವಿನ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ರಚಿಸಿ, ವಿವರಣೆಯ ಕ್ಯಾಶ್ ಅನ್ನು ಪರಿಶೀಲಿಸಿ, ವಿಷನ್ ಮಾದರಿಯನ್ನು **ಸಮಾನಾಂತರವಾಗಿ**
   (`Promise.allSettled`) ಕರೆ ಮಾಡಿ ಮತ್ತು ಅವುಗಳ ಸ್ಥಾನದಲ್ಲಿ `[Image N]: <description>` ಪಠ್ಯ ಭಾಗಗಳನ್ನು ಸೇರಿಸಿ.
   ವಿಫಲವಾದ ವಿವರಣೆಯು `null` ಅನ್ನು ನೀಡುತ್ತದೆ ಮತ್ತು ಮೂಲ ಚಿತ್ರದ ಭಾಗವನ್ನು **ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ** (#4012) — ಆದರೆ ಕಾಂಬೊ ವಿವರಣೆ ಮಾರ್ಗದಲ್ಲಿ ಪ್ರತಿಯೊಂದು ವಿವರಣೆಯೂ ವಿಫಲವಾದಾಗ ಇದಕ್ಕೆ ವಿನಾಯಿತಿ ಇದೆ; ಅಲ್ಲಿ ಖಚಿತಪಡಿಸಲಾದ ವಿಷನ್-ರಹಿತ ಅಪ್ಸ್ಟ್ರೀಮ್ ಬದಲಿಗೆ
   `(ಲಭ್ಯವಿಲ್ಲ — ಯಾವುದೇ ವಿಷನ್-ಸಾಮರ್ಥ್ಯವಿರುವ ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕಗೊಂಡಿಲ್ಲ)` ಸ್ಟಬ್ ಅನ್ನು ಪಡೆಯುತ್ತದೆ (#8430).
6. `modifiedPayload` + ಮೆಟಾ (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) ಅನ್ನು ಹಿಂದಿರುಗಿಸಿ.

| `reroute`  |          | ಮರುಮಾರ್ಗಗೊಳಿಸುವಿಕೆಯನ್ನು ಬಲವಂತಪಡಿಸಿ: ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಹೊಂದಿರುವ ಮಾದರಿಯನ್ನು ಉಳಿಸುವ ಗಾರ್ಡ್ ಅನ್ನು ಬೈಪಾಸ್ ಮಾಡಲಾಗುತ್ತದೆ. ಮರುಮಾರ್ಗಗೊಳಿಸುವಿಕೆಯ-**ಗುರಿ** ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಗಾರ್ಡ್ ಇನ್ನೂ ಅನ್ವಯಿಸುತ್ತದೆ — ಬಳಸಬಹುದಾದ ಯಾವುದೇ ವಿಷನ್ ಗುರಿ ಅಸ್ತಿತ್ವದಲ್ಲಿಲ್ಲದಿದ್ದರೆ, ವಿನಂತಿಯು ವಿವರಣೆಗೆ ಮುಂದುವರಿಯುತ್ತದೆ; ಹೀಗಾಗಿ ಕಚ್ಚಾ ಚಿತ್ರಗಳು ಪಠ್ಯ-ಮಾತ್ರದ ಬ್ಯಾಕ್ಎಂಡ್ ಅನ್ನು ಎಂದಿಗೂ ತಲುಪುವುದಿಲ್ಲ (#8430). |

ಬಲವಂತದ ಮೋಡ್ಗಳು ಸ್ವಯಂ ಹ್ಯೂರಿಸ್ಟಿಕ್ ರನ್ ಆಗುವುದಕ್ಕಿಂತ **ಮೊದಲೇ** ಶಾರ್ಟ್-ಸರ್ಕ್ಯೂಟ್ ಆಗುತ್ತವೆ; `auto` ವರ್ತನೆಯು PR-1 ಪೂರ್ವದ ಗಾರ್ಡ್ರೇಲ್ಗೆ ಬೈಟ್-ಮಟ್ಟದಲ್ಲಿ ಒಂದೇ ಆಗಿದೆ.

#### API-ಕೀ ವ್ಯಾಪ್ತಿ (`visionBridgeKeyScope.ts`)

ಕರೆ ಮಾಡುವವರ API ಕೀಯು `allowedConnections`, ಕೋಟಾ ಪೂಲ್ಗಳು
(`allowedQuotas`) ಅಥವಾ ಮಾದರಿಗಳನ್ನು (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) ನಿರ್ಬಂಧಿಸಿದಾಗ, ಬ್ರಿಡ್ಜ್ ಆ ಕೀಯು ಬಳಸಬಹುದಾದ ಸಂಪರ್ಕಗಳಲ್ಲಿ, ಆ ಕೀಯು ಬಳಸಬಹುದಾದ ಮರುಮಾರ್ಗಗೊಳಿಸುವಿಕೆ ಮತ್ತು ವಿವರಣೆ ಮಾದರಿಗಳನ್ನು ಮಾತ್ರ ಆಯ್ಕೆಮಾಡುತ್ತದೆ. ನಂತರ ವಿವರಣೆ ಕರೆಯು ಯಾವಾಗಲೂ `x-omniroute-self-loop-key-id` ಹೆಡರ್ನೊಂದಿಗೆ OmniRoute ಸ್ವಯಂ-ಲೂಪ್ ಮೂಲಕ ಸಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಸ್ವೀಕರಿಸುವ ಚಾಟ್ ವಿನಂತಿಯು ಆ ಕೀಯ ಸಂಪರ್ಕ ಮತ್ತು ಮಾದರಿ ನೀತಿಯನ್ನು ಮತ್ತೊಮ್ಮೆ ಜಾರಿಗೊಳಿಸುತ್ತದೆ. `enforceApiKeyPolicy()` ಆ ಹೆಡರ್ ಅನ್ನು ಸ್ವಯಂ-ಲೂಪ್ ಬೇರರ್ನೊಂದಿಗೆ ಮಾತ್ರ ಗೌರವಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಅದು ಪ್ರವೇಶವನ್ನು ಕೇವಲ ಮತ್ತಷ್ಟು ಸೀಮಿತಗೊಳಿಸಬಲ್ಲದು; ನಿರ್ಧರಿಸಲಾಗದ ಐಡಿಯನ್ನು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ.

ಕೀಯಿಗೆ ಯಾವುದೇ ವಿಷನ್ ಮಾದರಿಯನ್ನು ಅನುಮತಿಸದಿದ್ದರೆ, ವಿವರಣೆ ಮಾರ್ಗವು ಪಕ್ಕಕ್ಕೆ ಸರಿಯುತ್ತದೆ ಮತ್ತು ವಿನಂತಿಯು ಬದಲಾವಣೆಯಿಲ್ಲದೆ ಮುಂದುವರಿಯುತ್ತದೆ; ಇದು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಿದ ಗಾರ್ಡ್ರೇಲ್ನಂತೆಯೇ ಇರುವ ಫೇಲ್-ಓಪನ್ ವರ್ತನೆಯಾಗಿದೆ (ಮೆಟಾ `{ skipped: true, reason: "no_permitted_vision_model" }`).
ಕೀಯಿಲ್ಲದ ವಿನಂತಿಗಳು ಮತ್ತು ಈ ನಿರ್ಬಂಧಗಳಿಲ್ಲದ ಕೀಗಳು ಹಿಂದಿನಂತೆಯೇ ವರ್ತಿಸುತ್ತವೆ.

#### ಕಾರ್ಯ-ಅರಿವಿನ ವಿವರಣೆ ಪ್ರಾಂಪ್ಟ್ (`modalityBridgeVisionTaskAware`)

ಡೀಫಾಲ್ಟ್ **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) ಮೂಲ ವಿವರಣಾ ಪ್ರಾಂಪ್ಟ್ಗೆ **ಕೊನೆಯ ಬಳಕೆದಾರ ಸಂದೇಶದ** ಪಠ್ಯವನ್ನು (500 ಅಕ್ಷರಗಳಿಗೆ ಮೊಟಕುಗೊಳಿಸಿ) ಸೇರಿಸುತ್ತದೆ; ಇದರಿಂದ ವಿವರಣೆಯು ಬಳಕೆದಾರರು ನಿಜವಾಗಿ ಕೇಳಿದ ವಿಷಯದತ್ತ ನಿರ್ದೇಶಿಸಲ್ಪಡುತ್ತದೆ (codex-vision-proxy ಮಾದರಿ) ಮತ್ತು ಗೋಚರಿಸುವ ಪಠ್ಯವನ್ನು ಲಿಪ್ಯಂತರಿಸಲು vision ಮಾದರಿಯನ್ನು ಕೇಳುತ್ತದೆ. ಫ್ಲ್ಯಾಗ್ ಆಫ್ ಆಗಿದ್ದರೆ — ಅಥವಾ ಬಳಕೆದಾರರ ಪಠ್ಯ ಇಲ್ಲದಿದ್ದರೆ — ಮೂಲ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ಬದಲಾವಣೆ ಇಲ್ಲದೆ ಬಳಸಲಾಗುತ್ತದೆ.

ವಿವರಣಾ self-loopನ ಸ್ವಂತ OpenAI-ಹೊಂದಾಣಿಕೆಯ ವಿನಂತಿಯು (`visionBridgeHelpers.ts`ನಲ್ಲಿನ `callVisionModelSingle()`) ಯಾವಾಗಲೂ `image_url.detail: "high"` ಅನ್ನು ವಿನಂತಿಸುತ್ತದೆ — ಯಾವುದೇ client signal ಆಧಾರಿತ ನಿರ್ಬಂಧವಿಲ್ಲದೆ, ಪ್ರತಿಯೊಂದು caller/providerಗೂ ಇದು ಅನ್ವಯಿಸುತ್ತದೆ. ಈ ಪ್ರಾಂಪ್ಟ್ ಕೇಳುವ ಪಠ್ಯ-ಲಿಪ್ಯಂತರಣ ಕಾರ್ಯಕ್ಕೆ low-detail sampling ನಿಖರತೆಯನ್ನು ಕುಗ್ಗಿಸುತ್ತದೆ; ಆದ್ದರಿಂದ ಮೂಲ inbound ವಿನಂತಿಯು ಯಾವ detail level ಬಳಸಿದ್ದರೂ, ವಿವರಣಾ ಕರೆಯೇ ಯಾವಾಗಲೂ high detail ಅನ್ನು ಕೇಳುತ್ತದೆ. ಇದು ಆಂತರಿಕ ವಿವರಣಾ ವಿನಂತಿಯ body ಮೇಲೆ ಮಾತ್ರ ಪರಿಣಾಮ ಬೀರುತ್ತದೆ; ಪ್ರಾಥಮಿಕ ವಿನಂತಿಯಲ್ಲಿ callerನ ಸ್ವಂತ `image_url.detail` ಅನ್ನು OmniRoute ಹೇಗೆ ಫಾರ್ವರ್ಡ್ ಮಾಡುತ್ತದೆ ಎಂಬುದನ್ನು ಇದು ಬದಲಾಯಿಸುವುದಿಲ್ಲ — ಆ ಡೀಫಾಲ್ಟ್ ಅನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ, ಪತ್ತೆಯಾದ OpenCode clientsಗಳಿಗೆ ಮಾತ್ರ, `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) ನಲ್ಲಿ ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ. ವಿವರಣಾ self-loopನ Anthropic wire-format ಶಾಖೆಯಲ್ಲಿ `detail` field ಇಲ್ಲ ಮತ್ತು ಎರಡೂ ಡೀಫಾಲ್ಟ್ಗಳು ಅದರ ಮೇಲೆ ಪರಿಣಾಮ ಬೀರುವುದಿಲ್ಲ.

#### ವಿವರಣಾ ಔಟ್ಪುಟ್ ಮಿತಿ (`modalityBridgeVisionMaxChars`)

| ಕೀ                             | ಡೀಫಾಲ್ಟ್ | ವ್ಯಾಪ್ತಿ           |
| ------------------------------ | -------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`      | `0` ಅಥವಾ 100–50000 |

`0` (ಡೀಫಾಲ್ಟ್) ಎಂದರೆ **ಯಾವುದೇ ಮಿತಿ ಇಲ್ಲ** — `callVisionModel()` ಹಿಂತಿರುಗಿಸುವ ವಿವರಣೆಯನ್ನು ಮಾರ್ಪಡಿಸದೆ ರವಾನಿಸಲಾಗುತ್ತದೆ, ಇದರಿಂದ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ವರ್ತನೆ ಉಳಿಯುತ್ತದೆ. 100–50000 ವ್ಯಾಪ್ತಿಯ ಯಾವುದೇ ಮೌಲ್ಯವು ವಿವರಣೆಯನ್ನು `[Image N]: <description>` ಆಗಿ ಮರಳಿ ಸೇರಿಸುವ ಮೊದಲು `…` suffixನೊಂದಿಗೆ ಮೊಟಕುಗೊಳಿಸುತ್ತದೆ (`src/lib/guardrails/visionBridge.ts`ನಲ್ಲಿನ `VisionBridgeGuardrail.preCall()`). downstream ಮಾದರಿಗೆ ಸಂಪೂರ್ಣ ಲಿಪ್ಯಂತರಣ ಅಗತ್ಯವಿರುವ, ಹೆಚ್ಚು ವಿವರಗಳ OCR ಕಾರ್ಯಗಳಿಗಾಗಿ ಇದನ್ನು ಹೆಚ್ಚಿಸಿ; ಹೆಚ್ಚು ವಿಸ್ತಾರವಾಗಿ ಪ್ರತಿಕ್ರಿಯಿಸುವ vision ಮಾದರಿಗಳ token ಬಳಕೆಯನ್ನು ಮಿತಿಗೊಳಿಸಲು ಇದನ್ನು ಕಡಿಮೆ ಮಾಡಿ. dashboard field, Vision tabನ Advanced panelನಲ್ಲಿ ಇದೆ (`ModalityBridgeVisionTab.tsx`ನಲ್ಲಿನ `modality-bridge-max-chars`) ಮತ್ತು ಸ್ಪಷ್ಟವಾಗಿ ನೀಡಿದ `0` ಅನ್ನು ಬದಲಾಯಿಸದೆ ಉಳಿಸಿ, 1 ಮತ್ತು 99 ನಡುವಿನ ಯಾವುದೇ ಮೌಲ್ಯವನ್ನು ಕನಿಷ್ಠ ಮಿತಿಯಾದ 100ಕ್ಕೆ ಏರಿಸುತ್ತದೆ — `0` ಸ್ವತಃ ಮಾನ್ಯ Zod ಮೌಲ್ಯವಾಗಿದೆ (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), ಅದು ಕೇವಲ "ಹೊಂದಿಸಿಲ್ಲ" ಎಂಬ ಡೀಫಾಲ್ಟ್ ಅಲ್ಲ.

#### ವಿವರಣಾ cache (`modalityBridge/bridgeCache.ts`)

ವಿವರಣಾ ಔಟ್ಪುಟ್ಗಳಿಗಾಗಿ in-memory LRU + TTL cache, processನಾದ್ಯಂತ ಹಂಚಿಕೊಳ್ಳಲಾಗುತ್ತದೆ.  
ಕೀ = `sha256(imageRef + composedPrompt + configuredBridgeModel)`, length-prefix framingನೊಂದಿಗೆ (field-boundary collisionಗಳಿಲ್ಲ). ಮಾದರಿ ಘಟಕವು **configured** bridge model ಆಗಿದೆ, ನಿಜವಾಗಿ ಉತ್ತರಿಸಿದ ಮಾದರಿಯಲ್ಲ — `callVisionModel` ಆಂತರಿಕವಾಗಿ fallback ಮಾಡಬಹುದು ಮತ್ತು ಪ್ರತಿ ಪ್ರಯತ್ನದ ಆಧಾರದಲ್ಲಿ ಕೀ ರಚಿಸುವುದು cache ಅನ್ನು ವಿಭಜಿಸುತ್ತದೆ. ವಿಫಲವಾದ ವಿವರಣೆಗಳನ್ನು ಎಂದಿಗೂ cache ಮಾಡಲಾಗುವುದಿಲ್ಲ. ಸೆಟ್ಟಿಂಗ್ಗಳು:

| ಕೀ                              | ಡೀಫಾಲ್ಟ್ | ವ್ಯಾಪ್ತಿ |
| ------------------------------- | -------- | -------- |
| `modalityBridgeCacheEnabled`    | `true`   | —        |
| `modalityBridgeCacheTtlMinutes` | `60`     | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`    | 10–5000  |

#### Remote image normalization (self-loop ವಿವರಣೆ/base64 fetch)

bridge ಒಂದು **remote** ಚಿತ್ರವನ್ನು ಸ್ವತಃ fetch ಮಾಡಿದಾಗ — Anthropic ವಿವರಣಾ self-call ಮತ್ತು claude-wire-format base64 conversion (`ensureBase64ImagesForClaudeWire`), ಇವೆರಡೂ `visionBridgeHelpers.ts`ನಲ್ಲಿನ `fetchRemoteImageAsDataUri()` ಮೂಲಕ — ಪರಿಣಾಮವಾಗಿ ದೊರೆಯುವ data URI ಅನ್ನು vision-model ವಿನಂತಿಯಲ್ಲಿ embed ಮಾಡುವ ಮೊದಲು `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) ಮೂಲಕ ರವಾನಿಸಲಾಗುತ್ತದೆ. ಮಿತಿಗಿಂತ ದೊಡ್ಡ ಚಿತ್ರಗಳನ್ನು **2048px ಉದ್ದದ ಅಂಚಿಗೆ** downscale ಮಾಡಲಾಗುತ್ತದೆ (OpenAI/Anthropic ಈಗಾಗಲೇ server-sideನಲ್ಲಿ ಅನ್ವಯಿಸುವ resize capಗೆ ಹೊಂದಿಕೆಯಾಗುವಂತೆ); ಇದರಿಂದ vision ಮಾದರಿ ನೋಡುವುದನ್ನು ಬದಲಾಯಿಸದೆ upload bytes/latency ಕಡಿಮೆಯಾಗುತ್ತದೆ. resizingಗಾಗಿ dynamic import ಮೂಲಕ load ಮಾಡಲಾದ `sharp` ಅನ್ನು ಬಳಸಲಾಗುತ್ತದೆ: ಅದರ native binary load ಆಗಲು ವಿಫಲವಾಗುವ platformನಲ್ಲಿ, `normalizeDataUri()` **ಎಂದಿಗೂ throw ಮಾಡುವುದಿಲ್ಲ** — ಅದು ಮೂಲ bytesಗಳನ್ನು ಬದಲಾಯಿಸದೆ passthrough ಮಾಡುವ fallback ಬಳಸುತ್ತದೆ; ಆದ್ದರಿಂದ ವಿವರಣೆ/base64-conversion ಮಾರ್ಗವು ಯಾವಾಗಲೂ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಲೇ ಇರುತ್ತದೆ. image ಅಲ್ಲದ bytesಗಳನ್ನು (decode ಮಾಡಬಹುದಾದ image ಅನ್ನು ಹಿಂತಿರುಗಿಸದ fetch) ಸಹ ಬದಲಾಯಿಸದೆ ರವಾನಿಸಲಾಗುತ್ತದೆ. ಈ normalization, bridge ತನ್ನ ಸ್ವಂತ self-callಗಾಗಿ fetch ಮಾಡುವ ಚಿತ್ರಗಳಿಗೆ ಮಾತ್ರ ಸೀಮಿತವಾಗಿದೆ — callerನ raw passthrough payloadಗೆ ಇದನ್ನು ಎಂದಿಗೂ ಅನ್ವಯಿಸಲಾಗುವುದಿಲ್ಲ; ಇದು opt-in-only mutation ತತ್ವಕ್ಕೆ (Hard Rule #20) ಅನುಗುಣವಾಗಿದೆ.

#### ಸೆಟ್ಟಿಂಗ್ಗಳ schema + migration

   ಸಾಮರ್ಥ್ಯದ ಸಾಕ್ಷ್ಯವಿಲ್ಲದಿದ್ದರೆ `null` ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ. `false` ಮತ್ತು `null` ಎರಡೂ
   ಸಂರಕ್ಷಿತ ಬ್ರಿಡ್ಜ್ ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುತ್ತವೆ, ಆದರೆ `true` ಅದನ್ನು ಬೈಪಾಸ್ ಮಾಡುತ್ತದೆ.
2. `modalityBridgeAudio*` ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಪರಿಹರಿಸಿ ಮತ್ತು ಹಂಚಿಕೆಯ `detectMediaParts()`
   ಡಿಟೆಕ್ಟರ್ ಮೂಲಕ ಪ್ರತಿಯೊಂದು ಸಂದೇಶದಿಂದ ಸ್ಪ್ಲೈಸ್ ಮಾಡಬಹುದಾದ ಉನ್ನತ-ಹಂತದ
   ಆಡಿಯೊ ಭಾಗಗಳನ್ನು ಹೊರತೆಗೆಯಿರಿ. ಬೆಂಬಲಿತ ವೈರ್ ಆಕಾರಗಳು OpenAI `input_audio`, `audio_url`, ಮತ್ತು
   `source.media_type: "audio/*"` ಆಗಿವೆ. ನೆಸ್ಟೆಡ್ ಆಡಿಯೊವನ್ನು ರೂಟಿಂಗ್ಗಾಗಿ ಪತ್ತೆ ಮಾಡಲಾಗುತ್ತದೆ ಆದರೆ
   ಸ್ಪ್ಲೈಸ್ ಮಾರ್ಗದಿಂದ ತೆಗೆದುಹಾಕಲಾಗುವುದಿಲ್ಲ. ಕಾರ್ಯವು `modalityBridgeAudioMaxClips` ಮೂಲಕ ಮಿತಿಗೊಳಿಸಲ್ಪಡುತ್ತದೆ;
   ನಂತರದ ಭಾಗಗಳು ಹಾಗೆಯೇ ಉಳಿಯುತ್ತವೆ.
3. ಸಂರಚಿಸಿದ `provider/model` ಅನ್ನು ಗೌರವಿಸಿ, ಅಥವಾ `selectAudioBridgeModel()` ಗೆ
   `AUDIO_TRANSCRIPTION_PROVIDERS` ಅನ್ನು ಸ್ಥಿರ ಕ್ಯಾಟಲಾಗ್ ಕ್ರಮದಲ್ಲಿ ಪರಿಶೀಲಿಸಿ, ಬಳಸಬಹುದಾದ ಸಕ್ರಿಯ ಪೂರೈಕೆದಾರ
   ಕ್ರೆಡೆನ್ಷಿಯಲ್ ಹೊಂದಿರುವ ಮೊದಲ ಮಾದರಿಯನ್ನು ಆಯ್ಕೆ ಮಾಡಲು ಬಿಡಿ.
4. `callAudioTranscription()` base64/data-URI ಆಡಿಯೊವನ್ನು multipart
   `file` ಆಗಿ ಪರಿವರ್ತಿಸುತ್ತದೆ, ಅಥವಾ DNS ಪಿನ್ನಿಂಗ್ ಮತ್ತು 25 MB ಮಿತಿಯೊಂದಿಗೆ ಸಾರ್ವಜನಿಕ-ಮಾತ್ರ ಔಟ್ಬೌಂಡ್
   ಗಾರ್ಡ್ ಮೂಲಕ ದೂರಸ್ಥ `audio_url` ಅನ್ನು ಡೌನ್ಲೋಡ್ ಮಾಡುತ್ತದೆ. ನಂತರ ಇದು ಫೈಲ್ ಮತ್ತು ಆಯ್ಕೆಮಾಡಿದ
   ಮಾದರಿಯನ್ನು ಸ್ಥಳೀಯ `/v1/audio/transcriptions` ಸ್ವ-ಲೂಪ್ಗೆ POST ಮಾಡುತ್ತದೆ ಮತ್ತು
   `resolveSelfLoopBearer()` ಮೂಲಕ ದೃಢೀಕರಿಸುತ್ತದೆ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಲಿಪ್ಯಂತರ ಮಾರ್ಗವು ಸಾಮಾನ್ಯ
   ಕ್ರೆಡೆನ್ಷಿಯಲ್ ಹುಡುಕಾಟ, ಕೂಲ್ಡೌನ್/ದರ-ಮಿತಿ ನಿರ್ವಹಣೆ ಮತ್ತು ಪೂರೈಕೆದಾರ ಡಿಸ್ಪ್ಯಾಚ್ ಅನ್ನು ನಿರ್ವಹಿಸುತ್ತದೆ.
5. ಯಶಸ್ವಿ ಕರೆಗಳು ಅವುಗಳ ಭಾಗಗಳನ್ನು `[Audio N]: <transcript>` ನಿಂದ ಬದಲಾಯಿಸುತ್ತವೆ. ಕರೆಗಳು
   `Promise.allSettled` ನೊಂದಿಗೆ ಚಲಿಸುತ್ತವೆ: ಪ್ರತ್ಯೇಕ ವೈಫಲ್ಯವು ಮೂಲ
   ಆಡಿಯೊ ಭಾಗವನ್ನು ಉಳಿಸುತ್ತದೆ (#4012 ಒಪ್ಪಂದ). ಪ್ರತಿ ಕರೆಯೂ ವಿಫಲವಾದರೆ ಮತ್ತು ಗುರಿಯು
   `supportsAudio === false` ಎಂದು ಸಾಬೀತಾಗಿದ್ದರೆ, ಭಾಗಗಳು
   `[Audio N]: (unavailable — no STT provider connected)` ಆಗುತ್ತವೆ (#8430 ಒಪ್ಪಂದ). ಅಜ್ಞಾತ
   ಗುರಿಗೆ (`null`), ಎಲ್ಲವೂ-ವಿಫಲವಾದ ಫಲಿತಾಂಶವು ಹಾಗೆಯೇ ಉಳಿಯುತ್ತದೆ. ಬಳಸಬಹುದಾದ STT ಕ್ರೆಡೆನ್ಷಿಯಲ್ ಇಲ್ಲದ,
   ಪಠ್ಯ-ಮಾತ್ರ ಎಂದು ಸಾಬೀತಾದ ಗುರಿಯು ನೆಟ್ವರ್ಕ್ ಕರೆ ನೀಡದೆಯೇ ಅದೇ ಸ್ಪಷ್ಟ
   ಸ್ಟಬ್ ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ.

ಯಶಸ್ವಿ ಲಿಪ್ಯಂತರಗಳು ಪ್ರಕ್ರಿಯೆ-ವ್ಯಾಪಿ Modality Bridge LRU/TTL ಕ್ಯಾಶ್ ಅನ್ನು ಬಳಸುತ್ತವೆ.
ಕೀ ಆಡಿಯೊ ಉಲ್ಲೇಖ, ಸ್ಥಿರ `audio-transcription` ಕಾರ್ಯಾಚರಣೆ
ಲೇಬಲ್ ಮತ್ತು ಆಯ್ಕೆಮಾಡಿದ STT ಮಾದರಿಯನ್ನು ಸಂಯೋಜಿಸುತ್ತದೆ; ವೈಫಲ್ಯಗಳನ್ನು ಎಂದಿಗೂ ಕ್ಯಾಶ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ. ಆಡಿಯೊ ಪ್ರಯತ್ನಗಳು
ಹಂಚಿಕೆಯ `bridged`, `cacheHits`, `failures`, ಮತ್ತು `lastUsedAt` ಕೌಂಟರ್ಗಳನ್ನು ನವೀಕರಿಸುತ್ತವೆ.
ರೂಪಾಂತರಗೊಂಡ ಪ್ರತಿಕ್ರಿಯೆಗಳು
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ಅನ್ನು ಹೊಂದಿರುತ್ತವೆ; ಬದಲಾಗದ
ವಿನಂತಿಗಳು Audio Bridge ವಿಭಾಗವನ್ನು ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ.

ರನ್ಟೈಮ್ ಸೆಟ್ಟಿಂಗ್ಗಳು DB-ಆಧಾರಿತವಾಗಿದ್ದು Zod ಮೂಲಕ ಮೌಲ್ಯೀಕರಿಸಲ್ಪಡುತ್ತವೆ:

| ಕೀ                            | ಡೀಫಾಲ್ಟ್ | ವ್ಯಾಪ್ತಿ          |
| ----------------------------- | -------- | ----------------- |
| `modalityBridgeAudioEnabled`  | `true`   | —                 |
| `modalityBridgeAudioModel`    | `""`     | ಸ್ವಯಂ ಅಥವಾ STT ID |
| `modalityBridgeAudioTimeout`  | `60000`  | 1000–300000       |
| `modalityBridgeAudioMaxClips` | `3`      | 1–10              |

ಹಂಚಿಕೆಯ ಕ್ಯಾಶ್ ಅನ್ನು `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, ಮತ್ತು `modalityBridgeCacheMaxEntries` ನಿಯಂತ್ರಿಸುತ್ತವೆ.

### ವೀಡಿಯೊ ಬ್ರಿಡ್ಜ್ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ತಿಳಿದಿರುವ ಮೂಲ ವೀಡಿಯೊ ಬೆಂಬಲವಿಲ್ಲದ ಗುರಿಯನ್ನು ಕರೆಯುವ ಮೊದಲು, Chat Completions
`messages` ಮತ್ತು Responses API `input` ನಲ್ಲಿರುವ ಉನ್ನತ-ಹಂತದ ವೀಡಿಯೊ ಭಾಗಗಳನ್ನು
ತಡೆಹಿಡಿಯುತ್ತದೆ. ಬೆಂಬಲಿತ ಆಕಾರಗಳು `input_video`, `video_url`, `video_source`, HTTPS URLಗಳು,
ಮತ್ತು `data:video/*;base64,...` ಡೇಟಾ URIಗಳು. ಪಠ್ಯದಲ್ಲಿರುವ ಸರಳ ಫೈಲ್ ಹೆಸರುಗಳನ್ನು
ವೀಡಿಯೊ ಎಂದು ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) ವಿನಂತಿಯ ಟ್ರಾವರ್ಸಲ್,
ಸಾಮರ್ಥ್ಯ/ನೀತಿ ಪರಿಶೀಲನೆ, ಪ್ರತಿ-ವಿನಂತಿಯ ಒಟ್ಟುಗೂಡಿಸುವಿಕೆ, ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆ ಪೇಲೋಡ್ ಅನ್ನು
ನಿರ್ವಹಿಸುತ್ತದೆ. ಪ್ರತಿ-ವೀಡಿಯೊ ಕೆಲಸ — ಸ್ವಾಧೀನಪಡಿಸುವಿಕೆ, ಸಂಪೂರ್ಣ-ಫಲಿತಾಂಶದ ಕ್ಯಾಶ್,
ಫ್ರೇಮ್ ಅನುಕ್ರಮವನ್ನು ವಿವರಿಸುವುದು (ಇದು ಕರೆ ಮಾಡುವವರು ಘೋಷಿಸಿದ ಯಾವುದೇ ಆಡಿಯೊ ಪ್ರತಿಲಿಪಿಯನ್ನು
ಸಂಯೋಜಿಸುತ್ತದೆ), ಮತ್ತು ಪ್ರತಿ-ಪ್ರಯತ್ನದ ಮೆಟ್ರಿಕ್ಗಳು/ಸ್ಥಗಿತಗೊಳಿಸುವಿಕೆ/ಸ್ವಚ್ಛಗೊಳಿಸುವಿಕೆ — ಇವುಗಳನ್ನು
`videoBridgePipeline.ts` ನಲ್ಲಿನ `processVideoPart` ಹಿಂದೆ ಮರೆಮಾಡಲಾಗಿದೆ ಮತ್ತು
`preCall` ಲೂಪ್ನೊಳಗೆ ಪ್ರತಿ ವೀಡಿಯೊ ಭಾಗಕ್ಕೆ ಒಮ್ಮೆ ಕರೆಯಲಾಗುತ್ತದೆ.
ಆ ಮಾಡ್ಯೂಲ್ ಸ್ಪಷ್ಟವಾದ ಪೋರ್ಟ್ ಗಡಿಗಳಾದ `VideoMediaBrokerPort`
(ಬೈಟ್ಗಳನ್ನು ಸ್ವಾಧೀನಪಡಿಸುವುದು ಮತ್ತು ಮಾದರಿಗೊಳಿಸಿದ ಫ್ರೇಮ್ಗಳನ್ನು ಹೊರತೆಗೆಯುವುದು), `VideoAudioTranscriptionPort`
(ಕರೆ ಮಾಡುವವರು ಘೋಷಿಸಿದ ಆಡಿಯೊ ಪ್ರತಿಲಿಪಿಯನ್ನು ಮಾದರಿಗೊಳಿಸಿದ ಶೀರ್ಷಿಕೆಗಳೊಂದಿಗೆ ಸಂಯೋಜಿಸುವುದು), ಮತ್ತು
`VideoDrilldownPort` (ಫ್ರೇಮ್ ಡ್ರಿಲ್-ಡೌನ್ ಸ್ಥಿರತೆಯ ಗಡಿ; ಇದನ್ನು ಇನ್ನೂ
`processVideoPart` ಗೆ ಸಂಪರ್ಕಿಸಲಾಗಿಲ್ಲ — ಇಂದು ಪ್ರತ್ಯೇಕ `/api/modality-bridge/video/drilldown`
ಮಾರ್ಗ ಮಾತ್ರ ಡ್ರಿಲ್-ಡೌನ್ ನಮೂದುಗಳನ್ನು ಬರೆಯುತ್ತದೆ) ಇವುಗಳನ್ನೂ ವ್ಯಾಖ್ಯಾನಿಸುತ್ತದೆ.

ಸಾರ್ವಜನಿಕ `/v1` ವಿನಂತಿ ಪಥವು ಎಂದಿಗೂ ಉಪಪ್ರಕ್ರಿಯೆಯನ್ನು ಆಮದು ಮಾಡುವುದಿಲ್ಲ ಅಥವಾ ಆಹ್ವಾನಿಸುವುದಿಲ್ಲ.
ದೂರಸ್ಥ ವೀಡಿಯೊಗಳನ್ನು 50 MiB ಮಿತಿಯೊಳಗೆ ಡೌನ್ಲೋಡ್ ಮಾಡಲಾಗುತ್ತದೆ; ಸಾರ್ವಜನಿಕ JSON ವಿನಂತಿಯ
50 MiB ಪ್ರವೇಶ ಮಿತಿಯೊಳಗೆ ಮಾದರಿ/ಸಂದೇಶಗಳು/ಫ್ರೇಮಿಂಗ್ ಎನ್ವಲಪ್ ಉಳಿಯಲು, ಇನ್ಲೈನ್
base64 ವೀಡಿಯೊಗಳಿಗೆ ಪ್ರತಿ ವೀಡಿಯೊಗೆ ಸಂಯಮಿತ 36 MiB ಡಿಕೋಡ್ ಮಾಡಿದ ಗರಿಷ್ಠ ಮಿತಿ ಇದೆ.
ಹಂಚಿಕೆಗೂ ಮೊದಲು ಇನ್ಲೈನ್ ಉದ್ದ ಮತ್ತು ಡಿಕೋಡ್ ಮಾಡಿದ ಗಾತ್ರದ ಅಂದಾಜುಗಳನ್ನು ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ.
ಆರಂಭಿಕ ದೂರಸ್ಥ URL ಮತ್ತು ಪ್ರತಿ ಮರುನಿರ್ದೇಶನದಲ್ಲಿ HTTPS ಅಗತ್ಯವಿದ್ದು, DNS ಪಿನ್ನಿಂಗ್ ಹೊಂದಿರುವ
ಈಗಿರುವ ಸಾರ್ವಜನಿಕ-ಮಾತ್ರ ಔಟ್ಬೌಂಡ್ ಗಾರ್ಡ್ ಅನ್ನು ಬಳಸಲಾಗುತ್ತದೆ. ನಂತರ ಬೈಟ್ಗಳು ನಿಖರವಾದ ಆಂತರಿಕ
`POST /api/modality-bridge/video/extract` ಬ್ರೋಕರ್ ಗಡಿಯನ್ನು ದಾಟುತ್ತವೆ. ಆ ಮಾರ್ಗವು
`LOCAL_ONLY` ಮತ್ತು `SPAWN_CAPABLE` ಎರಡೂ ಆಗಿದ್ದು, ಪ್ರತಿ-ಪ್ರಕ್ರಿಯೆಗೆ ದೃಢೀಕರಿಸಲಾದ,
ವಿಶ್ವಾಸಾರ್ಹ-ಲೂಪ್ಬ್ಯಾಕ್ ವಿನಂತಿಗಳನ್ನು ಮಾತ್ರ ಸ್ವೀಕರಿಸುತ್ತದೆ ಮತ್ತು URL, ಫೈಲ್ಸಿಸ್ಟಂ ಪಥ, ಎಕ್ಸಿಕ್ಯೂಟೇಬಲ್,
ಅಥವಾ ಆರ್ಗ್ಯುಮೆಂಟ್ ಪಟ್ಟಿಯನ್ನು ಎಂದಿಗೂ ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ. API ಬಾಡಿ-ಗಾತ್ರ ಪೈಪ್ಲೈನ್ ಮತ್ತು ಹ್ಯಾಂಡ್ಲರ್ನ
ವೃದ್ಧಿಶೀಲ ಬಾಡಿ ರೀಡರ್ ಸ್ವತಂತ್ರವಾಗಿ 50 MiB ಬ್ರೋಕರ್ ಇನ್ಪುಟ್ ಮಿತಿಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ.
ಅದರ ಮಿತಿಗೊಳಿಸಿದ ಕ್ಯೂ ಒಂದು ಸಮಯದಲ್ಲಿ ಒಂದು ಹೊರತೆಗೆಯುವಿಕೆಯನ್ನು ನಡೆಸುತ್ತದೆ, ಬಾಕಿಯಿರುವ ನಾಲ್ಕು
ಕೆಲಸಗಳಿಗೆ ಅವಕಾಶ ನೀಡುತ್ತದೆ, ಮತ್ತು ಬಾಕಿಯಿರುವ ಇನ್ಪುಟ್ ಅನ್ನು 100 MiB ಗೆ ಮಿತಿಗೊಳಿಸುತ್ತದೆ.

ಬ್ರೋಕರ್ನೊಳಗೆ, `ffprobe` ಖಾಸಗಿ ಸ್ಥಳೀಯ ಫೈಲ್ ಅನ್ನು ಓದುತ್ತದೆ; ಸ್ಥಿರ ಫಾರ್ಮ್ಯಾಟ್
ಅನುಮತಿ ಪಟ್ಟಿಯು ಪ್ಲೇಲಿಸ್ಟ್ ಮತ್ತು ಮ್ಯಾನಿಫೆಸ್ಟ್ ಫಾರ್ಮ್ಯಾಟ್ಗಳನ್ನು ಹೊರತುಪಡಿಸುತ್ತದೆ. ಅನುಮತಿಸಲಾದ
MOV-ಕುಟುಂಬದ ಕಂಟೇನರ್ಗಳಿಗೆ, ಬಾಹ್ಯ MOV ಡೇಟಾ ಉಲ್ಲೇಖಗಳು ಡೀಫಾಲ್ಟ್ ಆಗಿ ನಿಷ್ಕ್ರಿಯವಾಗಿರುತ್ತವೆ,
ಮತ್ತು ಸ್ಥಿರ ಕಮಾಂಡ್ ಅವುಗಳನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುವುದಿಲ್ಲ. `ffprobe` ಮತ್ತು `ffmpeg` ಎರಡೂ
`file`-ಮಾತ್ರದ ಪ್ರೋಟೋಕಾಲ್ ಅನುಮತಿ ಪಟ್ಟಿ, ಒಂದು ಥ್ರೆಡ್, ಸ್ಥಿರ ಆರ್ಗ್ಯುಮೆಂಟ್ ಅರೆಗಳು, ಶೆಲ್ ಇಲ್ಲದೆ,
ಮತ್ತು `PATH` ನಿಂದ ಪರಿಹರಿಸಲಾದ ಎಕ್ಸಿಕ್ಯೂಟೇಬಲ್ಗಳನ್ನು ಬಳಸುತ್ತವೆ. ಲಗತ್ತಿಸಿದ-ಚಿತ್ರದ ಕವರ್ ಸ್ಟ್ರೀಮ್ಗಳು
ಪ್ಲೇ ಮಾಡಬಹುದಾದ ಅಭ್ಯರ್ಥಿಗಳಲ್ಲ. ಪ್ಲೇ ಮಾಡಬಹುದಾದ ಎಲ್ಲ ಸ್ಟ್ರೀಮ್ಗಳು ಮಿತಿಗಳನ್ನು ಪೂರೈಸಬೇಕು, ಮತ್ತು
ನಿರ್ಣಾಯಕ ಅತಿ-ಕಡಿಮೆ-ಸೂಚ್ಯಂಕದ ಪರ್ಯಾಯಕ್ಕೂ ಮೊದಲು ಸ್ಪಷ್ಟ ಡೀಫಾಲ್ಟ್ ಸ್ಟ್ರೀಮ್ಗೆ ಆದ್ಯತೆ ನೀಡಲಾಗುತ್ತದೆ.
ವೀಡಿಯೊಗಳನ್ನು 600 ಸೆಕೆಂಡುಗಳು, ಪ್ರತಿ ಆಯಾಮಕ್ಕೆ 8,192 ಪಿಕ್ಸೆಲ್ಗಳು, ಮತ್ತು
33,554,432 ಮೂಲ ಪಿಕ್ಸೆಲ್ಗಳಿಗೆ ಮಿತಿಗೊಳಿಸಲಾಗಿದೆ. FFmpeg 1–16 ಮಧ್ಯಬಿಂದು JPEG ಫ್ರೇಮ್ಗಳನ್ನು
ಮಾದರಿಗೊಳಿಸುತ್ತದೆ, ಚಿಕ್ಕ ಇನ್ಪುಟ್ಗಳನ್ನು ಮೇಲ್ಮಟ್ಟಕ್ಕೆ ಸ್ಕೇಲ್ ಮಾಡದೆ ಉದ್ದನೆಯ ಅಂಚನ್ನು ಗರಿಷ್ಠ
1,024 ಪಿಕ್ಸೆಲ್ಗಳಿಗೆ ಇಳಿಸುತ್ತದೆ, ಮತ್ತು ಎಂದಿಗೂ URL ಅನ್ನು ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ. ಮಾದರಿಗೊಳಿಸುವಿಕೆಯು
ಡೀಫಾಲ್ಟ್ ಆಗಿ `uniform` ಆಗಿರುತ್ತದೆ. ಐಚ್ಛಿಕ `scene_aware` ಮತ್ತು ಪ್ರಾಯೋಗಿಕ
`segment_aware` ನೀತಿಗಳು ಈಗಾಗಲೇ ಮೌಲ್ಯೀಕರಿಸಿದ ಸ್ಥಳೀಯ ಸ್ಟ್ರೀಮ್ ಮೇಲೆ ಒಂದು ಹೆಚ್ಚುವರಿ ಸ್ಥಿರ
FFmpeg ಪಾಸ್ ಅನ್ನು ನಿರ್ವಹಿಸುತ್ತವೆ, ಮಿತಿಗೊಳಿಸಿದ `showinfo` ದೃಶ್ಯ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ಗಳನ್ನು
ಆಯ್ಕೆಮಾಡುತ್ತವೆ, ಮತ್ತು ಡಿಟೆಕ್ಟರ್ ವೈಫಲ್ಯ, ಸಮಯ ಮೀರಿಕೆ, ದೋಷಪೂರಿತ ಔಟ್ಪುಟ್, ಅಥವಾ ಖಾಲಿ
ಅಭ್ಯರ್ಥಿ ಸಮೂಹದ ಸಂದರ್ಭದಲ್ಲಿ ನಿರ್ಣಾಯಕವಾಗಿ ಅದೇ ಸಮಾನ ಮಧ್ಯಬಿಂದುಗಳಿಗೆ ಹಿಂತಿರುಗುತ್ತವೆ.
ಸೆಗ್ಮೆಂಟ್-ಅವೇರ್ ಮೋಡ್ ಮೌಲ್ಯೀಕರಿಸಿದ ದೃಶ್ಯ ಮಧ್ಯಂತರಗಳಿಗೆ ಅನುಪಾತದಲ್ಲಿ ಮಧ್ಯಬಿಂದು ಮಾದರಿಗಳನ್ನು
ಹಂಚುತ್ತದೆ; ಸೆಗ್ಮೆಂಟ್-ಅವೇರ್ ಸಾಕ್ಷ್ಯ ಮತ್ತು ಪರ್ಯಾಯ ವರ್ತನೆಯನ್ನು ಕೆಳಗೆ ವಿವರಿಸಲಾಗಿದೆ.
ಪ್ರತಿ ನೀತಿಯಲ್ಲಿಯೂ ಆಯ್ಕೆಯ ನಂತರ ಕಠಿಣ 16-ಫ್ರೇಮ್ ಮಿತಿಯನ್ನು
ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ. ಸೀನ್-ಅವೇರ್ ವಿನಂತಿಯು ಕೇವಲ ಒಂದು-ಫ್ರೇಮ್ ಬಜೆಟ್ ಹೊಂದಿದ್ದಾಗ, ಅದು ಸಕ್ರಿಯ
ಪೂರ್ಣ-ವೀಡಿಯೊ ಅಥವಾ ಫೋಕಸ್ ವಿಂಡೋದ ಸಮಾನ ಮಧ್ಯಬಿಂದುವನ್ನು ಬಳಸುತ್ತದೆ ಮತ್ತು
`policyEffective: uniform` ಎಂದು ವರದಿ ಮಾಡುತ್ತದೆ: ಆಯ್ಕೆಮಾಡಿದ ಒಂದೇ ದೃಶ್ಯ ಫ್ರೇಮ್
ಎರಡೂ ಕಾಲಿಕ ತುದಿಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳಲು ಸಾಧ್ಯವಿಲ್ಲ. ಕರೆ ಮಾಡುವವರು ಐಚ್ಛಿಕವಾಗಿ ಸೀಮಿತ
ಫೋಕಸ್ ವಿಂಡೋವನ್ನು (`start`/`end` ಸೆಕೆಂಡುಗಳು) ಒದಗಿಸಬಹುದು; ಗಡಿಗಳನ್ನು ಮಾಧ್ಯಮದ
ಅವಧಿಗೆ ಕ್ಲ್ಯಾಂಪ್ ಮಾಡಲಾಗುತ್ತದೆ, ಹಿಮ್ಮುಖವಾದ ಅಥವಾ ಸೀಮಿತವಲ್ಲದ ವಿಂಡೋಗಳನ್ನು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ,
ಮತ್ತು ಎಲ್ಲಾ ಮಾದರಿಗೊಳಿಸುವ ನೀತಿಗಳನ್ನು ಸಾಮಾನ್ಯೀಕರಿಸಿದ ಮಧ್ಯಂತರದೊಳಗೆ ಮಾತ್ರ ನಿರ್ವಹಿಸಲಾಗುತ್ತದೆ.
ಫಲಿತಾಂಶದ ವಿಂಡೋವನ್ನು ಮಾದರಿಗೊಳಿಸುವಿಕೆ ಮೆಟಾಡೇಟಾದಲ್ಲಿ ಮತ್ತು ವಿಶ್ವಾಸಾರ್ಹವಲ್ಲದ ವಿವರಣೆಯ
ಪೂರ್ವಪ್ರತ್ಯಯದಲ್ಲಿ ಸೇರಿಸಲಾಗುತ್ತದೆ, ಇದರಿಂದ ಡೌನ್ಸ್ಟ್ರೀಮ್ ಮಾದರಿಗಳು ಕೇಂದ್ರೀಕೃತ ಆಯ್ದ ಭಾಗವನ್ನು
ಪೂರ್ಣ ಕಾಲರೇಖೆಯಿಂದ ಪ್ರತ್ಯೇಕಿಸಬಹುದು.

ಅರ್ಥಸಂಬಂಧಿತ ಶೀರ್ಷಿಕೆ ಫೋಕಸ್ ಒಂದು ಪ್ರತ್ಯೇಕ, ಸ್ಪಷ್ಟ ಸೆಟ್ಟಿಂಗ್ ಆಗಿದೆ. ಡೀಫಾಲ್ಟ್ `full`
ವಿಶ್ಲೇಷಣಾ ಮೋಡ್ ಈಗಿರುವ ಫ್ರೇಮ್ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ಉಳಿಸುತ್ತದೆ ಮತ್ತು ವಿನಂತಿಯ ಪಠ್ಯವನ್ನು ಕ್ಯಾಪ್ಷನ್
ಮಾದರಿಗೆ ಎಂದಿಗೂ ಫಾರ್ವರ್ಡ್ ಮಾಡುವುದಿಲ್ಲ. `focused` ಮೋಡ್ನಲ್ಲಿ, ಬ್ರಿಡ್ಜ್ ಅದೇ Chat ಅಥವಾ
Responses ಕಂಟೇನರ್ನಿಂದ ಬಳಕೆದಾರರು ರಚಿಸಿದ ಇತ್ತೀಚಿನ ಖಾಲಿಯಲ್ಲದ `text`/`input_text` ಅನ್ನು
ಮಾತ್ರ ಓದುತ್ತದೆ, ಅದನ್ನು NFC ಗೆ ಸಾಮಾನ್ಯೀಕರಿಸುತ್ತದೆ, ನಿಯಂತ್ರಣ ಅಕ್ಷರಗಳು ಮತ್ತು ಖಾಲಿ ಜಾಗವನ್ನು
ಸಂಕುಚಿಸುತ್ತದೆ, ಮತ್ತು ಅದನ್ನು 500 Unicode ಕೋಡ್ ಪಾಯಿಂಟ್ಗಳಿಗೆ ಮಿತಿಗೊಳಿಸುತ್ತದೆ. ಖಾಲಿ ಫಲಿತಾಂಶವು
ನಿಖರವಾದ `full` ಪ್ರಾಂಪ್ಟ್ಗೆ ಹಿಂತಿರುಗುತ್ತದೆ. ಬಳಸಬಹುದಾದ ಸೂಚನೆಯನ್ನು ಮೀಸಲಾದ
ವಿಶ್ವಾಸಾರ್ಹವಲ್ಲದ-ಬಳಕೆದಾರ-ಸಂದರ್ಭ ಬ್ಲಾಕ್ನಲ್ಲಿ JSON ಆಗಿ ಸೀರಿಯಲೈಸ್ ಮಾಡಲಾಗುತ್ತದೆ ಮತ್ತು ಅದು
ಗಮನಿಸಬಹುದಾದ ವಿವರಗಳಿಗೆ ಮಾತ್ರ ಆದ್ಯತೆ ನೀಡಬಹುದು; ಮಾಧ್ಯಮದಲ್ಲಿ ಕಾಣುವ ಅಥವಾ ಕೇಳಿಸುವ ಸೂಚನೆಗಳನ್ನು
ಅನುಸರಿಸಬಾರದೆಂಬ ಪ್ರತ್ಯೇಕ ಎಚ್ಚರಿಕೆಯನ್ನು ಅದು ಅತಿಕ್ರಮಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಪಠ್ಯಾತ್ಮಕ ಫೋಕಸ್ ಎಂದಿಗೂ
`start`/`end` ಅನ್ನು ಊಹಿಸುವುದಿಲ್ಲ ಅಥವಾ ಕಾಲಿಕ ಸ್ಯಾಂಪ್ಲರ್ ಅನ್ನು ಬದಲಾಯಿಸುವುದಿಲ್ಲ.

#### FU-07 ರಚನಾತ್ಮಕ ಸೆಗ್ಮೆಂಟ್ ಸಾಕ್ಷ್ಯ

`segment_aware` ಈಗಾಗಲೇ ಮೌಲ್ಯೀಕರಿಸಲಾದ ಸ್ಥಳೀಯ ವೀಡಿಯೊ ಸ್ಟ್ರೀಮ್ನ ಮೇಲೆ ಒಂದು
ಮಿತಿಗೊಳಿಸಲಾದ ಪೂರ್ವ-ವಿಶ್ಲೇಷಣಾ ಪಾಸ್ ಅನ್ನು ಬಳಸುತ್ತದೆ. ಸ್ಥಿರ ಫಿಲ್ಟರ್ ಸರಪಳಿಯು ಮೊದಲು
ಅಗಲವನ್ನು ಗರಿಷ್ಠ 320 ಪಿಕ್ಸೆಲ್ಗಳಿಗೆ ಸ್ಕೇಲ್ ಮಾಡುತ್ತದೆ, ದೃಶ್ಯ ಬದಲಾವಣೆಗಳು ಮತ್ತು
ಸ್ಥಗಿತಗೊಂಡ ಮಧ್ಯಂತರಗಳನ್ನು ಪತ್ತೆಹಚ್ಚುತ್ತದೆ, ನಂತರ ಮಸುಕು, ಸರಾಸರಿ ಲ್ಯೂಮಾ ಮತ್ತು
ಪ್ರಾದೇಶಿಕ/ಕಾಲಿಕ ಮಾಹಿತಿಗಾಗಿ ಪ್ರತಿ ಸೆಕೆಂಡಿಗೆ 1 ಫ್ರೇಮ್ನಂತೆ ಸ್ಯಾಂಪಲ್ ಮಾಡುತ್ತದೆ.
ಈ ಪಾಸ್ 600 ರಚನಾತ್ಮಕ ಸ್ಯಾಂಪಲ್ಗಳು, ಒಂದು FFmpeg/ಫಿಲ್ಟರ್ ಥ್ರೆಡ್, ಅದೇ
`file`-ಮಾತ್ರದ ಪ್ರೋಟೋಕಾಲ್ ಮತ್ತು ಕಂಟೇನರ್ ಅನುಮತಿ ಪಟ್ಟಿಗಳು, 1 MiB ಪ್ರಕ್ರಿಯೆ-ಔಟ್ಪುಟ್
ಮಿತಿ ಹಾಗೂ ಬ್ರೋಕರ್ನ ಹಂಚಿಕೆಯ ರದ್ದತಿ/ಗಡುವಿನೊಳಗಿನ ಗರಿಷ್ಠ 30 ಸೆಕೆಂಡುಗಳಿಗೆ
ಸೀಮಿತವಾಗಿದೆ. ಇದು ವಿನಂತಿಯಿಂದ ಯಾವುದೇ ಕಮಾಂಡ್, ಫಿಲ್ಟರ್, ಪಥ ಅಥವಾ URL ಅನ್ನು
ಎಂದಿಗೂ ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ.

ರಚನಾತ್ಮಕ ಮೌಲ್ಯಗಳು ನಿರ್ಧಾರಾತ್ಮಕ ಸ್ಯಾಂಪ್ಲಿಂಗ್ ಸಾಕ್ಷ್ಯವಾಗಿದ್ದು, ಅರ್ಥಾಧಾರಿತ ವೀಡಿಯೊ
ಗ್ರಹಿಕೆಯಲ್ಲ. ಅವು ವಿಷಯಗಳು, ಕ್ರಿಯೆಗಳು, ಶೀರ್ಷಿಕೆಗಳು, ಮಾತು ಅಥವಾ ಬಳಕೆದಾರರ
ಉದ್ದೇಶವನ್ನು ಊಹಿಸುವುದಿಲ್ಲ. ದೃಶ್ಯ ಮತ್ತು ಸ್ಥಗಿತ ಗಡಿಗಳು ಸೆಗ್ಮೆಂಟ್ಗಳನ್ನು ರೂಪಿಸುತ್ತವೆ;
ಸ್ಥಗಿತ ವ್ಯಾಪ್ತಿ, ಮಸುಕು, ಎಕ್ಸ್ಪೋಷರ್, ಪ್ರಾದೇಶಿಕ ವಿವರ ಮತ್ತು ಕಾಲಿಕ ಬದಲಾವಣೆಗಳು
ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ 1–16 ಫ್ರೇಮ್ ಬಜೆಟ್ ಅನ್ನು ಹೇಗೆ ಹಂಚಲಾಗುತ್ತದೆ ಎಂಬುದರ ಮೇಲೆ ಮಾತ್ರ
ಪ್ರಭಾವ ಬೀರುತ್ತವೆ. ಸಂಪೂರ್ಣವಾಗಿ ಸ್ಥಗಿತಗೊಂಡ ಸೆಗ್ಮೆಂಟ್ ಅನ್ನು ಒಂದು ಫ್ರೇಮ್ಗೆ
ಮಿತಿಗೊಳಿಸಲಾಗುತ್ತದೆ, ಆದರೆ ಸ್ಥಗಿತಗೊಳ್ಳದ ಸೆಗ್ಮೆಂಟ್ಗಳು ಉಳಿದ ಬಜೆಟ್ಗಾಗಿ
ಸ್ಪರ್ಧಿಸುತ್ತವೆ. ಗಡಿಗಳ ಸಂಖ್ಯೆ ಫ್ರೇಮ್ಗಳಿಗಿಂತ ಹೆಚ್ಚಾದಾಗ, ಆರಂಭದಲ್ಲಿನ ವೇಗದ ಕಟ್ಗಳು
ಉದ್ದವಾದ ಕೊನೆಯ ಸೆಗ್ಮೆಂಟ್ ಅನ್ನು ಮರೆಮಾಡದಂತೆ ಏಕರೂಪ ಟೈಮ್ಲೈನ್ ವ್ಯಾಪ್ತಿಯನ್ನು
ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ. ಸ್ಥಗಿತ ಗಡಿಯ 1-ಸೆಕೆಂಡ್ ವಿಶ್ಲೇಷಣಾ ರೆಸಲ್ಯೂಷನ್ನೊಳಗಿನ ದೃಶ್ಯ

ಒಬ್ಬ ಸುಧಾರಿತ ಕಾಲರ್ ಅದೇ ವೀಡಿಯೊಗಾಗಿ ಈಗಾಗಲೇ-ಅಧಿಕೃತಗೊಂಡಿರುವ `audioTranscript` ಟ್ರ್ಯಾಕ್ ಅನ್ನು ಒದಗಿಸಬಹುದು. ಫ್ಯೂಷನ್ ಸೀಮ್ ದೃಶ್ಯ ಮತ್ತು ಆಡಿಯೊ ಅವಲೋಕನಗಳನ್ನು ಒಂದೇ ಗಡುವು ಹಾಗೂ ಸ್ಥಗಿತ ಸಂಕೇತದ ಅಡಿಯಲ್ಲಿ ಚಲಾಯಿಸುತ್ತದೆ, ಅವುಗಳನ್ನು ಸಾಮಾನ್ಯ ಕಾಲರೇಖೆಯಲ್ಲಿ ಕ್ರಮಗೊಳಿಸುತ್ತದೆ, ಸಂಪೂರ್ಣವಾಗಿ ಒಂದೇ ಆಗಿರುವ ನಕಲುಗಳನ್ನು ಸಂಕುಚಿತಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಕೇವಲ ಒಂದು ಭಾಗ ಯಶಸ್ವಿಯಾದಾಗ ಭಾಗಶಃ ಫಲಿತಾಂಶವನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ. ಅಮಾನ್ಯವಾದ `audioTranscript`, ಸಂಪೂರ್ಣ ವೀಡಿಯೊ ವಿಫಲವಾಗುವಂತೆ ಮಾಡುವ ಬದಲು, ಆ ಭಾಗಶಃ ಫಲಿತಾಂಶಕ್ಕೆ ಇಳಿಮುಖವಾಗುತ್ತದೆ — ದೃಶ್ಯ ವಿವರಣೆಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ ಮತ್ತು ಆಡಿಯೊ ಶಾಖೆಯು ಸ್ವಚ್ಛಗೊಳಿಸಿದ ವೈಫಲ್ಯ ಕೋಡ್ ಅನ್ನು ದಾಖಲಿಸುತ್ತದೆ. ಪ್ರತಿ ಶಾಖೆಯ ಲಭ್ಯತೆ, ಭಾಗಶಃ ಫ್ಲ್ಯಾಗ್ ಮತ್ತು ಸ್ವಚ್ಛಗೊಳಿಸಿದ ವೈಫಲ್ಯ ಕೋಡ್ಗಳನ್ನು ವಿವರಿಸಲಾದ ಫಲಿತಾಂಶದಲ್ಲಿ, ಗಾರ್ಡ್ರೇಲ್ ಮೆಟಾಡೇಟಾದಲ್ಲಿ (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), ಫಲಿತಾಂಶ-ಕ್ಯಾಶ್ ಮೆಟಾಡೇಟಾದಲ್ಲಿ ಮತ್ತು ಬ್ರಿಡ್ಜ್ ಫ್ಯೂಷನ್ ಕೌಂಟರ್ಗಳಲ್ಲಿ ಸಂರಕ್ಷಿಸಲಾಗುತ್ತದೆ. ಡೀಫಾಲ್ಟ್ Video Bridge ಮಾರ್ಗವು ಸ್ಪೀಚ್-ಟು-ಟೆಕ್ಸ್ಟ್ ಅನ್ನು ಆಹ್ವಾನಿಸುವುದಿಲ್ಲ ಅಥವಾ ಎರಡನೇ ಮೀಡಿಯಾ ಪ್ರತಿಯನ್ನು ಡೌನ್ಲೋಡ್ ಮಾಡುವುದಿಲ್ಲ; ಆ ಸ್ಪಷ್ಟ ಟ್ರ್ಯಾಕ್ ಇಲ್ಲದೆ, ಅದು ವೀಡಿಯೊ-ಮಾತ್ರವಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ.

**ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ ಸಂರಕ್ಷಣೆ (#12150 P1).** Video Bridge (ಇದೇ ಆಯ್ಕೆಮಾಡಿ ಸಕ್ರಿಯಗೊಳಿಸಬೇಕಾದದ್ದು) ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ ಕ್ಯೂ ಅನ್ನು ರೆಂಡರ್ ಮಾಡುವಾಗಲೆಲ್ಲ ಇದು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಅನ್ವಯಿಸುತ್ತದೆ — ಪ್ರತ್ಯೇಕ ಸಂರಕ್ಷಣೆ ಫ್ಲ್ಯಾಗ್ ಇಲ್ಲ. ವಿನಂತಿಯೊಂದು ಯಾವುದೇ ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ ಕ್ಯೂ ಅನ್ನು (ಕಾಲರ್ ಘೋಷಿಸಿದ `transcript` ಅಥವಾ ಫ್ಯೂಸ್ ಮಾಡಿದ `audioTranscript`) ರೆಂಡರ್ ಮಾಡಿದಾಗ, ಗಾರ್ಡ್ರೇಲ್ ಅದನ್ನು `videoBridgeObserved` ಎಂದು ಗುರುತಿಸಿ ವೀಡಿಯೊ ವಿವರಣೆಯ ಪರಿಷ್ಕರಿಸಿದ ನೆರಳು-ಪ್ರತಿಯನ್ನು ರಚಿಸುತ್ತದೆ — ಪ್ರತಿ ಕ್ಯೂನ ಮುಕ್ತ-ಪಠ್ಯ ಭಾಗವನ್ನು `[redacted-video-transcript]` ನಿಂದ ಬದಲಿಸಿರುವ ಒಂದೇ ರೀತಿಯ ರೆಂಡರಿಂಗ್; ಸ್ಟ್ರಿಂಗ್ ಅನ್ನು ಜೋಡಿಸುವ ಮೊದಲು ರಚನಾತ್ಮಕ ಕ್ಯೂ ಫೀಲ್ಡ್ ಅನ್ನು ಬದಲಿಸುವ ಮೂಲಕ ಇದನ್ನು ನಿರ್ಮಿಸಲಾಗುತ್ತದೆ (ಸಮತಟ್ಟುಗೊಳಿಸಿದ ಪಠ್ಯವನ್ನು ಪಾರ್ಸ್ ಮಾಡುವ ಮೂಲಕ ಎಂದಿಗೂ ಅಲ್ಲ; ಆದ್ದರಿಂದ `]` ಹೊಂದಿರುವ `[inaudible]`/`[music]` ರೀತಿಯ ಭಾಗಗಳನ್ನು ಒಳಗೊಂಡಂತೆ, ವಿರೋಧಾತ್ಮಕವಾಗಿರಲಿ ಅಥವಾ ಸಾಮಾನ್ಯವಾಗಿರಲಿ, ಯಾವುದೇ ಕ್ಯೂ ವಿಷಯವು ಉಳಿಯಲು ಸಾಧ್ಯವಿಲ್ಲ). ಸಂರಕ್ಷಿಸಲಾದ ಕಾಲ್-ಲಾಗ್ ವಿನಂತಿ ಬಾಡಿಯು ವಿಷಯದ ಸಮಾನತೆಯ ಮೂಲಕ ಹೊಂದಿಸಿ, ವೀಡಿಯೊದಿಂದ ಪಡೆದ ಪ್ರತಿಯೊಂದು ಪಠ್ಯ ಭಾಗವನ್ನು ಆ ಪರಿಷ್ಕರಿಸಿದ ನೆರಳು-ಪ್ರತಿಯಿಂದ ಬದಲಿಸುತ್ತದೆ; ಪೂರ್ವ-ಕಾಲ್ ಗಾರ್ಡ್ರೇಲ್ನ ಪೂರ್ಣಗೊಂಡ ಪೇಲೋಡ್ನಿಂದ `fullText` ಆಂಕರ್ ಅನ್ನು ಪುನಃ ಓದಲಾಗುತ್ತದೆ. ಹೀಗಾಗಿ, ನಂತರದ ಚೈನ್ ಗಾರ್ಡ್ರೇಲ್ಗಳು (PII ಮತ್ತು ಕ್ರೆಡೆನ್ಷಿಯಲ್ ಮಾಸ್ಕರ್ಗಳು, ಆದ್ಯತೆಗಳು 10/95) ವಿವರಣೆಯ ಪಠ್ಯವನ್ನು ಅದೇ ಸ್ಥಳದಲ್ಲಿ ಮರುಬರೆದ ನಂತರವೂ ಮತ್ತು ಸಿಸ್ಟಂ-ಪ್ರಾಂಪ್ಟ್/ಹ್ಯಾಂಡ್ಆಫ್/ಮೆಮೊರಿ ಇಂಜೆಕ್ಷನ್ ಸಂದೇಶ ಅರೆ ಅನ್ನು ಮರುರೂಪಿಸಿದ ನಂತರವೂ ಹೊಂದಾಣಿಕೆ ಯಶಸ್ವಿಯಾಗುತ್ತದೆ. ಮಾಡೆಲ್ಗೆ ಅಪ್ಸ್ಟ್ರೀಮ್ ಕಳುಹಿಸಲಾದ ಬಾಡಿ ಬದಲಾಗುವುದಿಲ್ಲ. ಅವಲೋಕಿಸಲಾದ ವಿನಂತಿಯು ಯಾವುದೇ ಶಾಶ್ವತ Memory ಅನ್ನು ಸಹ ತುಂಬುವುದಿಲ್ಲ (ವಿನಂತಿ ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆಯಿಂದ ಪಡೆಯುವ ಎಕ್ಸ್ಟ್ರಾಕ್ಷನ್ ಎರಡನ್ನೂ ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ), ಆದ್ದರಿಂದ ಮಾಡೆಲ್ನ ಸ್ವಂತ ಉತ್ತರವು ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ ಪಠ್ಯವನ್ನು Memory ಒಳಗೆ ಪ್ರತಿಧ್ವನಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ.

**ಕಚ್ಚಾ ವೀಡಿಯೊ ಫೀಲ್ಡ್ಗಳು (#12430).** ಬ್ರಿಡ್ಜ್ ಸಕ್ರಿಯಗೊಂಡಿರುವಾಗ ಮತ್ತು ಸ್ಥಳೀಯ ವೀಡಿಯೊ ಬೆಂಬಲ ತಿಳಿದಿಲ್ಲದಿರುವಾಗ ಅಥವಾ ಲಭ್ಯವಿಲ್ಲದಿರುವಾಗ, ವ್ಯಾಖ್ಯಾನಿಸಲಾದ `transcript`/`audioTranscript` ಫೀಲ್ಡ್ಗಳು ವಿವರಣೆ ವಿಫಲವಾದ ನಂತರ ಅಥವಾ `maxVideos` ಮಿತಿಯ ನಂತರವೂ `videoBridgeObserved` ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುತ್ತವೆ. `null` ಮತ್ತು ಖಾಲಿ ಸ್ಟ್ರಿಂಗ್ಗಳನ್ನು ಪರಿಗಣಿಸಲಾಗುತ್ತದೆ; ಇಲ್ಲದಿರುವ ಫೀಲ್ಡ್ಗಳು ಮತ್ತು ವೀಡಿಯೊ-ಅಲ್ಲದ ಮೆಟಾಡೇಟಾವನ್ನು ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ. ಸಂರಕ್ಷಿಸಿದ ಪ್ರತಿಗಳು ಈ ಫೀಲ್ಡ್ಗಳನ್ನು ಪರಿಷ್ಕರಿಸುತ್ತವೆ ಅಥವಾ ವಿನಂತಿಯನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತವೆ, ಮತ್ತು ಕ್ಯಾಶ್ಗಳು/Memory ಅನ್ನು ಬೈಪಾಸ್ ಮಾಡಲಾಗುತ್ತದೆ. ಪ್ರೊವೈಡರ್ ಪೇಲೋಡ್ ಬದಲಾಗದೆ ಉಳಿಯುತ್ತದೆ.

ಹೆಚ್ಚುವರಿಯಾಗಿ ಸಂರಕ್ಷಿಸಲಾದ ಪ್ರತಿಗಳು ಅದೇ ಅವಲೋಕಿತ-ವಿನಂತಿ ಸಂಕೇತವನ್ನು ಬಳಸುತ್ತವೆ. ಕಚ್ಚಾ ಪೂರ್ವ-ಗಾರ್ಡ್ರೇಲ್ ಕ್ಲೈಂಟ್-ವಿನಂತಿ ಸ್ನ್ಯಾಪ್ಶಾಟ್, ಇನ್-ಮೆಮೊರಿ ಬಾಕಿಯಿರುವ ವಿನಂತಿ ಮತ್ತು ಮುಂಚಿತವಾಗಿ ತಿರಸ್ಕರಿಸಲಾದ-ವಿನಂತಿಯ ಲಾಗ್, ವೀಡಿಯೊ ಭಾಗಗಳಲ್ಲಿರುವ ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ ಫೀಲ್ಡ್ಗಳನ್ನು ರಚನಾತ್ಮಕವಾಗಿ ಬದಲಿಸುತ್ತವೆ; ಪೈಪ್ಲೈನ್ ಹಂತಗಳು ಮತ್ತು ಕಾಂಟೆಕ್ಸ್ಟ್ ಹ್ಯಾಂಡ್ಆಫ್ ಸಂಶ್ಲೇಷಿಸಿದ ಸ್ಟ್ರಿಂಗ್ ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ಸಂರಕ್ಷಿಸಲಾದ-ವಿನಂತಿ-ಬಾಡಿ ಸಿಂಕ್ನಲ್ಲಿ ಪರಿಷ್ಕರಿಸಲಾಗುತ್ತದೆ. ಸಂರಕ್ಷಿಸಲಾದ `video_content_removed` ಮಾರ್ಕರ್, ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ತ್ಯಜಿಸಲಾದ ಪಠ್ಯವನ್ನು ಮರುರಚಿಸುವ ಬದಲು `previous_response_id` ಮುಂದುವರಿಕೆ ಸುರಕ್ಷಿತವಾಗಿ ವಿಫಲವಾಗುವಂತೆ ಮಾಡುತ್ತದೆ. ಅವಲೋಕಿಸಲಾದ ವಿನಂತಿಯು ಲಾಗಿಂಗ್ಗೆ ಮೊದಲು ತನ್ನ ಪ್ರತಿ-ಭಾಗದ ಪರಿಷ್ಕರಣಾ ನೆರಳು-ಪ್ರತಿಯನ್ನು ಕಳೆದುಕೊಂಡರೆ, ಅಥವಾ ಹಲವಾರು ವೀಡಿಯೊ ನೆರಳು-ಪ್ರತಿಗಳಲ್ಲಿ ಒಂದಾದರೂ ನಂತರದ ವಿನಂತಿ ರೂಪಾಂತರಗಳ ಬಳಿಕ ಹೊಂದಾಣಿಕೆಯಾಗಲು ವಿಫಲವಾದರೆ, ಭಾಗಶಃ ಪರಿಷ್ಕರಿಸಿದ ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳುವ ಬದಲು ಸಂರಕ್ಷಿಸಬೇಕಾದ ವಿನಂತಿ ಬಾಡಿಯನ್ನೇ ಸಂಪೂರ್ಣವಾಗಿ ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ.

ಅವಲೋಕಿಸಲಾದ ವಿನಂತಿಗೆ, ಮಾಡೆಲ್ ಪ್ರತಿಕ್ರಿಯೆಯು ರಚನಾತ್ಮಕ ಕ್ಯೂ ಗಡಿ ಇಲ್ಲದೆಯೇ ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ನ ಯಾವುದೇ ಭಾಗವನ್ನು ಉಲ್ಲೇಖಿಸಬಹುದು. ಆದ್ದರಿಂದ ಅದರ ಸಂರಕ್ಷಿಸಲಾದ ಕಾಲ್-ಲಾಗ್ `responseBody` ಅನ್ನು ಬಿಟ್ಟುಬಿಡುವಿಕೆ ಮಾರ್ಕರ್ನಿಂದ ಬದಲಿಸಲಾಗುತ್ತದೆ; ವಿವರವಾದ ಪೈಪ್ಲೈನ್ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಅನ್ನು (ಇದು ಅಪ್ಸ್ಟ್ರೀಮ್/ಕ್ಲೈಂಟ್ ಬಾಡಿಗಳು ಮತ್ತು ಸ್ಟ್ರೀಮ್ ಚಂಕ್ಗಳನ್ನು ಒಳಗೊಂಡಿರಬಹುದು) ಸಂರಕ್ಷಿಸಲಾಗುವುದಿಲ್ಲ. ಸೆಮ್ಯಾಂಟಿಕ್, ಐಡೆಂಪೊಟೆನ್ಸಿ ಮತ್ತು ರೀಸನಿಂಗ್-ರೀಪ್ಲೇ ಕ್ಯಾಶ್ಗಳು ಆ ವಿನಂತಿಗೆ ಓದುವಿಕೆ ಮತ್ತು ಬರೆಯುವಿಕೆಗಳನ್ನು ಬೈಪಾಸ್ ಮಾಡುತ್ತವೆ. ಪ್ರೊವೈಡರ್ ವಿನಂತಿ ಮತ್ತು ಕ್ಲೈಂಟ್ಗೆ ಗೋಚರಿಸುವ ಪ್ರತಿಕ್ರಿಯೆ ಬದಲಾಗದೆ ಉಳಿಯುತ್ತವೆ. ವಿವರವಾದ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಟ್ಟಾಗ, ಆರಂಭಿಕ ಕೀಪ್ಅಲೈವ್ ಬೈಟ್ಗಳನ್ನು ತಾತ್ಕಾಲಿಕ ಬಫರ್ನಿಂದ ಖಾಲಿಮಾಡಲಾಗುತ್ತದೆ. Kiro ದೋಷಪೂರಿತ EventStream ಎಚ್ಚರಿಕೆಯು ಪೇಲೋಡ್ನ ಬೈಟ್ ಎಣಿಕೆಯನ್ನು ಮಾತ್ರ ವರದಿ ಮಾಡುತ್ತದೆ; ಅದರ ವಿಷಯವನ್ನಾಗಲಿ JSON ಪಾರ್ಸರ್ನ ಕಚ್ಚಾ ದೋಷವನ್ನಾಗಲಿ ಎಂದಿಗೂ ವರದಿ ಮಾಡುವುದಿಲ್ಲ.
ಪ್ರತಿಯೊಂದು ಸಂಬಂಧವಿಲ್ಲದ ಪ್ರೊವೈಡರ್/ಪ್ಲಗಿನ್ ಡಯಾಗ್ನೊಸ್ಟಿಕ್ ಅನ್ನು ಆಡಿಟ್ ಮಾಡಲಾಗಿದೆ ಎಂದು ಇದು ಪ್ರತಿಪಾದಿಸುವುದಿಲ್ಲ; ವಿಶಾಲವಾದ ಸಂರಕ್ಷಿತ-ಸಿಂಕ್ ಪರಿಶೀಲನೆಯನ್ನು #11658 ರಲ್ಲಿ ಟ್ರ್ಯಾಕ್ ಮಾಡಲಾಗುತ್ತದೆ.

ಆಂತರಿಕ `/api/modality-bridge/video/drilldown` ಜೀವನಚಕ್ರವು ಪ್ರತ್ಯೇಕವಾದ, ಲೂಪ್ಬ್ಯಾಕ್/ಟೋಕನ್-ದೃಢೀಕೃತ ಕ್ಯಾಶ್ ಸಬ್ಸ್ಟ್ರೇಟ್ ಆಗಿದೆ. ಪ್ರತಿಯೊಂದು ಕಾರ್ಯಾಚರಣೆಗೆ ಕ್ಯಾನಾನಿಕಲ್ ಅಪಾರದರ್ಶಕ ಪ್ರಿನ್ಸಿಪಲ್ ID ಕೂಡ ಅಗತ್ಯ. ಪ್ರೊಡಕ್ಷನ್ ಕಾಲರ್ ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುವ ಮೊದಲು, ಅದು ಆ ID ಅನ್ನು ದೃಢೀಕೃತ ಟೆನಂಟ್ನಿಂದ ಪಡೆಯಬೇಕು ಮತ್ತು ಕ್ಲೈಂಟ್ ಆಯ್ಕೆಮಾಡಿದ ಮೌಲ್ಯವನ್ನು ಎಂದಿಗೂ ಫಾರ್ವರ್ಡ್ ಮಾಡಬಾರದು. ಕ್ಯಾಶ್ ಕೀಗಳು ಆ ಪ್ರಿನ್ಸಿಪಲ್ ಅನ್ನು ಕ್ಯಾನಾನಿಕಲ್ ಸೆಷನ್ ಮತ್ತು ವೀಡಿಯೊ-ರೆಫರೆನ್ಸ್ ID ಗಳಿಗೆ ಬಂಧಿಸುತ್ತವೆ, ಅವುಗಳ SHA-256-ಮೂಲದ ಕೀಗಳನ್ನು ಮಾತ್ರ ಸಂಗ್ರಹಿಸುತ್ತವೆ ಮತ್ತು ಓದುವಿಕೆ ಹಾಗೂ ಅಳಿಸುವಿಕೆ ಎರಡನ್ನೂ ಅದೇ ಪ್ರಿನ್ಸಿಪಲ್ಗೆ ಸೀಮಿತಗೊಳಿಸುತ್ತವೆ. ಕ್ಯಾಶ್ ಪ್ರತಿ ಎಂಟ್ರಿಗೆ ಗರಿಷ್ಠ 16 ವ್ಯುತ್ಪನ್ನ JPEG ಫ್ರೇಮ್ಗಳನ್ನು ಸಂಗ್ರಹಿಸುತ್ತದೆ, ಹತ್ತು ನಿಮಿಷಗಳ ನಂತರ ಅವುಗಳ ಅವಧಿ ಮುಗಿಸುತ್ತದೆ ಮತ್ತು ಮಿತಿಗೊಳಿಸಿದ `start`/`end` ಓದುವಿಕೆಗಳು ಅಥವಾ ಸ್ಪಷ್ಟ ಸೆಷನ್ ಅಳಿಸುವಿಕೆಯನ್ನು ಬೆಂಬಲಿಸುತ್ತದೆ.

### PII Masker (`piiMasker.ts`)

**ಎರಡೂ** stagesನಲ್ಲಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ.

- **`preCall`** ಪೇಲೋಡ್ ಅನ್ನು ಕ್ಲೋನ್ ಮಾಡುತ್ತದೆ, `system`, `messages`, `input`, ಮತ್ತು
  `prompt` ಮೂಲಕ ಸಂಚರಿಸುತ್ತದೆ (ಸರಳ ಸ್ಟ್ರಿಂಗ್ ಐಟಂಗಳನ್ನು ಒಳಗೊಂಡಂತೆ), ಹಾಗೂ ಸ್ಟ್ರಿಂಗ್
  `content`/`text` ಕ್ಷೇತ್ರಗಳಿಗೆ (`@/shared/utils/inputSanitizer` ನಿಂದ)
  `processPII()` ಅನ್ನು ಅನ್ವಯಿಸುತ್ತದೆ. `PII_REDACTION_ENABLED=true` ಆಗಿರುವಾಗ,
  ಪತ್ತೆಯಾದ PII ಅನ್ನು ಹೊರಹೋಗುವ ಪೇಲೋಡ್ನಲ್ಲಿ ಮರೆಮಾಡಲಾಗುತ್ತದೆ. ಇದು
  `INPUT_SANITIZER_MODE` ನಿಂದ ಸ್ವತಂತ್ರವಾಗಿದೆ (ಅದು ಪ್ರಾಂಪ್ಟ್-ಇಂಜೆಕ್ಷನ್ ನೀತಿಯನ್ನು
  ಮಾತ್ರ ನಿಯಂತ್ರಿಸುತ್ತದೆ). ಮರೆಮಾಡುವಿಕೆ ಆಫ್ ಆಗಿರುವಾಗ, ವಿಷಯವನ್ನು ಮರುಬರೆಯದೆ ಕರೆ
  ಪತ್ತೆ ಎಣಿಕೆಗಳನ್ನು ದಾಖಲಿಸುತ್ತದೆ.
- **`postCall`** ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಡೀಪ್-ಕ್ಲೋನ್ ಮಾಡುತ್ತದೆ, `sanitizePIIResponse()` ಜೊತೆಗೆ
  Responses-API-ಆಕಾರದ ಮಾಸ್ಕರ್ ಅನ್ನು (`maskResponsesOutput` — ಇದು
  `output_text` ಮತ್ತು `output[].content[].text` ಅನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ) ಚಲಾಯಿಸುತ್ತದೆ.
  ಯಾವುದೇ ಮರೆಮಾಡುವಿಕೆ ಸಂಭವಿಸಿದರೆ, ಮಾರ್ಪಡಿಸಿದ ಪ್ರತಿಕ್ರಿಯೆಯು ಮೂಲ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು
  ಬದಲಿಸುತ್ತದೆ.

ಗಾರ್ಡ್ರೇಲ್ ಎಂದಿಗೂ ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ; ಅದು ಕೇವಲ ಟಿಪ್ಪಣಿ ಸೇರಿಸುತ್ತದೆ
(`meta.detections`, `meta.redacted`) ಅಥವಾ ಮರುಬರೆಯುತ್ತದೆ.

### ಪ್ರಾಂಪ್ಟ್ ಇಂಜೆಕ್ಷನ್ (`promptInjection.ts`)

ಬಳಕೆದಾರರು ಒದಗಿಸಿದ ವಿಷಯದಲ್ಲಿನ ಪ್ರತಿಕೂಲ ರಚನೆಗಳನ್ನು ಪತ್ತೆಹಚ್ಚುತ್ತದೆ ಮತ್ತು
ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ ನೀತಿಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತದೆ. ವರ್ತನೆಯನ್ನು ಪರಿಸರ ಚರಾಂಶಗಳು ಮತ್ತು
ಕನ್ಸ್ಟ್ರಕ್ಟರ್ ಆಯ್ಕೆಗಳು ನಿರ್ಧರಿಸುತ್ತವೆ:

| ಸೆಟ್ಟಿಂಗ್         | ಪರಿಸರ ಚರಾಂಶ                                                                                                     | ಡೀಫಾಲ್ಟ್ | ಪರಿಣಾಮ                                                                                                                                                                                                                        |
| ----------------- | --------------------------------------------------------------------------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ಸಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ | `INPUT_SANITIZER_ENABLED`                                                                                       | `true`   | `false` ಆಗಿರುವಾಗ, ಗಾರ್ಡ್ರೇಲ್ ಶಾರ್ಟ್-ಸರ್ಕ್ಯೂಟ್ ಆಗುತ್ತದೆ.                                                                                                                                                                       |
| ಮೋಡ್              | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                                 | `warn`   | ಇಂಜೆಕ್ಷನ್ ನೀತಿ: `block`, `warn`, ಅಥವಾ `log`. (`redact` ಅನ್ನು ಹಿಮ್ಮುಖ-ಹೊಂದಾಣಿಕೆಗಾಗಿ ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ, ಆದರೆ ಅದು ಇಂಜೆಕ್ಷನ್ ಪಠ್ಯವನ್ನು ತೆಗೆದುಹಾಕುವುದಿಲ್ಲ; ವಿನಂತಿಯ PII ಮರುಬರೆಯುವಿಕೆಯನ್ನು `PII_REDACTION_ENABLED` ನಿಯಂತ್ರಿಸುತ್ತದೆ.) |
| ನಿರ್ಬಂಧ ಮಿತಿ      | `blockThreshold` ಆಯ್ಕೆ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (`INJECTION_GUARD_BLOCK_THRESHOLD` ಎಂಬ ಪರ್ಯಾಯ ಹೆಸರು) | `high`   | ನಿರ್ಬಂಧಿಸಲು ಅಗತ್ಯವಿರುವ ಕನಿಷ್ಠ ತೀವ್ರತೆ. ಡೀಫಾಲ್ಟ್ನಲ್ಲಿ ಮಧ್ಯಮ ತೀವ್ರತೆಯು ವೀಕ್ಷಣೆ-ಮಾತ್ರವಾಗಿರುತ್ತದೆ.                                                                                                                                |

**ಮೋಡ್ ಆದ್ಯತೆ** (`getMode`): ಕರೆ ಮಾಡುವವರ `options.mode` →
`INJECTION_GUARD_MODE` **DB ವೈಶಿಷ್ಟ್ಯ-ಫ್ಲ್ಯಾಗ್ ಓವರ್ರೈಡ್** (ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಸೆಟ್ಟಿಂಗ್ಗಳು →
ವೈಶಿಷ್ಟ್ಯ ಫ್ಲ್ಯಾಗ್ಗಳು) → `INJECTION_GUARD_MODE` ಪರಿಸರ ಚರಾಂಶ → `INPUT_SANITIZER_MODE` ಪರಿಸರ ಚರಾಂಶ →
`warn`. ಆದ್ದರಿಂದ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಓವರ್ರೈಡ್ ಪರಿಸರ ಚರಾಂಶಗಳಿಗಿಂತ ಆದ್ಯತೆ ಪಡೆಯುತ್ತದೆ, ಹೀಗಾಗಿ ವೈಶಿಷ್ಟ್ಯ
ಫ್ಲ್ಯಾಗ್ಗಳ UI ಚಾಲನೆಯಲ್ಲಿರುವ ಗಾರ್ಡ್ ಅನ್ನು ನೇರವಾಗಿ ನಿಯಂತ್ರಿಸುತ್ತದೆ (ಮರುಪ್ರಾರಂಭ ಅಗತ್ಯವಿಲ್ಲ). DB ಓದುವಿಕೆ ವಿಫಲ-ಸುರಕ್ಷಿತವಾಗಿದೆ:
ಅದು ದೋಷಗೊಂಡರೆ, ಗಾರ್ಡ್ ಪರಿಸರ-ಆಧಾರಿತ ವರ್ತನೆಗೆ ಹಿಂತಿರುಗುತ್ತದೆ, ಮತ್ತು ಯಾವುದೇ
ಓವರ್ರೈಡ್ ಹೊಂದಿಸದಿದ್ದಾಗ ವರ್ತನೆಯು ಪರಿಸರ-ಮಾತ್ರದ ರೆಸಲ್ಯೂಷನ್ಗೆ ಸಮಾನವಾಗಿರುತ್ತದೆ.

1. `@/shared/utils/inputSanitizer` ನಿಂದ `sanitizeRequest()` (ಪೈಪ್ಲೈನ್ನ

`mode === "block"` ಆಗಿರುವಾಗ **ಮತ್ತು** ಕನಿಷ್ಠ ಒಂದು ಪತ್ತೆಯು ತೀವ್ರತಾ
ಮಿತಿಯನ್ನು ತಲುಪಿದಾಗ, `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ. `warn`/`log` ಮೋಡ್ಗಳಲ್ಲಿ ಗಾರ್ಡ್ರೇಲ್ ಲಾಗ್ ಮಾಡುತ್ತದೆ ಆದರೆ
ಕರೆಗೆ ಅನುಮತಿಸುತ್ತದೆ. ರಿಜಿಸ್ಟ್ರಿಯ ಮೂಲಕ ಹೋಗದೆ ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ಮೌಲ್ಯಮಾಪನ ಮಾಡಬೇಕಾದ
ಕರೆ ಮಾಡುವವರಿಗಾಗಿ ಹಂಚಿಕೆಯ ಸಹಾಯಕ `evaluatePromptInjection()` ಅನ್ನು ಸಹ ಎಕ್ಸ್ಪೋರ್ಟ್ ಮಾಡಲಾಗಿದೆ.

**ಸ್ಕ್ಯಾನ್ ಮಿತಿ (v3.8.20):** ಡಿಟೆಕ್ಟರ್ ಒಟ್ಟುಗೂಡಿಸಿದ ಪ್ರಾಂಪ್ಟ್ ಪಠ್ಯದ **ಮೊದಲ 16 KB** ಅನ್ನು
ಮಾತ್ರ ಪರಿಶೀಲಿಸುತ್ತದೆ — `src/shared/utils/inputSanitizer.ts` ನಲ್ಲಿ
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ಬೈಟ್ಗಳು). ಪ್ಯಾಟರ್ನ್ ಲೂಪ್ ಅನ್ನು
ಚಲಾಯಿಸುವ ಮೊದಲು `detectInjection()` ಮತ್ತು `evaluatePromptInjection()` ಎರಡೂ
`slice(0, MAX_INJECTION_SCAN_BYTES)` ಅನ್ನು ಬಳಸುತ್ತವೆ. ಇಂಜೆಕ್ಷನ್ ನಿರ್ದೇಶನಗಳು ಇನ್ಪುಟ್ನ
ಮೇಲ್ಭಾಗದ ಸಮೀಪದಲ್ಲಿರುತ್ತವೆ, ಆದ್ದರಿಂದ ಇದು ಪತ್ತೆ ಸಾಮರ್ಥ್ಯವನ್ನು ದುರ್ಬಲಗೊಳಿಸದೆ ನೂರಾರು-KB
ಪೇಲೋಡ್ಗಳಲ್ಲಿ ರೆಜೆಕ್ಸ್ CPU/GC ಅನ್ನು ಮಿತಿಗೊಳಿಸುತ್ತದೆ (ನೋಡಿ #3932, #4041).

### ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಮಾಸ್ಕರ್ (`credentialMasker.ts`)

ಡೀಫಾಲ್ಟ್ ಸರಪಳಿಯಲ್ಲಿ ಕೊನೆಯದಾಗಿ (ಆದ್ಯತೆ `95`), **ಎರಡೂ** ಹಂತಗಳಲ್ಲಿ ಚಲಿಸುತ್ತದೆ.
ಹೊರಹೋಗುವ ಪೇಲೋಡ್ನಿಂದ (ಸಂದೇಶದ ವಿಷಯ, ಟೂಲ್-ಕಾಲ್ ಆರ್ಗ್ಯುಮೆಂಟ್ಗಳು, ಟೂಲ್ ಫಲಿತಾಂಶಗಳು)
**ಮತ್ತು** ಪೂರೈಕೆದಾರರ ಪ್ರತಿಕ್ರಿಯೆಯಿಂದ ಪ್ರಸಿದ್ಧ API-ಕೀ / ರಹಸ್ಯ-ಟೋಕನ್ ಪ್ಯಾಟರ್ನ್ಗಳನ್ನು
ಮರೆಮಾಡುತ್ತದೆ, ಹೀಗಾಗಿ ಪ್ರಾಂಪ್ಟ್ಗೆ ಅಂಟಿಸಲಾದ (ಅಥವಾ ಟೂಲ್ ಫಲಿತಾಂಶದಿಂದ ಪ್ರತಿಧ್ವನಿಸಲಾದ)
ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಅಪ್ಸ್ಟ್ರೀಮ್ ಪೂರೈಕೆದಾರರಿಗೆ ಅಥವಾ ಕ್ಲೈಂಟ್ಗೆ ಮರಳಿ ಸೋರಿಕೆಯಾಗುವುದಿಲ್ಲ.

- **ಆಯ್ಕೆ ಮಾಡಿದರೆ ಮಾತ್ರ ಸಕ್ರಿಯ**, PII ಮರೆಮಾಚುವಿಕೆಯಂತೆಯೇ ಅದೇ ಸಂಪ್ರದಾಯ (Hard Rule #20-ಗೆ ಹೊಂದಿಕೊಂಡಂತೆ):
  `settings.credentialRedactionEnabled === true` **ಅಥವಾ**
  `CREDENTIAL_REDACTION_ENABLED=true` ಆಗಿರದ ಹೊರತು ನಿಷ್ಕ್ರಿಯವಾಗಿರುತ್ತದೆ. ಇದು ಆಫ್ ಆಗಿರುವಾಗ, ಗಾರ್ಡ್ರೇಲ್ ಯಾವುದೇ ಕಾರ್ಯ ಮಾಡುವುದಿಲ್ಲ —
  ಅದು ಎಂದಿಗೂ ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ ಮತ್ತು ಎಂದಿಗೂ ಮರುಬರೆಯುವುದಿಲ್ಲ.
- `redactCredentials()` ಸಂಪೂರ್ಣ ಪೇಲೋಡ್/ಪ್ರತಿಕ್ರಿಯೆ ಟ್ರೀ ಮೂಲಕ ಸಂಚರಿಸುತ್ತದೆ (`walkValue()`,
  ಪ್ರೋಟೋಟೈಪ್-ಪಲ್ಯೂಷನ್ನಿಂದ ಸುರಕ್ಷಿತ, `WeakSet` ಮೂಲಕ ಸೈಕಲ್ನಿಂದ ಸುರಕ್ಷಿತ) ಮತ್ತು ಹೊಂದಾಣಿಕೆಗಳನ್ನು
  `[REDACTED:<type>]` ಪ್ಲೇಸ್ಹೋಲ್ಡರ್ನಿಂದ ಬದಲಾಯಿಸುತ್ತದೆ; ವಾಸ್ತವವಾಗಿ
  ಬದಲಾದ ಶಾಖೆಗಳನ್ನು ಮಾತ್ರ ಕ್ಲೋನ್ ಮಾಡುತ್ತದೆ.
- `CREDENTIAL_PATTERNS` LLM ಪೂರೈಕೆದಾರರ ಕೀಗಳು (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ಟೋಕನ್ಗಳು (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), ಪಾವತಿ ಕೀಗಳು (Stripe, Square), ಕ್ಲೌಡ್
  ಕೀಗಳು (AWS ಆಕ್ಸೆಸ್ ಕೀ, Twilio, SendGrid, Mailgun), ಖಾಸಗಿ ಕೀಗಳು / JWTಗಳು,
  ರುಜುವಾತುಗಳನ್ನು ಹೊಂದಿರುವ ಸಂಪರ್ಕ ಸ್ಟ್ರಿಂಗ್ಗಳು (`mongodb://user:pass@...`, ಇತ್ಯಾದಿ), ಮತ್ತು
  ಸಾಮಾನ್ಯ `Authorization`/`x-api-key`/`api-key`/`apikey` ಹೆಡರ್-ಮೌಲ್ಯ
  ಪ್ಯಾಟರ್ನ್ ಅನ್ನು ಒಳಗೊಂಡಿದೆ. ಹೆಡರ್-ರೂಪದ ಕೀಗಳನ್ನು (`authorization`, `x-api-key`, `api-key`,
  `apikey`) ಸಾಮಾನ್ಯ ಪಠ್ಯ regex ಮೂಲಕ ಮಾಡುವ ಬದಲು ರಚನಾತ್ಮಕವಾಗಿ ಮರೆಮಾಚಲಾಗುತ್ತದೆ (ಮೌಲ್ಯ ಮಾತ್ರ,
  `Bearer `/`Basic ` ನಂತಹ ಸ್ಕೀಮ್ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಉಳಿಸಲಾಗುತ್ತದೆ).
- ಗಾರ್ಡ್ರೇಲ್ ಎಂದಿಗೂ ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ; ಅದು ಕೇವಲ ಮರುಬರೆಯುತ್ತದೆ (`modifiedPayload` /
  `modifiedResponse`) ಮತ್ತು ಟಿಪ್ಪಣಿ ಸೇರಿಸುತ್ತದೆ (`meta.credentialsRedacted`, `meta.count`).

ರಿಗ್ರೆಷನ್ ಗಾರ್ಡ್: `tests/unit/credential-masker-guardrail.test.ts`.

## ಮೂಲ ಒಪ್ಪಂದ (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ಸರಪಳಿಯನ್ನು ತಕ್ಷಣವೇ ಸ್ಥಗಿತಗೊಳಿಸುತ್ತದೆ
  message?: string; // ನಿರ್ಬಂಧಿಸುವಾಗ ಪ್ರದರ್ಶಿಸಲಾಗುತ್ತದೆ
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // ವಿನಂತಿಯನ್ನು ಮರುಬರೆಯಲು preCall ಮೂಲಕ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ
  modifiedResponse?: TValue; // ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಮರುಬರೆಯಲು postCall ಮೂಲಕ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

`void`, `{}`, ಅಥವಾ `{ block: false }` ಇವುಗಳಲ್ಲಿ ಯಾವುದನ್ನಾದರೂ ಹಿಂತಿರುಗಿಸುವ ಮೂಲಕ guardrail "ಯಾವುದೇ ಬದಲಾವಣೆ ಇಲ್ಲ" ಎಂದು ಸೂಚಿಸುತ್ತದೆ. `modifiedPayload`/`modifiedResponse` ಅನ್ನು ಹಿಂತಿರುಗಿಸುವುದರಿಂದ, ನಂತರದ guardrailಗಳಿಗಾಗಿ ಸರಪಳಿಯ ಮೂಲಕ ಹರಿಯುವ ಮೌಲ್ಯವನ್ನು ಅದು ಬದಲಿಸುತ್ತದೆ.
`signal?: AbortSignal` ಕಾಲರ್ನ ಜೀವನಚಕ್ರವನ್ನು guardrailಗಳಿಗೆ ಒಯ್ಯುತ್ತದೆ. ವಿನಂತಿಯ ರದ್ದತಿಯು ಉದ್ದೇಶಪೂರ್ವಕ fail-open ಅಪವಾದವಾಗಿದೆ: media bridgeಗಳು ಕೆಲಸವನ್ನು ನಿಲ್ಲಿಸಿ cleanup ಮಾಡುತ್ತವೆ ಮತ್ತು ಅದನ್ನು ಬೆಂಬಲಿಸುವುದಿಲ್ಲ ಎಂದು ತಿಳಿದಿರುವ ಗುರಿಗೆ raw media ಅನ್ನು ಮರುಸ್ಥಾಪಿಸುವುದಿಲ್ಲ.

## ರಿಜಿಸ್ಟ್ರಿ (`registry.ts`)

singleton `guardrailRegistry` ಈ ಕೆಳಗಿನವುಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ:

- `register(guardrail)` — guardrail ಅನ್ನು ಸೇರಿಸುತ್ತದೆ (ಅಥವಾ normalized name ಆಧಾರದಲ್ಲಿ ಬದಲಿಸುತ್ತದೆ) ಮತ್ತು ಏರಿಕೆ ಕ್ರಮದ `priority` ಪ್ರಕಾರ ಮರು-ವಿಂಗಡಿಸುತ್ತದೆ.
- `clear()` / `list()` — ಆಡಳಿತಾತ್ಮಕ ಸಹಾಯಕಗಳು.
- `runPreCallHooks(payload, context)` — ಸಕ್ರಿಯ guardrailಗಳ ಮೂಲಕ ಪುನರಾವರ್ತಿಸುತ್ತದೆ, `modifiedPayload` ಮೂಲಕ payload ಅನ್ನು ಮುಂದಕ್ಕೆ ಕೊಂಡೊಯ್ಯುತ್ತದೆ ಮತ್ತು ಮೊದಲ `block: true` ದೊರೆತಾಗ ನಿಲ್ಲುತ್ತದೆ.
- `runPostCallHooks(response, context)` — response ಭಾಗದಲ್ಲಿಯೂ ಇದೇ ಹರಿವನ್ನು ಅನುಸರಿಸುತ್ತದೆ.
- `resetGuardrailsForTests({ registerDefaults })` — ಸ್ಥಿತಿಯನ್ನು ತೆರವುಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಸ್ವಚ್ಛ test isolationಗಾಗಿ ಐಚ್ಛಿಕವಾಗಿ defaults ಅನ್ನು ಮರು-ನೋಂದಾಯಿಸುತ್ತದೆ.

ಎರಡೂ runnerಗಳು `{ blocked, payload|response, results, guardrail?, message? }` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತವೆ, ಇಲ್ಲಿ `results` ಎಂಬುದು ಪ್ರತಿಯೊಂದು guardrailಗೆ ಸಂಬಂಧಿಸಿದ `blocked`, `skipped`, `modified`, `error`, ಮತ್ತು `meta` ಕ್ಷೇತ್ರಗಳನ್ನು ಒಳಗೊಂಡಿರುವ `GuardrailExecutionResult` recordಗಳ array ಆಗಿದ್ದು, tracingಗೆ ಉಪಯುಕ್ತವಾಗಿದೆ.

### ಪ್ರತಿ ವಿನಂತಿಗೆ Guardrailಗಳನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವುದು

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` ಪ್ರಸ್ತುತ ವಿನಂತಿಗಾಗಿ ಬಿಟ್ಟುಬಿಡಬೇಕಾದ guardrail ಹೆಸರುಗಳ duplicate ತೆಗೆದುಹಾಕಿದ ಪಟ್ಟಿಯನ್ನು ಒಟ್ಟುಗೂಡಿಸುತ್ತದೆ. ಮೂಲಗಳು (ಎಲ್ಲವೂ ಐಚ್ಛಿಕ, ಎಲ್ಲವನ್ನೂ ವಿಲೀನಗೊಳಿಸಲಾಗುತ್ತದೆ):

- `apiKeyInfo.disabledGuardrails`
- ವಿನಂತಿಯ bodyಯಲ್ಲಿನ `disabledGuardrails` (top-level)
- ವಿನಂತಿಯ bodyಯಲ್ಲಿನ `metadata.disabledGuardrails`
- Header `x-omniroute-disabled-guardrails` (ಅಥವಾ ಹಳೆಯ
  `x-disabled-guardrails`)

ಮೌಲ್ಯಗಳು stringಗಳ array ಆಗಿರಬಹುದು ಅಥವಾ comma-separated string ಆಗಿರಬಹುದು; ಹೆಸರುಗಳನ್ನು lowercase kebab-caseಗೆ normalize ಮಾಡಲಾಗುತ್ತದೆ (`pii_masker` → `pii-masker`). ಫಲಿತಾಂಶವನ್ನು `context.disabledGuardrails` ಮೂಲಕ registryಗೆ ರವಾನಿಸಲಾಗುತ್ತದೆ, ಅದು ಹೊಂದಿಕೆಯಾಗುವ guardrailಗಳನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ (`results` ನಲ್ಲಿ `skipped: true`).

## ಕಾರ್ಯಗತಗೊಳಿಸುವ ಕ್ರಮ

`src/sse/handlers/chat.ts` ಮತ್ತು
`open-sse/handlers/chatCore.ts` ಮೂಲಕ ಹರಿಯುವ ಪ್ರತಿ ವಿನಂತಿಗಾಗಿ:

1. `resolveDisabledGuardrails(...)` API ಕೀ, ಬಾಡಿ ಮತ್ತು ಹೆಡರ್ಗಳಿಂದ ಬಿಟ್ಟುಬಿಡುವ ಪಟ್ಟಿಯನ್ನು ರಚಿಸುತ್ತದೆ.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು ಆದ್ಯತೆಯ ಆರೋಹಣ ಕ್ರಮದಲ್ಲಿ ಚಲಾಯಿಸುತ್ತದೆ:
   - ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾದ ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು `skipped` ಎಂದು ದಾಖಲಿಸಲಾಗುತ್ತದೆ.
   - ಪ್ರತಿ ಗಾರ್ಡ್ರೇಲ್ನ `preCall`, `modifiedPayload` ಮೂಲಕ ಪೇಲೋಡ್ ಅನ್ನು ಮರುಬರೆಯಬಹುದು.
   - ಮೊದಲ `block: true` ಸರಪಳಿಯನ್ನು ಅಲ್ಲಿಯೇ ನಿಲ್ಲಿಸುತ್ತದೆ ಮತ್ತು ಹ್ಯಾಂಡ್ಲರ್ ಗಾರ್ಡ್ರೇಲ್ ನಿರಾಕರಣೆಯ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ.
3. (ಸಂಭಾವ್ಯವಾಗಿ ಮರುಬರೆಯಲಾದ) ಪೇಲೋಡ್ ಕಾಂಬೊ ರೂಟಿಂಗ್ ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಡಿಸ್ಪ್ಯಾಚ್ಗೆ ಹರಿಯುತ್ತದೆ.
4. ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಜೋಡಿಸಿದ ನಂತರ, `guardrailRegistry.runPostCallHooks(...)` ಪ್ರತಿಕ್ರಿಯೆಯ ಮೇಲೆ ಅದೇ ಸರಪಳಿಯನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಇಲ್ಲಿ `block: true` ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಕೈಬಿಡುತ್ತದೆ.

ದೋಷ ಎಸೆಯುವ ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು `error: <message>` ಜೊತೆಗೆ ದಾಖಲಿಸಲಾಗುತ್ತದೆ ಮತ್ತು
`logger.warn` ಮೂಲಕ ಲಾಗ್ ಮಾಡಲಾಗುತ್ತದೆ, ಆದರೆ ಸರಪಳಿ ಮುಂದುವರಿಯುತ್ತದೆ — ವಿನ್ಯಾಸದ ಪ್ರಕಾರ ದೋಷ ಸಂಭವಿಸಿದಾಗಲೂ ಅನುಮತಿಸಲಾಗುತ್ತದೆ.

## ಕಸ್ಟಮ್ ಗಾರ್ಡ್ರೈಲ್ಗಳು

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ಹಂತಗಳು:

1. `BaseGuardrail` ಅನ್ನು ವಿಸ್ತರಿಸುವ `src/lib/guardrails/myGuardrail.ts` ಅನ್ನು ರಚಿಸಿ.
2. `preCall` ಮತ್ತು/ಅಥವಾ `postCall` ಅನ್ನು ಅನುಷ್ಠಾನಗೊಳಿಸಿ.
3. ಇಂಪೋರ್ಟ್ ಸಮಯದಲ್ಲಿಯೇ ನೋಂದಾಯಿಸಿ (`registerDefaultGuardrails` ನಿಂದ ಪುಶ್ ಮಾಡಿ) ಅಥವಾ
   ರನ್ಟೈಮ್ನಲ್ಲಿ `guardrailRegistry.register(...)` ಅನ್ನು ಕರೆ ಮಾಡಿ — ಅದೇ ಸಾಮಾನ್ಯೀಕರಿಸಿದ
   ಹೆಸರನ್ನು ಹೊಂದಿರುವ ಯಾವುದೇ ಹಿಂದಿನ ಗಾರ್ಡ್ರೈಲ್ ಅನ್ನು ರಿಜಿಸ್ಟ್ರಿ ಬದಲಿಸುತ್ತದೆ.
4. `tests/unit/` ಅಡಿಯಲ್ಲಿ ಪರೀಕ್ಷೆಗಳನ್ನು ಸೇರಿಸಿ (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಉದಾಹರಣೆಗಳು:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

ತಿಳಿದಿರುವ ಸ್ಥಿತಿಯಿಂದ ಪ್ರಾರಂಭಿಸಲು ಪರೀಕ್ಷೆಗಳ ನಡುವೆ `resetGuardrailsForTests()` ಅನ್ನು ಬಳಸಿ.
ಖಾಲಿ ರಿಜಿಸ್ಟ್ರಿಯೊಂದಿಗೆ ಪ್ರಾರಂಭಿಸಲು `{ registerDefaults: false }` ಅನ್ನು ಪಾಸ್ ಮಾಡಿ ಮತ್ತು
ಪರೀಕ್ಷೆಯಲ್ಲಿರುವ ಗಾರ್ಡ್ರೈಲ್ಗಳನ್ನು ಮಾತ್ರ ನೋಂದಾಯಿಸಿ. Vision Bridge ಡಿಪೆಂಡೆನ್ಸಿ
ಇಂಜೆಕ್ಷನ್ ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge,
ಸೆಟ್ಟಿಂಗ್ಗಳು, ಸಾಮರ್ಥ್ಯಗಳು, STT ಮಾದರಿ ಆಯ್ಕೆ, ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಪರಿಶೀಲನೆಗಳು ಮತ್ತು
ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಷನ್ಗಾಗಿ ಸಮಾನವಾದ ಸೀಮ್ಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ. ಆದ್ದರಿಂದ ಪರೀಕ್ಷೆಗಳು DB
ಅಥವಾ ನೆಟ್ವರ್ಕ್ ಪ್ರವೇಶವಿಲ್ಲದೆಯೇ ಎರಡೂ ಫ್ಲೋಗಳನ್ನು ಪರೀಕ್ಷಿಸಬಹುದು.

## ಇಂಜೆಕ್ಷನ್-ಗಾರ್ಡ್ ರೂಟ್ ವ್ಯಾಪ್ತಿ ಮತ್ತು ರೆಡ್-ಟೀಮ್ (ಹಂತ 8 · ಬ್ಲಾಕ್ D)

ಇಂಜೆಕ್ಷನ್-ಗಾರ್ಡ್ (`createInjectionGuard` / `withInjectionGuard`) ಬಳಕೆದಾರರ
ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ಸ್ವೀಕರಿಸುವ ಎಲ್ಲಾ ರೂಟ್ಗಳನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ. ಇದು `INJECTION_GUARD_MODE`
ಅನ್ನು ಗೌರವಿಸುತ್ತದೆ (ಡೀಫಾಲ್ಟ್ `warn` = ಲಾಗ್ ಮಾತ್ರ; `block` = HTTP 400 `SECURITY_001` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ).

| ಪ್ರಕಾರ                     | ರೂಟ್ಗಳು                                                                                                                                              | ಡೀಫಾಲ್ಟ್ ಮೋಡ್ |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| ಪಠ್ಯ (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವುದು) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn          |
| ಜನರೇಟಿವ್                   | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn          |
| ಡೇಟಾ                       | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn          |

ಪಠ್ಯ ಹೊರತೆಗೆಯುವಿಕೆ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ಅನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ.

**ರೆಡ್-ಟೀಮ್ (ಪ್ರತಿ ರಾತ್ರಿ, `nightly-llm-security.yml`):** `INJECTION_GUARD_MODE=block`
ನಲ್ಲಿ ಪ್ರತಿಯೊಂದು ರೂಟ್, `OWASP-LLM` ಕಾರ್ಪಸ್ ಅನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆ ಎಂಬುದನ್ನು promptfoo
ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ; garak ಪ್ರೋಬ್ಗಳನ್ನು ಚಲಾಯಿಸುತ್ತದೆ (ಸೀಕ್ರೆಟ್ ಇಲ್ಲದಿದ್ದರೆ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ).
ಸ್ಥಿರತೆಗಾಗಿ `moderations` ಅನ್ನು ಸೇರಿಸಲಾಗಿದೆ — ಬ್ಲಾಕ್-ಮೋಡ್ನಲ್ಲಿರುವ ಆಪರೇಟರ್ಗಳು
`resolveDisabledGuardrails` ಮೂಲಕ ಅದಕ್ಕೆ ವಿನಾಯಿತಿ ನೀಡಬಹುದು.

ಪ್ರತಿ ರಾತ್ರಿಯ ವರ್ಕ್ಫ್ಲೋ (`.github/workflows/nightly-llm-security.yml`, cron + ಮ್ಯಾನುಯಲ್
ಡಿಸ್ಪ್ಯಾಚ್) ಎರಡು ಜಾಬ್ಗಳನ್ನು ಹೊಂದಿದೆ:

- **`promptfoo-guard` (ನಿರ್ಬಂಧಿಸುವುದು)** — `INJECTION_GUARD_MODE=block` ಜೊತೆಗೆ
  `promptfoo eval -c promptfooconfig.yaml` ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಪ್ರತಿಯೊಂದು ಪ್ರತಿಕೂಲ
  ಪ್ರಕರಣವು (ಉದಾ. "ಹಿಂದಿನ ಎಲ್ಲಾ ಸೂಚನೆಗಳನ್ನು ನಿರ್ಲಕ್ಷಿಸಿ…", DAN-ಶೈಲಿಯ ಜೈಲ್ಬ್ರೇಕ್ಗಳು)
  ಪ್ರತಿಕ್ರಿಯೆಯು `error.code === "SECURITY_001"` ಅನ್ನು ಹೊಂದಿದೆ ಎಂದು ದೃಢೀಕರಿಸುತ್ತದೆ,
  ಅಂದರೆ ಗಾರ್ಡ್ ನಿಜವಾಗಿಯೂ ವಿನಂತಿಯನ್ನು ತಿರಸ್ಕರಿಸಿದೆ.
- **`garak` (ಸಲಹಾತ್ಮಕ)** — ಸ್ಥಳೀಯ OmniRoute ಇನ್ಸ್ಟನ್ಸ್
  (`http://localhost:20128/v1`) ವಿರುದ್ಧ garak `--probes promptinject,dan,leakreplay`
  ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಇದು ಪ್ರೊವೈಡರ್ ಸೀಕ್ರೆಟ್ (`PROMPTFOO_PROVIDER_KEY`) ಮೇಲೆ
  ಅವಲಂಬಿತವಾಗಿದೆ; ಸೀಕ್ರೆಟ್ ಇಲ್ಲದಿದ್ದರೆ ಸರಾಗವಾಗಿ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ ಮತ್ತು `|| true`
  ಪ್ರತ್ಯಯವನ್ನು ಹೊಂದಿರುತ್ತದೆ, ಆದ್ದರಿಂದ CI ವಿಫಲಗೊಳಿಸದೆಯೇ ವರದಿ ಮಾಡುತ್ತದೆ.
