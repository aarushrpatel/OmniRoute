## ಅವಲೋಕನ

ಎಲ್ಲಾ OmniRoute ನಿರ್ವಹಣಾ API ಮಾರ್ಗಗಳನ್ನು ಮೂರು ರಕ್ಷಣಾ ಹಂತಗಳಲ್ಲಿ ಒಂದಕ್ಕೆ
ವರ್ಗೀಕರಿಸಲಾಗಿದೆ. ವರ್ಗೀಕರಣವು ಸ್ಥಿರವಾಗಿದ್ದು, `src/server/authz/routeGuard.ts` ನಲ್ಲಿ
ವ್ಯಾಖ್ಯಾನಿಸಲಾಗಿದೆ ಮತ್ತು ಇತರ ಯಾವುದೇ ದೃಢೀಕರಣ ಶಾಖೆ ಕಾರ್ಯನಿರ್ವಹಿಸುವ ಮೊದಲು ಮೌಲ್ಯಮಾಪನ ಮಾಡಲಾಗುತ್ತದೆ.

## ಹಂತಗಳು

### ಹಂತ 1 — LOCAL_ONLY

**ಜಾರಿಗೊಳಿಸುವುದು:** `isLocalOnlyPath(path)` → ಲೂಪ್ಬ್ಯಾಕ್ ಹೋಸ್ಟ್ ಪರಿಶೀಲನೆ  
**ಬೈಪಾಸ್:** ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಯಾವುದೂ ಇಲ್ಲ. ವಿನಂತಿಯು `manage` ಸ್ಕೋಪ್ ಹೊಂದಿರುವ ಮಾನ್ಯ API ಕೀಲಿಯನ್ನು ಒಳಗೊಂಡಿರುವಾಗ, `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ನಲ್ಲಿನ ಪಥಗಳಿಗೆ ಮಾತ್ರ ಸೀಮಿತ ವಿನಾಯಿತಿ ಅನ್ವಯಿಸುತ್ತದೆ ([Manage-scope ವಿನಾಯಿತಿ](#manage-scope-carve-out) ನೋಡಿ).

ಈ ರೂಟ್ಗಳು ಚೈಲ್ಡ್ ಪ್ರೊಸೆಸ್ಗಳನ್ನು ಪ್ರಾರಂಭಿಸುತ್ತವೆ ಅಥವಾ ರನ್ಟೈಮ್ ಕೋಡ್ ಅನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುತ್ತವೆ. ಇವುಗಳನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಟ್ರಾಫಿಕ್ಗೆ ತೆರೆದಿಡುವುದರಿಂದ, ಮಾನ್ಯ JWT ಅನ್ನು ಪಡೆದಿರುವ ಆಕ್ರಮಣಕಾರನು (ಉದಾ., Cloudflared/Ngrok ಟನಲ್ ಮೂಲಕ) ಪ್ರೊಸೆಸ್ಗಳನ್ನು ಪ್ರಾರಂಭಿಸಲು ಸಾಧ್ಯವಾಗುತ್ತದೆ — ಇದು ತಿಳಿದಿರುವ CVE ವರ್ಗವಾಗಿದೆ ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj ಎಂದರೇನು (ಆಕ್ರಮಣದ ವರ್ಗ):** ಒಂದು ನಿರ್ವಹಣಾ/ಏಜೆಂಟ್ ಸರ್ವರ್ ಉಪಪ್ರಕ್ರಿಯೆಯನ್ನು (`npm install`, `node`, ಬ್ರೌಸರ್, ಪ್ರಾಕ್ಸಿ, `git`, `tar`, …) ಪ್ರಾರಂಭಿಸುವ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ. ಆ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಹೋಸ್ಟ್ನ ಹೊರಗಿನಿಂದ ತಲುಪಲು ಸಾಧ್ಯವಾದರೆ — ಆಪರೇಟರ್ OmniRoute ಅನ್ನು nginx/Cloudflare/Tailscale ಟನಲ್ನ ಹಿಂದೆ ಇರಿಸಿರುವುದರಿಂದ ಮತ್ತು JWT ಸೋರಿಕೆಯಾಗಿರುವುದರಿಂದ, ಅಥವಾ ದೃಢೀಕರಣವನ್ನು ತಪ್ಪಾಗಿ ಸಂರಚಿಸಿರುವುದರಿಂದ — ಆಕ್ರಮಣಕಾರನು "API ಅನ್ನು ಕರೆಮಾಡುವುದನ್ನು" "ಹೋಸ್ಟ್ನಲ್ಲಿ ಕಮಾಂಡ್ ಚಲಾಯಿಸುವುದಾಗಿ" (ರಿಮೋಟ್ ಕೋಡ್ ಎಕ್ಸಿಕ್ಯೂಷನ್) ಪರಿವರ್ತಿಸುತ್ತಾನೆ. ಸ್ಪಾನ್ ಮಾಡಲು ಸಮರ್ಥವಾಗಿರುವ ಪ್ರತಿಯೊಂದು ರೂಟ್ನಲ್ಲೂ, **ಯಾವುದೇ ದೃಢೀಕರಣ ಪರಿಶೀಲನೆಗೆ ಮುನ್ನ, ಷರತ್ತುರಹಿತವಾಗಿ ಲೂಪ್ಬ್ಯಾಕ್ ಹೋಸ್ಟ್ ಪರಿಶೀಲನೆಯನ್ನು** ಜಾರಿಗೊಳಿಸುವ ಮೂಲಕ OmniRoute ಇದನ್ನು ತಡೆಯುತ್ತದೆ: ಟನಲ್ ಮೂಲಕ ಸೋರಿಕೆಯಾದ ಟೋಕನ್ ಇದ್ದರೂ ಸ್ಪಾನ್ ಅನ್ನು ತಲುಪಲು ಸಾಧ್ಯವಿಲ್ಲ.

**ಸಂಪೂರ್ಣ LOCAL_ONLY ಸಮೂಹ.** ಅಧಿಕೃತ ಮೂಲವು `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ಆಗಿದೆ; ಕೆಳಗಿನ ಕೋಷ್ಟಕವು ಪ್ರಸ್ತುತ ಸ್ಥಿತಿಯನ್ನು ಪ್ರತಿಬಿಂಬಿಸುತ್ತದೆ. `check-route-guard-membership` ಗೇಟ್ ಸ್ಪಾನ್ ಮಾಡಲು ಸಮರ್ಥವಾಗಿರುವ ಪ್ರಿಫಿಕ್ಸ್ಗಳ ಅಡಿಯಲ್ಲಿರುವ ಪ್ರತಿಯೊಂದು `route.ts` ಅನ್ನು ಎಣಿಸುತ್ತದೆ ಮತ್ತು ಅವುಗಳಲ್ಲಿ ಯಾವುದಾದರೂ ಲೋಕಲ್-ಓನ್ಲಿ ಎಂದು ವರ್ಗೀಕರಿಸದಿದ್ದರೆ CI ವಿಫಲಗೊಳ್ಳುತ್ತದೆ.

#### ನಿರ್ವಹಣಾ-ವ್ಯಾಪ್ತಿಯ ವಿನಾಯಿತಿ

ವಿನಂತಿಯು `Authorization: Bearer <api-key>` ಅನ್ನು ಹೊಂದಿದ್ದು, ಅದರ
ಮೆಟಾಡೇಟಾದಲ್ಲಿ `manage` ವ್ಯಾಪ್ತಿ (ಅಥವಾ `admin`) ಇದ್ದರೆ ಮತ್ತು ಇದ್ದಾಗ ಮಾತ್ರ,
LOCAL_ONLY ಪಥಗಳ ಒಂದು ಉಪಸಮೂಹವನ್ನು ನಾನ್-ಲೂಪ್ಬ್ಯಾಕ್ನಿಂದಲೂ ಪ್ರವೇಶಿಸಬಹುದು.
ಪ್ರತಿ ಪಥಕ್ಕೂ ಈ ವಿನಾಯಿತಿಯನ್ನು `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ಮೂಲಕ
ಸ್ಪಷ್ಟವಾಗಿ ನಿಯಂತ್ರಿಸಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಯಾವುದೇ ಹೊಸ LOCAL_ONLY ಪಥದ ಪೂರ್ವನಿಯೋಜಿತ
ನಿಯಮವು ಕಟ್ಟುನಿಟ್ಟಾದ-ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ. ದೃಢೀಕರಿಸದ ವಿನಂತಿಗಳು ಮತ್ತು
ನಿರ್ವಹಣಾ ವ್ಯಾಪ್ತಿಯಿಲ್ಲದ ಕೀಗಳನ್ನು ಹೊಂದಿರುವ ವಿನಂತಿಗಳು ಇನ್ನೂ
`403 LOCAL_ONLY` ಮೂಲಕ ತಿರಸ್ಕರಿಸಲ್ಪಡುತ್ತವೆ.

ಪ್ರಸ್ತುತ ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದ ಏಕೈಕ ಪೂರ್ವಪ್ರತ್ಯಯ `/api/mcp/` ಆಗಿದೆ. `/api/cli-tools/runtime/` ಮತ್ತು
`/api/services/` ಅನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಹೊರಗಿಡಲಾಗಿದೆ, ಏಕೆಂದರೆ ಅವು ಅನಿಯಂತ್ರಿತ
ಉಪಪ್ರಕ್ರಿಯೆಗಳನ್ನು (`npm install`, `node`) ಸ್ಪಾನ್ ಮಾಡಬಲ್ಲವು; ಇದೇ ನಿಖರವಾದ CVE ವರ್ಗವನ್ನು
ತಡೆಯಲು LOCAL_ONLY ಹಂತವು ಅಸ್ತಿತ್ವದಲ್ಲಿದೆ.

#### ಆಪರೇಟರ್ ಮಾರ್ಗದರ್ಶನ ಮತ್ತು ಆಡಿಟಿಂಗ್

ನೀವು OmniRoute ಅನ್ನು ರಿವರ್ಸ್ ಪ್ರಾಕ್ಸಿ ಅಥವಾ ಟನಲ್ನ (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) ಹಿಂದೆ ಚಲಾಯಿಸಿದರೆ, ಲೂಪ್ಬ್ಯಾಕ್ ಪರಿಶೀಲನೆಯು ಮೇಲಿನ
ಸ್ಪಾನ್-ಸಾಮರ್ಥ್ಯವಿರುವ ರೂಟ್ಗಳನ್ನು ಇನ್ನೂ ರಕ್ಷಿಸುತ್ತದೆ — ಕ್ಲೈಂಟ್ ವಿಳಾಸವು ನಾನ್-ಲೂಪ್ಬ್ಯಾಕ್
ಆಗಿರುವ ವಿನಂತಿಯನ್ನು **ದೃಢೀಕರಣ ನಡೆಯುವ ಮೊದಲೇ** `403 LOCAL_ONLY` ಮೂಲಕ ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ,
ಆದ್ದರಿಂದ ಸೋರಿಕೆಯಾದ JWT ಸ್ಪಾನ್ವರೆಗೆ ತಲುಪಲು ಸಾಧ್ಯವಿಲ್ಲ. ಆಪರೇಟರ್ಗಳಿಗೆ ಎರಡು
ಜವಾಬ್ದಾರಿಗಳು ಉಳಿದಿವೆ:

- **ಕ್ಲೈಂಟ್ IP ಅನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ ಎಂದು ನಕಲಿ ಸೃಷ್ಟಿಸುವ ಮೂಲಕ 403 ಅನ್ನು "ಸರಿಪಡಿಸಬೇಡಿ".** `X-Forwarded-For: 127.0.0.1` ಅನ್ನು ಹೊಂದಿಸುವುದು ಅಥವಾ ಮೂಲ ವಿಳಾಸವನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ಗೆ ಮರುಬರೆಯುವ ಪ್ರಾಕ್ಸಿಯನ್ನು ಬಳಸುವುದು, ಈ ಹಂತವು ಮುಚ್ಚುವ ಅದೇ RCE ವರ್ಗವನ್ನು ಪುನಃ ತೆರೆಯುತ್ತದೆ. ಪ್ರಾಕ್ಸಿಯ ಮೂಲಕ dashboard/API ಅನ್ನು ಬಹಿರಂಗಪಡಿಸಿ — spawn-ಸಾಮರ್ಥ್ಯವಿರುವ ಮಾರ್ಗಗಳನ್ನು ಎಂದಿಗೂ ಬಹಿರಂಗಪಡಿಸಬೇಡಿ.
- **manage-scope ಬೈಪಾಸ್ ಅನ್ನು ಕನಿಷ್ಠ ಮಟ್ಟದಲ್ಲಿಡಿ.** `/api/mcp/` ಅನ್ನು ಮಾತ್ರ ಬೈಪಾಸ್ ಮಾಡಬಹುದು, ಮತ್ತು ಅದು `manage`-ಸ್ಕೋಪ್ ಹೊಂದಿರುವ API ಕೀಲಿಯೊಂದಿಗೆ ಮಾತ್ರ. `SPAWN_CAPABLE_PREFIXES` ಅನ್ನು ಬೈಪಾಸ್ ಪಟ್ಟಿಗೆ ಎಂದಿಗೂ ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ — zod ಸ್ಕೀಮಾ ಅವುಗಳನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ ಮತ್ತು `isLocalOnlyBypassableByManageScope` ರನ್ಟೈಮ್ನಲ್ಲಿ ಅವುಗಳನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ (ಆಳವಾದ ರಕ್ಷಣೆ), dashboard ನಲ್ಲಿ "ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದಂತೆ ರೂಪಿಸಲಾಗುವುದಿಲ್ಲ" ಎಂದು ಹೇಳುವುದರ ಅರ್ಥ ಇದೇ. ರನ್ಟೈಮ್ snapshot ಲೋಡರ್ ಸಹ ಸಂಗ್ರಹಿಸಿದ settings ಸಾಲಿನಿಂದ ಅಂತಹ ನಮೂದುಗಳನ್ನು ತೆಗೆದುಹಾಕುತ್ತದೆ, ಮತ್ತು legacy JSON import (`/api/settings/import-json`) ಬೈಪಾಸ್ ಕೀಲಿಗಳನ್ನು ಎಂದಿಗೂ ಬರೆಯುವುದಿಲ್ಲ. ಪ್ರತಿಯೊಂದು `LOCAL_ONLY_API_PREFIXES` ನಮೂದು deny-list ನಲ್ಲಿ ಇರಬೇಕು ಅಥವಾ ಬೈಪಾಸ್ಗೆ ಅರ್ಹವೇ ಎಂದು ಪರಿಶೀಲಿಸಲ್ಪಟ್ಟಿರಬೇಕು (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). `/api/providers/` ಅಡಿಯಲ್ಲಿರುವ dynamic-segment ಮತ್ತು static-path spawn-ಸಾಮರ್ಥ್ಯದ ಮಾರ್ಗಗಳು (ಉದಾ. `/login`, `/refresh-cursor`) `src/shared/constants/spawnCapablePrefixes.ts` ನಲ್ಲಿರುವ regex-ಆಧಾರಿತ `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` ಸಹಚರದಿಂದ ಒಳಗೊಳ್ಳುತ್ತವೆ, ಸಮತಟ್ಟಾದ `SPAWN_CAPABLE_PREFIXES` array ನಿಂದ ಅಲ್ಲ — ಅವುಗಳನ್ನು ಹಿಡಿಯಲು ಸಮತಟ್ಟಾದ array ಸಂಪೂರ್ಣ `/api/providers/` prefix ಅನ್ನು ಒಳಗೊಳ್ಳಬೇಕಾಗುತ್ತದೆ; ಇದರಿಂದ ದೂರಸ್ಥ dashboards ಗಳು provider CRUD ಗಾಗಿ ನ್ಯಾಯಸಮ್ಮತವಾಗಿ ಬಳಸುವ route tree ಅತಿಯಾಗಿ ವಿಸ್ತರಿಸುತ್ತದೆ.

**ಪ್ರವೇಶದ ಆಡಿಟಿಂಗ್** — host ಹೊರಗಿನಿಂದ ಯಾವುದೂ ಈ ಮಾರ್ಗಗಳನ್ನು ತಲುಪುತ್ತಿಲ್ಲ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಲು:

- `/dashboard/settings/security` ನಲ್ಲಿ **Authorization Inventory** ತೆರೆಯಿರಿ: ಇದು live LOCAL_ONLY prefix ಪಟ್ಟಿ, ಯಾವ prefixes ಗಳನ್ನು ಬೈಪಾಸ್ ಮಾಡಬಹುದು, ಮತ್ತು compile-time spawn-ಸಾಮರ್ಥ್ಯದ ("ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದಂತೆ ರೂಪಿಸಲಾಗುವುದಿಲ್ಲ") ಗುಚ್ಛವನ್ನು ಪ್ರದರ್ಶಿಸುತ್ತದೆ.
- ಮೇಲಿನ prefixes ಗಳನ್ನು loopback ಅಲ್ಲದ ಕ್ಲೈಂಟ್ ವಿಳಾಸದೊಂದಿಗೆ ಜೋಡಿಸಿ ನಿಮ್ಮ reverse-proxy / access logs ನಲ್ಲಿ grep ಮಾಡಿ. ಅಂತಹ ಯಾವುದೇ hit `403 LOCAL_ONLY` ಬದಲಿಗೆ `200` ಅನ್ನು ಹಿಂದಿರುಗಿಸಿದ್ದರೆ, ಪ್ರಾಕ್ಸಿಯು ನಿಜವಾದ ಕ್ಲೈಂಟ್ IP ಅನ್ನು ಮರೆಮಾಡುತ್ತಿದೆ ಎಂದರ್ಥ — ಪ್ರಾಕ್ಸಿಯನ್ನು ಸರಿಪಡಿಸಿ.
- ಈ ಮಾರ್ಗಗಳಲ್ಲಿ ಒಂದಕ್ಕಾಗಿ OmniRoute ನ logs ನಲ್ಲಿ ಕಾಣುವ `403 LOCAL_ONLY`, guard ಉದ್ದೇಶಿಸಿದಂತೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿದೆ ಎಂಬುದನ್ನು ಸೂಚಿಸುತ್ತದೆ; ಅದು ನಿಗ್ರಹಿಸಬೇಕಾದ ದೋಷವಲ್ಲ.

### ಹಂತ 2 — ALWAYS_PROTECTED

**ಇದರಿಂದ ಜಾರಿಗೊಳಿಸಲಾಗಿದೆ:** `isAlwaysProtectedPath(path)` → `requireLogin=false` ಬೈಪಾಸ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ  
**ಬೈಪಾಸ್:** `requireLogin=false` ಆಗಿರುವಾಗ ಯಾವುದೂ ಇಲ್ಲ; JWT ಯಾವಾಗಲೂ ಅಗತ್ಯ

ಈ ಮಾರ್ಗಗಳು ವಿನಾಶಕಾರಿ ಅಥವಾ ಹಿಂತಿರುಗಿಸಲಾಗದವು. "no-password" ಸ್ಥಾಪನೆಯಲ್ಲಿ ಇವುಗಳನ್ನು ಅನುಮತಿಸುವುದರಿಂದ, ಅದೇ LAN ನಲ್ಲಿರುವ ಯಾರಾದರೂ database ಅನ್ನು ಅಳಿಸಲು ಅಥವಾ server process ಅನ್ನು ಸ್ಥಗಿತಗೊಳಿಸಲು ಸಾಧ್ಯವಾಗುತ್ತದೆ.

| ಮಾರ್ಗ                                     | ಕಾರಣ                                                                      |
| ----------------------------------------- | ------------------------------------------------------------------------- |
| `/api/shutdown`                           | server process ಅನ್ನು ಕೊನೆಗೊಳಿಸುತ್ತದೆ                                      |
| `/api/settings/database`                  | database export, import ಮತ್ತು wipe                                        |
| `/api/db-backups`                         | ಪೂರ್ಣ database backup archive ಪ್ರವೇಶ                                      |
| `/api/settings/export-json`               | ಪೂರ್ಣ settings blob ಅನ್ನು export ಮಾಡುತ್ತದೆ (ರಹಸ್ಯಗಳನ್ನೂ ಒಳಗೊಂಡಂತೆ)        |
| `/api/settings/import-json`               | ಪೂರ್ಣ settings blob ಅನ್ನು ಬದಲಿಸುತ್ತದೆ                                     |
| `/api/providers/health-autopilot/actions` | autopilot remediation actions ಅನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುತ್ತದೆ                    |
| `/api/settings/obsidian`                  | ಯಾವುದೇ vault root ಗಾಗಿ ಮರುಬಳಕೆ ಮಾಡಬಹುದಾದ WebDAV creds ಅನ್ನು ಸೃಷ್ಟಿಸುತ್ತದೆ |

**ಉಲ್ಲಂಘನೆಯಾದಾಗ ಪ್ರತಿಕ್ರಿಯೆ:** `401 Authentication required`

`/api/settings/obsidian` ಅದರ `/webdav` child ಅನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ: `POST`, Next.js ಗಿಂತ ಮೊದಲು custom Node layer ಮೂಲಕ ಈ pipeline ಹೊರಗೆ ಸೇವೆ ಒದಗಿಸಲಾಗುವ WebDAV file service ಅನ್ನು caller ಆಯ್ಕೆಮಾಡಿದ root ಗೆ ಸೂಚಿಸುತ್ತದೆ ಮತ್ತು ಹೊಸದಾಗಿ ಸೃಷ್ಟಿಸಿದ Basic credentials ಅನ್ನು ಮರಳಿ ಪ್ರತಿಧ್ವನಿಸುತ್ತದೆ; `DELETE` ಅವುಗಳನ್ನು rotate ಮಾಡುತ್ತದೆ; ಮತ್ತು parent `POST`, Obsidian REST API token ಅನ್ನು ಸಂಗ್ರಹಿಸುತ್ತದೆ. GHSA-62vw ಕೇವಲ `GET` password ಬಹಿರಂಗಪಡಿಸುವಿಕೆಯನ್ನು ಮರೆಮಾಡಿತ್ತು; issuance ಇನ್ನೂ fail-open ಹಂತದಲ್ಲೇ ಇತ್ತು (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` ಹೆಚ್ಚುವರಿಯಾಗಿ data directory ಆಗಿರುವ, ಅದರೊಳಗೆ ಇರುವ, ಅಥವಾ ಅದನ್ನು ಒಳಗೊಂಡಿರುವ vault ಅನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ.

### ಹೊಸ ಸ್ಥಾಪನೆಯ bootstrap ಲೂಪ್ಬ್ಯಾಕ್ಗೆ ಮಾತ್ರ — ನಿಜವಾದ peer ಆಧಾರಿತ, `Host` ಆಧಾರಿತವಲ್ಲ

ಯಾವುದೇ management password ಸಂರಚಿಸದಿದ್ದಾಗ (ಮತ್ತು `INITIAL_PASSWORD` ಇಲ್ಲದಿದ್ದಾಗ), `src/shared/utils/apiAuth.ts` ನಲ್ಲಿನ `isAuthRequired()` ಅನಾಮಧೇಯ bootstrap ಅನ್ನು **loopback peers ಗಾಗಿ ಮಾತ್ರ** ತೆರೆದಿಡುತ್ತದೆ. ವಿಶ್ವಾಸಾರ್ಹ peer signals ಗಳಿಂದ ಈ ಕ್ರಮದಲ್ಲಿ loopback ಅನ್ನು ನಿರ್ಧರಿಸಲಾಗುತ್ತದೆ: token-stamped ನಿಜವಾದ TCP peer (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, policy ನೋಡುವುದು), pipeline ನ ಸ್ವಂತ `AUTHZ_HEADER_PEER_LOCALITY` verdict (route handlers ನೋಡುವುದು, `OMNIROUTE_PEER_STAMP_TOKEN` ಹೊಂದಿಸಿರುವಾಗ ಮಾತ್ರ ವಿಶ್ವಾಸಾರ್ಹ), ಅಥವಾ ನೇರ callers ಗಾಗಿ ನಿಜವಾದ socket peer. `Host` / `nextUrl.hostname` ಅನ್ನು ಎಂದಿಗೂ ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ, ಮತ್ತು ಮೊದಲ-password ಬರವಣಿಗೆಯು (`POST /api/settings/require-login`) ಪ್ರತಿಯೊಂದು network peer ಗೆ ತೆರೆದಿರುವ ಬದಲು ಇದೇ ನಿರ್ಬಂಧಕ್ಕೆ ಒಳಪಟ್ಟಿರುತ್ತದೆ (GHSA-7pq4-8pvv-rx7r). `managementPolicy` ತನ್ನದೇ ಆದ `peerContext` verdict ಅನ್ನು ಕೆಳಕ್ಕೆ ಸ್ಪಷ್ಟವಾಗಿ ರವಾನಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ORIGINAL (strip ಮಾಡುವುದಕ್ಕಿಂತ ಮುಂಚಿನ) request ನ headers ಅದನ್ನು ಎಂದಿಗೂ ನಿರ್ಧರಿಸುವುದಿಲ್ಲ.

### ಹಂತ 3 — MANAGEMENT (ಡೀಫಾಲ್ಟ್)

ಇತರೆ ಎಲ್ಲಾ management ಮಾರ್ಗಗಳು. `requireLogin=false` ಅನ್ನು ಸಂರಚಿಸದ ಹೊರತು auth ಅಗತ್ಯವಿದೆ. CLI tokens ಈ ಮಾರ್ಗಗಳನ್ನು authenticate ಮಾಡಬಹುದು (loopback + ಮಾನ್ಯ HMAC).

## ಮೌಲ್ಯಮಾಪನ ಕ್ರಮ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → ಲೂಪ್ಬ್ಯಾಕ್                                  → ಮುಂದುವರಿಸಿ
     → ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ, manage-scope Bearer
        ಮತ್ತು isLocalOnlyBypassableByManageScope   → ಅನುಮತಿಸಿ (management_key)
     → ಇಲ್ಲದಿದ್ದರೆ                                  → 403 LOCAL_ONLY ತಿರಸ್ಕರಿಸಿ
  2. isInternalModelSyncRequest(ctx)?
     → ಅನುಮತಿಸಿ (system)
  3. hasValidCliToken(headers)?
     → ಅನುಮತಿಸಿ (cli) [ಲೂಪ್ಬ್ಯಾಕ್ + timingSafeEqual HMAC ಪರಿಶೀಲನೆ]
  4. isAlwaysProtectedPath(path) ಅಥವಾ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → ಅನುಮತಿಸಿ (dashboard_session)
     → ಬೈಪಾಸ್ ಮಾಡಲಾಗದ ಪಥದಲ್ಲಿ manage-scope Bearer?
        → ಅನುಮತಿಸಿ (management_key)
     → 401/403 ತಿರಸ್ಕರಿಸಿ
  5. requireLogin=false?
     → ಅನುಮತಿಸಿ (anonymous)
```

ಹಂತ 1ರ manage-scope ಶಾಖೆಯು LOCAL_ONLY ಮಾರ್ಗವನ್ನು ಪೂರೈಸಬಲ್ಲ ಏಕೈಕ ದೃಢೀಕೃತ ಪಥವಾಗಿದೆ; ಅವಧಿ ಮೀರಿದ DB ಸದ್ದಿಲ್ಲದೆ "ನಿರಾಕರಿಸಿ" ಎಂಬುದಕ್ಕೆ ಕೆಳದರ್ಜೆಗಿಳಿಯದಂತೆ auth-backend ವೈಫಲ್ಯ ಸ್ಥಿತಿಯು 503 ಅನ್ನು (403 ಅಲ್ಲ) ಹಿಂದಿರುಗಿಸುತ್ತದೆ.

## ಹೊಸ spawn-ಸಾಮರ್ಥ್ಯವುಳ್ಳ ಮಾರ್ಗವನ್ನು ಸೇರಿಸುವುದು

1. `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_API_PREFIXES` ಗೆ ಪಥದ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಿ
2. ಹೊಸ ಪೂರ್ವಪ್ರತ್ಯಯಕ್ಕಾಗಿ `isLocalOnlyPath()` true ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ ಎಂದು ದೃಢಪಡಿಸುವ ಪರೀಕ್ಷೆಯನ್ನು `tests/unit/authz/routeGuard.test.ts` ನಲ್ಲಿ ಸೇರಿಸಿ
3. **ಈ ಹಂತವನ್ನು ಎಂದಿಗೂ ಬಿಟ್ಟುಬಿಡಬೇಡಿ** — `CLAUDE.md` ನಲ್ಲಿರುವ ಕಠಿಣ ನಿಯಮ #15 ಅನ್ನು ನೋಡಿ
4. ನಿರ್ಧರಿಸಿ: ಈ ಮಾರ್ಗವು `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ನಲ್ಲಿಯೂ ಇರಬೇಕೇ?
   ಪೂರ್ವನಿಯೋಜಿತ ಉತ್ತರ **ಇಲ್ಲ**. manage-scope ಹೊಂದಿರುವವರಿಗೆ ಮಾರ್ಗವನ್ನು ಬಹಿರಂಗಪಡಿಸುವುದು ಸುರಕ್ಷಿತವಾಗಿರುವಾಗ ಮಾತ್ರ ಆಯ್ಕೆಮಾಡಿ (ಅಂದರೆ, ಅದು ಬಳಕೆದಾರ-ನಿಯಂತ್ರಿತ ಯಾವುದೇ ಕೋಡ್ ಅನ್ನು spawn ಮಾಡುವುದಿಲ್ಲ).

## manage-scope ಮೂಲಕ ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದ ಪಥವನ್ನು ಸೇರಿಸುವುದು

1. ಮಾರ್ಗವು ಬಳಕೆದಾರರು ಒದಗಿಸಿದ ಕೋಡ್ ಅಥವಾ ಆದೇಶಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುವುದಿಲ್ಲ ಎಂಬುದನ್ನು ದೃಢಪಡಿಸಿ. ಅದು ಹಾಗೆ ಮಾಡುತ್ತಿದ್ದರೆ, ನಿಲ್ಲಿಸಿ — ಈ ವಿನಾಯಿತಿಯು ತಪ್ಪಾದ ಸಾಧನವಾಗಿದೆ.
2. `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ಗೆ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಿ
3. ಎಲ್ಲಾ ನಾಲ್ಕು ವಿನಂತಿ ಸ್ವರೂಪಗಳಿಗಾಗಿ `tests/unit/authz/management-policy.test.ts` ನಲ್ಲಿ ವ್ಯಾಪ್ತಿಯನ್ನು ಸೇರಿಸಿ: Bearer ಇಲ್ಲ (403), manage Bearer (ಅನುಮತಿಸಿ), manage ಅಲ್ಲದ Bearer (403), ಮತ್ತು manage Bearer ಇದ್ದರೂ `/api/cli-tools/runtime/*` ಕಟ್ಟುನಿಟ್ಟಾಗಿ ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ ಎಂಬ ಪ್ರತಿ-ಪೂರ್ವಪ್ರತ್ಯಯ ಹಿಂಜರಿತ ಪರೀಕ್ಷೆ.

## OpenAPI ನಲ್ಲಿ ಭದ್ರತಾ ಹಂತಗಳನ್ನು ದಾಖಲಿಸುವುದು

`docs/openapi.yaml` ಗೆ ಹೊಸ ಮಾರ್ಗವನ್ನು ಸೇರಿಸುವಾಗ, ಮಾರ್ಗವನ್ನು `routeGuard.ts` ವರ್ಗೀಕರಿಸಿದ್ದರೆ ಅದಕ್ಕೆ ಅನುಗುಣವಾದ vendor extension ಅನ್ನು ಅನ್ವಯಿಸಿ:

| routeGuard.ts ವರ್ಗೀಕರಣ                     | YAML ಟಿಪ್ಪಣಿ                | ಜಾರಿಗೊಳಿಸುವಿಕೆ                                                     |
| ------------------------------------------ | --------------------------- | ------------------------------------------------------------------ |
| `LOCAL_ONLY_API_PREFIXES`                  | `x-loopback-only: true`     | ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಮೂಲಗಳಿಂದ ಬರುವುದನ್ನು ಬೇಷರತ್ತಾಗಿ ನಿರ್ಬಂಧಿಸಲಾಗುತ್ತದೆ |
| `ALWAYS_PROTECTED_API_PATHS`               | `x-always-protected: true`  | `requireLogin=false` ಇದ್ದರೂ ದೃಢೀಕರಣ ಅಗತ್ಯವಿದೆ                      |
| ಆಂತರಿಕ admin/debug ಮಾರ್ಗ                   | `x-internal: true`          | ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ /dashboard/api-endpoints ನಿಂದ ಮರೆಮಾಡಲಾಗುತ್ತದೆ     |
| ಯಾವುದೂ ಇಲ್ಲ (ಸಾರ್ವಜನಿಕ / ಪ್ರಮಾಣಿತ ದೃಢೀಕರಣ) | (ಯಾವುದೇ ಟಿಪ್ಪಣಿ ಅಗತ್ಯವಿಲ್ಲ) | ಪ್ರಮಾಣಿತ `requireLogin`-ನಿಯಂತ್ರಿತ ಪ್ರವೇಶ                           |

### ಮೌಲ್ಯೀಕರಣ

ಎರಡು ಸ್ಕ್ರಿಪ್ಟ್ಗಳು YAML ಟಿಪ್ಪಣಿಗಳು ಮತ್ತು `routeGuard.ts` ನಡುವಿನ ಸ್ಥಿರತೆಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ:

- `scripts/check/check-openapi-coverage.mjs` — ವ್ಯಾಪ್ತಿ < 99% ಆಗಿದ್ದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` ಅಥವಾ
  `x-always-protected` ಟಿಪ್ಪಣಿಗಳು compile-time ಸ್ಥಿರಾಂಕಗಳಿಂದ ಭಿನ್ನವಾಗಿದ್ದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ

ಎರಡೂ ಸ್ಕ್ರಿಪ್ಟ್ಗಳು pre-commit hook ಮತ್ತು CI ನಲ್ಲಿ ಚಲಿಸುತ್ತವೆ.

### ತಪ್ಪು ಧನಾತ್ಮಕ ನಿಯಮ

`routeGuard.ts` ಸ್ಥಿರಾಂಕದಲ್ಲಿ ಇಲ್ಲದ ಮಾರ್ಗದ ಮೇಲೆ `x-always-protected` ಅಥವಾ `x-loopback-only` ಅನ್ನು ಟಿಪ್ಪಣಿಯಾಗಿ ಸೇರಿಸಿದರೆ, ವ್ಯಾಪ್ತಿ ಸ್ಕ್ರಿಪ್ಟ್ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ. ಸರಿಪಡಿಸುವ ವಿಧಾನವೆಂದರೆ ಯಾವಾಗಲೂ YAML ಅನ್ನು `routeGuard.ts` ನಿಜವಾಗಿ ಜಾರಿಗೊಳಿಸುವುದಕ್ಕೆ ಹೊಂದಿಸುವುದು — ಜಾರಿಗೊಳಿಸುವಿಕೆ ತರ್ಕವನ್ನೂ ಅನುಷ್ಠಾನಗೊಳಿಸದೆ `routeGuard.ts` ಗೆ ಮಾರ್ಗಗಳನ್ನು ಸೇರಿಸುವುದಲ್ಲ.
