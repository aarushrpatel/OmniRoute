## Overzicht

Alle OmniRoute-beheer-API-routes zijn ingedeeld in een van drie
beveiligingsniveaus. De classificatie is statisch, vastgelegd in
`src/server/authz/routeGuard.ts`, en wordt geëvalueerd voordat enige andere
authenticatievertakking wordt uitgevoerd.

## Niveaus

### Niveau 1 — LOCAL_ONLY

**Afgedwongen door:** `isLocalOnlyPath(path)` → controle op loopback-host
**Omzeiling:** Standaard geen. Beperkte uitzondering voor paden in
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` wanneer het verzoek een geldige
API-sleutel met het bereik `manage` bevat (zie [Uitzondering voor het manage-bereik](#manage-scope-carve-out)).

Deze routes starten onderliggende processen of voeren runtimecode uit. Als ze
toegankelijk zijn voor niet-loopbackverkeer, kan een aanvaller die een geldige JWT
heeft verkregen (bijvoorbeeld via een Cloudflared/Ngrok-tunnel) processen starten —
een bekende CVE-klasse
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Wat GHSA-fhh6-4qxv-rpqj is (de aanvalsklasse):** een beheer-/agentserver
stelt een endpoint beschikbaar dat een subproces start (`npm install`, `node`, een browser,
een proxy, `git`, `tar`, …). Als dat endpoint vanaf buiten de host bereikbaar is — omdat
de beheerder OmniRoute achter een nginx-/Cloudflare-/Tailscale-tunnel heeft geplaatst en een JWT
is gelekt, of de authenticatie onjuist was geconfigureerd — verandert de aanvaller „een API
aanroepen” in „een opdracht op de host uitvoeren” (uitvoering van externe code). OmniRoute voorkomt
dit door **onvoorwaardelijk, vóór elke authenticatiecontrole, een controle op de loopback-host af te dwingen**
voor elke route die processen kan starten: een gelekt token via een tunnel kan het starten van processen
nog steeds niet bereiken.

**De volledige LOCAL_ONLY-verzameling.** De gezaghebbende bron is
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` in
`src/server/authz/routeGuard.ts`; de onderstaande tabel weerspiegelt de huidige toestand. De
`check-route-guard-membership`-controle inventariseert elke `route.ts` onder de
prefixen die processen kunnen starten en laat CI mislukken als een daarvan niet als uitsluitend lokaal is geclassificeerd.

#### Uitzondering voor beheerscope

Een subset van LOCAL_ONLY-paden MAG ook vanaf niet-loopback-adressen worden
benaderd, uitsluitend als het verzoek een `Authorization: Bearer <api-key>`
bevat waarvan de metadata de scope `manage` (of `admin`) bevat. De uitzondering
wordt expliciet per pad beheerd via `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`,
zodat de standaard voor elk nieuw LOCAL_ONLY-pad strikt loopback blijft.
Niet-geverifieerde verzoeken en verzoeken met sleutels zonder beheerscope
worden nog steeds afgewezen met `403 LOCAL_ONLY`.

Momenteel is `/api/mcp/` het enige prefix waarvoor omzeiling is toegestaan.
`/api/cli-tools/runtime/` en `/api/services/` zijn opzettelijk uitgesloten,
omdat ze willekeurige subprocessen kunnen starten (`npm install`, `node`),
wat precies de CVE-klasse is die de LOCAL_ONLY-laag moet voorkomen.

**#7895 — beperkte scope `mcp:connect`:** de uitzondering voor `/api/mcp/`
accepteert OOK een Bearer-sleutel met de beperkte scope `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), gecontroleerd
via `hasMcpConnectOrManageScope()` in
`src/server/authz/policies/management.ts`. Dit is UITSLUITEND beperkt tot
`/api/mcp/` — `mcp:connect` verleent geen rechten op enige andere beheerroute
(inclusief elk ander LOCAL_ONLY-omzeilingsprefix, mocht er ooit een worden
toegevoegd), en de scope is bewust uitgesloten van
`MANAGEMENT_API_KEY_SCOPES`. Een sleutel met `manage`/`admin` valt nog steeds
op exact dezelfde wijze onder de uitzondering; `mcp:connect` is een alternatief
met minder rechten voor externe aanroepers die uitsluitend MCP gebruiken en
geen brede beheerstoegang nodig hebben.

| Verzoek                                             | Pad                        | Resultaat                  |
| --------------------------------------------------- | -------------------------- | -------------------------- |
| Niet-loopback, geen Bearer                          | `/api/mcp/*`               | 403 LOCAL_ONLY             |
| Niet-loopback, Bearer met de scope `manage`         | `/api/mcp/*`               | Toestaan                   |
| Niet-loopback, Bearer met de scope `mcp:connect`    | `/api/mcp/*`               | Toestaan                   |
| Niet-loopback, Bearer zonder `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY             |
| Niet-loopback, Bearer met de scope `mcp:connect`    | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY             |
| Niet-loopback, Bearer met de scope `manage`         | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY             |
| Loopback, met eender welke/zonder Bearer            | elk LOCAL_ONLY-pad         | Toestaan (controle slaagt) |

#### Richtlijnen voor beheerders en auditing

Als u OmniRoute achter een reverse proxy of tunnel uitvoert (nginx, Caddy,
Cloudflare Tunnel, Tailscale, Ngrok), beschermt de loopbackcontrole nog steeds
de bovenstaande routes die processen kunnen starten — een verzoek waarvan het
clientadres geen loopback-adres is, wordt **voordat authenticatie plaatsvindt**
afgewezen met `403 LOCAL_ONLY`, zodat een gelekte JWT geen proces kan starten.
Er blijven twee verantwoordelijkheden voor de beheerder over:

- **Probeer een 403 niet te ‘verhelpen’ door het IP-adres van de client als loopback te vervalsen.** Het instellen van
  `X-Forwarded-For: 127.0.0.1`, of een proxy die het bronadres herschrijft naar
  loopback, maakt precies de RCE-klasse die deze laag afsluit opnieuw mogelijk. Stel het
  dashboard/de API beschikbaar via de proxy — nooit de routes die processen kunnen starten.
- **Houd de omzeiling via het `manage`-bereik minimaal.** Alleen `/api/mcp/` kan worden omzeild, en
  uitsluitend met een API-sleutel met het bereik `manage`. De `SPAWN_CAPABLE_PREFIXES` kunnen nooit aan
  de omzeilingslijst worden toegevoegd — het zod-schema weigert ze en
  `isLocalOnlyBypassableByManageScope` weigert ze tijdens runtime (gelaagde beveiliging),
  wat het dashboard bedoelt met ‘kan niet omzeilbaar worden gemaakt’. De loader voor runtime-
  snapshots verwijdert dergelijke vermeldingen ook uit een opgeslagen instellingenrij, en de
  verouderde JSON-import (`/api/settings/import-json`) schrijft de omzeilingssleutels nooit weg.
  Elke vermelding in `LOCAL_ONLY_API_PREFIXES` moet ofwel in de weigeringslijst staan, of
  zijn beoordeeld als geschikt voor omzeiling (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Routes met dynamische segmenten
  en statische paden onder `/api/providers/` die processen kunnen starten (bijv. `/login`,
  `/refresh-cursor`) vallen onder de op reguliere expressies gebaseerde begeleidende
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` in
  `src/shared/constants/spawnCapablePrefixes.ts`, niet onder de platte
  `SPAWN_CAPABLE_PREFIXES`-array — de platte array zou het volledige
  voorvoegsel `/api/providers/` moeten omvatten om deze routes te onderscheppen, waardoor een routestructuur
  die externe dashboards rechtmatig gebruiken voor CRUD-bewerkingen van providers te ruim zou worden afgeschermd.

**Toegang controleren** — om na te gaan of niets buiten de host deze routes bereikt:

- Open de **Autorisatie-inventaris** op `/dashboard/settings/security`: deze toont de
  actuele lijst met LOCAL_ONLY-voorvoegsels, welke voorvoegsels omzeilbaar zijn en de tijdens compilatie
  vastgelegde set van routes die processen kunnen starten (‘kan niet omzeilbaar worden gemaakt’).
- Doorzoek de logs van uw reverse proxy / toegangslogs op de bovenstaande voorvoegsels in combinatie met een
  clientadres dat geen loopback-adres is. Elke dergelijke aanvraag die `200` retourneerde in plaats van
  `403 LOCAL_ONLY`, betekent dat de proxy het echte IP-adres van de client maskeert — corrigeer de proxy.
- Een `403 LOCAL_ONLY` in de logs van OmniRoute voor een van deze paden betekent dat de beveiliging
  naar behoren werkt en is geen fout die moet worden onderdrukt.

### Laag 2 — ALWAYS_PROTECTED

**Afgedwongen door:** `isAlwaysProtectedPath(path)` → omzeiling via `requireLogin=false` overslaan
**Omzeiling:** Geen wanneer `requireLogin=false`; JWT is altijd vereist

Deze routes zijn destructief of onomkeerbaar. Als ze in een installatie ‘zonder wachtwoord’
zouden worden toegestaan, zou iedereen op hetzelfde LAN de database kunnen wissen of het
serverproces kunnen beëindigen.

| Pad                                       | Reden                                                                        |
| ----------------------------------------- | ---------------------------------------------------------------------------- |
| `/api/shutdown`                           | Beëindigt het serverproces                                                   |
| `/api/settings/database`                  | Database exporteren, importeren en wissen                                    |
| `/api/db-backups`                         | Toegang tot volledige databaseback-up-archieven                              |
| `/api/settings/export-json`               | Exporteert de volledige instellingenblob (incl. geheimen)                    |
| `/api/settings/import-json`               | Vervangt de volledige instellingenblob                                       |
| `/api/providers/health-autopilot/actions` | Voert herstelacties van de autopilot uit                                     |
| `/api/settings/obsidian`                  | Genereert herbruikbare WebDAV-inloggegevens voor elke hoofdmap van een kluis |

**Reactie bij overtreding:** `401 Authentication required`

`/api/settings/obsidian` omvat het onderliggende pad `/webdav`: `POST` laat de WebDAV-bestandsservice —
die door de aangepaste Node-laag vóór Next.js en buiten deze pipeline wordt aangeboden — verwijzen naar een door de aanroeper gekozen hoofdmap
en retourneert nieuw gegenereerde Basic-inloggegevens, `DELETE` roteert deze en de bovenliggende `POST` slaat
het REST API-token van Obsidian op. GHSA-62vw maskeerde alleen de onthulling van het wachtwoord via `GET`; de uitgifte
viel nog steeds onder de laag die bij een fout toegang toestaat (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` weigert bovendien
een kluis die de gegevensmap is, zich daarin bevindt of deze bevat.

### Bootstrap van een nieuwe installatie is alleen via loopback beschikbaar — op basis van de echte peer, niet van `Host`

Wanneer er geen beheerwachtwoord is ingesteld (en geen `INITIAL_PASSWORD`), houdt `isAuthRequired()` in
`src/shared/utils/apiAuth.ts` de anonieme bootstrap **alleen voor loopback-peers** open.
Loopback wordt bepaald aan de hand van de vertrouwde peersignalen, in deze volgorde: de met een token gemarkeerde echte TCP-peer
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, wat het beleid ziet), het eigen
`AUTHZ_HEADER_PEER_LOCALITY`-oordeel van de pipeline (wat routehandlers zien, alleen vertrouwd zolang
`OMNIROUTE_PEER_STAMP_TOKEN` is ingesteld), of een echte socketpeer voor rechtstreekse aanroepers. `Host` /
`nextUrl.hostname` worden nooit geraadpleegd, en het instellen van het eerste wachtwoord
(`POST /api/settings/require-login`) valt onder dezelfde beperking en staat dus niet open voor elke
netwerkpeer (GHSA-7pq4-8pvv-rx7r). `managementPolicy` geeft zijn eigen `peerContext`-oordeel
expliciet door, zodat de headers van de OORSPRONKELIJKE aanvraag (vóór verwijdering) dit nooit bepalen.

### Laag 3 — MANAGEMENT (standaard)

Alle overige beheerroutes. Authenticatie is vereist, tenzij `requireLogin=false` is
geconfigureerd. CLI-tokens kunnen zich voor deze routes authenticeren (loopback + geldige HMAC).

## Evaluatievolgorde

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → doorgaan
     → niet-loopback, Bearer met manage-scope
        EN isLocalOnlyBypassableByManageScope    → toestaan (management_key)
     → anders                                    → weigeren met 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → toestaan (system)
  3. hasValidCliToken(headers)?
     → toestaan (cli) [loopback + timingSafeEqual HMAC-controle]
  4. isAlwaysProtectedPath(path) of requireLogin=true?
     → isDashboardSessionAuthenticated?
        → toestaan (dashboard_session)
     → Bearer met manage-scope op een niet-omzeilbaar pad?
        → toestaan (management_key)
     → weigeren met 401/403
  5. requireLogin=false?
     → toestaan (anonymous)
```

De manage-scope-tak van stap 1 is het enige geauthenticeerde pad dat aan een
LOCAL_ONLY-route kan voldoen; de foutmodus van de authenticatiebackend retourneert 503
(niet 403), zodat een verlopen database niet stilzwijgend terugvalt op "weigeren".

## Een nieuwe route toevoegen die processen kan starten

1. Voeg het padprefix toe aan `LOCAL_ONLY_API_PREFIXES` in
   `src/server/authz/routeGuard.ts`
2. Voeg een test toe in `tests/unit/authz/routeGuard.test.ts` die bevestigt dat
   `isLocalOnlyPath()` true retourneert voor het nieuwe prefix
3. **Sla deze stap nooit over** — zie harde regel #15 in `CLAUDE.md`
4. Beslis: hoort deze route OOK in `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Het standaardantwoord is **nee**. Kies hier alleen expliciet voor wanneer de route
   veilig beschikbaar kan worden gesteld aan een houder van een manage-scope (d.w.z.
   dat deze GEEN willekeurige, door de gebruiker aangestuurde code start).

## Een pad toevoegen dat met manage-scope kan worden omzeild

1. Bevestig dat de route geen door de gebruiker aangeleverde code of opdrachten
   uitvoert. Als dat wel zo is, stop dan — deze uitzondering is hiervoor niet het
   juiste middel.
2. Voeg het prefix toe aan `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` in
   `src/server/authz/routeGuard.ts`
3. Voeg testdekking toe in `tests/unit/authz/management-policy.test.ts` voor alle vier
   aanvraagvormen: geen Bearer (403), manage-Bearer (toestaan), niet-manage-Bearer
   (403), en de regressietest per prefix die controleert dat `/api/cli-tools/runtime/*`
   strikt tot loopback beperkt blijft, zelfs met een manage-Bearer.

## Beveiligingsniveaus documenteren in OpenAPI

Pas bij het toevoegen van een nieuwe route aan `docs/openapi.yaml` de bijbehorende
leveranciersuitbreiding toe als de route door `routeGuard.ts` is geclassificeerd:

| routeGuard.ts-classificatie              | YAML-annotatie             | Handhaving                                            |
| ---------------------------------------- | -------------------------- | ----------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                | `x-loopback-only: true`    | Onvoorwaardelijk geblokkeerd voor niet-loopback       |
| `ALWAYS_PROTECTED_API_PATHS`             | `x-always-protected: true` | Authenticatie vereist, zelfs met `requireLogin=false` |
| Interne beheer-/debugroute               | `x-internal: true`         | Standaard verborgen voor /dashboard/api-endpoints     |
| Geen (openbaar / standaardauthenticatie) | (geen annotatie nodig)     | Standaardtoegang beheerd via `requireLogin`           |

### Validatie

Twee scripts dwingen consistentie af tussen YAML-annotaties en `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — mislukt als de dekking < 99% is
- `scripts/check/check-openapi-security-tiers.mjs` — mislukt als annotaties voor
  `x-loopback-only` of `x-always-protected` afwijken van de compile-time-constanten

Beide scripts worden uitgevoerd in de pre-commithaak en in CI.

### Regel voor fout-positieven

Als `x-always-protected` of `x-loopback-only` is geannoteerd op een route die NIET in
de constante van `routeGuard.ts` staat, mislukt het dekkingsscript. De oplossing is
altijd om de YAML af te stemmen op wat `routeGuard.ts` daadwerkelijk afdwingt — niet
om routes aan `routeGuard.ts` toe te voegen zonder ook de handhavingslogica te
implementeren.
