> **सत्याचा अधिकृत स्रोत:** `src/lib/guardrails/`
> **शेवटचे अद्यतन:** 2026-08-29 — v3.8.51 (Video Bridge प्रतिलेखाचा उगम कॉलरद्वारे घोषित केला जातो,
> अद्याप सर्व्हरद्वारे सत्यापित केलेला नाही — #11661 नुसार स्पष्टीकरण दिले)

Guardrails, OmniRoute आणि अपस्ट्रीम प्रदात्यांच्या सीमेवर सुरक्षितता, धोरणे आणि आशय रूपांतरे लागू करतात. प्रत्येक guardrail विनंती payloads (`preCall`) आणि अपस्ट्रीम प्रतिसाद (`postCall`) तपासू शकतो (आणि पर्यायाने नाकारू, रूपांतरित करू किंवा त्यांवर भाष्य नोंदवू शकतो).

प्रणाली **fail-open** आहे: एखाद्या guardrail च्या अंमलबजावणीदरम्यान अपवाद निर्माण झाल्यास, विनंती अयशस्वी करण्याऐवजी registry त्रुटीची नोंद करून पुढील guardrail वर प्रक्रिया सुरू ठेवते. अवरोधित करणे हा नेहमी स्पष्ट निर्णय (`block: true`) असतो, अपघाताने ते कधीही होत नाही.

## अंगभूत सुरक्षा-नियंत्रणे

इम्पोर्ट केल्यावर रजिस्ट्री प्राधान्यक्रमानुसार सहा सुरक्षा-नियंत्रणे स्वयंचलितपणे लोड करते
(`registry.ts` → `registerDefaultGuardrails()` पाहा):

| `6`           | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |

### व्हिजन ब्रिज (`visionBridge.ts`) — मोडॅलिटी ब्रिज PR-1

**व्हिजन नसलेल्या मॉडेल्सना** उद्देशून केलेल्या, प्रतिमा असलेल्या विनंत्या अडवतो आणि एकतर
संपूर्ण विनंती व्हिजन-सक्षम मॉडेलकडे पुनर्मार्गित करतो किंवा अपस्ट्रीम कॉलपूर्वी
प्रतिमेचे भाग कॉन्फिगर करता येणाऱ्या व्हिजन मॉडेलने तयार केलेल्या मजकूर वर्णनांनी
बदलतो. यामुळे केवळ-मजकूर प्रदाते मल्टिमोडल पेलोड्स पारदर्शकपणे हाताळू शकतात.

प्रवाह:

1. लक्ष्य मॉडेल आधीपासूनच व्हिजनला समर्थन देत असल्यास वगळा (ते सक्तीच्या-ब्रिज
   सूची `isVisionBridgeForcedModel` मध्ये दिसत नसेल तर).
2. `extractImageParts(messages)` द्वारे प्रतिमेचे भाग काढा
   (`visionBridgeHelpers.ts`), जे `open-sse/utils/mediaParts.ts` मधील
   **एकीकृत मीडिया डिटेक्टर** `detectMediaParts()` कडे काम सोपवते — कॉम्बो
   सुसंगतता फिल्टरसह सामायिक केलेला सत्याचा एकमेव स्रोत.
   एक्स्ट्रॅक्शन फक्त `replaceImageParts` पुन्हा जोडू शकत असलेल्या आकारांच्या
   शीर्ष-स्तरीय भागांपुरते अनुमती-सूचीबद्ध आहे (extract↔replace करार): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, आणि Responses API `input_image`. नेस्टेड जुळण्या आणि
   केवळ-सूचक आकार हे कॉम्बो-फिल्टरसाठीचे घटक आहेत आणि ते कधीही काढले जात नाहीत.
   काहीही आढळले नाही तर वगळा.
3. `resolveVisionBridgeRuntimeSettings()` द्वारे रनटाइम कॉन्फिग निश्चित करा
   (`src/shared/constants/modalityBridgeDefaults.ts`): नवीन `modalityBridge*`
   सेटिंग्ज कीजना प्राधान्य मिळते; जुने `visionBridge*` कीज **एका-सायकलसाठी
   फॉलबॅक** म्हणून राहतात (रोलबॅक विंडो). ब्रिज अक्षम असल्यास कोणतेही मीडिया
   ट्रॅव्हर्सल करण्यापूर्वी वगळा.
4. मोड निवडक (`modalityBridgeVisionMode`, खालील तक्ता पाहा) पुनर्मार्गन की वर्णन
   हे ठरवतो. पुनर्मार्गन फक्त `model` बदललेले `modifiedPayload`, तसेच
   `{ rerouted, fromModel, toModel, imagesKept }` मेटा परत करते.
5. वर्णन मार्ग: प्रतिमांची संख्या `maxImages` पर्यंत मर्यादित करा, कार्य-जागरूक
   प्रॉम्प्ट तयार करा, वर्णन कॅश तपासा, व्हिजन मॉडेलला **समांतरपणे**
   (`Promise.allSettled`) कॉल करा, आणि त्यांच्या जागी `[Image N]: <description>`
   मजकूर भाग घाला. अयशस्वी वर्णनामुळे `null` मिळते आणि मूळ प्रतिमा भाग
   **जतन केला जातो** (#4012) — मात्र कॉम्बो वर्णन मार्गावर प्रत्येक वर्णन
   अयशस्वी झाल्यास, खात्री झालेल्या नॉन-व्हिजन अपस्ट्रीमला त्याऐवजी
   `(अनुपलब्ध — कोणताही व्हिजन-सक्षम प्रदाता कनेक्ट केलेला नाही)` स्टब मिळतो (#8430).
6. `modifiedPayload` + मेटा (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) परत करा.

#### मोड निवडक (`modalityBridgeVisionMode`)

| मोड        | डीफॉल्ट | वर्तन                                                                                                                                                                                                                                                                                                   |
| ---------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | जुने ह्युरिस्टिक, अपरिवर्तित (#6640/#7204): मूळ मॉडेलकडे आधीपासून वापरण्यायोग्य क्रेडेन्शियल्स नसतील, तर नॉन-कॉम्बो/`auto/` मॉडेल्स सर्वोत्तम व्हिजन मॉडेलकडे पुनर्मार्गित होतात (असल्यास वर्णन करतात); कॉम्बो लक्ष्ये नेहमी वर्णन करतात.                                                               |
| `describe` |         | नेहमी वर्णन करा — पुनर्मार्गन ब्लॉक पूर्णपणे वगळला जातो; वापरकर्त्याने निवडलेले मॉडेल नेहमी उत्तर देते.                                                                                                                                                                                                 |
| `reroute`  |         | सक्तीचे पुनर्मार्गन: क्रेडेन्शियल असलेले मॉडेल कायम ठेवण्याचे गार्ड बायपास केले जाते. पुनर्मार्गन-**लक्ष्य** क्रेडेन्शियल गार्ड तरीही लागू होते — वापरण्यायोग्य व्हिजन लक्ष्य अस्तित्वात नसल्यास, विनंती वर्णनाकडे जाते, जेणेकरून कच्च्या प्रतिमा कधीही केवळ-मजकूर बॅकएंडपर्यंत पोहोचणार नाहीत (#8430). |

सक्तीचे मोड `auto` ह्युरिस्टिक चालण्यापूर्वीच **शॉर्ट-सर्किट** होतात; `auto` चे वर्तन
PR-1 पूर्वीच्या सुरक्षा-नियंत्रणाशी बाइट-दर-बाइट एकसारखे आहे.

#### API-की व्याप्ती (`visionBridgeKeyScope.ts`)

कॉल करणाऱ्याची API की `allowedConnections`, कोटा पूल्स
(`allowedQuotas`) किंवा मॉडेल्स (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) मर्यादित करत असल्यास,
ब्रिज फक्त त्या कीला वापरण्याची परवानगी असलेली पुनर्मार्गन आणि वर्णन मॉडेल्स,
आणि त्या कीला वापरण्याची परवानगी असलेल्या कनेक्शन्सवरच निवडतो. त्यानंतर वर्णन
कॉल नेहमी `x-omniroute-self-loop-key-id` हेडरसह OmniRoute सेल्फ-लूपमधून जातो,
त्यामुळे प्राप्त करणारी चॅट विनंती त्या कीचे कनेक्शन आणि मॉडेल धोरण पुन्हा लागू
करते. `enforceApiKeyPolicy()` त्या हेडरचा केवळ सेल्फ-लूप बेअररसहच आदर करते,
त्यामुळे ते फक्त प्रवेश अधिक मर्यादित करू शकते, आणि निराकरण न होणारा id नाकारला जातो.

कीसाठी कोणत्याही व्हिजन मॉडेलला परवानगी नसल्यास, वर्णन मार्ग बाजूला होतो आणि
विनंती बदल न करता पुढे जाते; हे अक्षम सुरक्षा-नियंत्रणासारखेच फेल-ओपन वर्तन आहे
(मेटा `{ skipped: true, reason: "no_permitted_vision_model" }`).
की नसलेल्या विनंत्या आणि हे निर्बंध नसलेल्या कीज पूर्वीप्रमाणेच वागतात.

#### कार्य-जागरूक वर्णन प्रॉम्प्ट (`modalityBridgeVisionTaskAware`)

डीफॉल्ट **true** आहे. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) मूलभूत
वर्णन प्रॉम्प्टला **शेवटच्या वापरकर्ता संदेशाचा** मजकूर (500 वर्णांपर्यंत संक्षिप्त केलेला)
जोडते, त्यामुळे वर्णन वापरकर्त्याने प्रत्यक्षात काय विचारले त्यानुसार निर्देशित होते
(codex-vision-proxy नमुना) आणि व्हिजन मॉडेलला दृश्यमान मजकुराचे लिप्यंतरण करण्यास सांगितले
जाते. फ्लॅग बंद असल्यास — किंवा वापरकर्ता मजकूर नसल्यास — मूलभूत प्रॉम्प्ट कोणताही बदल न करता वापरला जातो.

वर्णन सेल्फ-लूपची स्वतःची OpenAI-सुसंगत विनंती (`callVisionModelSingle()`
मध्ये `visionBridgeHelpers.ts`) नेहमी `image_url.detail: "high"` ची विनंती करते —
बिनशर्त, प्रत्येक कॉलर/प्रोव्हायडरसाठी आणि कोणत्याही क्लायंट सिग्नलवर अवलंबून न राहता.
हा प्रॉम्प्ट ज्या मजकूर-लिप्यंतरण कार्याची मागणी करतो, त्यासाठी कमी-तपशील सॅम्पलिंगमुळे
OCR अचूकता कमी होते; त्यामुळे मूळ इनबाउंड विनंतीने कोणती तपशील पातळी वापरली होती
याची पर्वा न करता वर्णन कॉल स्वतः नेहमी उच्च तपशीलाची मागणी करतो. याचा परिणाम
फक्त अंतर्गत वर्णन विनंतीच्या बॉडीवर होतो; OmniRoute प्राथमिक विनंतीवर कॉलरचे स्वतःचे
`image_url.detail` कसे फॉरवर्ड करते हे यामुळे बदलत नाही — तो डीफॉल्ट स्वतंत्रपणे लागू
केला जातो आणि फक्त ओळखलेल्या OpenCode क्लायंटसाठी `defaultImageDetail()`
(`open-sse/handlers/chatCore/upstreamBody.ts`) मध्ये लागू होतो. वर्णन सेल्फ-लूपच्या
Anthropic वायर-फॉरमॅट शाखेत `detail` फील्ड नाही आणि कोणत्याही डीफॉल्टचा तिच्यावर परिणाम होत नाही.

#### वर्णन आउटपुट मर्यादा (`modalityBridgeVisionMaxChars`)

| की                             | डीफॉल्ट | श्रेणी              |
| ------------------------------ | ------- | ------------------- |
| `modalityBridgeVisionMaxChars` | `0`     | `0` किंवा 100–50000 |

`0` (डीफॉल्ट) म्हणजे **कोणतीही मर्यादा नाही** — `callVisionModel()` ने परत केलेले
वर्णन कोणताही बदल न करता पुढे पाठवले जाते, त्यामुळे विद्यमान वर्तन कायम राहते.
100–50000 श्रेणीतील कोणतेही मूल्य, वर्णन पुन्हा `[Image N]: <description>`
म्हणून जोडण्यापूर्वी त्याला `…` प्रत्ययासह संक्षिप्त करते
(`VisionBridgeGuardrail.preCall()` मध्ये `src/lib/guardrails/visionBridge.ts`).
तपशील-केंद्रित OCR कार्यांसाठी, ज्यांत डाउनस्ट्रीम मॉडेलला संपूर्ण लिप्यंतरण आवश्यक असते,
हे मूल्य वाढवा; अधिक मजकूर निर्माण करणाऱ्या व्हिजन मॉडेल्सचा टोकन वापर मर्यादित ठेवण्यासाठी
ते कमी करा. डॅशबोर्ड फील्ड Vision टॅबच्या Advanced पॅनेलवर आहे
(`modality-bridge-max-chars` मध्ये `ModalityBridgeVisionTab.tsx`) आणि स्पष्टपणे दिलेले `0`
न बदलता ठेवून 1 ते 99 मधील कोणतेही मूल्य किमान 100 पर्यंत वाढवते — `0` हे केवळ
"सेट न केलेले" डीफॉल्ट नसून, स्वतःहून वैध Zod मूल्य आहे
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`).

#### वर्णन कॅशे (`modalityBridge/bridgeCache.ts`)

वर्णन आउटपुटसाठी इन-मेमरी LRU + TTL कॅशे, जो संपूर्ण प्रोसेसमध्ये सामायिक असतो.
की = `sha256(imageRef + composedPrompt + configuredBridgeModel)`, ज्यात
लांबी-उपसर्ग फ्रेमिंग वापरले जाते (फील्ड-सीमांवर टक्कर होत नाही). मॉडेल घटक हा
**कॉन्फिगर केलेला** ब्रिज मॉडेल असतो, प्रत्यक्षात उत्तर देणारा मॉडेल नव्हे —
`callVisionModel` अंतर्गत फॉलबॅक करू शकते आणि प्रत्येक प्रयत्नानुसार की ठेवल्यास
कॅशेचे विखंडन होईल. अयशस्वी वर्णने कधीही कॅश केली जात नाहीत. सेटिंग्ज:

| की                              | डीफॉल्ट | श्रेणी  |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### रिमोट प्रतिमा सामान्यीकरण (सेल्फ-लूप वर्णन/base64 फेच)

ब्रिज स्वतः एखादी **रिमोट** प्रतिमा फेच करतो तेव्हा — Anthropic वर्णन
सेल्फ-कॉल आणि claude-वायर-फॉरमॅट base64 रूपांतरण
(`ensureBase64ImagesForClaudeWire`), हे दोन्ही `visionBridgeHelpers.ts` मधील
`fetchRemoteImageAsDataUri()` द्वारे — परिणामी डेटा URI व्हिजन-मॉडेल
विनंतीमध्ये एम्बेड करण्यापूर्वी `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) मधून पाठवला जातो. अतिमोठ्या प्रतिमा
**2048px लांब कडेपर्यंत** डाउनस्केल केल्या जातात (OpenAI/Anthropic आधीपासून
सर्व्हरच्या बाजूला लागू करत असलेल्या आकार-बदल मर्यादेशी सुसंगत), ज्यामुळे व्हिजन मॉडेलला
दिसणाऱ्या गोष्टीत बदल न करता अपलोड बाइट्स/विलंब कमी होतो. आकार बदलण्यासाठी
डायनॅमिक इम्पोर्टद्वारे लोड केलेले `sharp` वापरले जाते: ज्या प्लॅटफॉर्मवर त्याची नेटिव्ह
बायनरी लोड होण्यात अपयशी ठरते, तेथे `normalizeDataUri()` **कधीही त्रुटी फेकत नाही** —
ते मूळ बाइट्स जसाच्या तशा पुढे पाठवण्यावर फॉलबॅक करते, त्यामुळे वर्णन/base64-रूपांतरण
मार्ग नेहमी कार्यरत राहतो. प्रतिमा नसलेले बाइट्स (डिकोड करता येणारी प्रतिमा न देणारा फेच)
देखील कोणताही बदल न करता पुढे पाठवले जातात. हे सामान्यीकरण ब्रिजने स्वतःच्या सेल्फ-कॉलसाठी
फेच केलेल्या प्रतिमांपुरते मर्यादित आहे — ते कॉलरच्या रॉ पासथ्रू पेलोडवर कधीही लागू केले
जात नाही, जे केवळ ऑप्ट-इन केल्यावरच बदल करण्याच्या तत्त्वाशी सुसंगत आहे (Hard Rule #20).

नवीन `modalityBridge*` की `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`) मध्ये Zod-द्वारे वैध ठरवल्या जातात:
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, `modalityBridgeCache*` त्रिकूट आणि Audio Bridge द्वारे
वापरला जाणारा `modalityBridgeAudio*` गट. स्थलांतर
`141_modality_bridge_settings.sql` विद्यमान लेगसी `visionBridge*` मूल्ये संबंधित
नवीन कीमध्ये कॉपी करते (आयडेम्पोटंट, ऑपरेटरने सेट केलेले `modalityBridge*` मूल्य कधीही
ओव्हरराइट करत नाही); एका रिलीज चक्रासाठी लेगसी की रीड फॉलबॅक म्हणून स्वीकारल्या जात राहतात.

#### पारदर्शकता हेडर + आकडेवारी

वर्णनाद्वारे रूपांतरित प्रतिसादांमध्ये
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
समाविष्ट असते (`modalityBridge/bridgeStats.ts` मधील `buildModalityBridgeHeader()`
द्वारे तयार केलेले आणि `src/sse/handlers/chatHelpers.ts` मधील
`withModalityBridgeHeader()` द्वारे लागू केलेले).
पुनर्मार्गित विनंत्यांना **कोणतेही** हेडर मिळत नाही — पेलोड बदललेला नव्हता आणि मॉडेलमधील
बदल प्रतिसाद बॉडीच्या `model` फील्डमध्ये आधीच दिसतो.

`GET /api/modality-bridge/stats` (`GET /api/settings` प्रमाणेच समान स्तरावरील
व्यवस्थापन प्रमाणीकरण) `vision`, `audio`, आणि `video` साठी इन-मेमरी, प्रति-मोडॅलिटी
काउंटर
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` परत करते. `averageLatencyMs` त्याचा
भाजक म्हणून सर्व प्रयत्नांऐवजी `latencySamples` वापरते; वेळमापन नसलेले ऑपरेशन
शून्य-मिलिसेकंदाचा नमुना कृत्रिमरीत्या तयार करत नाही. यशस्वी रूपांतरणांसाठी
`bridged` हा मागील आवृत्त्यांशी सुसंगत उपनाम म्हणून कायम राहतो; अयशस्वी प्रयत्नांमुळे
तो वाढत नाही.
डिझाइननुसार प्रक्रिया रीस्टार्ट झाल्यावर काउंटर रीसेट होतात
(हे टेलिमेट्री आहे, लेखांकन नाही).

#### डॅशबोर्ड कॉन्फिगरेशन

समर्पित डॅशबोर्ड पृष्ठ
`/dashboard/settings/modality-bridge` आहे. त्याचे URL-द्वारे प्रवेशयोग्य `Vision`, `Audio`,
आणि `Video` टॅब `tab` मूल्य बदलताना क्वेरी पॅरामीटर्स जतन करतात.
Vision टॅब सक्षम करणे, मोड, मॉडेल निवड (स्वयंचलित डीफॉल्टसह),
कार्य-जागरूक प्रॉम्प्टिंग, प्रगत टाइमआउट/प्रतिमा/वर्णन-लांबी/कॅशे
मर्यादा, रनटाइम
काउंटर, आणि संरक्षित नमुना विनंती उपलब्ध करून देतो. Audio टॅबही कार्यरत आहे: तो
सक्षम करणे, Auto सह केवळ-STT मॉडेल पिकर, टाइमआउट/कमाल-क्लिप मर्यादा, ऑडिओ
काउंटर, आणि `input_audio` नमुना चाचणी उपलब्ध करून देतो. Video टॅब कार्यशील आहे: तो
FFmpeg/ffprobe रनटाइम स्थिती दाखवतो — चार स्पष्ट UI स्थितींपैकी एक (`unknown`, जेव्हा
प्रोब सुरू असतो किंवा पूर्ण होऊ शकत नाही; नॉन-लूपबॅक डॅशबोर्ड होस्टवर प्रोब
क्लायंट-साइड वगळला जातो तेव्हा `restricted`; प्रोब केल्यानंतर उपलब्ध नसल्याची पुष्टी
झाल्यावर `unavailable`; किंवा FFmpeg/ffprobe आवृत्त्यांसह `available`) — सक्षम
करणे/मॉडेल/फ्रेम/व्हिडिओ/टाइमआउट मर्यादा कायमस्वरूपी साठवतो, मॉडेल पिकरला
व्हिजन-सक्षम मॉडेल्सपुरते फिल्टर करतो, आणि व्हिडिओ काउंटर उपलब्ध करून देतो.

AI सेटिंग्जखालील पूर्वीचे Vision Bridge कार्ड आता नवीन पृष्ठाची सुसंगतता लिंक आहे;
ते यापुढे फॉर्मची दुसरी प्रत ठेवत नाही. विद्यमान Speech-to-Text प्लेग्राउंड न काढता
Media Providers हे Image-to-Text आणि Speech-to-Text कार्यप्रवाह संबंधित Modality
Bridge टॅबशी देखील जोडते.

**सेल्फ-लूप प्रवेश बायपास:** describe कॉल OmniRoute च्या स्वतःच्या `/v1`
सेल्फ-लूपमधून (अमानक प्रदाता मॉडेल) रूट होत असताना, उप-विनंती
`x-omniroute-admission-bypass: internal` पाठवते आणि निराकरण केलेल्या
सेल्फ-लूप क्रेडेन्शियलने प्रमाणीकृत केली जाते — लोकल मोडमध्ये स्थानिक
`sk_omniroute` सेंटिनेल, किंवा ऑपरेटरने कॉन्फिगर केलेली
`OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env की (#1350), ज्यामुळे
`REQUIRE_API_KEY=true` डिप्लॉयमेंट्सही describe कॉल चालवू शकतात. बायपासचा
स्वीकार फक्त याच अचूक क्रेडेन्शियल्ससाठी केला जातो, त्यामुळे बाह्य क्लायंट्स
प्रवेश तपासणी वगळण्यासाठी हा हेडर वापरू शकत नाहीत.

लेगसी डीफॉल्ट्स `src/shared/constants/visionBridgeDefaults.ts` मध्ये आहेत;
नवीन मोड/कार्य-जागरूक/कॅशे डीफॉल्ट्स आणि सेटिंग्ज रिझॉल्वर
`src/shared/constants/modalityBridgeDefaults.ts` मध्ये आहेत. गार्डरेल
`deps` कन्स्ट्रक्टर पर्याय उपलब्ध करून देते, ज्यामुळे चाचण्यांमध्ये बनावट
`getSettings` आणि `callVisionModel` अंमलबजावण्या इंजेक्ट करता येतात.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ऑडिओ इनपुट स्वीकारते हे ज्ञात नसलेल्या लक्ष्यापर्यंत ऑडिओ असलेल्या चॅट विनंत्या
पोहोचण्यापूर्वी त्यांना इंटरसेप्ट करते. हे चॅट विनंती कधीही पुन्हा रूट करत नाही:
विद्यमान OpenAI-सुसंगत मल्टिपार्ट एंडपॉइंटद्वारे ऑडिओ भागांचे लिप्यंतरण केले जाते
आणि निवडलेले चॅट मॉडेल मजकूर लिप्यंतरणांसह पुढे सुरू राहते.

प्रवाह:

1. `getResolvedModelCapabilities()` द्वारे `supportsAudio` चे निराकरण करा. स्पष्ट
   प्रदाता-रजिस्ट्री मेटाडेटाला प्रथम प्राधान्य, त्यानंतर स्थिर मॉडेल मेटाडेटा, आणि
   नंतर सिंक केलेले `modalities_input`. `audio` नसलेली घोषित इनपुट सूची `false`
   असते; क्षमतेचा कोणताही पुरावा नसल्यास मूल्य `null` राहते. `false` आणि `null`
   हे दोन्ही संरक्षित ब्रिज सक्रिय करतात, तर `true` त्याला बायपास करते.
2. `modalityBridgeAudio*` सेटिंग्जचे निराकरण करा आणि सामायिक
   `detectMediaParts()` डिटेक्टरद्वारे प्रत्येक संदेशातून स्प्लाइस करता येणारे
   टॉप-लेव्हल ऑडिओ भाग काढा. समर्थित वायर स्वरूपे OpenAI `input_audio`,
   `audio_url`, आणि `source.media_type: "audio/*"` आहेत. नेस्टेड ऑडिओ रूटिंगसाठी
   शोधला जातो, परंतु स्प्लाइस मार्गाद्वारे काढला जात नाही. कामाची मर्यादा
   `modalityBridgeAudioMaxClips` द्वारे निश्चित केली जाते; नंतरचे भाग बदलले जात
   नाहीत.
3. कॉन्फिगर केलेल्या `provider/model` चे पालन करा, किंवा
   `selectAudioBridgeModel()` ला स्थिर कॅटलॉग क्रमाने
   `AUDIO_TRANSCRIPTION_PROVIDERS` मधून जाऊ द्या आणि वापरण्यायोग्य सक्रिय
   प्रदाता क्रेडेन्शियल असलेले पहिले मॉडेल निवडू द्या.
4. `callAudioTranscription()` base64/data-URI ऑडिओचे मल्टिपार्ट `file` मध्ये
   रूपांतर करते, किंवा DNS पिनिंग आणि 25 MB मर्यादेसह केवळ-सार्वजनिक आउटबाउंड
   गार्डद्वारे रिमोट `audio_url` डाउनलोड करते. त्यानंतर ते फाइल आणि निवडलेले मॉडेल
   स्थानिक `/v1/audio/transcriptions` सेल्फ-लूपवर POST करते आणि
   `resolveSelfLoopBearer()` वापरून प्रमाणीकरण करते. विद्यमान ट्रान्सक्रिप्शन रूट
   सामान्य क्रेडेन्शियल शोध, कूलडाउन/दर-मर्यादा हाताळणी, आणि प्रदाता डिस्पॅच
   पार पाडतो.
5. यशस्वी कॉल त्यांचे भाग `[Audio N]: <transcript>` ने बदलतात. कॉल
   `Promise.allSettled` सह चालतात: एखादा स्वतंत्र कॉल अयशस्वी झाल्यास तो मूळ
   ऑडिओ भाग जतन केला जातो (#4012 करार). सर्व कॉल अयशस्वी झाल्यास आणि लक्ष्याचे
   `supportsAudio === false` असल्याचे सिद्ध झाल्यास, भाग
   `[Audio N]: (unavailable — no STT provider connected)` होतात (#8430 करार).
   अज्ञात लक्ष्यासाठी (`null`), सर्व कॉल अयशस्वी झाल्यास परिणाम बदलला जात नाही.
   वापरण्यायोग्य STT क्रेडेन्शियल नसलेल्या सिद्ध केवळ-मजकूर लक्ष्याला नेटवर्क कॉल
   न करता हाच स्पष्ट स्टब मिळतो.

यशस्वी लिप्यंतरणे प्रक्रियाव्यापी Modality Bridge LRU/TTL कॅशे वापरतात. कीमध्ये
ऑडिओ संदर्भ, स्थिर `audio-transcription` ऑपरेशन लेबल, आणि निवडलेले STT मॉडेल
एकत्रित केले जाते; अपयशे कधीही कॅशे केली जात नाहीत. ऑडिओ प्रयत्न सामायिक
`bridged`, `cacheHits`, `failures`, आणि `lastUsedAt` काउंटर अपडेट करतात.
रूपांतरित प्रतिसादांमध्ये
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` असते;
न बदललेल्या विनंत्यांना Audio Bridge सेगमेंट मिळत नाही.

रनटाइम सेटिंग्ज DB-बॅक्ड आणि Zod-द्वारे प्रमाणित आहेत:

| की                            | डीफॉल्ट | श्रेणी            |
| ----------------------------- | ------- | ----------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —                 |
| `modalityBridgeAudioModel`    | `""`    | Auto किंवा STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000       |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10              |

सामायिक कॅशे अजूनही `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, आणि `modalityBridgeCacheMaxEntries` द्वारे नियंत्रित केली जाते.

### व्हिडिओ ब्रिज (`videoBridge.ts`, `videoBridgePipeline.ts`)

ज्ञात नेटिव्ह व्हिडिओ समर्थन नसलेल्या लक्ष्याला कॉल करण्यापूर्वी Chat Completions
`messages` आणि Responses API `input` मधील उच्च-स्तरीय व्हिडिओ भागांना इंटरसेप्ट करते.
समर्थित स्वरूपे `input_video`, `video_url`, `video_source`, HTTPS URLs,
आणि `data:video/*;base64,...` डेटा URIs ही आहेत. मजकुरातील साधी फाइलनावे व्हिडिओ
म्हणून हाताळली जात नाहीत.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) विनंतीचे ट्रॅव्हर्सल,
क्षमता/धोरण तपासणी, प्रत्येक विनंतीचे एकत्रीकरण आणि प्रतिसाद पेलोड हाताळते.
प्रत्येक व्हिडिओवरील काम — प्राप्ती, संपूर्ण-निकाल कॅशे, फ्रेम अनुक्रमाचे
वर्णन करणे (ज्यामध्ये कॉलरने घोषित केलेला कोणताही ऑडिओ ट्रान्सक्रिप्ट एकत्रित केला जातो),
आणि प्रत्येक प्रयत्नाचे मेट्रिक्स/रद्दीकरण/क्लीनअप — `videoBridgePipeline.ts` मधील
`processVideoPart` च्या मागे लपवलेले आहे, ज्याला `preCall` च्या लूपमध्ये प्रत्येक
व्हिडिओ भागासाठी एकदा कॉल केले जाते. ते मॉड्यूल स्पष्ट पोर्ट सीमा
`VideoMediaBrokerPort` (बाइट्स प्राप्त करणे आणि नमुना फ्रेम्स काढणे),
`VideoAudioTranscriptionPort` (कॉलरने घोषित केलेला ऑडिओ ट्रान्सक्रिप्ट नमुना
कॅप्शन्ससोबत एकत्रित करणे), आणि `VideoDrilldownPort` (फ्रेम ड्रिल-डाउन
पर्सिस्टन्स सीमा; अद्याप `processVideoPart` शी जोडलेली नाही — सध्या केवळ स्वतंत्र
`/api/modality-bridge/video/drilldown` रूट ड्रिल-डाउन नोंदी लिहितो) देखील परिभाषित करते.

सार्वजनिक `/v1` विनंती पथ कधीही सबप्रोसेस इंपोर्ट किंवा इनव्होक करत नाही.
रिमोट व्हिडिओ 50 MiB मर्यादेत डाउनलोड केले जातात; सार्वजनिक JSON विनंतीच्या
50 MiB प्रवेश मर्यादेत मॉडेल/संदेश/फ्रेमिंग एन्व्हलप राहू शकेल यासाठी इनलाइन
base64 व्हिडिओंना प्रत्येक व्हिडिओमागे 36 MiB ची सावधगिरीची डीकोडेड मर्यादा असते.
वाटप करण्यापूर्वी इनलाइन लांबी आणि डीकोडेड आकाराचे अंदाज तपासले जातात. प्रारंभिक
रिमोट URL आणि प्रत्येक रीडायरेक्टसाठी HTTPS आवश्यक आहे, ज्यासाठी DNS पिनिंगसह
विद्यमान public-only आउटबाउंड गार्ड वापरला जातो. त्यानंतर बाइट्स अचूक अंतर्गत
`POST /api/modality-bridge/video/extract` ब्रोकर सीमा ओलांडतात. तो रूट
`LOCAL_ONLY` आणि `SPAWN_CAPABLE` दोन्ही आहे, केवळ प्रत्येक-प्रोसेससाठी
प्रमाणित केलेली, विश्वासार्ह-लूपबॅक विनंती स्वीकारतो आणि URL, फाइलसिस्टम पथ,
एक्झिक्युटेबल किंवा आर्ग्युमेंट सूची कधीही स्वीकारत नाही. API बॉडी-आकार
पाइपलाइन आणि हँडलरचा इन्क्रिमेंटल बॉडी रीडर स्वतंत्रपणे 50 MiB ब्रोकर इनपुट
मर्यादा लागू करतात. त्याची मर्यादित क्यू एका वेळी एक एक्स्ट्रॅक्शन चालवते,
चार प्रलंबित जॉब्सना अनुमती देते आणि प्रलंबित इनपुट 100 MiB पर्यंत मर्यादित करते.

ब्रोकरमध्ये `ffprobe` एक खाजगी स्थानिक फाइल वाचतो; निश्चित फॉरमॅट अनुमतीसूची
प्लेलिस्ट आणि मॅनिफेस्ट फॉरमॅट्स वगळते. अनुमत MOV-कुटुंबातील कंटेनर्ससाठी,
बाह्य MOV डेटा संदर्भ डीफॉल्टनुसार अक्षम राहतात आणि निश्चित कमांड त्यांना
सक्षम करत नाही. `ffprobe` आणि `ffmpeg` दोन्ही `file`-पुरती प्रोटोकॉल अनुमतीसूची,
एक थ्रेड, निश्चित आर्ग्युमेंट अॅरे, शेलशिवाय कार्यपद्धती आणि `PATH` मधून शोधलेले
एक्झिक्युटेबल्स वापरतात. संलग्न-चित्र कव्हर स्ट्रीम्स प्ले करण्यायोग्य उमेदवार
नसतात. सर्व प्ले करण्यायोग्य स्ट्रीम्सनी मर्यादा पूर्ण करणे आवश्यक आहे आणि
डिटरमिनिस्टिक सर्वात-कमी-इंडेक्स फॉलबॅकपूर्वी स्पष्ट डीफॉल्ट स्ट्रीमला प्राधान्य
दिले जाते. व्हिडिओ 600 सेकंद, प्रत्येक परिमाणात 8,192 पिक्सेल आणि 33,554,432
स्रोत पिक्सेल्सपर्यंत मर्यादित असतात. FFmpeg 1–16 मध्यबिंदू JPEG फ्रेम्सचे नमुने
घेतो, लहान इनपुट्सचे अपस्केलिंग न करता लांब कडा जास्तीत जास्त 1,024 पिक्सेलपर्यंत
कमी करतो आणि त्याला कधीही URL मिळत नाही. डीफॉल्टनुसार नमुना-निवड `uniform`
असते. पर्यायी `scene_aware` आणि प्रायोगिक `segment_aware` धोरणे आधीच प्रमाणित
केलेल्या स्थानिक स्ट्रीमवर एक अतिरिक्त निश्चित FFmpeg पास करतात, मर्यादित
`showinfo` दृश्य टाइमस्टॅम्प्स निवडतात आणि डिटेक्टर अपयश, टाइमआउट, विकृत आउटपुट
किंवा रिकामा उमेदवार संच असल्यास डिटरमिनिस्टिक पद्धतीने त्याच एकसमान मध्यबिंदूंवर
फॉलबॅक करतात. सेगमेंट-अवेयर मोड प्रमाणित दृश्य अंतरालांच्या प्रमाणात मध्यबिंदू
नमुने वाटप करतो; सेगमेंट-अवेयर पुरावे आणि फॉलबॅक वर्तनाचे तपशील खाली दिले आहेत.
प्रत्येक धोरणात निवडीनंतर 16 फ्रेम्सची कठोर मर्यादा लागू केली जाते. जेव्हा
सीन-अवेयर विनंतीसाठी केवळ एका फ्रेमचे बजेट असते, तेव्हा ती सक्रिय पूर्ण-व्हिडिओ
किंवा फोकस विंडोचा एकसमान मध्यबिंदू वापरते आणि `policyEffective: uniform` नोंदवते:
निवडलेली एकच दृश्य फ्रेम दोन्ही कालबद्ध टोके जतन करू शकत नाही. कॉलर इच्छेनुसार
मर्यादित फोकस विंडो (`start`/`end` सेकंद) देऊ शकतो; सीमा मीडिया कालावधीपर्यंत
क्लॅम्प केल्या जातात, उलट किंवा मर्यादित नसलेल्या विंडोज नाकारल्या जातात आणि
सर्व नमुना-निवड धोरणे केवळ सामान्यीकृत अंतरालातच पार पाडली जातात. परिणामी
विंडो नमुना-निवड मेटाडेटामध्ये आणि अविश्वसनीय वर्णन उपसर्गामध्ये समाविष्ट केली
जाते, ज्यामुळे डाउनस्ट्रीम मॉडेल्स केंद्रित उतारा आणि पूर्ण टाइमलाइन यांतील फरक
ओळखू शकतात.

सिमॅंटिक कॅप्शन फोकस ही स्वतंत्र, स्पष्ट सेटिंग आहे. डीफॉल्ट `full`
विश्लेषण मोड विद्यमान फ्रेम प्रॉम्प्ट जतन करतो आणि विनंतीमधील मजकूर कॅप्शन
मॉडेलकडे कधीही पाठवत नाही. `focused` मोडमध्ये, ब्रिज त्याच Chat किंवा Responses
कंटेनरमधून केवळ वापरकर्त्याने लिहिलेला सर्वात अलीकडील रिकामा नसलेला
`text`/`input_text` वाचतो, त्याचे NFC मध्ये सामान्यीकरण करतो, कंट्रोल कॅरेक्टर्स
आणि व्हाइटस्पेस संकुचित करतो आणि त्याला 500 Unicode कोड पॉइंट्सपर्यंत मर्यादित
करतो. रिकामा परिणाम हुबेहूब `full` प्रॉम्प्टवर फॉलबॅक करतो. वापरण्यायोग्य संकेत
समर्पित अविश्वसनीय-वापरकर्ता-संदर्भ ब्लॉकमध्ये JSON म्हणून सिरियलाइझ केला जातो
आणि तो केवळ निरीक्षण करता येण्याजोग्या तपशीलांना प्राधान्य देऊ शकतो; मीडियामध्ये
दिसणाऱ्या किंवा ऐकू येणाऱ्या सूचनांचे पालन करण्याविरुद्धची स्वतंत्र चेतावणी तो
ओव्हरराइड करू शकत नाही. मजकूर-आधारित फोकस कधीही `start`/`end` अनुमानित करत नाही
किंवा कालबद्ध सॅम्पलर बदलत नाही.

#### FU-07 संरचनात्मक सेगमेंट पुरावे

`segment_aware` आधीच प्रमाणित केलेल्या स्थानिक व्हिडिओ स्ट्रीमवर एक मर्यादित पूर्व-विश्लेषण फेरी वापरते. निश्चित फिल्टर साखळी प्रथम रुंदी जास्तीत जास्त 320 पिक्सेलपर्यंत स्केल करते, दृश्यबदल आणि गोठलेले कालखंड शोधते आणि नंतर अस्पष्टता, सरासरी ल्यूमा तसेच स्थानिक/कालिक माहितीसाठी प्रति सेकंद 1 फ्रेमचा नमुना घेते. ही फेरी 600 संरचनात्मक नमुने, एक FFmpeg/फिल्टर थ्रेड, तेच केवळ-`file` प्रोटोकॉल व कंटेनर अनुमती-सूची, 1 MiB प्रक्रिय-आउटपुट मर्यादा आणि ब्रोकरच्या सामायिक रद्दीकरण/अंतिम-मुदतीमध्ये जास्तीत जास्त 30 सेकंद इतकी मर्यादित आहे. ती विनंतीमधून कमांड, फिल्टर, पथ किंवा URL कधीही स्वीकारत नाही.

संरचनात्मक मूल्ये ही निर्धारक नमुना-आधारित साक्ष आहेत, अर्थाधारित व्हिडिओ आकलन नाही. ती विषय, कृती, मथळे, भाषण किंवा वापरकर्त्याचा हेतू अनुमानित करत नाहीत. दृश्य आणि गोठण्याच्या सीमा सेगमेंट तयार करतात; गोठलेले कव्हरेज, अस्पष्टता, एक्सपोजर, स्थानिक तपशील आणि कालिक बदल यांचा प्रभाव केवळ विद्यमान 1–16 फ्रेम बजेट कसे वाटले जाते यावर पडतो. पूर्णपणे गोठलेल्या सेगमेंटची मर्यादा एका फ्रेमपर्यंत ठेवली जाते, तर न गोठलेले सेगमेंट उर्वरित बजेटसाठी स्पर्धा करतात. सीमांची संख्या फ्रेमपेक्षा जास्त असताना, टाइमलाइनचे एकसमान कव्हरेज कायम ठेवले जाते, जेणेकरून सुरुवातीचे जलद कट्स शेवटचा मोठा सेगमेंट लपवू शकणार नाहीत. गोठण्याच्या सीमेपासून 1-सेकंदाच्या विश्लेषण रिझोल्यूशनमध्ये असलेल्या दृश्यसीमा एकत्र केल्या जातात.

फिल्टर अनुपलब्ध असणे, विकृत/रिक्त साक्ष, डिटेक्टर त्रुटी किंवा मर्यादित पूर्व-विश्लेषणाची कालमर्यादा संपणे यांमुळे नेमक्या एकसमान मध्यबिंदू धोरणाकडे खुले अपयश होते. कॉलरने केलेले रद्दीकरण किंवा ब्रोकरची अंतिम-मुदत मात्र खुले अपयश घडवत नाही: ते चालू उपप्रक्रिया समाप्त करते, त्यानंतरचे फ्रेम निष्कर्षण प्रतिबंधित करते आणि खासगी तात्पुरती ट्री `finally` मध्ये काढून टाकली जाते.

`scripts/perf/video-bridge-fu07-eval.ts` डिडुप्लिकेशननंतरच्या कॅप्शन-कॉल बचतीसाठी, घन-हालचालीच्या बजेट वाटपासाठी, अस्पष्टता/एक्सपोजर/SI-TI साक्षेसाठी, दीर्घ शेवट असलेल्या जलद कट्ससाठी आणि क्रमिक-फेडमधील चुकीच्या सकारात्मक निष्कर्षांसाठी निर्धारक, वास्तविक FFmpeg फिक्स्चर्स निर्माण करते. ते पूर्व-विश्लेषणाचा प्रत्यक्ष कालावधी आणि `/usr/bin/time` उपलब्ध असेल तेथे चाइल्ड CPU व कमाल RSS नोंदवते. त्याच्या गुणवत्ता तपासण्या केवळ संरचनात्मक ओरॅकल्स आहेत. वास्तविक कॅप्शन-मॉडेल गुणवत्ता `HOLD` स्थितीतच राहते, कारण या हार्नेसकडे अधिकृत एंडपॉइंट किंवा गोठवलेला निर्णायक नाही. `--caption-cost-per-call-usd` द्वारे प्रत्येक कॉलसाठी स्पष्ट सकारात्मक खर्च-अंदाज दिल्याशिवाय आर्थिक बचतही `HOLD` स्थितीतच राहते; स्क्रिप्ट यांपैकी कोणताही परिणाम कधीही बनावट तयार करत नाही.

प्रत्येक फ्रेम 4 MiB पर्यंत, सर्व रॉ फ्रेम्स मिळून 23 MiB पर्यंत आणि अनुक्रमित ब्रोकर प्रतिसाद 32 MiB पर्यंत मर्यादित असतो. खासगी तात्पुरती निर्देशिका `finally` मध्ये काढून टाकली जाते. OmniRoute मध्ये FFmpeg समाविष्ट नाही आणि ते सानुकूल एक्झिक्युटेबल पथ स्वीकारत नाही. कॅप्शनिंगपूर्वी ब्रिज एक सावध दृश्यात्मक डिडुप्लिकेशन फेरी लागू करतो: प्रत्येक JPEG चे 16×16 ग्रेस्केल बफरमध्ये रूपांतर केले जाते आणि त्याची तुलना केवळ शेवटी राखून ठेवलेल्या फ्रेमशी केली जाते. एका फ्रेमपेक्षा जास्त विनंती केलेल्या कॅप्शन बजेटसाठी, निष्कर्षण त्या बजेटच्या जास्तीत जास्त दुप्पट आणि कधीही 16 फ्रेमपेक्षा जास्त नसलेला मर्यादित उमेदवार संच पुरवते. विनंती केलेली कमाल मर्यादा केवळ डिडुप्लिकेशननंतर लागू केली जाते; बजेट किमान दोन असेल तेव्हा अंतिम विरळणीदरम्यान पहिले आणि शेवटचे निवडलेले उमेदवार जतन केले जातात. आवृत्तीकृत
`grayscale-16x16-mean-cells-v2` धोरण सरासरी ल्यूमा फरक आणि ज्यांचा सामान्यीकृत फरक किमान 0.05 आहे अशा थंबनेल सेल्सचे गुणोत्तर यांपैकी मोठे मूल्य वापरते. डुप्लिकेट थ्रेशोल्ड हा 0.04 स्थिरांक आहे; रनटाइम सेटिंग म्हणून उपलब्ध करण्याऐवजी पूर्वानुमेयतेसाठी तो निवडला आहे. हा दुय्यम
उच्च-कॉन्ट्रास्ट सिग्नल, केवळ सरासरीवर आधारित तुलना ज्यांना लपवू शकते असे लहान हालचाली आणि दृश्यमान मजकुरातील बदल जतन करतो. कंपॅरेटर किंवा डिकोडर त्रुटी खुले अपयश घडवतात आणि कव्हरेज कायम ठेवतात. आउटपुट मेटाडेटा निष्कर्षित उमेदवार, यशस्वीपणे वापरलेल्या फ्रेम्स आणि वगळलेले दृश्यात्मक डुप्लिकेट वेगवेगळे दर्शवतो.

स्पष्टपणे चिन्हांकित केलेला व्हिडिओ भाग टाइमस्टॅम्पयुक्त कॉन्टॅक्ट शीटची विनंती करू शकतो. ब्रिज जास्तीत जास्त 4-स्तंभांचा, 16-फ्रेमचा JPEG ग्रिड तयार करतो. प्रत्येक 512-पिक्सेल सेल त्याचा स्रोत टाइमस्टॅम्प उच्च-कॉन्ट्रास्ट तळाच्या पट्ट्यात कायमस्वरूपी उमटवतो, तर तेच टाइमस्टॅम्प पुढील संबद्धता आणि लेखापरीक्षणासाठी मजकूर मेटाडेटामध्येही राहतात. संपूर्ण JPEG ची मर्यादा 32 MiB इतकीच राहते. `sharp` ग्रिड डिकोड किंवा संयोजित करू शकत नसल्यास, ब्रिज स्वतंत्र JPEG फ्रेम्सकडे परत जातो; क्लायंटचे रद्दीकरण तरीही शीट ऑपरेशनमधून पुढे प्रसारित होते.

प्रमोशन साक्ष कृत्रिम संयोजन मायक्रोबेंचमार्कपासून जाणीवपूर्वक वेगळी ठेवली आहे. `scripts/perf/video-bridge-contact-sheet-eval.ts` वास्तविक OpenAI-सुसंगत व्हिजन मॉडेल्ससाठी स्कीमा-आवृत्तीकृत A/B हार्नेस परिभाषित करते. ते प्रदात्याने नोंदवलेले टोकन्स, सुरुवातीपासून शेवटपर्यंतचा प्रत्यक्ष विलंबकाल (शीट संयोजनासह), मॉडेल-कॉल संख्या आणि मॅनिफेस्ट-परिभाषित तथ्य धारणा मोजते. रॉ मॉडेल प्रतिसाद अहवालात लिहिले जात नाहीत; केवळ SHA-256 डायजेस्ट्स आणि जुळलेले तथ्य ID राखून ठेवले जातात. `--execute-real` दिल्याशिवाय आणि `--model`, `OMNIROUTE_BASE_URL` व `OMNIROUTE_API_KEY` कॉन्फिगर केल्याशिवाय हार्नेस कोणताही नेटवर्क किंवा सशुल्क मॉडेल कॉल करत नाही. अशी स्पष्ट वास्तविक रन नसल्यास, त्याचा मशीन-वाचनीय निकाल `HOLD` राहतो; केवळ कृत्रिम पेलोड/कॉल-संख्या मोजमापे प्रमोशन साक्ष नाहीत.

कॉलर्सकडे आधीपासून संरेखित मजकूर असल्यास ते समर्थित व्हिडिओ भागाला पर्यायी `transcript.cues` अॅरे जोडू शकतात. प्रत्येक क्यूमध्ये `text`, तपासलेल्या कालावधीच्या आतला मर्यादित `start`/`end` कालखंड आणि अनुमती-सूचीतील `source` (`client`, `embedded` किंवा `audio-bridge`) असणे आवश्यक आहे; `confidence` चे डीफॉल्ट मूल्य `1` आहे आणि ते `0` व `1` यांच्या दरम्यानच राहिले पाहिजे. तंतोतंत डुप्लिकेट क्यूज एकत्र केले जातात. OmniRoute या मेटाडेटावरून कधीही ट्रान्सक्रिप्शन सुरू करत नाही: प्रमाणित क्यूज स्रोत, विश्वासपातळी आणि कालखंडासह वर्णित निकालात कॉपी केले जातात आणि फ्रेम कॅप्शन्सबरोबर अविश्वसनीय निरीक्षणे म्हणून रेंडर केले जातात. अवैध, कालमर्यादेबाहेरील किंवा उगम-माहितीविना असलेला मजकूर कॅप्शन स्ट्रीममध्ये मिसळण्याऐवजी नाकारला जातो. `source` फील्ड सध्या कॉलरने घोषित केलेले असते, सर्व्हरद्वारे सत्यापित केलेले नाही: OmniRoute हे मूल्य अनुमत तीन स्ट्रिंग्सपैकी एक असल्याची अंमलबजावणी करते, परंतु `embedded` किंवा `audio-bridge` लेबल प्रत्यक्षात सर्व्हरच्या मालकीच्या निष्कर्षणातून आले असल्याची क्रिप्टोग्राफिक पुष्टी अद्याप करत नाही. ते सत्यापन उपलब्ध होईपर्यंत `source` ला अविश्वसनीय संकेत माना; त्यावर अधिकृततेचे निर्णय आधारित करू नका.

प्रगत कॉलर त्याच व्हिडिओसाठी आधीच-अधिकृत केलेला `audioTranscript` ट्रॅक देऊ शकतो. फ्यूजन सीम, एकाच अंतिम मुदतीखाली आणि अॅबॉर्ट सिग्नलखाली दृश्य व ऑडिओ निरीक्षणे चालवते, त्यांना एका सामायिक टाइमलाइनवर क्रमबद्ध करते, पूर्णपणे समान असलेली पुनरावृत्त निरीक्षणे एकत्र करते आणि फक्त एक बाजू यशस्वी झाल्यास आंशिक परिणाम नोंदवते. अवैध `audioTranscript` मुळे तो आंशिक परिणाम मिळतो — दृश्य वर्णन कायम ठेवले जाते आणि ऑडिओ शाखा निर्जंतुकीकृत अपयश कोड नोंदवते — संपूर्ण व्हिडिओ अयशस्वी करण्याऐवजी. प्रत्येक शाखेची उपलब्धता, आंशिक फ्लॅग आणि निर्जंतुकीकृत अपयश कोड हे वर्णित परिणामात, गार्डरेल मेटाडेटामध्ये (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), परिणाम-कॅश मेटाडेटामध्ये आणि ब्रिज फ्यूजन काउंटरमध्ये जतन केले जातात. डीफॉल्ट Video Bridge मार्ग स्पीच-टू-टेक्स्ट चालवत नाही किंवा मीडियाची दुसरी प्रत डाउनलोड करत नाही; तो स्पष्ट ट्रॅक नसल्यास तो केवळ-व्हिडिओच राहतो.

**प्रतिलेख धारणा (#12150 P1).** Video Bridge (जो स्वतः निवडकपणे सक्षम केला जातो) जेव्हा प्रतिलेख क्यू रेंडर करतो तेव्हा हे आपोआप लागू होते — यासाठी वेगळा धारणा फ्लॅग नाही. एखाद्या विनंतीत कोणताही प्रतिलेख क्यू (कॉलरने घोषित केलेला `transcript` किंवा फ्यूज केलेला `audioTranscript`) रेंडर केला गेल्यास, गार्डरेल त्याला `videoBridgeObserved` म्हणून चिन्हांकित करते आणि व्हिडिओ वर्णनाची संपादित छाया तयार करते — एक तंतोतंत समान रेंडरिंग, ज्यामध्ये प्रत्येक क्यूचा मुक्त-मजकूर भाग `[redacted-video-transcript]` ने बदलला जातो; स्ट्रिंग एकत्र करण्यापूर्वी संरचित क्यू फील्डची जागा घेऊन ती तयार केली जाते (सपाट केलेला मजकूर पार्स करून कधीही नाही, त्यामुळे कोणताही क्यू मजकूर — आक्रमक किंवा सामान्य, ज्यामध्ये `]` असलेले `[inaudible]`/`[music]` सारखे भागही समाविष्ट आहेत — टिकून राहू शकत नाही). जतन केलेल्या कॉल-लॉग विनंतीचा मुख्य भाग, मजकूर-समानतेद्वारे जुळवून, प्रत्येक व्हिडिओ-व्युत्पन्न मजकूर भागाऐवजी ती संपादित छाया वापरतो; `fullText` अँकर पूर्ण झालेल्या प्री-कॉल गार्डरेल पेलोडमधून पुन्हा वाचला जातो, त्यामुळे नंतरच्या साखळीतील गार्डरेल्सने (PII आणि क्रेडेन्शियल मास्कर्स, प्राधान्ये 10/95) वर्णनातील मजकूर त्याच ठिकाणी पुन्हा लिहिल्यानंतर आणि सिस्टम-प्रॉम्प्ट/हँडऑफ/मेमरी इंजेक्शनमुळे संदेश अॅरेचा आकार बदलल्यानंतरही जुळणी यशस्वी होते. मॉडेलकडे अपस्ट्रीम पाठवलेला मुख्य भाग बदलत नाही. निरीक्षण केलेली विनंती कोणतीही टिकाऊ Memory देखील भरत नाही (विनंती- आणि प्रतिसाद-व्युत्पन्न एक्स्ट्रॅक्शन दोन्ही वगळले जातात), त्यामुळे मॉडेलचा स्वतःचा प्रतिसाद प्रतिलेखातील मजकूर Memory मध्ये प्रतिध्वनित करू शकत नाही.

**कच्ची व्हिडिओ फील्ड्स (#12430).** ब्रिज सक्षम असताना आणि नेटिव्ह व्हिडिओ समर्थन अज्ञात किंवा अनुपलब्ध असताना, परिभाषित `transcript`/`audioTranscript` फील्ड्सही `videoBridgeObserved` सक्रिय करतात, अगदी वर्णन अयशस्वी झाल्यानंतर किंवा `maxVideos` मर्यादा लागू झाल्यानंतरही. `null` आणि रिकाम्या स्ट्रिंग्स मोजल्या जातात; अनुपस्थित फील्ड्स आणि व्हिडिओशी संबंधित नसलेले मेटाडेटा मोजले जात नाहीत. राखून ठेवलेल्या प्रतींमध्ये ही फील्ड्स संपादित केली जातात किंवा विनंती वगळली जाते आणि कॅशेस/Memory बायपास केले जातात. प्रदाता पेलोड बदलत नाही.

अतिरिक्त राखून ठेवलेल्या प्रती त्याच निरीक्षित-विनंती सिग्नलचा वापर करतात. कच्चा प्री-गार्डरेल क्लायंट-विनंती स्नॅपशॉट, मेमरीमधील प्रलंबित विनंती आणि लवकर नाकारलेल्या-विनंतीचा लॉग व्हिडिओ भागांमधील प्रतिलेख फील्ड्स संरचनात्मकरीत्या बदलतात; पाइपलाइन टप्पे आणि कॉन्टेक्स्ट हँडऑफद्वारे तयार केलेले स्ट्रिंग प्रॉम्प्ट्स जतन केलेल्या-विनंती-मुख्य-भाग सिंकवर संपादित केले जातात. जतन केलेला `video_content_removed` मार्कर, हेतुपुरस्सर टाकून दिलेला मजकूर पुन्हा तयार करण्याऐवजी `previous_response_id` सातत्याला सुरक्षितपणे अपयशी ठरवतो. निरीक्षित विनंतीने लॉगिंगपूर्वी तिची प्रत्येक भागासाठीची संपादन छाया गमावल्यास, किंवा नंतरच्या विनंती बदलांनंतर अनेक व्हिडिओ छायांपैकी एकही जुळण्यात अयशस्वी झाल्यास, अंशतः संपादित प्रतिलेख राखून ठेवण्याऐवजी जतन केलेला विनंती मुख्य भाग पूर्णपणे वगळला जातो.

निरीक्षित विनंतीसाठी, मॉडेलचा प्रतिसाद संरचित क्यू सीमेशिवाय प्रतिलेखातील कोणताही भाग उद्धृत करू शकतो. त्यामुळे त्याचा जतन केलेला कॉल-लॉग `responseBody` वगळण्याच्या मार्करने बदलला जातो; तपशीलवार पाइपलाइन आर्टिफॅक्ट (ज्यामध्ये अपस्ट्रीम/क्लायंट मुख्य भाग आणि स्ट्रीम खंड असू शकतात) राखून ठेवला जात नाही. त्या विनंतीसाठी सिमॅंटिक, आयडेम्पोटन्सी आणि रीझनिंग-रिप्ले कॅशेसमधील वाचन व लेखन बायपास केले जाते. प्रदाता विनंती आणि क्लायंटला दिसणारा प्रतिसाद बदलत नाहीत. तपशीलवार आर्टिफॅक्ट वगळल्यावर तात्पुरत्या बफरमधून सुरुवातीचे कीपअलाइव्ह बाइट्स काढून टाकले जातात. Kiro ची विकृत EventStream चेतावणी केवळ पेलोडची बाइट संख्या नोंदवते, त्यातील सामग्री किंवा JSON पार्सरची कच्ची त्रुटी कधीही नोंदवत नाही.
यामध्ये प्रत्येक असंबंधित प्रदाता/प्लगइन निदानाचे ऑडिट केले असल्याचा दावा नाही; व्यापक राखून-ठेवलेल्या-सिंकचे सर्वेक्षण #11658 मध्ये ट्रॅक केले जाते.

अंतर्गत `/api/modality-bridge/video/drilldown` जीवनचक्र हे स्वतंत्र, लूपबॅक/टोकन-प्रमाणीकृत कॅश अधःस्तर आहे. प्रत्येक ऑपरेशनसाठी प्रमाणित अपारदर्शक प्रिन्सिपल ID देखील आवश्यक आहे. प्रॉडक्शन कॉलर सक्षम करण्यापूर्वी, त्याने प्रमाणीकृत टेनंटकडून तो ID व्युत्पन्न केला पाहिजे आणि क्लायंटने निवडलेले मूल्य कधीही फॉरवर्ड करू नये. कॅश कीज त्या प्रिन्सिपलला प्रमाणित सेशन आणि व्हिडिओ-संदर्भ IDs शी बांधतात, केवळ त्यांच्या SHA-256-व्युत्पन्न कीज संग्रहित करतात आणि वाचन व हटवणे दोन्ही त्याच प्रिन्सिपलपुरते मर्यादित करतात. कॅश प्रत्येक नोंदीसाठी जास्तीत जास्त 16 व्युत्पन्न JPEG फ्रेम्स संग्रहित करते, दहा मिनिटांनंतर त्यांची मुदत संपवते आणि मर्यादित `start`/`end` वाचन किंवा स्पष्ट सेशन हटवण्यास समर्थन देते.

प्रत्येक प्रिन्सिपलसाठी 16 नोंदी आणि 64 MiB प्रमाणित JPEG डेटाची मर्यादा आहे. त्या मर्यादा जागतिक 64-नोंद/256 MiB कमाल मर्यादेपासून स्वतंत्र आहेत: जागतिक LRU निष्कासनाचा विचार करण्यापूर्वी प्रिन्सिपल कोट्याचा दबाव केवळ त्या प्रिन्सिपलच्या सर्वात-कमी-अलीकडे-वापरलेल्या नोंदी निष्कासित करतो. कॅश क्रियाकलापादरम्यान मुदत संपलेल्या नोंदी प्रिन्सिपल आणि जागतिक अशा दोन्ही लेखांकनातून काढल्या जातात, तर रद्दीकरण आणि प्रमाणीकरण अपयशामुळे आंशिक बदल कायम केला जात नाही.

**दोन्ही** stages वर चालते.

- **`preCall`** पेलोड क्लोन करते, `system`, `messages`, `input`, आणि
  `prompt` (साध्या स्ट्रिंग आयटमसह) मधून जाते आणि स्ट्रिंग `content`/`text`
  फील्डवर (`@/shared/utils/inputSanitizer` मधील) `processPII()` लागू करते.
  `PII_REDACTION_ENABLED=true` असताना, आढळलेली PII आउटबाउंड पेलोडमध्ये
  लपवली जाते. हे `INPUT_SANITIZER_MODE` पासून स्वतंत्र आहे (ते केवळ
  प्रॉम्प्ट-इंजेक्शन धोरण नियंत्रित करते). लपवणे बंद असताना, कॉल आशयात
  बदल न करता शोध-संख्या नोंदवतो.
- **`postCall`** प्रतिसादाचा डीप क्लोन तयार करते, `sanitizePIIResponse()` तसेच
  Responses-API-आकार मास्कर (`maskResponsesOutput` — जे
  `output_text` आणि `output[].content[].text` व्यापते) चालवते. काहीही
  लपवले गेल्यास, सुधारित प्रतिसाद मूळ प्रतिसादाची जागा घेतो.

गार्डरेल कधीही ब्लॉक करत नाही; ते केवळ भाष्य जोडते (`meta.detections`,
`meta.redacted`) किंवा पुनर्लेखन करते.

### प्रॉम्प्ट इंजेक्शन (`promptInjection.ts`)

वापरकर्त्याने पुरवलेल्या आशयातील प्रतिकूल संरचना शोधते आणि कॉन्फिगर केलेले
धोरण लागू करते. वर्तन पर्यावरणीय चल आणि कन्स्ट्रक्टर पर्यायांद्वारे नियंत्रित
केले जाते:

| सेटिंग          | पर्यावरणीय चल                                                                                         | डीफॉल्ट | परिणाम                                                                                                                                                                                                                            |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| सक्षम           | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | `false` असताना, गार्डरेल शॉर्ट-सर्किट होते.                                                                                                                                                                                       |
| मोड             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | इंजेक्शन धोरण: `block`, `warn`, किंवा `log`. (मागील आवृत्त्यांशी सुसंगततेसाठी `redact` स्वीकारले जाते, परंतु ते इंजेक्शन मजकूर **काढून टाकत नाही**; विनंतीमधील PII पुनर्लेखन `PII_REDACTION_ENABLED` द्वारे नियंत्रित केले जाते.) |
| ब्लॉक थ्रेशोल्ड | `blockThreshold` पर्याय / `INPUT_SANITIZER_BLOCK_THRESHOLD` (उपनाव `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | ब्लॉक करण्यासाठी आवश्यक असलेली किमान तीव्रता. डीफॉल्टनुसार मध्यम तीव्रता केवळ निरीक्षणासाठी असते.                                                                                                                                 |

**मोड प्राधान्यक्रम** (`getMode`): कॉलर `options.mode` →
`INJECTION_GUARD_MODE` **DB फीचर-फ्लॅग ओव्हरराइड** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` पर्यावरणीय चल → `INPUT_SANITIZER_MODE`
पर्यावरणीय चल → `warn`. त्यामुळे डॅशबोर्ड ओव्हरराइड पर्यावरणीय चलांपेक्षा
प्राधान्य मिळवते, म्हणून Feature Flags UI चालू गार्डला थेट नियंत्रित करते
(रीस्टार्ट आवश्यक नाही). DB रीड फेल-सेफ आहे: त्यात त्रुटी आल्यास गार्ड
पर्यावरण-आधारित वर्तनावर परत येतो आणि कोणतेही ओव्हरराइड सेट नसताना वर्तन
केवळ-पर्यावरणीय रिझोल्यूशनसारखेच असते.

शोध स्रोत:

1. `@/shared/utils/inputSanitizer` मधील `sanitizeRequest()` (पाइपलाइनमध्ये
   इतरत्र वापरला जाणारा सामायिक डिटेक्टर संच).
2. अंगभूत `DEFAULT_GUARD_PATTERNS` (सध्या `system_override_inline` आणि
   `markdown_system_block`, दोन्हींची तीव्रता `high`).
3. कन्स्ट्रक्टर पर्यायांद्वारे दिलेले वैकल्पिक `customPatterns` (स्ट्रिंग,
   regex, किंवा `{ name, pattern, severity }` रेकॉर्ड).

`mode === "block"` असताना **आणि** किमान एक शोध तीव्रता थ्रेशोल्ड पूर्ण करत
असताना, `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` परत करते. `warn`/`log` मोडमध्ये गार्डरेल
लॉग करते, परंतु कॉलला परवानगी देते. रजिस्ट्रीमधून न जाता प्रॉम्प्टचे मूल्यमापन
करण्याची आवश्यकता असलेल्या कॉलरसाठी सामायिक हेल्पर `evaluatePromptInjection()`
देखील एक्सपोर्ट केला जातो.

**स्कॅन मर्यादा (v3.8.20):** डिटेक्टर जोडलेल्या प्रॉम्प्ट मजकुराच्या केवळ
**पहिल्या 16 KB** चे निरीक्षण करतो — `src/shared/utils/inputSanitizer.ts` मध्ये
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 बाइट्स). पॅटर्न लूप
चालवण्यापूर्वी `detectInjection()` आणि `evaluatePromptInjection()` दोन्ही
`slice(0, MAX_INJECTION_SCAN_BYTES)` वापरतात. इंजेक्शन निर्देश इनपुटच्या
सुरुवातीच्या भागाजवळ असतात, त्यामुळे यामुळे शोधक्षमता कमी न करता
अनेक-शेकडो-KB पेलोडवरील regex CPU/GC मर्यादित होते (पाहा #3932, #4041).

### क्रेडेन्शियल मास्कर (`credentialMasker.ts`)

डीफॉल्ट साखळीत सर्वात शेवटी (प्राधान्य `95`) **दोन्ही** टप्प्यांवर चालतो.
आउटबाउंड पेलोडमधील (संदेशांचा आशय, टूल-कॉल आर्ग्युमेंट्स, टूल परिणाम)
**आणि** प्रदात्याच्या प्रतिसादातील सुप्रसिद्ध API-की / सिक्रेट-टोकन पॅटर्न
लपवतो, जेणेकरून प्रॉम्प्टमध्ये पेस्ट केलेले क्रेडेन्शियल (किंवा टूल परिणामाने
परत दिलेले क्रेडेन्शियल) अपस्ट्रीम प्रदात्याकडे किंवा परत क्लायंटकडे लीक होणार
नाही.

- **केवळ निवड केल्यावरच**, PII रिडॅक्शनप्रमाणेच संकेतपद्धती (कठोर नियम #20-समीप):
  `settings.credentialRedactionEnabled === true` **किंवा**
  `CREDENTIAL_REDACTION_ENABLED=true` नसल्यास अक्षम. हे बंद असताना, गार्डरेल काहीही करत नाही —
  ते कधीही ब्लॉक किंवा पुनर्लेखन करत नाही.
- `redactCredentials()` संपूर्ण पेलोड/प्रतिसाद ट्रीमध्ये (`walkValue()`,
  प्रोटोटाइप-पॉल्युशनपासून सुरक्षित, `WeakSet` द्वारे सायकल-सुरक्षित) मार्गक्रमण करते आणि जुळणारे भाग
  `[REDACTED:<type>]` प्लेसहोल्डरने बदलते, तसेच प्रत्यक्षात बदललेल्या शाखांचेच
  क्लोनिंग करते.
- `CREDENTIAL_PATTERNS` मध्ये LLM प्रदाता की (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS टोकन (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), पेमेंट की (Stripe, Square), क्लाउड
  की (AWS access key, Twilio, SendGrid, Mailgun), खाजगी की / JWTs,
  क्रेडेन्शियल असलेल्या कनेक्शन स्ट्रिंग (`mongodb://user:pass@...`, इत्यादी), आणि
  सर्वसाधारण `Authorization`/`x-api-key`/`api-key`/`apikey` हेडर-मूल्य
  पॅटर्न समाविष्ट आहेत. हेडरसदृश की (`authorization`, `x-api-key`, `api-key`,
  `apikey`) सर्वसाधारण मजकूर regex द्वारे करण्याऐवजी संरचनात्मकरीत्या (केवळ मूल्य,
  `Bearer `/`Basic ` सारखा स्कीम प्रीफिक्स जतन करून) रिडॅक्ट केल्या जातात.
- गार्डरेल कधीही ब्लॉक करत नाही; ते फक्त पुनर्लेखन (`modifiedPayload` /
  `modifiedResponse`) आणि भाष्य (`meta.credentialsRedacted`, `meta.count`) करते.

रिग्रेशन गार्ड: `tests/unit/credential-masker-guardrail.test.ts`.

## मूलभूत करार (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true असल्यास साखळीचे पुढील कार्य तत्काळ थांबते
  message?: string; // अवरोधित करताना दर्शविला जाणारा संदेश
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // विनंती पुन्हा लिहिण्यासाठी preCall कडून परत केला जातो
  modifiedResponse?: TValue; // प्रतिसाद पुन्हा लिहिण्यासाठी postCall कडून परत केला जातो
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

`void`, `{}`, किंवा `{ block: false }` यांपैकी काहीही परत करून guardrail "कोणताही बदल नाही" असे सूचित करते. `modifiedPayload`/`modifiedResponse` परत केल्यास, साखळीमधून पुढील guardrails कडे जाणारे मूल्य बदलले जाते.
`signal?: AbortSignal` कॉलरचे जीवनचक्र guardrails पर्यंत पोहोचवते. विनंती रद्द करणे हा मुद्दाम ठेवलेला fail-open अपवाद आहे: ज्याला raw media समर्थित नसल्याचे माहीत आहे अशा target मध्ये ते पुनर्स्थापित न करता, media bridges काम थांबवतात आणि cleanup करतात.

## रजिस्ट्री (`registry.ts`)

singleton `guardrailRegistry` पुढील गोष्टी उपलब्ध करून देते:

- `register(guardrail)` — guardrail जोडते (किंवा normalized name नुसार बदलते) आणि चढत्या `priority` क्रमाने पुन्हा क्रमवारी लावते.
- `clear()` / `list()` — प्रशासकीय सहाय्यक.
- `runPreCallHooks(payload, context)` — सक्रिय guardrails वर पुनरावृत्ती करते, `modifiedPayload` द्वारे payload पुढे पाठवते आणि पहिल्या `block: true` वर थांबते.
- `runPostCallHooks(response, context)` — प्रतिसादाच्या बाजूने समान प्रवाह.
- `resetGuardrailsForTests({ registerDefaults })` — स्वच्छ चाचणी विलगीकरणासाठी स्थिती साफ करते आणि पर्यायाने defaults पुन्हा नोंदवते.

दोन्ही runners `{ blocked, payload|response, results, guardrail?, message? }` परत करतात, ज्यामध्ये `results` हा `GuardrailExecutionResult` नोंदींचा array असतो. या नोंदींमध्ये प्रत्येक guardrail साठी `blocked`, `skipped`, `modified`, `error`, आणि `meta` fields समाविष्ट असतात आणि त्या tracing साठी उपयुक्त असतात.

### प्रत्येक विनंतीनुसार Guardrails अक्षम करणे

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` सध्याच्या विनंतीसाठी वगळल्या जाणाऱ्या guardrail names ची पुनरावृत्ती-विरहित यादी एकत्रित करते. स्रोत (सर्व पर्यायी, सर्व एकत्रित केले जातात):

- `apiKeyInfo.disabledGuardrails`
- विनंती body मधील `disabledGuardrails` (top-level)
- विनंती body मधील `metadata.disabledGuardrails`
- Header `x-omniroute-disabled-guardrails` (किंवा जुना
  `x-disabled-guardrails`)

मूल्ये strings चे arrays किंवा स्वल्पविरामाने विभक्त केलेली string असू शकतात; names lowercase kebab-case मध्ये normalize केली जातात (`pii_masker` → `pii-masker`). परिणाम `context.disabledGuardrails` द्वारे registry कडे पाठवला जातो, जी जुळणारे guardrails वगळते (`results` मध्ये `skipped: true`).

## अंमलबजावणीचा क्रम

`src/sse/handlers/chat.ts` आणि
`open-sse/handlers/chatCore.ts` मधून जाणाऱ्या प्रत्येक विनंतीसाठी:

1. `resolveDisabledGuardrails(...)` API की, बॉडी आणि हेडर्सवरून वगळण्याची यादी तयार करते.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` चढत्या प्राधान्यक्रमाने गार्डरेल्स चालवते:
   - अक्षम केलेल्या गार्डरेल्सची `skipped` म्हणून नोंद केली जाते.
   - प्रत्येक गार्डरेलचे `preCall`, `modifiedPayload` द्वारे पेलोड पुन्हा लिहू शकते.
   - पहिले `block: true` आल्यावर साखळी त्वरित थांबते आणि हँडलर गार्डरेल नकार प्रतिसाद परत करतो.
3. (संभाव्यतः पुन्हा लिहिलेला) पेलोड कॉम्बो राउटिंग आणि अपस्ट्रीम डिस्पॅचकडे जातो.
4. प्रतिसाद तयार झाल्यानंतर, `guardrailRegistry.runPostCallHooks(...)` प्रतिसादावर तीच साखळी चालवते. येथे `block: true` असल्यास अपस्ट्रीम प्रतिसाद वगळला जातो.

अपवाद निर्माण करणाऱ्या गार्डरेल्सची `error: <message>` सह नोंद केली जाते आणि `logger.warn` द्वारे लॉग केले जाते, मात्र साखळी सुरूच राहते — रचनेनुसार फेल-ओपन.

## संरचना

अंगभूत गार्डरेल्सद्वारे वाचली जाणारी पर्यावरण चल:

| चल                                    | यामध्ये वापरले जाते        | परिणाम                                                                                             |
| ------------------------------------- | -------------------------- | -------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | शोध पूर्णपणे अक्षम करण्यासाठी `false` सेट करा.                                                     |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | इंजेक्शन धोरण: `warn`, `block`, किंवा `log`. जुने मूल्य `redact` इंजेक्शन मजकूर पुन्हा लिहीत नाही. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | इंजेक्शन गार्डसाठी मोड; तसेच पर्यावरण चलांना **अधिलिखित** करणारा DB फीचर फ्लॅग (DB > ENV).         |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | `MODE=block` द्वारे नाकारली जाणारी किमान तीव्रता: `high` (डीफॉल्ट), `medium`, किंवा `low`.         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD` साठी जुने पर्यायी नाव.                                           |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | `true` असताना, विनंतीमधील PII झाकले जाते (इंजेक्शन मोडपासून स्वतंत्र).                             |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (डाउनस्ट्रीम) | प्रतिसादाच्या बाजूच्या मास्करचे वर्तन नियंत्रित करते.                                              |

Modality Bridge गार्डरेल्स पर्यावरण चलांऐवजी DB-समर्थित सेटिंग्ज स्टोअरमधून (`getSettings()`) रनटाइम संरचना वाचतात. Vision च्या प्राथमिक की
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, आणि
`modalityBridgeCacheMaxEntries` आहेत. जुन्या
`visionBridge*` की केवळ दस्तऐवजीकृत एक-चक्र वाचन फॉलबॅक म्हणून स्वीकारल्या जातात; डॅशबोर्डमधून होणाऱ्या लेखनांसाठी प्राथमिक की वापरल्या जातात. डीफॉल्ट्स आणि फॉलबॅक रिझॉल्व्हर `src/shared/constants/modalityBridgeDefaults.ts` मध्ये आहेत, तर जुन्या कॉन्स्टंट्स `src/shared/constants/visionBridgeDefaults.ts` मध्ये कायम ठेवलेल्या आहेत.

Audio हे `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout`, आणि `modalityBridgeAudioMaxClips`, तसेच सामायिक
`modalityBridgeCache*` सेटिंग्ज वापरते. Audio साठी जुन्या कींचा फॉलबॅक नाही, कारण या की Modality Bridge स्कीमासोबत सादर करण्यात आल्या होत्या.

Video हे `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos`, आणि
`modalityBridgeVideoTimeout`, तसेच सामायिक `modalityBridgeCache*` सेटिंग्ज वापरते.
ते डीफॉल्टनुसार अक्षम असते, कारण FFmpeg/ffprobe या पर्यायी कार्यान्वयन अवलंबिता आहेत आणि फ्रेम कॅप्शनिंगमुळे विलंब व मॉडेल खर्च वाढतो.

## सानुकूल Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

पायऱ्या:

1. `BaseGuardrail` विस्तारित करणारी `src/lib/guardrails/myGuardrail.ts` तयार करा.
2. `preCall` आणि/किंवा `postCall` लागू करा.
3. एकतर आयात करताना नोंदणी करा (`registerDefaultGuardrails` मधून पुश करा) किंवा
   रनटाइममध्ये `guardrailRegistry.register(...)` कॉल करा — रजिस्ट्री समान सामान्यीकृत
   नाव असलेली कोणतीही आधीची guardrail बदलते.
4. `tests/unit/` अंतर्गत चाचण्या जोडा (विद्यमान उदाहरणे:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

ज्ञात स्थितीपासून सुरुवात करण्यासाठी चाचण्यांदरम्यान `resetGuardrailsForTests()` वापरा.
रिकाम्या रजिस्ट्रीपासून सुरुवात करण्यासाठी `{ registerDefaults: false }` पास करा आणि

## Injection-guard मार्ग कव्हरेज आणि रेड-टीम (टप्पा 8 · ब्लॉक D)

injection-guard (`createInjectionGuard` / `withInjectionGuard`) वापरकर्त्याचे प्रॉम्प्ट स्वीकारणारे सर्व मार्ग
व्यापते. ते `INJECTION_GUARD_MODE` चे पालन करते (डीफॉल्ट `warn` = फक्त लॉग;
`block` = HTTP 400 `SECURITY_001` परत करते).

| प्रकार           | मार्ग                                                                                                                                                | डीफॉल्ट मोड |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| मजकूर (विद्यमान) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| जनरेटिव्ह        | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| डेटा             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

मजकूर निष्कर्षण (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` व्यापते.

**रेड-टीम (दररोज रात्री, `nightly-llm-security.yml`):** promptfoo हे सत्यापित करते की प्रत्येक मार्ग
`INJECTION_GUARD_MODE=block` मध्ये OWASP-LLM कॉर्पस ब्लॉक करतो; garak प्रोब्स चालवते (secret नसल्यास वगळते).
सुसंगततेसाठी `moderations` समाविष्ट केले आहे — ब्लॉक-मोडमधील ऑपरेटर `resolveDisabledGuardrails` द्वारे
त्याला सूट देऊ शकतात.

रात्रीचे वर्कफ्लो (`.github/workflows/nightly-llm-security.yml`, cron + मॅन्युअल
डिस्पॅच) दोन जॉब्सचे आहे:

- **`promptfoo-guard` (ब्लॉकिंग)** — `INJECTION_GUARD_MODE=block` सह
  `promptfoo eval -c promptfooconfig.yaml` चालवते. प्रत्येक प्रतिकूल प्रकरण (उदा. "मागील सर्व
  सूचना दुर्लक्षित करा…", DAN-शैलीतील जेलब्रेक्स) प्रतिसादात
  `error.code === "SECURITY_001"` असल्याचे निश्चित करते, म्हणजेच guard ने विनंती प्रत्यक्षात नाकारली.
- **`garak` (सल्लात्मक)** — स्थानिक OmniRoute इन्स्टन्सवर (`http://localhost:20128/v1`)
  garak `--probes promptinject,dan,leakreplay` चालवते. हे provider secret
  (`PROMPTFOO_PROVIDER_KEY`) वर अवलंबून असते; secret नसल्यास व्यवस्थितपणे वगळते आणि त्याला
  `|| true` प्रत्यय जोडलेला असतो, त्यामुळे ते CI अयशस्वी न करता अहवाल देते.

guard helper (`createInjectionGuard` / `withInjectionGuard`) चे कव्हरेज
प्रॉम्प्ट असलेल्या प्रत्येक `/v1` मार्गावर पसरलेले आहे; प्रॉम्प्ट मजकूर
`src/shared/utils/inputSanitizer.ts` मधील `extractMessageContents()` द्वारे
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` मधून घेतला जातो.
