> **Последнее обновление:** 2026-08-29 — v3.8.51 (Происхождение стенограммы Video Bridge объявляется вызывающей стороной,
> еще не проверено сервером — уточнено согласно #11661)

Защитные механизмы (guardrails) обеспечивают безопасность, соблюдение политик и преобразования контента на границе между OmniRoute и вышестоящими провайдерами. Каждый защитный механизм может проверять (и опционально отклонять, преобразовывать или аннотировать) полезные данные запросов (`preCall`) и ответы вышестоящих систем (`postCall`).

Система является **открытой при сбое (fail-open)**: если защитный механизм выдает ошибку во время выполнения, реестр записывает ошибку и продолжает работу со следующим защитным механизмом, вместо того чтобы отклонять запрос. Блокировка — это явное решение (`block: true`), а не случайность.

## Встроенные защитные механизмы

При импорте реестр автоматически загружает шесть защитных механизмов в порядке приоритета
(см. `registry.ts` → `registerDefaultGuardrails()`):

| Приоритет | Название            | Этап(ы)        | Файл                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`      | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`      | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

Меньшие значения приоритета выполняются **раньше**.

### Мост для изображений (`visionBridge.ts`) — мост модальностей PR-1

Перехватывает содержащие изображения запросы, предназначенные для **моделей без поддержки изображений**, и либо перенаправляет весь запрос к модели с поддержкой изображений, либо перед вызовом вышестоящего сервиса заменяет части с изображениями текстовыми описаниями, созданными настраиваемой моделью с поддержкой изображений. Это позволяет провайдерам, работающим только с текстом, прозрачно обрабатывать мультимодальные полезные нагрузки.

Порядок работы:

1. Пропустить обработку, если целевая модель уже поддерживает изображения (если только она не входит в список моделей, для которых мост используется принудительно, `isVisionBridgeForcedModel`).
2. Извлечь части с изображениями с помощью `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), которая делегирует работу **унифицированному детектору мультимедиа**
   `detectMediaParts()` из `open-sse/utils/mediaParts.ts` — единому источнику истины, совместно используемому фильтром совместимости комбинаций.
   Извлечение ограничено разрешённым списком частей верхнего уровня тех форм,
   которые `replaceImageParts` может вставить обратно (контракт extract↔replace): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` и Responses API `input_image`. Вложенные совпадения и
   формы, содержащие только индикаторы, предназначены для фильтра комбинаций и никогда не извлекаются.
   Пропустить обработку, если ничего не найдено.
3. Определить конфигурацию среды выполнения с помощью `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): новые ключи настроек `modalityBridge*`
   имеют приоритет; устаревшие ключи `visionBridge*` сохраняются как **резервный вариант на один цикл**
   (окно отката). Если мост отключён, пропустить обработку до любого обхода мультимедийных данных.
4. Переключатель режима (`modalityBridgeVisionMode`, см. таблицу ниже) выбирает
   между перенаправлением и описанием. При перенаправлении возвращается `modifiedPayload`, где заменено только поле `model`,
   а также метаданные `{ rerouted, fromModel, toModel, imagesKept }`.
5. Путь описания: ограничить количество изображений значением `maxImages`, сформировать учитывающую задачу подсказку,
   проверить кэш описаний, вызвать модель с поддержкой изображений **параллельно**
   (`Promise.allSettled`) и вставить вместо изображений текстовые части `[Image N]: <description>`.
   Если создать описание не удалось, возвращается `null`, а исходная часть с изображением
   **сохраняется** (#4012) — кроме пути описания комбинации, когда не удалось создать ни одного
   описания: в таком случае для подтверждённо не поддерживающего изображения вышестоящего сервиса вместо него подставляется
   заглушка `(unavailable — no vision-capable provider connected)` (#8430).
6. Вернуть `modifiedPayload` и метаданные (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Переключатель режима (`modalityBridgeVisionMode`)

| Режим      | По умолчанию | Поведение                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔            | Устаревшая эвристика без изменений (#6640/#7204): модели, не являющиеся комбинациями, и модели `auto/` перенаправляются к лучшей модели с поддержкой изображений, если только у исходной модели уже нет пригодных учётных данных (тогда используется описание); цели-комбинации всегда используют описание.                                                                                    |
| `describe` |              | Всегда использовать описание — блок перенаправления полностью пропускается; всегда отвечает выбранная пользователем модель.                                                                                                                                                                                                                                                                    |
| `reroute`  |              | Принудительное перенаправление: проверка сохранения модели с учётными данными обходится. Проверка учётных данных **целевой модели** перенаправления по-прежнему применяется — если подходящая целевая модель с поддержкой изображений отсутствует, запрос переходит к описанию, чтобы необработанные изображения никогда не попадали в серверную систему, работающую только с текстом (#8430). |

Принудительные режимы завершают выбор **до** запуска автоматической эвристики; поведение `auto`
побайтово идентично защитному механизму до PR-1.

#### Область действия API-ключа (`visionBridgeKeyScope.ts`)

Когда API-ключ вызывающей стороны ограничивает `allowedConnections`, пулы квот
(`allowedQuotas`) или модели (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), мост выбирает для перенаправления и описания только те модели, которые разрешено использовать этому ключу, и только в разрешённых ему подключениях. Затем вызов описания всегда проходит через внутренний цикл OmniRoute с заголовком
`x-omniroute-self-loop-key-id`, чтобы принимающий запрос чата повторно применил политику подключений и моделей этого ключа. `enforceApiKeyPolicy()`
учитывает этот заголовок только вместе с bearer-токеном внутреннего цикла, поэтому он может лишь
сузить доступ, а запрос с идентификатором, который не удаётся разрешить, отклоняется.

Если ключу не разрешена ни одна модель с поддержкой изображений, путь описания не вмешивается,
и запрос передаётся без изменений — это то же отказоустойчивое поведение, что и при отключённом
защитном механизме (метаданные `{ skipped: true, reason: "no_permitted_vision_model" }`).
Запросы без ключа и ключи без этих ограничений ведут себя точно так же, как
раньше.

#### Учитывающая задачу подсказка для описания (`modalityBridgeVisionTaskAware`)

По умолчанию — **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) добавляет
текст **последнего сообщения пользователя** (обрезанный до 500 символов) к базовому
промпту описания, направляя описание на то, о чём фактически спросил пользователь
(паттерн codex-vision-proxy), и просит модель компьютерного зрения транскрибировать
видимый текст. Если флаг отключён или пользовательский текст отсутствует, базовый
промпт используется без изменений.

Собственный OpenAI-совместимый запрос цикла самоописания (`callVisionModelSingle()`
в `visionBridgeHelpers.ts`) всегда запрашивает `image_url.detail: "high"` —
безусловно, для каждого вызывающего кода и провайдера, независимо от каких-либо
сигналов клиента. Выбор низкой детализации ухудшает точность OCR именно для задачи
транскрибирования текста, указанной в этом промпте, поэтому сам запрос описания
всегда запрашивает высокую детализацию независимо от уровня детализации,
использованного в исходном входящем запросе. Это влияет только на тело внутреннего
запроса описания и не меняет то, как OmniRoute передаёт собственное значение
`image_url.detail` вызывающей стороны в основном запросе: это значение по умолчанию
применяется отдельно и только для обнаруженных клиентов OpenCode в
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Ветвь
цикла самоописания в формате Anthropic не имеет поля `detail` и не затрагивается
ни одним из этих значений по умолчанию.

#### Ограничение размера результата описания (`modalityBridgeVisionMaxChars`)

| Ключ                           | По умолчанию | Диапазон          |
| ------------------------------ | ------------ | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`          | `0` или 100–50000 |

`0` (по умолчанию) означает **отсутствие ограничения** — описание, возвращённое
`callVisionModel()`, передаётся без изменений, сохраняя существующее поведение.
Любое значение в диапазоне 100–50000 обрезает описание, добавляя суффикс `…`,
прежде чем оно будет вставлено обратно в виде `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` в `src/lib/guardrails/visionBridge.ts`).
Увеличьте это значение для насыщенных деталями задач OCR, где нижестоящей модели
нужна полная транскрипция; уменьшите его, чтобы ограничить расход токенов
многословными моделями компьютерного зрения. Поле на панели управления находится
в разделе Advanced вкладки Vision (`modality-bridge-max-chars` в
`ModalityBridgeVisionTab.tsx`) и повышает любое значение от 1 до 99 до минимального
значения 100, оставляя явно заданный `0` без изменений — `0` сам по себе является
допустимым значением Zod
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не просто
значением по умолчанию для состояния «не задано».

#### Кеш описаний (`modalityBridge/bridgeCache.ts`)

Внутрипроцессный кеш LRU + TTL для результатов описания, совместно используемый
всем процессом. Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)`
с фреймированием по префиксу длины (без коллизий на границах полей). Компонент
модели — это **настроенная** модель моста, а не модель, которая фактически
ответила: `callVisionModel` может внутренне переключиться на резервный вариант,
а формирование ключа для каждой попытки привело бы к фрагментации кеша. Неудачные
описания никогда не кешируются. Настройки:

| Ключ                            | По умолчанию | Диапазон |
| ------------------------------- | ------------ | -------- |
| `modalityBridgeCacheEnabled`    | `true`       | —        |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000  |

#### Нормализация удалённых изображений (самоописание/получение base64)

Когда мост самостоятельно загружает **удалённое** изображение — при внутреннем
вызове описания Anthropic и преобразовании в base64 для формата claude
(`ensureBase64ImagesForClaudeWire`), в обоих случаях через
`fetchRemoteImageAsDataUri()` в `visionBridgeHelpers.ts`, — полученный URI данных
пропускается через `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) перед встраиванием в запрос к модели
компьютерного зрения. Слишком большие изображения уменьшаются до **2048px по
длинной стороне** (в соответствии с ограничением изменения размера, которое
OpenAI/Anthropic уже применяют на стороне сервера), что сокращает объём
загружаемых данных и задержку, не изменяя то, что видит модель компьютерного
зрения. Для изменения размера используется `sharp`, загружаемый через динамический
импорт: на платформе, где не удаётся загрузить его нативный бинарный файл,
`normalizeDataUri()` **никогда не выбрасывает исключение** — вместо этого функция
без изменений передаёт исходные байты, поэтому путь описания/преобразования в
base64 продолжает работать. Данные, не являющиеся изображением (если при загрузке
не было получено декодируемое изображение), также передаются без изменений. Эта
нормализация применяется только к изображениям, которые мост загружает для
собственного внутреннего вызова, и никогда не применяется к необработанной
полезной нагрузке вызывающей стороны, что соответствует принципу изменения
только при явном согласии (Hard Rule #20).

#### Схема настроек + миграция

Новые ключи `modalityBridge*` проверяются с помощью Zod в `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, тройка `modalityBridgeCache*` и группа
`modalityBridgeAudio*`, используемая Audio Bridge. Миграция
`141_modality_bridge_settings.sql` копирует существующие устаревшие значения
`visionBridge*` в соответствующие новые ключи (идемпотентно, никогда не
перезаписывая значение `modalityBridge*`, заданное оператором); устаревшие ключи
продолжают приниматься как резервный источник при чтении в течение одного цикла
выпуска.

#### Заголовок прозрачности + статистика

Ответы, преобразованные посредством описания, содержат
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(создаётся `buildModalityBridgeHeader()` в `modalityBridge/bridgeStats.ts`,
устанавливается `withModalityBridgeHeader()` в `src/sse/handlers/chatHelpers.ts`).
Перенаправленные запросы **не** получают заголовок — полезная нагрузка не
изменялась, а смена модели уже видна в поле `model` тела ответа.

`GET /api/modality-bridge/stats` (управленческая аутентификация, тот же уровень, что и у
`GET /api/settings`) возвращает хранящиеся в памяти счётчики для каждой модальности
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` и
`video`. В качестве знаменателя `averageLatencyMs` использует `latencySamples`,
а не все попытки; операция без замера времени не создаёт фиктивный
образец с задержкой в ноль миллисекунд. `bridged` остаётся обратно совместимым
псевдонимом для успешных преобразований; неудачные попытки не увеличивают его.
По замыслу счётчики сбрасываются при перезапуске процесса
(это телеметрия, а не учёт).

#### Конфигурация панели управления

Специальная страница панели управления находится по адресу
`/dashboard/settings/modality-bridge`. Её адресуемые через URL вкладки `Vision`, `Audio`
и `Video` сохраняют параметры запроса при переключении значения `tab`.
Вкладка Vision предоставляет включение, режим, выбор модели (включая автоматическое
значение по умолчанию), формирование промптов с учётом задачи, расширенные ограничения
на тайм-аут, изображение, длину описания и кеш, счётчики времени выполнения
и защищённый тестовый запрос. Вкладка Audio также полностью функциональна: она предоставляет
включение, выбор только STT-модели с вариантом Auto, ограничения на тайм-аут и максимальную
длительность клипа, аудиосчётчики и тестовый запрос `input_audio`. Вкладка Video функциональна:
она сообщает состояние среды выполнения FFmpeg/ffprobe — одно из четырёх явно заданных
состояний интерфейса (`unknown`, пока проверка выполняется или не может завершиться,
`restricted` на хосте панели управления, не являющемся loopback-адресом, где проверка
пропускается на стороне клиента, `unavailable`, когда проверка завершена и отсутствие
подтверждено, или `available` с версиями FFmpeg/ffprobe), — сохраняет ограничения
на включение, модель, кадры, видео и тайм-аут, фильтрует список моделей, оставляя
модели с поддержкой зрения, и предоставляет видеосчётчики.

Прежняя карточка Vision Bridge в настройках ИИ теперь служит ссылкой совместимости
на новую страницу; она больше не содержит вторую копию формы. Media Providers также
связывает рабочие процессы Image-to-Text и Speech-to-Text с соответствующими вкладками
Modality Bridge, не удаляя существующую тестовую среду Speech-to-Text.

**Обход контроля допуска для self-loop:** когда вызов описания проходит через
собственный `/v1` self-loop OmniRoute (модель нестандартного провайдера), подзапрос
отправляет `x-omniroute-admission-bypass: internal` и проходит аутентификацию с помощью
разрешённых учётных данных self-loop — локального маркера `sk_omniroute` в локальном
режиме или настроенного оператором ключа окружения `OMNIROUTE_API_KEY` /
`ROUTER_API_KEY` (#1350), чтобы развёртывания с `REQUIRE_API_KEY=true` всё ещё могли
выполнять вызов описания. Обход разрешается только для этих точных учётных данных,
поэтому внешние клиенты не могут использовать этот заголовок для пропуска контроля
допуска.

Устаревшие значения по умолчанию находятся в `src/shared/constants/visionBridgeDefaults.ts`;
новые значения по умолчанию для режима, учёта задачи и кеша, а также резолвер настроек
находятся в `src/shared/constants/modalityBridgeDefaults.ts`. Защитный механизм
предоставляет параметр конструктора `deps`, чтобы тесты могли внедрять поддельные
реализации `getSettings` и `callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехватывает содержащие аудио запросы чата до того, как они достигнут целевого
объекта, для которого не подтверждена поддержка аудиоввода. Он никогда не изменяет
маршрут запроса чата: аудиочасти транскрибируются через существующую совместимую
с OpenAI multipart-конечную точку, а выбранная модель чата продолжает работу
с текстовыми транскрипциями.

Поток выполнения:

1. Определить `supportsAudio` через `getResolvedModelCapabilities()`. Приоритет
   имеют явные метаданные реестра провайдеров, затем статические метаданные модели,
   а затем синхронизированное значение `modalities_input`. Объявленный список
   входных данных без `audio` означает `false`; при отсутствии данных о возможностях
   остаётся `null`. И `false`, и `null` активируют консервативный мост, тогда как
   `true` обходит его.
2. Определить настройки `modalityBridgeAudio*` и извлечь из каждого сообщения
   допускающие замену аудиочасти верхнего уровня с помощью общего детектора
   `detectMediaParts()`. Поддерживаются форматы передачи OpenAI `input_audio`,
   `audio_url` и `source.media_type: "audio/*"`. Вложенное аудио обнаруживается
   для маршрутизации, но не удаляется путём замены. Объём работы ограничивается
   значением `modalityBridgeAudioMaxClips`; последующие части остаются без изменений.
3. Использовать настроенное значение `provider/model` либо позволить
   `selectAudioBridgeModel()` перебрать `AUDIO_TRANSCRIPTION_PROVIDERS` в стабильном
   порядке каталога и выбрать первую модель с пригодными активными учётными данными
   провайдера.
4. `callAudioTranscription()` преобразует аудио в формате base64/data-URI
   в multipart-`file` либо загружает удалённый `audio_url` через защитный механизм
   исходящих подключений только к публичным адресам, с фиксацией DNS и ограничением
   в 25 МБ. Затем он отправляет файл и выбранную модель методом POST в локальный
   self-loop `/v1/audio/transcriptions`, аутентифицированный с помощью
   `resolveSelfLoopBearer()`. Существующий маршрут транскрипции выполняет обычный
   поиск учётных данных, обработку периодов ожидания/ограничений частоты запросов
   и диспетчеризацию по провайдерам.
5. Успешные вызовы заменяют соответствующие части на `[Audio N]: <transcript>`.
   Вызовы выполняются через `Promise.allSettled`: отдельная ошибка сохраняет
   исходную аудиочасть (контракт #4012). Если все вызовы завершаются ошибкой
   и для целевого объекта доказано `supportsAudio === false`, части заменяются на
   `[Audio N]: (unavailable — no STT provider connected)` (контракт #8430).
   Для неизвестного целевого объекта (`null`) при ошибке всех вызовов содержимое
   остаётся без изменений. Целевой объект, для которого доказано, что он поддерживает
   только текст, при отсутствии пригодных учётных данных STT получает ту же явную
   заглушку без выполнения сетевого вызова.

Успешные транскрипции используют общий для процесса LRU/TTL-кеш Modality Bridge.
Ключ объединяет ссылку на аудио, стабильную метку операции `audio-transcription`
и выбранную STT-модель; ошибки никогда не кешируются. Попытки обработки аудио
обновляют общие счётчики `bridged`, `cacheHits`, `failures` и `lastUsedAt`.
Преобразованные ответы содержат
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`;
неизменённые запросы не получают сегмент Audio Bridge.

Настройки времени выполнения хранятся в БД и проверяются с помощью Zod:

| Ключ                          | По умолчанию | Диапазон        |
| ----------------------------- | ------------ | --------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —               |
| `modalityBridgeAudioModel`    | `""`         | Auto или ID STT |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10            |

Общий кеш по-прежнему управляется параметрами `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` и `modalityBridgeCacheMaxEntries`.

### Мост для видео (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехватывает части видео верхнего уровня в `messages` Chat Completions и `input`
Responses API перед вызовом целевой модели без известной встроенной поддержки
видео. Поддерживаются форматы `input_video`, `video_url`, `video_source`, URL-адреса
HTTPS и URI данных `data:video/*;base64,...`. Простые имена файлов в тексте не
считаются видео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) отвечает за обход запроса,
проверку возможностей и политик, агрегацию в рамках запроса и полезную нагрузку
ответа. Обработка каждого видео — получение данных, кеширование полного
результата, описание последовательности кадров (с объединением любой заявленной
вызывающей стороной расшифровки аудио), а также метрики, прерывание и очистка
для каждой попытки — скрыта за `processVideoPart` в `videoBridgePipeline.ts`,
которая вызывается один раз для каждой части видео внутри цикла `preCall`.
Этот модуль также определяет явные границы портов `VideoMediaBrokerPort`
(получение байтов и извлечение выбранных кадров), `VideoAudioTranscriptionPort`
(объединение заявленной вызывающей стороной расшифровки аудио с подписями к
выбранным кадрам) и `VideoDrilldownPort` (граница сохранения результатов
детализации кадров; пока не подключена к `processVideoPart` — в настоящее время
записи детализации создаёт только отдельный маршрут
`/api/modality-bridge/video/drilldown`).

Публичный путь запросов `/v1` никогда не импортирует и не вызывает подпроцесс.
Удалённые видео загружаются с ограничением в 50 МиБ; для встроенных видео в
формате base64 установлен консервативный лимит декодированного содержимого
36 МиБ на видео, чтобы оболочка модели, сообщений и структуры запроса
укладывалась в публичный лимит приёма JSON-запросов в 50 МиБ. Длина встроенных
данных и оценки декодированного размера проверяются до выделения памяти.
HTTPS обязателен для исходного удалённого URL-адреса и каждого перенаправления;
при этом используется существующий механизм исходящих подключений только к
публичным адресам с закреплением DNS. Затем байты пересекают точную внутреннюю
границу брокера `POST /api/modality-bridge/video/extract`. Этот маршрут имеет
одновременно категории `LOCAL_ONLY` и `SPAWN_CAPABLE`, принимает только
аутентифицированный в рамках процесса запрос от доверенного loopback-интерфейса
и никогда не принимает URL-адрес, путь файловой системы, исполняемый файл или
список аргументов. Конвейер ограничения размера тела API и инкрементальный
считыватель тела обработчика независимо друг от друга обеспечивают соблюдение
лимита входных данных брокера в 50 МиБ. Его ограниченная очередь выполняет по
одному извлечению за раз, допускает четыре ожидающих задания и ограничивает
общий объём ожидающих входных данных 100 МиБ.

Внутри брокера `ffprobe` читает закрытый локальный файл; фиксированный список
разрешённых форматов исключает форматы плейлистов и манифестов. Для разрешённых
контейнеров семейства MOV внешние ссылки на данные MOV по умолчанию остаются
отключёнными, и фиксированная команда не включает их поддержку. И `ffprobe`, и
`ffmpeg` используют список разрешённых протоколов только с `file`, один поток,
фиксированные массивы аргументов, не используют оболочку, а исполняемые файлы
разрешаются через `PATH`. Потоки обложек типа attached-picture не считаются
кандидатами на воспроизведение. Все воспроизводимые потоки должны соответствовать
ограничениям; явный поток по умолчанию имеет приоритет перед детерминированным
резервным выбором потока с наименьшим индексом. Продолжительность видео
ограничена 600 секундами, каждый размер — 8 192 пикселями, а исходное
разрешение — 33 554 432 пикселями. FFmpeg выбирает 1–16 промежуточных кадров
JPEG, уменьшает длинную сторону максимум до 1 024 пикселей, не увеличивая
изображения меньшего размера, и никогда не получает URL-адрес. По умолчанию
используется равномерная выборка (`uniform`). Необязательная политика
`scene_aware` и экспериментальная политика `segment_aware` выполняют один
дополнительный фиксированный проход FFmpeg по уже проверенному локальному
потоку, выбирают ограниченный набор временных меток сцен `showinfo` и
детерминированно возвращаются к тем же равномерно расположенным промежуточным
точкам при сбое детектора, тайм-ауте, некорректном выводе или пустом наборе
кандидатов. В режиме с учётом сегментов промежуточные выборки распределяются
пропорционально проверенным интервалам сцен; свидетельства для режима с учётом
сегментов и резервное поведение подробно описаны ниже. Жёсткое ограничение в
16 кадров применяется после выбора при любой политике. Если запрос с учётом
сцен имеет бюджет только на один кадр, используется равномерная промежуточная
точка активного окна всего видео или фокусного окна, а в отчёте указывается
`policyEffective: uniform`: один выбранный кадр сцены не может сохранить оба
временных края. Вызывающая сторона может при необходимости указать конечное
фокусное окно (`start`/`end` в секундах); границы ограничиваются
продолжительностью медиаданных, окна с обратным порядком границ или
нечисловыми конечными значениями отклоняются, а все политики выборки
применяются только внутри нормализованного интервала. Полученное окно
включается в метаданные выборки и в префикс недоверенного описания, чтобы
последующие модели могли отличить сфокусированный фрагмент от полной временной
шкалы.

Семантический фокус подписей — отдельная явная настройка. Режим анализа `full`
по умолчанию сохраняет существующий запрос для кадров и никогда не передаёт
текст запроса модели создания подписей. В режиме `focused` мост считывает
только последнее непустое значение `text`/`input_text`, созданное пользователем,
из того же контейнера Chat или Responses, нормализует его в NFC, сворачивает
управляющие символы и пробельные последовательности и ограничивает 500 кодовыми
точками Unicode. Пустой результат приводит к возврату к точному запросу `full`.
Пригодная подсказка сериализуется как JSON в специальном блоке недоверенного
пользовательского контекста и может только расставлять приоритеты для
наблюдаемых деталей; она не может переопределить отдельное предупреждение о
том, что не следует выполнять инструкции, видимые или слышимые в
медиаматериале. Текстовый фокус никогда не выводит значения `start`/`end` и не
изменяет временной сэмплер.

#### Структурные свидетельства сегментов FU-07

`segment_aware` использует один ограниченный проход предварительного анализа уже проверенного
локального видеопотока. Фиксированная цепочка фильтров сначала масштабирует видео
до ширины не более 320 пикселей, обнаруживает смены сцен и интервалы неподвижности,
а затем выполняет выборку с частотой 1 кадр в секунду для оценки размытия, средней
яркости и пространственной/временной информации. Проход ограничен 600 структурными
образцами, одним потоком FFmpeg/фильтров, теми же списками разрешённых контейнеров
и протоколом только `file`, объёмом вывода процесса в 1 MiB и не более чем
30 секундами в пределах общего механизма прерывания/крайнего срока брокера. Он
никогда не принимает из запроса команду, фильтр, путь или URL.

Структурные значения являются детерминированными данными выборки, а не результатом
семантического понимания видео. Они не определяют объекты, действия, подписи, речь
или намерения пользователя. Границы сцен и неподвижных интервалов формируют
сегменты; доля неподвижности, размытие, экспозиция, пространственная детализация
и временные изменения влияют только на распределение существующего бюджета в
1–16 кадров. Полностью неподвижный сегмент ограничивается одним кадром, тогда как
неподвижные не полностью сегменты конкурируют за оставшийся бюджет. Когда границ
больше, чем кадров, сохраняется равномерное покрытие временной шкалы, чтобы
быстрые смены сцен в начале не могли скрыть длинный завершающий сегмент. Границы
сцен, находящиеся в пределах 1-секундного разрешения анализа от границы
неподвижности, объединяются.

Отсутствующие фильтры, некорректные/пустые данные, ошибка детектора или превышение
времени ограниченного предварительного анализа приводят к безопасному возврату
к точной политике равномерных средних точек. Прерывание со стороны вызывающего
кода или достижение крайнего срока брокера не приводят к такому возврату: они
завершают выполняющийся подпроцесс, предотвращают последующее извлечение кадров,
а приватное временное дерево удаляется в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` создаёт детерминированные реальные
фикстуры FFmpeg для оценки сокращения числа вызовов создания подписей после
дедупликации, распределения бюджета при интенсивном движении, данных о
размытии/экспозиции/SI-TI, быстрых смен сцен с длинным завершающим фрагментом и
ложноположительных результатов при постепенном затухании. Скрипт фиксирует
фактическое время предварительного анализа и, если доступен `/usr/bin/time`,
процессорное время дочернего процесса и пиковое значение RSS. Его проверки
качества используют только структурные эталоны. Качество реальной модели
создания подписей остаётся `HOLD`, поскольку у этого стенда нет авторизованной
конечной точки или зафиксированного оценщика. Денежная экономия также остаётся
`HOLD`, если `--caption-cost-per-call-usd` не задаёт явную положительную оценку
стоимости одного вызова; скрипт никогда не выдумывает ни один из этих результатов.

Размер каждого кадра ограничен 4 MiB, совокупный размер всех необработанных
кадров — 23 MiB, а размер сериализованного ответа брокера — 32 MiB. Приватный
временный каталог удаляется в `finally`. OmniRoute не включает FFmpeg в комплект
поставки и не принимает пользовательский путь к исполняемому файлу. Перед
созданием подписей мост применяет консервативную визуальную дедупликацию: каждый
JPEG уменьшается до буфера оттенков серого размером 16×16 и сравнивается только
с последним сохранённым кадром. Если запрошенный бюджет подписей превышает один
кадр, извлечение предоставляет ограниченный пул кандидатов размером не более
удвоенного бюджета и никогда не более 16 кадров. Запрошенное ограничение
применяется только после дедупликации; при окончательном прореживании сохраняются
первый и последний выбранные кандидаты, если бюджет составляет не менее двух
кадров. Версионированная политика
`grayscale-16x16-mean-cells-v2` использует большее из двух значений: средней
дельты яркости и доли ячеек миниатюры, нормализованная дельта которых составляет
не менее 0.05. Порог дубликата задан константой 0.04, выбранной ради
предсказуемости, а не предоставленной как параметр времени выполнения. Этот
вторичный высококонтрастный сигнал сохраняет небольшие движения и изменения
видимого текста, которые может скрыть сравнение только по среднему значению.
Ошибки компаратора или декодера обрабатываются с сохранением покрытия. Метаданные
вывода отдельно указывают извлечённых кандидатов, успешно использованные кадры
и отброшенные визуальные дубликаты.

Явно помеченная часть видео может запрашивать контактный лист с временными
метками. Мост создаёт JPEG-сетку не более чем из 4 столбцов и 16 кадров. В
каждую 512-пиксельную ячейку временная метка исходного кадра впечатывается на
высококонтрастной нижней полосе, а те же временные метки сохраняются в текстовых
метаданных для последующего сопоставления и аудита. Размер полного JPEG остаётся
ограниченным 32 MiB. Если `sharp` не удаётся декодировать или скомпоновать сетку,
мост возвращается к отдельным JPEG-кадрам; прерывание со стороны клиента
по-прежнему распространяется на операцию создания листа.

Данные для продвижения намеренно отделены от синтетического микротеста
компоновки. `scripts/perf/video-bridge-contact-sheet-eval.ts` определяет
A/B-стенд с версионированной схемой для реальных моделей компьютерного зрения,
совместимых с OpenAI. Он измеряет сообщаемое поставщиком число токенов,
сквозную фактическую задержку (включая компоновку листа), количество вызовов
модели и сохранение фактов, определённых манифестом. Необработанные ответы модели
не записываются в отчёт; сохраняются только дайджесты SHA-256 и идентификаторы
совпавших фактов. Стенд не выполняет сетевые или платные вызовы модели, если не
передан `--execute-real` и не настроены `--model`, `OMNIROUTE_BASE_URL` и
`OMNIROUTE_API_KEY`. Без такого явно запрошенного реального запуска его
машиночитаемый вердикт остаётся `HOLD`; одних синтетических измерений размера
данных/количества вызовов недостаточно для продвижения.

Вызывающий код может прикрепить необязательный массив `transcript.cues` к
поддерживаемой части видео, если у него уже есть синхронизированный текст. Каждая
реплика должна содержать `text`, конечный интервал `start`/`end` в пределах
определённой длительности и `source` из списка разрешённых значений (`client`,
`embedded` или `audio-bridge`); значение `confidence` по умолчанию равно `1` и
должно оставаться в диапазоне от `0` до `1`. Полностью совпадающие реплики
объединяются. OmniRoute никогда не запускает транскрибирование на основании этих
метаданных: проверенные реплики копируются в описанный результат вместе с
источником, уверенностью и интервалом и отображаются как недоверенные наблюдения
рядом с подписями кадров. Некорректный текст, текст вне допустимого диапазона или
текст без сведений о происхождении отклоняется, а не смешивается с потоком
подписей. В настоящее время поле `source` объявляется вызывающей стороной, а не
проверяется сервером: OmniRoute обеспечивает, чтобы значение было одной из трёх
разрешённых строк, но пока криптографически не подтверждает, что метка
`embedded` или `audio-bridge` действительно получена в результате извлечения,
контролируемого сервером. Считайте `source` недоверенной подсказкой до появления
такой проверки; не основывайте на нём решения об авторизации.

Продвинутый вызывающий код может предоставить уже авторизованную дорожку `audioTranscript`
для того же видео. Механизм объединения запускает анализ визуальных и аудиоданных с единым
крайним сроком и сигналом прерывания, упорядочивает их на общей временной шкале, сворачивает
точные дубликаты и возвращает частичный результат, если успешно обработана только одна
сторона. Недопустимый `audioTranscript` приводит к такому частичному результату — визуальное
описание сохраняется, а аудиоветвь записывает санитизированный код ошибки —
вместо сбоя обработки всего видео. Доступность каждой ветви, флаг частичного результата
и санитизированные коды ошибок сохраняются в описанном результате, в метаданных
защитных механизмов (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), в метаданных кеша результатов и в счетчиках
объединения моста. Путь Video Bridge по умолчанию не запускает преобразование речи в текст
и не загружает вторую копию медиафайла; без явно указанной дорожки он продолжает
обрабатывать только видео.

**Хранение расшифровок (#12150 P1).** Это применяется автоматически всякий раз, когда
Video Bridge (который сам требует явного включения) отображает метку расшифровки — отдельного
флага хранения нет. Когда запрос отображает любую метку расшифровки (объявленную вызывающим кодом
`transcript` или объединенную `audioTranscript`), защитный механизм помечает его как
`videoBridgeObserved` и создает отредактированную теневую копию описания видео —
идентичное представление, в котором произвольный текст каждой метки заменен на
`[redacted-video-transcript]`; оно создается путем подстановки структурированного поля метки
до сборки строки (а не путем разбора плоского текста, поэтому никакое содержимое
метки — вредоносное или обычное, включая содержимое с символом `]`, например
`[inaudible]`/`[music]`, — сохраниться не может). В сохраняемом теле запроса журнала вызовов
каждая текстовая часть, полученная из видео, заменяется этой отредактированной теневой копией,
сопоставленной по равенству содержимого; якорь `fullText` повторно считывается из завершенной
полезной нагрузки защитного механизма перед вызовом, поэтому сопоставление по-прежнему успешно
выполняется после того, как последующие цепочечные защитные механизмы (маскировщики PII и
учетных данных с приоритетами 10/95) изменяют текст описания на месте, а внедрение системного
промпта, передачи контекста и памяти изменяет структуру массива сообщений. Тело, отправляемое
модели, остается неизменным. Наблюдаемый запрос также не записывает ничего в долговременную
Memory (извлечение как из запроса, так и из ответа пропускается), поэтому собственный ответ
модели не может скопировать текст расшифровки в Memory.

**Необработанные поля видео (#12430).** Когда мост включен, а наличие встроенной поддержки видео неизвестно или она отсутствует, определенные поля `transcript`/`audioTranscript` также активируют `videoBridgeObserved`, даже после сбоя формирования описания или достижения ограничения `maxVideos`. Значения `null` и пустые строки учитываются; отсутствующие поля и метаданные, не относящиеся к видео, — нет. В сохраняемых копиях эти поля редактируются либо запрос исключается, а кеши/Memory обходятся. Полезная нагрузка провайдера остается неизменной.

Дополнительные сохраняемые копии используют тот же сигнал наблюдаемого запроса. Необработанный
снимок клиентского запроса до применения защитных механизмов, ожидающий обработки запрос в памяти
и журнал запроса, отклоненного на раннем этапе, структурно заменяют поля расшифровки в видеочастях;
строковые промпты, создаваемые этапами конвейера и при передаче контекста, редактируются
в точке сохранения тела запроса. Сохраняемый маркер `video_content_removed`
заставляет продолжение по `previous_response_id` завершаться безопасным отказом вместо восстановления
текста, который был намеренно удален. Если наблюдаемый запрос теряет свою
теневую копию редактирования для отдельной части до журналирования или хотя бы одна из нескольких
теневых копий видео не сопоставляется после последующих изменений запроса, сохраняемое тело запроса
полностью исключается вместо сохранения частично отредактированной расшифровки.

Для наблюдаемого запроса ответ модели может цитировать любую часть
расшифровки без структурированной границы метки. Поэтому его сохраняемое в журнале вызовов
поле `responseBody` заменяется маркером исключения; подробный
артефакт конвейера (который может включать тела обмена с вышестоящим сервисом и клиентом, а также фрагменты потока)
не сохраняется. Семантический кеш, кеш идемпотентности и кеш воспроизведения рассуждений
не выполняют чтение и запись для этого запроса. Запрос к провайдеру и видимый клиенту
ответ остаются неизменными. Ранние байты keepalive удаляются из временного
буфера, когда подробный артефакт исключается. Предупреждение Kiro о некорректном EventStream
сообщает только число байтов полезной нагрузки и никогда не включает ее содержимое или необработанную
ошибку JSON-парсера.
Это не означает, что была проведена проверка всех не связанных с этим диагностических сообщений
провайдеров и плагинов; более широкий аудит точек сохранения отслеживается в #11658.

Внутренний жизненный цикл `/api/modality-bridge/video/drilldown` представляет собой отдельную,
аутентифицируемую по loopback/token кеширующую инфраструктуру. Для каждой операции также требуется
канонический непрозрачный идентификатор субъекта. Прежде чем рабочему вызывающему коду будет разрешен доступ, он должен
получать этот идентификатор из аутентифицированного арендатора и никогда не пересылать
значение, выбранное клиентом. Ключи кеша связывают этот субъект с каноническими идентификаторами
сеанса и ссылки на видео, сохраняют только их ключи, производные от SHA-256, и ограничивают
как чтение, так и удаление тем же субъектом. Кеш хранит не более 16 производных JPEG-кадров
на запись, удаляет их через десять минут и поддерживает ограниченное чтение
по `start`/`end` либо явное удаление сеанса.

Для каждого субъекта действует ограничение в 16 записей и 64 MiB канонических данных JPEG. Эти
ограничения не зависят от глобального предела в 64 записи/256 MiB: при исчерпании квоты
субъекта сначала вытесняются только записи этого субъекта, использовавшиеся давнее всего,
и лишь затем рассматривается глобальное вытеснение по LRU. Просроченные записи удаляются
из учета как для субъекта, так и глобально при активности кеша, а при отмене и ошибке валидации
частичная замена не фиксируется.

Кэш отклоняет неканонический Base64, избыточное дополнение, медиаданные не в формате JPEG, повреждённые или
усечённые JPEG-файлы, а также JPEG-файлы, при полном декодировании которых с помощью `sharp`
в заданных пределах возникает предупреждение. Каждое принятое изображение повторно кодируется как канонический JPEG; ширина и высота
определяются по декодированным байтам, а не по полям вызывающей стороны, а любые завершающие
полиглотные байты отбрасываются, а не сохраняются. В обе квоты засчитывается только ограниченный по размеру канонический сжатый буфер.
Ограничение для передачи JSON учитывает накладные расходы Base64 для предельного объёма
декодированных входных данных в 32 MiB. Для каждого
сохранённого производного объекта записываются его проверенные формат и разрешение JPEG, политика сэмплирования,
версия формирования производного объекта, время создания, вычисленный сервером хеш содержимого и хешированная ссылка на родительский объект,
а также хеш содержимого родительского объекта от доверенной вызывающей стороны. Отмена проверяется
между асинхронными этапами декодирования и хеширования до атомарной фиксации в кэше.

Этот этап пока не подключает промышленный источник данных к маршруту и не
обеспечивает выбор вариантов с разным разрешением. Поэтому прозрачный путь запроса Video Bridge
не выполняет дополнительной работы, а формирование привязанных к арендатору субъектов
и полный жизненный цикл FU-08 для нескольких разрешений остаются явно обозначенной последующей работой,
а не документированным завершённым поведением.

Кадры последовательно снабжаются описаниями с помощью настроенной модели Video. Пустое
переопределение Video наследует настройку Vision; если обе настройки пусты, автоматический маршрутизатор
Vision выбирает подходящую модель с поддержкой зрения. Успешно созданные описания
заменяют исходную часть текстом со стабильным префиксом `[Video description:`, который также
помечает текст как недоверенное наблюдение, полученное из медиаданных, и предписывает последующим
моделям не следовать инструкциям, обнаруженным в медиаданных. Ключи кэша описаний кадров
включают байты JPEG, запрос, временную метку и фактически выбранную модель; кэшируются только успешно созданные
описания. Записи кэша сохраняют фактическую модель-производитель, успешно обработавшую запрос,
включая резервную модель; если разные кадры были обработаны разными моделями,
мост сообщает `mixed`. При попадании в кэш повторно используется идентификатор этого производителя,
а не назначается метка запрошенного плана маршрутизации. Кэш результатов для всего видео
формирует ключ из каждого входного параметра, влияющего на результат: запроса, фактически выбранной
модели, политики сэмплирования, количества кадров, режима семантического анализа, отпечатка SHA-256
нормализованной подсказки фокуса, окна фокуса, `transcript`,
`audioTranscript` и флага контактного листа. Поэтому изменение любого из этих
параметров приводит к промаху кэша, а устаревший результат никогда не используется повторно. Версия политики
визуальной дедупликации, пороговое значение и ограниченное число кадров-кандидатов также явно включаются в
ключ и метаданные кэша результатов; таким образом, при изменении политики устаревшее
описание всего видео не может быть использовано повторно. Метаданные кэша результатов v4 сохраняют режим и
отпечаток, но никогда не сохраняют исходную пользовательскую задачу. Метаданные защитных механизмов сообщают как
запрошенный, так и фактический режим анализа; запрошенный режим `focused` без
пригодного пользовательского текста отображается как фактически применённый режим `full`.

Защитный механизм извлекает все поддерживаемые части видео, но описывает не более
`modalityBridgeVideoMaxVideos`. Для целевого объекта, у которого подтверждено
`supportsVideo === false`, видео, обработка которых завершилась ошибкой или которые превышают лимит, заменяются явными безопасными
текстовыми маркерами, чтобы необработанные видеоданные не сохранились. Если поддержка возможности неизвестна, эти части
остаются без изменений. Целевые объекты с `supportsVideo === true` обходят мост.
Сигнал отмены клиентского запроса распространяется на скачивание, очередь брокера,
подпроцессы и вызовы создания описаний; отмена останавливает обработку между видео и никогда не приводит к
небезопасному пропуску необработанных медиаданных.

Настройки среды выполнения хранятся в БД и проверяются с помощью Zod:

| Ключ                                | Значение по умолчанию | Диапазон / поведение                                                                                                                    |
| ----------------------------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`               | Необязательная возможность среды выполнения, включаемая явно                                                                            |
| `modalityBridgeVideoAnalysisMode`   | `"full"`              | `full` сохраняет универсальные описания; `focused` использует ограниченный недоверенный контекст последнего пользовательского сообщения |
| `modalityBridgeVideoModel`          | `""`                  | Наследует модель Vision Bridge                                                                                                          |
| `modalityBridgeVideoFrameCount`     | `8`                   | 1–16                                                                                                                                    |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`           | `uniform`, `scene_aware` или пропорциональный `segment_aware`; при сбое детектора используется `uniform`                                |
| `modalityBridgeVideoMaxVideos`      | `1`                   | 1–4                                                                                                                                     |
| `modalityBridgeVideoTimeout`        | `120000`              | 1000–120000 ms                                                                                                                          |

Сохранённые ранее значения тайм-аута Video свыше 120 секунд ограничиваются
крайним сроком брокера; новые значения настроек, превышающие этот предел, отклоняются.
`GET /api/modality-bridge/video/runtime` до аутентификации или проверки среды выполнения требует
доверенного подтверждённого локального loopback-подключения, а затем требует
управленческой аутентификации. Эндпоинт возвращает только `available`, очищенные версии FFmpeg/ffprobe и фиксированную
причину, если среда выполнения недоступна. Внутренний эндпоинт извлечения не является
публичным API загрузки: при насыщении очереди возвращаются `503` и `Retry-After`, при отключении
вызывающей стороны — `499`, а при наступлении фиксированного крайнего срока брокера — `504`. Преобразованные ответы добавляют
`video->text;model=<visionModel>;parts=<videos>` в центральный заголовок
`x-omniroute-modality-bridge`, не удаляя сегменты Vision или Audio.

### Маскирование PII (`piiMasker.ts`)

Выполняется на **обоих** этапах.

- **`preCall`** клонирует полезную нагрузку, обходит `system`, `messages`, `input` и
  `prompt` (включая элементы в виде обычных строк) и применяет `processPII()` (из
  `@/shared/utils/inputSanitizer`) к строковым полям `content`/`text`. Когда
  `PII_REDACTION_ENABLED=true`, обнаруженные персональные данные редактируются в исходящей
  полезной нагрузке. Это не зависит от `INPUT_SANITIZER_MODE` (который управляет
  только политикой защиты от инъекций в промпт). Когда редактирование отключено, вызов записывает
  количество обнаружений, не изменяя содержимое.
- **`postCall`** выполняет глубокое клонирование ответа, запускает `sanitizePIIResponse()`, а также
  маскировщик структуры Responses API (`maskResponsesOutput` — охватывает
  `output_text` и `output[].content[].text`). Если выполнено какое-либо редактирование,
  изменённый ответ заменяет исходный.

Защитный механизм никогда не блокирует; он только добавляет аннотации (`meta.detections`,
`meta.redacted`) или изменяет содержимое.

### Инъекция в промпт (`promptInjection.ts`)

Обнаруживает вредоносные структуры в предоставленном пользователем содержимом и применяет
настроенную политику. Поведение определяется переменными окружения и параметрами
конструктора:

| Настройка        | Переменная окружения                                                                                        | По умолчанию | Эффект                                                                                                                                                                                                                       |
| ---------------- | ----------------------------------------------------------------------------------------------------------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Включено         | `INPUT_SANITIZER_ENABLED`                                                                                   | `true`       | При значении `false` защитный механизм немедленно завершает работу.                                                                                                                                                          |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                             | `warn`       | Политика защиты от инъекций: `block`, `warn` или `log`. (`redact` поддерживается для обратной совместимости, но **не** удаляет текст инъекции; изменение персональных данных в запросе управляется `PII_REDACTION_ENABLED`.) |
| Порог блокировки | Параметр `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдоним `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | Минимальный уровень серьёзности, необходимый для блокировки. При настройках по умолчанию средний уровень используется только для наблюдения.                                                                                 |

**Приоритет режима** (`getMode`): `options.mode`, переданный вызывающей стороной →
**переопределение флагом функции из БД** для `INJECTION_GUARD_MODE` (Панель управления → Настройки →
Флаги функций) → переменная окружения `INJECTION_GUARD_MODE` → переменная окружения `INPUT_SANITIZER_MODE` →
`warn`. Таким образом, переопределение через панель управления имеет приоритет над переменными окружения, поэтому
интерфейс флагов функций управляет работающим защитным механизмом в реальном времени (без перезапуска). Чтение из БД является отказоустойчивым:
если при нём возникает ошибка, защитный механизм возвращается к поведению на основе переменных окружения, а когда
переопределение не задано, поведение идентично разрешению только по переменным окружения.

Источники обнаружения:

1. `sanitizeRequest()` из `@/shared/utils/inputSanitizer` (общий набор детекторов,
   используемый в других частях конвейера).
2. Встроенные `DEFAULT_GUARD_PATTERNS` (в настоящее время `system_override_inline` и
   `markdown_system_block`, оба с уровнем серьёзности `high`).
3. Необязательные `customPatterns`, передаваемые через параметры конструктора (строки, регулярные выражения
   или записи `{ name, pattern, severity }`).

Когда `mode === "block"` **и** хотя бы одно обнаружение достигает порогового уровня
серьёзности, `preCall` возвращает `{ block: true, message: "Запрос отклонён:
обнаружено подозрительное содержимое" }`. В режимах `warn`/`log` защитный механизм записывает событие в журнал, но
разрешает вызов. Общая вспомогательная функция `evaluatePromptInjection()` также экспортируется
для вызывающих сторон, которым необходимо проверять промпты без использования реестра.

**Ограничение сканирования (v3.8.20):** детектор проверяет только **первые 16 КБ**
объединённого текста промпта — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байта) в
`src/shared/utils/inputSanitizer.ts`. И `detectInjection()`, и
`evaluatePromptInjection()` применяют `slice(0, MAX_INJECTION_SCAN_BYTES)` перед запуском
цикла сопоставления с шаблонами. Директивы инъекций располагаются ближе к началу входных данных, поэтому это
ограничивает нагрузку регулярных выражений на процессор и сборщик мусора для полезных нагрузок размером в сотни КБ, не ослабляя обнаружение (см.
#3932, #4041).

### Маскировщик учётных данных (`credentialMasker.ts`)

Запускается на **обоих** этапах, последним в цепочке по умолчанию (приоритет `95`). Редактирует
известные шаблоны API-ключей и секретных токенов в исходящей полезной нагрузке (содержимом
сообщений, аргументах вызовов инструментов, результатах инструментов) **и** в ответе провайдера, чтобы
учётные данные, вставленные в промпт (или возвращённые в результате работы инструмента), не утекли
вышестоящему провайдеру или обратно клиенту.

- **Только с явным включением**, по аналогии с редактированием PII (рядом с жёстким правилом № 20):
  отключено, если только `settings.credentialRedactionEnabled === true` **или**
  `CREDENTIAL_REDACTION_ENABLED=true`. Когда функция отключена, защитный механизм ничего не делает —
  он никогда не блокирует и не изменяет данные.
- `redactCredentials()` обходит всё дерево полезной нагрузки/ответа (`walkValue()`,
  с защитой от загрязнения прототипа и циклических ссылок через `WeakSet`) и заменяет совпадения
  заполнителем `[REDACTED:<type>]`, клонируя только те ветви, которые действительно
  изменились.
- `CREDENTIAL_PATTERNS` охватывает ключи поставщиков LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токены VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платёжные ключи (Stripe, Square), облачные
  ключи (ключ доступа AWS, Twilio, SendGrid, Mailgun), закрытые ключи / JWT,
  строки подключения, содержащие учётные данные (`mongodb://user:pass@...` и т. д.), а также
  универсальный шаблон значений заголовков `Authorization`/`x-api-key`/`api-key`/`apikey`.
  Ключи, имеющие форму заголовков (`authorization`, `x-api-key`, `api-key`,
  `apikey`), редактируются структурно (только значение, при этом префикс схемы, например
  `Bearer `/`Basic `, сохраняется), а не с помощью универсального текстового регулярного выражения.
- Защитный механизм никогда не блокирует данные; он только изменяет их (`modifiedPayload` /
  `modifiedResponse`) и добавляет метаданные (`meta.credentialsRedacted`, `meta.count`).

Защита от регрессий: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовый контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // значение true прерывает цепочку
  message?: string; // отображается при блокировке
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // возвращается методом preCall для изменения запроса
  modifiedResponse?: TValue; // возвращается методом postCall для изменения ответа
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Защитный механизм сообщает об отсутствии изменений, возвращая `void`, `{}` или
`{ block: false }`. Возврат `modifiedPayload`/`modifiedResponse` заменяет
значение, передаваемое по цепочке последующим защитным механизмам.
`signal?: AbortSignal` передаёт жизненный цикл вызывающей стороны защитным механизмам. Прерывание запроса является намеренным исключением из принципа fail-open: медиамосты прекращают работу и выполняют очистку, не восстанавливая необработанные медиаданные для целевой системы, которая заведомо их не поддерживает.

## Реестр (`registry.ts`)

Синглтон `guardrailRegistry` предоставляет:

- `register(guardrail)` — добавляет (или заменяет по нормализованному имени) защитный механизм и
  повторно сортирует по возрастанию `priority`.
- `clear()` / `list()` — вспомогательные функции администрирования.
- `runPreCallHooks(payload, context)` — итерирует активные защитные механизмы, пропускает
  полезную нагрузку через `modifiedPayload` и останавливается на первом `block: true`.
- `runPostCallHooks(response, context)` — тот же поток на стороне ответа.
- `resetGuardrailsForTests({ registerDefaults })` — очищает состояние и опционально
  повторно регистрирует значения по умолчанию для чистой изоляции тестов.

Оба запускатора возвращают `{ blocked, payload|response, results, guardrail?, message? }`,
где `results` — это массив записей `GuardrailExecutionResult`, которые включают
поля `blocked`, `skipped`, `modified`, `error` и `meta` для каждого защитного механизма,
полезные для трассировки.

### Отключение защитных механизмов для каждого запроса

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` агрегирует
дедуплицированный список имен защитных механизмов, которые должны быть пропущены для текущего
запроса. Источники (все опциональные, все объединенные):

- `apiKeyInfo.disabledGuardrails`
- Тело запроса `disabledGuardrails` (верхний уровень)
- Тело запроса `metadata.disabledGuardrails`
- Заголовок `x-omniroute-disabled-guardrails` (или устаревший
  `x-disabled-guardrails`)

Значения могут быть массивами строк или строкой, разделенной запятыми; имена
нормализуются в нижний регистр kebab-case (`pii_masker` → `pii-masker`). Результат
передается через `context.disabledGuardrails` в реестр, который пропускает
соответствующие защитные механизмы (`skipped: true` в `results`).

## Порядок выполнения

Для каждого запроса, проходящего через `src/sse/handlers/chat.ts` и
`open-sse/handlers/chatCore.ts`:

1.  `resolveDisabledGuardrails(...)` формирует список исключений из ключа API, тела запроса
    и заголовков.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` запускает защитные механизмы в порядке
    возрастания приоритета:
    - Отключенные защитные механизмы записываются как `skipped`.
    - Метод `preCall` каждого защитного механизма может переписывать полезную нагрузку через `modifiedPayload`.
    - Первый `block: true` прерывает цепочку, и обработчик возвращает
      ответ об отклонении защитным механизмом.
3.  (Потенциально переписанная) полезная нагрузка поступает в комбинированную маршрутизацию и
    диспетчеризацию вышестоящему сервису.
4.  После сборки ответа `guardrailRegistry.runPostCallHooks(...)`
    запускает ту же цепочку для ответа. `block: true` здесь отбрасывает
    ответ вышестоящего сервиса.

Защитные механизмы, которые выбрасывают исключения, записываются с `error: <message>` и
логируются через `logger.warn`, но цепочка продолжается — по замыслу, система
открыта к сбоям.

## Конфигурация

Переменные окружения, считываемые встроенными защитными механизмами:

| Переменная                            | Используется                  | Эффект                                                                                                                 |
| :------------------------------------ | :---------------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`            | Установите `false`, чтобы полностью отключить обнаружение.                                                             |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`            | Политика инъекций: `warn`, `block` или `log`. Устаревшее значение `redact` не переписывает текст инъекции.             |
| `INJECTION_GUARD_MODE`                | `prompt-injection`            | Режим для защиты от инъекций; также флаг функции БД, который **переопределяет** переменные окружения (БД > ОКРУЖЕНИЕ). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`            | Минимальная серьезность, при которой `MODE=block` отклоняет: `high` (по умолчанию), `medium` или `low`.                |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`            | Устаревший псевдоним для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                            |
| `PII_REDACTION_ENABLED`               | `pii-masker`                  | Если `true`, PII запроса скрывается (независимо от режима инъекции).                                                   |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ниже по потоку) | Управляет поведением маскировщика на стороне ответа.                                                                   |

Защитные механизмы Modality Bridge считывают конфигурацию времени выполнения из хранилища настроек,
поддерживаемого БД (`getSettings()`), а не из переменных окружения. Основные ключи Vision:
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` и
`modalityBridgeCacheMaxEntries`. Устаревшие ключи
`visionBridge*` принимаются только в качестве документированного одноциклового
резервного чтения; записи с панели управления используют основные ключи. Значения по умолчанию и
резервный резолвер находятся в `src/shared/constants/modalityBridgeDefaults.ts`,
при этом устаревшие константы сохранены в `src/shared/constants/visionBridgeDefaults.ts`.

Аудио использует `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` и `modalityBridgeAudioMaxClips`, а также общие
настройки `modalityBridgeCache*`. У Аудио нет резервного варианта для устаревших ключей,
поскольку эти ключи были введены со схемой Modality Bridge.

Видео использует `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` и
`modalityBridgeVideoTimeout`, а также общие настройки `modalityBridgeCache*`.
По умолчанию оно отключено, поскольку FFmpeg/ffprobe являются необязательными
операционными зависимостями, а создание подписей к кадрам увеличивает задержку и
стоимость модели.

## Пользовательские Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Шаги:

1.  Создайте `src/lib/guardrails/myGuardrail.ts`, расширяющий `BaseGuardrail`.
2.  Реализуйте `preCall` и/или `postCall`.
3.  Либо зарегистрируйте во время импорта (push из `registerDefaultGuardrails`), либо
    вызовите `guardrailRegistry.register(...)` во время выполнения — реестр заменяет
    любой предыдущий guardrail с тем же нормализованным именем.
4.  Добавьте тесты в `tests/unit/` (существующие примеры:
    `tests/unit/guardrails-registry.test.ts`,
    `tests/unit/prompt-injection-guard.test.ts`,
    `tests/unit/guardrails/visionBridge.test.ts`).

## Тестирование

Используйте `resetGuardrailsForTests()` между тестами, чтобы начать с известного состояния.
Передайте `{ registerDefaults: false }`, чтобы начать с пустого реестра и
зарегистрировать только тестируемые guardrails. Vision Bridge принимает внедрение зависимостей
(`deps.getSettings`, `deps.callVisionModel`); Audio Bridge предоставляет эквивалентные точки расширения
для настроек, возможностей, выбора модели STT, проверки учетных данных и транскрипции.
Таким образом, тесты могут проверять оба потока без доступа к БД или сети.

## Покрытие маршрутов защитой от инъекций и red-team (Фаза 8 · Блок D)

Защита от инъекций (`createInjectionGuard` / `withInjectionGuard`) охватывает все маршруты,
которые принимают пользовательские промпты. Она учитывает `INJECTION_GUARD_MODE` (по умолчанию `warn` = только логирование;
`block` = возвращает HTTP 400 `SECURITY_001`).

| Тип                  | Маршруты                                                                                                                                             | Режим по умолчанию |
| :------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------- |
| Текст (существующий) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn               |
| Генеративный         | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn               |
| Данные               | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn               |

Извлечение текста (`extractMessageContents`) охватывает `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Red-team (ночной, `nightly-llm-security.yml`):** promptfoo проверяет, что каждый маршрут блокирует
корпус OWASP-LLM в режиме `INJECTION_GUARD_MODE=block`; garak запускает зонды (пропускает без секрета).
`moderations` включен для согласованности — операторы в режиме блокировки могут исключить его через
`resolveDisabledGuardrails`.

Ночной рабочий процесс (`.github/workflows/nightly-llm-security.yml`, cron + ручной
запуск) состоит из двух задач:

- **`promptfoo-guard` (блокирующий)** — запускает `promptfoo eval -c promptfooconfig.yaml`
  с `INJECTION_GUARD_MODE=block`. Каждый adversarial-кейс (например, "игнорировать все
  предыдущие инструкции...", джейлбрейки в стиле DAN) подтверждает, что ответ содержит
  `error.code === "SECURITY_001"`, то есть защита фактически отклонила запрос.
- **`garak` (консультативный)** — запускает garak `--probes promptinject,dan,leakreplay`
  против локального экземпляра OmniRoute (`http://localhost:20128/v1`). Ограничен
  секретом провайдера (`PROMPTFOO_PROVIDER_KEY`); корректно пропускается и имеет суффикс
  `|| true`, поэтому он сообщает о результатах, не приводя к сбою CI.

Покрытие вспомогательной функции защиты (`createInjectionGuard` / `withInjectionGuard`)
охватывает каждый маршрут `/v1`, содержащий промпты; текст промпта извлекается из
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` с помощью
`extractMessageContents()` в `src/shared/utils/inputSanitizer.ts`.
