## Обзор

Все маршруты API управления OmniRoute относятся к одному из трёх уровней
защиты. Классификация статична, определена в `src/server/authz/routeGuard.ts`
и проверяется до выполнения любой другой ветви аутентификации.

## Уровни

### Уровень 1 — LOCAL_ONLY

**Обеспечивается посредством:** `isLocalOnlyPath(path)` → проверка loopback-хоста  
**Обход:** По умолчанию отсутствует. Узкое исключение для путей из
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, когда запрос содержит действительный
API-ключ с областью действия `manage` (см. [Исключение для области действия manage](#manage-scope-carve-out)).

Эти маршруты запускают дочерние процессы или выполняют код среды исполнения. Их
доступность для трафика не с loopback-интерфейса позволила бы злоумышленнику,
получившему действительный JWT (например, через туннель Cloudflared/Ngrok),
инициировать запуск процессов — известный класс CVE
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Что представляет собой GHSA-fhh6-4qxv-rpqj (класс атаки):** сервер управления/агент
предоставляет конечную точку, которая запускает подпроцесс (`npm install`, `node`, браузер,
прокси, `git`, `tar`, …). Если эта конечная точка доступна извне хоста — поскольку
оператор разместил OmniRoute за туннелем nginx/Cloudflare/Tailscale, а JWT
утёк или аутентификация была настроена неверно, — злоумышленник превращает «вызов API» в
«выполнение команды на хосте» (удалённое выполнение кода). OmniRoute предотвращает это,
безусловно выполняя **проверку loopback-хоста до любой проверки аутентификации** для каждого
маршрута, способного запускать процессы: утёкший токен при доступе через туннель всё равно
не позволит инициировать запуск процесса.

**Полный набор LOCAL_ONLY.** Авторитетным источником являются
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` в
`src/server/authz/routeGuard.ts`; приведённая ниже таблица отражает текущее состояние.
Проверка `check-route-guard-membership` перечисляет каждый файл `route.ts` в
префиксах, способных запускать процессы, и завершает CI с ошибкой, если какой-либо из них
не классифицирован как доступный только локально.

#### Исключение для области действия управления

К подмножеству путей LOCAL_ONLY ТАКЖЕ МОЖНО обращаться не через loopback-интерфейс в том и
только в том случае, если запрос содержит `Authorization: Bearer <api-key>`, в
метаданных которого указана область действия `manage` (или `admin`). Это исключение
явно включается отдельно для каждого пути через `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, поэтому
для любого нового пути LOCAL_ONLY по умолчанию сохраняется строгое требование loopback-интерфейса. Неаутентифицированные
запросы и запросы с ключами без области действия управления по-прежнему отклоняются с
`403 LOCAL_ONLY`.

В настоящее время единственным префиксом, допускающим обход, является `/api/mcp/`. `/api/cli-tools/runtime/` и
`/api/services/` намеренно исключены, поскольку они могут запускать произвольные
подпроцессы (`npm install`, `node`), а именно от этого класса CVE
предназначен защищать уровень LOCAL_ONLY.

**#7895 — узкая область действия `mcp:connect`:** исключение для `/api/mcp/` ТАКЖЕ допускает
Bearer-ключ с узкой областью действия `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), проверяемой посредством
`hasMcpConnectOrManageScope()` в `src/server/authz/policies/management.ts`.
Она распространяется ТОЛЬКО на `/api/mcp/` — `mcp:connect` не предоставляет никаких прав для любых других
маршрутов управления (включая все остальные префиксы обхода LOCAL_ONLY, если они
когда-либо будут добавлены) и намеренно исключена из
`MANAGEMENT_API_KEY_SCOPES`. Ключ с областью действия `manage`/`admin` по-прежнему использует
это исключение точно так же, как и прежде; `mcp:connect` — это альтернатива с более низким уровнем привилегий
для удалённых клиентов, работающих только с MCP, которым не нужен широкий доступ к управлению.

| Запрос                                                                | Путь                       | Результат                     |
| --------------------------------------------------------------------- | -------------------------- | ----------------------------- |
| Не через loopback-интерфейс, без Bearer                               | `/api/mcp/*`               | 403 LOCAL_ONLY                |
| Не через loopback-интерфейс, Bearer с областью действия `manage`      | `/api/mcp/*`               | Разрешить                     |
| Не через loopback-интерфейс, Bearer с областью действия `mcp:connect` | `/api/mcp/*`               | Разрешить                     |
| Не через loopback-интерфейс, Bearer без `manage`/`mcp:connect`        | `/api/mcp/*`               | 403 LOCAL_ONLY                |
| Не через loopback-интерфейс, Bearer с областью действия `mcp:connect` | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                |
| Не через loopback-интерфейс, Bearer с областью действия `manage`      | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                |
| Через loopback-интерфейс, любой Bearer или без него                   | любой LOCAL_ONLY           | Разрешить (проверка пройдена) |

#### Рекомендации для операторов и аудит

Если вы запускаете OmniRoute за обратным прокси-сервером или туннелем (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), проверка loopback-интерфейса по-прежнему защищает указанные выше
маршруты, способные запускать процессы: запрос, адрес клиента которого не относится к loopback-интерфейсу, отклоняется с
`403 LOCAL_ONLY` **до запуска аутентификации**, поэтому утечка JWT не позволит запустить процесс. При этом
у оператора остаются две обязанности:

- **Не «исправляйте» ошибку 403, подделывая IP-адрес клиента под loopback-адрес.** Установка
  `X-Forwarded-For: 127.0.0.1` или использование прокси, который переписывает исходный адрес на
  loopback-адрес, вновь открывает именно тот класс RCE-уязвимостей, который закрывает этот уровень. Предоставляйте доступ через прокси к
  панели управления/API — но никогда к маршрутам, способным запускать процессы.
- **Сохраняйте обход для области manage минимальным.** Обход разрешён только для `/api/mcp/` и
  только с API-ключом, имеющим область `manage`. Элементы `SPAWN_CAPABLE_PREFIXES` никогда нельзя
  добавлять в список обхода — схема zod отклоняет их, а
  `isLocalOnlyBypassableByManageScope` запрещает их во время выполнения (эшелонированная защита),
  что и подразумевает формулировка панели управления «нельзя разрешить обход». Загрузчик снимка состояния во время выполнения
  также удаляет такие элементы из сохранённой строки настроек, а
  устаревший импорт JSON (`/api/settings/import-json`) никогда не записывает ключи обхода.
  Каждый элемент `LOCAL_ONLY_API_PREFIXES` должен либо находиться в списке запрета, либо
  быть проверен на допустимость обхода (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Маршруты
  с динамическими сегментами и статическими путями, способные запускать процессы, в `/api/providers/` (например, `/login`,
  `/refresh-cursor`) охватываются основанными на регулярных выражениях сопутствующими наборами `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` в
  `src/shared/constants/spawnCapablePrefixes.ts`, а не плоским
  массивом `SPAWN_CAPABLE_PREFIXES` — иначе плоскому массиву пришлось бы охватывать
  весь префикс `/api/providers/`, чрезмерно расширяя охват дерева маршрутов,
  которое удалённые панели управления правомерно используют для CRUD-операций с провайдерами.

**Аудит доступа** — чтобы убедиться, что никакие запросы извне хоста не достигают этих маршрутов:

- Откройте **Инвентаризацию авторизации** на `/dashboard/settings/security`: там отображается
  актуальный список префиксов LOCAL_ONLY, префиксы, для которых разрешён обход, и определённый на этапе компиляции
  набор маршрутов, способных запускать процессы («нельзя разрешить обход»).
- Выполните поиск в журналах обратного прокси / доступа по указанным выше префиксам в сочетании с
  адресом клиента, не являющимся loopback-адресом. Любое такое обращение, вернувшее `200` вместо
  `403 LOCAL_ONLY`, означает, что прокси скрывает реальный IP-адрес клиента — исправьте конфигурацию прокси.
- Запись `403 LOCAL_ONLY` в журналах OmniRoute для одного из этих путей означает, что защита
  работает должным образом, а не ошибку, которую следует подавлять.

### Уровень 2 — ALWAYS_PROTECTED

**Обеспечивается:** `isAlwaysProtectedPath(path)` → обход `requireLogin=false` пропускается
**Обход:** отсутствует при `requireLogin=false`; JWT требуется всегда

Эти маршруты выполняют разрушительные или необратимые действия. Если разрешить их в установке
«без пароля», любой пользователь в той же локальной сети сможет стереть базу данных или завершить
серверный процесс.

| Путь                                      | Причина                                                                          |
| ----------------------------------------- | -------------------------------------------------------------------------------- |
| `/api/shutdown`                           | Завершает серверный процесс                                                      |
| `/api/settings/database`                  | Экспорт, импорт и очистка базы данных                                            |
| `/api/db-backups`                         | Доступ к полным архивам резервных копий базы данных                              |
| `/api/settings/export-json`               | Экспортирует полный набор настроек (включая секреты)                             |
| `/api/settings/import-json`               | Заменяет полный набор настроек                                                   |
| `/api/providers/health-autopilot/actions` | Выполняет корректирующие действия автопилота                                     |
| `/api/settings/obsidian`                  | Выпускает повторно используемые учётные данные WebDAV для любого корня хранилища |

**Ответ при нарушении:** `401 Authentication required`

`/api/settings/obsidian` охватывает свой дочерний маршрут `/webdav`: `POST` направляет файловый сервис WebDAV —
обслуживаемый пользовательским слоем Node перед Next.js, вне этого конвейера — на выбранный вызывающей стороной корневой каталог
и возвращает недавно выпущенные учётные данные Basic, `DELETE` выполняет их ротацию, а родительский `POST` сохраняет
токен REST API Obsidian. GHSA-62vw лишь скрыла раскрытие пароля через `GET`; выпуск
по-прежнему находился на уровне, допускающем доступ при сбое защиты (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` дополнительно
отклоняет хранилище, которое является каталогом данных, находится внутри него или содержит его.

### Первоначальная настройка при новой установке доступна только через loopback — согласно реальному узлу, а не `Host`

Если пароль управления не настроен (и отсутствует `INITIAL_PASSWORD`), `isAuthRequired()` в
`src/shared/utils/apiAuth.ts` оставляет анонимную первоначальную настройку доступной **только для loopback-узлов**.
Принадлежность к loopback определяется по доверенным сигналам узла в следующем порядке: реальный TCP-узел, помеченный токеном
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, то, что видит политика), собственный вердикт конвейера
`AUTHZ_HEADER_PEER_LOCALITY` (то, что видят обработчики маршрутов; считается доверенным, только пока
задана `OMNIROUTE_PEER_STAMP_TOKEN`), либо реальный узел сокета для прямых вызывающих сторон. `Host` /
`nextUrl.hostname` никогда не учитываются, а первоначальная запись пароля
(`POST /api/settings/require-login`) подчиняется тому же ограничению, а не открывается для любого
сетевого узла (GHSA-7pq4-8pvv-rx7r). `managementPolicy` явно передаёт ниже собственный вердикт
`peerContext`, поэтому заголовки ИСХОДНОГО запроса (до их удаления) никогда не влияют на это решение.

### Уровень 3 — MANAGEMENT (по умолчанию)

Все остальные маршруты управления. Аутентификация обязательна, если не настроено
`requireLogin=false`. Токены CLI могут использоваться для аутентификации на этих маршрутах (loopback + действительный HMAC).

## Порядок проверки

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → перейти к следующей проверке
     → не loopback, Bearer с областью manage
        И isLocalOnlyBypassableByManageScope     → разрешить (management_key)
     → иначе                                     → отклонить с 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → разрешить (system)
  3. hasValidCliToken(headers)?
     → разрешить (cli) [loopback + проверка HMAC через timingSafeEqual]
  4. isAlwaysProtectedPath(path) или requireLogin=true?
     → isDashboardSessionAuthenticated?
        → разрешить (dashboard_session)
     → Bearer с областью manage для пути, не допускающего обход?
        → разрешить (management_key)
     → отклонить с 401/403
  5. requireLogin=false?
     → разрешить (anonymous)
```

Ветвь с областью manage на шаге 1 — единственный аутентифицированный способ получить доступ к маршруту
LOCAL_ONLY; при сбое бэкенда аутентификации возвращается 503 (а не 403), поэтому
истёкшая БД не приводит незаметно к режиму «запретить».

## Добавление нового маршрута, способного запускать процессы

1. Добавьте префикс пути в `LOCAL_ONLY_API_PREFIXES` в
   `src/server/authz/routeGuard.ts`
2. Добавьте тест в `tests/unit/authz/routeGuard.test.ts`, проверяющий, что
   `isLocalOnlyPath()` возвращает true для нового префикса
3. **Никогда не пропускайте этот шаг** — см. строгое правило №15 в `CLAUDE.md`
4. Решите: должен ли этот маршрут ТАКЖЕ входить в `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Ответ по умолчанию — **нет**. Добавляйте его только тогда, когда маршрут безопасно предоставлять
   обладателю области manage (то есть он НЕ запускает произвольный код, управляемый пользователем).

## Добавление пути, допускающего обход с областью manage

1. Убедитесь, что маршрут не выполняет предоставленный пользователем код или команды. Если
   выполняет, остановитесь — это исключение здесь неприменимо.
2. Добавьте префикс в `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` в
   `src/server/authz/routeGuard.ts`
3. Добавьте покрытие в `tests/unit/authz/management-policy.test.ts` для всех четырёх
   вариантов запроса: без Bearer (403), Bearer с областью manage (разрешить), Bearer без области manage
   (403), а также отдельный регрессионный тест для префикса, подтверждающий, что `/api/cli-tools/runtime/*` остаётся
   доступным строго через loopback даже при наличии Bearer с областью manage.

## Документирование уровней безопасности в OpenAPI

При добавлении нового маршрута в `docs/openapi.yaml` примените соответствующее
пользовательское расширение, если маршрут классифицирован в `routeGuard.ts`:

| Классификация routeGuard.ts                  | Аннотация YAML             | Применяемое ограничение                                   |
| -------------------------------------------- | -------------------------- | --------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                    | `x-loopback-only: true`    | Безусловно блокируется для запросов не через loopback     |
| `ALWAYS_PROTECTED_API_PATHS`                 | `x-always-protected: true` | Аутентификация обязательна даже при `requireLogin=false`  |
| Внутренний маршрут администрирования/отладки | `x-internal: true`         | По умолчанию скрыт из /dashboard/api-endpoints            |
| Нет (публичный / стандартная аутентификация) | (аннотация не требуется)   | Стандартный доступ, управляемый параметром `requireLogin` |

### Проверка

Два скрипта обеспечивают согласованность аннотаций YAML с `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — завершается с ошибкой, если покрытие < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — завершается с ошибкой, если аннотации `x-loopback-only` или
  `x-always-protected` расходятся с константами времени компиляции

Оба скрипта запускаются в хуке перед коммитом и в CI.

### Правило ложноположительного срабатывания

Если маршрут аннотирован `x-always-protected` или `x-loopback-only`, но НЕ входит в
соответствующую константу `routeGuard.ts`, скрипт проверки покрытия завершается с ошибкой. Исправление всегда заключается в том, чтобы привести
YAML в соответствие с тем, что фактически контролирует `routeGuard.ts`, а не добавлять маршруты в `routeGuard.ts`
без одновременной реализации логики ограничения доступа.
