## 概述

所有 OmniRoute 管理 API 路由均歸類為三種保護層級之一。分類是靜態的，定義於 `src/server/authz/routeGuard.ts`，並會在執行任何其他驗證分支之前進行評估。

## 層級

### 層級 1 — LOCAL_ONLY

**強制執行方式：** `isLocalOnlyPath(path)` → 回送主機檢查  
**繞過方式：** 預設不允許。若請求攜帶具有 `manage` 範圍的有效 API 金鑰，則會針對 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` 中的路徑提供有限度的例外（請參閱[管理範圍例外](#manage-scope-carve-out)）。

這些路由會產生子行程或執行執行階段程式碼。若將它們暴露給非回送流量，取得有效 JWT 的攻擊者（例如透過 Cloudflared/Ngrok 通道）便能觸發行程產生——這是一種已知的 CVE 類別（[GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)）。

**GHSA-fhh6-4qxv-rpqj 的本質（攻擊類別）：** 管理／代理程式伺服器公開了一個可啟動子行程（`npm install`、`node`、瀏覽器、Proxy、`git`、`tar` 等）的端點。若該端點可從主機外部存取——例如操作者將 OmniRoute 放在 nginx/Cloudflare/Tailscale 通道後方，而且 JWT 外洩，或驗證設定有誤——攻擊者便能將「呼叫 API」轉變成「在主機上執行命令」（遠端程式碼執行）。OmniRoute 透過在每個具有行程產生能力的路由上，**無條件地在任何驗證檢查之前強制執行回送主機檢查**，來封堵此風險：即使權杖透過通道外洩，仍無法存取行程產生功能。

**完整的 LOCAL_ONLY 集合。** 權威來源是 `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`；下表反映目前的狀態。`check-route-guard-membership` 閘門會列舉具有行程產生能力之前綴下的每個 `route.ts`，若其中任何路由未被分類為僅限本機，CI 就會失敗。

#### 管理範圍例外

部分 LOCAL_ONLY 路徑也可從非迴路位址存取，但前提是且僅限於請求攜帶 `Authorization: Bearer <api-key>`，且其
中繼資料包含 `manage` 範圍（或 `admin`）。此例外透過
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` 逐路徑明確管控，因此
任何新增 LOCAL_ONLY 路徑的預設行為仍為嚴格僅限迴路位址。未驗證的
請求，以及使用不具管理範圍金鑰的請求，仍會遭到拒絕並回傳
`403 LOCAL_ONLY`。

目前唯一可略過限制的前綴是 `/api/mcp/`。`/api/cli-tools/runtime/` 與
`/api/services/` 被刻意排除，因為它們可以建立任意
子程序（`npm install`、`node`）；這正是
LOCAL_ONLY 層級旨在防止的 CVE 類別。

**#7895 — `mcp:connect` 窄範圍：** `/api/mcp/` 例外也接受
持有窄範圍 `mcp:connect` 的 Bearer 金鑰
（`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`），並透過
`src/server/authz/policies/management.ts` 中的 `hasMcpConnectOrManageScope()` 進行檢查。
這僅限於 `/api/mcp/` — `mcp:connect` 不會授予任何其他
管理路由的權限（包括未來可能新增的任何其他 LOCAL_ONLY 略過前綴），而且它被刻意排除在
`MANAGEMENT_API_KEY_SCOPES` 之外。持有 `manage`/`admin` 的金鑰仍會
與先前完全相同地通過此例外；`mcp:connect` 則是權限較低的替代方案，
適用於不應需要廣泛管理存取權的遠端 MCP 專用呼叫端。

| 請求                                           | 路徑                       | 結果             |
| ---------------------------------------------- | -------------------------- | ---------------- |
| 非迴路位址，無 Bearer                          | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| 非迴路位址，Bearer 具有 `manage` 範圍          | `/api/mcp/*`               | 允許             |
| 非迴路位址，Bearer 具有 `mcp:connect` 範圍     | `/api/mcp/*`               | 允許             |
| 非迴路位址，Bearer 不具 `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| 非迴路位址，Bearer 具有 `mcp:connect` 範圍     | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| 非迴路位址，Bearer 具有 `manage` 範圍          | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| 迴路位址，無論是否有 Bearer                    | 任何 LOCAL_ONLY            | 允許（通過閘門） |

#### 操作者指引與稽核

若您在反向代理或隧道（nginx、Caddy、Cloudflare
Tunnel、Tailscale、Ngrok）後方執行 OmniRoute，迴路檢查仍會保護上述
可建立程序的路由 — 用戶端位址為非迴路位址的請求會在
**執行驗證之前**遭到拒絕並回傳 `403 LOCAL_ONLY`，因此洩漏的 JWT 無法觸及程序建立功能。操作者仍有兩項責任：

- **請勿透過偽造用戶端 IP 為迴送位址來「修正」403。** 設定
  `X-Forwarded-For: 127.0.0.1`，或使用會將來源位址改寫為
  迴送位址的代理，將會重新開啟此層級所封鎖的同類 RCE 漏洞。請透過代理公開
  儀表板/API——絕不可公開具有產生程序能力的路由。
- **將管理範圍的繞過機制維持在最小限度。** 只有 `/api/mcp/` 可以繞過，
  且僅限使用具有 `manage` 範圍的 API 金鑰。`SPAWN_CAPABLE_PREFIXES` 絕不能
  加入繞過清單——zod 結構描述會拒絕它們，而
  `isLocalOnlyBypassableByManageScope` 也會在執行階段拒絕它們（縱深防禦），
  這正是儀表板中「無法設為可繞過」的含義。執行階段快照載入器也會從已儲存的
  設定資料列中捨棄此類項目，而舊版 JSON 匯入功能
  (`/api/settings/import-json`) 絕不會寫入繞過金鑰。
  每個 `LOCAL_ONLY_API_PREFIXES` 項目都必須位於拒絕清單中，或已經過
  可繞過資格審查 (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`)。位於
  `/api/providers/` 下具有動態區段與靜態路徑的產生程序能力路由（例如 `/login`、
  `/refresh-cursor`），由
  `src/shared/constants/spawnCapablePrefixes.ts` 中以規則運算式為基礎的
  `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` 配套機制涵蓋，而非由扁平的
  `SPAWN_CAPABLE_PREFIXES` 陣列涵蓋——若要由扁平陣列攔截它們，就必須涵蓋
  整個 `/api/providers/` 前綴，這會過度擴大限制範圍，影響遠端儀表板為提供者
  執行合法 CRUD 操作時所使用的路由樹。

**稽核存取情況**——若要確認沒有任何主機外部流量能夠存取這些路由：

- 在 `/dashboard/settings/security` 開啟 **Authorization Inventory**：其中會呈現
  即時的 LOCAL_ONLY 前綴清單、哪些前綴可以繞過，以及編譯時期的
  產生程序能力（「無法設為可繞過」）集合。
- 在反向代理／存取記錄中，使用 grep 搜尋上述前綴與非迴送用戶端位址的配對。
  若任何此類請求傳回 `200` 而非 `403 LOCAL_ONLY`，即表示代理遮蔽了真實的
  用戶端 IP——請修正代理。
- 若 OmniRoute 的記錄中有這些路徑之一的 `403 LOCAL_ONLY`，代表防護機制
  正常運作，而不是應予抑制的錯誤。

### 第 2 層級 — ALWAYS_PROTECTED

**強制執行方式：** `isAlwaysProtectedPath(path)` → 略過 `requireLogin=false` 繞過機制
**繞過：** 當 `requireLogin=false` 時也無法繞過；一律需要 JWT

這些路由具有破壞性或不可逆性。若允許在「無密碼」安裝環境中存取它們，
將意味著同一個 LAN 上的任何人都能清除資料庫或終止伺服器程序。

| 路徑                                      | 原因                                           |
| ----------------------------------------- | ---------------------------------------------- |
| `/api/shutdown`                           | 終止伺服器程序                                 |
| `/api/settings/database`                  | 資料庫匯出、匯入與清除                         |
| `/api/db-backups`                         | 完整資料庫備份封存檔存取                       |
| `/api/settings/export-json`               | 匯出完整設定資料區塊（包括機密資料）           |
| `/api/settings/import-json`               | 取代完整設定資料區塊                           |
| `/api/providers/health-autopilot/actions` | 執行 autopilot 修復動作                        |
| `/api/settings/obsidian`                  | 為任何保存庫根目錄簽發可重複使用的 WebDAV 認證 |

**違規時的回應：** `401 Authentication required`

`/api/settings/obsidian` 也涵蓋其 `/webdav` 子路徑：`POST` 會將 WebDAV 檔案服務——
由自訂 Node 層在 Next.js 之前提供，位於此管線之外——指向呼叫者選擇的根目錄，
並回傳新簽發的 Basic 認證；`DELETE` 會輪替這些認證，而父路徑的 `POST` 則會儲存
Obsidian REST API 權杖。GHSA-62vw 只遮蔽了 `GET` 對密碼的洩露；簽發功能仍位於
失效時開放層級（GHSA-7pq4-8pvv-rx7r）。`enableObsidianVaultSync()` 還會拒絕
本身即為資料目錄、位於資料目錄內，或包含資料目錄的保存庫。

### 全新安裝的啟動程序僅限迴送——依據真實對等端，而非 `Host`

若未設定管理密碼（且沒有 `INITIAL_PASSWORD`），
`src/shared/utils/apiAuth.ts` 中的 `isAuthRequired()` 只會為迴送對等端保持匿名
啟動程序開放。迴送狀態會依序根據受信任的對等端訊號判定：加上權杖戳記的真實
TCP 對等端（`PEER_IP_HEADER` + `VIA_PROXY_HEADER`，即原則所看到的內容）、
管線本身的 `AUTHZ_HEADER_PEER_LOCALITY` 判定結果（即路由處理常式所看到的內容，
且僅在設定 `OMNIROUTE_PEER_STAMP_TOKEN` 時才受信任），或直接呼叫者的真實
通訊端對等端。系統絕不會參考 `Host` / `nextUrl.hostname`，而第一次寫入密碼
(`POST /api/settings/require-login`) 也受相同限制，而非向每個網路對等端開放
（GHSA-7pq4-8pvv-rx7r）。`managementPolicy` 會明確向下傳遞其自身的
`peerContext` 判定結果，因此 ORIGINAL（剝除前）請求的標頭永遠不會決定該結果。

### 第 3 層級 — MANAGEMENT（預設）

所有其他管理路由。除非已設定 `requireLogin=false`，否則需要驗證。
CLI 權杖可以驗證這些路由（迴送 + 有效的 HMAC）。

## 評估順序

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → 繼續執行
     → 非 loopback、具 manage 範圍的 Bearer
        且 isLocalOnlyBypassableByManageScope   → 允許 (management_key)
     → 否則                                      → 拒絕 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → 允許 (system)
  3. hasValidCliToken(headers)?
     → 允許 (cli) [loopback + timingSafeEqual HMAC 檢查]
  4. isAlwaysProtectedPath(path) 或 requireLogin=true?
     → isDashboardSessionAuthenticated?
        → 允許 (dashboard_session)
     → 在不可繞過路徑上具 manage 範圍的 Bearer？
        → 允許 (management_key)
     → 拒絕 401/403
  5. requireLogin=false?
     → 允許 (anonymous)
```

步驟 1 的 manage 範圍分支，是唯一能滿足 LOCAL_ONLY 路由的已驗證路徑；驗證後端失敗時會傳回 503（而非 403），因此過期的 DB 不會在無提示的情況下降級為「拒絕」。

## 新增可啟動程序的路由

1. 將路徑前綴新增至
   `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_API_PREFIXES`
2. 在 `tests/unit/authz/routeGuard.test.ts` 中新增測試，斷言
   `isLocalOnlyPath()` 對新前綴傳回 true
3. **絕不可略過此步驟** — 請參閱 `CLAUDE.md` 中的硬性規則 #15
4. 決定：此路由是否也應納入 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`？
   預設答案為**否**。僅當該路由能安全地公開給 manage 範圍持有者時，才選擇加入（亦即不會啟動任意由使用者控制的程式碼）。

## 新增可由 manage 範圍繞過的路徑

1. 確認該路由不會執行使用者提供的程式碼或命令。如果會，請停止 — 此例外機制並不適用。
2. 將前綴附加至
   `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`
3. 在 `tests/unit/authz/management-policy.test.ts` 中，針對所有四種請求形式新增測試涵蓋：無 Bearer（403）、manage Bearer（允許）、非 manage Bearer（403），以及每個前綴的迴歸測試，確保 `/api/cli-tools/runtime/*` 即使帶有 manage Bearer，仍嚴格限制為 loopback。

## 在 OpenAPI 中記錄安全層級

將新路由新增至 `docs/openapi.yaml` 時，若該路由由 `routeGuard.ts` 分類，請套用對應的提供者擴充欄位：

| routeGuard.ts 分類           | YAML 註記                  | 強制執行方式                          |
| ---------------------------- | -------------------------- | ------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`    | `x-loopback-only: true`    | 無條件封鎖來自非 loopback 的請求      |
| `ALWAYS_PROTECTED_API_PATHS` | `x-always-protected: true` | 即使 `requireLogin=false` 仍要求驗證  |
| 內部管理員／偵錯路由         | `x-internal: true`         | 預設不顯示於 /dashboard/api-endpoints |
| 無（公開／標準驗證）         | （不需要註記）             | 由標準 `requireLogin` 控制的存取      |

### 驗證

有兩個指令碼會強制確保 YAML 註記與 `routeGuard.ts` 之間的一致性：

- `scripts/check/check-openapi-coverage.mjs` — 若涵蓋率低於 99%，則執行失敗
- `scripts/check/check-openapi-security-tiers.mjs` — 若 `x-loopback-only` 或
  `x-always-protected` 註記與編譯期常數不一致，則執行失敗

這兩個指令碼都會在 pre-commit hook 和 CI 中執行。

### 誤判規則

若某個路由標有 `x-always-protected` 或 `x-loopback-only`，但未列於
`routeGuard.ts` 常數中，涵蓋率指令碼將會失敗。修正方式一律是讓 YAML 與
`routeGuard.ts` 實際強制執行的內容保持一致，而不是在尚未實作強制執行邏輯的情況下，逕自將路由新增至 `routeGuard.ts`。
