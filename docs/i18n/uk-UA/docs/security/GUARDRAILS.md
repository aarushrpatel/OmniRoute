> **Джерело істини:** `src/lib/guardrails/`
> **Останнє оновлення:** 2026-08-29 — v3.8.51 (Походження стенограми Video Bridge оголошується абонентом,
> ще не перевірено сервером — уточнено згідно з #11661)

Захисні механізми забезпечують безпеку, політику та трансформації вмісту на межі між OmniRoute та вищестоящими провайдерами. Кожен захисний механізм може перевіряти (та за бажанням відхиляти, трансформувати або анотувати) корисні навантаження запитів (`preCall`) та відповіді вищестоящих систем (`postCall`).

Система є **відкритою при збої**: якщо захисний механізм видає помилку під час виконання, реєстр записує помилку та продовжує роботу з наступним захисним механізмом, замість того, щоб відхиляти запит. Блокування є явним рішенням (`block: true`), а не випадковістю.

## Вбудовані захисні механізми

Під час імпорту реєстр автоматично завантажує шість захисних механізмів у порядку пріоритету
(див. `registry.ts` → `registerDefaultGuardrails()`):

| Пріоритет | Назва               | Етап(и)        | Файл                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`      | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`      | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

Менші номери пріоритету виконуються **першими**.

### Міст комп’ютерного зору (`visionBridge.ts`) — міст модальностей PR-1

Перехоплює запити із зображеннями, спрямовані до **моделей без підтримки комп’ютерного зору**, і або
перенаправляє весь запит до моделі з підтримкою комп’ютерного зору, або замінює частини із
зображеннями текстовими описами, створеними налаштовуваною моделлю комп’ютерного зору перед
викликом вищого рівня. Це дає змогу провайдерам, які підтримують лише текст, прозоро обробляти
мультимодальні корисні навантаження.

Потік виконання:

1. Пропустити, якщо цільова модель уже підтримує комп’ютерний зір (якщо тільки вона не входить до
   списку примусового застосування моста `isVisionBridgeForcedModel`).
2. Видобути частини із зображеннями за допомогою `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), яка делегує обробку **уніфікованому детектору
   медіаданих** `detectMediaParts()` у `open-sse/utils/mediaParts.ts` — єдиному
   джерелу істини, спільному з фільтром сумісності combo.
   Видобування дозволено лише для частин верхнього рівня у форматах, які
   `replaceImageParts` може вставити назад (контракт видобування↔заміни): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` та Responses API `input_image`. Вкладені збіги й
   формати лише з індикаторами є матеріалом для combo-фільтра й ніколи не видобуваються.
   Пропустити, якщо нічого не знайдено.
3. Визначити конфігурацію середовища виконання за допомогою `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): нові ключі налаштувань `modalityBridge*`
   мають перевагу; застарілі ключі `visionBridge*` залишаються **резервним варіантом на один цикл**
   (вікно відкочування). Якщо міст вимкнено, пропустити обробку до будь-якого обходу медіаданих.
4. Селектор режиму (`modalityBridgeVisionMode`, див. таблицю нижче) визначає,
   чи виконувати перенаправлення або опис. Перенаправлення повертає `modifiedPayload`, у якому
   замінено лише `model`, а також метадані `{ rerouted, fromModel, toModel, imagesKept }`.
5. Шлях опису: обмежити кількість зображень значенням `maxImages`, сформувати
   запит з урахуванням завдання, перевірити кеш описів, викликати модель комп’ютерного зору **паралельно**
   (`Promise.allSettled`) і вставити замість зображень текстові частини
   `[Image N]: <description>`. Невдала спроба опису повертає `null`, а початкова частина із зображенням
   **зберігається** (#4012) — крім шляху опису combo, коли всі
   спроби опису завершилися невдало: у такому разі для підтвердженої моделі вищого рівня без підтримки
   комп’ютерного зору підставляється заглушка
   `(недоступно — не підключено жодного провайдера з підтримкою комп’ютерного зору)` (#8430).
6. Повернути `modifiedPayload` + метадані (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Селектор режиму (`modalityBridgeVisionMode`)

| Режим      | Типово | Поведінка                                                                                                                                                                                                                                                                                                                                                        |
| ---------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔      | Застаріла евристика, без змін (#6640/#7204): моделі не-combo/`auto/` перенаправляються до найкращої моделі комп’ютерного зору, якщо початкова модель уже не має придатних облікових даних (тоді створюється опис); для цілей combo завжди створюється опис.                                                                                                      |
| `describe` |        | Завжди створювати опис — блок перенаправлення повністю пропускається; завжди відповідає вибрана користувачем модель.                                                                                                                                                                                                                                             |
| `reroute`  |        | Примусове перенаправлення: перевірка збереження моделі з обліковими даними обходиться. Перевірка облікових даних **цілі** перенаправлення все одно застосовується — якщо придатної цільової моделі комп’ютерного зору немає, запит переходить до створення опису, щоб необроблені зображення ніколи не потрапляли до бекенда, який підтримує лише текст (#8430). |

Примусові режими виконують раннє завершення **до** запуску автоматичної евристики; поведінка `auto`
побайтово ідентична захисному механізму до PR-1.

#### Область дії API-ключа (`visionBridgeKeyScope.ts`)

Коли API-ключ виклику обмежує `allowedConnections`, пули квот
(`allowedQuotas`) або моделі (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), міст вибирає для
перенаправлення й опису лише моделі, які дозволено використовувати цьому ключу, через з’єднання, які
дозволено використовувати цьому ключу. Після цього виклик опису завжди проходить через самозациклення
OmniRoute із заголовком `x-omniroute-self-loop-key-id`, щоб отриманий запит чату
повторно застосував політику з’єднань і моделей цього ключа. `enforceApiKeyPolicy()`
враховує цей заголовок лише разом із bearer-токеном самозациклення, тому він може
лише звужувати доступ, а ідентифікатор, який не вдається визначити, відхиляється.

Якщо для ключа не дозволено жодної моделі комп’ютерного зору, шлях опису не втручається, а
запит передається без змін — така сама fail-open поведінка, як і для вимкненого
захисного механізму (метадані `{ skipped: true, reason: "no_permitted_vision_model" }`).
Запити без ключа та ключі без цих обмежень поводяться так само, як
і раніше.

#### Запит опису з урахуванням завдання (`modalityBridgeVisionTaskAware`)

За замовчуванням — **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) додає
текст **останнього повідомлення користувача** (обрізаний до 500 символів) до базового
промпту опису, спрямовуючи опис на те, про що насправді запитав користувач
(патерн codex-vision-proxy), і просить візуальну модель транскрибувати видимий
текст. Якщо прапорець вимкнено або текст користувача відсутній, базовий промпт
використовується без змін.

Власний OpenAI-сумісний запит циклу самоопису (`callVisionModelSingle()`
у `visionBridgeHelpers.ts`) завжди запитує `image_url.detail: "high"` —
безумовно, для кожного викликувача/провайдера, незалежно від будь-якого сигналу
клієнта. Вибірка з низькою деталізацією погіршує точність OCR саме для завдання
транскрибування тексту, яке вимагає цей промпт, тому сам виклик опису завжди
запитує високу деталізацію незалежно від рівня деталізації, використаного у
вихідному вхідному запиті. Це впливає лише на тіло внутрішнього запиту опису;
це не змінює спосіб, у який OmniRoute пересилає власне значення
`image_url.detail` викликувача в основному запиті — це значення за замовчуванням
застосовується окремо й лише для виявлених клієнтів OpenCode у
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Гілка
циклу самоопису у форматі передавання Anthropic не має поля `detail`, тому
жодне з цих значень за замовчуванням на неї не впливає.

#### Обмеження виводу опису (`modalityBridgeVisionMaxChars`)

| Ключ                           | За замовчуванням | Діапазон          |
| ------------------------------ | ---------------- | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`              | `0` або 100–50000 |

`0` (значення за замовчуванням) означає **відсутність обмеження** — опис, повернутий
`callVisionModel()`, передається без змін, зберігаючи поточну
поведінку. Будь-яке значення в діапазоні 100–50000 обрізає опис із
суфіксом `…`, перш ніж його буде вставлено назад як `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` у `src/lib/guardrails/visionBridge.ts`).
Збільшуйте це значення для насичених деталями завдань OCR, де наступній моделі
потрібна повна транскрипція; зменшуйте його, щоб обмежити використання токенів
багатослівними візуальними моделями. Поле панелі керування розташоване на
панелі Advanced вкладки Vision
(`modality-bridge-max-chars` у `ModalityBridgeVisionTab.tsx`) і підвищує будь-яке
значення від 1 до 99 до мінімуму 100, залишаючи явно вказаний `0`
без змін — `0` сам по собі є допустимим значенням Zod
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не лише
значенням за замовчуванням для стану «не задано».

#### Кеш описів (`modalityBridge/bridgeCache.ts`)

Внутрішньопроцесний кеш LRU + TTL для результатів опису, спільний для всього процесу.
Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` із
фреймінгом за префіксом довжини (без колізій на межах полів). Компонент моделі —
це **налаштована** модель мосту, а не модель, яка фактично відповіла:
`callVisionModel` може внутрішньо перейти до резервної моделі, а формування
ключа для кожної спроби фрагментувало б кеш. Невдалі описи ніколи не кешуються.
Налаштування:

| Ключ                            | За замовчуванням | Діапазон |
| ------------------------------- | ---------------- | -------- |
| `modalityBridgeCacheEnabled`    | `true`           | —        |
| `modalityBridgeCacheTtlMinutes` | `60`             | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`            | 10–5000  |

#### Нормалізація віддалених зображень (самоопис/отримання base64)

Коли міст самостійно отримує **віддалене** зображення — для самовиклику опису
Anthropic і перетворення у base64 для формату передавання Claude
(`ensureBase64ImagesForClaudeWire`), в обох випадках через
`fetchRemoteImageAsDataUri()` у `visionBridgeHelpers.ts` — отриманий URI даних
перед вбудовуванням у запит до візуальної моделі передається через
`normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`). Завеликі зображення зменшуються до
**2048px по довгій стороні** (відповідно до обмеження зміни розміру, яке
OpenAI/Anthropic уже застосовують на стороні сервера), що зменшує обсяг
завантажуваних даних і затримку, не змінюючи те, що бачить візуальна модель.
Для зміни розміру використовується `sharp`, завантажений через динамічний імпорт:
на платформі, де його нативний бінарний файл не вдається завантажити,
`normalizeDataUri()` **ніколи не викидає виняток** — натомість він без змін
передає вихідні байти, тож шлях опису/перетворення у base64 завжди продовжує
працювати. Дані, які не є зображенням (коли під час отримання не було повернуто
зображення, придатне для декодування), також передаються без змін. Ця
нормалізація застосовується лише до зображень, які міст отримує для власного
самовиклику, і ніколи не застосовується до необробленого наскрізного корисного
навантаження викликувача, що відповідає принципу внесення змін лише за явною
згодою (Жорстке правило №20).

#### Схема налаштувань + міграція

Нові ключі `modalityBridge*` перевіряються за допомогою Zod у
`updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, трійка `modalityBridgeCache*` і група
`modalityBridgeAudio*`, яку використовує Audio Bridge. Міграція
`141_modality_bridge_settings.sql` копіює наявні застарілі значення
`visionBridge*` до відповідних нових ключів (ідемпотентно, ніколи не
перезаписуючи значення `modalityBridge*`, установлене оператором); застарілі
ключі залишаються допустимими як резервний варіант читання протягом одного
циклу випуску.

#### Заголовок прозорості + статистика

Перетворені через опис відповіді містять
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(створюється `buildModalityBridgeHeader()` у `modalityBridge/bridgeStats.ts`,
додається `withModalityBridgeHeader()` у `src/sse/handlers/chatHelpers.ts`).
Перенаправлені запити **не** отримують заголовка — корисне навантаження не було
змінено, а заміну моделі вже видно в полі `model` тіла відповіді.

`GET /api/modality-bridge/stats` (автентифікація керування, той самий рівень, що й для
`GET /api/settings`) повертає збережені в пам’яті лічильники для кожної модальності
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` та
`video`. `averageLatencyMs` використовує `latencySamples`, а не всі спроби, як
знаменник; операція без вимірювання часу не створює штучний зразок із тривалістю
нуль мілісекунд. `bridged` залишається зворотно сумісним псевдонімом для успішних
перетворень; невдалі спроби не збільшують його значення.
Лічильники за задумом скидаються під час перезапуску процесу
(це телеметрія, а не облік).

#### Конфігурація панелі керування

Окрема сторінка панелі керування розташована за адресою
`/dashboard/settings/modality-bridge`. Її вкладки `Vision`, `Audio`
та `Video`, доступні через URL, зберігають параметри запиту під час перемикання
значення `tab`.
Вкладка Vision надає налаштування ввімкнення, режиму, вибору моделі (включно з
автоматичним значенням за замовчуванням), формування запитів з урахуванням завдання,
розширених обмежень часу очікування, зображення, довжини опису й кешу, лічильники
середовища виконання та захищений тестовий запит. Вкладка Audio також працює:
вона надає налаштування ввімкнення, засіб вибору лише STT-моделей із варіантом Auto,
обмеження часу очікування й максимальної тривалості кліпу, лічильники аудіо та
тестовий запит `input_audio`. Вкладка Video є функціональною: вона повідомляє
стан середовища виконання FFmpeg/ffprobe — один із чотирьох явних станів інтерфейсу
користувача (`unknown`, поки перевірка триває або не може завершитися; `restricted`
на хості панелі керування, що не є loopback-адресою, де перевірка пропускається на
боці клієнта; `unavailable` після перевірки та підтвердження відсутності; або
`available` із версіями FFmpeg/ffprobe), — зберігає обмеження ввімкнення, моделі,
кадрів, відео й часу очікування, фільтрує засіб вибору моделей до моделей із
підтримкою комп’ютерного зору та надає лічильники відео.

Колишня картка Vision Bridge у налаштуваннях ШІ тепер є посиланням для сумісності
на нову сторінку; вона більше не містить другої копії форми. Media Providers також
пов’язує робочі процеси Image-to-Text і Speech-to-Text із відповідними вкладками
Modality Bridge, не видаляючи наявний майданчик Speech-to-Text.

**Обхід контролю допуску для власного циклу:** коли виклик опису маршрутизується
через власний `/v1`-цикл OmniRoute (нестандартна модель постачальника), підзапит
надсилає `x-omniroute-admission-bypass: internal` й автентифікується за допомогою
визначених облікових даних власного циклу — локального маркера `sk_omniroute`
у локальному режимі або налаштованого оператором ключа середовища
`OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), щоб розгортання з
`REQUIRE_API_KEY=true` усе ще могли виконувати виклик опису. Обхід дозволено лише
для цих точних облікових даних, тому зовнішні клієнти не можуть використовувати
цей заголовок для пропуску контролю допуску.

Застарілі значення за замовчуванням містяться в
`src/shared/constants/visionBridgeDefaults.ts`; нові значення режиму, урахування
завдання й кешу за замовчуванням, а також засіб визначення налаштувань містяться в
`src/shared/constants/modalityBridgeDefaults.ts`. Захисний механізм надає параметр
конструктора `deps`, щоб тести могли підставляти фіктивні реалізації `getSettings`
і `callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехоплює запити чату з аудіо до того, як вони потраплять до цільової системи,
про яку не відомо, чи підтримує вона аудіовхід. Він ніколи не змінює маршрут
запиту чату: аудіочастини транскрибуються через наявну сумісну з OpenAI кінцеву
точку multipart, а вибрана модель чату продовжує роботу з текстовими транскриптами.

Потік:

1. Визначити `supportsAudio` через `getResolvedModelCapabilities()`. Явні
   метадані реєстру постачальників мають пріоритет, далі йдуть статичні метадані
   моделі, а потім синхронізовані `modalities_input`. Оголошений список вхідних
   даних без `audio` означає `false`; відсутність даних про можливості означає
   `null`. Як `false`, так і `null` активують консервативний міст, тоді як `true`
   обходить його.
2. Визначити налаштування `modalityBridgeAudio*` і видобути придатні для вставлення
   аудіочастини верхнього рівня з кожного повідомлення за допомогою спільного
   детектора `detectMediaParts()`. Підтримувані формати передавання — OpenAI
   `input_audio`, `audio_url` і `source.media_type: "audio/*"`. Вкладене аудіо
   виявляється для маршрутизації, але не видаляється шляхом вставлення. Обсяг
   роботи обмежується `modalityBridgeAudioMaxClips`; наступні частини залишаються
   без змін.
3. Використати налаштоване значення `provider/model` або дозволити
   `selectAudioBridgeModel()` пройти `AUDIO_TRANSCRIPTION_PROVIDERS` у стабільному
   порядку каталогу й вибрати першу модель із придатними активними обліковими
   даними постачальника.
4. `callAudioTranscription()` перетворює аудіо у форматі base64/data-URI на
   multipart-файл `file` або завантажує віддалений `audio_url` через захист
   вихідних підключень, що дозволяє лише публічні адреси, із фіксацією DNS і
   обмеженням 25 МБ. Потім він надсилає файл і вибрану модель методом POST до
   локального власного циклу `/v1/audio/transcriptions`, автентифікованого через
   `resolveSelfLoopBearer()`. Наявний маршрут транскрибування виконує звичайний
   пошук облікових даних, обробку періоду очікування/обмеження частоти та
   диспетчеризацію до постачальника.
5. Успішні виклики замінюють відповідні частини на
   `[Audio N]: <transcript>`. Виклики виконуються через `Promise.allSettled`:
   окремий збій зберігає початкову аудіочастину (контракт #4012). Якщо всі виклики
   завершуються невдало й для цільової системи доведено
   `supportsAudio === false`, частини стають
   `[Audio N]: (unavailable — no STT provider connected)` (контракт #8430). Для
   невідомої цільової системи (`null`) результат із суцільними збоями залишається
   без змін. Цільова система, для якої доведено підтримку лише тексту та немає
   придатних облікових даних STT, отримує ту саму явну заглушку без виконання
   мережевого виклику.

Успішні транскрипти використовують спільний для всього процесу LRU/TTL-кеш
Modality Bridge. Ключ поєднує посилання на аудіо, стабільну мітку операції
`audio-transcription` та вибрану STT-модель; збої ніколи не кешуються. Спроби
обробки аудіо оновлюють спільні лічильники `bridged`, `cacheHits`, `failures` і
`lastUsedAt`. Перетворені відповіді містять
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; незмінені
запити не отримують сегмент Audio Bridge.

Налаштування середовища виконання зберігаються в БД і перевіряються за допомогою Zod:

| Ключ                          | Типове значення | Діапазон        |
| ----------------------------- | --------------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`          | —               |
| `modalityBridgeAudioModel`    | `""`            | Auto або STT ID |
| `modalityBridgeAudioTimeout`  | `60000`         | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`             | 1–10            |

Спільний кеш і надалі керується параметрами `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` і `modalityBridgeCacheMaxEntries`.

### Відеоміст (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехоплює частини відео верхнього рівня в `messages` Chat Completions та `input`
Responses API до виклику цільової моделі, для якої не відома вбудована підтримка
відео. Підтримувані формати: `input_video`, `video_url`, `video_source`, URL-адреси
HTTPS і URI даних `data:video/*;base64,...`. Звичайні імена файлів у тексті не
вважаються відео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) відповідає за обхід запиту,
перевірку можливостей і політики, агрегацію в межах запиту та корисне
навантаження відповіді. Обробка кожного відео — отримання, кешування всього
результату, опис послідовності кадрів (з об'єднанням будь-якої заявленої
викликачем транскрипції аудіо), а також метрики, переривання й очищення для
кожної спроби — прихована за `processVideoPart` у `videoBridgePipeline.ts`,
яка викликається один раз для кожної частини відео в циклі `preCall`.
Цей модуль також визначає явні межі портів `VideoMediaBrokerPort`
(отримання байтів і видобування вибіркових кадрів), `VideoAudioTranscriptionPort`
(об'єднання заявленої викликачем транскрипції аудіо з підписами вибіркових
кадрів) і `VideoDrilldownPort` (межа збереження деталізації кадрів; іще не
підключена до `processVideoPart` — наразі записи деталізації створює лише
окремий маршрут `/api/modality-bridge/video/drilldown`).

Публічний шлях запиту `/v1` ніколи не імпортує й не викликає підпроцес.
Віддалені відео завантажуються з обмеженням у 50 MiB; вбудовані base64-відео
мають консервативне обмеження декодованого розміру в 36 MiB на відео, щоб
обгортка моделі, повідомлень і фреймінгу залишалася в межах публічного ліміту
приймання JSON-запитів у 50 MiB. Довжина вбудованих даних і оцінки декодованого
розміру перевіряються до виділення пам'яті. HTTPS є обов'язковим для початкової
віддаленої URL-адреси та кожного перенаправлення; використовується наявний
захист лише для публічних вихідних з'єднань із фіксацією DNS. Потім байти
перетинають точну внутрішню межу брокера `POST /api/modality-bridge/video/extract`.
Цей маршрут має одночасно позначки `LOCAL_ONLY` і `SPAWN_CAPABLE`, приймає лише
автентифікований у межах процесу запит із довіреного loopback-інтерфейсу та
ніколи не приймає URL-адресу, шлях файлової системи, виконуваний файл або список
аргументів. Конвеєр обмеження розміру тіла API та інкрементальний зчитувач тіла
обробника незалежно забезпечують обмеження вхідних даних брокера в 50 MiB.
Його обмежена черга виконує по одному видобуванню за раз, дозволяє чотири
очікувальні завдання та обмежує обсяг очікувальних вхідних даних до 100 MiB.

Усередині брокера `ffprobe` читає приватний локальний файл; фіксований білий
список форматів виключає формати списків відтворення та маніфестів. Для
дозволених контейнерів сімейства MOV зовнішні посилання на дані MOV за
замовчуванням залишаються вимкненими, і фіксована команда не вмикає їх.
І `ffprobe`, і `ffmpeg` використовують білий список протоколів лише з `file`,
один потік, фіксовані масиви аргументів, не використовують оболонку, а
виконувані файли визначаються через `PATH`. Потоки обкладинок у вигляді
прикріплених зображень не вважаються кандидатами для відтворення. Усі потоки,
придатні для відтворення, мають відповідати обмеженням, а явний потік за
замовчуванням має пріоритет перед детермінованим резервним вибором потоку з
найменшим індексом. Відео обмежуються тривалістю 600 секунд, 8 192 пікселями
на вимір і 33 554 432 вихідними пікселями. FFmpeg вибирає 1–16 проміжних
JPEG-кадрів, зменшує довгу сторону максимум до 1 024 пікселів, не збільшуючи
менші вхідні дані, і ніколи не отримує URL-адресу. За замовчуванням вибірка має
значення `uniform`. Необов'язкові політики `scene_aware` та експериментальна
`segment_aware` виконують один додатковий фіксований прохід FFmpeg по вже
перевіреному локальному потоку, вибирають обмежений набір часових позначок сцен
`showinfo` і детерміновано повертаються до тих самих рівномірно розподілених
середніх точок у разі помилки детектора, перевищення часу очікування,
некоректних вихідних даних або порожнього набору кандидатів. Режим з урахуванням
сегментів розподіляє вибірки середніх точок пропорційно до перевірених
інтервалів сцен; докази з урахуванням сегментів і резервна поведінка докладно
описані нижче. Жорстке обмеження в 16 кадрів застосовується після вибору в
кожній політиці. Якщо запит з урахуванням сцен має бюджет лише в один кадр, він
використовує рівномірну середню точку активного вікна всього відео або вікна
фокусування та повідомляє `policyEffective: uniform`: один вибраний кадр сцени
не може зберегти обидві часові межі. Викликач може додатково надати скінченне
вікно фокусування (`start`/`end` у секундах); межі обмежуються тривалістю
медіафайлу, перевернуті або нескінченні вікна відхиляються, а всі політики
вибірки застосовуються лише в межах нормалізованого інтервалу. Отримане вікно
включається в метадані вибірки та в префікс ненадійного опису, щоб подальші
моделі могли відрізнити сфокусований уривок від повної часової шкали.

Семантичне фокусування підписів є окремим явним параметром. Стандартний режим
аналізу `full` зберігає наявний запит для кадрів і ніколи не передає текст
запиту моделі створення підписів. У режимі `focused` міст зчитує лише останній
непорожній створений користувачем `text`/`input_text` із того самого контейнера
Chat або Responses, нормалізує його до NFC, згортає керівні символи й пробіли
та обмежує довжину до 500 кодових точок Unicode. Порожній результат спричиняє
повернення до точного запиту `full`. Придатна підказка серіалізується як JSON
у спеціальному блоці ненадійного користувацького контексту й може лише
визначати пріоритет спостережуваних деталей; вона не може скасувати окреме
застереження про невиконання інструкцій, видимих або чутних у медіа. Текстове
фокусування ніколи не виводить `start`/`end` і не змінює часовий семплер.

#### FU-07 — структурні докази сегментів

`segment_aware` використовує один обмежений прохід попереднього аналізу вже перевіреного локального відеопотоку. Фіксований ланцюжок фільтрів спочатку масштабує відео до ширини не більше ніж 320 пікселів, виявляє зміни сцен і завмерлі інтервали, а потім виконує вибірку з частотою 1 кадр на секунду для оцінювання розмиття, середньої яскравості та просторової/часової інформації. Прохід обмежено 600 структурними вибірками, одним потоком FFmpeg/фільтра, тими самими списками дозволених протоколів лише `file` і контейнерів, обсягом виведення процесу не більше 1 MiB та щонайбільше 30 секундами в межах спільного переривання/граничного терміну брокера. Він ніколи не приймає з запиту команду, фільтр, шлях або URL.

Структурні значення є детермінованими свідченнями вибірки, а не семантичним розумінням відео. Вони не визначають об’єкти, дії, підписи, мовлення чи наміри користувача. Межі сцен і завмирань формують сегменти; покриття завмирання, розмиття, експозиція, просторова деталізація та часові зміни впливають лише на розподіл наявного бюджету в 1–16 кадрів. Для повністю завмерлого сегмента встановлено обмеження в один кадр, тоді як незавмерлі сегменти конкурують за решту бюджету. Коли меж більше, ніж кадрів, зберігається рівномірне покриття часової шкали, щоб швидкі ранні зміни кадру не могли приховати довгий кінцевий сегмент. Межі сцен, що перебувають у межах 1-секундної роздільності аналізу від межі завмирання, об’єднуються.

Відсутні фільтри, некоректні/порожні свідчення, помилка детектора або перевищення часу обмеженого попереднього аналізу призводять до безпечного переходу до точної політики рівномірного вибору середніх точок. Переривання з боку викликувача або настання граничного терміну брокера не призводить до такого переходу: воно завершує активний підпроцес, запобігає подальшому видобуванню кадрів, а приватне тимчасове дерево видаляється в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` створює детерміновані реальні тестові дані FFmpeg для оцінювання скорочення кількості викликів створення підписів після дедуплікації, розподілу бюджету для щільного руху, свідчень розмиття/експозиції/SI-TI, швидких змін кадру з довгим завершальним фрагментом і хибнопозитивних спрацювань під час поступового згасання. Скрипт записує фактичний час попереднього аналізу, а там, де доступна `/usr/bin/time`, — процесорний час дочірнього процесу та піковий RSS. Його перевірки якості є лише структурними еталонами. Якість реальної моделі створення підписів залишається `HOLD`, оскільки цей засіб тестування не має авторизованої кінцевої точки або зафіксованого оцінювача. Грошова економія також залишається `HOLD`, якщо параметр `--caption-cost-per-call-usd` не надає явну додатну оцінку вартості одного виклику; скрипт ніколи не вигадує жодного з цих результатів.

Розмір кожного кадру обмежено 4 MiB, сукупний розмір усіх необроблених кадрів — 23 MiB, а розмір серіалізованої відповіді брокера — 32 MiB. Приватний тимчасовий каталог видаляється в `finally`. OmniRoute не включає FFmpeg і не приймає користувацький шлях до виконуваного файлу. Перед створенням підписів міст застосовує консервативний прохід візуальної дедуплікації: кожен JPEG зменшується до буфера у відтінках сірого розміром 16×16 і порівнюється лише з останнім збереженим кадром. Якщо запитаний бюджет підписів перевищує один кадр, видобування надає обмежений пул кандидатів розміром до подвійного бюджету, але не більше ніж 16 кадрів. Запитане обмеження застосовується лише після дедуплікації, причому під час остаточного проріджування зберігаються перший і останній вибрані кандидати, якщо бюджет становить щонайменше два кадри. Версіонована політика `grayscale-16x16-mean-cells-v2` використовує більше зі значень: середню різницю яскравості або частку комірок мініатюри, нормалізована різниця яких становить щонайменше 0.05. Порогове значення дублювання — константа 0.04, вибрана заради передбачуваності, а не доступності як параметра часу виконання. Цей вторинний висококонтрастний сигнал зберігає незначний рух і зміни видимого тексту, які може приховати порівняння лише за середнім значенням. Помилки компаратора або декодера призводять до безпечного збереження покриття. Метадані виведення розрізняють видобутих кандидатів, успішно використані кадри та відкинуті візуальні дублікати.

Явно позначена відеочастина може запитувати контактний аркуш із часовими позначками. Міст створює JPEG-сітку щонайбільше з 4 стовпців і 16 кадрів. У кожну 512-піксельну комірку часова позначка джерела вписується у висококонтрастну нижню смугу, водночас ті самі часові позначки зберігаються в текстових метаданих для подальшого зіставлення та аудиту. Розмір повного JPEG залишається обмеженим 32 MiB. Якщо `sharp` не може декодувати або скомпонувати сітку, міст повертається до окремих JPEG-кадрів; переривання з боку клієнта все одно поширюється на операцію з аркушем.

Свідчення для просування навмисно відокремлено від синтетичного мікротесту продуктивності компонування. `scripts/perf/video-bridge-contact-sheet-eval.ts` визначає A/B-засіб тестування з версіонованою схемою для реальних моделей комп’ютерного зору, сумісних з OpenAI. Він вимірює повідомлену постачальником кількість токенів, наскрізну фактичну затримку (включно з компонуванням аркуша), кількість викликів моделі та збереження фактів, визначених маніфестом. Необроблені відповіді моделі не записуються до звіту; зберігаються лише дайджести SHA-256 та ідентифікатори зіставлених фактів. Засіб тестування не здійснює мережевих або платних викликів моделі, якщо не передано `--execute-real` і не налаштовано `--model`, `OMNIROUTE_BASE_URL` та `OMNIROUTE_API_KEY`. Без такого явного реального запуску його машинозчитуваний вердикт залишається `HOLD`; самі лише синтетичні вимірювання корисного навантаження/кількості викликів не є свідченнями для просування.

Викликувачі можуть додати необов’язковий масив `transcript.cues` до підтримуваної відеочастини, якщо вони вже мають синхронізований текст. Кожна репліка повинна містити `text`, скінченний інтервал `start`/`end` у межах визначеної тривалості та значення `source` з дозволеного списку (`client`, `embedded` або `audio-bridge`); стандартне значення `confidence` — `1`, і воно має залишатися в діапазоні від `0` до `1`. Точні дублікати реплік згортаються. OmniRoute ніколи не запускає транскрибування на основі цих метаданих: перевірені репліки копіюються до описаного результату разом із джерелом, упевненістю та інтервалом і відтворюються як ненадійні спостереження поряд із підписами кадрів. Некоректний текст, текст поза допустимим діапазоном або текст без відомостей про походження відхиляється, а не змішується з потоком підписів. Наразі поле `source` оголошується викликувачем, а не перевіряється сервером: OmniRoute гарантує, що значення є одним із трьох дозволених рядків, але поки що не підтверджує криптографічно, що позначка `embedded` або `audio-bridge` справді надійшла від видобування, яким керує сервер. Вважайте `source` ненадійною підказкою, доки не буде реалізовано таку перевірку; не будуйте на ньому рішення щодо авторизації.

Досвідчений викликач може надати вже авторизовану доріжку `audioTranscript`
для того самого відео. Рівень об’єднання виконує візуальні й аудіоспостереження
в межах одного кінцевого терміну та сигналу переривання, упорядковує їх на спільній
часовій шкалі, згортає точні дублікати й повертає частковий результат, якщо успішною
є лише одна зі сторін. Недійсний `audioTranscript` призводить до такого часткового
результату — візуальний опис зберігається, а аудіогілка записує очищений код помилки —
замість збою обробки всього відео. Доступність кожної гілки, ознака часткового
результату та очищені коди помилок зберігаються в результаті опису, у метаданих
захисних обмежень (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), у метаданих кешу результатів і в лічильниках
об’єднання моста. Стандартний шлях Video Bridge не викликає перетворення мовлення
на текст і не завантажує другу копію медіафайлу; без явно наданої доріжки він
залишається суто відеорежимом.

**Зберігання транскрипту (#12150 P1).** Це застосовується автоматично щоразу, коли
Video Bridge (який сам потребує явного ввімкнення) відтворює репліку транскрипту —
окремої ознаки зберігання немає. Коли запит відтворює будь-яку репліку транскрипту
(оголошений викликачем `transcript` або об’єднаний `audioTranscript`), захисне
обмеження позначає його як `videoBridgeObserved` і створює редаговану тіньову копію
опису відео — ідентичне відтворення, у якому довільний текст кожної репліки замінено
на `[redacted-video-transcript]`. Цю копію створюють шляхом підстановки в
структуроване поле репліки до формування рядка (а не аналізом зведеного тексту,
тому жоден вміст репліки — зловмисний або звичайний, зокрема текст, що містить
`]`, як-от `[inaudible]`/`[music]`, — не може зберегтися). У збереженому тілі
запиту журналу викликів кожна отримана з відео текстова частина замінюється цією
редагованою тіньовою копією на основі збігу вмісту; прив’язка `fullText` повторно
зчитується із завершеного корисного навантаження захисних обмежень перед викликом,
тож збіг зберігається навіть після того, як наступні захисні обмеження ланцюжка
(маскувальники персональних даних і облікових даних із пріоритетами 10/95)
перезапишуть текст опису на місці, а впровадження системної підказки, передавання
контексту або пам’яті змінить структуру масиву повідомлень. Тіло, надіслане моделі,
не змінюється. Спостережуваний запит також не заповнює довготривалу Memory
(видобування як із запиту, так і з відповіді пропускається), тому власна відповідь
моделі не може продублювати текст транскрипту в Memory.

**Необроблені поля відео (#12430).** Коли міст увімкнено, а підтримка нативного відео невідома або відсутня, визначені поля `transcript`/`audioTranscript` також активують `videoBridgeObserved`, навіть після помилки опису або перевищення обмеження `maxVideos`. Значення `null` і порожні рядки враховуються; відсутні поля та метадані, не пов’язані з відео, — ні. У збережених копіях ці поля редагуються або запит вилучається, а кеші/Memory обходяться. Корисне навантаження постачальника залишається незмінним.

Для додаткових збережених копій використовується той самий сигнал спостережуваного
запиту. У необробленому знімку клієнтського запиту до застосування захисних
обмежень, незавершеному запиті в пам’яті та журналі завчасно відхилених запитів
поля транскрипту в частинах відео замінюються структурно; рядкові підказки,
сформовані етапами конвеєра та під час передавання контексту, редагуються в точці
збереження тіла запиту. Збережений маркер `video_content_removed` змушує
продовження через `previous_response_id` завершуватися безпечною відмовою замість
відновлення тексту, який було навмисно видалено. Якщо спостережуваний запит втрачає
свою тіньову копію для редагування окремої частини до журналювання або якщо навіть
одна з кількох тіньових копій відео не збігається після подальших змін запиту,
збережене тіло запиту вилучається повністю, щоб не зберігати частково редагований
транскрипт.

Для спостережуваного запиту відповідь моделі може цитувати будь-яку частину
транскрипту без структурованої межі репліки. Тому її збережене поле `responseBody`
у журналі викликів замінюється маркером вилучення; докладний артефакт конвеєра
(який може містити тіла upstream- і клієнтських повідомлень та фрагменти потоку)
не зберігається. Семантичний кеш, кеш ідемпотентності та кеш повторного відтворення
міркувань не використовуються для читання й запису цього запиту. Запит до
постачальника та видима клієнту відповідь залишаються незмінними. Ранні байти
keepalive видаляються з тимчасового буфера, коли докладний артефакт вилучається.
Попередження Kiro про некоректний EventStream повідомляє лише кількість байтів
корисного навантаження й ніколи не містить ані самого вмісту, ані необробленої
помилки JSON-парсера.
Це не означає, що було перевірено кожну непов’язану діагностику постачальника або
плагіна; ширше охоплення збережених точок приймання даних відстежується в #11658.

Внутрішній життєвий цикл `/api/modality-bridge/video/drilldown` є окремою,
автентифікованою за loopback/token кешувальною інфраструктурою. Кожна операція
також потребує канонічного непрозорого ідентифікатора принципала. Перш ніж
увімкнути виробничий викликач, він має отримувати цей ID з автентифікованого
тенанта й ніколи не передавати значення, вибране клієнтом. Ключі кешу прив’язують
цього принципала до канонічних ідентифікаторів сеансу та посилання на відео,
зберігають лише ключі, отримані за допомогою SHA-256, і обмежують як читання, так
і видалення тим самим принципалом. Кеш зберігає не більше 16 похідних JPEG-кадрів
на запис, видаляє їх через десять хвилин і підтримує обмежені читання `start`/`end`
або явне видалення сеансу.

Для кожного принципала встановлено обмеження в 16 записів і 64 MiB канонічних
JPEG-даних. Ці обмеження не залежать від глобальної верхньої межі в 64 записи/256
MiB: тиск квоти принципала спочатку витісняє лише найдавніше використовувані
записи цього принципала, і лише потім розглядається глобальне LRU-витіснення.
Під час операцій із кешем прострочені записи вилучаються з обліку як принципала,
так і глобального обліку, тоді як скасування та помилка валідації не фіксують
часткову заміну.

Кеш відхиляє неканонічний Base64, надлишкове доповнення, медіадані не у форматі JPEG, пошкоджені або
усічені JPEG, а також JPEG, які спричиняють попередження під час обмеженого декодування повного зображення за допомогою `sharp`.
Кожне прийняте зображення повторно кодується як канонічний JPEG, його ширина й висота визначаються
з декодованих байтів, а не з полів, наданих викликачем, а будь-які кінцеві
поліглотні байти відкидаються замість збереження. До обох квот зараховується лише обмежений
канонічний стиснений буфер. Обмеження для передавання JSON враховує накладні витрати Base64 для граничного
розміру декодованих вхідних даних у 32 MiB. Кожна
збережена похідна сутність містить підтверджені формат і роздільну здатність JPEG, політику семплювання,
версію похідної сутності, час створення, обчислений сервером хеш вмісту, хешоване посилання
на батьківський об’єкт, а також хеш вмісту батьківського об’єкта від довіреного викликача. Скасування перевіряється
між асинхронними етапами декодування й хешування до атомарної фіксації в кеші.

Цей етап ще не підключає робочий джерельний компонент до маршруту й не
забезпечує вибір варіантів із різною роздільною здатністю. Тому прозорий шлях запиту
Video Bridge не виконує додаткової роботи, тоді як виведення прив’язаної до орендаря
приналежності та повний життєвий цикл FU-08 із підтримкою кількох роздільних здатностей залишаються явно визначеною подальшою роботою,
а не поведінкою, задокументованою як завершена.

Кадри послідовно описуються налаштованою моделлю Video. Порожнє
перевизначення Video успадковує налаштування Vision; якщо обидва значення порожні, автоматичний
маршрутизатор Vision вибирає фактичну модель із підтримкою зору. Успішні описи
замінюють початкову частину стабільним префіксом `[Video description:`, який також
позначає текст як ненадійне спостереження, отримане з медіаданих, і вказує наступним
моделям не виконувати інструкції, знайдені в медіаданих. Ключі кешу описів кадрів
включають байти JPEG, підказку, позначку часу та фактичну модель; кешуються лише успішні
описи. Записи кешу зберігають фактичну модель-виробника, яка успішно виконала операцію,
зокрема резервну модель; міст повідомляє `mixed`, коли різні кадри
були створені різними моделями. Влучання в кеш повторно використовує ідентичність цього виробника
замість її перепозначення як запитаного плану маршрутизації. Кеш результату
для всього відео має ключ, сформований з усіх вхідних даних, що змінюють результат: підказки, фактичної
моделі, політики семплювання, кількості кадрів, режиму семантичного аналізу, відбитка SHA-256
нормалізованої підказки щодо фокуса, вікна фокуса, `transcript`,
`audioTranscript` і прапорця контактного аркуша — тому зміна будь-якого з цих
вимірів спричиняє промах кешу, а не повторне використання застарілих даних. Версія політики
візуальної дедуплікації, поріг і обмежена кількість кадрів-кандидатів також явно включені до
ключа й метаданих кешу результатів; отже, зміна політики не може повторно використати застарілий
опис усього відео. Метадані кешу результатів v4 зберігають режим і
відбиток, але ніколи не зберігають необроблене завдання користувача. Метадані захисного механізму повідомляють як
запитаний, так і фактичний режими аналізу; запитаний режим `focused` без
придатного користувацького тексту позначається як фактично `full`.

Захисний механізм видобуває всі підтримувані частини відео, але описує не більше ніж
`modalityBridgeVideoMaxVideos`. Для цільового об’єкта, щодо якого доведено, що
`supportsVideo === false`, невдалі відео та відео понад ліміт перетворюються на явні безпечні
текстові маркери, щоб необроблене відео не збереглося. Якщо можливості невідомі, ці частини
залишаються без змін. Цільові об’єкти з `supportsVideo === true` обходять міст.
Сигнал переривання клієнтського запиту поширюється через завантаження, чергу брокера,
підпроцеси та виклики створення описів; переривання зупиняють обробку між відео й ніколи не допускають
аварійного переходу до необроблених медіаданих.

Налаштування середовища виконання зберігаються в БД і перевіряються за допомогою Zod:

| Ключ                                | Значення за замовчуванням | Діапазон / поведінка                                                                                                     |
| ----------------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `modalityBridgeVideoEnabled`        | `false`                   | Необов’язкове середовище виконання, потребує явного ввімкнення                                                           |
| `modalityBridgeVideoAnalysisMode`   | `"full"`                  | `full` зберігає загальні описи; `focused` використовує обмежений ненадійний контекст останнього повідомлення користувача |
| `modalityBridgeVideoModel`          | `""`                      | Успадковує модель Vision Bridge                                                                                          |
| `modalityBridgeVideoFrameCount`     | `8`                       | 1–16                                                                                                                     |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`               | `uniform`, `scene_aware` або пропорційний `segment_aware`; у разі збою детектора використовується `uniform`              |
| `modalityBridgeVideoMaxVideos`      | `1`                       | 1–4                                                                                                                      |
| `modalityBridgeVideoTimeout`        | `120000`                  | 1000–120000 ms                                                                                                           |

Застарілі збережені значення тайм-ауту Video, що перевищують 120 секунд, обмежуються
кінцевим терміном брокера; нові записи налаштувань понад цю межу відхиляються.
`GET /api/modality-bridge/video/runtime` вимагає довіреної локальності loopback, підтвердженої штампом,
до автентифікації або перевірки середовища виконання, а потім вимагає автентифікації
керування. Він повертає лише `available`, очищені версії FFmpeg/ffprobe та фіксовану
причину, коли середовище виконання недоступне. Внутрішня кінцева точка видобування не є
публічним API завантаження: насичення черги повертає `503` разом із `Retry-After`, від’єднання
викликача повертає `499`, а фіксований кінцевий термін брокера повертає `504`. Перетворені відповіді додають
`video->text;model=<visionModel>;parts=<videos>` до централізованого
заголовка `x-omniroute-modality-bridge`, не видаляючи сегменти Vision або Audio.

### Маскувальник PII (`piiMasker.ts`)

Працює на **обох** етапах.

- **`preCall`** клонує корисне навантаження, обходить `system`, `messages`, `input` і
  `prompt` (включно з елементами у вигляді простих рядків) та застосовує `processPII()` (з
  `@/shared/utils/inputSanitizer`) до рядкових полів `content`/`text`. Коли
  `PII_REDACTION_ENABLED=true`, виявлені персональні дані редагуються у вихідному
  корисному навантаженні. Це не залежить від `INPUT_SANITIZER_MODE` (який керує лише
  політикою щодо інʼєкцій у промпти). Коли редагування вимкнено, виклик записує
  кількість виявлень, не змінюючи вміст.
- **`postCall`** виконує глибоке клонування відповіді, запускає `sanitizePIIResponse()`, а також
  маскувальник структури Responses API (`maskResponsesOutput` — охоплює
  `output_text` і `output[].content[].text`). Якщо відбувається будь-яке редагування,
  змінена відповідь замінює оригінальну.

Захисний механізм ніколи не блокує; він лише додає анотації (`meta.detections`,
`meta.redacted`) або перезаписує дані.

### Інʼєкція у промпти (`promptInjection.ts`)

Виявляє ворожі структури в наданому користувачем вмісті та застосовує
налаштовану політику. Поведінка визначається змінними середовища та параметрами
конструктора:

| Налаштування     | Змінна середовища                                                                                           | Типове значення | Вплив                                                                                                                                                                                                                 |
| ---------------- | ----------------------------------------------------------------------------------------------------------- | --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Увімкнено        | `INPUT_SANITIZER_ENABLED`                                                                                   | `true`          | Коли `false`, захисний механізм негайно завершує обробку.                                                                                                                                                             |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                             | `warn`          | Політика щодо інʼєкцій: `block`, `warn` або `log`. (`redact` підтримується для зворотної сумісності, але **не** видаляє текст інʼєкції; перезапис персональних даних у запиті контролюється `PII_REDACTION_ENABLED`.) |
| Поріг блокування | Параметр `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдонім `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`          | Мінімальний рівень серйозності, необхідний для блокування. За типових налаштувань середній рівень передбачає лише спостереження.                                                                                      |

**Пріоритет режимів** (`getMode`): `options.mode`, наданий викликачем →
**перевизначення прапорцем функції в БД** для `INJECTION_GUARD_MODE` (Панель керування → Налаштування →
Прапорці функцій) → змінна середовища `INJECTION_GUARD_MODE` → змінна середовища `INPUT_SANITIZER_MODE` →
`warn`. Таким чином, перевизначення через панель керування має пріоритет над змінними середовища, тому інтерфейс
прапорців функцій керує активним захисним механізмом у реальному часі (без перезапуску). Читання з БД є відмовостійким:
у разі помилки захисний механізм повертається до поведінки на основі змінних середовища, а якщо
перевизначення не задано, поведінка ідентична визначенню лише за змінними середовища.

Джерела виявлення:

1. `sanitizeRequest()` з `@/shared/utils/inputSanitizer` (спільний набір детекторів,
   який використовується в інших частинах конвеєра).
2. Вбудовані `DEFAULT_GUARD_PATTERNS` (наразі `system_override_inline` і
   `markdown_system_block`, обидва з рівнем серйозності `high`).
3. Необовʼязкові `customPatterns`, передані через параметри конструктора (рядки, регулярні вирази
   або записи `{ name, pattern, severity }`).

Коли `mode === "block"` **і** принаймні одне виявлення відповідає порогу
серйозності, `preCall` повертає `{ block: true, message: "Запит відхилено:
виявлено підозрілий вміст" }`. У режимах `warn`/`log` захисний механізм веде журнал, але
дозволяє виклик. Спільний допоміжний засіб `evaluatePromptInjection()` також експортується
для викликачів, яким потрібно оцінювати промпти без використання реєстру.

**Межа сканування (v3.8.20):** детектор перевіряє лише **перші 16 КБ**
обʼєднаного тексту промпту — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байти) у
`src/shared/utils/inputSanitizer.ts`. І `detectInjection()`, і
`evaluatePromptInjection()` застосовують `slice(0, MAX_INJECTION_SCAN_BYTES)` перед запуском
циклу шаблонів. Директиви інʼєкції розташовуються ближче до початку вхідних даних, тому це
обмежує використання ЦП регулярними виразами та навантаження на збирання сміття для корисних навантажень розміром у сотні КБ, не послаблюючи виявлення (див.
#3932, #4041).

### Маскувальник облікових даних (`credentialMasker.ts`)

Виконується на **обох** етапах, останнім у типовому ланцюжку (пріоритет `95`). Редагує
відомі шаблони ключів API / секретних токенів у вихідному корисному навантаженні (вміст
повідомлень, аргументи викликів інструментів, результати інструментів) **і** у відповіді постачальника, щоб
облікові дані, вставлені в промпт (або повернуті результатом інструмента), не потрапили
до зовнішнього постачальника чи назад до клієнта.

- **Лише за явної згоди**, за тією самою домовленістю, що й редагування PII (поруч із жорстким правилом №20):
  вимкнено, якщо тільки `settings.credentialRedactionEnabled === true` **або**
  `CREDENTIAL_REDACTION_ENABLED=true`. Коли функцію вимкнено, захисний механізм нічого не робить —
  він ніколи не блокує й не переписує.
- `redactCredentials()` обходить усе дерево корисного навантаження/відповіді (`walkValue()`,
  із захистом від забруднення прототипу та безпечним опрацюванням циклів через `WeakSet`) і замінює збіги
  заповнювачем `[REDACTED:<type>]`, клонуючи лише ті гілки, які фактично
  змінилися.
- `CREDENTIAL_PATTERNS` охоплює ключі постачальників LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токени VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платіжні ключі (Stripe, Square), хмарні
  ключі (ключ доступу AWS, Twilio, SendGrid, Mailgun), приватні ключі / JWT,
  рядки підключення, що містять облікові дані (`mongodb://user:pass@...` тощо), а також
  загальний шаблон значення заголовка `Authorization`/`x-api-key`/`api-key`/`apikey`.
  Ключі у форматі заголовків (`authorization`, `x-api-key`, `api-key`,
  `apikey`) редагуються структурно (лише значення, зі збереженням префікса схеми на кшталт
  `Bearer `/`Basic `), а не за допомогою загального регулярного виразу для тексту.
- Захисний механізм ніколи не блокує; він лише переписує (`modifiedPayload` /
  `modifiedResponse`) та додає анотації (`meta.credentialsRedacted`, `meta.count`).

Захист від регресій: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовий контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true перериває ланцюжок
  message?: string; // відображається під час блокування
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // повертається preCall для перезапису запиту
  modifiedResponse?: TValue; // повертається postCall для перезапису відповіді
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Захисний механізм сигналізує про «відсутність змін», повертаючи `void`, `{}` або
`{ block: false }`. Повернення `modifiedPayload`/`modifiedResponse` замінює
значення, що передається ланцюжком до наступних захисних механізмів.
`signal?: AbortSignal` передає життєвий цикл виклику до захисних механізмів. Переривання запиту є навмисним винятком із принципу fail-open: медіамости припиняють роботу й виконують очищення, не відновлюючи необроблені медіадані для цільової системи, яка, як відомо, їх не підтримує.

## Реєстр (`registry.ts`)

Синглтон `guardrailRegistry` надає:

- `register(guardrail)` — додає (або замінює за нормалізованим ім'ям) захисний механізм та пересортовує за зростанням `priority`.
- `clear()` / `list()` — допоміжні функції адміністрування.
- `runPreCallHooks(payload, context)` — ітерує активні захисні механізми, пропускає `payload` через `modifiedPayload` і зупиняється на першому `block: true`.
- `runPostCallHooks(response, context)` — той самий потік на стороні відповіді.
- `resetGuardrailsForTests({ registerDefaults })` — очищає стан та, за бажанням, повторно реєструє значення за замовчуванням для чистої ізоляції тестів.

Обидва виконавці повертають `{ blocked, payload|response, results, guardrail?, message? }`, де `results` — це масив записів `GuardrailExecutionResult`, що містять поля `blocked`, `skipped`, `modified`, `error` та `meta` для кожного захисного механізму, корисні для трасування.

### Вимкнення захисних механізмів для кожного запиту

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` агрегує дедуплікований список імен захисних механізмів, які слід пропустити для поточного запиту. Джерела (всі необов'язкові, всі об'єднані):

- `apiKeyInfo.disabledGuardrails`
- Тіло запиту `disabledGuardrails` (верхнього рівня)
- Тіло запиту `metadata.disabledGuardrails`
- Заголовок `x-omniroute-disabled-guardrails` (або застарілий `x-disabled-guardrails`)

Значення можуть бути масивами рядків або рядком, розділеним комами; імена нормалізуються до нижнього регістру в kebab-case (`pii_masker` → `pii-masker`). Результат передається через `context.disabledGuardrails` до реєстру, який пропускає відповідні захисні механізми (`skipped: true` у `results`).

## Порядок виконання

Для кожного запиту, що проходить через `src/sse/handlers/chat.ts` та
`open-sse/handlers/chatCore.ts`:

1.  `resolveDisabledGuardrails(...)` створює список винятків з ключа API, тіла запиту
    та заголовків.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` запускає захисні механізми у порядку
    зростання пріоритету:
    - Вимкнені захисні механізми записуються як `skipped`.
    - `preCall` кожного захисного механізму може переписати корисне навантаження
      через `modifiedPayload`.
    - Перший `block: true` перериває ланцюжок, і обробник повертає
      відповідь про відхилення захисним механізмом.
3.  (Потенційно переписане) корисне навантаження надходить до комбінованої маршрутизації
    та вихідної диспетчеризації.
4.  Після формування відповіді `guardrailRegistry.runPostCallHooks(...)`
    запускає той самий ланцюжок на відповіді. `block: true` тут відкидає
    вихідну відповідь.

Захисні механізми, які викликають помилку, записуються з `error: <message>` та
реєструються через `logger.warn`, але ланцюжок продовжується — за задумом,
система працює за принципом "відмова-відкриття".

## Конфігурація

Змінні середовища, які читаються вбудованими захисними механізмами:

| Змінна                                | Використовується               | Ефект                                                                                                          |
| :------------------------------------ | :----------------------------- | :------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`             | Встановіть `false`, щоб повністю вимкнути виявлення.                                                           |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`             | Політика ін'єкцій: `warn`, `block` або `log`. Застаріле значення `redact` не переписує текст ін'єкції.         |
| `INJECTION_GUARD_MODE`                | `prompt-injection`             | Режим для захисту від ін'єкцій; також прапорець функції БД, який **перевизначає** змінні середовища (БД > ЗМ). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`             | Мінімальна серйозність, при якій `MODE=block` відхиляє: `high` (за замовчуванням), `medium` або `low`.         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`             | Застарілий псевдонім для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                    |
| `PII_REDACTION_ENABLED`               | `pii-masker`                   | Якщо `true`, PII запиту редагується (незалежно від режиму ін'єкції).                                           |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (нижче за течією) | Контролює поведінку маскувальника на стороні відповіді.                                                        |

Захисні механізми Modality Bridge читають конфігурацію часу виконання зі сховища
налаштувань на основі БД (`getSettings()`), а не зі змінних середовища.
Основними ключами Vision є `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` та `modalityBridgeCacheMaxEntries`.
Застарілі ключі `visionBridge*` приймаються лише як задокументований
одноцикловий резервний варіант читання; записи на панелі керування
використовують основні ключі. Значення за замовчуванням та резервний
розв'язувач знаходяться в `src/shared/constants/modalityBridgeDefaults.ts`,
а застарілі константи зберігаються в
`src/shared/constants/visionBridgeDefaults.ts`.

Аудіо використовує `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` та `modalityBridgeAudioMaxClips`, а також спільні
налаштування `modalityBridgeCache*`. Аудіо не має резервного варіанту
застарілих ключів, оскільки ці ключі були введені зі схемою Modality Bridge.

Відео використовує `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`, `modalityBridgeVideoFrameCount`,
`modalityBridgeVideoSamplingPolicy`, `modalityBridgeVideoMaxVideos` та
`modalityBridgeVideoTimeout`, а також спільні налаштування `modalityBridgeCache*`.
Він вимкнений за замовчуванням, оскільки FFmpeg/ffprobe є необов'язковими
операційними залежностями, а створення субтитрів кадрів додає затримку та
витрати на модель.

## Користувацькі обмежувачі (Guardrails)

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Кроки:

1.  Створіть `src/lib/guardrails/myGuardrail.ts`, розширюючи `BaseGuardrail`.
2.  Реалізуйте `preCall` та/або `postCall`.
3.  Зареєструйте під час імпорту (виштовхніть з `registerDefaultGuardrails`) або
    викличте `guardrailRegistry.register(...)` під час виконання — реєстр замінює
    будь-який попередній обмежувач з тим самим нормалізованим ім'ям.
4.  Додайте тести до `tests/unit/` (існуючі приклади:
    `tests/unit/guardrails-registry.test.ts`,
    `tests/unit/prompt-injection-guard.test.ts`,
    `tests/unit/guardrails/visionBridge.test.ts`).

## Тестування

Використовуйте `resetGuardrailsForTests()` між тестами, щоб почати з відомого стану.
Передайте `{ registerDefaults: false }`, щоб почати з порожнього реєстру та
зареєструвати лише обмежувачі, що тестуються. Vision Bridge приймає впровадження
залежностей (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge надає
еквівалентні точки для налаштувань, можливостей, вибору моделі STT, перевірок
облікових даних та транскрипції. Таким чином, тести можуть перевіряти обидва
потоки без доступу до БД або мережі.

## Покриття маршрутів захисту від ін'єкцій та червона команда (Фаза 8 · Блок D)

Захист від ін'єкцій (`createInjectionGuard` / `withInjectionGuard`) охоплює всі маршрути,
які приймають підказки користувача. Він враховує `INJECTION_GUARD_MODE` (за замовчуванням `warn` = лише логування;
`block` = повертає HTTP 400 `SECURITY_001`).

| Тип              | Маршрути                                                                                                                                             | Режим за замовчуванням |
| :--------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------- |
| Текст (існуючий) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                   |
| Генеративний     | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                   |
| Дані             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                   |

Вилучення тексту (`extractMessageContents`) охоплює `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Червона команда (нічна, `nightly-llm-security.yml`):** promptfoo перевіряє, що кожен маршрут блокує
корпус OWASP-LLM у режимі `INJECTION_GUARD_MODE=block`; garak запускає зонди (пропускає без секрету).
`moderations` включено для послідовності — оператори в режимі блокування можуть виключити його через
`resolveDisabledGuardrails`.

Нічний робочий процес (`.github/workflows/nightly-llm-security.yml`, cron + ручний
запуск) має два завдання:

- **`promptfoo-guard` (блокування)** — запускає `promptfoo eval -c promptfooconfig.yaml`
  з `INJECTION_GUARD_MODE=block`. Кожен ворожий випадок (наприклад, "ігнорувати всі
  попередні інструкції...", "jailbreaks" у стилі DAN) стверджує, що відповідь містить
  `error.code === "SECURITY_001"`, тобто обмежувач фактично відхилив запит.
- **`garak` (консультативний)** — запускає garak `--probes promptinject,dan,leakreplay`
  проти локального екземпляра OmniRoute (`http://localhost:20128/v1`). Залежить від
  секрету провайдера (`PROMPTFOO_PROVIDER_KEY`); пропускається без помилок і має суфікс
  `|| true`, тому він звітує без збою CI.

Покриття допоміжного обмежувача (`createInjectionGuard` / `withInjectionGuard`)
охоплює кожен маршрут `/v1`, що містить підказки; текст підказки витягується з
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` за допомогою
`extractMessageContents()` у `src/shared/utils/inputSanitizer.ts`.
