## மேலோட்டம்

அனைத்து OmniRoute மேலாண்மை API வழிகளும் மூன்று பாதுகாப்பு
அடுக்குகளில் ஒன்றாக வகைப்படுத்தப்படுகின்றன. வகைப்பாடு நிலையானது,
`src/server/authz/routeGuard.ts`-இல் வரையறுக்கப்பட்டு, வேறு எந்த அங்கீகாரக்
கிளையும் இயங்குவதற்கு முன் மதிப்பீடு செய்யப்படுகிறது.

## அடுக்குகள்

### அடுக்கு 1 — LOCAL_ONLY

**செயல்படுத்தப்படுவது:** `isLocalOnlyPath(path)` → loopback host சரிபார்ப்பு  
**தவிர்க்கும் வழி:** இயல்புநிலையில் எதுவுமில்லை. கோரிக்கையில் `manage` scope கொண்ட செல்லுபடியாகும் API key இருக்கும்போது, `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-இல் உள்ள பாதைகளுக்கு மட்டும் குறுகிய விதிவிலக்கு வழங்கப்படும் ([Manage-scope விதிவிலக்கு](#manage-scope-carve-out) என்பதைப் பார்க்கவும்).

இந்த வழித்தடங்கள் child process-களைத் தொடங்குகின்றன அல்லது runtime code-ஐ இயக்குகின்றன. இவற்றை loopback அல்லாத போக்குவரத்திற்கு வெளிப்படுத்துவது, செல்லுபடியாகும் JWT-ஐப் பெற்ற தாக்குநரை (எ.கா., Cloudflared/Ngrok tunnel வழியாக) process-களைத் தொடங்க அனுமதிக்கும் — இது அறியப்பட்ட ஒரு CVE வகையாகும் ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj என்பது என்ன (தாக்குதல் வகை):** ஒரு management/agent server, subprocess ஒன்றைத் தொடங்கும் endpoint-ஐ வெளிப்படுத்துகிறது (`npm install`, `node`, ஒரு browser, ஒரு proxy, `git`, `tar`, …). அந்த endpoint-ஐ host-க்கு வெளியிலிருந்து அணுக முடிந்தால் — operator, OmniRoute-ஐ nginx/Cloudflare/Tailscale tunnel-க்குப் பின்னால் வைத்திருந்து JWT கசிந்துவிட்டாலோ, அல்லது authentication தவறாக உள்ளமைக்கப்பட்டிருந்தாலோ — தாக்குநர் "API ஒன்றை அழைப்பது" என்பதை "host-இல் command ஒன்றை இயக்குவது" ஆக மாற்றிவிடுகிறார் (remote code execution). Process-ஐத் தொடங்கக்கூடிய ஒவ்வொரு route-இலும், **எந்த authentication சரிபார்ப்புக்கும் முன்பாக, நிபந்தனையின்றி loopback host சரிபார்ப்பைச் செயல்படுத்துவதன் மூலம்** OmniRoute இதைத் தடுக்கிறது: tunnel வழியாக token கசிந்தாலும், அந்த spawn செயல்பாட்டை இன்னும் அணுக முடியாது.

**முழுமையான LOCAL_ONLY தொகுப்பு.** அதிகாரப்பூர்வ மூலம் `src/server/authz/routeGuard.ts`-இல் உள்ள `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ஆகும்; கீழுள்ள அட்டவணை தற்போதைய நிலையைப் பிரதிபலிக்கிறது. `check-route-guard-membership` gate, spawn திறனுள்ள prefix-களின் கீழுள்ள ஒவ்வொரு `route.ts`-ஐயும் பட்டியலிட்டு, அவற்றில் ஏதேனும் ஒன்று local-only என வகைப்படுத்தப்படவில்லை என்றால் CI-ஐத் தோல்வியடையச் செய்கிறது.

#### நிர்வாக வரம்புக்கான விதிவிலக்கு

LOCAL_ONLY பாதைகளின் ஒரு துணைத்தொகுதியை, கோரிக்கையில் `Authorization: Bearer <api-key>`
இருந்து, அதன் மெட்டாடேட்டாவில் `manage` வரம்பு (அல்லது `admin`) இருந்தால் மட்டுமே,
லூப்பேக் அல்லாத இடத்திலிருந்தும் அணுகலாம். இந்த விதிவிலக்கு ஒவ்வொரு பாதைக்கும்
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` மூலம் வெளிப்படையாகக் கட்டுப்படுத்தப்படுகிறது;
எனவே எந்தப் புதிய LOCAL_ONLY பாதைக்கும் இயல்புநிலை கடுமையான லூப்பேக்-மட்டும் என்பதாகவே
இருக்கும். அங்கீகரிக்கப்படாத கோரிக்கைகளும் நிர்வாக வரம்பு இல்லாத விசைகளைக் கொண்ட
கோரிக்கைகளும் தொடர்ந்து `403 LOCAL_ONLY` உடன் நிராகரிக்கப்படும்.

தற்போது விதிவிலக்கு அளிக்கக்கூடிய ஒரே முன்னொட்டு `/api/mcp/` ஆகும். `/api/cli-tools/runtime/`

தொடங்கக்கூடியவை என்பதால் வேண்டுமென்றே விலக்கப்பட்டுள்ளன; இதுவே LOCAL_ONLY அடுக்கு
தடுக்க உருவாக்கப்பட்டுள்ள துல்லியமான CVE வகையாகும்.

#### இயக்குநர் வழிகாட்டுதலும் தணிக்கையும்

நீங்கள் OmniRoute ஐ ரிவர்ஸ் ப்ராக்ஸி அல்லது டன்னல் (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) பின்னால் இயக்கினாலும், மேலே உள்ள செயல்முறை-தொடக்கத்
திறனுள்ள வழித்தடங்களை லூப்பேக் சோதனை தொடர்ந்து பாதுகாக்கும் — கிளையன்ட் முகவரி
லூப்பேக் அல்லாத ஒரு கோரிக்கை, **அங்கீகாரம் செயல்படுவதற்கு முன்பே**
`403 LOCAL_ONLY` உடன் நிராகரிக்கப்படும்; எனவே கசிந்த JWT ஒன்றால் செயல்முறையைத்
தொடங்கும் இடத்தை அணுக முடியாது. இரண்டு இயக்குநர் பொறுப்புகள் இன்னும் உள்ளன:

- **கிளையன்ட் IP-ஐ loopback ஆகப் போலியாக்கி 403-ஐ "சரிசெய்ய" வேண்டாம்.**
  `X-Forwarded-For: 127.0.0.1` என அமைப்பது அல்லது மூல முகவரியை
  loopback ஆக மாற்றியெழுதும் proxy-ஐப் பயன்படுத்துவது, இந்த அடுக்கு தடுக்கும் அதே RCE
  வகையை மீண்டும் திறந்துவிடும். Dashboard/API-ஐ proxy வழியாக வெளிப்படுத்துங்கள் —
  spawn செய்யக்கூடிய routes-ஐ ஒருபோதும் வெளிப்படுத்தாதீர்கள்.
- **manage-scope bypass-ஐக் குறைந்தபட்சமாக வைத்திருங்கள்.** `/api/mcp/` மட்டுமே bypass
  செய்யக்கூடியது, அதுவும் `manage`-scope கொண்ட API key மூலம் மட்டுமே.
  `SPAWN_CAPABLE_PREFIXES`-ஐ bypass பட்டியலில் ஒருபோதும் சேர்க்க முடியாது — zod schema
  அவற்றை நிராகரிக்கிறது, மேலும் runtime-இல் `isLocalOnlyBypassableByManageScope`
  அவற்றை மறுக்கிறது (பல-அடுக்கு பாதுகாப்பு); இதைத்தான் dashboard
  "bypass செய்யக்கூடியதாக மாற்ற முடியாது" எனக் குறிப்பிடுகிறது. சேமிக்கப்பட்ட settings
  row-இலிருந்து runtime snapshot loader இத்தகைய உள்ளீடுகளையும் நீக்கிவிடுகிறது; மேலும்
  பழைய JSON import (`/api/settings/import-json`) bypass keys-ஐ ஒருபோதும் எழுதாது.
  ஒவ்வொரு `LOCAL_ONLY_API_PREFIXES` உள்ளீடும் deny-list-இல் இருக்க வேண்டும் அல்லது
  bypass-க்கு தகுதியானதா என மதிப்பாய்வு செய்யப்பட்டிருக்க வேண்டும்
  (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). `/api/providers/`-இன் கீழுள்ள
  dynamic-segment மற்றும் static-path spawn செய்யக்கூடிய routes (எ.கா. `/login`,
  `/refresh-cursor`) ஆகியவை
  `src/shared/constants/spawnCapablePrefixes.ts`-இல் உள்ள regex அடிப்படையிலான
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` துணையால்
  கையாளப்படுகின்றன; தட்டையான `SPAWN_CAPABLE_PREFIXES` array மூலம் அல்ல — அவற்றைக்
  கண்டறிய அந்தத் தட்டையான array முழு `/api/providers/` prefix-ஐ உள்ளடக்க வேண்டியிருக்கும்;
  இது provider CRUD-க்காக remote dashboards நியாயமாகப் பயன்படுத்தும் route tree-ஐ
  அளவுக்கு அதிகமாக விரிவுபடுத்திவிடும்.

**அணுகலைத் தணிக்கை செய்தல்** — host-க்கு வெளியிலிருந்து எதுவும் இந்த routes-ஐ
அடையவில்லை என்பதைச் சரிபார்க்க:

- `/dashboard/settings/security`-இல் உள்ள **Authorization Inventory**-ஐத் திறக்கவும்:
  அது செயலில் உள்ள LOCAL_ONLY prefix பட்டியல், bypass செய்யக்கூடிய prefixes மற்றும்
  compile-time spawn செய்யக்கூடிய ("bypass செய்யக்கூடியதாக மாற்ற முடியாது") தொகுப்பைக்
  காட்டுகிறது.
- மேலே உள்ள prefixes-ஐ loopback அல்லாத client address-உடன் இணைத்துத் தேட உங்கள்
  reverse-proxy / access logs-இல் grep செய்யவும். `403 LOCAL_ONLY` என்பதற்குப் பதிலாக
  `200` வழங்கிய அத்தகைய hit ஏதேனும் இருந்தால், proxy உண்மையான client IP-ஐ
  மறைக்கிறது என்று பொருள் — proxy-ஐச் சரிசெய்யவும்.
- இந்த paths-இல் ஒன்றுக்காக OmniRoute logs-இல் தோன்றும் `403 LOCAL_ONLY` என்பது guard
  திட்டமிட்டபடி செயல்படுவதைக் குறிக்கிறது; மறைக்க வேண்டிய பிழை அல்ல.

### புதிய நிறுவலின் bootstrap உண்மையான peer அடிப்படையில் loopback-க்கு மட்டுமே — `Host` அடிப்படையில் அல்ல

`src/shared/utils/apiAuth.ts`-இல் உள்ள `isAuthRequired()` பெயரில்லா bootstrap-ஐ

signals மூலம் தீர்மானிக்கப்படுகிறது: token-stamp செய்யப்பட்ட உண்மையான TCP peer
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, policy காண்பது), pipeline-இன் சொந்த
`AUTHZ_HEADER_PEER_LOCALITY` தீர்ப்பு (route handlers காண்பது; `OMNIROUTE_PEER_STAMP_TOKEN`
அமைக்கப்பட்டிருக்கும்போது மட்டுமே நம்பப்படும்), அல்லது நேரடி callers-க்கான உண்மையான socket
peer. `Host` / `nextUrl.hostname` ஒருபோதும் பயன்படுத்தப்படுவதில்லை; முதல் password write
(`POST /api/settings/require-login`) ஒவ்வொரு network peer-க்கும் திறந்துவிடப்படாமல் இதே
கட்டுப்பாட்டின் கீழ் உள்ளது (GHSA-7pq4-8pvv-rx7r). `managementPolicy` தனது சொந்த
`peerContext` தீர்ப்பை வெளிப்படையாகக் கீழ்நிலைக்கு அனுப்புவதால், ORIGINAL (strip செய்வதற்கு
முந்தைய) request-இன் headers அதை ஒருபோதும் தீர்மானிப்பதில்லை.

### அடுக்கு 3 — MANAGEMENT (இயல்புநிலை)

மற்ற அனைத்து management routes-உம் இதில் அடங்கும். `requireLogin=false` என
அமைக்கப்படாதவரை authentication தேவை. CLI tokens இந்த routes-இல் authenticate செய்ய
முடியும் (loopback + செல்லுபடியாகும் HMAC).

## மதிப்பீட்டு வரிசை

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → அடுத்த படிக்குச் செல்
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → அனுமதி (management_key)
     → இல்லையெனில்                                → நிராகரி 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → அனுமதி (system)
  3. hasValidCliToken(headers)?
     → அனுமதி (cli) [loopback + timingSafeEqual HMAC சரிபார்ப்பு]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → அனுமதி (dashboard_session)
     → தளர்த்த முடியாத பாதையில் manage-scope Bearer உள்ளதா?
        → அனுமதி (management_key)
     → நிராகரி 401/403
  5. requireLogin=false?
     → அனுமதி (anonymous)
```

படி 1-இன் manage-scope கிளை மட்டுமே LOCAL_ONLY வழித்தடத்தைப் பூர்த்திசெய்யக்கூடிய அங்கீகரிக்கப்பட்ட பாதையாகும்; காலாவதியான DB அமைதியாக "deny" நிலைக்குத் தாழ்த்தப்படாமல் இருக்க, auth-backend தோல்வி நிலை 503-ஐத் (403 அல்ல) திருப்பியளிக்கிறது.

## உருவாக்கும் திறனுள்ள புதிய வழித்தடத்தைச் சேர்த்தல்

1. `src/server/authz/routeGuard.ts`-இல் உள்ள `LOCAL_ONLY_API_PREFIXES`-க்குப் பாதை முன்னொட்டைச் சேர்க்கவும்
2. புதிய முன்னொட்டுக்கு `isLocalOnlyPath()` true-ஐத் திருப்பியளிக்கிறது என்பதை உறுதிப்படுத்தும் சோதனையை `tests/unit/authz/routeGuard.test.ts`-இல் சேர்க்கவும்
3. **இந்தப் படியை ஒருபோதும் தவிர்க்க வேண்டாம்** — `CLAUDE.md`-இல் உள்ள கடுமையான விதி #15-ஐப் பார்க்கவும்
4. முடிவெடுக்கவும்: இந்த வழித்தடம் `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-லும் இடம்பெற வேண்டுமா?
   இயல்புநிலைப் பதில் **இல்லை**. manage-scope வைத்திருப்பவருக்கு இந்த வழித்தடத்தை வெளிப்படுத்துவது பாதுகாப்பானதாக இருக்கும்போது மட்டுமே இதைத் தேர்வுசெய்யவும் (அதாவது, பயனர் கட்டுப்படுத்தும் தன்னிச்சையான குறியீட்டை இது உருவாக்கக் கூடாது).

## manage-scope மூலம் தளர்த்தக்கூடிய பாதையைச் சேர்த்தல்

1. இந்த வழித்தடம் பயனர் வழங்கிய குறியீடு அல்லது கட்டளைகளைச் செயல்படுத்தவில்லை என்பதை உறுதிப்படுத்தவும். அவ்வாறு செயல்படுத்தினால், நிறுத்தவும் — இந்த விதிவிலக்கு அதற்கான சரியான கருவி அல்ல.
2. `src/server/authz/routeGuard.ts`-இல் உள்ள `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-க்கு முன்னொட்டைச் சேர்க்கவும்
3. பின்வரும் நான்கு கோரிக்கை வடிவங்களுக்கும் `tests/unit/authz/management-policy.test.ts`-இல் சோதனைகளைச் சேர்க்கவும்: Bearer இல்லை (403), manage Bearer (அனுமதி), non-manage Bearer (403), மேலும் manage Bearer இருந்தாலும் `/api/cli-tools/runtime/*` strict-loopback ஆகவே இருப்பதை உறுதிப்படுத்தும் ஒவ்வொரு முன்னொட்டுக்குமான பின்னடைவு சோதனை.

## OpenAPI-இல் பாதுகாப்பு அடுக்குகளை ஆவணப்படுத்துதல்

`docs/openapi.yaml`-இல் புதிய வழித்தடத்தைச் சேர்க்கும்போது, அந்த வழித்தடம் `routeGuard.ts` மூலம் வகைப்படுத்தப்பட்டிருந்தால், அதற்குரிய vendor extension-ஐப் பயன்படுத்தவும்:

| routeGuard.ts வகைப்பாடு                 | YAML குறிப்பு              | அமலாக்கம்                                                |
| --------------------------------------- | -------------------------- | -------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`               | `x-loopback-only: true`    | non-loopback-இலிருந்து நிபந்தனையின்றித் தடுக்கப்படும்    |
| `ALWAYS_PROTECTED_API_PATHS`            | `x-always-protected: true` | `requireLogin=false` ஆக இருந்தாலும் அங்கீகாரம் தேவை      |
| உள் admin/debug வழித்தடம்               | `x-internal: true`         | இயல்பாக /dashboard/api-endpoints-இலிருந்து மறைக்கப்படும் |
| எதுவுமில்லை (பொது / நிலையான அங்கீகாரம்) | (குறிப்பு தேவையில்லை)      | நிலையான `requireLogin`-ஆல் கட்டுப்படுத்தப்படும் அணுகல்   |

### சரிபார்ப்பு

YAML குறிப்புகளுக்கும் `routeGuard.ts`-க்கும் இடையிலான ஒத்திசைவை இரண்டு scripts அமல்படுத்துகின்றன:

- `scripts/check/check-openapi-coverage.mjs` — coverage < 99% எனில் தோல்வியடையும்
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` அல்லது
  `x-always-protected` குறிப்புகள் compile-time மாறிலிகளிலிருந்து வேறுபட்டால் தோல்வியடையும்

இரண்டு scripts-உம் pre-commit hook-இலும் CI-இலும் இயங்குகின்றன.

### தவறான நேர்மறை விதி

`routeGuard.ts` மாறிலியில் இல்லாத ஒரு வழித்தடத்தில் `x-always-protected` அல்லது `x-loopback-only` குறிக்கப்பட்டிருந்தால், coverage script தோல்வியடையும். `routeGuard.ts` உண்மையில் அமல்படுத்துவதுடன் YAML-ஐ ஒத்திசைப்பதே எப்போதும் சரியான தீர்வு — அமலாக்கத் தர்க்கத்தையும் சேர்க்காமல் `routeGuard.ts`-க்கு வழித்தடங்களைச் சேர்ப்பது தீர்வல்ல.
