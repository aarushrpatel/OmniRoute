## Descripción general

Todas las rutas de la API de administración de OmniRoute se clasifican en uno de tres niveles de
protección. La clasificación es estática, se define en `src/server/authz/routeGuard.ts`
y se evalúa antes de que se ejecute cualquier otra rama de autenticación.

## Niveles

### Nivel 1 — LOCAL_ONLY

**Aplicado mediante:** `isLocalOnlyPath(path)` → comprobación del host de loopback  
**Omisión:** Ninguna de forma predeterminada. Excepción limitada para las rutas incluidas en
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` cuando la solicitud contiene una clave de
API válida con el ámbito `manage` (consulte [Excepción para el ámbito manage](#manage-scope-carve-out)).

Estas rutas generan procesos secundarios o ejecutan código en tiempo de ejecución. Exponerlas al
tráfico que no procede de loopback permitiría que un atacante que hubiera obtenido un JWT válido (p. ej.,
a través de un túnel de Cloudflared/Ngrok) activara la generación de procesos, una clase conocida de
CVE ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Qué es GHSA-fhh6-4qxv-rpqj (la clase de ataque):** un servidor de administración/agente
expone un endpoint que inicia un subproceso (`npm install`, `node`, un navegador,
un proxy, `git`, `tar`, …). Si se puede acceder a ese endpoint desde fuera del host — porque
el operador colocó OmniRoute detrás de un túnel de nginx/Cloudflare/Tailscale y se filtró un JWT,
o la autenticación estaba mal configurada —, el atacante convierte «llamar a una API» en «ejecutar un
comando en el host» (ejecución remota de código). OmniRoute evita esto aplicando una
**comprobación del host de loopback de forma incondicional, antes de cualquier comprobación de autenticación**, en todas las
rutas capaces de generar procesos: un token filtrado a través de un túnel sigue sin poder acceder a la generación de procesos.

**El conjunto LOCAL_ONLY completo.** La fuente oficial es
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` en
`src/server/authz/routeGuard.ts`; la tabla siguiente refleja el estado actual. La
puerta `check-route-guard-membership` enumera cada `route.ts` bajo los
prefijos capaces de generar procesos y hace que la CI falle si alguno no está clasificado como solo local.

#### Excepción para el ámbito de administración

Un subconjunto de rutas LOCAL_ONLY TAMBIÉN PUEDE ser accesible desde direcciones que no sean de bucle local si y
solo si la solicitud incluye un `Authorization: Bearer <api-key>` cuyos
metadatos contengan el ámbito `manage` (o `admin`). La excepción se habilita
explícitamente por ruta mediante `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, por lo que el
valor predeterminado para cualquier ruta LOCAL_ONLY nueva sigue siendo el acceso estricto desde el bucle local. Las solicitudes
no autenticadas y las solicitudes con claves sin permisos de administración se siguen rechazando con
`403 LOCAL_ONLY`.

Actualmente, el único prefijo que admite la excepción es `/api/mcp/`. `/api/cli-tools/runtime/` y
`/api/services/` se excluyen intencionadamente porque pueden iniciar
subprocesos arbitrarios (`npm install`, `node`), que constituyen exactamente la clase de CVE que el
nivel LOCAL_ONLY pretende evitar.

**#7895 — ámbito limitado `mcp:connect`:** la excepción de `/api/mcp/` TAMBIÉN acepta
una clave Bearer que contenga el ámbito limitado `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), comprobado mediante
`hasMcpConnectOrManageScope()` en `src/server/authz/policies/management.ts`.
Esto se limita ÚNICAMENTE a `/api/mcp/`: `mcp:connect` no concede ningún permiso en ninguna otra
ruta de administración (incluidos todos los demás prefijos de excepción LOCAL_ONLY, si alguna vez
se añadiera alguno) y se excluye deliberadamente de
`MANAGEMENT_API_KEY_SCOPES`. Una clave que contenga `manage`/`admin` sigue superando la
excepción exactamente igual que antes; `mcp:connect` es una alternativa con menos privilegios
para clientes MCP remotos que no deberían necesitar un acceso de administración amplio.

| Solicitud                                          | Ruta                       | Resultado                    |
| -------------------------------------------------- | -------------------------- | ---------------------------- |
| Sin bucle local, sin Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY               |
| Sin bucle local, Bearer con ámbito `manage`        | `/api/mcp/*`               | Permitir                     |
| Sin bucle local, Bearer con ámbito `mcp:connect`   | `/api/mcp/*`               | Permitir                     |
| Sin bucle local, Bearer sin `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY               |
| Sin bucle local, Bearer con ámbito `mcp:connect`   | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY               |
| Sin bucle local, Bearer con ámbito `manage`        | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY               |
| Bucle local, con cualquier Bearer o sin él         | cualquier LOCAL_ONLY       | Permitir (supera la barrera) |

#### Orientación para operadores y auditoría

Si ejecuta OmniRoute detrás de un proxy inverso o un túnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), la comprobación de bucle local sigue protegiendo las rutas anteriores
capaces de iniciar procesos: una solicitud cuya dirección de cliente no sea de bucle local se rechaza con
`403 LOCAL_ONLY` **antes de que se ejecute la autenticación**, por lo que un JWT filtrado no puede iniciar ningún proceso. Siguen
existiendo dos responsabilidades para el operador:

- **No «solucione» un error 403 falsificando la IP del cliente como loopback.** Configurar
  `X-Forwarded-For: 127.0.0.1`, o usar un proxy que reescriba la dirección de origen como
  loopback, vuelve a abrir exactamente la clase de RCE que este nivel bloquea. Exponga el
  panel/API a través del proxy, pero nunca las rutas capaces de iniciar procesos.
- **Mantenga al mínimo la omisión mediante el ámbito manage.** Solo se puede omitir `/api/mcp/`, y
  únicamente con una clave de API con ámbito `manage`. Los `SPAWN_CAPABLE_PREFIXES` nunca pueden
  añadirse a la lista de omisión: el esquema zod los rechaza e
  `isLocalOnlyBypassableByManageScope` los deniega en tiempo de ejecución (defensa en profundidad),
  que es a lo que se refiere el panel con «no se puede permitir su omisión». El cargador de
  instantáneas en tiempo de ejecución también descarta dichas entradas de una fila de configuración
  almacenada, y la importación JSON heredada (`/api/settings/import-json`) nunca escribe las claves
  de omisión. Cada entrada de `LOCAL_ONLY_API_PREFIXES` debe estar en la lista de denegación o
  revisarse como apta para omisión (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Las rutas
  capaces de iniciar procesos con segmentos dinámicos y rutas estáticas bajo `/api/providers/`
  (p. ej., `/login`, `/refresh-cursor`) están cubiertas por los elementos complementarios basados en
  expresiones regulares `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` de
  `src/shared/constants/spawnCapablePrefixes.ts`, no por el array plano
  `SPAWN_CAPABLE_PREFIXES`: el array plano tendría que abarcar todo el prefijo
  `/api/providers/` para detectarlas, lo que ampliaría en exceso un árbol de rutas
  que los paneles remotos utilizan legítimamente para las operaciones CRUD de proveedores.

**Auditoría del acceso** — para verificar que nada externo al host esté accediendo a estas rutas:

- Abra el **Inventario de autorización** en `/dashboard/settings/security`: muestra la
  lista activa de prefijos LOCAL_ONLY, qué prefijos permiten omisión y el conjunto de rutas
  capaces de iniciar procesos determinado en tiempo de compilación («no se puede permitir su omisión»).
- Busque en los registros del proxy inverso o de acceso los prefijos anteriores asociados con una
  dirección de cliente que no sea loopback. Cualquier acceso de este tipo que haya devuelto `200` en
  lugar de `403 LOCAL_ONLY` significa que el proxy está ocultando la IP real del cliente: corrija el proxy.
- Un `403 LOCAL_ONLY` en los registros de OmniRoute para una de estas rutas indica que la protección
  funciona según lo previsto, no un error que deba suprimirse.

### Nivel 2 — ALWAYS_PROTECTED

**Aplicado por:** `isAlwaysProtectedPath(path)` → omite la elusión `requireLogin=false`
**Omisión:** Ninguna cuando `requireLogin=false`; siempre se requiere JWT

Estas rutas son destructivas o irreversibles. Permitirlas en una instalación «sin contraseña»
implicaría que cualquier persona de la misma LAN podría borrar la base de datos o finalizar el
proceso del servidor.

| Ruta                                      | Motivo                                                                |
| ----------------------------------------- | --------------------------------------------------------------------- |
| `/api/shutdown`                           | Finaliza el proceso del servidor                                      |
| `/api/settings/database`                  | Exportación, importación y borrado de la base de datos                |
| `/api/db-backups`                         | Acceso al archivo completo de copia de seguridad de la base de datos  |
| `/api/settings/export-json`               | Exporta el bloque completo de configuración (incluidos los secretos)  |
| `/api/settings/import-json`               | Reemplaza el bloque completo de configuración                         |
| `/api/providers/health-autopilot/actions` | Ejecuta acciones correctivas del piloto automático                    |
| `/api/settings/obsidian`                  | Emite credenciales WebDAV reutilizables para cualquier raíz de bóveda |

**Respuesta ante una infracción:** `401 Authentication required`

`/api/settings/obsidian` abarca su ruta secundaria `/webdav`: `POST` dirige el servicio de archivos WebDAV —
servido por la capa personalizada de Node antes de Next.js, fuera de esta canalización— hacia una raíz
elegida por el solicitante y devuelve credenciales Basic recién emitidas, `DELETE` las rota y el `POST`
del elemento principal almacena el token de la API REST de Obsidian. GHSA-62vw solo ocultó la revelación
de la contraseña mediante `GET`; la emisión seguía estando en el nivel con apertura en caso de fallo
(GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` además rechaza una bóveda que sea el directorio de
datos, esté dentro de él o lo contenga.

### El arranque de una instalación nueva está limitado a loopback, según el par real, no `Host`

Cuando no hay ninguna contraseña de administración configurada (ni `INITIAL_PASSWORD`), `isAuthRequired()` en
`src/shared/utils/apiAuth.ts` mantiene abierto el arranque anónimo **solo para pares loopback**.
El estado loopback se determina a partir de las señales de confianza del par, en este orden: el par TCP real
marcado mediante token (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, lo que ve la política), el veredicto
`AUTHZ_HEADER_PEER_LOCALITY` de la propia canalización (lo que ven los controladores de rutas, y en lo que solo
se confía mientras `OMNIROUTE_PEER_STAMP_TOKEN` esté definido) o el par real del socket para solicitantes
directos. Nunca se consultan `Host` ni `nextUrl.hostname`, y la escritura de la primera contraseña
(`POST /api/settings/require-login`) está sujeta a la misma restricción, en lugar de estar abierta a todos
los pares de la red (GHSA-7pq4-8pvv-rx7r). `managementPolicy` transmite explícitamente su propio veredicto
`peerContext`, de modo que los encabezados de la solicitud ORIGINAL (antes de eliminarlos) nunca lo determinan.

### Nivel 3 — MANAGEMENT (predeterminado)

Todas las demás rutas de administración. Se requiere autenticación salvo que se haya configurado
`requireLogin=false`. Los tokens de CLI pueden autenticar estas rutas (loopback + HMAC válido).

## Orden de evaluación

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → continuar
     → no loopback, Bearer con ámbito manage
        AND isLocalOnlyBypassableByManageScope   → permitir (management_key)
     → de lo contrario                           → rechazar 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → permitir (system)
  3. hasValidCliToken(headers)?
     → permitir (cli) [loopback + comprobación HMAC con timingSafeEqual]
  4. isAlwaysProtectedPath(path) o requireLogin=true?
     → isDashboardSessionAuthenticated?
        → permitir (dashboard_session)
     → ¿Bearer con ámbito manage en una ruta no eludible?
        → permitir (management_key)
     → rechazar 401/403
  5. requireLogin=false?
     → permitir (anonymous)
```

La rama del ámbito manage del paso 1 es la única ruta autenticada que puede satisfacer una
ruta LOCAL_ONLY; el modo de fallo del backend de autenticación devuelve 503 (no 403), para que una
base de datos caducada no se degrade silenciosamente a «denegar».

## Añadir una nueva ruta con capacidad de iniciar procesos

1. Añada el prefijo de la ruta a `LOCAL_ONLY_API_PREFIXES` en
   `src/server/authz/routeGuard.ts`
2. Añada una prueba en `tests/unit/authz/routeGuard.test.ts` que verifique que
   `isLocalOnlyPath()` devuelve true para el nuevo prefijo
3. **Nunca omita este paso** — consulte la regla estricta n.º 15 en `CLAUDE.md`
4. Decida: ¿esta ruta TAMBIÉN debe incluirse en `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   La respuesta predeterminada es **no**. Inclúyala solo cuando sea seguro exponer la ruta a un
   titular del ámbito manage (es decir, cuando NO inicie código arbitrario controlado por el usuario).

## Añadir una ruta eludible mediante el ámbito manage

1. Confirme que la ruta no ejecuta código ni comandos proporcionados por el usuario. Si lo
   hace, deténgase: esta excepción no es la herramienta adecuada.
2. Añada el prefijo a `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` en
   `src/server/authz/routeGuard.ts`
3. Añada cobertura en `tests/unit/authz/management-policy.test.ts` para las cuatro
   formas de solicitud: sin Bearer (403), Bearer con ámbito manage (permitir), Bearer sin ámbito manage
   (403) y la regresión por prefijo que garantiza que `/api/cli-tools/runtime/*` siga
   restringida estrictamente a loopback incluso con un Bearer con ámbito manage.

## Documentación de los niveles de seguridad en OpenAPI

Al añadir una nueva ruta a `docs/openapi.yaml`, aplique la extensión de proveedor
correspondiente si la ruta está clasificada por `routeGuard.ts`:

| Clasificación de routeGuard.ts            | Anotación YAML             | Aplicación                                                        |
| ----------------------------------------- | -------------------------- | ----------------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                 | `x-loopback-only: true`    | Bloqueada incondicionalmente para conexiones que no sean loopback |
| `ALWAYS_PROTECTED_API_PATHS`              | `x-always-protected: true` | Se requiere autenticación incluso con `requireLogin=false`        |
| Ruta interna de administración/depuración | `x-internal: true`         | Oculta de /dashboard/api-endpoints de forma predeterminada        |
| Ninguna (pública/autenticación estándar)  | (no se necesita anotación) | Acceso estándar controlado por `requireLogin`                     |

### Validación

Dos scripts garantizan la coherencia entre las anotaciones YAML y `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — falla si la cobertura es < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — falla si las anotaciones
  `x-loopback-only` o `x-always-protected` difieren de las constantes en tiempo de compilación

Ambos scripts se ejecutan en el hook de pre-commit y en CI.

### Regla de falsos positivos

Si `x-always-protected` o `x-loopback-only` está anotado en una ruta que NO se encuentra en
la constante de `routeGuard.ts`, el script de cobertura falla. La solución siempre consiste en alinear el
YAML con lo que `routeGuard.ts` aplica realmente, no en añadir rutas a `routeGuard.ts`
sin implementar también la lógica de aplicación.
