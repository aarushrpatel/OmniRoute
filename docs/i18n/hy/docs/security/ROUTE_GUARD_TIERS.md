## Ընդհանուր ակնարկ

OmniRoute-ի կառավարման API-ի բոլոր երթուղիները դասակարգվում են պաշտպանության երեք
մակարդակներից մեկում։ Դասակարգումը ստատիկ է, սահմանված է `src/server/authz/routeGuard.ts`-ում
և գնահատվում է նախքան նույնականացման որևէ այլ ճյուղի գործարկումը։

## Մակարդակներ

### Մակարդակ 1 — LOCAL_ONLY

**Կիրառվում է՝** `isLocalOnlyPath(path)` → loopback հոսթի ստուգում  
**Շրջանցում՝** Լռելյայն՝ չկա։ Սահմանափակ բացառություն է նախատեսված
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ում ներառված ուղիների համար, երբ հարցումը պարունակում է
`manage` scope-ով վավեր API բանալի (տե՛ս [Manage-scope բացառությունը](#manage-scope-carve-out))։

Այս երթուղիները ստեղծում են դուստր գործընթացներ կամ կատարում են runtime կոդ։ Դրանք
ոչ loopback տրաֆիկի համար հասանելի դարձնելը վավեր JWT ձեռք բերած հարձակվողին (օրինակ՝
Cloudflared/Ngrok թունելի միջոցով) թույլ կտար գործարկել գործընթացների ստեղծում՝ հայտնի CVE
դաս ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj))։

**Ինչ է GHSA-fhh6-4qxv-rpqj-ը (հարձակման դասը)՝** կառավարման/գործակալային սերվերը
հասանելի է դարձնում endpoint, որը գործարկում է ենթագործընթաց (`npm install`, `node`, դիտարկիչ,
պրոքսի, `git`, `tar`, …)։ Եթե այդ endpoint-ը հասանելի է հոսթից դուրս, քանի որ
օպերատորը OmniRoute-ը տեղադրել է nginx/Cloudflare/Tailscale թունելի հետևում, և JWT-ն
արտահոսել է, կամ նույնականացումը սխալ է կազմաձևվել, ապա հարձակվողը «կանչել API»-ն վերածում է «հոսթի վրա
հրաման գործարկելու» (հեռավար կոդի կատարում)։ OmniRoute-ը կանխում է դա՝ գործընթաց ստեղծելու ունակությամբ յուրաքանչյուր
երթուղու համար **անվերապահորեն՝ նույնականացման ցանկացած ստուգումից առաջ, կիրառելով loopback հոսթի ստուգում**.
թունելի միջոցով արտահոսած token-ը միևնույն է չի կարող հասնել գործընթացի ստեղծմանը։

**LOCAL_ONLY-ի ամբողջական բազմությունը։** Հեղինակավոր աղբյուրներն են
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`-ը՝
`src/server/authz/routeGuard.ts`-ում. ստորև բերված աղյուսակն արտացոլում է ընթացիկ վիճակը։
`check-route-guard-membership` դարպասը թվարկում է գործընթաց ստեղծելու ունակությամբ
նախածանցների տակ գտնվող յուրաքանչյուր `route.ts` և ձախողում է CI-ը, եթե դրանցից որևէ մեկը դասակարգված չէ որպես միայն տեղային։

**Պատասխան խախտման դեպքում՝** `403 LOCAL_ONLY`

#### Կառավարման տիրույթի բացառություն

LOCAL_ONLY ուղիների ենթաբազմությունը ԿԱՐՈՂ Է հասանելի լինել նաև ոչ loopback հասցեներից, եթե և
միայն եթե հարցումը պարունակում է `Authorization: Bearer <api-key>`, որի
մետատվյալները ներառում են `manage` տիրույթը (կամ `admin`)։ Բացառությունը
յուրաքանչյուր ուղու համար բացահայտորեն կառավարվում է `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ի միջոցով, որպեսզի
ցանկացած նոր LOCAL_ONLY ուղու լռելյայն վարքագիծը մնա խիստ loopback-ով սահմանափակված։ Չնույնականացված
հարցումները և ոչ կառավարման բանալիներով հարցումները շարունակում են մերժվել
`403 LOCAL_ONLY`-ով։

Այս պահին բացառությունը թույլատրող միակ նախածանցը `/api/mcp/`-ն է։ `/api/cli-tools/runtime/`-ը և
`/api/services/`-ը միտումնավոր բացառված են, քանի որ կարող են գործարկել կամայական
ենթագործընթացներ (`npm install`, `node`), ինչը հենց այն CVE դասն է, որը կանխելու համար
գոյություն ունի LOCAL_ONLY մակարդակը։

**#7895 — `mcp:connect` նեղ տիրույթ՝** `/api/mcp/` բացառությունը ՆԱԵՎ ընդունում է
նեղ `mcp:connect` տիրույթն ունեցող Bearer բանալի
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), որը ստուգվում է
`src/server/authz/policies/management.ts`-ի `hasMcpConnectOrManageScope()`-ի միջոցով։
Սա սահմանափակված է ՄԻԱՅՆ `/api/mcp/`-ով. `mcp:connect`-ը որևէ թույլտվություն չի տալիս կառավարման որևէ այլ
երթուղու համար (ներառյալ LOCAL_ONLY բացառության ցանկացած այլ նախածանց, եթե երբևէ այդպիսիք
ավելացվեն), և այն միտումնավոր բացառված է
`MANAGEMENT_API_KEY_SCOPES`-ից։ `manage`/`admin` ունեցող բանալին նախկինի պես
անցնում է բացառությունը. `mcp:connect`-ը նվազ արտոնություններով այլընտրանք է
հեռակա՝ միայն MCP օգտագործող կանչողների համար, որոնց կառավարման լայն հասանելիություն անհրաժեշտ չէ։

#### Օպերատորի ուղեցույց և աուդիտ

Եթե OmniRoute-ը գործարկում եք հակադարձ պրոքսիի կամ թունելի հետևում (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), loopback-ի ստուգումը շարունակում է պաշտպանել վերևում նշված՝
գործարկում կատարելու ունակ երթուղիները. այն հարցումը, որի հաճախորդի հասցեն loopback չէ, մերժվում է
`403 LOCAL_ONLY`-ով՝ **նախքան նույնականացման գործարկումը**, ուստի արտահոսած JWT-ն չի կարող հասնել
գործարկման գործողությանը։ Օպերատորի երկու պարտականություն մնում է.

- **Մի՛ փորձեք «շտկել» 403-ը՝ հաճախորդի IP հասցեն կեղծելով որպես loopback։** Սահմանելով
  `X-Forwarded-For: 127.0.0.1` կամ օգտագործելով proxy, որը սկզբնաղբյուրի հասցեն վերագրում է որպես
  loopback, կրկին բացվում է հենց այն RCE դասը, որը փակում է այս մակարդակը։ Proxy-ի միջոցով հասանելի դարձրեք
  dashboard/API-ն, բայց երբեք՝ գործընթաց ստեղծելու ունակ երթուղիները։
- **Պահպանեք manage շրջանակի շրջանցումը նվազագույն։** Միայն `/api/mcp/`-ն է հնարավոր շրջանցել, և
  միայն `manage` շրջանակով API բանալիով։ `SPAWN_CAPABLE_PREFIXES`-ը երբեք չի կարող
  ավելացվել շրջանցման ցանկում․ zod սխեման մերժում է դրանք, իսկ
  `isLocalOnlyBypassableByManageScope`-ը կատարման ժամանակ արգելում է դրանք (բազմաշերտ պաշտպանություն),
  ինչն էլ dashboard-ում նկատի է առնվում «cannot be made bypassable» արտահայտությամբ։ Կատարման ժամանակի
  snapshot բեռնիչը նաև հեռացնում է նման գրառումները պահված կարգավորումների տողից, իսկ
  հին JSON ներմուծումը (`/api/settings/import-json`) երբեք չի գրանցում շրջանցման բանալիները։
  `LOCAL_ONLY_API_PREFIXES`-ի յուրաքանչյուր գրառում պետք է կամ լինի արգելման ցանկում, կամ
  ստուգված լինի որպես շրջանցման համար թույլատրելի (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`)։ Դինամիկ հատվածներով
  և ստատիկ ուղիներով՝ գործընթաց ստեղծելու ունակ երթուղիները `/api/providers/`-ի ներքո (օրինակ՝ `/login`,
  `/refresh-cursor`) ներառված են regex-ի վրա հիմնված `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` ուղեկցող սահմանումների միջոցով՝
  `src/shared/constants/spawnCapablePrefixes.ts`-ում, այլ ոչ թե հարթ
  `SPAWN_CAPABLE_PREFIXES` զանգվածի միջոցով․ դրանք հայտնաբերելու համար հարթ զանգվածը պետք է ներառեր
  ամբողջ `/api/providers/` նախածանցը՝ չափազանց լայնացնելով այն երթուղիների ծառը,
  որը հեռակա dashboard-ներն օրինաչափորեն օգտագործում են provider-ների CRUD գործողությունների համար։

**Մուտքի աուդիտ** — ստուգելու համար, որ արտաքին հոսթերից ոչինչ չի հասնում այս երթուղիներին․

- Բացեք **Authorization Inventory**-ն `/dashboard/settings/security`-ում․ այն ցուցադրում է
  ընթացիկ LOCAL_ONLY նախածանցների ցանկը, թե որ նախածանցներն են շրջանցելի, և կոմպիլյացիայի ժամանակ սահմանված՝
  գործընթաց ստեղծելու ունակ («cannot be made bypassable») հավաքածուն։
- Ձեր reverse-proxy-ի / մուտքի մատյաններում grep-ով որոնեք վերը նշված նախածանցները՝ զուգակցված
  ոչ loopback հաճախորդի հասցեի հետ։ Ցանկացած նման հարցում, որը `403 LOCAL_ONLY`-ի փոխարեն վերադարձրել է
  `200`, նշանակում է, որ proxy-ն քողարկում է հաճախորդի իրական IP-ն․ շտկեք proxy-ն։
- Այս ուղիներից որևէ մեկի համար OmniRoute-ի մատյաններում առկա `403 LOCAL_ONLY`-ը նշանակում է, որ պաշտպանիչ
  մեխանիզմն աշխատում է նախատեսվածի պես, այլ ոչ թե սխալ է, որը պետք է թաքցնել։

որը սպասարկվում է հատուկ Node շերտի կողմից՝ Next.js-ից առաջ և այս pipeline-ից դուրս — ուղղում է հարցում կատարողի ընտրած արմատին
և վերադարձնում է նոր ստեղծված Basic հավատարմագրերը, `DELETE`-ը փոխարինում է դրանք, իսկ ծնող `POST`-ը պահպանում է
Obsidian REST API token-ը։ GHSA-62vw-ն միայն քողարկել էր `GET`-ով գաղտնաբառի բացահայտումը․ տրամադրումը
դեռևս fail-open մակարդակում էր (GHSA-7pq4-8pvv-rx7r)։ `enableObsidianVaultSync()`-ը նաև
մերժում է այն vault-ը, որը տվյալների գրացուցակն է, գտնվում է դրա ներսում կամ պարունակում է այն։

### Նոր տեղադրման bootstrap-ը միայն loopback-ի համար է՝ ըստ իրական peer-ի, ոչ թե `Host`-ի

Երբ կառավարման գաղտնաբառ կազմաձևված չէ (և չկա `INITIAL_PASSWORD`), `isAuthRequired()`-ը
`src/shared/utils/apiAuth.ts`-ում անանուն bootstrap-ը բաց է պահում **միայն loopback peer-ների համար**։
Loopback-ը որոշվում է վստահելի peer ազդանշաններից՝ հետևյալ հերթականությամբ․ token-ով դրոշմված իրական TCP peer-ը
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, որը տեսնում է քաղաքականությունը), pipeline-ի սեփական
`AUTHZ_HEADER_PEER_LOCALITY` որոշումը (որը տեսնում են երթուղիների մշակիչները և վստահելի է միայն այն ժամանակ, երբ
`OMNIROUTE_PEER_STAMP_TOKEN`-ը սահմանված է), կամ ուղղակի կանչողների իրական socket peer-ը։ `Host`-ը /
`nextUrl.hostname`-ը երբեք հաշվի չեն առնվում, իսկ առաջին գաղտնաբառի գրանցումը
(`POST /api/settings/require-login`) ենթակա է նույն սահմանափակմանը՝ բոլոր
ցանցային peer-ների համար բաց լինելու փոխարեն (GHSA-7pq4-8pvv-rx7r)։ `managementPolicy`-ն իր սեփական `peerContext` որոշումը
բացահայտորեն փոխանցում է ներքև, այնպես որ ՍԿԶԲՆԱԿԱՆ (մինչև հեռացումը) հարցման header-ները երբեք չեն որոշում այն։

### Մակարդակ 3 — MANAGEMENT (լռելյայն)

Կառավարման մյուս բոլոր երթուղիները։ Նույնականացում է պահանջվում, եթե կազմաձևված չէ
`requireLogin=false`։ CLI token-ները կարող են նույնականացնել այս երթուղիների հարցումները (loopback + վավեր HMAC)։

## Գնահատման հերթականությունը

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → անցնել հաջորդ քայլին
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → թույլատրել (management_key)
     → հակառակ դեպքում                           → մերժել 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → թույլատրել (system)
  3. hasValidCliToken(headers)?
     → թույլատրել (cli) [loopback + timingSafeEqual HMAC ստուգում]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → թույլատրել (dashboard_session)
     → manage-scope Bearer չշրջանցվող ուղու վրա?
        → թույլատրել (management_key)
     → մերժել 401/403
  5. requireLogin=false?
     → թույլատրել (anonymous)
```

Քայլ 1-ի manage-scope ճյուղը նույնականացված միակ ուղին է, որը կարող է բավարարել
LOCAL_ONLY երթուղու պահանջները․ auth-backend-ի խափանման ռեժիմը վերադարձնում է 503 (ոչ թե 403), որպեսզի
ժամկետանց DB-ն աննկատ չանցնի «մերժել» ռեժիմի։

## Նոր՝ spawn-ի հնարավորություն ունեցող երթուղու ավելացում

1. Ուղու նախածանցն ավելացրեք `LOCAL_ONLY_API_PREFIXES`-ում՝
   `src/server/authz/routeGuard.ts`
2. `tests/unit/authz/routeGuard.test.ts`-ում ավելացրեք թեստ, որը հաստատում է, որ
   `isLocalOnlyPath()`-ը նոր նախածանցի համար վերադարձնում է true
3. **Երբեք բաց մի թողեք այս քայլը** — տե՛ս Hard Rule #15-ը `CLAUDE.md`-ում
4. Որոշեք՝ արդյո՞ք այս երթուղին ՆԱԵՎ պետք է լինի `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ում։
   Լռելյայն պատասխանը **ոչ** է։ Ներառեք միայն այն դեպքում, երբ երթուղին անվտանգ է
   manage-scope կրողին հասանելի դարձնելու համար (այսինքն՝ ՉԻ գործարկում օգտատիրոջ կողմից կառավարվող կամայական կոդ)։

## Manage-scope-ով շրջանցվող ուղու ավելացում

1. Համոզվեք, որ երթուղին չի կատարում օգտատիրոջ տրամադրած կոդը կամ հրամանները։ Եթե
   կատարում է, կանգ առեք․ այս բացառությունը ճիշտ գործիք չէ։
2. Նախածանցն ավելացրեք `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ին՝
   `src/server/authz/routeGuard.ts`
3. `tests/unit/authz/management-policy.test.ts`-ում ավելացրեք ծածկույթ հարցման բոլոր չորս
   ձևերի համար՝ առանց Bearer-ի (403), manage Bearer (թույլատրել), ոչ manage Bearer
   (403), ինչպես նաև ըստ նախածանցի ռեգրեսիոն թեստ, որը հաստատում է, որ `/api/cli-tools/runtime/*`-ը
   մնում է խիստ loopback՝ նույնիսկ manage Bearer-ի առկայության դեպքում։

| -------------------------------------------- | --------------------------------------------------- |

| `src/server/authz/policies/management.ts`    | Գնահատման տրամաբանություն                           |

| `tests/unit/authz/management-policy.test.ts` | evaluate()-ի միավորային թեստեր                      |

## Անվտանգության մակարդակների փաստաթղթավորումը OpenAPI-ում

`docs/openapi.yaml`-ում նոր երթուղի ավելացնելիս կիրառեք համապատասխան
մատակարարի ընդլայնումը, եթե երթուղին դասակարգված է `routeGuard.ts`-ի կողմից․

| routeGuard.ts դասակարգում                | YAML նշագրում              | Կիրառում                                                           |
| ---------------------------------------- | -------------------------- | ------------------------------------------------------------------ |
| `LOCAL_ONLY_API_PREFIXES`                | `x-loopback-only: true`    | Անվերապահորեն արգելափակվում է non-loopback-ից                      |
| `ALWAYS_PROTECTED_API_PATHS`             | `x-always-protected: true` | Նույնականացումը պարտադիր է նույնիսկ `requireLogin=false`-ի դեպքում |
| Ներքին admin/debug երթուղի               | `x-internal: true`         | Լռելյայն թաքցված է /dashboard/api-endpoints-ից                     |
| Չկա (հանրային / ստանդարտ նույնականացում) | (նշագրում անհրաժեշտ չէ)    | Ստանդարտ՝ `requireLogin`-ով կառավարվող հասանելիություն             |

### Վավերացում

Երկու սկրիպտ ապահովում են YAML նշագրումների և `routeGuard.ts`-ի համապատասխանությունը․

- `scripts/check/check-openapi-coverage.mjs` — ձախողվում է, եթե ծածկույթը < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — ձախողվում է, եթե `x-loopback-only` կամ
  `x-always-protected` նշագրումները տարբերվում են կոմպիլացման ժամանակի հաստատուններից

Երկու սկրիպտներն էլ գործարկվում են pre-commit hook-ում և CI-ում։

### Կեղծ դրական արդյունքի կանոն

Եթե `x-always-protected`-ը կամ `x-loopback-only`-ը նշված է այնպիսի երթուղու վրա, որը ՉԿԱ
`routeGuard.ts` հաստատունում, ծածկույթի սկրիպտը ձախողվում է։ Ուղղումը միշտ YAML-ը
`routeGuard.ts`-ի իրական կիրառած կանոններին համապատասխանեցնելն է, այլ ոչ թե երթուղիները `routeGuard.ts`-ում
ավելացնելը՝ առանց կիրառման տրամաբանությունը նույնպես իրականացնելու։
