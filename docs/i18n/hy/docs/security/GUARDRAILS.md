> **Ճշմարտության աղբյուր՝** `src/lib/guardrails/`
> **Վերջին թարմացումը՝** 2026-08-29 — v3.8.51 (Video Bridge-ի տրանսկրիպտի ծագումը հայտարարում է կանչողը,
> և այն դեռ չի ստուգվում սերվերի կողմից — հստակեցվել է ըստ #11661-ի)

Պաշտպանիչ սահմանափակումներն ապահովում են անվտանգությունը, քաղաքականությունների կիրառումը և բովանդակության փոխակերպումները
OmniRoute-ի ու վերին մակարդակի մատակարարների միջև ընկած սահմանագծում։ Յուրաքանչյուր պաշտպանիչ սահմանափակում կարող է ստուգել (և
ըստ անհրաժեշտության մերժել, փոխակերպել կամ ծանոթագրել) հարցման օգտակար բեռները (`preCall`) և
վերին մակարդակի պատասխանները (`postCall`)։

Համակարգը գործում է **fail-open** սկզբունքով․ եթե պաշտպանիչ սահմանափակման կատարման ընթացքում բացառություն է առաջանում, ռեեստրը
գրանցում է սխալը և հարցումը ձախողելու փոխարեն շարունակում է հաջորդ պաշտպանիչ սահմանափակմամբ։
Արգելափակումը միշտ բացահայտ որոշում է (`block: true`) և երբեք՝ պատահականություն։

## Ներկառուցված պաշտպանիչ մեխանիզմներ

Ներմուծման ժամանակ ռեեստրը առաջնահերթության կարգով ինքնաշխատ բեռնում է վեց պաշտպանիչ մեխանիզմ

### Տեսողական կամուրջ (`visionBridge.ts`) — Մոդալության կամուրջ PR-1

Ընդհատում է պատկերներ պարունակող և **տեսողություն չաջակցող մոդելներին** ուղղված հարցումները և կամ ամբողջ հարցումը վերահասցեավորում է տեսողություն աջակցող մոդելի, կամ սկզբնական կանչից առաջ պատկերային մասերը փոխարինում է կարգավորվող տեսողական մոդելի ստեղծած տեքստային նկարագրություններով։ Սա թույլ է տալիս միայն տեքստ աջակցող մատակարարներին թափանցիկ կերպով մշակել բազմամոդալ օգտակար բեռներ։

Ընթացքը՝

1. Բաց թողնել, եթե թիրախային մոդելն արդեն աջակցում է տեսողություն (բացառությամբ այն դեպքի, երբ այն առկա է հարկադիր կամրջման `isVisionBridgeForcedModel` ցանկում)։
2. Արտահանել պատկերային մասերը `extractImageParts(messages)`-ի միջոցով
   (`visionBridgeHelpers.ts`), որը պատվիրակում է **միասնական մեդիա
   հայտնաբերիչին**՝ `open-sse/utils/mediaParts.ts`-ի `detectMediaParts()`-ին՝
   ճշմարտության միակ աղբյուրին, որը համատեղ օգտագործվում է համակցված համատեղելիության զտիչի հետ։
   Արտահանումը թույլատրված է միայն վերին մակարդակի այն ձևերի համար, որոնք
   `replaceImageParts`-ը կարող է կրկին տեղադրել (արտահանում↔փոխարինում պայմանագիր)՝ OpenAI-ի
   `image_url`, Anthropic-ի base64 `source.type:"base64"`, Anthropic-ի URL
   `source.type:"url"` և Responses API-ի `input_image`։ Ներդրված համընկնումները և
   միայն ցուցիչ պարունակող ձևերը համակցված զտիչի նյութ են և երբեք չեն արտահանվում։
   Բաց թողնել, եթե ոչինչ չի գտնվել։
3. Կատարման միջավայրի կազմաձևը որոշել `resolveVisionBridgeRuntimeSettings()`-ի միջոցով
   (`src/shared/constants/modalityBridgeDefaults.ts`)․ նոր `modalityBridge*`
   կարգավորումների բանալիներն ունեն առաջնահերթություն, իսկ հին `visionBridge*` բանալիները մնում են որպես **մեկ ցիկլի
   պահուստային տարբերակ** (հետադարձման պատուհան)։ Եթե կամուրջն անջատված է, բաց թողնել նախքան մեդիայի որևէ շրջանցում։
4. Ռեժիմի ընտրիչը (`modalityBridgeVisionMode`, տե՛ս ստորև բերված աղյուսակը) որոշում է՝
   վերահասցեավորել, թե նկարագրել։ Վերահասցեավորումը վերադարձնում է `modifiedPayload`, որտեղ փոխված է միայն `model`-ը,
   ինչպես նաև `{ rerouted, fromModel, toModel, imagesKept }` մետատվյալները։
5. Նկարագրման ուղի․ պատկերների քանակը սահմանափակել `maxImages`-ով, կազմել առաջադրանքը հաշվի առնող հուշումը,
   ստուգել նկարագրությունների շտեմարանը, տեսողական մոդելը կանչել **զուգահեռաբար**
   (`Promise.allSettled`) և պատկերների փոխարեն ներարկել `[Image N]: <description>` տեքստային մասեր։
   Չհաջողված նկարագրումը վերադարձնում է `null`, և սկզբնական պատկերային մասը
   **պահպանվում է** (#4012), բացառությամբ համակցված նկարագրման ուղու, երբ բոլոր
   նկարագրումները ձախողվել են․ այդ դեպքում տեսողություն չաջակցող հաստատված սկզբնական ծառայությանը փոխանցվում է
   `(unavailable — no vision-capable provider connected)` փոխարինիչը (#8430)։
6. Վերադարձնել `modifiedPayload` + մետատվյալները (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`)։

#### Ռեժիմի ընտրիչ (`modalityBridgeVisionMode`)

| Ռեժիմ      | Լռելյայն | Վարքագիծ                                                                                                                                                                                                                                                                                                                          |
| ---------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔        | Հին էվրիստիկա՝ անփոփոխ (#6640/#7204)․ ոչ համակցված/`auto/` մոդելները վերահասցեավորվում են լավագույն տեսողական մոդելին, եթե սկզբնական մոդելն արդեն չունի օգտագործելի հավատարմագրեր (այդ դեպքում՝ նկարագրել), իսկ համակցված թիրախները միշտ նկարագրվում են։                                                                          |
| `describe` |          | Միշտ նկարագրել․ վերահասցեավորման բլոկն ամբողջությամբ բաց է թողնվում, և միշտ պատասխանում է օգտատիրոջ ընտրած մոդելը։                                                                                                                                                                                                                |
| `reroute`  |          | Հարկադիր վերահասցեավորում․ հավատարմագրեր ունեցող մոդելը պահպանելու ստուգումը շրջանցվում է։ Վերահասցեավորման **թիրախի** հավատարմագրերի ստուգումը շարունակում է կիրառվել․ երբ հասանելի տեսողական թիրախ չկա, հարցումն անցնում է նկարագրման ուղուն, որպեսզի չմշակված պատկերները երբեք չհասնեն միայն տեքստ աջակցող հետնամասին (#8430)։ |

Հարկադիր ռեժիմները կարճ միացմամբ ավարտվում են **նախքան** ինքնաշխատ էվրիստիկայի գործարկումը․ `auto`-ի վարքագիծը
բայթ առ բայթ նույնական է PR-1-ին նախորդող պաշտպանիչ մեխանիզմի վարքագծին։

#### API բանալու շրջանակ (`visionBridgeKeyScope.ts`)

Երբ կանչողի API բանալին սահմանափակում է `allowedConnections`-ը, քվոտաների պուլերը
(`allowedQuotas`) կամ մոդելները (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), կամուրջը վերահասցեավորման և նկարագրման համար ընտրում է միայն այն մոդելները, որոնք բանալին կարող է օգտագործել, և միայն այն կապերից, որոնք բանալին կարող է օգտագործել։ Այնուհետև նկարագրման կանչը միշտ անցնում է OmniRoute-ի ինքնաշրջանով՝
`x-omniroute-self-loop-key-id` վերնագրով, որպեսզի այն ստացող զրույցի հարցումը
կրկին կիրառի այդ բանալու կապի և մոդելի քաղաքականությունը։ `enforceApiKeyPolicy()`-ն
այդ վերնագիրը հաշվի է առնում միայն ինքնաշրջանի bearer-ի հետ միասին, ուստի այն կարող է միայն
նեղացնել հասանելիությունը, իսկ չորոշվող id-ն մերժվում է։

Եթե բանալու համար որևէ տեսողական մոդել թույլատրված չէ, նկարագրման ուղին մի կողմ է քաշվում, և
հարցումն անփոփոխ փոխանցվում է՝ ինչպես անջատված պաշտպանիչ մեխանիզմի դեպքում բաց թողնելու նույն վարքագծով
(մետատվյալներ՝ `{ skipped: true, reason: "no_permitted_vision_model" }`)։
Առանց բանալու հարցումները և այս սահմանափակումները չունեցող բանալիները գործում են ճիշտ այնպես,
ինչպես նախկինում։

#### Առաջադրանքը հաշվի առնող նկարագրման հուշում (`modalityBridgeVisionTaskAware`)

Լռելյայն՝ **true**։ `composeVisionPrompt()`-ը (`visionBridgeHelpers.ts`) հիմնական նկարագրության հուշմանը կցում է **օգտատիրոջ վերջին հաղորդագրության** տեքստը (կրճատված մինչև 500 նիշ)՝ նկարագրությունն ուղղորդելով դեպի այն, ինչ օգտատերն իրականում հարցրել է (codex-vision-proxy ձևանմուշ), և տեսողության մոդելին խնդրելով արտագրել տեսանելի տեքստը։ Դրոշն անջատված լինելու կամ օգտատիրոջ տեքստի բացակայության դեպքում հիմնական հուշումն օգտագործվում է անփոփոխ։

Նկարագրության ինքնաշրջանի սեփական OpenAI-ի հետ համատեղելի հարցումը (`callVisionModelSingle()`-ը `visionBridgeHelpers.ts`-ում) միշտ պահանջում է `image_url.detail: "high"`՝ առանց պայմանների, յուրաքանչյուր կանչողի/մատակարարի համար և անկախ հաճախորդի որևէ ազդանշանից։ Ցածր մանրամասնությամբ նմուշառումը վատացնում է OCR-ի ճշգրտությունը հենց այն տեքստի արտագրման առաջադրանքի համար, որը պահանջում է այս հուշումը, ուստի նկարագրության կանչն ինքնին միշտ պահանջում է բարձր մանրամասնություն՝ անկախ նրանից, թե մուտքային սկզբնական հարցումն ինչ մանրամասնության մակարդակ է օգտագործել։ Սա ազդում է միայն ներքին նկարագրության հարցման մարմնի վրա և չի փոխում, թե OmniRoute-ն ինչպես է հիմնական հարցման մեջ փոխանցում կանչողի սեփական `image_url.detail`-ը․ այդ լռելյայն արժեքը կիրառվում է առանձին և միայն հայտնաբերված OpenCode հաճախորդների համար՝ `defaultImageDetail()`-ում (`open-sse/handlers/chatCore/upstreamBody.ts`)։ Նկարագրության ինքնաշրջանի Anthropic հաղորդալարային ձևաչափի ճյուղը `detail` դաշտ չունի և այս լռելյայն արժեքներից ոչ մեկի ազդեցությունը չի կրում։

#### Նկարագրության ելքի սահմանաչափ (`modalityBridgeVisionMaxChars`)

| Բանալի                         | Լռելյայն | Միջակայք          |
| ------------------------------ | -------- | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`      | `0` կամ 100–50000 |

`0`-ն (լռելյայն) նշանակում է **առանց սահմանաչափի**․ `callVisionModel()`-ի վերադարձած նկարագրությունը փոխանցվում է անփոփոխ՝ պահպանելով առկա վարքագիծը։ 100–50000 միջակայքի ցանկացած արժեք նկարագրությունը կրճատում է՝ ավելացնելով `…` վերջածանց, նախքան այն որպես `[Image N]: <description>` հետ տեղադրելը (`VisionBridgeGuardrail.preCall()`-ը `src/lib/guardrails/visionBridge.ts`-ում)։ Բարձրացրեք այս արժեքը մանրամասներով հարուստ OCR առաջադրանքների համար, որոնց դեպքում հաջորդ մոդելին անհրաժեշտ է ամբողջական արտագրությունը․ նվազեցրեք այն՝ շատախոս տեսողության մոդելների թոքենների օգտագործումը սահմանափակելու համար։ Կառավարման վահանակի դաշտը գտնվում է Vision ներդիրի Advanced վահանակում (`modality-bridge-max-chars`-ը `ModalityBridgeVisionTab.tsx`-ում) և 1-ից 99 ցանկացած արժեք բարձրացնում է մինչև նվազագույն 100-ը՝ միաժամանակ անփոփոխ թողնելով հստակ նշված `0`-ն․ `0`-ն ինքնին վավեր Zod արժեք է (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), այլ ոչ պարզապես «չսահմանված» լռելյայն արժեք։

#### Նկարագրության քեշ (`modalityBridge/bridgeCache.ts`)

Հիշողության մեջ պահվող LRU + TTL քեշ՝ նկարագրությունների ելքերի համար, որը համօգտագործվում է ամբողջ պրոցեսի մակարդակով։ Բանալի = `sha256(imageRef + composedPrompt + configuredBridgeModel)`՝ երկարության նախածանցով շրջանակմամբ (առանց դաշտերի սահմանների բախումների)։ Մոդելի բաղադրիչը **կարգավորված** կամրջի մոդելն է, ոչ թե իրականում պատասխանած մոդելը․ `callVisionModel`-ը կարող է ներքին կերպով անցնել պահուստային տարբերակի, իսկ ըստ յուրաքանչյուր փորձի բանալիների ստեղծումը կմասնատի քեշը։ Ձախողված նկարագրությունները երբեք չեն քեշավորվում։ Կարգավորումներ՝

| Բանալի                          | Լռելյայն | Միջակայք |
| ------------------------------- | -------- | -------- |
| `modalityBridgeCacheEnabled`    | `true`   | —        |
| `modalityBridgeCacheTtlMinutes` | `60`     | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`    | 10–5000  |

#### Հեռակա պատկերների նորմալացում (ինքնաշրջանի նկարագրություն/base64 ներբեռնում)

Երբ կամուրջն ինքն է ներբեռնում **հեռակա** պատկեր՝ Anthropic-ի նկարագրության ինքնականչի և claude հաղորդալարային ձևաչափի base64 փոխակերպման (`ensureBase64ImagesForClaudeWire`) համար, երկու դեպքում էլ `visionBridgeHelpers.ts`-ի `fetchRemoteImageAsDataUri()`-ի միջոցով, ստացված տվյալների URI-ն նախքան տեսողության մոդելի հարցման մեջ ներառվելը փոխանցվում է `normalizeDataUri()`-ով (`open-sse/utils/imageNormalize.ts`)։ Չափազանց մեծ պատկերները փոքրացվում են մինչև **2048px երկար եզր** (համապատասխանելով չափափոխման այն սահմանաչափին, որը OpenAI-ը/Anthropic-ը արդեն կիրառում են սերվերի կողմից), ինչը նվազեցնում է վերբեռնվող բայթերի քանակը/ուշացումը՝ առանց փոխելու այն, ինչ տեսնում է տեսողության մոդելը։ Չափափոխման համար օգտագործվում է `sharp`-ը, որը բեռնվում է դինամիկ ներմուծմամբ․ այն հարթակում, որտեղ դրա բնիկ երկուական ֆայլը չի բեռնվում, `normalizeDataUri()`-ն **երբեք սխալ չի նետում**․ այն անցնում է սկզբնական բայթերի անփոփոխ փոխանցման, որպեսզի նկարագրության/base64 փոխակերպման ուղին միշտ շարունակի աշխատել։ Պատկեր չհանդիսացող բայթերը (երբ ներբեռնումը չի վերադարձրել վերծանելի պատկեր) նույնպես փոխանցվում են անփոփոխ։ Այս նորմալացումը սահմանափակված է այն պատկերներով, որոնք կամուրջը ներբեռնում է իր սեփական ինքնականչի համար․ այն երբեք չի կիրառվում կանչողի անմշակ, անփոփոխ փոխանցվող օգտակար բեռի վրա՝ համաձայն միայն հստակ միացման դեպքում փոփոխելու սկզբունքի (Կոշտ կանոն #20)։

#### Կարգավորումների սխեմա + միգրացիա

Նոր `modalityBridge*` բանալիները Zod-ով վավերացվում են `updateSettingsSchema`-ում (`src/shared/validation/settingsSchemas.ts`)՝ `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCache*` եռյակը և Audio Bridge-ի կողմից օգտագործվող `modalityBridgeAudio*` խումբը։ `141_modality_bridge_settings.sql` միգրացիան առկա հին `visionBridge*` արժեքները պատճենում է համապատասխան նոր բանալիների մեջ (իդեմպոտենտ է և երբեք չի վերագրում օպերատորի կողմից սահմանված `modalityBridge*` արժեքը)․ հին բանալիները մեկ թողարկման ցիկլի ընթացքում շարունակում են ընդունվել որպես ընթերցման պահուստային տարբերակ։

#### Թափանցիկության վերնագիր + վիճակագրություն

Նկարագրության միջոցով փոխակերպված պատասխանները պարունակում են
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
վերնագիրը (կառուցվում է `buildModalityBridgeHeader()`-ով՝ `modalityBridge/bridgeStats.ts`-ում, և դրվում է `withModalityBridgeHeader()`-ով՝ `src/sse/handlers/chatHelpers.ts`-ում)։ Վերաուղղորդված հարցումները **չեն** ստանում վերնագիր․ օգտակար բեռը չի փոփոխվել, իսկ մոդելի փոխարինումն արդեն տեսանելի է պատասխանի մարմնի `model` դաշտում։

`GET /api/modality-bridge/stats`-ը (կառավարման նույնականացմամբ, նույն մակարդակում, ինչ
`GET /api/settings`-ը) վերադարձնում է հիշողության մեջ պահվող՝ ըստ մոդալության հաշվիչները՝
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }`՝ `vision`, `audio` և
`video` մոդալությունների համար։ `averageLatencyMs`-ը որպես հայտարար օգտագործում է
`latencySamples`-ը, այլ ոչ բոլոր փորձերը․ ժամանակաչափում չունեցող գործողությունը չի
ստեղծում կեղծ՝ զրո միլիվայրկյանանոց նմուշ։ `bridged`-ը մնում է հաջող
փոխակերպումների հետադարձ համատեղելի կեղծանունը․ ձախողված փորձերը չեն ավելացնում այն։
Ըստ նախագծման՝ հաշվիչները զրոյացվում են գործընթացի վերագործարկման ժամանակ
(հեռաչափություն, ոչ թե հաշվառում)։

#### Կառավարման վահանակի կազմաձևում

Կառավարման վահանակի հատուկ էջն է
`/dashboard/settings/modality-bridge`-ը։ URL-ով հասցեավորվող դրա `Vision`, `Audio`
և `Video` ներդիրները պահպանում են հարցման պարամետրերը՝ `tab` արժեքը փոխելիս։
Vision ներդիրը տրամադրում է միացման, ռեժիմի, մոդելի ընտրության (ներառյալ ավտոմատ
լռելյայնը), առաջադրանքը հաշվի առնող հուշումների, սպասման ժամանակի/պատկերի/նկարագրության
երկարության/քեշի ընդլայնված սահմանաչափերի, կատարման ժամանակի
հաշվիչների և պաշտպանված նմուշային հարցման կարգավորումներ։ Audio ներդիրը նույնպես
գործող է․ այն տրամադրում է միացման կարգավորում, միայն STT մոդելների ընտրիչ՝ Auto
տարբերակով, սպասման ժամանակի/հոլովակի առավելագույն սահմանաչափեր, աուդիո
հաշվիչներ և `input_audio` նմուշային փորձարկում։ Video ներդիրը գործունակ է․ այն
ցուցադրում է FFmpeg/ffprobe-ի կատարման միջավայրի վիճակը՝ UI-ի չորս հստակ վիճակներից
մեկը (`unknown`, երբ ստուգումն ընթացքի մեջ է կամ չի կարողացել ավարտվել,
`restricted`՝ ոչ loopback կառավարման վահանակի հոսթում, որտեղ ստուգումը բաց է թողնվում
հաճախորդի կողմից, `unavailable`՝ ստուգումից և բացակայությունը հաստատելուց հետո,
կամ `available`՝ FFmpeg/ffprobe տարբերակներով), պահպանում է միացման/մոդելի/կադրի/
տեսանյութի/սպասման ժամանակի սահմանաչափերը, մոդելի ընտրիչը զտում է՝ թողնելով տեսողության
հնարավորություն ունեցող մոդելները, և տրամադրում է տեսանյութի հաշվիչները։

AI-ի կարգավորումների տակ գտնվող նախկին Vision Bridge քարտն այժմ դեպի նոր էջ տանող
համատեղելիության հղում է․ այն այլևս չի պահում ձևի երկրորդ պատճենը։ Media Providers-ը
նաև Image-to-Text և Speech-to-Text աշխատանքային հոսքերը կապում է Modality
Bridge-ի համապատասխան ներդիրների հետ՝ առանց գոյություն ունեցող Speech-to-Text
փորձարկման միջավայրը հեռացնելու։

**Ինքնաշրջանցի ընդունման շրջանցում․** երբ նկարագրման կանչը երթուղավորվում է OmniRoute-ի
սեփական `/v1` ինքնաշրջանցով (ոչ ստանդարտ մատակարարի մոդել), ենթահարցումն ուղարկում է
`x-omniroute-admission-bypass: internal` և նույնականացվում է որոշված
ինքնաշրջանցի հավատարմագրով՝ տեղային ռեժիմում տեղային `sk_omniroute` հատուկ արժեքով կամ
օպերատորի կազմաձևած `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` միջավայրի բանալիով (#1350),
որպեսզի `REQUIRE_API_KEY=true` տեղակայումները նույնպես կարողանան կատարել նկարագրման
կանչը։ Շրջանցումը թույլատրվում է միայն հենց այդ հավատարմագրերի համար, ուստի արտաքին
հաճախորդները չեն կարող օգտագործել վերնագիրը՝ ընդունման ստուգումը շրջանցելու համար։

Ժառանգական լռելյայն արժեքները գտնվում են `src/shared/constants/visionBridgeDefaults.ts`-ում,
իսկ նոր ռեժիմի/առաջադրանքը հաշվի առնելու/քեշի լռելյայն արժեքներն ու կարգավորումների
որոշիչը՝ `src/shared/constants/modalityBridgeDefaults.ts`-ում։ Պաշտպանիչ մեխանիզմը
տրամադրում է `deps` կոնստրուկտորի ընտրանք, որպեսզի թեստերը կարողանան ներարկել կեղծ
`getSettings` և `callVisionModel` իրականացումներ։

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Ընդհատում է աուդիո պարունակող զրույցի հարցումները՝ նախքան դրանք կհասնեն թիրախի, որի
մասին հայտնի չէ, որ այն ընդունում է աուդիո մուտք։ Այն երբեք չի վերաերթուղավորում
զրույցի հարցումը․ աուդիո մասերը տառադարձվում են գոյություն ունեցող՝ OpenAI-ի հետ
համատեղելի բազմամաս վերջնակետի միջոցով, իսկ ընտրված զրույցի մոդելը շարունակում է
աշխատել տեքստային տառադարձումներով։

Հոսքը՝

1. Որոշել `supportsAudio`-ն `getResolvedModelCapabilities()`-ի միջոցով։ Մատակարարների
   գրանցամատյանի հստակ մետատվյալներն ունեն առաջնահերթություն, ապա՝ ստատիկ մոդելի
   մետատվյալները, ապա՝ համաժամացված `modalities_input`-ը։ Հայտարարված մուտքային ցանկն
   առանց `audio`-ի տալիս է `false`, իսկ հնարավորության մասին որևէ ապացույցի
   բացակայության դեպքում մնում է `null`։ Ե՛վ `false`-ը, և՛ `null`-ը ակտիվացնում են
   պահպանողական կամուրջը, մինչդեռ `true`-ն շրջանցում է այն։
2. Որոշել `modalityBridgeAudio*` կարգավորումները և յուրաքանչյուր հաղորդագրությունից
   դուրս բերել վերին մակարդակի՝ տեղադրմամբ փոխարինելի աուդիո մասերը՝ ընդհանուր
   `detectMediaParts()` հայտնաբերիչի միջոցով։ Աջակցվող հաղորդալարային ձևաչափերն են
   OpenAI-ի `input_audio`, `audio_url` և `source.media_type: "audio/*"` ձևերը։
   Ներդրված աուդիոն հայտնաբերվում է երթուղավորման համար, բայց տեղադրմամբ փոխարինման
   ուղին այն չի հեռացնում։ Մշակվող աշխատանքի քանակը սահմանափակվում է
   `modalityBridgeAudioMaxClips`-ով․ ավելի ուշ մասերը մնում են անփոփոխ։
3. Օգտագործել կազմաձևված `provider/model`-ը կամ թույլ տալ, որ
   `selectAudioBridgeModel()`-ը կայուն կատալոգային հերթականությամբ անցնի
   `AUDIO_TRANSCRIPTION_PROVIDERS`-ով և ընտրի օգտագործելի ակտիվ մատակարարի
   հավատարմագիր ունեցող առաջին մոդելը։
4. `callAudioTranscription()`-ը base64/data-URI աուդիոն փոխակերպում է բազմամաս
   `file`-ի կամ հեռակա `audio_url`-ը ներբեռնում է միայն հանրային ելքային կապ թույլատրող
   պաշտպանիչ մեխանիզմի միջոցով՝ DNS ամրագրմամբ և 25 MB սահմանաչափով։ Այնուհետև այն
   POST հարցմամբ ֆայլն ու ընտրված մոդելն ուղարկում է տեղային
   `/v1/audio/transcriptions` ինքնաշրջանց՝ նույնականացվելով
   `resolveSelfLoopBearer()`-ով։ Գոյություն ունեցող տառադարձման երթուղին կատարում է
   հավատարմագրերի սովորական որոնում, հովացման ժամանակահատվածի/արագության սահմանաչափի
   մշակում և մատակարարին ուղղորդում։
5. Հաջող կանչերը իրենց մասերը փոխարինում են `[Audio N]: <transcript>`-ով։ Կանչերը
   կատարվում են `Promise.allSettled`-ով․ առանձին ձախողման դեպքում պահպանվում է տվյալ
   սկզբնական աուդիո մասը (#4012 պայմանագիր)։ Եթե բոլոր կանչերը ձախողվում են, և
   հաստատված է, որ թիրախի `supportsAudio === false`, մասերը դառնում են
   `[Audio N]: (unavailable — no STT provider connected)` (#8430 պայմանագիր)։ Անհայտ
   թիրախի (`null`) դեպքում բոլոր կանչերի ձախողման արդյունքը մնում է անփոփոխ։
   Հաստատված՝ միայն տեքստ ընդունող թիրախը, որի համար չկա օգտագործելի STT հավատարմագիր,
   ստանում է նույն հստակ փոխարինիչը՝ առանց ցանցային կանչ կատարելու։

Հաջող տառադարձումներն օգտագործում են գործընթացի ողջ մասշտաբով գործող Modality Bridge
LRU/TTL քեշը։ Բանալին համադրում է աուդիո հղումը, կայուն `audio-transcription`
գործողության պիտակը և ընտրված STT մոդելը․ ձախողումները երբեք չեն քեշավորվում։ Աուդիոյի
փորձերը թարմացնում են ընդհանուր `bridged`, `cacheHits`, `failures` և `lastUsedAt`
հաշվիչները։ Փոխակերպված պատասխանները պարունակում են
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`․ անփոփոխ
հարցումները չեն ստանում Audio Bridge հատված։

Կատարման ժամանակի կարգավորումները պահվում են DB-ում և վավերացվում են Zod-ով․

| Բանալի                        | Լռելյայն | Միջակայք           |
| ----------------------------- | -------- | ------------------ |
| `modalityBridgeAudioEnabled`  | `true`   | —                  |
| `modalityBridgeAudioModel`    | `""`     | Ավտոմատ կամ STT ID |
| `modalityBridgeAudioTimeout`  | `60000`  | 1000–300000        |
| `modalityBridgeAudioMaxClips` | `3`      | 1–10               |

Ընդհանուր քեշը շարունակում է կառավարվել `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` և `modalityBridgeCacheMaxEntries` պարամետրերով։

### Տեսանյութի կամուրջ (`videoBridge.ts`, `videoBridgePipeline.ts`)

Ընդհատում է Chat Completions-ի `messages`-ում և Responses
API-ի `input`-ում գտնվող վերին մակարդակի տեսանյութային մասերը՝ նախքան հայտնի ներկառուցված տեսանյութային աջակցություն չունեցող թիրախը կանչելը։
Աջակցվող ձևաչափերն են `input_video`, `video_url`, `video_source`, HTTPS URL-ները
և `data:video/*;base64,...` տվյալների URI-ները։ Տեքստում առկա սովորական ֆայլերի անունները
չեն դիտարկվում որպես տեսանյութ։

`VideoBridgeGuardrail.preCall`-ը (`videoBridge.ts`) պատասխանատու է հարցման շրջանցման,
հնարավորությունների/քաղաքականության ստուգման, յուրաքանչյուր հարցման համար ագրեգացման և պատասխանի օգտակար բեռնվածքի համար։
Յուրաքանչյուր տեսանյութի մշակումը՝ ստացումը, ամբողջ արդյունքի քեշավորումը, կադրերի
հաջորդականության նկարագրումը (որը միավորում է կանչողի կողմից հայտարարված ձայնային վերծանումը)
և յուրաքանչյուր փորձի չափումները/ընդհատումը/մաքրումը, թաքցված է
`videoBridgePipeline.ts`-ի `processVideoPart`-ի հետևում, որը `preCall`-ի ցիկլի ներսում
կանչվում է մեկ անգամ՝ յուրաքանչյուր տեսանյութային մասի համար։
Այդ մոդուլը նաև սահմանում է հստակ պորտային սահմանները՝ `VideoMediaBrokerPort`
(բայթերի ստացում և նմուշառված կադրերի արդյունահանում), `VideoAudioTranscriptionPort`
(կանչողի կողմից հայտարարված ձայնային վերծանման միավորում նմուշառված ենթագրերի հետ) և
`VideoDrilldownPort` (կադրերի խորացված վերլուծության պահպանման սահմանը, որը դեռ միացված չէ
`processVideoPart`-ին. ներկայում միայն առանձին `/api/modality-bridge/video/drilldown`
երթուղին է գրանցում խորացված վերլուծության գրառումները)։

Հանրային `/v1` հարցման ուղին երբեք չի ներմուծում կամ կանչում ենթագործընթաց։
Հեռավար տեսանյութերը ներբեռնվում են 50 MiB սահմանափակմամբ, իսկ ներկառուցված base64 տեսանյութերի
համար սահմանված է պահպանողական՝ յուրաքանչյուր տեսանյութի համար 36 MiB ապակոդավորված չափի
առավելագույն սահման, որպեսզի մոդելի/հաղորդագրությունների/շրջանակավորման թաղանթը տեղավորվի
հանրային JSON հարցման ընդունման 50 MiB սահմանաչափում։ Ներկառուցված տվյալների երկարությունը և
ապակոդավորված չափի գնահատականները ստուգվում են նախքան հիշողության հատկացումը։ HTTPS-ը
պարտադիր է սկզբնական հեռավար URL-ի և յուրաքանչյուր վերահղման համար՝ օգտագործելով միայն
հանրային ելքային կապի գոյություն ունեցող պաշտպանիչ մեխանիզմը՝ DNS ամրագրմամբ։ Այնուհետև բայթերն
անցնում են ճշգրիտ ներքին `POST /api/modality-bridge/video/extract` բրոքերային սահմանով։
Այդ երթուղին միաժամանակ `LOCAL_ONLY` և `SPAWN_CAPABLE` է, ընդունում է միայն յուրաքանչյուր
գործընթացի համար նույնականացված, վստահելի loopback հարցում և երբեք չի ընդունում URL,
ֆայլային համակարգի ուղի, գործարկվող ֆայլ կամ արգումենտների ցանկ։ API-ի մարմնի չափի մշակման
շղթան և մշակողի՝ մարմնի աստիճանական ընթերցիչն անկախ կերպով կիրառում են բրոքերի մուտքային
տվյալների 50 MiB սահմանաչափը։ Դրա սահմանափակ հերթը միաժամանակ կատարում է մեկ արդյունահանում,
թույլատրում է սպասող չորս առաջադրանք և սպասող մուտքային տվյալները սահմանափակում է 100 MiB-ով։

Բրոքերի ներսում `ffprobe`-ը կարդում է մասնավոր տեղային ֆայլ. ձևաչափերի ֆիքսված
թույլատրացանկը բացառում է նվագացանկերի և մանիֆեստների ձևաչափերը։ Թույլատրված MOV ընտանիքի
բեռնարկղերի համար արտաքին MOV տվյալների հղումները լռելյայն մնում են անջատված, իսկ ֆիքսված
հրամանը չի միացնում դրանք։ Ե՛վ `ffprobe`-ը, և՛ `ffmpeg`-ն օգտագործում են միայն `file`
պրոտոկոլի թույլատրացանկ, մեկ հոսք, արգումենտների ֆիքսված զանգվածներ, առանց shell-ի,
իսկ գործարկվող ֆայլերը որոշվում են `PATH`-ից։ Կցված պատկերով շապիկի հոսքերը չեն համարվում
նվագարկման թեկնածուներ։ Նվագարկման ենթակա բոլոր հոսքերը պետք է համապատասխանեն
սահմանափակումներին, և բացահայտ լռելյայն հոսքը նախընտրելի է դետերմինացված՝ ամենացածր
ինդեքսով պահուստային տարբերակից առաջ։ Տեսանյութերը սահմանափակված են 600 վայրկյանով,
յուրաքանչյուր չափության համար՝ 8,192 պիքսելով, իսկ սկզբնաղբյուրի ընդհանուր չափը՝
33,554,432 պիքսելով։ FFmpeg-ը նմուշառում է 1–16 միջնակետային JPEG կադր, փոքրացնում է
երկար եզրը մինչև առավելագույնը 1,024 պիքսել՝ առանց ավելի փոքր մուտքային տվյալները
խոշորացնելու, և երբեք URL չի ստանում։ Լռելյայն նմուշառումը `uniform` է։ Ընտրովի
`scene_aware` և փորձարարական `segment_aware` քաղաքականությունները կատարում են մեկ լրացուցիչ
ֆիքսված FFmpeg անցում արդեն վավերացված տեղային հոսքի վրայով, ընտրում են սահմանափակ
`showinfo` տեսարանների ժամանակային դրոշմներ և հայտնաբերման ձախողման, ժամանակի սպառման,
սխալ ձևաչափված ելքի կամ թեկնածուների դատարկ հավաքածուի դեպքում դետերմինացված կերպով
վերադառնում են նույն հավասարաչափ միջնակետերին։ Հատվածներին հարմարեցված ռեժիմը միջնակետային
նմուշները համամասնորեն բաշխում է վավերացված տեսարանային միջակայքերին. հատվածներին
հարմարեցված ապացույցները և պահուստային վարքագիծը մանրամասն ներկայացված են ստորև։
16 կադրի խիստ սահմանաչափը յուրաքանչյուր քաղաքականության դեպքում կիրառվում է ընտրությունից
հետո։ Երբ տեսարաններին հարմարեցված հարցումն ունի միայն մեկ կադրի բյուջե, այն օգտագործում է
ակտիվ՝ ամբողջ տեսանյութի կամ կիզակետային պատուհանի հավասարաչափ միջնակետը և հաղորդում է
`policyEffective: uniform`. ընտրված մեկ տեսարանային կադրը չի կարող պահպանել ժամանակային
երկու եզրերն էլ։ Կանչողը կարող է ընտրովի տրամադրել վերջավոր կիզակետային պատուհան
(`start`/`end` վայրկյաններով). սահմանները հարմարեցվում են մեդիայի տևողությանը, հակադարձված
կամ ոչ վերջավոր պատուհանները մերժվում են, իսկ նմուշառման բոլոր քաղաքականությունները
կատարվում են միայն նորմալացված միջակայքի ներսում։ Ստացված պատուհանը ներառվում է նմուշառման
մետատվյալներում և անվստահելի նկարագրության նախածանցում, որպեսզի հետագա մոդելները կարողանան
տարբերակել կենտրոնացված հատվածը ամբողջ ժամանակագծից։

Ենթագրերի իմաստային կենտրոնացումը առանձին, բացահայտ կարգավորում է։ Լռելյայն `full`
վերլուծության ռեժիմը պահպանում է կադրերի առկա հուշումը և երբեք հարցման տեքստը չի փոխանցում
ենթագրերի մոդելին։ `focused` ռեժիմում կամուրջը նույն Chat կամ Responses բեռնարկղից կարդում է
միայն օգտատիրոջ հեղինակած վերջին ոչ դատարկ `text`/`input_text`-ը, նորմալացնում է այն NFC-ի,
միավորում է կառավարման նիշերն ու բացատները և սահմանափակում մինչև Unicode-ի 500 կոդային կետ։
Դատարկ արդյունքի դեպքում այն վերադառնում է ճշգրիտ `full` հուշմանը։ Օգտագործելի հուշումը
սերիականացվում է որպես JSON՝ անվստահելի օգտատիրոջ համատեքստի հատուկ բլոկում, և կարող է միայն
առաջնահերթություն տալ դիտարկելի մանրամասներին. այն չի կարող չեղարկել մեդիայում տեսանելի կամ
լսելի հրահանգներին չհետևելու վերաբերյալ առանձին նախազգուշացումը։ Տեքստային կենտրոնացումը երբեք
չի ենթադրում `start`/`end` և չի փոխում ժամանակային նմուշառիչը։

#### FU-07 կառուցվածքային հատվածի ապացույցներ

`segment_aware`-ը կիրառում է մեկ սահմանափակ նախնական վերլուծության անցում արդեն վավերացված տեղային տեսահոսքի նկատմամբ։ Ֆիքսված զտիչների շղթան նախ լայնությունը մասշտաբավորում է առավելագույնը մինչև 320 պիքսել, հայտնաբերում է տեսարանների փոփոխություններն ու սառեցված միջակայքերը, ապա յուրաքանչյուր վայրկյանից վերցնում է 1 կադր՝ լղոզվածությունը, միջին լուսավորությունը և տարածական/ժամանակային տեղեկությունը գնահատելու համար։ Անցումը սահմանափակված է 600 կառուցվածքային նմուշով, մեկ FFmpeg/զտիչ հոսքով, նույն՝ միայն `file` արձանագրության և կոնտեյներների թույլատրելի ցուցակներով, գործընթացի ելքի 1 MiB սահմանաչափով և բրոքերի ընդհանուր ընդհատման/վերջնաժամկետի ներսում առավելագույնը 30 վայրկյանով։ Այն երբեք հարցումից հրաման, զտիչ, ուղի կամ URL չի ընդունում։

Կառուցվածքային արժեքները դետերմինիստական նմուշառման վկայություններ են, ոչ թե տեսանյութի իմաստային ըմբռնում։ Դրանք չեն եզրակացնում առարկաները, գործողությունները, ենթագրերը, խոսքը կամ օգտատիրոջ մտադրությունը։ Տեսարանների և սառեցումների սահմանները ձևավորում են հատվածներ․ սառեցման ընդգրկումը, լղոզվածությունը, էքսպոզիցիան, տարածական մանրամասնությունը և ժամանակային փոփոխությունն ազդում են միայն այն բանի վրա, թե ինչպես է բաշխվում կադրերի առկա 1–16 բյուջեն։ Ամբողջությամբ սառեցված հատվածը սահմանափակվում է մեկ կադրով, իսկ չսառեցված հատվածները մրցում են մնացած բյուջեի համար։ Երբ սահմանների քանակը գերազանցում է կադրերի քանակը, պահպանվում է ժամանակագծի համաչափ ընդգրկումը, որպեսզի սկզբի արագ անցումները չկարողանան թաքցնել վերջում գտնվող երկար հատվածը։ Սառեցման սահմանից վերլուծության 1-վայրկյանանոց ճշտության սահմաններում գտնվող տեսարանների սահմանները միավորվում են։

Բացակայող զտիչների, սխալ ձևաչափով կամ դատարկ վկայությունների, դետեկտորի սխալի կամ սահմանափակված նախնական վերլուծության ժամանակի սպառման դեպքում համակարգը բաց ձախողմամբ անցնում է միջնակետերի ճիշտ նույն համաչափ քաղաքականությանը։ Կանչողի ընդհատումը կամ բրոքերի վերջնաժամկետը բաց ձախողում չեն առաջացնում․ դրանք դադարեցնում են ընթացիկ ենթագործընթացը, կանխում հետագա կադրերի հանումը, իսկ մասնավոր ժամանակավոր ծառը հեռացվում է `finally`-ում։

`scripts/perf/video-bridge-fu07-eval.ts`-ը ստեղծում է դետերմինիստական իրական FFmpeg փորձանմուշներ՝ կրկնօրինակների հեռացումից հետո ենթագրավորման կանչերի խնայողության, խիտ շարժման դեպքում բյուջեի բաշխման, լղոզվածության/էքսպոզիցիայի/SI-TI վկայությունների, երկար վերջնամասով արագ անցումների և աստիճանական մարման կեղծ դրական արդյունքների համար։ Այն գրանցում է նախնական վերլուծության իրական անցած ժամանակը և, երբ `/usr/bin/time`-ը հասանելի է, ենթագործընթացի CPU-ն ու RSS-ի առավելագույն արժեքը։ Դրա որակի ստուգումները միայն կառուցվածքային օրակուլներ են։ Իրական ենթագրավորման մոդելի որակը մնում է `HOLD`, քանի որ այս փորձարկման համակարգը չունի լիազորված վերջնակետ կամ սառեցված գնահատիչ։ Դրամական խնայողությունը նույնպես մնում է `HOLD`, եթե `--caption-cost-per-call-usd`-ը չի տրամադրում յուրաքանչյուր կանչի արժեքի բացահայտ դրական գնահատական․ սկրիպտը երբեք չի հորինում այդ արդյունքներից որևէ մեկը։

Յուրաքանչյուր կադր սահմանափակված է 4 MiB-ով, բոլոր չմշակված կադրերը միասին՝ 23 MiB-ով, իսկ սերիականացված բրոքերային պատասխանը՝ 32 MiB-ով։ Մասնավոր ժամանակավոր գրացուցակը հեռացվում է `finally`-ում։ OmniRoute-ը չի ներառում FFmpeg և չի ընդունում կատարվող ֆայլի հատուկ ուղի։ Նախքան ենթագրավորումը՝ կամուրջը կիրառում է պահպանողական տեսողական ապակրկնօրինակման անցում․ յուրաքանչյուր JPEG վերածվում է 16×16 մոխրագույնի բուֆերի և համեմատվում է միայն վերջին պահպանված կադրի հետ։ Մեկ կադրից ավելի ենթագրավորման պահանջված բյուջեի դեպքում հանումը տրամադրում է մինչև այդ բյուջեի կրկնապատիկը կազմող, սակայն երբեք 16 կադրը չգերազանցող սահմանափակ թեկնածուների հավաքածու։ Պահանջված վերին սահմանը կիրառվում է միայն ապակրկնօրինակումից հետո, իսկ երբ բյուջեն առնվազն երկու է, վերջնական նոսրացման ժամանակ պահպանվում են առաջին և վերջին ընտրված թեկնածուները։ Տարբերակավորված `grayscale-16x16-mean-cells-v2` քաղաքականությունն օգտագործում է միջին լուսավորության տարբերության և այն մանրապատկերի բջիջների հարաբերակցության ավելի մեծ արժեքը, որոնց նորմավորված տարբերությունն առնվազն 0.05 է։ Կրկնօրինակի շեմը 0.04 հաստատունն է, որն ընտրվել է կանխատեսելիության համար՝ այն կատարման ժամանակի կարգավորում դարձնելու փոխարեն։ Այս երկրորդային բարձր հակադրությամբ ազդանշանը պահպանում է փոքր շարժումները և տեսանելի տեքստի փոփոխությունները, որոնք միայն միջինի վրա հիմնված համեմատությունը կարող է թաքցնել։ Համեմատիչի կամ ապակոդավորիչի սխալների դեպքում համակարգը բաց ձախողմամբ պահպանում է ընդգրկումը։ Ելքային մետատվյալներն առանձնացնում են հանված թեկնածուները, հաջողությամբ օգտագործված կադրերը և հեռացված տեսողական կրկնօրինակները։

Բացահայտ նշագրված տեսանյութային մասը կարող է պահանջել ժամանակադրոշմներով կոնտակտային թերթ։ Կամուրջը կառուցում է առավելագույնը 4 սյունակով և 16 կադրով JPEG ցանց։ 512-պիքսելանոց յուրաքանչյուր բջիջ իր աղբյուրի ժամանակադրոշմը դրոշմում է բարձր հակադրությամբ ներքևի շերտում, մինչդեռ նույն ժամանակադրոշմները մնում են տեքստային մետատվյալներում՝ հետագա կապակցման և աուդիտի համար։ Ամբողջական JPEG-ը շարունակում է սահմանափակված լինել 32 MiB-ով։ Եթե `sharp`-ը չի կարող ապակոդավորել կամ կազմել ցանցը, կամուրջը վերադառնում է առանձին JPEG կադրերին․ հաճախորդի ընդհատումը, այնուամենայնիվ, տարածվում է թերթի գործողության վրա։

Առաջխաղացման վկայությունները միտումնավոր առանձնացված են սինթետիկ կազմման միկրոհենանիշից։ `scripts/perf/video-bridge-contact-sheet-eval.ts`-ը սահմանում է սխեմայի տարբերակով A/B փորձարկման համակարգ՝ իրական OpenAI-compatible տեսողական մոդելների համար։ Այն չափում է մատակարարի հաղորդած թոքենները, սկզբից մինչև վերջ իրական ուշացումը՝ ներառյալ թերթի կազմումը, մոդելի կանչերի քանակը և մանիֆեստով սահմանված փաստերի պահպանումը։ Մոդելի չմշակված պատասխանները հաշվետվության մեջ չեն գրվում․ պահպանվում են միայն SHA-256 դայջեստներն ու համընկած փաստերի ID-ները։ Փորձարկման համակարգը ցանցային կամ վճարովի մոդելի որևէ կանչ չի կատարում, եթե չի փոխանցվել `--execute-real`, և կարգավորված չեն `--model`, `OMNIROUTE_BASE_URL` ու `OMNIROUTE_API_KEY`։ Առանց այդ բացահայտ իրական գործարկման՝ դրա մեքենայաընթեռնելի վճիռը մնում է `HOLD`․ միայն սինթետիկ բեռնվածքի/կանչերի քանակի չափումները առաջխաղացման վկայություն չեն։

Կանչողները կարող են աջակցվող տեսանյութային մասին կցել ընտրովի `transcript.cues` զանգված, երբ արդեն ունեն ժամանակով համաժամեցված տեքստ։ Յուրաքանչյուր նշում պետք է պարունակի `text`, զոնդավորված տևողության ներսում գտնվող վերջավոր `start`/`end` միջակայք և թույլատրելի ցուցակում ներառված `source` (`client`, `embedded` կամ `audio-bridge`)․ `confidence`-ի լռելյայն արժեքը `1` է, և այն պետք է մնա `0`-ի ու `1`-ի միջև։ Ճշգրիտ կրկնվող նշումները միավորվում են։ OmniRoute-ը երբեք այս մետատվյալներից չի սկսում տրանսկրիպցիա․ վավերացված նշումները՝ աղբյուրի, վստահության և միջակայքի հետ միասին, պատճենվում են նկարագրված արդյունքի մեջ և կադրերի ենթագրերի կողքին ներկայացվում որպես անվստահելի դիտարկումներ։ Անվավեր, միջակայքից դուրս կամ ծագման տվյալներից զուրկ տեքստը մերժվում է՝ ենթագրերի հոսքի մեջ խառնվելու փոխարեն։ Ներկայում `source` դաշտը հայտարարվում է կանչողի կողմից և չի ստուգվում սերվերի կողմից․ OmniRoute-ը պահանջում է, որ արժեքը լինի երեք թույլատրելի տողերից մեկը, սակայն դեռ գաղտնագրորեն չի հաստատում, որ `embedded` կամ `audio-bridge` պիտակն իսկապես ստացվել է սերվերին պատկանող հանման գործընթացից։ Մինչ այդ ստուգման ներդրումը՝ `source`-ը դիտարկեք որպես անվստահելի հուշում․ դրա վրա մի հիմնեք լիազորման որոշումները։

Փորձառու կանչողը նույն տեսանյութի համար կարող է տրամադրել արդեն իսկ թույլատրված `audioTranscript` ուղի։ Միաձուլման հանգույցը տեսողական և ձայնային դիտարկումները գործարկում է մեկ վերջնաժամկետի և ընդհատման ազդանշանի ներքո, դասավորում է դրանք ընդհանուր ժամանակագծի վրա, միավորում է լիովին նույնական կրկնօրինակները և հաղորդում մասնակի արդյունք, երբ հաջողվում է միայն կողմերից մեկը։ Անվավեր `audioTranscript`-ը հանգեցնում է այդ մասնակի արդյունքին՝ տեսողական նկարագրությունը պահպանվում է, իսկ ձայնային ճյուղն արձանագրում է մաքրված ձախողման կոդ, փոխանակ ամբողջ տեսանյութի մշակումը ձախողելու։ Յուրաքանչյուր ճյուղի հասանելիությունը, մասնակի լինելու դրոշը և մաքրված ձախողման կոդերը պահպանվում են նկարագրված արդյունքում, պաշտպանիչ սահմանափակումների մետատվյալներում (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), արդյունքների քեշի մետատվյալներում և կամրջի միաձուլման հաշվիչներում։ Լռելյայն Video Bridge ուղին չի գործարկում խոսքը տեքստի փոխակերպում և չի ներբեռնում մեդիայի երկրորդ պատճենը․ առանց այդ բացահայտ ուղու այն շարունակում է մշակել միայն տեսանյութը։

**Տրանսկրիպտի պահպանումը (#12150 P1)։** Սա կիրառվում է ինքնաբերաբար ամեն անգամ, երբ Video Bridge-ը (որն ինքնին կամընտիր է) արտապատկերում է տրանսկրիպտի նշում․ պահպանման առանձին դրոշ չկա։ Երբ հարցումն արտապատկերում է տրանսկրիպտի որևէ նշում (կանչողի հայտարարած `transcript` կամ միաձուլված `audioTranscript`), պաշտպանիչ սահմանափակումը այն նշում է որպես `videoBridgeObserved` և ստեղծում տեսանյութի նկարագրության քողարկված ստվերային տարբերակը՝ նույնական արտապատկերում, որում յուրաքանչյուր նշման ազատ տեքստային բովանդակությունը փոխարինված է `[redacted-video-transcript]`-ով։ Այն կառուցվում է՝ կառուցվածքային նշման դաշտը փոխարինելով նախքան տողի ձևավորումը (երբեք՝ հարթեցված տեքստը վերլուծելով, որպեսզի նշման որևէ բովանդակություն՝ վնասաբեր կամ սովորական, ներառյալ `]` պարունակող բովանդակությունները, ինչպիսիք են `[inaudible]`/`[music]`, չկարողանա պահպանվել)։ Պահպանվող կանչերի մատյանի հարցման մարմինը տեսանյութից ստացված յուրաքանչյուր տեքստային մասը փոխարինում է այդ քողարկված ստվերով՝ դրանք համադրելով ըստ բովանդակության հավասարության։ `fullText` հենակետը կրկին ընթերցվում է կանչից առաջ ավարտված պաշտպանիչ սահմանափակման բեռնվածքից, ուստի համադրումը շարունակում է հաջողվել այն բանից հետո, երբ շղթայի հետագա պաշտպանիչ սահմանափակումները (PII-ի և հավատարմագրերի քողարկիչները՝ 10/95 առաջնահերթություններով) տեղում վերագրում են նկարագրության տեքստը, ինչպես նաև երբ համակարգային հուշման, փոխանցման կամ հիշողության ներարկումը վերաձևավորում է հաղորդագրությունների զանգվածը։ Մոդելին ուղարկվող մարմինը մնում է անփոփոխ։ Դիտարկված հարցումը նաև որևէ կայուն Memory չի համալրում (բաց են թողնվում ինչպես հարցումից, այնպես էլ պատասխանից ստացվող տվյալների առանձնացումը), ուստի մոդելի սեփական պատասխանը չի կարող տրանսկրիպտի տեքստը կրկնօրինակել Memory-ում։

**Տեսանյութի չմշակված դաշտերը (#12430)։** Երբ կամուրջը միացված է, իսկ տեսանյութի բնիկ աջակցությունն անհայտ է կամ բացակայում է, սահմանված `transcript`/`audioTranscript` դաշտերը նույնպես ակտիվացնում են `videoBridgeObserved`-ը՝ նույնիսկ նկարագրության ձախողումից կամ `maxVideos` սահմանաչափից հետո։ `null`-ը և դատարկ տողերը հաշվի են առնվում, իսկ բացակայող դաշտերն ու տեսանյութին չվերաբերող մետատվյալները՝ ոչ։ Պահպանվող պատճեններում այդ դաշտերը քողարկվում են, կամ հարցումը բաց է թողնվում, իսկ քեշերը և Memory-ն շրջանցվում են։ Մատակարարի բեռնվածքը մնում է անփոփոխ։

Լրացուցիչ պահպանվող պատճեններն օգտագործում են դիտարկված հարցման նույն ազդանշանը։ Պաշտպանիչ սահմանափակումների կիրառումից առաջ ստացված հաճախորդի հարցման չմշակված ակնթարթային պատճենը, հիշողության մեջ սպասող հարցումը և վաղ մերժված հարցման մատյանը կառուցվածքային եղանակով փոխարինում են տեսանյութի մասերի տրանսկրիպտի դաշտերը։ Գործընթացաշարի փուլերի և համատեքստի փոխանցման միջոցով սինթեզված տողային հուշումները քողարկվում են պահպանվող հարցման մարմնի վերջնական ընդունիչում։ Պահպանված `video_content_removed` նշիչը ստիպում է, որ `previous_response_id`-ով շարունակումը փակ եղանակով ձախողվի՝ դիտավորյալ հեռացված տեքստը վերականգնելու փոխարեն։ Եթե դիտարկված հարցումը գրանցումից առաջ կորցնում է ըստ մասերի քողարկման իր ստվերը, կամ եթե տեսանյութի մի քանի ստվերներից թեկուզ մեկը չի համընկնում հարցման հետագա փոփոխություններից հետո, պահպանվող հարցման մարմինն ամբողջությամբ բաց է թողնվում՝ մասնակիորեն քողարկված տրանսկրիպտ պահպանելու փոխարեն։

Դիտարկված հարցման դեպքում մոդելի պատասխանը կարող է մեջբերել տրանսկրիպտի ցանկացած հատված՝ առանց կառուցվածքային նշման սահմանի։ Այդ պատճառով կանչերի մատյանում պահպանվող դրա `responseBody`-ն փոխարինվում է բացթողման նշիչով, իսկ գործընթացաշարի մանրամասն արտեֆակտը (որը կարող է ներառել վերին հոսքի/հաճախորդի մարմինները և հոսքի հատվածները) չի պահպանվում։ Իմաստային, իդեմպոտենտության և տրամաբանական վերարտադրման քեշերը շրջանցում են այդ հարցման ընթերցումներն ու գրառումները։ Մատակարարի հարցումը և հաճախորդին տեսանելի պատասխանը մնում են անփոփոխ։ Վաղ keepalive բայթերը հեռացվում են ժամանակավոր բուֆերից, երբ մանրամասն արտեֆակտը բաց է թողնվում։ Kiro-ի սխալ ձևավորված EventStream-ի նախազգուշացումը հաղորդում է միայն բեռնվածքի բայթերի քանակը և երբեք՝ դրա բովանդակությունը կամ JSON վերլուծիչի չմշակված սխալը։
Սա չի պնդում, որ մատակարարի/փլագինի հետ չկապված յուրաքանչյուր ախտորոշիչ հաղորդագրություն ստուգվել է․ պահպանվող ընդունիչների ավելի լայն ստուգումը հետևվում է #11658-ում։

Ներքին `/api/modality-bridge/video/drilldown` կենսացիկլը առանձին, loopback/token-ով իսկորոշված քեշային ենթաշերտ է։ Յուրաքանչյուր գործողություն պահանջում է նաև կանոնական, անթափանց principal ID։ Նախքան արտադրական կանչողին միացնելը՝ այն պետք է այդ ID-ն ածանցի իսկորոշված tenant-ից և երբեք չփոխանցի հաճախորդի ընտրած արժեքը։ Քեշի բանալիներն այդ principal-ը կապում են կանոնական session և video-reference ID-ների հետ, պահպանում են միայն դրանց SHA-256-ից ածանցված բանալիները և թե՛ ընթերցումները, թե՛ ջնջումը սահմանափակում են նույն principal-ի շրջանակով։ Քեշը յուրաքանչյուր գրառման համար պահում է առավելագույնը 16 ածանցված JPEG կադր, դրանք ժամկետանց է դարձնում տասը րոպե անց և աջակցում է սահմանափակված `start`/`end` ընթերցումներին կամ session-ի բացահայտ ջնջմանը։

Յուրաքանչյուր principal սահմանափակված է 16 գրառումով և 64 MiB կանոնական JPEG տվյալներով։ Այդ սահմանաչափերն անկախ են ընդհանուր 64 գրառում/256 MiB առավելագույն շեմից․ principal-ի քվոտայի ճնշման դեպքում նախ հեռացվում են միայն տվյալ principal-ի ամենաերկար ժամանակ չօգտագործված գրառումները, և միայն դրանից հետո է դիտարկվում ընդհանուր LRU հեռացումը։ Ժամկետանց գրառումները քեշային ակտիվության ժամանակ հեռացվում են ինչպես principal-ի, այնպես էլ ընդհանուր հաշվառումից, մինչդեռ չեղարկումը և վավերացման ձախողումը չեն գրանցում մասնակի փոխարինում։

Քեշը մերժում է ոչ կանոնական Base64-ը, ավելորդ լցոնումը, ոչ JPEG մեդիան, սխալ ձևավորված կամ
կրճատված JPEG-ները և այն JPEG-ները, որոնք սահմանափակ ամբողջական պատկերի `sharp`
վերծանման ընթացքում նախազգուշացում են առաջացնում։ Այն յուրաքանչյուր ընդունված պատկեր վերակոդավորում է որպես կանոնական JPEG, լայնությունն ու բարձրությունը
որոշում է վերծանված բայթերից՝ կանչողի դաշտերին վստահելու փոխարեն, և հեռացնում է վերջում կցված
պոլիգլոտ բայթերը՝ դրանք պահպանելու փոխարեն։ Երկու քվոտաների հաշվին էլ գրանցվում է միայն սահմանափակ կանոնական սեղմված բուֆերը։
JSON փոխանցման սահմանաչափը ներառում է Base64-ի հավելյալ ծավալը՝ 32 MiB
վերծանված մուտքային տվյալների առավելագույն չափի համար։ Յուրաքանչյուր
պահված ածանցում գրանցում է իր վավերացված JPEG ձևաչափը/լուծաչափը, նմուշառման քաղաքականությունը,
ածանցման տարբերակը, ստեղծման ժամանակը, սերվերի հաշվարկած բովանդակության հեշը և հեշավորված ծնող
հղումը՝ վստահելի կանչողի տրամադրած ծնող բովանդակության հեշի հետ միասին։ Չեղարկման առկայությունը ստուգվում է
ասինքրոն վերծանման/հեշավորման փուլերի միջև՝ ատոմային քեշային հաստատումից առաջ։

Այս փուլը դեռ չի միացնում արտադրական պրոդյուսերը երթուղուն և չի
ապահովում բազմալուծաչափ տարբերակների ընտրություն։ Հետևաբար Video Bridge-ի թափանցիկ հարցման
ուղին որևէ լրացուցիչ աշխատանք չի կատարում, մինչդեռ թենանտին կապված պրինցիպալի ածանցումը և
FU-08-ի ամբողջական բազմալուծաչափ կենսացիկլը մնում են հստակ հետագա աշխատանքներ, այլ
ոչ թե փաստաթղթավորված ավարտուն վարքագիծ։

Կադրերը հաջորդաբար մակագրում են կազմաձևված Video մոդելով։ Դատարկ
Video վերասահմանումը ժառանգում է Vision կարգավորումը․ եթե երկուսն էլ դատարկ են, Vision-ի
ավտոերթուղիչն ընտրում է տեսողական հնարավորություններով արդյունավետ մոդելը։ Հաջողված մակագրությունները
փոխարինում են սկզբնական մասը կայուն `[Video description:` նախածանցով, որը նաև
նշում է տեքստը որպես մեդիայից ածանցված անվստահելի դիտարկում և հաջորդող
մոդելներին հուշում է չհետևել մեդիայում հայտնաբերված հրահանգներին։ Կադրերի մակագրությունների քեշային բանալիները
ներառում են JPEG բայթերը, հուշումը, ժամանակադրոշմը և արդյունավետ մոդելը․ քեշավորվում են միայն հաջողված
մակագրությունները։ Քեշային գրառումները պահպանում են փաստացի հաջողված պրոդյուսեր մոդելը՝
ներառյալ պահուստային մոդելը․ երբ տարբեր կադրեր ստեղծվել են տարբեր մոդելների
կողմից, կամուրջը հաղորդում է `mixed`։ Քեշի համընկնման դեպքում վերօգտագործվում է այդ պրոդյուսերի ինքնությունը՝
այն որպես պահանջված երթուղավորման պլան վերապիտակավորելու փոխարեն։ Ամբողջ տեսանյութի արդյունքների
քեշի բանալին ձևավորվում է արդյունքը փոփոխող յուրաքանչյուր մուտքային տվյալից՝ հուշումից, արդյունավետ
մոդելից, նմուշառման քաղաքականությունից, կադրերի քանակից, իմաստաբանական վերլուծության ռեժիմից, նորմալացված
կենտրոնացման հուշման SHA-256 մատնահետքից, կենտրոնացման պատուհանից, `transcript`-ից,
`audioTranscript`-ից և կոնտակտային թերթիկի դրոշակից, ուստի այդ
չափումներից որևէ մեկի փոփոխությունը հանգեցնում է քեշի անհամընկնման, ոչ երբեք՝ հնացած արդյունքի վերօգտագործման։ Տեսողական կրկնօրինակների վերացման քաղաքականության
տարբերակը, շեմը և սահմանափակ թեկնածու կադրերի քանակը նույնպես հստակ ներառված են
արդյունքների քեշի բանալիում և մետատվյալներում․ հետևաբար քաղաքականության փոփոխությունը չի կարող վերօգտագործել հնացած
ամբողջական տեսանյութի նկարագրությունը։ Արդյունքների քեշի v4 մետատվյալները պահպանում են ռեժիմն ու
մատնահետքը, բայց երբեք՝ օգտատիրոջ չմշակված առաջադրանքը։ Պաշտպանիչ սահմանափակումների մետատվյալները հաղորդում են ինչպես
պահանջված, այնպես էլ արդյունավետ վերլուծության ռեժիմները․ առանց կիրառելի օգտատիրոջ տեքստի պահանջված `focused` ռեժիմը
հաղորդվում է որպես արդյունավետորեն `full`։

Պաշտպանիչ սահմանափակումը հանում է տեսանյութի յուրաքանչյուր աջակցվող մաս, սակայն նկարագրում է առավելագույնը
`modalityBridgeVideoMaxVideos` քանակով մասեր։ Այն թիրախի համար, որի
`supportsVideo === false` լինելը հաստատված է, անհաջող և սահմանաչափը գերազանցող տեսանյութերը վերածվում են հստակ անվտանգ
տեքստային նշիչների, որպեսզի որևէ չմշակված տեսանյութ չպահպանվի։ Երբ հնարավորությունն անհայտ է, այդ մասերը
մնում են անփոփոխ։ `supportsVideo === true` ունեցող թիրախները շրջանցում են կամուրջը։
Հաճախորդի հարցման ընդհատման ազդանշանը փոխանցվում է ներբեռնման, բրոքերի հերթի,
ենթապրոցեսների և մակագրումների կանչերի միջով․ ընդհատումները կանգ են առնում տեսանյութերի միջև և երբեք խափանման դեպքում
չեն թույլատրում չմշակված մեդիայի փոխանցումը։

Կատարման միջավայրի կարգավորումները պահվում են DB-ում և վավերացվում են Zod-ով․

| ----------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------- |

բրոքերի վերջնաժամկետը․ այդ սահմանաչափը գերազանցող կարգավորումների նոր գրանցումները մերժվում են։
`GET /api/modality-bridge/video/runtime`-ը մինչև նույնականացումը կամ կատարման միջավայրի ստուգումը պահանջում է վստահելի դրոշմված loopback
տեղայնություն, ապա՝ կառավարման
նույնականացում։ Այն վերադարձնում է միայն `available`, մաքրված FFmpeg/ffprobe տարբերակները և հաստատուն
պատճառ, երբ կատարման միջավայրն անհասանելի է։ Ներքին արտահանման վերջնակետը հանրային
վերբեռնման API չէ․ հերթի գերբեռնվածությունը վերադարձնում է `503`՝ `Retry-After`-ի հետ, կանչողի
անջատումը վերադարձնում է `499`, իսկ բրոքերի հաստատուն վերջնաժամկետը՝ `504`։ Փոխակերպված պատասխանները կենտրոնական
`x-omniroute-modality-bridge` վերնագրին ավելացնում են
`video->text;model=<visionModel>;parts=<videos>`՝ առանց Vision կամ Audio հատվածները հեռացնելու։

### PII քողարկիչ (`piiMasker.ts`)

Գործարկվում է **երկու** փուլերում էլ։

- **`preCall`**-ը կլոնավորում է օգտակար բեռը, շրջանցում `system`, `messages`, `input` և
  `prompt` դաշտերը (ներառյալ սովորական տողային տարրերը) և տողային
  `content`/`text` դաշտերի նկատմամբ կիրառում է `processPII()`-ը (`@/shared/utils/inputSanitizer`-ից)։ Երբ
  `PII_REDACTION_ENABLED=true`, հայտնաբերված անձնական նույնականացնող տեղեկությունները (PII) քողարկվում են ելքային
  օգտակար բեռում։ Սա անկախ է `INPUT_SANITIZER_MODE`-ից (որը վերահսկում է միայն
  հուշման ներարկման քաղաքականությունը)։ Երբ քողարկումն անջատված է, կանչը գրանցում է հայտնաբերումների
  քանակը՝ առանց բովանդակությունը վերագրելու։
- **`postCall`**-ը ստեղծում է պատասխանի խորը կլոն, գործարկում `sanitizePIIResponse()`-ը և
  Responses API-ի ձևաչափի քողարկիչը (`maskResponsesOutput` — ընդգրկում է
  `output_text` և `output[].content[].text`)։ Եթե որևէ քողարկում է կատարվում,
  փոփոխված պատասխանը փոխարինում է սկզբնականին։

Պաշտպանիչ մեխանիզմը երբեք չի արգելափակում․ այն միայն ավելացնում է նշումներ (`meta.detections`,
`meta.redacted`) կամ վերագրում է բովանդակությունը։

### Հուշման ներարկում (`promptInjection.ts`)

Հայտնաբերում է օգտատիրոջ տրամադրած բովանդակության հակազդող կառուցվածքները և կիրառում
կարգավորված քաղաքականությունը։ Վարքագիծը որոշվում է միջավայրի փոփոխականներով և կոնստրուկտորի
ընտրանքներով․

| Կարգավորում      | Միջավայրի փոփոխական                                                                                        | Լռելյայն | Արդյունք                                                                                                                                                                                                                     |
| ---------------- | ---------------------------------------------------------------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Միացված է        | `INPUT_SANITIZER_ENABLED`                                                                                  | `true`   | Երբ `false` է, պաշտպանիչ մեխանիզմը անմիջապես ավարտում է աշխատանքը։                                                                                                                                                           |
| Ռեժիմ            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                            | `warn`   | Ներարկման քաղաքականություն՝ `block`, `warn` կամ `log`։ (`redact`-ն ընդունվում է հետադարձ համատեղելիության համար, բայց **չի** հեռացնում ներարկման տեքստը․ հարցման PII-ի վերագրումը վերահսկվում է `PII_REDACTION_ENABLED`-ով։) |
| Արգելափակման շեմ | `blockThreshold` ընտրանք / `INPUT_SANITIZER_BLOCK_THRESHOLD` (այլանուն՝ `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`   | Արգելափակման համար պահանջվող նվազագույն լրջությունը։ Լռելյայն կարգավորման դեպքում միջին մակարդակը միայն դիտարկվում է։                                                                                                        |

**Ռեժիմի առաջնահերթությունը** (`getMode`)՝ կանչողի `options.mode` →
`INJECTION_GUARD_MODE`-ի **ՏԲ-ի գործառույթի դրոշակի վերասահմանում** (Կառավարման վահանակ → Կարգավորումներ →
Գործառույթների դրոշակներ) → միջավայրի `INJECTION_GUARD_MODE` → միջավայրի `INPUT_SANITIZER_MODE` →
`warn`։ Այսպիսով, կառավարման վահանակի վերասահմանումը գերակայում է միջավայրի փոփոխականների նկատմամբ, ուստի Գործառույթների
դրոշակների միջերեսը վերահսկում է գործող պաշտպանիչ մեխանիզմը իրական ժամանակում (առանց վերագործարկման)։ ՏԲ-ից ընթերցումը խափանումների նկատմամբ անվտանգ է․
սխալի դեպքում պաշտպանիչ մեխանիզմը վերադառնում է միջավայրի վրա հիմնված վարքագծին, իսկ երբ
վերասահմանում սահմանված չէ, վարքագիծը նույնական է միայն միջավայրի փոփոխականների միջոցով որոշվող վարքագծին։

Հայտնաբերման աղբյուրները․

1. `sanitizeRequest()`՝ `@/shared/utils/inputSanitizer`-ից (ընդհանուր հայտնաբերիչների
   հավաքածու, որն օգտագործվում է նաև մշակման շղթայի այլ մասերում)։
2. Ներկառուցված `DEFAULT_GUARD_PATTERNS` (ներկայում՝ `system_override_inline` և
   `markdown_system_block`, երկուսն էլ՝ `high` լրջությամբ)։
3. Կոնստրուկտորի ընտրանքների միջոցով փոխանցված ոչ պարտադիր `customPatterns` (տողեր, կանոնավոր արտահայտություններ
   կամ `{ name, pattern, severity }` գրառումներ)։

Երբ `mode === "block"` է, **և** առնվազն մեկ հայտնաբերում համապատասխանում է լրջության
շեմին, `preCall`-ը վերադարձնում է `{ block: true, message: "Request rejected:
suspicious content detected" }`։ `warn`/`log` ռեժիմներում պաշտպանիչ մեխանիզմը գրանցում է իրադարձությունը, բայց
թույլատրում է կանչը։ Ընդհանուր `evaluatePromptInjection()` օժանդակ ֆունկցիան նույնպես արտահանվում է
այն կանչողների համար, որոնք պետք է գնահատեն հուշումները՝ առանց ռեեստրի միջոցով անցնելու։

**Սկանավորման սահմանը (v3.8.20)․** հայտնաբերիչը ստուգում է միայն միացված հուշման տեքստի
**առաջին 16 KB**-ը՝ `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 բայթ)
`src/shared/utils/inputSanitizer.ts`-ում։ Թե՛ `detectInjection()`-ը, թե՛
`evaluatePromptInjection()`-ը կիրառում են `slice(0, MAX_INJECTION_SCAN_BYTES)`՝ նախքան
ձևանմուշների ցիկլը գործարկելը։ Ներարկման հրահանգները սովորաբար գտնվում են մուտքային տվյալների սկզբնամասում, ուստի սա
սահմանափակում է կանոնավոր արտահայտությունների CPU/GC ծախսը հարյուրավոր ԿԲ չափով օգտակար բեռների դեպքում՝ առանց հայտնաբերման արդյունավետությունը նվազեցնելու (տես՝
#3932, #4041)։

### Հավատարմագրերի քողարկիչ (`credentialMasker.ts`)

Գործարկվում է **երկու** փուլերում էլ՝ լռելյայն շղթայում վերջինը (առաջնահերթություն՝ `95`)։ Քողարկում է
հայտնի API բանալիների / գաղտնի թոքենների ձևանմուշները ելքային օգտակար բեռից (հաղորդագրության
բովանդակություն, գործիքի կանչի արգումենտներ, գործիքի արդյունքներ) **և** մատակարարի պատասխանից, որպեսզի
հուշման մեջ տեղադրված (կամ գործիքի արդյունքով կրկնված) հավատարմագիրը չարտահոսի
դեպի վերին մակարդակի մատակարար կամ հետ՝ դեպի հաճախորդ։

- **Միայն բացահայտ միացմամբ**, նույն սկզբունքով, ինչ PII-ի քողարկումը (Խիստ կանոն #20-ին հարակից).
  անջատված է, եթե `settings.credentialRedactionEnabled === true` **կամ**
  `CREDENTIAL_REDACTION_ENABLED=true` չէ։ Երբ այն անջատված է, պաշտպանիչ մեխանիզմը ոչինչ չի անում՝
  այն երբեք չի արգելափակում և երբեք չի վերագրում։
- `redactCredentials()`-ը շրջանցում է օգտակար բեռնվածքի/պատասխանի ամբողջ ծառը (`walkValue()`,
  պաշտպանված է նախատիպի աղտոտումից, իսկ ցիկլերից՝ `WeakSet`-ի միջոցով) և համընկնումները փոխարինում է
  `[REDACTED:<type>]` տեղապահով՝ պատճենելով միայն այն ճյուղերը, որոնք իրականում
  փոխվել են։
- `CREDENTIAL_PATTERNS`-ը ներառում է LLM մատակարարների բանալիները (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS թոքենները (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), վճարային բանալիները (Stripe, Square), ամպային
  բանալիները (AWS մուտքի բանալի, Twilio, SendGrid, Mailgun), մասնավոր բանալիները / JWT-ները,
  հավատարմագրեր պարունակող միացման տողերը (`mongodb://user:pass@...` և այլն), ինչպես նաև
  `Authorization`/`x-api-key`/`api-key`/`apikey` վերնագրի արժեքների ընդհանուր
  օրինաչափությունը։ Վերնագրի տեսք ունեցող բանալիները (`authorization`, `x-api-key`, `api-key`,
  `apikey`) քողարկվում են կառուցվածքային եղանակով (միայն արժեքը, իսկ սխեմայի նախածանցը, օրինակ՝
  `Bearer `/`Basic `, պահպանվում է), այլ ոչ թե տեքստի ընդհանուր կանոնավոր արտահայտության միջոցով։
- Պաշտպանիչ մեխանիզմը երբեք չի արգելափակում. այն միայն վերագրում է (`modifiedPayload` /
  `modifiedResponse`) և նշագրում (`meta.credentialsRedacted`, `meta.count`)։

Ռեգրեսիայի պաշտպանիչ թեստ՝ `tests/unit/credential-masker-guardrail.test.ts`։

## Հիմնական պայմանագիր (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true-ը անմիջապես դադարեցնում է շղթայի կատարումը
  message?: string; // ցուցադրվում է արգելափակման ժամանակ
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // վերադարձվում է preCall-ի կողմից՝ հարցումը վերագրելու համար
  modifiedResponse?: TValue; // վերադարձվում է postCall-ի կողմից՝ պատասխանը վերագրելու համար
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Պաշտպանիչ սահմանափակումը ազդարարում է «փոփոխություն չկա»՝ վերադարձնելով կա՛մ `void`, կա՛մ `{}`, կա՛մ
`{ block: false }`։ `modifiedPayload`/`modifiedResponse` վերադարձնելը փոխարինում է
շղթայով դեպի հաջորդ պաշտպանիչ սահմանափակումներ փոխանցվող արժեքը։
`signal?: AbortSignal`-ը կանչողի կենսացիկլը փոխանցում է պաշտպանիչ սահմանափակումներին։ Հարցման ընդհատումը կանխամտածված fail-open բացառություն է․ մեդիա կամուրջները դադարեցնում են աշխատանքը և մաքրում ռեսուրսները՝ առանց չմշակված մեդիան վերականգնելու այն թիրախի համար, որը, ինչպես հայտնի է, չի աջակցում այն։

## Ռեեստր (`registry.ts`)

`guardrailRegistry` եզակի օրինակը տրամադրում է՝

- `register(guardrail)` — ավելացնում է պաշտպանիչ սահմանափակում (կամ փոխարինում է այն ըստ նորմալացված անվան) և
  վերադասավորում ըստ աճող `priority`-ի։
- `clear()` / `list()` — վարչական օժանդակ մեթոդներ։
- `runPreCallHooks(payload, context)` — հերթով մշակում է ակտիվ պաշտպանիչ սահմանափակումները, փոխանցում է
  payload-ը `modifiedPayload`-ի միջոցով և կանգ է առնում առաջին `block: true`-ի դեպքում։
- `runPostCallHooks(response, context)` — նույն հոսքը պատասխանի կողմում։
- `resetGuardrailsForTests({ registerDefaults })` — մաքրում է վիճակը և, ըստ անհրաժեշտության,
  վերագրանցում է լռելյայնները՝ թեստերի մաքուր մեկուսացման համար։

Երկու գործարկիչներն էլ վերադարձնում են `{ blocked, payload|response, results, guardrail?, message? }`,
որտեղ `results`-ը `GuardrailExecutionResult` գրառումների զանգված է, որոնք ներառում են
յուրաքանչյուր պաշտպանիչ սահմանափակման `blocked`, `skipped`, `modified`, `error` և `meta` դաշտերը,
որոնք օգտակար են հետագծման համար։

### Յուրաքանչյուր հարցման համար պաշտպանիչ սահմանափակումների անջատում

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })`-ը հավաքում է
պաշտպանիչ սահմանափակումների անունների կրկնազերծված ցանկ, որոնք պետք է բաց թողնվեն ընթացիկ
հարցման համար։ Աղբյուրները (բոլորն ընտրովի են, բոլորը միավորվում են)՝

- `apiKeyInfo.disabledGuardrails`
- Հարցման մարմնի `disabledGuardrails` (վերին մակարդակում)
- Հարցման մարմնի `metadata.disabledGuardrails`
- `x-omniroute-disabled-guardrails` վերնագիր (կամ հին
  `x-disabled-guardrails`)

Արժեքները կարող են լինել տողերի զանգվածներ կամ ստորակետերով բաժանված տող․ անունները
նորմալացվում են փոքրատառ kebab-case ձևաչափի (`pii_masker` → `pii-masker`)։ Արդյունքը
`context.disabledGuardrails`-ի միջոցով փոխանցվում է ռեեստրին, որը բաց է թողնում
համապատասխան պաշտպանիչ սահմանափակումները (`skipped: true`՝ `results`-ում)։

## Կատարման հերթականություն

`src/sse/handlers/chat.ts`-ով և
`open-sse/handlers/chatCore.ts`-ով անցնող յուրաքանչյուր հարցման համար՝

1. `resolveDisabledGuardrails(...)`-ը API բանալիից, հարցման մարմնից և
   վերնագրերից կազմում է բաց թողնման ցանկը։
2. `guardrailRegistry.runPreCallHooks(body, ctx)`-ը պաշտպանիչ սահմանափակումները գործարկում է
   առաջնահերթության աճման կարգով՝
   - Անջատված պաշտպանիչ սահմանափակումներն արձանագրվում են որպես `skipped`։
   - Յուրաքանչյուր պաշտպանիչ սահմանափակման `preCall`-ը կարող է վերագրել օգտակար բեռը՝ օգտագործելով `modifiedPayload`։
   - Առաջին `block: true`-ն անմիջապես ընդհատում է շղթան, և մշակիչը վերադարձնում է
     պաշտպանիչ սահմանափակման մերժման պատասխան։
3. Հնարավոր վերագրված օգտակար բեռը փոխանցվում է համակցված երթուղավորմանը և վերին հոսքի
   ուղարկմանը։
4. Պատասխանը կազմելուց հետո `guardrailRegistry.runPostCallHooks(...)`-ը
   պատասխանի վրա գործարկում է նույն շղթան։ Այստեղ `block: true`-ն հեռացնում է վերին հոսքի
   պատասխանը։

Սխալ արձակող պաշտպանիչ սահմանափակումներն արձանագրվում են `error: <message>`-ով և գրանցվում
`logger.warn`-ի միջոցով, սակայն շղթան շարունակվում է. նախագծմամբ կիրառվում է սխալի դեպքում թույլատրելու մոտեցումը։

## Կազմաձևում

Ներկառուցված պաշտպանիչ սահմանափակումների կողմից ընթերցվող միջավայրի փոփոխականները՝

| Փոփոխական                             | Օգտագործվում է             | Ազդեցություն                                                                                                                  |
| ------------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | Հայտնաբերումն ամբողջությամբ անջատելու համար սահմանեք `false`։                                                                 |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | Ներարկման քաղաքականությունը՝ `warn`, `block` կամ `log`։ Հնացած `redact` արժեքը չի վերագրում ներարկման տեքստը։                 |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | Ներարկման պաշտպանիչի ռեժիմը. նաև ՏԲ-ի գործառույթի դրոշակ է, որը **գերակայում է** միջավայրի փոփոխականների նկատմամբ (DB > ENV)։ |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | Նվազագույն խստությունը, որը մերժվում է `MODE=block`-ի դեպքում՝ `high` (լռելյայն), `medium` կամ `low`։                         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD`-ի հնացած այլանունը։                                                                         |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | Երբ `true` է, հարցման PII-ը քողարկվում է՝ անկախ ներարկման ռեժիմից։                                                            |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ներքևի հոսք) | Կառավարում է պատասխանի կողմում քողարկիչի վարքագիծը։                                                                           |

Մոդալության կամրջի պաշտպանիչ սահմանափակումները կատարման ժամանակի կազմաձևումն ընթերցում են ՏԲ-ով ապահովվող կարգավորումների
պահոցից (`getSettings()`), ոչ թե միջավայրի փոփոխականներից։ Պատկերի մշակման հիմնական բանալիներն են՝
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` և
`modalityBridgeCacheMaxEntries`։ Հնացած
`visionBridge*` բանալիներն ընդունվում են միայն որպես փաստաթղթավորված՝ մեկ ցիկլի ընթերցման
պահուստային տարբերակ. կառավարման վահանակից գրանցումները կիրառում են հիմնական բանալիները։ Լռելյայն արժեքները և պահուստային
լուծիչը գտնվում են `src/shared/constants/modalityBridgeDefaults.ts`-ում, իսկ հնացած
հաստատունները պահպանվում են `src/shared/constants/visionBridgeDefaults.ts`-ում։

Ձայնի մշակումն օգտագործում է `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` և `modalityBridgeAudioMaxClips`, ինչպես նաև ընդհանուր
`modalityBridgeCache*` կարգավորումները։ Ձայնի մշակման համար հնացած բանալիների պահուստային տարբերակ չկա, քանի որ այս
բանալիները ներդրվել են Մոդալության կամրջի սխեմայի հետ։

Տեսանյութի մշակումն օգտագործում է `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` և
`modalityBridgeVideoTimeout`, ինչպես նաև ընդհանուր `modalityBridgeCache*` կարգավորումները։
Այն լռելյայն անջատված է, քանի որ FFmpeg/ffprobe-ը ոչ պարտադիր գործառնական
կախվածություններ են, իսկ կադրերի նկարագրությունների ստեղծումն ավելացնում է ուշացումն ու մոդելի օգտագործման արժեքը։

## Հատուկ պաշտպանիչ կանոններ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Քայլեր՝

1. Ստեղծեք `src/lib/guardrails/myGuardrail.ts`՝ ընդլայնելով `BaseGuardrail`-ը։
2. Իրագործեք `preCall`-ը և/կամ `postCall`-ը։
3. Կամ գրանցեք ներմուծման պահին (`registerDefaultGuardrails`-ից ավելացնելով), կամ
   գործարկման ընթացքում կանչեք `guardrailRegistry.register(...)`-ը․ ռեեստրը փոխարինում է
   նույն նորմալացված անունն ունեցող ցանկացած նախորդ պաշտպանիչ կանոն։
4. Ավելացրեք թեստեր `tests/unit/`-ում (առկա օրինակներ՝
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)։

## Թեստավորում

Թեստերի միջև օգտագործեք `resetGuardrailsForTests()`՝ հայտնի վիճակից սկսելու համար։
Փոխանցեք `{ registerDefaults: false }`՝ դատարկ ռեեստրից սկսելու և
միայն թեստավորվող պաշտպանիչ կանոնները գրանցելու համար։ Vision Bridge-ն աջակցում է կախվածությունների
ներմուծմանը (`deps.getSettings`, `deps.callVisionModel`), իսկ Audio Bridge-ը տրամադրում է
համարժեք միջերեսներ՝ կարգավորումների, հնարավորությունների, STT մոդելի ընտրության, հավատարմագրերի
ստուգումների և տրանսկրիպցիայի համար։ Հետևաբար, թեստերը կարող են ստուգել երկու հոսքերն էլ՝ առանց DB-ի
կամ ցանցային հասանելիության։

## Ներարկման պաշտպանիչ կանոնով երթուղիների ծածկույթ և red-team թեստավորում (Փուլ 8 · Բլոկ D)

Ներարկման պաշտպանիչ կանոնը (`createInjectionGuard` / `withInjectionGuard`) ընդգրկում է օգտատիրոջ հուշումներ
ընդունող բոլոր երթուղիները։ Այն հաշվի է առնում `INJECTION_GUARD_MODE`-ը (լռելյայն՝ `warn` = միայն գրանցել մատյանում,
`block` = վերադարձնում է HTTP 400 `SECURITY_001`)։

| Տեսակ        | Երթուղիներ                                                                                                                                           | Լռելյայն ռեժիմ |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| Տեքստ (առկա) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn           |
| Գեներատիվ    | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn           |
| Տվյալներ     | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn           |

Տեքստի արտաբերումը (`extractMessageContents`) ներառում է `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`։

**Red-team (ամեն գիշեր, `nightly-llm-security.yml`)․** promptfoo-ն ստուգում է, որ յուրաքանչյուր երթուղի արգելափակում է
OWASP-LLM կորպուսը `INJECTION_GUARD_MODE=block` ռեժիմում, իսկ garak-ը կատարում է ստուգումներ (գաղտնիքի բացակայության դեպքում՝ բաց է թողնում)։
`moderations`-ը ներառված է հետևողականության համար․ արգելափակման ռեժիմն օգտագործող օպերատորները կարող են այն բացառել
`resolveDisabledGuardrails`-ի միջոցով։

Գիշերային աշխատանքային հոսքը (`.github/workflows/nightly-llm-security.yml`, cron + ձեռքով
գործարկում) ունի երկու առաջադրանք՝

- **`promptfoo-guard` (արգելափակող)** — գործարկում է `promptfoo eval -c promptfooconfig.yaml`-ը
  `INJECTION_GUARD_MODE=block`-ով։ Յուրաքանչյուր հակառակորդային դեպք (օրինակ՝ «անտեսիր բոլոր
  նախորդ հրահանգները…», DAN ոճի jailbreak-ներ) հաստատում է, որ պատասխանը պարունակում է
  `error.code === "SECURITY_001"`, այսինքն՝ պաշտպանիչ կանոնն իսկապես մերժել է հարցումը։
- **`garak` (խորհրդատվական)** — գործարկում է garak-ը `--probes promptinject,dan,leakreplay`-ով
  տեղային OmniRoute օրինակի (`http://localhost:20128/v1`) նկատմամբ։ Պայմանավորված է
  մատակարարի գաղտնիքի (`PROMPTFOO_PROVIDER_KEY`) առկայությամբ․ դրա բացակայության դեպքում առանց սխալի բաց է թողնվում և վերջում
  ունի `|| true`, ուստի այն հաշվետվություն է ներկայացնում՝ առանց CI-ն ձախողելու։
