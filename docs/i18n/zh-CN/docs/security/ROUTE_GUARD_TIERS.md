## 概述

所有 OmniRoute 管理 API 路由均被划分为三个保护层级之一。分类是静态的，定义于 `src/server/authz/routeGuard.ts` 中，并在运行任何其他身份验证分支之前进行评估。

## 层级

### 层级 1 — LOCAL_ONLY

**执行方式：** `isLocalOnlyPath(path)` → 环回主机检查  
**绕过方式：** 默认不可绕过。对于 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` 中的路径，存在一个范围严格受限的例外：当请求携带具有 `manage` 作用域的有效 API 密钥时可绕过（参见 [manage 作用域例外](#manage-scope-carve-out)）。

这些路由会生成子进程或执行运行时代码。将它们暴露给非环回流量，会使已获取有效 JWT 的攻击者（例如通过 Cloudflared/Ngrok 隧道）能够触发进程生成——这是一类已知的 CVE（[GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)）。

**GHSA-fhh6-4qxv-rpqj 是什么（攻击类型）：** 管理/代理服务器暴露了一个可启动子进程的端点（`npm install`、`node`、浏览器、代理、`git`、`tar` 等）。如果该端点可从主机外部访问——例如，运维人员将 OmniRoute 部署在 nginx/Cloudflare/Tailscale 隧道之后，并且 JWT 泄露或身份验证配置错误——攻击者便可将“调用 API”转变为“在主机上运行命令”（远程代码执行）。OmniRoute 通过对每个能够生成进程的路由**在任何身份验证检查之前无条件执行环回主机检查**来阻止这种情况：即使令牌通过隧道泄露，也仍然无法访问进程生成能力。

**完整的 LOCAL_ONLY 集合。** 权威来源是 `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`；下表反映了当前状态。`check-route-guard-membership` 门禁会枚举所有支持进程生成的前缀下的每个 `route.ts`，如果其中任何一个未被归类为仅限本地访问，CI 就会失败。

#### 管理作用域例外

仅当请求携带 `Authorization: Bearer <api-key>`，且其元数据包含
`manage` 作用域（或 `admin`）时，才可以从非环回地址访问部分 LOCAL_ONLY
路径。此例外通过 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` 按路径显式启用，
因此任何新增 LOCAL_ONLY 路径默认仍严格限制为仅允许环回地址访问。未经身份验证的
请求以及使用不具备管理作用域的密钥发起的请求仍将被拒绝，并返回
`403 LOCAL_ONLY`。

目前唯一可以绕过限制的前缀是 `/api/mcp/`。`/api/cli-tools/runtime/` 和
`/api/services/` 被有意排除，因为它们可以生成任意子进程
（`npm install`、`node`），而这正是 LOCAL_ONLY 层旨在防范的
CVE 类型。

**#7895 — `mcp:connect` 窄作用域：** `/api/mcp/` 例外还接受
持有窄作用域 `mcp:connect`
（`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`）的 Bearer 密钥，
该作用域通过 `src/server/authz/policies/management.ts` 中的
`hasMcpConnectOrManageScope()` 进行检查。此作用域仅适用于 `/api/mcp/` —
`mcp:connect` 不会授予对任何其他管理路由的权限（包括以后可能添加的任何其他
LOCAL_ONLY 绕过前缀），并且它被特意排除在
`MANAGEMENT_API_KEY_SCOPES` 之外。持有 `manage`/`admin` 的密钥仍会与之前完全一样
通过此例外；对于只应远程调用 MCP 且不需要广泛管理访问权限的调用方，
`mcp:connect` 是一种权限更低的替代方案。

| 请求                                             | 路径                       | 结果             |
| ------------------------------------------------ | -------------------------- | ---------------- |
| 非环回地址，无 Bearer                            | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| 非环回地址，Bearer 具有 `manage` 作用域          | `/api/mcp/*`               | 允许             |
| 非环回地址，Bearer 具有 `mcp:connect` 作用域     | `/api/mcp/*`               | 允许             |
| 非环回地址，Bearer 不具有 `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| 非环回地址，Bearer 具有 `mcp:connect` 作用域     | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| 非环回地址，Bearer 具有 `manage` 作用域          | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| 环回地址，有或无任意 Bearer                      | 任意 LOCAL_ONLY            | 允许（通过门控） |

#### 运维人员指南与审计

如果你在反向代理或隧道（nginx、Caddy、Cloudflare Tunnel、Tailscale、Ngrok）
后运行 OmniRoute，环回检查仍会保护上述具备进程生成能力的路由 — 客户端地址为
非环回地址的请求会在**身份验证运行之前**被拒绝并返回 `403 LOCAL_ONLY`，
因此泄露的 JWT 无法触发进程生成。运维人员仍需承担两项责任：

- **不要通过将客户端 IP 伪造成回环地址来“修复” 403。** 设置
  `X-Forwarded-For: 127.0.0.1`，或使用将源地址重写为
  回环地址的代理，会重新引入本层所封堵的同一类 RCE 漏洞。请通过代理公开
  仪表板/API——绝不要公开具备进程启动能力的路由。
- **将管理作用域绕过权限保持在最低限度。** 只有 `/api/mcp/` 可以绕过，
  且只能使用具有 `manage` 作用域的 API 密钥。`SPAWN_CAPABLE_PREFIXES` 永远不能
  添加到绕过列表中——zod schema 会拒绝它们，并且
  `isLocalOnlyBypassableByManageScope` 会在运行时阻止它们（纵深防御），
  这正是仪表板中“无法设为可绕过”的含义。运行时
  快照加载器也会从已存储的设置行中丢弃此类条目，而
  旧版 JSON 导入（`/api/settings/import-json`）绝不会写入绕过键。
  每个 `LOCAL_ONLY_API_PREFIXES` 条目必须位于拒绝列表中，或
  已经过可绕过资格审查（`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`）。位于
  `/api/providers/` 下具备进程启动能力的动态段和静态路径路由（例如 `/login`、
  `/refresh-cursor`）由基于正则表达式的 `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` 配套项覆盖，该配套项位于
  `src/shared/constants/spawnCapablePrefixes.ts` 中，而不是由扁平的
  `SPAWN_CAPABLE_PREFIXES` 数组覆盖——若要捕获这些路由，扁平数组必须覆盖
  整个 `/api/providers/` 前缀，这会使远程仪表板合理用于提供者 CRUD 的
  路由树范围被过度扩大。

**审计访问**——要验证没有任何来自主机外部的请求到达这些路由：

- 在 `/dashboard/settings/security` 打开 **授权清单**：其中会呈现实时的
  LOCAL_ONLY 前缀列表、哪些前缀可绕过，以及编译时确定的
  具备进程启动能力（“无法设为可绕过”）的集合。
- 在反向代理/访问日志中 grep 上述前缀，并查找与非回环客户端地址配对的记录。
  任何此类命中若返回 `200` 而不是 `403 LOCAL_ONLY`，都意味着代理正在掩盖
  真实客户端 IP——请修复代理。
- OmniRoute 日志中这些路径之一出现 `403 LOCAL_ONLY`，表示防护机制正在
  按预期工作，而不是应当抑制的错误。

### 第 2 层 — ALWAYS_PROTECTED

**强制执行者：** `isAlwaysProtectedPath(path)` → 跳过 `requireLogin=false` 绕过
**绕过：** 当 `requireLogin=false` 时也无法绕过；始终需要 JWT

这些路由具有破坏性或不可逆性。若允许在“无密码”
安装中访问它们，则同一 LAN 上的任何人都可以擦除数据库或终止
服务器进程。

| 路径                                      | 原因                                           |
| ----------------------------------------- | ---------------------------------------------- |
| `/api/shutdown`                           | 终止服务器进程                                 |
| `/api/settings/database`                  | 数据库导出、导入和擦除                         |
| `/api/db-backups`                         | 完整数据库备份归档访问                         |
| `/api/settings/export-json`               | 导出完整设置数据块（包括机密信息）             |
| `/api/settings/import-json`               | 替换完整设置数据块                             |
| `/api/providers/health-autopilot/actions` | 执行自动驾驶修复操作                           |
| `/api/settings/obsidian`                  | 为任意保管库根目录签发可重复使用的 WebDAV 凭据 |

**违规时的响应：** `401 Authentication required`

`/api/settings/obsidian` 涵盖其 `/webdav` 子路由：`POST` 会将 WebDAV 文件服务——
由自定义 Node 层在 Next.js 之前、此管线之外提供——指向调用者选择的根目录，
并回显新签发的 Basic 凭据；`DELETE` 会轮换这些凭据，而父级 `POST` 则会存储
Obsidian REST API 令牌。GHSA-62vw 仅掩盖了 `GET` 中暴露密码的问题；凭据签发
仍处于故障开放层级（GHSA-7pq4-8pvv-rx7r）。`enableObsidianVaultSync()` 还会
拒绝以下保管库：其本身就是数据目录、位于数据目录内，或包含数据目录。

### 全新安装的引导仅限回环访问——依据真实对等方，而非 `Host`

在未配置管理密码（且没有 `INITIAL_PASSWORD`）时，
`src/shared/utils/apiAuth.ts` 中的 `isAuthRequired()` **仅对回环对等方**
保持匿名引导开放。是否为回环地址根据可信的对等方信号按以下顺序判定：
由令牌盖章的真实 TCP 对等方（`PEER_IP_HEADER` + `VIA_PROXY_HEADER`，即策略所见内容）、
管线自身的 `AUTHZ_HEADER_PEER_LOCALITY` 判定结果（即路由处理程序所见内容，
仅在设置了 `OMNIROUTE_PEER_STAMP_TOKEN` 时才受信任），或直接调用者的真实
套接字对等方。绝不会参考 `Host` / `nextUrl.hostname`，且首次密码写入
（`POST /api/settings/require-login`）同样受此约束，而不是向所有
网络对等方开放（GHSA-7pq4-8pvv-rx7r）。`managementPolicy` 会显式向下传递
自己的 `peerContext` 判定结果，因此原始（剥离前）请求中的标头绝不会决定该结果。

### 第 3 层 — MANAGEMENT（默认）

所有其他管理路由。除非配置了 `requireLogin=false`，否则需要身份验证。
CLI 令牌可以对这些路由进行身份验证（回环地址 + 有效 HMAC）。

## 评估顺序

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → 回环地址                                  → 继续执行
     → 非回环地址、具有 manage 作用域的 Bearer
        且 isLocalOnlyBypassableByManageScope   → 允许 (management_key)
     → 否则                                      → 拒绝 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → 允许 (system)
  3. hasValidCliToken(headers)?
     → 允许 (cli) [回环地址 + timingSafeEqual HMAC 检查]
  4. isAlwaysProtectedPath(path) 或 requireLogin=true?
     → isDashboardSessionAuthenticated?
        → 允许 (dashboard_session)
     → 不可绕过路径上的具有 manage 作用域的 Bearer?
        → 允许 (management_key)
     → 拒绝 401/403
  5. requireLogin=false?
     → 允许 (anonymous)
```

步骤 1 中的 manage 作用域分支是唯一能够满足 LOCAL_ONLY 路由要求的认证路径；认证后端故障时返回 503（而不是 403），因此数据库过期不会静默降级为“拒绝”。

## 添加具有进程启动能力的新路由

1. 将路径前缀添加到
   `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_API_PREFIXES`
2. 在 `tests/unit/authz/routeGuard.test.ts` 中添加测试，断言
   `isLocalOnlyPath()` 对新前缀返回 true
3. **绝不要跳过此步骤** — 请参阅 `CLAUDE.md` 中的硬性规则 #15
4. 决定：此路由是否也应属于 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`？
   默认答案是**否**。仅当该路由可以安全地向 manage 作用域持有者公开时才选择加入（即不会启动任意用户控制的代码）。

## 添加可由 manage 作用域绕过的路径

1. 确认该路由不会执行用户提供的代码或命令。如果会，请停止 — 此例外机制并不适用。
2. 将前缀追加到
   `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`
3. 在 `tests/unit/authz/management-policy.test.ts` 中为全部四种请求形式添加覆盖：无 Bearer（403）、manage Bearer（允许）、非 manage Bearer（403），以及针对每个前缀的回归测试，确保 `/api/cli-tools/runtime/*` 即使带有 manage Bearer 也始终严格限制为回环地址。

## 在 OpenAPI 中记录安全层级

向 `docs/openapi.yaml` 添加新路由时，如果该路由已由 `routeGuard.ts` 分类，请应用对应的供应商扩展：

| routeGuard.ts 分类           | YAML 注解                  | 强制执行规则                             |
| ---------------------------- | -------------------------- | ---------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`    | `x-loopback-only: true`    | 无条件阻止来自非回环地址的访问           |
| `ALWAYS_PROTECTED_API_PATHS` | `x-always-protected: true` | 即使 `requireLogin=false` 也要求认证     |
| 内部管理/调试路由            | `x-internal: true`         | 默认不在 /dashboard/api-endpoints 中显示 |
| 无（公开/标准认证）          | （无需注解）               | 由标准 `requireLogin` 控制的访问         |

### 验证

以下两个脚本用于确保 YAML 注解与 `routeGuard.ts` 之间的一致性：

- `scripts/check/check-openapi-coverage.mjs` — 覆盖率低于 99% 时失败
- `scripts/check/check-openapi-security-tiers.mjs` — 当 `x-loopback-only` 或
  `x-always-protected` 注解与编译时常量不一致时失败

这两个脚本都会在预提交钩子和 CI 中运行。

### 误报规则

如果某个路由带有 `x-always-protected` 或 `x-loopback-only` 注解，但并不在
`routeGuard.ts` 常量中，覆盖率脚本将失败。正确的修复方式始终是让 YAML 与
`routeGuard.ts` 实际强制执行的规则保持一致 — 而不是在尚未实现相应强制执行逻辑的情况下，将路由添加到 `routeGuard.ts`。
