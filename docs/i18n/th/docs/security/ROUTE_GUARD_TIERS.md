## ภาพรวม

เส้นทาง API สำหรับการจัดการ OmniRoute ทั้งหมดจะถูกจัดประเภทให้อยู่ในระดับการป้องกัน
หนึ่งในสามระดับ การจัดประเภทนี้เป็นแบบคงที่ โดยกำหนดไว้ใน `src/server/authz/routeGuard.ts`
และได้รับการประเมินก่อนที่สาขาการตรวจสอบสิทธิ์อื่นใดจะทำงาน

## ระดับ

### ระดับ 1 — LOCAL_ONLY

**บังคับใช้โดย:** `isLocalOnlyPath(path)` → การตรวจสอบโฮสต์แบบลูปแบ็ก
**การข้ามข้อจำกัด:** โดยค่าเริ่มต้นไม่มี มีข้อยกเว้นแบบจำกัดสำหรับพาธใน
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` เมื่อคำขอมี API key ที่ถูกต้อง
พร้อมขอบเขต `manage` (ดู [ข้อยกเว้นสำหรับขอบเขต Manage](#manage-scope-carve-out))

เส้นทางเหล่านี้สร้างโปรเซสลูกหรือเรียกใช้โค้ดขณะรันไทม์ การเปิดให้ทราฟฟิก
ที่ไม่ใช่ลูปแบ็กเข้าถึงเส้นทางเหล่านี้ จะทำให้ผู้โจมตีที่ได้รับ JWT ที่ถูกต้อง
(เช่น ผ่านอุโมงค์ Cloudflared/Ngrok) สามารถทริกเกอร์การสร้างโปรเซสได้ ซึ่งเป็น
ช่องโหว่ประเภท CVE ที่ทราบกันดี
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj))

**GHSA-fhh6-4qxv-rpqj คืออะไร (ประเภทการโจมตี):** เซิร์ฟเวอร์การจัดการ/เอเจนต์
เปิดเผยเอนด์พอยต์ที่เรียกใช้โปรเซสย่อย (`npm install`, `node`, เบราว์เซอร์,
พร็อกซี, `git`, `tar`, …) หากเอนด์พอยต์นั้นเข้าถึงได้จากภายนอกโฮสต์ เนื่องจาก
ผู้ปฏิบัติงานวาง OmniRoute ไว้หลังอุโมงค์ nginx/Cloudflare/Tailscale และ JWT
รั่วไหล หรือมีการกำหนดค่าการยืนยันตัวตนผิดพลาด ผู้โจมตีจะเปลี่ยนจาก
"เรียก API" เป็น "เรียกใช้คำสั่งบนโฮสต์" (การเรียกใช้โค้ดจากระยะไกล)
OmniRoute ปิดช่องโหว่นี้ด้วยการบังคับใช้ **การตรวจสอบโฮสต์แบบลูปแบ็กโดยไม่มีเงื่อนไข
ก่อนการตรวจสอบสิทธิ์ใดๆ** กับทุกเส้นทางที่สามารถสร้างโปรเซสได้ ดังนั้นโทเค็น
ที่รั่วไหลผ่านอุโมงค์ก็ยังไม่สามารถเข้าถึงการสร้างโปรเซสได้

**ชุด LOCAL_ONLY ทั้งหมด** แหล่งข้อมูลที่เชื่อถือได้คือ
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ใน
`src/server/authz/routeGuard.ts` โดยตารางด้านล่างสะท้อนสถานะปัจจุบัน เกต
`check-route-guard-membership` จะแจกแจงไฟล์ `route.ts` ทุกไฟล์ภายใต้คำนำหน้าที่
สามารถสร้างโปรเซสได้ และทำให้ CI ล้มเหลวหากมีไฟล์ใดไม่ได้รับการจัดประเภทเป็น

#### ข้อยกเว้นสำหรับขอบเขต manage

เส้นทาง LOCAL_ONLY บางส่วนอาจเข้าถึงได้จากที่อยู่ที่ไม่ใช่ลูปแบ็กเช่นกัน ก็ต่อเมื่อ
คำขอมี `Authorization: Bearer <api-key>` ซึ่งข้อมูลเมทาดาทาของคีย์
มีขอบเขต `manage` (หรือ `admin`) ข้อยกเว้นนี้ถูกควบคุม
อย่างชัดเจนเป็นรายเส้นทางผ่าน `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` เพื่อให้
ค่าเริ่มต้นสำหรับเส้นทาง LOCAL_ONLY ใหม่ทุกเส้นทางยังคงบังคับให้เข้าถึงจากลูปแบ็กเท่านั้น คำขอที่ไม่ผ่านการยืนยันตัวตน
และคำขอที่ใช้คีย์ซึ่งไม่มีขอบเขต manage ยังคงถูกปฏิเสธด้วย
`403 LOCAL_ONLY`

ปัจจุบัน คำนำหน้าเดียวที่ข้ามข้อจำกัดได้คือ `/api/mcp/` ส่วน `/api/cli-tools/runtime/` และ
`/api/services/` ถูกยกเว้นโดยเจตนา เนื่องจากสามารถสร้าง
โพรเซสย่อยใดๆ ก็ได้ (`npm install`, `node`) ซึ่งเป็นช่องโหว่ในกลุ่ม CVE เดียวกับที่
ระดับ LOCAL_ONLY ถูกสร้างขึ้นมาเพื่อป้องกันโดยตรง

**#7895 — ขอบเขต `mcp:connect` แบบจำกัด:** ข้อยกเว้นของ `/api/mcp/` ยังยอมรับ
คีย์ Bearer ที่มีขอบเขตแบบจำกัด `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`) ซึ่งตรวจสอบผ่าน
`hasMcpConnectOrManageScope()` ใน `src/server/authz/policies/management.ts`
ขอบเขตนี้จำกัดไว้สำหรับ `/api/mcp/` เท่านั้น — `mcp:connect` ไม่ให้สิทธิ์ใดๆ บน
เส้นทางการจัดการอื่น (รวมถึงคำนำหน้าข้อยกเว้น LOCAL_ONLY อื่นทั้งหมด หากมีการเพิ่มในอนาคต)
และถูกแยกออกจาก `MANAGEMENT_API_KEY_SCOPES` โดยเจตนา คีย์ที่มี
`manage`/`admin` ยังคงผ่านข้อยกเว้นได้เหมือนเดิมทุกประการ ส่วน `mcp:connect`
เป็นทางเลือกที่มีสิทธิ์ต่ำกว่าสำหรับผู้เรียก MCP เท่านั้นจากระยะไกล ซึ่งไม่ควรต้องใช้
สิทธิ์การจัดการแบบกว้าง

| คำขอ                                                  | เส้นทาง                    | ผลลัพธ์          |
| ----------------------------------------------------- | -------------------------- | ---------------- |
| ไม่ใช่ลูปแบ็ก, ไม่มี Bearer                           | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| ไม่ใช่ลูปแบ็ก, Bearer ที่มีขอบเขต `manage`            | `/api/mcp/*`               | อนุญาต           |
| ไม่ใช่ลูปแบ็ก, Bearer ที่มีขอบเขต `mcp:connect`       | `/api/mcp/*`               | อนุญาต           |
| ไม่ใช่ลูปแบ็ก, Bearer ที่ไม่มี `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| ไม่ใช่ลูปแบ็ก, Bearer ที่มีขอบเขต `mcp:connect`       | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| ไม่ใช่ลูปแบ็ก, Bearer ที่มีขอบเขต `manage`            | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| ลูปแบ็ก, มีหรือไม่มี Bearer ก็ได้                     | LOCAL_ONLY ใดๆ             | อนุญาต (ผ่านเกต) |

#### คำแนะนำสำหรับผู้ปฏิบัติการและการตรวจสอบ

หากคุณใช้งาน OmniRoute หลัง reverse proxy หรือ tunnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) การตรวจสอบลูปแบ็กจะยังคงปกป้อง
เส้นทางที่สามารถสร้างโพรเซสข้างต้น — คำขอที่มีที่อยู่ไคลเอนต์ไม่ใช่ลูปแบ็กจะถูกปฏิเสธด้วย
`403 LOCAL_ONLY` **ก่อนดำเนินการยืนยันตัวตน** ดังนั้น JWT ที่รั่วไหลจึงไม่สามารถเข้าถึงการสร้างโพรเซสได้
ผู้ปฏิบัติการยังคงมีหน้าที่รับผิดชอบสองประการ:

- **อย่า "แก้" 403 ด้วยการปลอม IP ของไคลเอนต์ให้เป็น loopback** การตั้งค่า
  `X-Forwarded-For: 127.0.0.1` หรือใช้พร็อกซีที่เขียนที่อยู่ต้นทางใหม่ให้เป็น
  loopback จะเปิดช่องโหว่ประเภท RCE แบบเดียวกับที่ระดับนี้ปิดกั้นไว้อีกครั้ง ให้เปิดเผย
  dashboard/API ผ่านพร็อกซีเท่านั้น — ห้ามเปิดเผยเส้นทางที่สามารถ spawn โปรเซสได้
- **จำกัดการ bypass ด้วย scope `manage` ให้น้อยที่สุด** เฉพาะ `/api/mcp/` เท่านั้นที่ bypass
  ได้ และต้องใช้ API key ที่มี scope `manage` เท่านั้น `SPAWN_CAPABLE_PREFIXES` จะไม่สามารถ
  ถูกเพิ่มลงในรายการ bypass ได้ — zod schema จะปฏิเสธรายการเหล่านี้ และ
  `isLocalOnlyBypassableByManageScope` จะปฏิเสธรายการดังกล่าวขณะรันไทม์ (การป้องกันเชิงลึก)
  ซึ่งตรงกับความหมายของข้อความ "cannot be made bypassable" ใน dashboard ตัวโหลด snapshot
  ขณะรันไทม์จะทิ้งรายการดังกล่าวจากแถวการตั้งค่าที่จัดเก็บไว้ด้วย และการนำเข้า JSON แบบเดิม
  (`/api/settings/import-json`) จะไม่เขียนคีย์ bypass ทุก entry ใน
  `LOCAL_ONLY_API_PREFIXES` ต้องอยู่ใน deny-list หรือผ่านการตรวจสอบแล้วว่าสามารถ bypass ได้
  (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`) เส้นทางที่สามารถ spawn
  โปรเซสได้ทั้งแบบ dynamic-segment และ static-path ภายใต้ `/api/providers/` (เช่น `/login`,
  `/refresh-cursor`) จะถูกครอบคลุมโดยองค์ประกอบร่วมแบบ regex อย่าง `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` ใน
  `src/shared/constants/spawnCapablePrefixes.ts` ไม่ใช่อาร์เรย์แบบแบน
  `SPAWN_CAPABLE_PREFIXES` — อาร์เรย์แบบแบนจะต้องครอบคลุม prefix `/api/providers/`
  ทั้งหมดเพื่อให้ตรวจจับเส้นทางเหล่านี้ได้ ซึ่งจะทำให้ขอบเขตของแผนผังเส้นทางกว้างเกินไป
  ทั้งที่ dashboard ระยะไกลมีการใช้งานอย่างถูกต้องสำหรับ CRUD ของ provider

**การตรวจสอบการเข้าถึง** — เพื่อตรวจยืนยันว่าไม่มีสิ่งใดจากนอกโฮสต์เข้าถึงเส้นทางเหล่านี้:

- เปิด **Authorization Inventory** ที่ `/dashboard/settings/security`: หน้านี้จะแสดงรายการ
  prefix ของ LOCAL_ONLY ที่ใช้งานจริง, prefix ที่สามารถ bypass ได้ และชุดเส้นทางที่สามารถ spawn
  โปรเซสได้ซึ่งกำหนดไว้ตอนคอมไพล์ ("cannot be made bypassable")
- ใช้ grep ค้นหา prefix ข้างต้นใน log ของ reverse-proxy / การเข้าถึง โดยจับคู่กับ
  ที่อยู่ไคลเอนต์ที่ไม่ใช่ loopback หากมีรายการใดตอบกลับ `200` แทนที่จะเป็น
  `403 LOCAL_ONLY` แสดงว่าพร็อกซีกำลังปิดบัง IP จริงของไคลเอนต์ — ให้แก้ไขพร็อกซี
- `403 LOCAL_ONLY` ใน log ของ OmniRoute สำหรับ path ใด path หนึ่งเหล่านี้หมายความว่า guard
  ทำงานตามที่ออกแบบไว้ ไม่ใช่ข้อผิดพลาดที่ควรถูกระงับ

### ระดับ 2 — ALWAYS_PROTECTED

**บังคับใช้โดย:** `isAlwaysProtectedPath(path)` → ข้าม bypass ของ `requireLogin=false`
**การ bypass:** ไม่มีเมื่อ `requireLogin=false`; ต้องใช้ JWT เสมอ

เส้นทางเหล่านี้ก่อให้เกิดการทำลายหรือไม่สามารถย้อนกลับได้ การอนุญาตเส้นทางเหล่านี้ในการติดตั้ง
แบบ "ไม่มีรหัสผ่าน" จะหมายความว่าทุกคนใน LAN เดียวกันสามารถล้างฐานข้อมูลหรือยุติโปรเซส
ของเซิร์ฟเวอร์ได้

| Path                                      | เหตุผล                                                           |
| ----------------------------------------- | ---------------------------------------------------------------- |
| `/api/shutdown`                           | ยุติโปรเซสของเซิร์ฟเวอร์                                         |
| `/api/settings/database`                  | ส่งออก นำเข้า และล้างฐานข้อมูล                                   |
| `/api/db-backups`                         | เข้าถึงไฟล์ archive สำรองฐานข้อมูลทั้งหมด                        |
| `/api/settings/export-json`               | ส่งออก blob การตั้งค่าทั้งหมด (รวมถึงข้อมูลลับ)                  |
| `/api/settings/import-json`               | แทนที่ blob การตั้งค่าทั้งหมด                                    |
| `/api/providers/health-autopilot/actions` | ดำเนินการแก้ไขปัญหาโดย autopilot                                 |
| `/api/settings/obsidian`                  | สร้างข้อมูลประจำตัว WebDAV ที่ใช้ซ้ำได้สำหรับ root ของ vault ใดๆ |

**การตอบกลับเมื่อมีการละเมิด:** `401 Authentication required`

`/api/settings/obsidian` ครอบคลุมเส้นทางลูก `/webdav` ของมัน: `POST` จะกำหนดให้บริการไฟล์ WebDAV —
ซึ่งให้บริการโดยเลเยอร์ Node แบบกำหนดเองก่อน Next.js และอยู่นอก pipeline นี้ — ชี้ไปยัง root
ที่ผู้เรียกเลือก และส่งข้อมูลประจำตัว Basic ที่เพิ่งสร้างกลับไป, `DELETE` จะหมุนเวียนข้อมูลประจำตัว
ดังกล่าว และ `POST` ของ parent จะจัดเก็บโทเค็น Obsidian REST API ส่วน GHSA-62vw เพียงปกปิด
การเปิดเผยรหัสผ่านผ่าน `GET`; กระบวนการออกข้อมูลประจำตัวยังคงอยู่ในระดับที่เปิดให้ผ่านโดยค่าเริ่มต้น
(GHSA-7pq4-8pvv-rx7r) นอกจากนี้ `enableObsidianVaultSync()` จะปฏิเสธ vault ที่เป็น
data directory, อยู่ภายใน data directory หรือมี data directory อยู่ภายใน

### การ bootstrap สำหรับการติดตั้งใหม่จำกัดเฉพาะ loopback — โดยพิจารณาจาก peer จริง ไม่ใช่ `Host`

เมื่อไม่ได้กำหนดรหัสผ่านสำหรับการจัดการ (และไม่มี `INITIAL_PASSWORD`) `isAuthRequired()` ใน
`src/shared/utils/apiAuth.ts` จะเปิดให้ทำ bootstrap แบบไม่ระบุตัวตน **เฉพาะสำหรับ loopback peer**
เท่านั้น การตัดสินว่าเป็น loopback จะพิจารณาจากสัญญาณ peer ที่เชื่อถือได้ตามลำดับดังนี้: TCP peer จริง
ที่ประทับโทเค็นไว้ (`PEER_IP_HEADER` + `VIA_PROXY_HEADER` ซึ่งเป็นสิ่งที่ policy มองเห็น),
ผลการตัดสิน `AUTHZ_HEADER_PEER_LOCALITY` ของ pipeline เอง (ซึ่งเป็นสิ่งที่ route handler มองเห็น
และเชื่อถือเฉพาะเมื่อมีการตั้งค่า `OMNIROUTE_PEER_STAMP_TOKEN`) หรือ socket peer จริงสำหรับ
ผู้เรียกโดยตรง ระบบจะไม่ตรวจสอบ `Host` / `nextUrl.hostname` และการเขียนรหัสผ่านครั้งแรก
(`POST /api/settings/require-login`) อยู่ภายใต้ข้อจำกัดเดียวกัน แทนที่จะเปิดให้ network peer
ทุกรายเข้าถึงได้ (GHSA-7pq4-8pvv-rx7r) `managementPolicy` จะส่งผลการตัดสิน `peerContext`
ของตัวเองลงไปอย่างชัดเจน ดังนั้น header ของคำขอ ORIGINAL (ก่อนการตัดออก) จะไม่มีส่วนในการตัดสิน

### ระดับ 3 — MANAGEMENT (ค่าเริ่มต้น)

เส้นทางการจัดการอื่นๆ ทั้งหมด ต้องยืนยันตัวตน เว้นแต่จะกำหนดค่า
`requireLogin=false` โทเค็น CLI สามารถใช้ยืนยันตัวตนกับเส้นทางเหล่านี้ได้
(loopback + HMAC ที่ถูกต้อง)

## ลำดับการประเมิน

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → ดำเนินการต่อ
     → non-loopback, Bearer ที่มี manage-scope
        และ isLocalOnlyBypassableByManageScope   → อนุญาต (management_key)
     → มิฉะนั้น                                  → ปฏิเสธ 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → อนุญาต (system)
  3. hasValidCliToken(headers)?
     → อนุญาต (cli) [loopback + การตรวจสอบ HMAC ด้วย timingSafeEqual]
  4. isAlwaysProtectedPath(path) หรือ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → อนุญาต (dashboard_session)
     → Bearer ที่มี manage-scope บนพาธที่ไม่สามารถข้ามได้?
        → อนุญาต (management_key)
     → ปฏิเสธ 401/403
  5. requireLogin=false?
     → อนุญาต (anonymous)
```

แขนง manage-scope ในขั้นตอนที่ 1 เป็นพาธที่ผ่านการยืนยันตัวตนเพียงพาธเดียวที่สามารถเข้าถึง
เส้นทาง LOCAL_ONLY ได้ โหมดความล้มเหลวของ auth-backend จะส่งคืน 503 (ไม่ใช่ 403) เพื่อให้
DB ที่หมดอายุไม่ลดระดับเป็น "ปฏิเสธ" โดยไม่แจ้งให้ทราบ

## การเพิ่มเส้นทางใหม่ที่สามารถ spawn ได้

1. เพิ่มคำนำหน้าพาธลงใน `LOCAL_ONLY_API_PREFIXES` ที่
   `src/server/authz/routeGuard.ts`
2. เพิ่มการทดสอบใน `tests/unit/authz/routeGuard.test.ts` เพื่อยืนยันว่า
   `isLocalOnlyPath()` ส่งคืน true สำหรับคำนำหน้าใหม่
3. **ห้ามข้ามขั้นตอนนี้โดยเด็ดขาด** — ดูกฎตายตัวข้อที่ 15 ใน `CLAUDE.md`
4. ตัดสินใจว่าเส้นทางนี้ควรอยู่ใน `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ด้วยหรือไม่?
   คำตอบเริ่มต้นคือ **ไม่** ให้เลือกใช้เฉพาะเมื่อเส้นทางนั้นปลอดภัยพอที่จะเปิดให้ผู้ถือ
   manage-scope เข้าถึงได้ (กล่าวคือ ต้องไม่ spawn โค้ดตามอำเภอใจที่ผู้ใช้ควบคุม)

## การเพิ่มพาธที่ manage-scope สามารถข้ามข้อจำกัดได้

1. ยืนยันว่าเส้นทางนี้ไม่เรียกใช้โค้ดหรือคำสั่งที่ผู้ใช้ระบุ หากมีการเรียกใช้
   ให้หยุด — ข้อยกเว้นนี้ไม่ใช่เครื่องมือที่เหมาะสม
2. เพิ่มคำนำหน้าต่อท้าย `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ใน
   `src/server/authz/routeGuard.ts`
3. เพิ่มความครอบคลุมใน `tests/unit/authz/management-policy.test.ts` สำหรับรูปแบบ
   คำขอทั้งสี่แบบ ได้แก่ ไม่มี Bearer (403), Bearer ที่มี manage-scope (อนุญาต),
   Bearer ที่ไม่มี manage-scope (403) และการทดสอบการถดถอยรายคำนำหน้าเพื่อให้
   `/api/cli-tools/runtime/*` ยังคงจำกัดเฉพาะ loopback อย่างเคร่งครัด แม้จะมี Bearer
   ที่มี manage-scope

- `scripts/check/check-openapi-coverage.mjs` — ล้มเหลวหากความครอบคลุม < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — ล้มเหลวหากคำอธิบายประกอบ
  `x-loopback-only` หรือ `x-always-protected` ไม่สอดคล้องกับค่าคงที่ ณ เวลาคอมไพล์

สคริปต์ทั้งสองทำงานใน pre-commit hook และใน CI

### กฎเกี่ยวกับผลบวกลวง

หากมีการใส่คำอธิบายประกอบ `x-always-protected` หรือ `x-loopback-only` ให้กับเส้นทางที่ไม่ได้อยู่ใน
ค่าคงที่ของ `routeGuard.ts` สคริปต์ตรวจสอบความครอบคลุมจะล้มเหลว วิธีแก้คือต้องปรับ YAML
ให้สอดคล้องกับสิ่งที่ `routeGuard.ts` บังคับใช้จริงเสมอ — ไม่ใช่เพิ่มเส้นทางลงใน `routeGuard.ts`
โดยไม่ได้ติดตั้งตรรกะการบังคับใช้ด้วย
