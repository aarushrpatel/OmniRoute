> **อัปเดตล่าสุด:** 2026-08-29 — v3.8.51 (ที่มาของทรานสคริปต์ Video Bridge ถูกประกาศโดยผู้เรียก
> และยังไม่ได้รับการตรวจสอบโดยเซิร์ฟเวอร์ — ชี้แจงตาม #11661)

Guardrails บังคับใช้มาตรการด้านความปลอดภัย นโยบาย และการแปลงเนื้อหาที่ขอบเขต
ระหว่าง OmniRoute กับผู้ให้บริการต้นทาง Guardrail แต่ละตัวสามารถตรวจสอบ (และ
เลือกที่จะปฏิเสธ แปลง หรือใส่คำอธิบายประกอบ) เพย์โหลดคำขอ (`preCall`) และ
การตอบกลับจากต้นทาง (`postCall`)

ระบบนี้เป็นแบบ **fail-open**: หาก Guardrail เกิดข้อผิดพลาดขณะทำงาน รีจิสทรี
จะบันทึกข้อผิดพลาดและดำเนินการต่อด้วย Guardrail ตัวถัดไป แทนที่จะทำให้
คำขอล้มเหลว การบล็อกต้องเกิดจากการตัดสินใจอย่างชัดเจน (`block: true`) ไม่ใช่เหตุบังเอิญ

### บริดจ์การมองเห็น (`visionBridge.ts`) — บริดจ์โมดาลิตี PR-1

ดักจับคำขอที่มีรูปภาพซึ่งส่งไปยัง **โมเดลที่ไม่รองรับการมองเห็น** แล้วเลือก
เปลี่ยนเส้นทางคำขอทั้งหมดไปยังโมเดลที่รองรับการมองเห็น หรือแทนที่ส่วนรูปภาพ
ด้วยคำอธิบายข้อความที่สร้างโดยโมเดลการมองเห็นที่กำหนดค่าได้ก่อนเรียกใช้
ระบบต้นทาง วิธีนี้ช่วยให้ผู้ให้บริการที่รองรับเฉพาะข้อความสามารถจัดการ
เพย์โหลดแบบหลายโมดาลิตีได้อย่างโปร่งใส

ลำดับการทำงาน:

1. ข้ามหากโมเดลเป้าหมายรองรับการมองเห็นอยู่แล้ว (เว้นแต่โมเดลนั้นจะปรากฏใน
   รายการบังคับใช้บริดจ์ `isVisionBridgeForcedModel`)
2. แยกส่วนรูปภาพผ่าน `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`) ซึ่งมอบหมายให้ **ตัวตรวจจับสื่อแบบรวมศูนย์**
   `detectMediaParts()` ใน `open-sse/utils/mediaParts.ts` — แหล่งข้อมูลจริง
   เพียงแหล่งเดียวที่ใช้ร่วมกับตัวกรองความเข้ากันได้ของคอมโบ
   การแยกจะอนุญาตเฉพาะส่วนระดับบนสุดที่มีรูปแบบซึ่ง
   `replaceImageParts` สามารถแทรกกลับเข้าไปได้ (ข้อตกลง extract↔replace):
   `image_url` ของ OpenAI, `source.type:"base64"` แบบ base64 ของ Anthropic,
   `source.type:"url"` แบบ URL ของ Anthropic และ `input_image` ของ Responses API
   รายการที่ตรวจพบแบบซ้อนและรูปแบบที่เป็นเพียงตัวบ่งชี้เป็นข้อมูลสำหรับ
   ตัวกรองคอมโบ และจะไม่ถูกแยกออกมา หากไม่พบรายการใดให้ข้าม
3. แก้ไขการกำหนดค่ารันไทม์ผ่าน `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): คีย์การตั้งค่าใหม่
   `modalityBridge*` มีสิทธิ์เหนือกว่า ส่วนคีย์เดิม `visionBridge*` ยังคงเป็น
   **ตัวสำรองสำหรับหนึ่งรอบ** (ช่วงเวลาสำหรับการย้อนกลับ) ข้ามก่อนการไล่ตรวจ
   สื่อใดๆ เมื่อปิดใช้งานบริดจ์
4. ตัวเลือกโหมด (`modalityBridgeVisionMode` ดูตารางด้านล่าง) จะตัดสินใจว่า
   จะเปลี่ยนเส้นทางหรืออธิบาย การเปลี่ยนเส้นทางจะคืนค่า `modifiedPayload`
   โดยสลับเฉพาะ `model` พร้อมเมตา `{ rerouted, fromModel, toModel, imagesKept }`
5. เส้นทางการอธิบาย: จำกัดจำนวนรูปภาพไว้ที่ `maxImages` สร้างพรอมต์ที่รับรู้
   งาน ตรวจสอบแคชคำอธิบาย เรียกโมเดลการมองเห็น **แบบขนาน**
   (`Promise.allSettled`) และแทรกส่วนข้อความ `[Image N]: <description>`
   เข้าไปแทนที่ หากการอธิบายล้มเหลวจะให้ผลเป็น `null` และส่วนรูปภาพต้นฉบับ
   จะถูก **คงไว้** (#4012) — ยกเว้นในเส้นทางการอธิบายแบบคอมโบเมื่อการอธิบาย
   ทั้งหมดล้มเหลว ซึ่งระบบต้นทางที่ยืนยันแล้วว่าไม่รองรับการมองเห็นจะได้รับ
   ข้อความแทน `(unavailable — no vision-capable provider connected)` (#8430)
6. คืนค่า `modifiedPayload` + เมตา (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`)

#### ตัวเลือกโหมด (`modalityBridgeVisionMode`)

| โหมด       | ค่าเริ่มต้น | ลักษณะการทำงาน                                                                                                                                                                                                                                                                        |
| ---------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔           | ฮิวริสติกเดิมโดยไม่มีการเปลี่ยนแปลง (#6640/#7204): โมเดลที่ไม่ใช่คอมโบ/`auto/` จะเปลี่ยนเส้นทางไปยังโมเดลการมองเห็นที่ดีที่สุด เว้นแต่โมเดลต้นฉบับจะมีข้อมูลประจำตัวที่ใช้งานได้อยู่แล้ว (ในกรณีนั้นจะใช้การอธิบาย) ส่วนเป้าหมายแบบคอมโบจะใช้การอธิบายเสมอ                            |
| `describe` |             | อธิบายเสมอ — ข้ามบล็อกการเปลี่ยนเส้นทางทั้งหมด โมเดลที่ผู้ใช้เลือกจะเป็นผู้ตอบเสมอ                                                                                                                                                                                                    |
| `reroute`  |             | บังคับเปลี่ยนเส้นทาง: ข้ามกลไกป้องกันที่ให้คงโมเดลซึ่งมีข้อมูลประจำตัวไว้ กลไกป้องกันข้อมูลประจำตัวของ **เป้าหมาย** การเปลี่ยนเส้นทางยังคงมีผล — เมื่อไม่มีเป้าหมายการมองเห็นที่ใช้งานได้ คำขอจะเปลี่ยนไปใช้การอธิบาย เพื่อไม่ให้รูปภาพดิบไปถึงแบ็กเอนด์ที่รองรับเฉพาะข้อความ (#8430) |

โหมดบังคับจะลัดวงจร **ก่อน** ที่ฮิวริสติก `auto` จะทำงาน ลักษณะการทำงานของ
`auto` จะเหมือนกับกลไกป้องกันก่อน PR-1 ทุกไบต์

#### ขอบเขตคีย์ API (`visionBridgeKeyScope.ts`)

เมื่อคีย์ API ของผู้เรียกจำกัด `allowedConnections` กลุ่มโควตา
(`allowedQuotas`) หรือโมเดล (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) บริดจ์จะเลือกเฉพาะ
โมเดลสำหรับการเปลี่ยนเส้นทางและการอธิบายที่คีย์ได้รับอนุญาตให้ใช้ บนการเชื่อมต่อ
ที่คีย์ได้รับอนุญาตให้ใช้ จากนั้นการเรียกเพื่ออธิบายจะผ่านลูปกลับเข้าตัวเองของ
OmniRoute พร้อมส่วนหัว `x-omniroute-self-loop-key-id` เสมอ เพื่อให้คำขอแชต
ที่รับเข้ามาบังคับใช้นโยบายการเชื่อมต่อและโมเดลของคีย์นั้นอีกครั้ง
`enforceApiKeyPolicy()` จะยอมรับส่วนหัวดังกล่าวเฉพาะเมื่อใช้ร่วมกับ bearer
สำหรับลูปกลับเข้าตัวเอง ดังนั้นจึงทำได้เพียงจำกัดสิทธิ์ให้แคบลง และ id
ที่ไม่สามารถแก้ไขได้จะถูกปฏิเสธ

หากไม่มีโมเดลการมองเห็นใดที่ได้รับอนุญาตสำหรับคีย์ เส้นทางการอธิบายจะหลีกทาง
และส่งคำขอผ่านไปโดยไม่เปลี่ยนแปลง ซึ่งเป็นลักษณะการทำงานแบบเปิดให้ผ่านเมื่อ
ล้มเหลวเช่นเดียวกับกลไกป้องกันที่ถูกปิดใช้งาน (เมตา
`{ skipped: true, reason: "no_permitted_vision_model" }`)
คำขอที่ไม่มีคีย์และคีย์ที่ไม่มีข้อจำกัดเหล่านี้จะทำงานเหมือนเดิมทุกประการ

#### พรอมต์การอธิบายที่รับรู้งาน (`modalityBridgeVisionTaskAware`)

ค่าเริ่มต้นคือ **true** `composeVisionPrompt()` (`visionBridgeHelpers.ts`) จะต่อท้าย
พรอมต์คำอธิบายพื้นฐานด้วยข้อความจาก **ข้อความล่าสุดของผู้ใช้** (ตัดให้เหลือไม่เกิน 500 อักขระ)
เพื่อชี้นำคำอธิบายไปยังสิ่งที่ผู้ใช้ถามจริง
(รูปแบบ codex-vision-proxy) และขอให้โมเดลการมองเห็นถอดข้อความที่มองเห็น
เมื่อปิดแฟล็กนี้ — หรือไม่มีข้อความจากผู้ใช้ — ระบบจะใช้พรอมต์พื้นฐานโดยไม่มีการเปลี่ยนแปลง

คำขอที่เข้ากันได้กับ OpenAI ของ describe self-loop เอง (`callVisionModelSingle()`
ใน `visionBridgeHelpers.ts`) จะขอ `image_url.detail: "high"` เสมอ —
โดยไม่มีเงื่อนไข สำหรับผู้เรียก/ผู้ให้บริการทุกราย และไม่ได้ขึ้นอยู่กับสัญญาณใดๆ จากไคลเอนต์
การสุ่มตัวอย่างแบบรายละเอียดต่ำลดความแม่นยำของ OCR สำหรับงานถอดข้อความ
ที่พรอมต์นี้ร้องขอโดยตรง ดังนั้นการเรียก describe เองจึงขอรายละเอียดระดับสูงเสมอ
ไม่ว่าคำขอขาเข้าดั้งเดิมจะใช้ระดับรายละเอียดใดก็ตาม การดำเนินการนี้
มีผลเฉพาะกับเนื้อหาคำขอ describe ภายในเท่านั้น และไม่เปลี่ยนวิธีที่
OmniRoute ส่งต่อ `image_url.detail` ของผู้เรียกในคำขอหลัก —
ค่าเริ่มต้นดังกล่าวจะถูกนำไปใช้แยกต่างหาก และใช้เฉพาะกับไคลเอนต์ OpenCode ที่ตรวจพบ
ใน `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`)
ส่วนรูปแบบ wire ของ Anthropic ใน describe self-loop ไม่มีฟิลด์ `detail`
และไม่ได้รับผลกระทบจากค่าเริ่มต้นทั้งสองแบบ

#### ขีดจำกัดเอาต์พุตของ Describe (`modalityBridgeVisionMaxChars`)

| คีย์                           | ค่าเริ่มต้น | ช่วง               |
| ------------------------------ | ----------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`         | `0` หรือ 100–50000 |

`0` (ค่าเริ่มต้น) หมายถึง **ไม่มีขีดจำกัด** — คำอธิบายที่ส่งคืนโดย
`callVisionModel()` จะถูกส่งต่อโดยไม่มีการแก้ไข เพื่อคงพฤติกรรมเดิมไว้
ค่าใดๆ ในช่วง 100–50000 จะตัดคำอธิบายและเติมส่วนต่อท้าย
`…` ก่อนนำกลับไปแทรกเป็น `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` ใน `src/lib/guardrails/visionBridge.ts`)
ให้เพิ่มค่านี้สำหรับงาน OCR ที่มีรายละเอียดมาก ซึ่งโมเดลปลายทางต้องใช้
ข้อความถอดเสียงฉบับเต็ม หรือลดค่านี้เพื่อจำกัดการใช้โทเค็นของโมเดลการมองเห็น
ที่ให้คำตอบยืดยาว ฟิลด์ในแดชบอร์ดอยู่ในแผง Advanced ของแท็บ Vision
(`modality-bridge-max-chars` ใน `ModalityBridgeVisionTab.tsx`) และจะปรับ
ค่าใดๆ ระหว่าง 1 ถึง 99 ขึ้นเป็นค่าต่ำสุด 100 โดยไม่เปลี่ยนค่า `0`
ที่ระบุอย่างชัดเจน — `0` เป็นค่า Zod ที่ถูกต้องในตัวเอง
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`) ไม่ได้เป็นเพียง
ค่าเริ่มต้นสำหรับสถานะ "ไม่ได้ตั้งค่า"

#### แคชของ Describe (`modalityBridge/bridgeCache.ts`)

แคช LRU + TTL ในหน่วยความจำสำหรับเอาต์พุต describe ซึ่งใช้ร่วมกันทั่วทั้งโปรเซส
คีย์ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` พร้อม
การจัดเฟรมด้วยคำนำหน้าความยาว (ไม่มีการชนกันที่ขอบเขตฟิลด์) องค์ประกอบโมเดลคือ
โมเดลบริดจ์ที่ **กำหนดค่าไว้** ไม่ใช่โมเดลที่ตอบกลับจริง —
`callVisionModel` อาจใช้โมเดลสำรองภายใน และการสร้างคีย์แยกตามแต่ละครั้งที่ลอง
จะทำให้แคชแตกกระจาย ผลลัพธ์ describe ที่ล้มเหลวจะไม่ถูกแคช การตั้งค่า:

| คีย์                            | ค่าเริ่มต้น | ช่วง    |
| ------------------------------- | ----------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`      | —       |
| `modalityBridgeCacheTtlMinutes` | `60`        | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`       | 10–5000 |

#### การปรับภาพระยะไกลให้เป็นมาตรฐาน (self-loop describe/การดึงข้อมูล base64)

เมื่อบริดจ์ดึงภาพ **ระยะไกล** ด้วยตนเอง — ทั้งการเรียกตัวเองสำหรับ describe
ของ Anthropic และการแปลงเป็น base64 ในรูปแบบ claude-wire-format
(`ensureBase64ImagesForClaudeWire`) ซึ่งทั้งคู่ดำเนินการผ่าน
`fetchRemoteImageAsDataUri()` ใน `visionBridgeHelpers.ts` — URI ข้อมูลที่ได้
จะถูกส่งผ่าน `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) ก่อนฝังลงในคำขอไปยังโมเดลการมองเห็น
ภาพที่มีขนาดใหญ่เกินไปจะถูกย่อให้มี **ด้านยาว 2048px** (ตรงกับ
ขีดจำกัดการปรับขนาดที่ OpenAI/Anthropic ใช้อยู่แล้วฝั่งเซิร์ฟเวอร์) ซึ่งช่วยลด
จำนวนไบต์ที่อัปโหลด/เวลาแฝง โดยไม่เปลี่ยนสิ่งที่โมเดลการมองเห็นเห็น การปรับขนาด
ใช้ `sharp` ซึ่งโหลดผ่าน dynamic import: บนแพลตฟอร์มที่ไบนารีแบบเนทีฟ
โหลดไม่สำเร็จ `normalizeDataUri()` จะ **ไม่ throw โดยเด็ดขาด** — แต่จะย้อนกลับ
ไปส่งผ่านไบต์ต้นฉบับ ดังนั้นเส้นทาง describe/การแปลงเป็น base64
จึงยังทำงานต่อไปเสมอ ไบต์ที่ไม่ใช่ภาพ (ผลลัพธ์จากการดึงข้อมูลที่ไม่ใช่
ภาพซึ่งถอดรหัสได้) จะถูกส่งผ่านโดยไม่มีการเปลี่ยนแปลงเช่นกัน การปรับให้เป็นมาตรฐานนี้
จำกัดเฉพาะภาพที่บริดจ์ดึงมาเพื่อการเรียกตัวเองเท่านั้น — และจะไม่ถูกนำไปใช้
กับเพย์โหลดแบบส่งผ่านดิบของผู้เรียก ซึ่งสอดคล้องกับหลักการแก้ไขเฉพาะเมื่อเลือกใช้
(กฎตายตัว #20)

#### เฮดเดอร์ความโปร่งใส + สถิติ

การตอบกลับที่ผ่านการแปลงด้วย describe จะมี
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(สร้างโดย `buildModalityBridgeHeader()` ใน `modalityBridge/bridgeStats.ts`
และประทับโดย `withModalityBridgeHeader()` ใน `src/sse/handlers/chatHelpers.ts`)
คำขอที่ถูกเปลี่ยนเส้นทางจะ **ไม่มี** เฮดเดอร์นี้ — เพย์โหลดไม่ได้ถูกแก้ไข
และการสลับโมเดลจะแสดงอยู่แล้วในฟิลด์ `model` ของเนื้อหาการตอบกลับ

`GET /api/modality-bridge/stats` (การยืนยันตัวตนสำหรับการจัดการ ระดับเดียวกับ
`GET /api/settings`) ส่งคืนตัวนับในหน่วยความจำแยกตามโมดาลิตี
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` สำหรับ `vision`, `audio` และ
`video` โดย `averageLatencyMs` ใช้ `latencySamples` เป็นตัวหาร ไม่ใช่จำนวนความพยายามทั้งหมด
การดำเนินการที่ไม่มีข้อมูลเวลาไม่ได้สร้างตัวอย่างเวลาศูนย์มิลลิวินาทีขึ้นมา
`bridged` ยังคงเป็นชื่อแทนที่เข้ากันได้ย้อนหลังสำหรับการแปลงที่สำเร็จ
ความพยายามที่ล้มเหลวจะไม่เพิ่มค่านี้
ตัวนับจะรีเซ็ตเมื่อกระบวนการเริ่มใหม่ตามการออกแบบ
(ใช้เพื่อการวัดผล ไม่ใช่การทำบัญชี)

#### การกำหนดค่าแดชบอร์ด

หน้าแดชบอร์ดเฉพาะอยู่ที่
`/dashboard/settings/modality-bridge` แท็บ `Vision`, `Audio`
และ `Video` ที่ระบุผ่าน URL ได้จะคงพารามิเตอร์คิวรีไว้ขณะสลับค่า `tab`
แท็บ Vision มีการตั้งค่าการเปิดใช้งาน โหมด การเลือกโมเดล (รวมถึงค่าเริ่มต้นแบบอัตโนมัติ)
พรอมป์ที่คำนึงถึงงาน ขีดจำกัดขั้นสูงสำหรับระยะหมดเวลา/รูปภาพ/ความยาวคำอธิบาย/แคช
ตัวนับระหว่างรันไทม์
และคำขอตัวอย่างที่มีการป้องกัน แท็บ Audio ใช้งานได้จริงเช่นกัน โดยมี
การตั้งค่าการเปิดใช้งาน ตัวเลือกโมเดลเฉพาะ STT พร้อม Auto ขีดจำกัดระยะหมดเวลา/ความยาวคลิปสูงสุด
ตัวนับเสียง และการทดสอบตัวอย่าง `input_audio` แท็บ Video ทำงานได้อย่างสมบูรณ์ โดยรายงาน
สถานะรันไทม์ของ FFmpeg/ffprobe ซึ่งเป็นหนึ่งในสี่สถานะ UI ที่กำหนดไว้อย่างชัดเจน (`unknown` ขณะที่
การตรวจสอบกำลังดำเนินอยู่หรือไม่สามารถดำเนินการให้เสร็จได้, `restricted` บนโฮสต์แดชบอร์ด
ที่ไม่ใช่ loopback ซึ่งข้ามการตรวจสอบที่ฝั่งไคลเอนต์, `unavailable` หลังจากตรวจสอบแล้ว
และยืนยันว่าไม่มี หรือ `available` พร้อมเวอร์ชันของ FFmpeg/ffprobe) รวมทั้งบันทึก
ขีดจำกัดการเปิดใช้งาน/โมเดล/เฟรม/วิดีโอ/ระยะหมดเวลาอย่างถาวร กรองตัวเลือกโมเดลให้เหลือเฉพาะ
โมเดลที่รองรับ Vision และแสดงตัวนับวิดีโอ

การ์ด Vision Bridge เดิมภายใต้การตั้งค่า AI ปัจจุบันเป็นลิงก์เพื่อความเข้ากันได้ไปยัง
หน้าใหม่เท่านั้น และไม่ได้ถือครองสำเนาฟอร์มชุดที่สองอีกต่อไป นอกจากนี้ Media Providers
ยังเชื่อมโยงเวิร์กโฟลว์ Image-to-Text และ Speech-to-Text ไปยังแท็บ Modality
Bridge ที่เกี่ยวข้อง โดยไม่ลบพื้นที่ทดลอง Speech-to-Text ที่มีอยู่

**การข้ามการตรวจรับสำหรับ self-loop:** เมื่อคำขออธิบายถูกกำหนดเส้นทางผ่าน
`/v1` self-loop ของ OmniRoute เอง (โมเดลผู้ให้บริการที่ไม่เป็นมาตรฐาน) คำขอย่อยจะส่ง
`x-omniroute-admission-bypass: internal` และยืนยันตัวตนด้วยข้อมูลประจำตัว self-loop
ที่ได้รับการแก้ค่าแล้ว ซึ่งได้แก่ sentinel `sk_omniroute` ภายในเครื่องในโหมด local หรือ
คีย์ env `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` ที่ผู้ปฏิบัติงานกำหนดค่าไว้ (#1350)
เพื่อให้การติดตั้งใช้งานที่ตั้งค่า `REQUIRE_API_KEY=true` ยังคงเรียกคำขออธิบายได้ การข้ามนี้
จะได้รับการยอมรับเฉพาะเมื่อใช้ข้อมูลประจำตัวที่ตรงกันทุกประการเท่านั้น ดังนั้นไคลเอนต์ภายนอกจึงไม่สามารถใช้
เฮดเดอร์นี้เพื่อข้ามการตรวจรับได้

ค่าเริ่มต้นแบบเดิมอยู่ใน `src/shared/constants/visionBridgeDefaults.ts`
ส่วนค่าเริ่มต้นใหม่สำหรับโหมด/การคำนึงถึงงาน/แคช และตัวแก้ค่าการตั้งค่าอยู่ใน
`src/shared/constants/modalityBridgeDefaults.ts` กลไกป้องกันมีตัวเลือกคอนสตรักเตอร์
`deps` เพื่อให้การทดสอบสามารถฉีดอิมพลีเมนเทชันจำลองของ `getSettings` และ
`callVisionModel` ได้

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

สกัดกั้นคำขอแชตที่มีเสียงก่อนที่จะไปถึงเป้าหมายซึ่งไม่เป็นที่ทราบว่ารองรับ
อินพุตเสียง ระบบจะไม่เปลี่ยนเส้นทางคำขอแชต แต่จะถอดเสียงส่วนเสียงผ่านเอนด์พอยต์
multipart ที่เข้ากันได้กับ OpenAI ซึ่งมีอยู่แล้ว และโมเดลแชตที่เลือกจะดำเนินการต่อด้วยข้อความถอดเสียง

ลำดับการทำงาน:

1. แก้ค่า `supportsAudio` ผ่าน `getResolvedModelCapabilities()` โดยเมทาดาทา
   ของรีจิสทรีผู้ให้บริการที่ระบุไว้อย่างชัดเจนมีลำดับความสำคัญสูงสุด ตามด้วยเมทาดาทาโมเดลแบบคงที่ และ
   `modalities_input` ที่ซิงค์ไว้ รายการอินพุตที่ประกาศไว้โดยไม่มี `audio` จะมีค่าเป็น `false`
   ส่วนกรณีที่ไม่มีหลักฐานด้านความสามารถจะยังคงเป็น `null` ทั้ง `false` และ `null` จะเปิดใช้
   บริดจ์แบบระมัดระวัง ขณะที่ `true` จะข้ามบริดจ์
2. แก้ค่าการตั้งค่า `modalityBridgeAudio*` และแยกส่วนเสียงระดับบนสุดที่สามารถ splice ได้
   จากทุกข้อความผ่านตัวตรวจจับ `detectMediaParts()` ที่ใช้ร่วมกัน รูปแบบ wire ที่รองรับคือ
   `input_audio` ของ OpenAI, `audio_url` และ `source.media_type: "audio/*"`
   ระบบตรวจพบเสียงที่ซ้อนอยู่เพื่อใช้กำหนดเส้นทาง แต่เส้นทาง splice จะไม่ลบออก ปริมาณงานถูกจำกัดโดย
   `modalityBridgeAudioMaxClips` ส่วนที่อยู่ถัดจากขีดจำกัดจะคงเดิม
3. ใช้ `provider/model` ที่กำหนดค่าไว้ หรือให้ `selectAudioBridgeModel()` ไล่ตรวจสอบ
   `AUDIO_TRANSCRIPTION_PROVIDERS` ตามลำดับแค็ตตาล็อกที่คงที่ และเลือกโมเดลแรก
   ที่มีข้อมูลประจำตัวของผู้ให้บริการที่ใช้งานได้และเปิดใช้งานอยู่
4. `callAudioTranscription()` แปลงเสียง base64/data-URI เป็น `file` แบบ multipart
   หรือดาวน์โหลด `audio_url` ระยะไกลผ่านกลไกป้องกันการส่งออกที่อนุญาตเฉพาะปลายทางสาธารณะ
   พร้อมการตรึง DNS และขีดจำกัด 25 MB จากนั้นจะ POST ไฟล์และโมเดลที่เลือกไปยัง
   `/v1/audio/transcriptions` self-loop ภายในเครื่อง โดยยืนยันตัวตนด้วย
   `resolveSelfLoopBearer()` เส้นทางการถอดเสียงที่มีอยู่จะดำเนินการค้นหาข้อมูลประจำตัวตามปกติ
   จัดการช่วงพัก/ขีดจำกัดอัตรา และส่งต่อไปยังผู้ให้บริการ
5. การเรียกที่สำเร็จจะแทนที่ส่วนนั้นด้วย `[Audio N]: <transcript>` การเรียกต่าง ๆ
   ทำงานด้วย `Promise.allSettled` โดยความล้มเหลวแต่ละรายการจะคงส่วนเสียงเดิมนั้นไว้
   (ข้อกำหนด #4012) หากการเรียกทั้งหมดล้มเหลวและได้รับการพิสูจน์แล้วว่าเป้าหมายมี
   `supportsAudio === false` ส่วนนั้นจะกลายเป็น
   `[Audio N]: (unavailable — no STT provider connected)` (ข้อกำหนด #8430)
   สำหรับเป้าหมายที่ไม่ทราบความสามารถ (`null`) ผลลัพธ์ที่ล้มเหลวทั้งหมดจะยังคงไม่ถูกแก้ไข
   เป้าหมายที่ได้รับการพิสูจน์แล้วว่ารองรับเฉพาะข้อความและไม่มีข้อมูลประจำตัว STT ที่ใช้งานได้
   จะได้รับข้อความแทนที่แบบชัดเจนเดียวกันโดยไม่ส่งคำขอเครือข่าย

ข้อความถอดเสียงที่สำเร็จจะใช้แคช LRU/TTL ของ Modality Bridge ซึ่งใช้ร่วมกันทั้งกระบวนการ
คีย์ประกอบด้วยการอ้างอิงเสียง ป้ายกำกับการดำเนินการ `audio-transcription` ที่คงที่
และโมเดล STT ที่เลือก โดยจะไม่แคชความล้มเหลว ความพยายามประมวลผลเสียงจะอัปเดต
ตัวนับ `bridged`, `cacheHits`, `failures` และ `lastUsedAt` ที่ใช้ร่วมกัน
การตอบกลับที่ผ่านการแปลงจะมี
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`
ส่วนคำขอที่ไม่ถูกแก้ไขจะไม่ได้รับเซกเมนต์ Audio Bridge

การตั้งค่ารันไทม์ได้รับการสนับสนุนโดย DB และตรวจสอบความถูกต้องด้วย Zod:

| คีย์                          | ค่าเริ่มต้น | ช่วงค่า                  |
| ----------------------------- | ----------- | ------------------------ |
| `modalityBridgeAudioEnabled`  | `true`      | —                        |
| `modalityBridgeAudioModel`    | `""`        | อัตโนมัติหรือ ID ของ STT |
| `modalityBridgeAudioTimeout`  | `60000`     | 1000–300000              |
| `modalityBridgeAudioMaxClips` | `3`         | 1–10                     |

### บริดจ์วิดีโอ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ดักจับส่วนวิดีโอระดับบนสุดใน `messages` ของ Chat Completions และ `input` ของ
Responses API ก่อนเรียกใช้ปลายทางที่ไม่ทราบแน่ชัดว่ารองรับวิดีโอโดยตรง
รูปแบบที่รองรับได้แก่ `input_video`, `video_url`, `video_source`, URL แบบ HTTPS
และ data URI รูปแบบ `data:video/*;base64,...` ส่วนชื่อไฟล์ธรรมดาในข้อความจะไม่ถูกถือว่า
เป็นวิดีโอ

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) รับผิดชอบการสำรวจคำขอ
การตรวจสอบความสามารถ/นโยบาย การรวมผลต่อคำขอ และเพย์โหลดการตอบกลับ
งานต่อวิดีโอแต่ละรายการ ได้แก่ การดึงข้อมูล แคชผลลัพธ์ทั้งหมด การอธิบายลำดับเฟรม
(ซึ่งผสานทรานสคริปต์เสียงที่ผู้เรียกประกาศไว้ หากมี) ตลอดจนเมตริก/การยกเลิก/การล้างข้อมูล
ของแต่ละความพยายาม จะถูกซ่อนไว้เบื้องหลัง `processVideoPart` ใน
`videoBridgePipeline.ts` ซึ่งถูกเรียกหนึ่งครั้งต่อส่วนวิดีโอภายในลูปของ `preCall`
โมดูลดังกล่าวยังกำหนดขอบเขตพอร์ตที่ชัดเจน ได้แก่ `VideoMediaBrokerPort`
(การดึงไบต์และการแยกเฟรมตัวอย่าง), `VideoAudioTranscriptionPort`
(การผสานทรานสคริปต์เสียงที่ผู้เรียกประกาศไว้กับคำบรรยายเฟรมตัวอย่าง) และ
`VideoDrilldownPort` (ขอบเขตการจัดเก็บข้อมูลถาวรสำหรับการเจาะลึกรายละเอียดเฟรม ซึ่งยังไม่ได้เชื่อมต่อ
เข้ากับ `processVideoPart` — ปัจจุบันมีเพียงเส้นทาง `/api/modality-bridge/video/drilldown`
ที่เขียนรายการเจาะลึกรายละเอียด)

เส้นทางคำขอสาธารณะ `/v1` จะไม่นำเข้าหรือเรียกใช้กระบวนการย่อย
วิดีโอระยะไกลจะถูกดาวน์โหลดภายใต้ขีดจำกัด 50 MiB ส่วนวิดีโอ base64 แบบอินไลน์มีขีดจำกัด
ขนาดหลังถอดรหัสต่อวิดีโอแบบเผื่อความปลอดภัยที่ 36 MiB เพื่อให้เอนเวโลปของโมเดล/ข้อความ/เฟรม
ยังคงอยู่ภายในขีดจำกัดการรับคำขอ JSON สาธารณะที่ 50 MiB
ระบบจะตรวจสอบความยาวแบบอินไลน์และค่าประมาณขนาดหลังถอดรหัสก่อนจัดสรรหน่วยความจำ
URL ระยะไกลเริ่มต้นและทุกการเปลี่ยนเส้นทางต้องใช้ HTTPS โดยใช้
ตัวป้องกันขาออกเฉพาะปลายทางสาธารณะที่มีอยู่เดิมพร้อมการตรึง DNS จากนั้นไบต์จะข้ามขอบเขตโบรกเกอร์ภายใน
`POST /api/modality-bridge/video/extract` โดยตรง เส้นทางดังกล่าวเป็นทั้ง
`LOCAL_ONLY` และ `SPAWN_CAPABLE` โดยยอมรับเฉพาะคำขอจากลูปแบ็กที่เชื่อถือได้
และผ่านการรับรองความถูกต้องภายในแต่ละโปรเซสเท่านั้น และจะไม่ยอมรับ URL, พาธระบบไฟล์, ไฟล์ปฏิบัติการ
หรือรายการอาร์กิวเมนต์เป็นอันขาด ไปป์ไลน์ขนาดเนื้อหาของ API และตัวอ่านเนื้อหาแบบเพิ่มหน่วย
ของตัวจัดการจะบังคับใช้ขีดจำกัดอินพุตโบรกเกอร์ 50 MiB แยกจากกัน คิวแบบมีขอบเขตของระบบ
จะทำการแยกข้อมูลครั้งละหนึ่งงาน อนุญาตให้มีงานรอได้สี่งาน และจำกัดอินพุตที่รออยู่ไว้ที่
100 MiB

ภายในโบรกเกอร์ `ffprobe` จะอ่านไฟล์ภายในแบบส่วนตัว รายการรูปแบบที่อนุญาตแบบตายตัว
จะไม่รวมรูปแบบเพลย์ลิสต์และแมนิเฟสต์ สำหรับคอนเทนเนอร์ตระกูล MOV ที่อนุญาต
การอ้างอิงข้อมูล MOV ภายนอกจะยังคงปิดใช้งานโดยค่าเริ่มต้น และคำสั่งแบบตายตัว
จะไม่เลือกเปิดใช้งาน ทั้ง `ffprobe` และ `ffmpeg` ใช้รายการโปรโตคอลที่อนุญาต
เฉพาะ `file` หนึ่งเธรด อาร์เรย์อาร์กิวเมนต์แบบตายตัว ไม่มีเชลล์
และไฟล์ปฏิบัติการที่ค้นหาจาก `PATH` สตรีมภาพปกที่แนบมาจะไม่ถือเป็น
ตัวเลือกที่เล่นได้ สตรีมที่เล่นได้ทั้งหมดต้องเป็นไปตามขีดจำกัด และระบบจะเลือก
สตรีมเริ่มต้นที่ระบุอย่างชัดเจนก่อนทางเลือกสำรองแบบกำหนดแน่นอนซึ่งใช้ดัชนีต่ำสุด
วิดีโอถูกจำกัดไว้ที่ 600 วินาที, 8,192 พิกเซลต่อมิติ และ
33,554,432 พิกเซลต้นฉบับ FFmpeg จะสุ่มตัวอย่างเฟรม JPEG ที่จุดกึ่งกลางจำนวน 1–16 เฟรม
ลดขนาดขอบด้านยาวลงให้ไม่เกิน 1,024 พิกเซลโดยไม่ขยายอินพุตที่มีขนาดเล็กกว่า
และจะไม่ได้รับ URL เป็นอันขาด โดยค่าเริ่มต้น การสุ่มตัวอย่างจะเป็น `uniform`
นโยบาย `scene_aware` ซึ่งเป็นทางเลือกและ `segment_aware` ซึ่งเป็นแบบทดลอง
จะดำเนินการ FFmpeg แบบตายตัวเพิ่มอีกหนึ่งรอบกับสตรีมภายในที่ผ่านการตรวจสอบแล้ว
เลือกการประทับเวลาของฉากจาก `showinfo` ภายในขอบเขต และย้อนกลับไปใช้จุดกึ่งกลางแบบสม่ำเสมอเดิม
อย่างกำหนดแน่นอนเมื่อการตรวจจับล้มเหลว หมดเวลา เอาต์พุตผิดรูปแบบ หรือชุดตัวเลือกว่างเปล่า
โหมดที่รับรู้เซกเมนต์จะจัดสรรตัวอย่างจุดกึ่งกลางตามสัดส่วนของช่วงฉากที่ผ่านการตรวจสอบ
หลักฐานและพฤติกรรมสำรองของโหมดที่รับรู้เซกเมนต์จะอธิบายโดยละเอียดด้านล่าง
ขีดจำกัดสูงสุดแบบตายตัวที่ 16 เฟรมจะถูกนำไปใช้หลังการเลือกในทุกนโยบาย
เมื่อคำขอแบบรับรู้ฉากมีงบประมาณเพียงหนึ่งเฟรม ระบบจะใช้จุดกึ่งกลางแบบสม่ำเสมอ
ของวิดีโอเต็มหรือหน้าต่างโฟกัสที่ใช้งานอยู่ และรายงาน `policyEffective: uniform`:
เฟรมฉากที่เลือกเพียงเฟรมเดียวไม่สามารถคงข้อมูลของปลายช่วงเวลาทั้งสองด้านไว้ได้
ผู้เรียกอาจระบุหน้าต่างโฟกัสที่มีค่าจำกัด (`start`/`end` เป็นวินาที) หรือไม่ก็ได้
ขอบเขตจะถูกปรับให้อยู่ภายในระยะเวลาของสื่อ หน้าต่างที่กลับลำดับหรือมีค่าไม่จำกัดจะถูกปฏิเสธ
และนโยบายการสุ่มตัวอย่างทั้งหมดจะดำเนินการเฉพาะภายในช่วงที่ปรับให้เป็นมาตรฐานแล้ว
หน้าต่างที่ได้จะรวมอยู่ในข้อมูลเมตาการสุ่มตัวอย่างและคำนำหน้าคำอธิบายที่ไม่น่าเชื่อถือ
เพื่อให้โมเดลปลายทางสามารถแยกแยะส่วนที่เน้นเฉพาะจากไทม์ไลน์ทั้งหมดได้

การโฟกัสคำบรรยายเชิงความหมายเป็นการตั้งค่าที่ชัดเจนและแยกต่างหาก โหมดการวิเคราะห์
`full` ซึ่งเป็นค่าเริ่มต้นจะคงพรอมต์เฟรมเดิมไว้และจะไม่ส่งต่อข้อความคำขอ
ไปยังโมเดลคำบรรยาย ในโหมด `focused` บริดจ์จะอ่านเฉพาะ `text`/`input_text`
ล่าสุดที่ไม่ว่างและผู้ใช้เป็นผู้เขียน จากคอนเทนเนอร์ Chat หรือ Responses เดียวกัน
ปรับให้เป็นรูปแบบ NFC รวมอักขระควบคุมและช่องว่าง และจำกัดไว้ที่ 500 จุดรหัส Unicode
ผลลัพธ์ว่างเปล่าจะย้อนกลับไปใช้พรอมต์ `full` เดิมทุกประการ คำใบ้ที่ใช้งานได้
จะถูกแปลงเป็น JSON ในบล็อกบริบทผู้ใช้ที่ไม่น่าเชื่อถือโดยเฉพาะ
และใช้ได้เพียงเพื่อจัดลำดับความสำคัญของรายละเอียดที่สังเกตได้เท่านั้น โดยไม่สามารถลบล้าง
คำเตือนแยกต่างหากที่ห้ามปฏิบัติตามคำสั่งซึ่งมองเห็นหรือได้ยินในสื่อ
โฟกัสแบบข้อความจะไม่อนุมาน `start`/`end` หรือเปลี่ยนแปลงตัวสุ่มตัวอย่างเชิงเวลา

#### หลักฐานเซกเมนต์เชิงโครงสร้าง FU-07

`segment_aware` ใช้การวิเคราะห์ล่วงหน้าแบบมีขอบเขตหนึ่งรอบกับสตรีมวิดีโอภายในที่ผ่านการตรวจสอบแล้ว ห่วงโซ่ตัวกรองแบบคงที่จะย่อขนาดให้มีความกว้างไม่เกิน 320 พิกเซล ตรวจจับการเปลี่ยนฉากและช่วงภาพค้าง จากนั้นสุ่มตัวอย่างที่ 1 เฟรมต่อวินาทีเพื่อวัดความเบลอ ค่าลูมาเฉลี่ย และข้อมูลเชิงพื้นที่/เวลา รอบการวิเคราะห์นี้จำกัดไว้ที่ตัวอย่างเชิงโครงสร้าง 600 ตัวอย่าง ใช้เธรด FFmpeg/ตัวกรองหนึ่งเธรด ใช้รายการอนุญาตสำหรับโปรโตคอลเฉพาะ `file` และคอนเทนเนอร์ชุดเดียวกัน จำกัดเอาต์พุตของกระบวนการไว้ที่ 1 MiB และใช้เวลาได้ไม่เกิน 30 วินาทีภายในกลไกยกเลิก/กำหนดเวลาสิ้นสุดร่วมของโบรกเกอร์ ระบบจะไม่รับคำสั่ง ตัวกรอง พาธ หรือ URL จากคำขอโดยเด็ดขาด

ค่าเชิงโครงสร้างเป็นหลักฐานจากการสุ่มตัวอย่างที่ให้ผลแบบกำหนดแน่นอน ไม่ใช่ความเข้าใจเชิงความหมายของวิดีโอ ค่าเหล่านี้ไม่ได้อนุมานวัตถุ การกระทำ คำบรรยาย เสียงพูด หรือเจตนาของผู้ใช้ ขอบเขตของฉากและภาพค้างจะก่อตัวเป็นเซกเมนต์ ส่วนสัดส่วนภาพค้าง ความเบลอ การรับแสง รายละเอียดเชิงพื้นที่ และการเปลี่ยนแปลงตามเวลา มีผลเฉพาะต่อวิธีจัดสรรงบประมาณ 1–16 เฟรมที่มีอยู่เท่านั้น เซกเมนต์ที่ภาพค้างทั้งหมดจะถูกจำกัดไว้ที่หนึ่งเฟรม ขณะที่เซกเมนต์ที่ไม่ค้างจะแข่งขันกันเพื่อใช้งบประมาณที่เหลือ เมื่อจำนวนขอบเขตมากกว่าจำนวนเฟรม ระบบจะยังคงการครอบคลุมไทม์ไลน์แบบสม่ำเสมอ เพื่อไม่ให้การตัดฉากอย่างรวดเร็วในช่วงต้นบดบังเซกเมนต์ยาวที่อยู่ท้ายวิดีโอ ขอบเขตฉากที่อยู่ภายในความละเอียดการวิเคราะห์ 1 วินาทีจากขอบเขตภาพค้างจะถูกรวมเข้าด้วยกัน

หากไม่มีตัวกรอง หลักฐานผิดรูปแบบ/ว่างเปล่า ตัวตรวจจับเกิดข้อผิดพลาด หรือการวิเคราะห์ล่วงหน้าแบบมีขอบเขตหมดเวลา ระบบจะเปิดทางให้ดำเนินการต่อโดยใช้นโยบายจุดกึ่งกลางแบบสม่ำเสมอที่ตรงกันทุกประการ การยกเลิกโดยผู้เรียกหรือการถึงกำหนดเวลาสิ้นสุดของโบรกเกอร์จะไม่เปิดทางให้ดำเนินการต่อ แต่จะยุติกระบวนการย่อยที่กำลังทำงาน ป้องกันการแยกเฟรมในภายหลัง และลบโครงสร้างไดเรกทอรีชั่วคราวส่วนตัวใน `finally`

`scripts/perf/video-bridge-fu07-eval.ts` สร้างฟิกซ์เจอร์ FFmpeg จริงที่ให้ผลแบบกำหนดแน่นอน สำหรับวัดการลดจำนวนครั้งที่เรียกสร้างคำบรรยายหลังการขจัดรายการซ้ำ การจัดสรรงบประมาณสำหรับการเคลื่อนไหวหนาแน่น หลักฐานความเบลอ/การรับแสง/SI-TI การตัดฉากอย่างรวดเร็วที่มีช่วงท้ายยาว และผลบวกลวงจากการเฟดแบบค่อยเป็นค่อยไป สคริปต์จะบันทึกเวลาจริงที่ใช้ในการวิเคราะห์ล่วงหน้า และในกรณีที่มี `/usr/bin/time` ให้ใช้งาน จะบันทึก CPU ของกระบวนการลูกและค่า RSS สูงสุดด้วย การตรวจสอบคุณภาพของสคริปต์เป็นเพียงออราเคิลเชิงโครงสร้างเท่านั้น คุณภาพของโมเดลสร้างคำบรรยายจริงยังคงเป็น `HOLD` เนื่องจากชุดทดสอบนี้ไม่มีเอนด์พอยต์ที่ได้รับอนุญาตหรือผู้ตัดสินที่ตรึงไว้ การประหยัดต้นทุนยังคงเป็น `HOLD` เช่นกัน เว้นแต่ `--caption-cost-per-call-usd` จะระบุค่าประมาณต้นทุนต่อครั้งที่เป็นบวกอย่างชัดเจน สคริปต์จะไม่สร้างผลลัพธ์ทั้งสองขึ้นเอง

แต่ละเฟรมถูกจำกัดไว้ที่ 4 MiB เฟรมดิบทั้งหมดรวมกันถูกจำกัดไว้ที่ 23 MiB และการตอบกลับของโบรกเกอร์ที่ผ่านการทำให้เป็นอนุกรมถูกจำกัดไว้ที่ 32 MiB ไดเรกทอรีชั่วคราวส่วนตัวจะถูกลบใน `finally` OmniRoute ไม่ได้รวม FFmpeg มาด้วยและไม่ยอมรับพาธไฟล์ปฏิบัติการที่กำหนดเอง ก่อนสร้างคำบรรยาย บริดจ์จะใช้กระบวนการขจัดภาพซ้ำแบบระมัดระวัง โดยลด JPEG แต่ละภาพให้เป็นบัฟเฟอร์ระดับสีเทาขนาด 16×16 แล้วเปรียบเทียบเฉพาะกับเฟรมล่าสุดที่เก็บไว้ สำหรับงบประมาณคำบรรยายที่ร้องขอซึ่งมากกว่าหนึ่งเฟรม การแยกเฟรมจะจัดเตรียมพูลผู้สมัครแบบมีขอบเขตที่มีขนาดไม่เกินสองเท่าของงบประมาณดังกล่าว และไม่เกิน 16 เฟรม ขีดจำกัดที่ร้องขอจะถูกนำมาใช้หลังการขจัดรายการซ้ำเท่านั้น โดยจะรักษาผู้สมัครตัวแรกและตัวสุดท้ายที่เลือกไว้ระหว่างการลดจำนวนขั้นสุดท้าย เมื่องบประมาณมีอย่างน้อยสองเฟรม นโยบายแบบมีเวอร์ชัน `grayscale-16x16-mean-cells-v2` ใช้ค่าที่มากกว่าระหว่างผลต่างของค่าลูมาเฉลี่ยกับอัตราส่วนของเซลล์ภาพย่อที่มีผลต่างแบบทำให้เป็นมาตรฐานอย่างน้อย 0.05 เกณฑ์สำหรับภาพซ้ำเป็นค่าคงที่ 0.04 ซึ่งเลือกเพื่อให้คาดการณ์ได้ แทนที่จะเปิดให้ตั้งค่าขณะรัน สัญญาณคอนทราสต์สูงลำดับรองนี้ช่วยรักษาการเคลื่อนไหวขนาดเล็กและการเปลี่ยนแปลงของข้อความที่มองเห็นได้ ซึ่งการเปรียบเทียบด้วยค่าเฉลี่ยเพียงอย่างเดียวอาจบดบังไว้ ข้อผิดพลาดของตัวเปรียบเทียบหรือตัวถอดรหัสจะเปิดทางให้ดำเนินการต่อและคงการครอบคลุมไว้ เมทาดาทาเอาต์พุตจะแยกผู้สมัครที่แยกออกมา เฟรมที่ใช้งานสำเร็จ และภาพซ้ำที่ถูกตัดทิ้งออกจากกัน

ส่วนวิดีโอที่ทำเครื่องหมายไว้อย่างชัดเจนอาจร้องขอคอนแทคชีตพร้อมการประทับเวลา บริดจ์จะสร้างกริด JPEG ที่มีไม่เกิน 4 คอลัมน์และ 16 เฟรม แต่ละเซลล์ขนาด 512 พิกเซลจะฝังเวลาต้นทางลงในแถบคอนทราสต์สูงที่ด้านล่าง ขณะเดียวกันจะเก็บเวลาเดียวกันไว้ในเมทาดาทาแบบข้อความสำหรับการเชื่อมโยงและการตรวจสอบย้อนหลังในขั้นตอนถัดไป JPEG ฉบับสมบูรณ์ยังคงถูกจำกัดไว้ที่ 32 MiB หาก `sharp` ไม่สามารถถอดรหัสหรือประกอบกริดได้ บริดจ์จะย้อนกลับไปใช้เฟรม JPEG แยกแต่ละเฟรม ส่วนการยกเลิกโดยไคลเอนต์จะยังคงส่งผ่านไปยังกระบวนการสร้างชีต

หลักฐานสำหรับการเลื่อนสถานะแยกออกจากไมโครเบนช์มาร์กการประกอบแบบสังเคราะห์โดยเจตนา `scripts/perf/video-bridge-contact-sheet-eval.ts` กำหนดชุดทดสอบ A/B ที่มีการกำหนดเวอร์ชันสคีมาสำหรับโมเดลการมองเห็นจริงที่เข้ากันได้กับ OpenAI โดยวัดโทเค็นที่ผู้ให้บริการรายงาน เวลาแฝงตั้งแต่ต้นจนจบตามเวลาจริงซึ่งรวมการประกอบชีต จำนวนครั้งที่เรียกโมเดล และการคงไว้ซึ่งข้อเท็จจริงที่กำหนดในแมนิเฟสต์ การตอบกลับดิบจากโมเดลจะไม่ถูกเขียนลงในรายงาน โดยจะเก็บไว้เฉพาะไดเจสต์ SHA-256 และ ID ของข้อเท็จจริงที่ตรงกัน ชุดทดสอบจะไม่เรียกใช้เครือข่ายหรือโมเดลแบบเสียค่าใช้จ่าย เว้นแต่จะส่ง `--execute-real` และกำหนดค่า `--model`, `OMNIROUTE_BASE_URL` และ `OMNIROUTE_API_KEY` แล้ว หากไม่มีการรันจริงที่ระบุอย่างชัดเจนดังกล่าว คำตัดสินที่เครื่องอ่านได้จะยังคงเป็น `HOLD` การวัดเพย์โหลด/จำนวนครั้งที่เรียกแบบสังเคราะห์เพียงอย่างเดียวไม่ถือเป็นหลักฐานสำหรับการเลื่อนสถานะ

ผู้เรียกสามารถแนบอาร์เรย์ `transcript.cues` ซึ่งเป็นตัวเลือกไปยังส่วนวิดีโอที่รองรับได้ เมื่อมีข้อความที่จัดแนวเวลาไว้แล้ว แต่ละคิวต้องมี `text` ช่วงเวลา `start`/`end` ที่เป็นค่าจำกัดและอยู่ภายในระยะเวลาที่ตรวจสอบได้ และ `source` ที่อยู่ในรายการอนุญาต (`client`, `embedded` หรือ `audio-bridge`) โดย `confidence` มีค่าเริ่มต้นเป็น `1` และต้องอยู่ระหว่าง `0` ถึง `1` คิวที่ซ้ำกันทุกประการจะถูกรวมเข้าด้วยกัน OmniRoute จะไม่เริ่มการถอดเสียงจากเมทาดาทานี้ โดยคิวที่ผ่านการตรวจสอบแล้วจะถูกคัดลอกไปยังผลลัพธ์ที่อธิบาย พร้อมแหล่งที่มา ความเชื่อมั่น และช่วงเวลา และจะแสดงผลเป็นข้อสังเกตที่ไม่น่าเชื่อถือควบคู่กับคำบรรยายเฟรม ข้อความที่ไม่ถูกต้อง อยู่นอกช่วง หรือไม่มีที่มาจะถูกปฏิเสธแทนที่จะนำไปผสมกับสตรีมคำบรรยาย ปัจจุบันฟิลด์ `source` เป็นค่าที่ผู้เรียกประกาศเอง ไม่ใช่ค่าที่เซิร์ฟเวอร์ตรวจสอบ OmniRoute บังคับใช้เพียงว่าค่าต้องเป็นหนึ่งในสามสตริงที่อนุญาต แต่ยังไม่ได้ยืนยันด้วยวิธีการเข้ารหัสลับว่าป้ายกำกับ `embedded` หรือ `audio-bridge` มาจากการแยกข้อมูลที่เซิร์ฟเวอร์เป็นเจ้าของจริง ให้ถือว่า `source` เป็นเพียงคำบอกใบ้ที่ไม่น่าเชื่อถือจนกว่าจะมีการตรวจสอบดังกล่าว และอย่าใช้ฟิลด์นี้เป็นพื้นฐานในการตัดสินใจด้านการอนุญาตสิทธิ์

ผู้เรียกใช้งานขั้นสูงอาจระบุแทร็ก `audioTranscript` ที่ได้รับอนุญาตแล้ว

| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` จะคงคำบรรยายทั่วไปไว้ ส่วน `focused` จะใช้บริบทล่าสุดจากผู้ใช้ที่ไม่น่าเชื่อถือและมีขอบเขตจำกัด          |
| `modalityBridgeVideoModel`          | `""`        | สืบทอดโมเดล Vision Bridge                                                                                       |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                            |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware` หรือ `segment_aware` แบบเป็นสัดส่วน หากตัวตรวจจับล้มเหลว ระบบจะย้อนกลับไปใช้ `uniform` |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                             |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                                  |

ค่าไทม์เอาต์ Video แบบเดิมที่บันทึกไว้นานกว่า 120 วินาทีจะถูกจำกัดไว้ที่กำหนดเวลาสิ้นสุดของโบรกเกอร์ ส่วนการเขียนการตั้งค่าใหม่ที่เกินขีดจำกัดดังกล่าวจะถูกปฏิเสธ `GET /api/modality-bridge/video/runtime` กำหนดให้ต้องมีตำแหน่งแบบลูปแบ็กที่ประทับตราและเชื่อถือได้ ก่อนการยืนยันตัวตนหรือการตรวจสอบรันไทม์ จากนั้นจึงต้องมีสิทธิ์ยืนยันตัวตนระดับการจัดการ ระบบจะส่งคืนเฉพาะ `available` เวอร์ชัน FFmpeg/ffprobe ที่ผ่านการปรับให้ปลอดภัยแล้ว และเหตุผลคงที่เมื่อรันไทม์ไม่พร้อมใช้งาน เอนด์พอยต์สำหรับการแยกข้อมูลภายในไม่ใช่ API อัปโหลดสาธารณะ เมื่อคิวเต็มจะส่งคืน `503` พร้อม `Retry-After` เมื่อผู้เรียกตัดการเชื่อมต่อจะส่งคืน `499` และเมื่อถึงกำหนดเวลาสิ้นสุดคงที่ของโบรกเกอร์จะส่งคืน `504` การตอบกลับที่แปลงแล้วจะเพิ่ม `video->text;model=<visionModel>;parts=<videos>` ลงในส่วนหัวส่วนกลาง `x-omniroute-modality-bridge` โดยไม่ลบเซกเมนต์ Vision หรือ Audio

### ตัวปกปิด PII (`piiMasker.ts`)

ทำงานใน **ทั้งสอง** ขั้นตอน

- **`preCall`** โคลนเพย์โหลด ตรวจสอบ `system`, `messages`, `input` และ
  `prompt` (รวมถึงรายการที่เป็นสตริงล้วน) และใช้ `processPII()` (จาก
  `@/shared/utils/inputSanitizer`) กับฟิลด์ `content`/`text` ที่เป็นสตริง เมื่อ
  `PII_REDACTION_ENABLED=true` ระบบจะปกปิด PII ที่ตรวจพบในเพย์โหลดขาออก
  การทำงานนี้ไม่ขึ้นกับ `INPUT_SANITIZER_MODE` (ซึ่งควบคุมเฉพาะนโยบาย
  การแทรกคำสั่งในพรอมต์) เมื่อปิดการปกปิด การเรียกจะบันทึกจำนวนการตรวจพบ
  โดยไม่แก้ไขเนื้อหา
- **`postCall`** ทำ deep clone การตอบกลับ แล้วเรียกใช้ `sanitizePIIResponse()`
  พร้อมกับตัวปกปิดสำหรับโครงสร้าง Responses API (`maskResponsesOutput` —
  ครอบคลุม `output_text` และ `output[].content[].text`) หากมีการปกปิดใดๆ
  การตอบกลับที่แก้ไขแล้วจะแทนที่การตอบกลับเดิม

การ์ดเรลจะไม่บล็อก แต่จะเพิ่มคำอธิบายประกอบ (`meta.detections`,
`meta.redacted`) หรือเขียนเนื้อหาใหม่เท่านั้น

### การแทรกคำสั่งในพรอมต์ (`promptInjection.ts`)

ตรวจจับโครงสร้างเชิงโจมตีในเนื้อหาที่ผู้ใช้ป้อนและบังคับใช้นโยบาย
ที่กำหนดค่าไว้ ลักษณะการทำงานถูกควบคุมโดยตัวแปรสภาพแวดล้อมและตัวเลือก
ของ constructor:

| การตั้งค่า    | ตัวแปรสภาพแวดล้อม                                                                                        | ค่าเริ่มต้น | ผล                                                                                                                                                                                              |
| ------------- | -------------------------------------------------------------------------------------------------------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| เปิดใช้งาน    | `INPUT_SANITIZER_ENABLED`                                                                                | `true`      | เมื่อเป็น `false` การ์ดเรลจะลัดวงจรและหยุดทำงานทันที                                                                                                                                            |
| โหมด          | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                          | `warn`      | นโยบายการแทรกคำสั่ง: `block`, `warn` หรือ `log` (`redact` ยังคงรองรับเพื่อความเข้ากันได้ย้อนหลัง แต่จะ **ไม่** ลบข้อความการแทรกคำสั่ง การเขียน PII ในคำขอใหม่ควบคุมโดย `PII_REDACTION_ENABLED`) |
| เกณฑ์การบล็อก | ตัวเลือก `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (นามแฝง `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`      | ระดับความรุนแรงขั้นต่ำที่จำเป็นสำหรับการบล็อก โดยค่าเริ่มต้น ระดับปานกลางจะใช้สำหรับการเฝ้าสังเกตเท่านั้น                                                                                       |

**ลำดับความสำคัญของโหมด** (`getMode`): `options.mode` ของผู้เรียก →
การแทนที่ด้วย **แฟล็กฟีเจอร์ใน DB** สำหรับ `INJECTION_GUARD_MODE` (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` ในสภาพแวดล้อม → `INPUT_SANITIZER_MODE` ในสภาพแวดล้อม →
`warn` ดังนั้น การแทนที่จากแดชบอร์ดจะมีความสำคัญเหนือกว่าตัวแปรสภาพแวดล้อม
ทำให้ UI ของ Feature Flags ควบคุมการ์ดที่กำลังทำงานได้แบบสดๆ (ไม่ต้องรีสตาร์ต)
การอ่าน DB มีระบบป้องกันความล้มเหลว: หากเกิดข้อผิดพลาด การ์ดจะกลับไปใช้พฤติกรรม
ตามสภาพแวดล้อม และเมื่อไม่ได้ตั้งค่าการแทนที่ พฤติกรรมจะเหมือนกับการประมวลผล
โดยอาศัยสภาพแวดล้อมเพียงอย่างเดียว

แหล่งที่มาของการตรวจจับ:

1. `sanitizeRequest()` จาก `@/shared/utils/inputSanitizer` (ชุดตัวตรวจจับร่วม
   ที่ใช้ในส่วนอื่นของไปป์ไลน์)
2. `DEFAULT_GUARD_PATTERNS` ในตัว (ปัจจุบันคือ `system_override_inline` และ
   `markdown_system_block` ซึ่งทั้งคู่มีระดับความรุนแรง `high`)
3. `customPatterns` แบบไม่บังคับที่ส่งผ่านตัวเลือกของ constructor (สตริง, regex
   หรือเรคคอร์ด `{ name, pattern, severity }`)

เมื่อ `mode === "block"` **และ** มีการตรวจพบอย่างน้อยหนึ่งรายการที่ถึงเกณฑ์
ระดับความรุนแรง `preCall` จะคืนค่า `{ block: true, message: "Request rejected:
suspicious content detected" }` ในโหมด `warn`/`log` การ์ดเรลจะบันทึกล็อก
แต่อนุญาตให้ดำเนินการเรียกต่อไป นอกจากนี้ shared helper `evaluatePromptInjection()`
ยังถูก export ไว้สำหรับผู้เรียกที่ต้องการประเมินพรอมต์โดยไม่ผ่าน registry

**ขอบเขตการสแกน (v3.8.20):** ตัวตรวจจับจะตรวจสอบเฉพาะ **16 KB แรก** ของ
ข้อความพรอมต์ที่รวมแล้ว — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ไบต์) ใน
`src/shared/utils/inputSanitizer.ts` ทั้ง `detectInjection()` และ
`evaluatePromptInjection()` จะใช้ `slice(0, MAX_INJECTION_SCAN_BYTES)` ก่อนเรียกใช้
ลูปรูปแบบ คำสั่งแทรกมักอยู่ใกล้ส่วนต้นของอินพุต ดังนั้นวิธีนี้จึงจำกัดการใช้
CPU/GC ของ regex บนเพย์โหลดขนาดหลายร้อย KB โดยไม่ลดประสิทธิภาพการตรวจจับ (ดู
#3932, #4041)

### ตัวปกปิดข้อมูลประจำตัว (`credentialMasker.ts`)

ทำงานใน **ทั้งสอง** ขั้นตอน โดยเป็นลำดับสุดท้ายในเชนเริ่มต้น (ลำดับความสำคัญ `95`)
ปกปิดรูปแบบ API key / โทเค็นลับที่รู้จักกันทั่วไปจากเพย์โหลดขาออก (เนื้อหาข้อความ
อาร์กิวเมนต์การเรียกเครื่องมือ ผลลัพธ์จากเครื่องมือ) **และ** การตอบกลับจากผู้ให้บริการ
เพื่อไม่ให้ข้อมูลประจำตัวที่วางลงในพรอมต์ (หรือถูกส่งกลับมาจากผลลัพธ์ของเครื่องมือ)
รั่วไหลไปยังผู้ให้บริการต้นทางหรือกลับไปยังไคลเอนต์

- **เปิดใช้งานโดยสมัครใจเท่านั้น** ตามแนวทางเดียวกับการปกปิด PII (ใกล้เคียงกับกฎตายตัวข้อ #20):
  ปิดใช้งาน เว้นแต่ `settings.credentialRedactionEnabled === true` **หรือ**
  `CREDENTIAL_REDACTION_ENABLED=true` เมื่อปิดอยู่ guardrail นี้จะไม่ดำเนินการใด ๆ —
  โดยจะไม่บล็อกและไม่เขียนข้อมูลใหม่
- `redactCredentials()` จะไล่ตรวจสอบโครงสร้างทั้งหมดของ payload/response (`walkValue()`
  ปลอดภัยจาก prototype pollution และป้องกันวงจรด้วย `WeakSet`) พร้อมแทนที่รายการที่ตรงกันด้วย
  ตัวแทน `[REDACTED:<type>]` โดยโคลนเฉพาะ branch ที่มีการเปลี่ยนแปลงจริงเท่านั้น
- `CREDENTIAL_PATTERNS` ครอบคลุมคีย์ของผู้ให้บริการ LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), โทเค็น VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), คีย์การชำระเงิน (Stripe, Square), คีย์บริการคลาวด์
  (AWS access key, Twilio, SendGrid, Mailgun), private key / JWT,
  connection string ที่มีข้อมูลประจำตัว (`mongodb://user:pass@...` เป็นต้น) และ
  รูปแบบค่าของ header แบบทั่วไปสำหรับ `Authorization`/`x-api-key`/`api-key`/`apikey`
  คีย์ที่มีรูปแบบเป็น header (`authorization`, `x-api-key`, `api-key`,
  `apikey`) จะถูกปกปิดตามโครงสร้าง (เฉพาะค่า โดยคงคำนำหน้ารูปแบบการยืนยันตัวตน เช่น
  `Bearer `/`Basic ` ไว้) แทนการใช้ regex ข้อความทั่วไป
- guardrail นี้จะไม่บล็อก แต่จะเขียนข้อมูลใหม่เท่านั้น (`modifiedPayload` /
  `modifiedResponse`) และเพิ่มคำอธิบายกำกับ (`meta.credentialsRedacted`, `meta.count`)

ตัวป้องกัน regression: `tests/unit/credential-masker-guardrail.test.ts`

## สัญญาพื้นฐาน (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // ค่า true จะลัดวงจรของเชน
  message?: string; // แสดงเมื่อมีการบล็อก
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // ส่งคืนโดย preCall เพื่อเขียนคำขอใหม่
  modifiedResponse?: TValue; // ส่งคืนโดย postCall เพื่อเขียนการตอบกลับใหม่
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

การ์ดเรลระบุว่า "ไม่มีการเปลี่ยนแปลง" ด้วยการส่งคืน `void`, `{}` หรือ
`{ block: false }` อย่างใดอย่างหนึ่ง การส่งคืน `modifiedPayload`/`modifiedResponse`
จะแทนที่ค่าที่ไหลผ่านเชนสำหรับการ์ดเรลลำดับถัดไป
`signal?: AbortSignal` ส่งต่อวงจรชีวิตของผู้เรียกไปยังการ์ดเรล การยกเลิกคำขอเป็นข้อยกเว้นแบบยอมให้ทำงานต่อโดยเจตนา: บริดจ์สื่อจะหยุดการทำงานและล้างทรัพยากร โดยไม่กู้คืนสื่อดิบไปยังปลายทางที่ทราบว่าไม่รองรับสื่อนั้น

## รีจิสทรี (`registry.ts`)

ซิงเกิลตัน `guardrailRegistry` เปิดเผยเมธอดต่อไปนี้:

- `register(guardrail)` — เพิ่มการ์ดเรล (หรือแทนที่ตามชื่อที่ผ่านการทำให้เป็นมาตรฐาน)
  และเรียงลำดับใหม่ตาม `priority` จากน้อยไปมาก
- `clear()` / `list()` — ตัวช่วยสำหรับการดูแลระบบ
- `runPreCallHooks(payload, context)` — วนซ้ำการ์ดเรลที่ทำงานอยู่ ส่งต่อ
  เพย์โหลดผ่าน `modifiedPayload` และหยุดเมื่อพบ `block: true` ครั้งแรก
- `runPostCallHooks(response, context)` — ใช้โฟลว์เดียวกันกับฝั่งการตอบกลับ
- `resetGuardrailsForTests({ registerDefaults })` — ล้างสถานะและเลือก
  ลงทะเบียนค่าเริ่มต้นใหม่เพื่อแยกการทดสอบอย่างสะอาด

รันเนอร์ทั้งสองส่งคืน `{ blocked, payload|response, results, guardrail?, message? }`
โดย `results` เป็นอาร์เรย์ของเรคคอร์ด `GuardrailExecutionResult` ซึ่งประกอบด้วย
ฟิลด์ `blocked`, `skipped`, `modified`, `error` และ `meta` ของแต่ละการ์ดเรล
ซึ่งมีประโยชน์สำหรับการติดตาม

### การปิดใช้งานการ์ดเรลสำหรับแต่ละคำขอ

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` รวบรวมรายการ
ชื่อการ์ดเรลที่ตัดรายการซ้ำแล้ว ซึ่งควรข้ามสำหรับคำขอปัจจุบัน
แหล่งที่มา (ทั้งหมดเป็นตัวเลือกและนำมารวมกันทั้งหมด):

- `apiKeyInfo.disabledGuardrails`
- `disabledGuardrails` ในเนื้อหาคำขอ (ระดับบนสุด)
- `metadata.disabledGuardrails` ในเนื้อหาคำขอ
- เฮดเดอร์ `x-omniroute-disabled-guardrails` (หรือชื่อเดิม
  `x-disabled-guardrails`)

ค่าอาจเป็นอาร์เรย์ของสตริงหรือสตริงที่คั่นด้วยจุลภาค ชื่อจะถูก
ทำให้เป็นอักษรพิมพ์เล็กในรูปแบบ kebab-case (`pii_masker` → `pii-masker`) ผลลัพธ์
จะถูกส่งผ่าน `context.disabledGuardrails` ไปยังรีจิสทรี ซึ่งจะข้าม
การ์ดเรลที่ตรงกัน (`skipped: true` ใน `results`)

## ลำดับการดำเนินการ

สำหรับแต่ละคำขอที่ไหลผ่าน `src/sse/handlers/chat.ts` และ
`open-sse/handlers/chatCore.ts`:

1. `resolveDisabledGuardrails(...)` สร้างรายการที่ต้องข้ามจาก API key, body
   และ headers
2. `guardrailRegistry.runPreCallHooks(body, ctx)` เรียกใช้ guardrails ตามลำดับ
   priority จากน้อยไปมาก:
   - Guardrails ที่ปิดใช้งานจะถูกบันทึกเป็น `skipped`
   - `preCall` ของแต่ละ guardrail อาจเขียน payload ใหม่ผ่าน `modifiedPayload`
   - รายการแรกที่มี `block: true` จะยุติลำดับการทำงานทันที และ handler จะส่งคืน
     การตอบกลับที่ระบุว่า guardrail ปฏิเสธคำขอ
3. Payload ที่อาจถูกเขียนใหม่จะถูกส่งต่อไปยัง combo routing และการส่งคำขอ
   ไปยัง upstream
4. หลังจากประกอบการตอบกลับแล้ว `guardrailRegistry.runPostCallHooks(...)`
   จะเรียกใช้ลำดับเดิมกับการตอบกลับ หากพบ `block: true` ในขั้นตอนนี้ การตอบกลับ
   จาก upstream จะถูกละทิ้ง

Guardrails ที่ throw ข้อผิดพลาดจะถูกบันทึกด้วย `error: <message>` และเขียน log ผ่าน
`logger.warn` แต่ลำดับการทำงานจะดำเนินต่อไป ซึ่งเป็นการออกแบบแบบ fail-open

## การกำหนดค่า

ตัวแปรสภาพแวดล้อมที่ guardrails ในตัวอ่าน:

| ตัวแปร                                | ใช้โดย                    | ผลกระทบ                                                                                                  |
| ------------------------------------- | ------------------------- | -------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | ตั้งค่าเป็น `false` เพื่อปิดใช้งานการตรวจจับทั้งหมด                                                      |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`        | นโยบายการตรวจจับ injection: `warn`, `block` หรือ `log` ค่าเดิม `redact` จะไม่เขียนข้อความ injection ใหม่ |
| `INJECTION_GUARD_MODE`                | `prompt-injection`        | โหมดสำหรับ injection guard และยังเป็น DB feature flag ที่ **มีผลเหนือกว่า** env vars (DB > ENV)          |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`        | ระดับความรุนแรงขั้นต่ำที่ `MODE=block` จะปฏิเสธ: `high` (ค่าเริ่มต้น), `medium` หรือ `low`               |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`        | Alias แบบเดิมสำหรับ `INPUT_SANITIZER_BLOCK_THRESHOLD`                                                    |
| `PII_REDACTION_ENABLED`               | `pii-masker`              | เมื่อเป็น `true` ข้อมูล PII ในคำขอจะถูกปกปิด (ไม่ขึ้นกับโหมด injection)                                  |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (downstream) | ควบคุมลักษณะการทำงานของ masker ฝั่งการตอบกลับ                                                            |

Guardrails ของ Modality Bridge อ่านการกำหนดค่าขณะรันไทม์จาก settings
store ที่มี DB รองรับ (`getSettings()`) ไม่ใช่จาก env vars โดย primary keys ของ Vision คือ
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` และ
`modalityBridgeCacheMaxEntries` ส่วน keys แบบเดิม
`visionBridge*` จะได้รับการยอมรับเฉพาะในฐานะกลไกสำรองสำหรับการอ่านหนึ่งรอบตามที่ระบุไว้
ในเอกสารเท่านั้น การเขียนค่าจาก dashboard จะใช้ primary keys ค่าเริ่มต้นและตัวแก้ไข
fallback อยู่ใน `src/shared/constants/modalityBridgeDefaults.ts` ขณะที่ constants
แบบเดิมยังคงอยู่ใน `src/shared/constants/visionBridgeDefaults.ts`

Audio ใช้ `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` และ `modalityBridgeAudioMaxClips` ร่วมกับ settings
`modalityBridgeCache*` ที่ใช้ร่วมกัน Audio ไม่มีกลไก fallback ไปยัง keys แบบเดิม เนื่องจาก
keys เหล่านี้ถูกนำมาใช้พร้อมกับ schema ของ Modality Bridge

Video ใช้ `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` และ
`modalityBridgeVideoTimeout` ร่วมกับ settings `modalityBridgeCache*` ที่ใช้ร่วมกัน
โดยค่าเริ่มต้นจะปิดใช้งาน เนื่องจาก FFmpeg/ffprobe เป็น operational dependencies
ที่ไม่บังคับ และการสร้างคำบรรยายให้แต่ละ frame จะเพิ่มเวลาแฝงและต้นทุนของโมเดล

## การ์ดเรลแบบกำหนดเอง

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ขั้นตอน:

1. สร้าง `src/lib/guardrails/myGuardrail.ts` โดยสืบทอดจาก `BaseGuardrail`
2. อิมพลีเมนต์ `preCall` และ/หรือ `postCall`
3. ลงทะเบียนขณะนำเข้า (เพิ่มจาก `registerDefaultGuardrails`) หรือ
   เรียก `guardrailRegistry.register(...)` ขณะรันไทม์ — รีจิสทรีจะแทนที่
   การ์ดเรลก่อนหน้าที่มีชื่อหลังการปรับรูปแบบเหมือนกัน
4. เพิ่มการทดสอบภายใต้ `tests/unit/` (ตัวอย่างที่มีอยู่:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)

## การทดสอบ

ใช้ `resetGuardrailsForTests()` ระหว่างการทดสอบแต่ละรายการเพื่อเริ่มต้นจากสถานะที่ทราบแน่ชัด
ส่ง `{ registerDefaults: false }` เพื่อเริ่มต้นด้วยรีจิสทรีว่างและ
ลงทะเบียนเฉพาะการ์ดเรลที่กำลังทดสอบ Vision Bridge รองรับการฉีดการพึ่งพา
(`deps.getSettings`, `deps.callVisionModel`); Audio Bridge มีจุดเชื่อมต่อ
ที่เทียบเท่ากันสำหรับการตั้งค่า ความสามารถ การเลือกโมเดล STT การตรวจสอบข้อมูลรับรอง
และการถอดเสียง ดังนั้นการทดสอบจึงสามารถตรวจสอบโฟลว์ทั้งสองได้โดยไม่ต้องเข้าถึง DB
หรือเครือข่าย

## ความครอบคลุมของเส้นทางและการทดสอบแบบเรดทีมสำหรับการป้องกันการแทรกคำสั่ง (Phase 8 · Block D)

การป้องกันการแทรกคำสั่ง (`createInjectionGuard` / `withInjectionGuard`) ครอบคลุมทุกเส้นทาง
ที่รับพรอมต์จากผู้ใช้ โดยจะเคารพ `INJECTION_GUARD_MODE` (ค่าเริ่มต้น `warn` = บันทึกล็อกเท่านั้น;
`block` = ส่งคืน HTTP 400 `SECURITY_001`)

| ประเภท         | เส้นทาง                                                                                                                                              | โหมดเริ่มต้น |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| ข้อความ (เดิม) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn         |
| เชิงสร้างสรรค์ | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn         |
| ข้อมูล         | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn         |

การแยกข้อความ (`extractMessageContents`) ครอบคลุม `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`

**เรดทีม (ทุกคืน, `nightly-llm-security.yml`):** promptfoo ตรวจสอบว่าแต่ละเส้นทางบล็อก
คลัง OWASP-LLM ใน `INJECTION_GUARD_MODE=block`; garak เรียกใช้โพรบ (ข้ามหากไม่มีข้อมูลลับ)
`moderations` ถูกรวมไว้เพื่อความสอดคล้อง — ผู้ดูแลระบบที่ใช้โหมดบล็อกสามารถยกเว้นเส้นทางนี้ผ่าน
`resolveDisabledGuardrails`

เวิร์กโฟลว์รายคืน (`.github/workflows/nightly-llm-security.yml`, cron + การสั่งงาน
ด้วยตนเอง) มีสองงาน:

- **`promptfoo-guard` (บล็อกเมื่อไม่ผ่าน)** — เรียกใช้ `promptfoo eval -c promptfooconfig.yaml`
  โดยใช้ `INJECTION_GUARD_MODE=block` กรณีโจมตีแต่ละกรณี (เช่น "เพิกเฉยต่อ
  คำสั่งก่อนหน้าทั้งหมด…", การเจลเบรกแบบ DAN) จะยืนยันว่าการตอบกลับมี
  `error.code === "SECURITY_001"` กล่าวคือ การ์ดได้ปฏิเสธคำขอจริง
- **`garak` (ให้คำแนะนำ)** — เรียกใช้ garak `--probes promptinject,dan,leakreplay`
  กับอินสแตนซ์ OmniRoute ภายในเครื่อง (`http://localhost:20128/v1`) โดยขึ้นอยู่กับ
  ข้อมูลลับของผู้ให้บริการ (`PROMPTFOO_PROVIDER_KEY`); จะข้ามอย่างราบรื่นหากไม่มีข้อมูลดังกล่าว และต่อท้ายด้วย
  `|| true` จึงรายงานผลโดยไม่ทำให้ CI ล้มเหลว

ความครอบคลุมของตัวช่วยการ์ด (`createInjectionGuard` / `withInjectionGuard`)
ครอบคลุมทุกเส้นทาง `/v1` ที่มีพรอมต์; ข้อความพรอมต์จะถูกดึงจาก
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` โดย
`extractMessageContents()` ใน `src/shared/utils/inputSanitizer.ts`
