## Vue d’ensemble

Toutes les routes de l’API de gestion d’OmniRoute sont classées dans l’un des trois niveaux de protection. Cette classification est statique, définie dans `src/server/authz/routeGuard.ts`, et évaluée avant l’exécution de toute autre branche d’authentification.

## Niveaux

### Niveau 1 — LOCAL_ONLY

**Appliqué par :** `isLocalOnlyPath(path)` → vérification de l’hôte de bouclage
**Contournement :** aucun par défaut. Exception limitée pour les chemins figurant dans
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` lorsque la requête contient une clé
API valide avec la portée `manage` (voir [Exception liée à la portée manage](#manage-scope-carve-out)).

Ces routes lancent des processus enfants ou exécutent du code à l’exécution. Les exposer au
trafic ne provenant pas de l’interface de bouclage permettrait à un attaquant ayant obtenu un JWT valide (p. ex.,
via un tunnel Cloudflared/Ngrok) de déclencher le lancement de processus — une classe de CVE
connue ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Ce qu’est GHSA-fhh6-4qxv-rpqj (la classe d’attaque) :** un serveur de gestion/d’agent
expose un point de terminaison qui lance un sous-processus (`npm install`, `node`, un navigateur,
un proxy, `git`, `tar`, …). Si ce point de terminaison est accessible depuis l’extérieur de l’hôte — parce que
l’opérateur a placé OmniRoute derrière un tunnel nginx/Cloudflare/Tailscale et qu’un JWT
a fuité, ou que l’authentification a été mal configurée — l’attaquant transforme « appeler une API » en « exécuter une
commande sur l’hôte » (exécution de code à distance). OmniRoute empêche cela en appliquant
**sans condition une vérification de l’hôte de bouclage, avant toute vérification d’authentification**, sur chaque
route capable de lancer des processus : même divulgué, un jeton utilisé via un tunnel ne permet toujours pas d’accéder au mécanisme de lancement.

**L’ensemble complet de LOCAL_ONLY.** La source faisant autorité est
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` dans
`src/server/authz/routeGuard.ts` ; le tableau ci-dessous reflète l’état actuel. Le contrôle
`check-route-guard-membership` énumère chaque fichier `route.ts` sous les
préfixes capables de lancer des processus et fait échouer la CI si l’un d’eux n’est pas classé comme local uniquement.

#### Exception pour la portée de gestion

Un sous-ensemble des chemins LOCAL_ONLY PEUT également être accessible hors de l'interface de bouclage si et
seulement si la requête contient un en-tête `Authorization: Bearer <api-key>` dont les
métadonnées incluent la portée `manage` (ou `admin`). L'exception est activée
explicitement pour chaque chemin via `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, afin que le
comportement par défaut de tout nouveau chemin LOCAL_ONLY reste strictement limité à l'interface de bouclage. Les requêtes
non authentifiées et celles utilisant des clés sans portée de gestion sont toujours rejetées avec
`403 LOCAL_ONLY`.

À ce jour, le seul préfixe pouvant bénéficier de l'exception est `/api/mcp/`. `/api/cli-tools/runtime/` et
`/api/services/` sont intentionnellement exclus, car ils peuvent lancer des
sous-processus arbitraires (`npm install`, `node`), ce qui correspond précisément à la classe de CVE que le
niveau LOCAL_ONLY vise à empêcher.

**#7895 — portée restreinte `mcp:connect` :** l'exception `/api/mcp/` accepte ÉGALEMENT
une clé Bearer possédant la portée restreinte `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), vérifiée via
`hasMcpConnectOrManageScope()` dans `src/server/authz/policies/management.ts`.
Cette portée est limitée à `/api/mcp/` UNIQUEMENT — `mcp:connect` n'accorde aucun droit sur les autres
routes de gestion (y compris tout autre préfixe d'exception LOCAL_ONLY, si un tel préfixe
venait à être ajouté), et elle est délibérément exclue de
`MANAGEMENT_API_KEY_SCOPES`. Une clé possédant `manage`/`admin` bénéficie toujours de
l'exception exactement comme auparavant ; `mcp:connect` constitue une option avec des privilèges inférieurs
pour les appelants distants utilisant uniquement MCP, qui ne devraient pas avoir besoin d'un accès étendu à la gestion.

| Requête                                                         | Chemin                     | Résultat                          |
| --------------------------------------------------------------- | -------------------------- | --------------------------------- |
| Hors interface de bouclage, sans Bearer                         | `/api/mcp/*`               | 403 LOCAL_ONLY                    |
| Hors interface de bouclage, Bearer avec la portée `manage`      | `/api/mcp/*`               | Autorisé                          |
| Hors interface de bouclage, Bearer avec la portée `mcp:connect` | `/api/mcp/*`               | Autorisé                          |
| Hors interface de bouclage, Bearer sans `manage`/`mcp:connect`  | `/api/mcp/*`               | 403 LOCAL_ONLY                    |
| Hors interface de bouclage, Bearer avec la portée `mcp:connect` | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                    |
| Hors interface de bouclage, Bearer avec la portée `manage`      | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                    |
| Interface de bouclage, avec ou sans Bearer                      | tout chemin LOCAL_ONLY     | Autorisé (le contrôle est validé) |

#### Recommandations pour les opérateurs et audit

Si vous exécutez OmniRoute derrière un proxy inverse ou un tunnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), la vérification de l'interface de bouclage protège toujours les routes
ci-dessus capables de lancer des processus — une requête dont l'adresse client n'appartient pas à l'interface de bouclage est rejetée avec
`403 LOCAL_ONLY` **avant l'exécution de l'authentification** ; ainsi, un JWT divulgué ne peut pas déclencher de lancement. Deux
responsabilités incombent encore aux opérateurs :

- **Ne « corrigez » pas une erreur 403 en falsifiant l’adresse IP du client pour la faire passer pour l’adresse de bouclage.** Définir
  `X-Forwarded-For: 127.0.0.1`, ou utiliser un proxy qui réécrit l’adresse source en
  adresse de bouclage, rouvre précisément la classe de vulnérabilités RCE que ce niveau bloque. Exposez le
  tableau de bord/l’API par l’intermédiaire du proxy — jamais les routes capables de lancer des processus.
- **Limitez au strict minimum le contournement lié à la portée manage.** Seul `/api/mcp/` peut être contourné, et
  uniquement avec une clé API dotée de la portée `manage`. Les `SPAWN_CAPABLE_PREFIXES` ne peuvent jamais être
  ajoutés à la liste de contournement — le schéma zod les rejette et
  `isLocalOnlyBypassableByManageScope` les refuse lors de l’exécution (défense en profondeur),
  ce que le tableau de bord désigne par « impossible à rendre contournable ». Le chargeur
  d’instantanés d’exécution supprime également ces entrées d’une ligne de paramètres stockée, et
  l’importation JSON héritée (`/api/settings/import-json`) n’écrit jamais les clés de contournement.
  Chaque entrée de `LOCAL_ONLY_API_PREFIXES` doit soit figurer dans la liste de refus, soit
  être examinée pour déterminer si elle peut bénéficier d’un contournement (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Les routes capables
  de lancer des processus comportant des segments dynamiques ou des chemins statiques sous `/api/providers/` (par ex. `/login`,
  `/refresh-cursor`) sont couvertes par les éléments complémentaires basés sur des expressions régulières `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` dans
  `src/shared/constants/spawnCapablePrefixes.ts`, et non par le tableau plat
  `SPAWN_CAPABLE_PREFIXES` — ce tableau devrait couvrir l’intégralité du
  préfixe `/api/providers/` pour les détecter, ce qui élargirait excessivement l’arborescence de routes
  que les tableaux de bord distants utilisent légitimement pour les opérations CRUD sur les fournisseurs.

**Audit des accès** — pour vérifier qu’aucune entité externe à l’hôte n’atteint ces routes :

- Ouvrez l’**inventaire des autorisations** sur `/dashboard/settings/security` : il affiche la
  liste active des préfixes LOCAL_ONLY, les préfixes qui peuvent être contournés et l’ensemble
  des éléments capables de lancer des processus défini à la compilation (« impossible à rendre contournable »).
- Recherchez dans les journaux de votre proxy inverse / d’accès les préfixes ci-dessus associés à une
  adresse cliente qui n’est pas une adresse de bouclage. Toute requête de ce type ayant renvoyé `200` au lieu de
  `403 LOCAL_ONLY` signifie que le proxy masque l’adresse IP réelle du client — corrigez le proxy.
- Une réponse `403 LOCAL_ONLY` dans les journaux d’OmniRoute pour l’un de ces chemins indique que la protection
  fonctionne comme prévu, et non une erreur à supprimer.

### Niveau 2 — ALWAYS_PROTECTED

**Appliqué par :** `isAlwaysProtectedPath(path)` → ignore le contournement `requireLogin=false`
**Contournement :** aucun lorsque `requireLogin=false` ; JWT toujours requis

Ces routes sont destructrices ou irréversibles. Les autoriser dans une installation « sans mot de passe »
signifierait que n’importe qui sur le même réseau local pourrait effacer la base de données ou arrêter le
processus serveur.

| Chemin                                    | Motif                                                                               |
| ----------------------------------------- | ----------------------------------------------------------------------------------- |
| `/api/shutdown`                           | Arrête le processus serveur                                                         |
| `/api/settings/database`                  | Exportation, importation et effacement de la base de données                        |
| `/api/db-backups`                         | Accès à l’archive complète de sauvegarde de la base de données                      |
| `/api/settings/export-json`               | Exporte l’intégralité du bloc de paramètres (secrets inclus)                        |
| `/api/settings/import-json`               | Remplace l’intégralité du bloc de paramètres                                        |
| `/api/providers/health-autopilot/actions` | Exécute les actions correctives de l’autopilote                                     |
| `/api/settings/obsidian`                  | Génère des identifiants WebDAV réutilisables pour n’importe quelle racine de coffre |

**Réponse en cas de violation :** `401 Authentication required`

`/api/settings/obsidian` couvre son enfant `/webdav` : `POST` fait pointer le service de fichiers WebDAV —
servi par la couche Node personnalisée avant Next.js, en dehors de ce pipeline — vers une racine choisie par
l’appelant et renvoie en écho des identifiants Basic nouvellement générés, `DELETE` les renouvelle, et le `POST`
du parent stocke le jeton de l’API REST d’Obsidian. GHSA-62vw ne faisait que masquer la révélation du mot de passe
par `GET` ; l’émission se trouvait toujours dans le niveau ouvert en cas de défaillance (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()`
refuse en outre un coffre qui correspond au répertoire de données, se trouve à l’intérieur de celui-ci ou le contient.

### L’amorçage d’une nouvelle installation est réservé à l’adresse de bouclage — selon le pair réel, et non `Host`

Lorsqu’aucun mot de passe de gestion n’est configuré (et en l’absence de `INITIAL_PASSWORD`), `isAuthRequired()` dans
`src/shared/utils/apiAuth.ts` maintient l’amorçage anonyme ouvert **uniquement aux pairs de bouclage**.
Le bouclage est déterminé à partir des signaux de pair fiables, dans l’ordre suivant : le pair TCP réel marqué par jeton
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, ce que voit la politique), le verdict
`AUTHZ_HEADER_PEER_LOCALITY` propre au pipeline (ce que voient les gestionnaires de routes, considéré comme fiable uniquement lorsque
`OMNIROUTE_PEER_STAMP_TOKEN` est défini), ou le véritable pair de socket pour les appelants directs. `Host` /
`nextUrl.hostname` ne sont jamais consultés, et la définition du premier mot de passe
(`POST /api/settings/require-login`) est soumise à la même contrainte au lieu d’être ouverte à tous les
pairs du réseau (GHSA-7pq4-8pvv-rx7r). `managementPolicy` transmet explicitement son propre verdict
`peerContext`, de sorte que les en-têtes de la requête ORIGINALE (avant suppression) ne le déterminent jamais.

### Niveau 3 — MANAGEMENT (par défaut)

Toutes les autres routes de gestion. L’authentification est requise sauf si `requireLogin=false` est
configuré. Les jetons CLI peuvent authentifier ces routes (bouclage + HMAC valide).

## Ordre d’évaluation

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → poursuivre
     → hors loopback, Bearer avec portée manage
        ET isLocalOnlyBypassableByManageScope    → autoriser (management_key)
     → sinon                                     → rejeter avec 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → autoriser (system)
  3. hasValidCliToken(headers)?
     → autoriser (cli) [loopback + vérification HMAC avec timingSafeEqual]
  4. isAlwaysProtectedPath(path) ou requireLogin=true?
     → isDashboardSessionAuthenticated?
        → autoriser (dashboard_session)
     → Bearer avec portée manage sur un chemin non contournable ?
        → autoriser (management_key)
     → rejeter avec 401/403
  5. requireLogin=false?
     → autoriser (anonymous)
```

La branche avec portée manage de l’étape 1 est le seul chemin authentifié pouvant satisfaire une route
LOCAL_ONLY ; le mode d’échec du backend d’authentification renvoie 503 (et non 403), afin qu’une
base de données expirée ne soit pas silencieusement rétrogradée en « refus ».

## Ajout d’une nouvelle route capable de lancer des processus

1. Ajoutez le préfixe du chemin à `LOCAL_ONLY_API_PREFIXES` dans
   `src/server/authz/routeGuard.ts`
2. Ajoutez un test dans `tests/unit/authz/routeGuard.test.ts` vérifiant que
   `isLocalOnlyPath()` renvoie true pour le nouveau préfixe
3. **Ne sautez jamais cette étape** — consultez la règle absolue nº 15 dans `CLAUDE.md`
4. Décidez : cette route doit-elle ÉGALEMENT figurer dans `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ?
   La réponse par défaut est **non**. N’y consentez que lorsque la route peut être exposée en toute sécurité à un
   détenteur de la portée manage (c.-à-d. qu’elle ne lance PAS de code arbitraire contrôlé par l’utilisateur).

## Ajout d’un chemin contournable avec la portée manage

1. Vérifiez que la route n’exécute pas de code ou de commandes fournis par l’utilisateur. Si c’est
   le cas, arrêtez-vous — cette exception n’est pas l’outil approprié.
2. Ajoutez le préfixe à `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` dans
   `src/server/authz/routeGuard.ts`
3. Ajoutez une couverture dans `tests/unit/authz/management-policy.test.ts` pour les quatre
   formes de requêtes : sans Bearer (403), Bearer avec portée manage (autorisation), Bearer sans portée manage
   (403), ainsi que la régression par préfixe vérifiant que `/api/cli-tools/runtime/*` reste
   strictement limité au loopback, même avec un Bearer doté de la portée manage.

## Documentation des niveaux de sécurité dans OpenAPI

Lors de l’ajout d’une nouvelle route à `docs/openapi.yaml`, appliquez l’extension
fournisseur correspondante si la route est classifiée par `routeGuard.ts` :

| Classification de routeGuard.ts               | Annotation YAML                | Application                                             |
| --------------------------------------------- | ------------------------------ | ------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                     | `x-loopback-only: true`        | Blocage inconditionnel hors loopback                    |
| `ALWAYS_PROTECTED_API_PATHS`                  | `x-always-protected: true`     | Authentification requise même avec `requireLogin=false` |
| Route interne d’administration/débogage       | `x-internal: true`             | Masquée de /dashboard/api-endpoints par défaut          |
| Aucune (publique / authentification standard) | (aucune annotation nécessaire) | Accès standard contrôlé par `requireLogin`              |

### Validation

Deux scripts garantissent la cohérence entre les annotations YAML et `routeGuard.ts` :

- `scripts/check/check-openapi-coverage.mjs` — échoue si la couverture est < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — échoue si les annotations `x-loopback-only` ou
  `x-always-protected` divergent des constantes définies à la compilation

Les deux scripts s’exécutent dans le hook de précommit et dans la CI.

### Règle relative aux faux positifs

Si `x-always-protected` ou `x-loopback-only` est annoté sur une route qui ne figure PAS dans
la constante de `routeGuard.ts`, le script de couverture échoue. La correction consiste toujours à aligner le
YAML sur ce que `routeGuard.ts` applique réellement — et non à ajouter des routes à `routeGuard.ts`
sans également implémenter la logique d’application.
