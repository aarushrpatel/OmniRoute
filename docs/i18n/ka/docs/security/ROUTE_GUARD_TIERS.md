## მიმოხილვა

OmniRoute-ის მართვის API-ის ყველა მარშრუტი დაცვის სამი დონიდან ერთ-ერთს
მიეკუთვნება. კლასიფიკაცია სტატიკურია, განსაზღვრულია `src/server/authz/routeGuard.ts`-ში
და მოწმდება ავტორიზაციის ნებისმიერი სხვა განშტოების შესრულებამდე.

## დონეები

### დონე 1 — LOCAL_ONLY

**უზრუნველყოფილია:** `isLocalOnlyPath(path)` → loopback ჰოსტის შემოწმება  
**გვერდის ავლა:** ნაგულისხმევად შეუძლებელია. ვიწრო გამონაკლისი მოქმედებს `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ში შემავალი ბილიკებისთვის, როდესაც მოთხოვნა შეიცავს მოქმედ API გასაღებს `manage` წვდომის არეალით (იხ. [გამონაკლისი manage წვდომის არეალისთვის](#manage-scope-carve-out)).

ეს მარშრუტები შვილობილ პროცესებს უშვებს ან შესრულების გარემოს კოდს ასრულებს. მათი loopback-ის მიღმა არსებული ტრაფიკისთვის გახსნა საშუალებას მისცემდა თავდამსხმელს, რომელმაც მოქმედი JWT მოიპოვა (მაგ., Cloudflared/Ngrok გვირაბის მეშვეობით), პროცესების გაშვება გამოეწვია — ეს CVE-ის ცნობილი კლასია ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**რა არის GHSA-fhh6-4qxv-rpqj (შეტევის კლასი):** მართვის/აგენტის სერვერი ხელმისაწვდომს ხდის საბოლოო წერტილს, რომელიც ქვეპროცესს უშვებს (`npm install`, `node`, ბრაუზერს, პროქსის, `git`, `tar`, …). თუ ეს საბოლოო წერტილი ჰოსტის გარედან ხელმისაწვდომია — რადგან ოპერატორმა OmniRoute nginx/Cloudflare/Tailscale გვირაბის უკან განათავსა და JWT-მა გაჟონა, ან ავთენტიფიკაცია არასწორად იყო კონფიგურირებული — თავდამსხმელი „API-ის გამოძახებას“ „ჰოსტზე ბრძანების გაშვებად“ აქცევს (კოდის დისტანციური შესრულება). OmniRoute ამას ყველა იმ მარშრუტზე, რომელსაც პროცესის გაშვება შეუძლია, **ნებისმიერი ავთენტიფიკაციის შემოწმებამდე loopback ჰოსტის შემოწმების უპირობოდ აღსრულებით** აღკვეთს: გვირაბის მეშვეობით გაჟონილი ტოკენიც კი ვერ შეძლებს პროცესის გაშვების მექანიზმამდე მიღწევას.

**LOCAL_ONLY-ის სრული ნაკრები.** ავტორიტეტული წყაროა `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ფაილში `src/server/authz/routeGuard.ts`; ქვემოთ მოცემული ცხრილი მიმდინარე მდგომარეობას ასახავს. `check-route-guard-membership`-ის შემოწმება პროცესის გაშვების უნარის მქონე პრეფიქსების ქვეშ არსებულ ყველა `route.ts`-ს ჩამოთვლის და CI-ს წარუმატებლად ასრულებს, თუ რომელიმე მათგანი მხოლოდ ლოკალურად ხელმისაწვდომად არ არის კლასიფიცირებული.

#### გამონაკლისი მართვის უფლებამოსილებისთვის

მეტამონაცემებიც მოიცავს `manage` უფლებამოსილებას (ან `admin`-ს). გამონაკლისი
თითოეული გზისთვის ცალსახად კონტროლდება `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ის

მკაცრი ლუპბექ-წვდომა. არაავტორიზებული მოთხოვნები და მოთხოვნები, რომლებიც შეიცავს

#### ოპერატორის მითითებები და აუდიტი

თუ OmniRoute-ს უკუპროქსის ან გვირაბის (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) მიღმა უშვებთ, ლუპბექის შემოწმება მაინც იცავს ზემოთ
ჩამოთვლილ, პროცესების გაშვების შესაძლებლობის მქონე მარშრუტებს — მოთხოვნა,
რომლის კლიენტის მისამართიც არალუპბექია, უარყოფილია პასუხით `403 LOCAL_ONLY`
**ავტორიზაციის შესრულებამდე**, ამიტომ გაჟონილი JWT პროცესის გაშვებამდე ვერ
მიაღწევს. ოპერატორს კვლავ რჩება ორი პასუხისმგებლობა:

- **ნუ ეცდებით 403-ის „გამოსწორებას“ კლიენტის IP-ის loopback-ად გაყალბებით.** `X-Forwarded-For: 127.0.0.1`-ის მითითება ან ისეთი proxy-ის გამოყენება, რომელიც წყაროს მისამართს loopback-ად გადაწერს, ხელახლა ხსნის ზუსტად იმ RCE კლასს, რომელსაც ეს დონე კეტავს. proxy-ის მეშვეობით ხელმისაწვდომი გახადეთ dashboard/API — არასოდეს გახადოთ ხელმისაწვდომი პროცესების გაშვების შესაძლებლობის მქონე მარშრუტები.
- **`manage` scope-ის გვერდის ავლა მინიმუმამდე დაიყვანეთ.** გვერდის ავლა შესაძლებელია მხოლოდ `/api/mcp/`-ისთვის და მხოლოდ `manage` scope-ის მქონე API გასაღებით. `SPAWN_CAPABLE_PREFIXES` ვერასოდეს დაემატება გვერდის ავლის სიას — zod სქემა მათ უარყოფს, ხოლო `isLocalOnlyBypassableByManageScope` შესრულების დროს მათ კრძალავს (მრავალშრიანი დაცვა), რასაც dashboard-ზე ეწოდება „გვერდის ავლის შესაძლებლობა ვერ მიენიჭება“. შესრულების დროის snapshot loader-იც გამოტოვებს ასეთ ჩანაწერებს შენახული პარამეტრების სტრიქონიდან, ხოლო მოძველებული JSON-ის იმპორტი (`/api/settings/import-json`) გვერდის ავლის გასაღებებს არასოდეს წერს. `LOCAL_ONLY_API_PREFIXES`-ის თითოეული ჩანაწერი ან უარყოფის სიაში უნდა იყოს, ან განხილული უნდა იყოს, როგორც გვერდის ავლისთვის დაშვებული (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). `/api/providers/`-ის ქვეშ არსებული, დინამიკური სეგმენტებისა და სტატიკური ბილიკების მქონე პროცესის გაშვების შესაძლებლობის მქონე მარშრუტები (მაგალითად, `/login`, `/refresh-cursor`) დაფარულია regex-ზე დაფუძნებული `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` კომპანიონით `src/shared/constants/spawnCapablePrefixes.ts`-ში და არა ბრტყელი `SPAWN_CAPABLE_PREFIXES` მასივით — მათ დასაფიქსირებლად ბრტყელ მასივს მთელი `/api/providers/` პრეფიქსის დაფარვა მოუწევდა, რაც ზედმეტად გააფართოებდა მარშრუტების ხეს, რომელსაც დისტანციური dashboard-ები provider-ების CRUD ოპერაციებისთვის კანონიერად იყენებენ.

**წვდომის აუდიტი** — იმის დასადასტურებლად, რომ ამ მარშრუტებს ჰოსტის გარედან არაფერი უკავშირდება:

- გახსენით **ავტორიზაციის ინვენტარი** მისამართზე `/dashboard/settings/security`: ის აჩვენებს მიმდინარე LOCAL_ONLY პრეფიქსების სიას, იმ პრეფიქსებს, რომელთათვისაც გვერდის ავლა დასაშვებია, და კომპილაციის დროს განსაზღვრულ, პროცესის გაშვების შესაძლებლობის მქონე („გვერდის ავლის შესაძლებლობა ვერ მიენიჭება“) ნაკრებს.
- reverse-proxy-ის / წვდომის ჟურნალებში მოძებნეთ ზემოთ ჩამოთვლილი პრეფიქსები, რომლებიც დაწყვილებულია არა-loopback კლიენტის მისამართთან. ნებისმიერი ასეთი მოთხოვნა, რომელმაც `403 LOCAL_ONLY`-ის ნაცვლად `200` დააბრუნა, ნიშნავს, რომ proxy რეალური კლიენტის IP-ს ნიღბავს — გაასწორეთ proxy.
- OmniRoute-ის ჟურნალებში ამ ბილიკებიდან ერთ-ერთისთვის დაფიქსირებული `403 LOCAL_ONLY` ნიშნავს, რომ დამცავი მექანიზმი დანიშნულებისამებრ მუშაობს და არა იმას, რომ ეს შეცდომა უნდა ჩაახშოთ.

GHSA-62vw მხოლოდ `GET`-ის მიერ პაროლის გამჟღავნებას ნიღბავდა; მონაცემების გაცემა კვლავ fail-open დონეზე რჩებოდა (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` დამატებით უარყოფს vault-ს, რომელიც მონაცემთა დირექტორიაა, მის შიგნით მდებარეობს ან მას შეიცავს.

### ახალი ინსტალაციის საწყისი კონფიგურაცია მხოლოდ loopback-იდან არის ხელმისაწვდომი — რეალური peer-ის მიხედვით და არა `Host`-ის

როდესაც მართვის პაროლი არ არის კონფიგურირებული (და არც `INITIAL_PASSWORD` არსებობს), `src/shared/utils/apiAuth.ts`-ში არსებული `isAuthRequired()` ანონიმურ საწყის კონფიგურაციას ღიას ტოვებს **მხოლოდ loopback peer-ებისთვის**. loopback განისაზღვრება სანდო peer სიგნალებიდან, შემდეგი თანმიმდევრობით: ტოკენით მონიშნული რეალური TCP peer (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, რასაც policy ხედავს), თავად pipeline-ის `AUTHZ_HEADER_PEER_LOCALITY` ვერდიქტი (რასაც მარშრუტის დამმუშავებლები ხედავენ და რომელიც სანდოა მხოლოდ მანამ, სანამ `OMNIROUTE_PEER_STAMP_TOKEN` დაყენებულია), ან პირდაპირი გამომძახებლებისთვის რეალური socket peer. `Host` / `nextUrl.hostname` არასოდეს მოწმდება, ხოლო პირველი პაროლის ჩაწერა (`POST /api/settings/require-login`) იმავე შეზღუდვას ექვემდებარება და არ არის ღია ქსელის ყველა peer-ისთვის (GHSA-7pq4-8pvv-rx7r). `managementPolicy` საკუთარ `peerContext` ვერდიქტს ქვემოთ პირდაპირ გადასცემს, ამიტომ ამას ORIGINAL (გასუფთავებამდე არსებული) მოთხოვნის header-ები არასოდეს განსაზღვრავს.

### დონე 3 — MANAGEMENT (ნაგულისხმევი)

მართვის ყველა სხვა მარშრუტი. ავტორიზაცია სავალდებულოა, თუ `requireLogin=false` არ არის კონფიგურირებული. CLI ტოკენებს ამ მარშრუტებზე ავტორიზაცია შეუძლიათ (loopback + მოქმედი HMAC).

## შეფასების თანმიმდევრობა

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → შემდეგ ეტაპზე გადასვლა
     → non-loopback, manage-სკოპის Bearer
        AND isLocalOnlyBypassableByManageScope   → დაშვება (management_key)
     → სხვა შემთხვევაში                           → უარყოფა 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → დაშვება (system)
  3. hasValidCliToken(headers)?
     → დაშვება (cli) [loopback + timingSafeEqual HMAC შემოწმება]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → დაშვება (dashboard_session)
     → manage-სკოპის Bearer არაგვერდასავლელ მარშრუტზე?
        → დაშვება (management_key)
     → უარყოფა 401/403
  5. requireLogin=false?
     → დაშვება (anonymous)
```

1-ლი ნაბიჯის manage-სკოპის განშტოება ერთადერთი ავთენტიფიცირებული გზაა, რომელსაც
LOCAL_ONLY მარშრუტის დაკმაყოფილება შეუძლია; ავთენტიფიკაციის ბექენდის გაუმართაობის
რეჟიმი აბრუნებს 503-ს (და არა 403-ს), რათა ვადაგასული DB შეუმჩნევლად არ
გადავიდეს „უარყოფის“ რეჟიმზე.

## ახალი პროცესის გაშვების უნარის მქონე მარშრუტის დამატება

1. დაამატეთ გზის პრეფიქსი `LOCAL_ONLY_API_PREFIXES`-ში,
   `src/server/authz/routeGuard.ts` ფაილში
2. დაამატეთ ტესტი `tests/unit/authz/routeGuard.test.ts`-ში, რომელიც ადასტურებს,
   რომ ახალი პრეფიქსისთვის `isLocalOnlyPath()` აბრუნებს true-ს
3. **არასოდეს გამოტოვოთ ეს ნაბიჯი** — იხილეთ მკაცრი წესი #15 `CLAUDE.md`-ში
4. გადაწყვიტეთ: უნდა შედიოდეს თუ არა ეს მარშრუტი ასევე
   `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ში?
   ნაგულისხმევი პასუხია **არა**. ჩართეთ მხოლოდ მაშინ, როდესაც მარშრუტის
   manage-სკოპის მფლობელისთვის გახსნა უსაფრთხოა (ანუ ის არ უშვებს მომხმარებლის
   მიერ სრულად კონტროლირებად ნებისმიერ კოდს).

### ვალიდაცია

ორი სკრიპტი უზრუნველყოფს YAML ანოტაციებსა და `routeGuard.ts`-ს შორის
თანმიმდევრულობას:

- `scripts/check/check-openapi-coverage.mjs` — მარცხდება, თუ დაფარვა < 99%

  ან `x-always-protected` ანოტაციები კომპილაციის დროის კონსტანტებს არ ემთხვევა

### ცრუ დადებითი შედეგის წესი

თუ `x-always-protected` ან `x-loopback-only` ანოტაცია მითითებულია მარშრუტზე,
რომელიც `routeGuard.ts`-ის კონსტანტაში არ შედის, დაფარვის სკრიპტი მარცხდება.
გამოსავალი ყოველთვის არის YAML-ის შესაბამისობაში მოყვანა იმასთან, რასაც
`routeGuard.ts` რეალურად აღასრულებს — და არა მარშრუტების `routeGuard.ts`-ში
დამატება აღსრულების ლოგიკის იმავდროულად განხორციელების გარეშე.
