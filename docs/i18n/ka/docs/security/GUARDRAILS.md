> **ბოლოს განახლდა:** 2026-08-29 — v3.8.51 (ვიდეო ხიდის ტრანსკრიპტის წარმომავლობა დეკლარირებულია გამომძახებლის მიერ, ჯერ არ არის სერვერის მიერ დამოწმებული — განმარტებულია #11661-ის მიხედვით)

Guardrails უზრუნველყოფენ უსაფრთხოებას, პოლიტიკას და კონტენტის ტრანსფორმაციებს OmniRoute-სა და upstream პროვაიდერებს შორის საზღვარზე. თითოეულ guardrail-ს შეუძლია შეამოწმოს (და სურვილისამებრ უარყოს, გარდაქმნას ან ანოტირება გაუკეთოს) მოთხოვნის payload-ები (`preCall`) და upstream პასუხები (`postCall`).

სისტემა არის **fail-open**: თუ guardrail-ის შესრულებისას შეცდომა მოხდა, რეგისტრატორი აღრიცხავს შეცდომას და აგრძელებს შემდეგ guardrail-ზე, ნაცვლად მოთხოვნის შეწყვეტისა. დაბლოკვა არის მკაფიო გადაწყვეტილება (`block: true`), არასდროს შემთხვევითობა.

### ვიზუალური ხიდი (`visionBridge.ts`) — მოდალობის ხიდი PR-1

იჭერს გამოსახულებების შემცველ მოთხოვნებს, რომლებიც მიმართულია **ვიზუალური შესაძლებლობების არმქონე მოდელებისკენ**, და ან
მთელ მოთხოვნას გადაამისამართებს ვიზუალური შესაძლებლობების მქონე მოდელზე, ან upstream
გამოძახებამდე გამოსახულების ნაწილებს ჩაანაცვლებს კონფიგურირებადი ვიზუალური მოდელის მიერ
შექმნილი ტექსტური აღწერებით. ეს მხოლოდ ტექსტზე მომუშავე პროვაიდერებს მულტიმოდალური
payload-ების გამჭვირვალედ დამუშავების საშუალებას აძლევს.

ნაკადი:

1. გამოტოვება, თუ სამიზნე მოდელს უკვე აქვს ვიზუალური მხარდაჭერა (გარდა იმ შემთხვევისა, როდესაც ის
   იძულებითი ხიდის სიაში `isVisionBridgeForcedModel` გვხვდება).
2. გამოსახულების ნაწილების ამოღება `extractImageParts(messages)`-ის მეშვეობით
   (`visionBridgeHelpers.ts`), რომელიც დელეგირებას ახდენს **მედიის ერთიან
   დეტექტორზე** `detectMediaParts()` ფაილში `open-sse/utils/mediaParts.ts` — ეს არის
   სიმართლის ერთადერთი წყარო, რომელიც combo თავსებადობის ფილტრთან საზიაროა.
   ამოღება ნებადართულია მხოლოდ ზედა დონის იმ ფორმის ნაწილებისთვის,
   რომელთა უკან ჩასმაც `replaceImageParts`-ს შეუძლია (ამოღება↔ჩანაცვლების კონტრაქტი): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` და Responses API `input_image`. ჩადგმული დამთხვევები და
   მხოლოდ ინდიკატორის შემცველი ფორმები combo ფილტრისთვისაა განკუთვნილი და არასდროს ამოიღება.
   გამოტოვება, თუ არცერთი არ მოიძებნა.
3. შესრულების დროის კონფიგურაციის განსაზღვრა `resolveVisionBridgeRuntimeSettings()`-ის მეშვეობით
   (`src/shared/constants/modalityBridgeDefaults.ts`): ახალ `modalityBridge*`
   პარამეტრების გასაღებებს უპირატესობა ენიჭება; ძველი `visionBridge*` გასაღებები რჩება **ერთი ციკლის
   სარეზერვო ვარიანტად** (უკან დაბრუნების ფანჯარა). თუ ხიდი გამორთულია, გამოტოვება ხდება
   მედიის ნებისმიერ შემოვლამდე.
4. რეჟიმის ამომრჩეველი (`modalityBridgeVisionMode`, იხილეთ ქვემოთ მოცემული ცხრილი) წყვეტს,
   მოხდეს გადამისამართება თუ აღწერა. გადამისამართება აბრუნებს `modifiedPayload`-ს, რომელშიც მხოლოდ `model`
   არის ჩანაცვლებული, ასევე meta-ს `{ rerouted, fromModel, toModel, imagesKept }`.
5. აღწერის გზა: გამოსახულებების რაოდენობის შეზღუდვა `maxImages`-ით, ამოცანის შესაბამისი prompt-ის შედგენა,
   აღწერის cache-ის შემოწმება, ვიზუალური მოდელის **პარალელურად**
   გამოძახება (`Promise.allSettled`) და მათ ადგილას `[Image N]: <description>` ტექსტური ნაწილების
   ჩასმა. წარუმატებელი აღწერა აბრუნებს `null`-ს და გამოსახულების თავდაპირველი ნაწილი
   **შენარჩუნდება** (#4012) — გარდა combo აღწერის გზისა, როცა ყველა
   აღწერა წარუმატებელია; ამ შემთხვევაში დადასტურებული არავიზუალური upstream იღებს
   `(მიუწვდომელია — ვიზუალური შესაძლებლობების მქონე პროვაიდერი დაკავშირებული არ არის)` ჩანაცვლებით ტექსტს (#8430).
6. `modifiedPayload`-ისა და meta-ს დაბრუნება (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### API გასაღების ფარგლები (`visionBridgeKeyScope.ts`)

როდესაც გამომძახებლის API გასაღები ზღუდავს `allowedConnections`-ს, კვოტის პულებს
(`allowedQuotas`) ან მოდელებს (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), ხიდი გადამისამართებისა და
აღწერისთვის მხოლოდ იმ მოდელებს ირჩევს, რომელთა გამოყენებაც გასაღებს შეუძლია, და მხოლოდ იმ კავშირებზე,
რომელთა გამოყენებაც ამ გასაღებისთვის ნებადართულია. შემდეგ აღწერის გამოძახება ყოველთვის OmniRoute-ის თვითმარყუჟის გავლით
ხდება, `x-omniroute-self-loop-key-id` სათაურით, რათა მიმღებმა chat მოთხოვნამ
ხელახლა აღასრულოს ამ გასაღების კავშირებისა და მოდელების პოლიტიკა. `enforceApiKeyPolicy()`
ამ სათაურს მხოლოდ თვითმარყუჟის bearer-თან ერთად ითვალისწინებს, ამიტომ მას მხოლოდ
წვდომის შევიწროება შეუძლია, ხოლო id, რომელიც ვერ მოიძებნება, უარყოფილია.

თუ გასაღებისთვის არცერთი ვიზუალური მოდელი არ არის ნებადართული, აღწერის გზა გვერდზე გადგება და
მოთხოვნა უცვლელად გადის — იგივე fail-open ქცევით, როგორც გამორთული
დამცავი მექანიზმის შემთხვევაში (meta `{ skipped: true, reason: "no_permitted_vision_model" }`).
გასაღების გარეშე გაგზავნილი მოთხოვნები და გასაღებები, რომლებსაც ეს შეზღუდვები არ აქვს, ზუსტად ისე
იქცევა, როგორც ადრე.

#### ამოცანის შესაბამისი აღწერის prompt (`modalityBridgeVisionTaskAware`)

ნაგულისხმევად **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) საბაზისო აღწერის მოთხოვნას ამატებს **მომხმარებლის ბოლო შეტყობინების** ტექსტს (შემოკლებულს 500 სიმბოლომდე), რათა აღწერა მიმართოს იმისკენ, რაც მომხმარებელმა რეალურად მოითხოვა (codex-vision-proxy-ის ნიმუში), და ხედვის მოდელს სთხოვს ხილული ტექსტის ტრანსკრიფციას. თუ ალამი გამორთულია — ან მომხმარებლის ტექსტი არ არსებობს — საბაზისო მოთხოვნა უცვლელად გამოიყენება.

აღწერის თვითციკლის საკუთარი OpenAI-თან თავსებადი მოთხოვნა (`callVisionModelSingle()`
ფაილში `visionBridgeHelpers.ts`) ყოველთვის ითხოვს `image_url.detail: "high"` —
უპირობოდ, ყოველი გამომძახებლისთვის/პროვაიდერისთვის, კლიენტის რომელიმე სიგნალზე დამოკიდებულების გარეშე.
დაბალი დეტალიზაციის სემპლინგი OCR-ის სიზუსტეს აუარესებს ზუსტად იმ ტექსტის ტრანსკრიფციის
ამოცანისთვის, რომელსაც ეს მოთხოვნა ითხოვს, ამიტომ თავად აღწერის გამოძახება ყოველთვის ითხოვს მაღალ
დეტალიზაციას, იმის მიუხედავად, დეტალიზაციის რა დონე გამოიყენა თავდაპირველმა შემომავალმა მოთხოვნამ. ეს
მხოლოდ აღწერის შიდა მოთხოვნის სხეულზე მოქმედებს; ის არ ცვლის იმას, თუ როგორ გადააგზავნის
OmniRoute გამომძახებლის საკუთარ `image_url.detail`-ს ძირითად მოთხოვნაში —
ეს ნაგულისხმევი მნიშვნელობა ცალკე გამოიყენება და მხოლოდ აღმოჩენილი OpenCode კლიენტებისთვის,
`defaultImageDetail()`-ში (`open-sse/handlers/chatCore/upstreamBody.ts`). აღწერის
თვითციკლის Anthropic wire-format განშტოებას `detail` ველი არ აქვს და მასზე არცერთი ნაგულისხმევი
მნიშვნელობა არ მოქმედებს.

#### აღწერის გამოტანის ზღვარი (`modalityBridgeVisionMaxChars`)

| გასაღები                       | ნაგულისხმევი | დიაპაზონი        |
| ------------------------------ | ------------ | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`          | `0` ან 100–50000 |

`0` (ნაგულისხმევი) ნიშნავს **ზღვრის გარეშე** — `callVisionModel()`-ის მიერ დაბრუნებული
აღწერა უცვლელად გადაიცემა, რაც არსებულ ქცევას ინარჩუნებს. 100–50000 დიაპაზონში ნებისმიერი
მნიშვნელობა აღწერას ამოკლებს `…` სუფიქსით, სანამ ის ხელახლა ჩაისმება ფორმატით
`[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` ფაილში `src/lib/guardrails/visionBridge.ts`).
გაზარდეთ ეს მნიშვნელობა დეტალებით დატვირთული OCR ამოცანებისთვის, სადაც ქვემდგომ მოდელს
სრული ტრანსკრიფცია სჭირდება; შეამცირეთ იგი სიტყვაუხვი ხედვის მოდელების ტოკენების გამოყენების
შესაზღუდად. დაფის ველი მდებარეობს Vision ჩანართის Advanced პანელზე
(`modality-bridge-max-chars` ფაილში `ModalityBridgeVisionTab.tsx`) და 1-დან 99-მდე
ნებისმიერ მნიშვნელობას მინიმალურ 100-მდე ზრდის, ხოლო აშკარად მითითებულ `0`-ს ხელუხლებლად
ტოვებს — `0` თავისთავად მართებული Zod მნიშვნელობაა
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`) და არა უბრალოდ
„დაყენებული არ არის“ ნაგულისხმევი მნიშვნელობა.

#### აღწერის კეში (`modalityBridge/bridgeCache.ts`)

მეხსიერებაში არსებული LRU + TTL კეში აღწერის შედეგებისთვის, რომელიც საერთო პროცესის მასშტაბით
გამოიყენება. გასაღები = `sha256(imageRef + composedPrompt + configuredBridgeModel)`,
სიგრძის პრეფიქსიანი ჩარჩოებით (ველების საზღვრების კოლიზიების გარეშე). მოდელის კომპონენტი არის
**კონფიგურირებული** ხიდის მოდელი და არა მოდელი, რომელმაც რეალურად უპასუხა —
`callVisionModel`-მა შეიძლება შიდა fallback გამოიყენოს, ხოლო თითოეული მცდელობის მიხედვით
გასაღების შექმნა კეშს დააქუცმაცებდა. წარუმატებელი აღწერები არასოდეს კეშირდება. პარამეტრები:

| გასაღები                        | ნაგულისხმევი | დიაპაზონი |
| ------------------------------- | ------------ | --------- |
| `modalityBridgeCacheEnabled`    | `true`       | —         |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440    |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000   |

#### დისტანციური სურათის ნორმალიზაცია (თვითციკლის აღწერა/base64 მიღება)

როდესაც ხიდი თავად იღებს **დისტანციურ** სურათს — Anthropic-ის აღწერის
თვითგამოძახება და claude-wire-format-ის base64 კონვერტაცია
(`ensureBase64ImagesForClaudeWire`), ორივე `fetchRemoteImageAsDataUri()`-ის მეშვეობით
ფაილში `visionBridgeHelpers.ts` — მიღებული მონაცემთა URI ხედვის მოდელის მოთხოვნაში
ჩაშენებამდე გადაეცემა `normalizeDataUri()`-ს
(`open-sse/utils/imageNormalize.ts`). ზედმეტად დიდი სურათები მცირდება **2048px სიგრძის
გვერდამდე** (რაც შეესაბამება ზომის ზღვარს, რომელსაც OpenAI/Anthropic უკვე სერვერის მხარეს
იყენებენ), რაც ამცირებს ასატვირთ ბაიტებს/დაყოვნებას ისე, რომ ხედვის მოდელის მიერ დანახული
არ იცვლება. ზომის შეცვლა იყენებს `sharp`-ს, რომელიც დინამიკური იმპორტით იტვირთება:
პლატფორმაზე, სადაც მისი ნატიური ბინარული ფაილის ჩატვირთვა ვერ ხერხდება,
`normalizeDataUri()` **არასოდეს ისვრის გამონაკლისს** — ის საწყისი ბაიტების უცვლელად
გატარებაზე გადადის, ამიტომ აღწერის/base64-კონვერტაციის გზა ყოველთვის განაგრძობს მუშაობას.
არასურათის ბაიტებიც (მიღება, რომელმაც დეკოდირებადი სურათი არ დააბრუნა) უცვლელად გადაიცემა.
ეს ნორმალიზაცია შემოიფარგლება სურათებით, რომლებსაც ხიდი საკუთარი თვითგამოძახებისთვის იღებს —
ის არასოდეს გამოიყენება გამომძახებლის დაუმუშავებელ, პირდაპირ გადასაცემ მონაცემებზე, რაც
შეესაბამება მხოლოდ აშკარა თანხმობით ცვლილების პრინციპს (მკაცრი წესი #20).

#### გამჭვირვალობის სათაური + სტატისტიკა

აღწერით გარდაქმნილ პასუხებს ახლავს
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(იქმნება `buildModalityBridgeHeader()`-ით ფაილში `modalityBridge/bridgeStats.ts`,
ემატება `withModalityBridgeHeader()`-ით ფაილში `src/sse/handlers/chatHelpers.ts`).
ხელახლა მარშრუტიზებულ მოთხოვნებს სათაური **არ** ემატება — მონაცემები ხელუხლებელი იყო, ხოლო მოდელის
ჩანაცვლება უკვე ჩანს პასუხის სხეულის `model` ველში.

`GET /api/modality-bridge/stats` (მართვის ავტორიზაციით, იმავე დონეზე, რომელზეც
`GET /api/settings`) აბრუნებს მეხსიერებაში შენახულ, თითოეული მოდალობის მრიცხველებს
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` `vision`, `audio` და
`video` მოდალობებისთვის. `averageLatencyMs` მნიშვნელის სახით იყენებს
`latencySamples`-ს და არა ყველა მცდელობას; დროის გაზომვის გარეშე შესრულებული
ოპერაცია ნულმილიწამიან ხელოვნურ ნიმუშს არ ქმნის. `bridged` წარმატებული
კონვერსიების უკუთავსებად ფსევდონიმად რჩება; წარუმატებელი მცდელობები მას არ ზრდის.
დიზაინის მიხედვით, პროცესის ხელახლა გაშვებისას მრიცხველები ნულდება
(ტელემეტრია და არა აღრიცხვა).

უკუთავსებადობის ბმულია; ის ფორმის მეორე ასლს აღარ შეიცავს. Media Providers ასევე
აკავშირებს Image-to-Text და Speech-to-Text სამუშაო პროცესებს Modality Bridge-ის
შესაბამის ჩანართებთან, არსებული Speech-to-Text საცდელი გარემოს წაშლის გარეშე.

**თვითმარყუჟის დაშვების გვერდის ავლა:** როდესაც აღწერის გამოძახება OmniRoute-ის
საკუთარი `/v1` თვითმარყუჟის გავლით მარშრუტდება (პროვაიდერის არასტანდარტული
მოდელი), ქვემოთხოვნა აგზავნის `x-omniroute-admission-bypass: internal` სათაურს
და ავთენტიფიცირდება განსაზღვრული თვითმარყუჟის ავტორიზაციის მონაცემით — ლოკალურ
რეჟიმში ლოკალური `sk_omniroute` სენტინელით, ან ოპერატორის მიერ კონფიგურირებული
`OMNIROUTE_API_KEY` / `ROUTER_API_KEY` გარემოს გასაღებით (#1350), რათა
`REQUIRE_API_KEY=true` განთავსებებშიც შესაძლებელი იყოს აღწერის გამოძახება.
გვერდის ავლა მხოლოდ ზუსტად ამ ავტორიზაციის მონაცემებისთვის მოქმედებს, ამიტომ
გარე კლიენტები დაშვების გამოსატოვებლად ამ სათაურს ვერ გამოიყენებენ.

`src/shared/constants/visionBridgeDefaults.ts`-ში; ახალი რეჟიმის,
ამოცანაზე მორგებისა და ქეშის ნაგულისხმევი მნიშვნელობები და პარამეტრების
გადამწყვეტი განთავსებულია

`getSettings` და `callVisionModel` იმპლემენტაციების ინექცია.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

აუდიოს შემცველ ჩატის მოთხოვნებს აკავებს მანამ, სანამ ისინი აუდიოშეყვანის
მიმღებად უცნობ სამიზნემდე მიაღწევენ. ის ჩატის მოთხოვნას არასოდეს გადაამისამართებს:
აუდიონაწილები ტრანსკრიბირდება არსებული OpenAI-თავსებადი multipart საბოლოო
წერტილის მეშვეობით, ხოლო არჩეული ჩატის მოდელი მუშაობას ტექსტური
ტრანსკრიპტებით აგრძელებს.

ნაკადი:

1. განსაზღვრეთ `supportsAudio` `getResolvedModelCapabilities()`-ის მეშვეობით.
   უპირატესობა ენიჭება პროვაიდერთა რეესტრის მკაფიო მეტამონაცემებს, შემდეგ
   სტატიკურ მოდელის მეტამონაცემებს, შემდეგ კი სინქრონიზებულ
   `modalities_input`-ს. გამოცხადებული შეყვანის სია `audio`-ს გარეშე არის
   `false`; შესაძლებლობის შესახებ მტკიცებულების არქონისას მნიშვნელობა რჩება
   `null`. როგორც `false`, ისე `null` ააქტიურებს კონსერვატიულ ხიდს, ხოლო
   `true` მას გვერდს უვლის.
2. განსაზღვრეთ `modalityBridgeAudio*` პარამეტრები და თითოეული შეტყობინებიდან
   ამოიღეთ ჩასანაცვლებლად ვარგისი ზედა დონის აუდიონაწილები გაზიარებული
   `detectMediaParts()` დეტექტორის მეშვეობით. მხარდაჭერილი გადაცემის ფორმებია
   OpenAI-ის `input_audio`, `audio_url` და `source.media_type: "audio/*"`.
   ჩადგმული აუდიო მარშრუტიზაციისთვის ამოიცნობა, თუმცა ჩანაცვლების გზით არ
   იშლება. სამუშაოს მოცულობა შეზღუდულია `modalityBridgeAudioMaxClips`-ით;
   მომდევნო ნაწილები ხელუხლებელი რჩება.
3. გამოიყენეთ კონფიგურირებული `provider/model`, ან მიეცით
   `selectAudioBridgeModel()`-ს საშუალება, სტაბილური კატალოგის თანმიმდევრობით
   გაიაროს `AUDIO_TRANSCRIPTION_PROVIDERS` და შეარჩიოს პირველი მოდელი, რომლის
   აქტიური პროვაიდერის ავტორიზაციის მონაცემის გამოყენებაც შესაძლებელია.
4. `callAudioTranscription()` base64/data-URI აუდიოს გარდაქმნის multipart
   `file`-ად, ან ჩამოტვირთავს დისტანციურ `audio_url`-ს მხოლოდ საჯარო რესურსებზე
   გამავალი კავშირის დამცავი მექანიზმის გავლით, DNS-ის დაფიქსირებითა და 25 MB
   შეზღუდვით. შემდეგ ის POST-ით აგზავნის ფაილსა და არჩეულ მოდელს ლოკალურ
   `/v1/audio/transcriptions` თვითმარყუჟში, `resolveSelfLoopBearer()`-ით
   ავთენტიფიკაციის გამოყენებით. არსებული ტრანსკრიფციის მარშრუტი ასრულებს
   ავტორიზაციის მონაცემების ჩვეულებრივ მოძიებას, დაყოვნების/სიხშირის ლიმიტის
   დამუშავებასა და პროვაიდერთან გადაგზავნას.
5. წარმატებული გამოძახებები საკუთარ ნაწილებს ანაცვლებს
   `[Audio N]: <transcript>`-ით. გამოძახებები სრულდება `Promise.allSettled`-ით:
   ინდივიდუალური წარუმატებლობა ინარჩუნებს შესაბამის თავდაპირველ აუდიონაწილს
   (#4012 კონტრაქტი). თუ ყველა გამოძახება წარუმატებელია და დადასტურებულია, რომ
   სამიზნეს აქვს `supportsAudio === false`, ნაწილები ხდება
   `[Audio N]: (unavailable — no STT provider connected)` (#8430 კონტრაქტი).
   უცნობი სამიზნისთვის (`null`) ყველა გამოძახების წარუმატებლობისას მოთხოვნა
   ხელუხლებელი რჩება. დადასტურებულად მხოლოდ ტექსტზე მომუშავე სამიზნე, რომლისთვისაც
   გამოსაყენებელი STT ავტორიზაციის მონაცემი არ არსებობს, იმავე მკაფიო
   ჩამნაცვლებელს იღებს ქსელური გამოძახების გარეშე.

წარმატებული ტრანსკრიპტები იყენებს მთელი პროცესისთვის საერთო Modality Bridge
LRU/TTL ქეშს. გასაღები აერთიანებს აუდიოზე მითითებას, სტაბილურ
`audio-transcription` ოპერაციის ჭდეს და არჩეულ STT მოდელს; წარუმატებლობები
ქეშში არასოდეს ინახება. აუდიოს მცდელობები აახლებს გაზიარებულ `bridged`,
`cacheHits`, `failures` და `lastUsedAt` მრიცხველებს. გარდაქმნილ პასუხებს ახლავს
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; ხელუხლებელ
მოთხოვნებს Audio Bridge სეგმენტი არ ემატება.

გაშვების დროის პარამეტრები მონაცემთა ბაზაში ინახება და Zod-ით ვალიდირდება:

| გასაღები                      | ნაგულისხმევი მნიშვნელობა | დიაპაზონი      |
| ----------------------------- | ------------------------ | -------------- |
| `modalityBridgeAudioEnabled`  | `true`                   | —              |
| `modalityBridgeAudioModel`    | `""`                     | Auto ან STT ID |
| `modalityBridgeAudioTimeout`  | `60000`                  | 1000–300000    |
| `modalityBridgeAudioMaxClips` | `3`                      | 1–10           |

გაზიარებული კეში კვლავ იმართება `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` და `modalityBridgeCacheMaxEntries` პარამეტრებით.

### ვიდეოხიდი (`videoBridge.ts`, `videoBridgePipeline.ts`)

Chat Completions-ის `messages`-ში და Responses API-ის `input`-ში ზედა დონის ვიდეონაწილებს წყვეტს მანამ, სანამ გამოძახებული იქნება სამიზნე, რომელსაც ცნობილი ჩაშენებული ვიდეომხარდაჭერა არ აქვს.
მხარდაჭერილი ფორმატებია `input_video`, `video_url`, `video_source`, HTTPS URL-ები
და `data:video/*;base64,...` მონაცემთა URI-ები. ტექსტში არსებული უბრალო ფაილის სახელები
ვიდეოდ არ განიხილება.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) პასუხისმგებელია მოთხოვნის შემოვლაზე,
შესაძლებლობის/პოლიტიკის შემოწმებაზე, თითოეული მოთხოვნის აგრეგაციასა და პასუხის დატვირთვაზე.
თითოეულ ვიდეოზე შესასრულებელი სამუშაო — მოპოვება, სრული შედეგის კეში, კადრების
მიმდევრობის აღწერა (რომელიც აერთიანებს გამომძახებლის მიერ დეკლარირებულ აუდიოტრანსკრიპტს)
და თითოეული მცდელობის მეტრიკები/შეწყვეტა/გასუფთავება — დამალულია
`videoBridgePipeline.ts`-ში არსებული `processVideoPart`-ის მიღმა, რომელიც `preCall`-ის ციკლში
თითოეული ვიდეონაწილისთვის ერთხელ გამოიძახება.
ეს მოდული ასევე განსაზღვრავს პორტების მკაფიო საზღვრებს: `VideoMediaBrokerPort`
(ბაიტების მოპოვება და შერჩეული კადრების ამოღება), `VideoAudioTranscriptionPort`
(გამომძახებლის მიერ დეკლარირებული აუდიოტრანსკრიპტის შერჩეული კადრების აღწერებთან გაერთიანება)
და `VideoDrilldownPort` (კადრებში დეტალიზაციის მუდმივი შენახვის საზღვარი; ჯერ არ არის
დაკავშირებული `processVideoPart`-თან — ამჟამად დეტალიზაციის ჩანაწერებს მხოლოდ ცალკე
`/api/modality-bridge/video/drilldown` მარშრუტი წერს).

საჯარო `/v1` მოთხოვნის გზა არასოდეს ახდენს ქვეპროცესის იმპორტს ან გამოძახებას. დისტანციური
ვიდეოები იტვირთება 50 MiB-ის ზღვრის დაცვით; ჩასმული base64 ვიდეოებისთვის მოქმედებს
კონსერვატიული, თითო ვიდეოზე 36 MiB-ის დეკოდირებული მონაცემების ზღვარი, რათა მოდელის/შეტყობინებების/ჩარჩოების
გარსი დარჩეს საჯარო JSON მოთხოვნის მიღების 50 MiB-იან ლიმიტში. ჩასმული მონაცემების
სიგრძე და დეკოდირებული ზომის შეფასებები მოწმდება მეხსიერების გამოყოფამდე. HTTPS
სავალდებულოა როგორც საწყისი დისტანციური URL-ისთვის, ისე ყოველი გადამისამართებისთვის,
რისთვისაც გამოიყენება არსებული მხოლოდ საჯარო მიმართულების დამცავი მექანიზმი DNS-ის
ფიქსაციით. შემდეგ ბაიტები კვეთს ზუსტად განსაზღვრულ შიდა
`POST /api/modality-bridge/video/extract` ბროკერის საზღვარს. ეს მარშრუტი არის როგორც
`LOCAL_ONLY`, ისე `SPAWN_CAPABLE`, იღებს მხოლოდ თითოეული პროცესისთვის ავთენტიფიცირებულ,
სანდო loopback-მოთხოვნას და არასოდეს იღებს URL-ს, ფაილური სისტემის ბილიკს, შესრულებად
ფაილს ან არგუმენტების სიას. API-ის სხეულის ზომის დამუშავების კონვეიერი და დამმუშავებლის
ინკრემენტული სხეულის წამკითხველი ერთმანეთისგან დამოუკიდებლად უზრუნველყოფენ ბროკერის
შეყვანის 50 MiB-იან ზღვარს. მისი შეზღუდული რიგი ერთ ჯერზე ერთ ამოღებას ასრულებს,
უშვებს ოთხ მომლოდინე დავალებას და მომლოდინე შეყვანის მოცულობას 100 MiB-მდე ზღუდავს.

კადრებს თანმიმდევრულად ენიჭება აღწერები კონფიგურირებული Video მოდელის გამოყენებით.
Video-ს ცარიელი გადაფარვა მემკვიდრეობით იღებს Vision-ის პარამეტრს; თუ ორივე ცარიელია,
Vision-ის ავტომარშრუტიზატორი ირჩევს ეფექტურ, ხედვის შესაძლებლობის მქონე მოდელს.
წარმატებული აღწერები საწყის ნაწილს ანაცვლებს სტაბილური `[Video description:`
პრეფიქსით, რომელიც ტექსტს ასევე აღნიშნავს, როგორც მედიიდან მიღებულ არასანდო
დაკვირვებას, და შემდგომ მოდელებს მიუთითებს, არ მიჰყვნენ მედიაში აღმოჩენილ
ინსტრუქციებს. კადრის აღწერის ქეშის გასაღებები მოიცავს JPEG ბაიტებს, მოთხოვნას,
დროის ნიშნულსა და ეფექტურ მოდელს; ქეშდება მხოლოდ წარმატებული აღწერები. ქეშის
ჩანაწერები ინარჩუნებს რეალურად წარმატებული პროდიუსერი მოდელის იდენტობას, მათ შორის
სარეზერვო მოდელისას; როდესაც სხვადასხვა კადრი სხვადასხვა მოდელმა შექმნა, ხიდი
აბრუნებს `mixed`-ს. ქეშში დამთხვევისას ხელახლა გამოიყენება ამ პროდიუსერის იდენტობა
და მას მოთხოვნილი მარშრუტიზაციის გეგმის სახელი არ ენიჭება. მთლიანი ვიდეოს შედეგის
ქეშის გასაღები ეფუძნება ყველა შეყვანას, რომელიც გამომავალს ცვლის — მოთხოვნას,
ეფექტურ მოდელს, შერჩევის პოლიტიკას, კადრების რაოდენობას, სემანტიკური ანალიზის რეჟიმს,
ნორმალიზებული ფოკუსის მინიშნების SHA-256 ანაბეჭდს, ფოკუსის ფანჯარას, `transcript`-ს,
`audioTranscript`-სა და საკონტაქტო ფურცლის დროშას — ამიტომ რომელიმე ამ განზომილების
შეცვლა იწვევს ქეშში აცდენას და არასდროს — მოძველებული ჩანაწერის ხელახლა გამოყენებას.
ვიზუალური დუბლიკატების მოცილების პოლიტიკის ვერსია, ზღვარი და კანდიდატი კადრების
შეზღუდული რაოდენობა ასევე ცალსახად შედის შედეგის ქეშის გასაღებსა და მეტამონაცემებში;
შესაბამისად, პოლიტიკის ცვლილება ვერ გამოიყენებს მთლიანი ვიდეოს მოძველებულ აღწერას.
შედეგის ქეშის v4 მეტამონაცემები ინახავს რეჟიმსა და ანაბეჭდს, მაგრამ არასდროს —
მომხმარებლის დაუმუშავებელ ამოცანას. დამცავი მექანიზმის მეტამონაცემები ასახავს როგორც
მოთხოვნილ, ისე ეფექტურ ანალიზის რეჟიმებს; მოთხოვნილი `focused` რეჟიმი გამოსადეგი
მომხმარებლის ტექსტის გარეშე აისახება, როგორც ეფექტურად `full`.

დამცავი მექანიზმი იღებს ყველა მხარდაჭერილ ვიდეონაწილს, თუმცა აღწერს არაუმეტეს
`modalityBridgeVideoMaxVideos` რაოდენობისა. სამიზნისთვის, რომლის შემთხვევაშიც
დადასტურებულია `supportsVideo === false`, წარუმატებელი და ლიმიტს გადაცილებული
ვიდეოები ჩანაცვლდება ცალსახა, უსაფრთხო ტექსტური ნიშნულებით, რათა დაუმუშავებელი ვიდეო
არ გადარჩეს. როდესაც შესაძლებლობა უცნობია, ეს ნაწილები უცვლელი რჩება.
`supportsVideo === true`-ის მქონე სამიზნეები ხიდს გვერდს უვლიან. კლიენტის მოთხოვნის
გაუქმების სიგნალი ვრცელდება ჩამოტვირთვაზე, ბროკერის რიგზე, ქვეპროცესებსა და აღწერის
გამოძახებებზე; გაუქმებები აჩერებს დამუშავებას ვიდეოებს შორის და არასდროს უშვებს
დაუმუშავებელ მედიას შეცდომის შემთხვევაში.

გაშვების დროის პარამეტრები ინახება DB-ში და ვალიდირდება Zod-ით:

| გასაღები                            | ნაგულისხმევი | დიაპაზონი / ქცევა                                                                                     |
| ----------------------------------- | ------------ | ----------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`      | არჩევითი გაშვების გარემო, ხელით ჩასართავი                                                             |
| `modalityBridgeVideoAnalysisMode`   | `"full"`     | `full` ინარჩუნებს ზოგად აღწერებს; `focused` იყენებს შეზღუდულ, არასანდო, მომხმარებლის უახლეს კონტექსტს |
| `modalityBridgeVideoModel`          | `""`         | მემკვიდრეობით იღებს Vision Bridge-ის მოდელს                                                           |
| `modalityBridgeVideoFrameCount`     | `8`          | 1–16                                                                                                  |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`  | `uniform`, `scene_aware` ან პროპორციული `segment_aware`; დეტექტორის შეცდომისას გამოიყენება `uniform`  |
| `modalityBridgeVideoMaxVideos`      | `1`          | 1–4                                                                                                   |
| `modalityBridgeVideoTimeout`        | `120000`     | 1000–120000 ms                                                                                        |

ადრე შენახული Video-ს დროის ამოწურვის მნიშვნელობები, რომლებიც 120 წამს აღემატება,
იზღუდება ბროკერის ბოლო ვადამდე; ამ ლიმიტზე მაღალი ახალი პარამეტრების ჩაწერა
უარყოფილია. `GET /api/modality-bridge/video/runtime` ავთენტიფიკაციამდე ან გაშვების
გარემოს შემოწმებამდე მოითხოვს სანდო ნიშნით დადასტურებულ loopback ლოკალურობას, შემდეგ
კი — მართვის ავთენტიფიკაციას. ის აბრუნებს მხოლოდ `available`-ს, გასუფთავებულ
FFmpeg/ffprobe ვერსიებსა და ფიქსირებულ მიზეზს, როდესაც გაშვების გარემო მიუწვდომელია.
შიდა ამოღების საბოლოო წერტილი საჯარო ატვირთვის API არ არის: რიგის გადავსება
აბრუნებს `503`-ს და `Retry-After`-ს, გამომძახებლის გათიშვა — `499`-ს, ხოლო ბროკერის
ფიქსირებული ბოლო ვადის ამოწურვა — `504`-ს. გარდაქმნილი პასუხები ცენტრალურ
`x-omniroute-modality-bridge` სათაურს ამატებს
`video->text;model=<visionModel>;parts=<videos>`-ს Vision-ის ან Audio-ს სეგმენტების
წაშლის გარეშე.

### PII-ის შემნიღბველი (`piiMasker.ts`)

მუშაობს **ორივე** ეტაპზე.

- **`preCall`** კლონირებს payload-ს, გადის `system`, `messages`, `input` და
  `prompt` ველებზე (უბრალო სტრიქონული ელემენტების ჩათვლით) და სტრიქონულ
  `content`/`text` ველებზე იყენებს `processPII()`-ს (`@/shared/utils/inputSanitizer`-დან).
  როდესაც `PII_REDACTION_ENABLED=true`, აღმოჩენილი PII გამავალი payload-იდან
  რედაქტირდება. ეს არ არის დამოკიდებული `INPUT_SANITIZER_MODE`-ზე (რომელიც მხოლოდ
  prompt injection-ის პოლიტიკას აკონტროლებს). როდესაც რედაქტირება გამორთულია,
  გამოძახება აფიქსირებს აღმოჩენების რაოდენობას შიგთავსის გადაწერის გარეშე.
- **`postCall`** ქმნის პასუხის ღრმა კლონს, უშვებს `sanitizePIIResponse()`-ს და
  Responses API-ის ფორმის ნიღბვის ფუნქციას (`maskResponsesOutput` — მოიცავს
  `output_text`-სა და `output[].content[].text`-ს). თუ რაიმე რედაქტირება მოხდა,
  შეცვლილი პასუხი ანაცვლებს თავდაპირველს.

დამცავი მექანიზმი მოთხოვნას არასოდეს ბლოკავს; ის მხოლოდ ანოტაციას ამატებს
(`meta.detections`, `meta.redacted`) ან შიგთავსს გადაწერს.

### Prompt Injection (`promptInjection.ts`)

აღმოაჩენს მომხმარებლის მიერ მოწოდებულ შიგთავსში მტრულ სტრუქტურებს და აღასრულებს
კონფიგურირებულ პოლიტიკას. ქცევას განსაზღვრავს გარემოს ცვლადები და კონსტრუქტორის
პარამეტრები:

| პარამეტრი         | გარემოს ცვლადი                                                                                                | ნაგულისხმევი | ეფექტი                                                                                                                                                                                     |
| ----------------- | ------------------------------------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ჩართულია          | `INPUT_SANITIZER_ENABLED`                                                                                     | `true`       | როდესაც არის `false`, დამცავი მექანიზმი შემდგომ დამუშავებას წყვეტს.                                                                                                                        |
| რეჟიმი            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                               | `warn`       | ინექციის პოლიტიკა: `block`, `warn` ან `log`. (`redact` მიღებულია უკუთავსებადობისთვის, თუმცა ინექციის ტექსტს **არ** შლის; მოთხოვნაში PII-ის გადაწერას `PII_REDACTION_ENABLED` აკონტროლებს.) |
| ბლოკირების ზღვარი | `blockThreshold` პარამეტრი / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ფსევდონიმი `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | ბლოკირებისთვის საჭირო მინიმალური სიმძიმე. ნაგულისხმევად, საშუალო სიმძიმის შემთხვევებზე მხოლოდ დაკვირვება ხდება.                                                                            |

**რეჟიმის პრიორიტეტულობა** (`getMode`): გამომძახებლის `options.mode` →
`INJECTION_GUARD_MODE`-ის **DB feature-flag override** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` გარემოს ცვლადი → `INPUT_SANITIZER_MODE`
გარემოს ცვლადი → `warn`. შესაბამისად, dashboard-ის override-ს გარემოს ცვლადებზე
უპირატესობა აქვს, ამიტომ Feature Flags UI გაშვებული დამცავი მექანიზმის მართვის
საშუალებას რეალურ დროში იძლევა (გადატვირთვის გარეშე). DB-დან წაკითხვა
შეცდომამედეგია: შეცდომის შემთხვევაში დამცავი მექანიზმი გარემოს ცვლადებზე
დაფუძნებულ ქცევას უბრუნდება, ხოლო თუ override დაყენებული არ არის, ქცევა მხოლოდ
გარემოს ცვლადებით განსაზღვრული ქცევის იდენტურია.

აღმოჩენის წყაროები:

1. `sanitizeRequest()` `@/shared/utils/inputSanitizer`-დან (საერთო დეტექტორების
   ნაკრები, რომელიც pipeline-ის სხვა ნაწილებშიც გამოიყენება).
2. ჩაშენებული `DEFAULT_GUARD_PATTERNS` (ამჟამად `system_override_inline` და
   `markdown_system_block`, ორივე `high` სიმძიმით).
3. კონსტრუქტორის პარამეტრების მეშვეობით გადაცემული არასავალდებულო `customPatterns`
   (სტრიქონები, რეგულარული გამოსახულებები ან `{ name, pattern, severity }` ჩანაწერები).

როდესაც `mode === "block"` **და** სულ მცირე ერთი აღმოჩენა აკმაყოფილებს სიმძიმის
ზღვარს, `preCall` აბრუნებს `{ block: true, message: "Request rejected:
suspicious content detected" }`. `warn`/`log` რეჟიმებში დამცავი მექანიზმი ჩანაწერს
ლოგში ამატებს, თუმცა გამოძახებას უშვებს. საერთო დამხმარე ფუნქცია
`evaluatePromptInjection()` ასევე ექსპორტირებულია იმ გამომძახებლებისთვის,
რომლებსაც prompt-ების შეფასება registry-ის გავლის გარეშე სჭირდებათ.

### ავტორიზაციის მონაცემების ნიღბვა (`credentialMasker.ts`)

ეშვება **ორივე** ეტაპზე, ნაგულისხმევ ჯაჭვში ბოლოს (პრიორიტეტი `95`). გამავალი
payload-იდან (შეტყობინების შიგთავსი, tool call-ის არგუმენტები, tool-ის შედეგები)
**და** პროვაიდერის პასუხიდან რედაქტირებს ფართოდ ცნობილ API key-ის / secret
token-ის ნიმუშებს, რათა prompt-ში ჩასმული ავტორიზაციის მონაცემები (ან tool-ის
შედეგში დაბრუნებული მათი ასლი) არ გაჟონოს გარე პროვაიდერთან ან უკან, კლიენტთან.

- **მხოლოდ ჩართვის შემთხვევაში**, იგივე კონვენციით, როგორც PII-ის რედაქტირება (Hard Rule #20-ის მომიჯნავე):
  გამორთულია, თუ `settings.credentialRedactionEnabled === true` **ან**
  `CREDENTIAL_REDACTION_ENABLED=true` არ არის მითითებული. გამორთულ მდგომარეობაში დამცავი მექანიზმი არაფერს აკეთებს —
  ის არასდროს ბლოკავს და არასდროს გადაწერს.
- `redactCredentials()` სრულად გაივლის payload-ის/response-ის ხეს (`walkValue()`,
  დაცულია prototype pollution-ისგან და ციკლებისგან `WeakSet`-ის მეშვეობით) და დამთხვევებს
  `[REDACTED:<type>]` ჩანაცვლების ნიშნით ცვლის, ამასთან კლონირდება მხოლოდ რეალურად
  შეცვლილი განშტოებები.
- `CREDENTIAL_PATTERNS` მოიცავს LLM პროვაიდერების გასაღებებს (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ტოკენებს (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), გადახდის გასაღებებს (Stripe, Square), ღრუბლოვანი
  სერვისების გასაღებებს (AWS-ის წვდომის გასაღები, Twilio, SendGrid, Mailgun), პირად გასაღებებს / JWT-ებს,
  ავტორიზაციის მონაცემების შემცველ კავშირის სტრიქონებს (`mongodb://user:pass@...` და ა.შ.) და
  ზოგად `Authorization`/`x-api-key`/`api-key`/`apikey` სათაურის მნიშვნელობის
  პატერნს. სათაურის ფორმის გასაღებები (`authorization`, `x-api-key`, `api-key`,
  `apikey`) რედაქტირდება სტრუქტურულად (მხოლოდ მნიშვნელობა, ხოლო სქემის პრეფიქსი, როგორიცაა
  `Bearer `/`Basic `, შენარჩუნებულია), და არა ზოგადი ტექსტური რეგულარული გამოსახულების მეშვეობით.
- დამცავი მექანიზმი არასდროს ბლოკავს; ის მხოლოდ გადაწერს (`modifiedPayload` /
  `modifiedResponse`) და ამატებს ანოტაციებს (`meta.credentialsRedacted`, `meta.count`).

რეგრესიისგან დამცავი ტესტი: `tests/unit/credential-masker-guardrail.test.ts`.

## საბაზისო კონტრაქტი (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ჯაჭვის შესრულებას დაუყოვნებლივ წყვეტს
  message?: string; // ნაჩვენებია დაბლოკვისას
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // მოთხოვნის გადასაწერად აბრუნებს preCall
  modifiedResponse?: TValue; // პასუხის გადასაწერად აბრუნებს postCall
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

დამცავი მექანიზმი „ცვლილება არ არის“ მდგომარეობის შესახებ მიანიშნებს `void`-ის, `{}`-ის ან
`{ block: false }`-ის დაბრუნებით. `modifiedPayload`/`modifiedResponse`-ის დაბრუნება
ჩაანაცვლებს ჯაჭვში გამავალ მნიშვნელობას მომდევნო დამცავი მექანიზმებისთვის.
`signal?: AbortSignal` გამომძახებლის სასიცოცხლო ციკლს დამცავ მექანიზმებს გადასცემს. მოთხოვნის შეწყვეტა წინასწარგანზრახული fail-open გამონაკლისია: მედია-ხიდები წყვეტენ მუშაობას და ასუფთავებენ რესურსებს ისე, რომ დაუმუშავებელი მედია არ აღადგინონ სამიზნეზე, რომლის შესახებაც ცნობილია, რომ მას მხარს არ უჭერს.

## რეგისტრატორი (`registry.ts`)

სინგლტონი `guardrailRegistry` აჩვენებს:

- `register(guardrail)` — ამატებს (ან ცვლის ნორმალიზებული სახელით) გარდრეილს და
  ხელახლა ალაგებს ზრდადი `priority`-ის მიხედვით.
- `clear()` / `list()` — ადმინისტრაციული დამხმარეები.
- `runPreCallHooks(payload, context)` — ახდენს აქტიური გარდრეილების იტერაციას,
  გადასცემს `payload`-ს `modifiedPayload`-ის გავლით და ჩერდება პირველ `block: true`-ზე.
- `runPostCallHooks(response, context)` — იგივე ნაკადი პასუხის მხარეს.
- `resetGuardrailsForTests({ registerDefaults })` — ასუფთავებს მდგომარეობას და სურვილისამებრ
  ხელახლა არეგისტრირებს ნაგულისხმევ პარამეტრებს ტესტის სუფთა იზოლაციისთვის.

ორივე რანერი აბრუნებს `{ blocked, payload|response, results, guardrail?, message? }`-ს,
სადაც `results` არის `GuardrailExecutionResult` ჩანაწერების მასივი, რომელიც მოიცავს
თითოეული გარდრეილის `blocked`, `skipped`, `modified`, `error` და `meta` ველებს,
რაც სასარგებლოა ტრეისინგისთვის.

### გარდრეილების გამორთვა თითო მოთხოვნაზე

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` აგროვებს
გარდრეილების სახელების დედუპლიცირებულ სიას, რომლებიც უნდა გამოტოვებულ იქნას
მიმდინარე მოთხოვნისთვის. წყაროები (ყველა არასავალდებულო, ყველა გაერთიანებულია):

- `apiKeyInfo.disabledGuardrails`
- მოთხოვნის სხეული `disabledGuardrails` (ზედა დონის)
- მოთხოვნის სხეული `metadata.disabledGuardrails`
- ჰედერი `x-omniroute-disabled-guardrails` (ან მოძველებული
  `x-disabled-guardrails`)

მნიშვნელობები შეიძლება იყოს სტრიქონების მასივები ან მძიმით გამოყოფილი სტრიქონი;
სახელები ნორმალიზდება პატარა ასოებით kebab-case-ში (`pii_masker` → `pii-masker`).
შედეგი გადაეცემა `context.disabledGuardrails`-ის გავლით რეგისტრატორს,
რომელიც გამოტოვებს შესაბამის გარდრეილებს (`skipped: true` `results`-ში).

## შესრულების თანმიმდევრობა

ყოველი მოთხოვნისთვის, რომელიც გადის `src/sse/handlers/chat.ts`-სა და `open-sse/handlers/chatCore.ts`-ის გავლით:

1.  `resolveDisabledGuardrails(...)` აგებს გამოტოვების სიას API გასაღებიდან, სხეულიდან და სათაურებიდან.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` ასრულებს დამცავ მექანიზმებს პრიორიტეტის ზრდადი თანმიმდევრობით:
    - გამორთული დამცავი მექანიზმები აღირიცხება როგორც `skipped`.
    - თითოეული დამცავი მექანიზმის `preCall`-მა შეიძლება გადაწეროს მონაცემთა პაკეტი `modifiedPayload`-ის მეშვეობით.
    - პირველი `block: true` წყვეტს ჯაჭვს და დამმუშავებელი აბრუნებს დამცავი მექანიზმის უარყოფის პასუხს.
3.  (პოტენციურად გადაწერილი) მონაცემთა პაკეტი მიედინება კომბინირებულ მარშრუტიზაციასა და ზედა დინების გაგზავნაში.
4.  პასუხის აწყობის შემდეგ, `guardrailRegistry.runPostCallHooks(...)` აწარმოებს იმავე ჯაჭვს პასუხზე. `block: true` აქ აგდებს ზედა დინების პასუხს.

დამცავი მექანიზმები, რომლებიც შეცდომას აგდებენ, აღირიცხება `error: <message>`-ით და აღინიშნება `logger.warn`-ის მეშვეობით, მაგრამ ჯაჭვი გრძელდება — დიზაინით ღიაა წარუმატებლობისთვის.

## კონფიგურაცია

ჩაშენებული დამცავი მექანიზმების მიერ წაკითხული გარემოს ცვლადები:

| ცვლადი                                | გამოიყენება                 | ეფექტი                                                                                                      |
| :------------------------------------ | :-------------------------- | :---------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`          | დააყენეთ `false` გამოვლენის სრულად გამორთვისთვის.                                                           |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`          | ინექციის პოლიტიკა: `warn`, `block`, ან `log`. მოძველებული მნიშვნელობა `redact` არ გადაწერს ინექციის ტექსტს. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`          | რეჟიმი ინექციის დამცავისთვის; ასევე DB ფუნქციის დროშა, რომელიც **გადაფარავს** გარემოს ცვლადებს (DB > ENV).  |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`          | მინიმალური სიმძიმე, რომელსაც `MODE=block` უარყოფს: `high` (ნაგულისხმევი), `medium`, ან `low`.               |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`          | მოძველებული ფსევდონიმი `INPUT_SANITIZER_BLOCK_THRESHOLD`-ისთვის.                                            |
| `PII_REDACTION_ENABLED`               | `pii-masker`                | როდესაც `true`, მოთხოვნის PII რედაქტირდება (ინექციის რეჟიმისგან დამოუკიდებლად).                             |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ქვედა დინება) | აკონტროლებს პასუხის მხარის ნიღბის ქცევას.                                                                   |

Modality Bridge-ის დამცავი მექანიზმები კითხულობენ გაშვების კონფიგურაციას DB-ზე დაფუძნებული პარამეტრების საცავიდან (`getSettings()`), და არა გარემოს ცვლადებიდან. Vision-ის ძირითადი გასაღებებია `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, და `modalityBridgeCacheMaxEntries`. მოძველებული `visionBridge*` გასაღებები მიიღება მხოლოდ როგორც დოკუმენტირებული ერთციკლიანი წაკითხვის სარეზერვო ვარიანტი; დაფის ჩანაწერები იყენებენ ძირითად გასაღებებს. ნაგულისხმევი მნიშვნელობები და სარეზერვო გადამწყვეტი განთავსებულია `src/shared/constants/modalityBridgeDefaults.ts`-ში, მოძველებული კონსტანტები შენარჩუნებულია `src/shared/constants/visionBridgeDefaults.ts`-ში.

აუდიო იყენებს `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`, `modalityBridgeAudioTimeout`, და `modalityBridgeAudioMaxClips`, პლუს გაზიარებულ `modalityBridgeCache*` პარამეტრებს. აუდიოს არ აქვს მოძველებული გასაღების სარეზერვო ვარიანტი, რადგან ეს გასაღებები შემოღებულ იქნა Modality Bridge სქემასთან ერთად.

ვიდეო იყენებს `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`, `modalityBridgeVideoModel`, `modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`, `modalityBridgeVideoMaxVideos`, და `modalityBridgeVideoTimeout`, პლუს გაზიარებულ `modalityBridgeCache*` პარამეტრებს. ის ნაგულისხმევად გამორთულია, რადგან FFmpeg/ffprobe არის არჩევითი ოპერაციული დამოკიდებულებები და კადრების წარწერა ზრდის შეყოვნებასა და მოდელის ღირებულებას.

## მორგებული Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ნაბიჯები:

1.  შექმენით `src/lib/guardrails/myGuardrail.ts`, რომელიც აფართოებს `BaseGuardrail`-ს.
2.  განახორციელეთ `preCall` და/ან `postCall`.
3.  ან დაარეგისტრირეთ იმპორტის დროს (`registerDefaultGuardrails`-დან დამატებით) ან გამოიძახეთ `guardrailRegistry.register(...)` გაშვების დროს — რეესტრი ჩაანაცვლებს ნებისმიერ წინა guardrail-ს იგივე ნორმალიზებული სახელით.
4.  დაამატეთ ტესტები `tests/unit/`-ში (არსებული მაგალითები: `tests/unit/guardrails-registry.test.ts`, `tests/unit/prompt-injection-guard.test.ts`, `tests/unit/guardrails/visionBridge.test.ts`).

## ტესტირება

გამოიყენეთ `resetGuardrailsForTests()` ტესტებს შორის, რათა დაიწყოთ ცნობილი მდგომარეობიდან. გადაეცით `{ registerDefaults: false }`, რათა დაიწყოთ ცარიელი რეესტრით და დაარეგისტრიროთ მხოლოდ ტესტირებადი guardrails. Vision Bridge იღებს დამოკიდებულების ინექციას (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge აჩვენებს ექვივალენტურ წერტილებს პარამეტრებისთვის, შესაძლებლობებისთვის, STT მოდელის არჩევისთვის, სერთიფიკატების შემოწმებისთვის და ტრანსკრიფციისთვის. ამიტომ, ტესტებს შეუძლიათ ორივე ნაკადის შემოწმება მონაცემთა ბაზის ან ქსელზე წვდომის გარეშე.

## ინექციისგან დამცავი მარშრუტების დაფარვა და წითელი გუნდი (ფაზა 8 · ბლოკი D)

ინექციისგან დამცავი მექანიზმი (`createInjectionGuard` / `withInjectionGuard`) მოიცავს ყველა მარშრუტს, რომელიც იღებს მომხმარებლის მოთხოვნებს. ის ითვალისწინებს `INJECTION_GUARD_MODE`-ს (ნაგულისხმევი `warn` = მხოლოდ ჟურნალი; `block` = აბრუნებს HTTP 400 `SECURITY_001`).

| ტიპი            | მარშრუტები                                                                                                                                           | ნაგულისხმევი რეჟიმი |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| Text (existing) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                |
| Generative      | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                |
| Data            | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                |

ტექსტის ამოღება (`extractMessageContents`) მოიცავს `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`-ს.

**წითელი გუნდი (ღამის, `nightly-llm-security.yml`):** promptfoo ამოწმებს, რომ თითოეული მარშრუტი ბლოკავს OWASP-LLM კორპუსს `INJECTION_GUARD_MODE=block` რეჟიმში; garak აწარმოებს ზონდებს (გამოტოვებს საიდუმლოს გარეშე). `moderations` შედის თანმიმდევრულობისთვის — ოპერატორებს ბლოკირების რეჟიმში შეუძლიათ მისი გათავისუფლება `resolveDisabledGuardrails`-ის მეშვეობით.

ღამის სამუშაო პროცესი (`.github/workflows/nightly-llm-security.yml`, cron + ხელით გაშვება) მოიცავს ორ დავალებას:

- **`promptfoo-guard` (ბლოკირება)** — აწარმოებს `promptfoo eval -c promptfooconfig.yaml`-ს `INJECTION_GUARD_MODE=block`-ით. თითოეული მტრული შემთხვევა (მაგ. „უგულებელყავით ყველა წინა ინსტრუქცია…“, DAN-ის სტილის jailbreaks) ადასტურებს, რომ პასუხი შეიცავს `error.code === "SECURITY_001"`, ანუ guard-მა რეალურად უარყო მოთხოვნა.
- **`garak` (საკონსულტაციო)** — აწარმოებს garak `--probes promptinject,dan,leakreplay`-ს ლოკალური OmniRoute ინსტანციის წინააღმდეგ (`http://localhost:20128/v1`). დაცულია პროვაიდერის საიდუმლო გასაღებით (`PROMPTFOO_PROVIDER_KEY`); გამოტოვებს შეცდომის გარეშე და დამატებულია `|| true`, ასე რომ, ის აფიქსირებს CI-ის ჩავარდნის გარეშე.

guard დამხმარის (`createInjectionGuard` / `withInjectionGuard`) დაფარვა მოიცავს ყველა მოთხოვნის შემცველ `/v1` მარშრუტს; მოთხოვნის ტექსტი ამოღებულია `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`-დან `extractMessageContents()` ფუნქციის მიერ `src/shared/utils/inputSanitizer.ts`-ში.
