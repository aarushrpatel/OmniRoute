> **છેલ્લે અપડેટ કરેલું:** 2026-08-29 — v3.8.51 (Video Bridge ટ્રાન્સક્રિપ્ટનું મૂળ કૉલર દ્વારા જાહેર કરવામાં આવે છે,
> હજી સર્વર દ્વારા ચકાસાયેલું નથી — #11661 અનુસાર સ્પષ્ટ કરવામાં આવ્યું)

Guardrails, OmniRoute અને અપસ્ટ્રીમ પ્રદાતાઓ વચ્ચેની સીમા પર સુરક્ષા, નીતિ અને કન્ટેન્ટ રૂપાંતરણો લાગુ કરે છે. દરેક guardrail વિનંતીના payloads (`preCall`) અને અપસ્ટ્રીમ પ્રતિસાદો (`postCall`)નું નિરીક્ષણ કરી શકે છે (અને વૈકલ્પિક રીતે તેમને નકારી, રૂપાંતરિત અથવા ઍનોટેટ કરી શકે છે).

સિસ્ટમ **fail-open** છે: જો કોઈ guardrail કાર્યરત હોય ત્યારે અપવાદ ફેંકે, તો registry ભૂલ નોંધે છે અને વિનંતીને નિષ્ફળ કરવાને બદલે આગામી guardrail સાથે ચાલુ રહે છે. બ્લૉક કરવું હંમેશાં સ્પષ્ટ નિર્ણય (`block: true`) હોય છે, ક્યારેય આકસ્મિક ઘટના નહીં.

## બિલ્ટ-ઇન ગાર્ડરેલ્સ

રજિસ્ટ્રી ઇમ્પોર્ટ વખતે પ્રાથમિકતાના ક્રમમાં છ ગાર્ડરેલ્સ આપમેળે લોડ કરે છે
(`registry.ts` → `registerDefaultGuardrails()` જુઓ):

| પ્રાથમિકતા | નામ                 | સ્ટેજ          | ફાઇલ                  |
| ---------- | ------------------- | -------------- | --------------------- |
| `5`        | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`        | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`        | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`       | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`       | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`       | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

ઓછા પ્રાથમિકતા અંકો **પહેલા** ચાલે છે.

### વિઝન બ્રિજ (`visionBridge.ts`) — મોડાલિટી બ્રિજ PR-1

**નોન-વિઝન મોડલ્સ**ને લક્ષ્ય બનાવતી, ઇમેજ ધરાવતી વિનંતીઓને ઇન્ટરસેપ્ટ કરે છે અને
કાં તો આખી વિનંતીને વિઝન-સક્ષમ મોડલ પર ફરી રૂટ કરે છે અથવા અપસ્ટ્રીમ કૉલ પહેલાં
ઇમેજના ભાગોને કન્ફિગર કરી શકાય તેવા વિઝન મોડલ દ્વારા બનાવેલા ટેક્સ્ટ વર્ણનોથી
બદલે છે. આ ટેક્સ્ટ-ઓનલી પ્રોવાઇડર્સને મલ્ટિમોડલ પેલોડ્સ પારદર્શક રીતે હેન્ડલ
કરવા દે છે.

પ્રવાહ:

1. જો લક્ષ્ય મોડલ પહેલેથી જ વિઝનને સપોર્ટ કરતું હોય, તો તેને છોડી દો (સિવાય કે તે
   ફરજિયાત-બ્રિજ યાદી `isVisionBridgeForcedModel`માં દેખાતું હોય).
2. `extractImageParts(messages)` દ્વારા ઇમેજના ભાગો એક્સ્ટ્રેક્ટ કરો
   (`visionBridgeHelpers.ts`), જે `open-sse/utils/mediaParts.ts`માં આવેલા
   **એકીકૃત મીડિયા ડિટેક્ટર** `detectMediaParts()`ને કાર્ય સોંપે છે — આ કોમ્બો
   સુસંગતતા ફિલ્ટર સાથે શેર કરાયેલ સત્યનો એકમાત્ર સ્રોત છે.
   એક્સ્ટ્રેક્શન એવા ટોપ-લેવલ ભાગોના આકારો સુધી allowlist કરાયેલું છે, જેને
   `replaceImageParts` ફરી સ્પ્લાઇસ કરી શકે છે (extract↔replace કરાર): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, અને Responses API `input_image`. નેસ્ટેડ મેળ અને
   માત્ર-સૂચક આકારો કોમ્બો-ફિલ્ટર માટેની સામગ્રી છે અને ક્યારેય એક્સ્ટ્રેક્ટ
   થતા નથી. જો કોઈ ન મળે તો છોડી દો.
3. `resolveVisionBridgeRuntimeSettings()` દ્વારા રનટાઇમ કન્ફિગ ઉકેલો
   (`src/shared/constants/modalityBridgeDefaults.ts`): નવી `modalityBridge*`
   સેટિંગ્સ કીઝને પ્રાથમિકતા મળે છે; જૂની `visionBridge*` કીઝ **એક-ચક્ર
   ફૉલબૅક** (રોલબૅક વિન્ડો) તરીકે રહે છે. બ્રિજ અક્ષમ હોય ત્યારે કોઈપણ મીડિયા
   ટ્રાવર્સલ પહેલાં છોડી દો.
4. મોડ સિલેક્ટર (`modalityBridgeVisionMode`, નીચેનું કોષ્ટક જુઓ) ફરી રૂટ કરવું
   કે વર્ણન કરવું તે નક્કી કરે છે. રિરાઉટ માત્ર `model` બદલેલા
   `modifiedPayload` સાથે meta `{ rerouted, fromModel, toModel, imagesKept }`
   પરત કરે છે.
5. વર્ણન પાથ: ઇમેજની સંખ્યાને `maxImages` સુધી મર્યાદિત કરો, કાર્ય-સચેત પ્રોમ્પ્ટ
   તૈયાર કરો, વર્ણન કૅશ તપાસો, વિઝન મોડલને **સમાંતરે** કૉલ કરો
   (`Promise.allSettled`), અને તેમની જગ્યાએ `[Image N]: <description>` ટેક્સ્ટ
   ભાગો દાખલ કરો. નિષ્ફળ વર્ણન `null` આપે છે અને મૂળ ઇમેજ ભાગ
   **જાળવવામાં આવે છે** (#4012) — સિવાય કે કોમ્બો વર્ણન પાથ પર દરેક વર્ણન
   નિષ્ફળ ગયું હોય; એ કિસ્સામાં પુષ્ટિ થયેલા નોન-વિઝન અપસ્ટ્રીમને તેના બદલે
   `(અનુપલબ્ધ — કોઈ વિઝન-સક્ષમ પ્રોવાઇડર કનેક્ટેડ નથી)` સ્ટબ મળે છે (#8430).
6. `modifiedPayload` + meta (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) પરત કરો.

#### મોડ સિલેક્ટર (`modalityBridgeVisionMode`)

| મોડ        | ડિફૉલ્ટ | વર્તન                                                                                                                                                                                                                                                                                       |
| ---------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | લેગસી હ્યુરિસ્ટિક, અપરિવર્તિત (#6640/#7204): નોન-કોમ્બો/`auto/` મોડલ્સ શ્રેષ્ઠ વિઝન મોડલ પર ફરી રૂટ થાય છે, સિવાય કે મૂળ મોડલ પાસે પહેલેથી ઉપયોગ કરી શકાય તેવા ક્રેડેન્શિયલ્સ હોય (તો વર્ણન કરે); કોમ્બો લક્ષ્યો હંમેશાં વર્ણન કરે છે.                                                      |
| `describe` |         | હંમેશાં વર્ણન કરો — રિરાઉટ બ્લોક સંપૂર્ણપણે છોડી દેવામાં આવે છે; વપરાશકર્તાએ પસંદ કરેલું મોડલ હંમેશાં જવાબ આપે છે.                                                                                                                                                                          |
| `reroute`  |         | રિરાઉટ ફરજિયાત કરો: ક્રેડેન્શિયલ ધરાવતા મોડલને જાળવી રાખતો ગાર્ડ બાયપાસ થાય છે. રિરાઉટ-**લક્ષ્ય** ક્રેડેન્શિયલ ગાર્ડ હજી પણ લાગુ પડે છે — ઉપયોગ કરી શકાય તેવું કોઈ વિઝન લક્ષ્ય ન હોય ત્યારે વિનંતી વર્ણન તરફ આગળ વધે છે, જેથી કાચી ઇમેજ ક્યારેય ટેક્સ્ટ-ઓનલી બૅકએન્ડ સુધી ન પહોંચે (#8430). |

ફરજિયાત મોડ્સ auto હ્યુરિસ્ટિક ચાલે તે **પહેલાં** શૉર્ટ-સર્કિટ કરે છે; `auto`નું
વર્તન PR-1 પહેલાના ગાર્ડરેલ સાથે બાઇટ-સમાન છે.

#### API-કી સ્કોપ (`visionBridgeKeyScope.ts`)

જ્યારે કૉલરની API કી `allowedConnections`, ક્વોટા પૂલ્સ
(`allowedQuotas`) અથવા મોડલ્સ (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`)ને પ્રતિબંધિત કરે છે,
ત્યારે બ્રિજ માત્ર એવા કનેક્શન્સ પરના રિરાઉટ અને વર્ણન મોડલ્સ પસંદ કરે છે, જેનો
ઉપયોગ કી કરી શકે. ત્યારબાદ વર્ણન કૉલ હંમેશાં
`x-omniroute-self-loop-key-id` હેડર સાથે OmniRoute સેલ્ફ-લૂપ મારફતે જાય છે,
જેથી પ્રાપ્ત થતી ચેટ વિનંતી તે કીની કનેક્શન અને મોડલ નીતિ ફરીથી લાગુ કરે.
`enforceApiKeyPolicy()` તે હેડરને માત્ર સેલ્ફ-લૂપ બેરર સાથે જ માન્ય રાખે છે,
તેથી તે ફક્ત ઍક્સેસને વધુ મર્યાદિત કરી શકે છે, અને ઉકેલી ન શકાય તેવું id
નકારવામાં આવે છે.

જો કી માટે કોઈ વિઝન મોડલની પરવાનગી ન હોય, તો વર્ણન પાથ બાજુએ ખસી જાય છે અને
વિનંતી કોઈ ફેરફાર વિના પસાર થાય છે, જે અક્ષમ ગાર્ડરેલ જેવું જ fail-open વર્તન
છે (meta `{ skipped: true, reason: "no_permitted_vision_model" }`).
કી વગરની વિનંતીઓ અને આ પ્રતિબંધો વગરની કીઝ પહેલાંની જેમ જ વર્તે છે.

#### કાર્ય-સચેત વર્ણન પ્રોમ્પ્ટ (`modalityBridgeVisionTaskAware`)

ડિફૉલ્ટ **true** છે. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) બેઝ
વર્ણન પ્રોમ્પ્ટમાં **છેલ્લા વપરાશકર્તા સંદેશા**નો ટેક્સ્ટ (500 અક્ષરો સુધી કાપેલો)
ઉમેરે છે, જેથી વર્ણન વપરાશકર્તાએ ખરેખર શું પૂછ્યું હતું તે તરફ દોરાય
(codex-vision-proxy પેટર્ન) અને વિઝન મોડલને દૃશ્યમાન ટેક્સ્ટનું ટ્રાન્સક્રિપ્શન
કરવાનું કહે છે. ફ્લૅગ બંધ હોય — અથવા કોઈ વપરાશકર્તા ટેક્સ્ટ ન હોય — તો બેઝ
પ્રોમ્પ્ટ કોઈ ફેરફાર વિના વપરાય છે.

વર્ણન સેલ્ફ-લૂપની પોતાની OpenAI-સુસંગત વિનંતી (`callVisionModelSingle()`
in `visionBridgeHelpers.ts`) હંમેશાં `image_url.detail: "high"`ની વિનંતી કરે છે —
દરેક કૉલર/પ્રોવાઇડર માટે બિનશરતી રીતે, કોઈપણ ક્લાયન્ટ સિગ્નલ પર આધારિત નહીં.
આ પ્રોમ્પ્ટ જે ટેક્સ્ટ-ટ્રાન્સક્રિપ્શન કાર્ય માટે કહે છે તેમાં ઓછા-વિગતનું
સેમ્પલિંગ OCRની ચોકસાઈ ઘટાડે છે, તેથી મૂળ ઇનબાઉન્ડ વિનંતીએ કયા વિગત સ્તરનો
ઉપયોગ કર્યો હતો તે ધ્યાનમાં લીધા વિના વર્ણન કૉલ પોતે હંમેશાં ઉચ્ચ વિગત માંગે
છે. આ માત્ર આંતરિક વર્ણન વિનંતીના બૉડીને અસર કરે છે; પ્રાથમિક વિનંતી પર
OmniRoute કૉલરના પોતાના `image_url.detail`ને કેવી રીતે ફૉર્વર્ડ કરે છે તે બદલતું
નથી — તે ડિફૉલ્ટ અલગથી લાગુ થાય છે, અને ફક્ત શોધાયેલા OpenCode ક્લાયન્ટ્સ માટે,
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`)માં.
વર્ણન સેલ્ફ-લૂપની Anthropic વાયર-ફૉર્મેટ શાખામાં કોઈ `detail` ફીલ્ડ નથી અને
બંનેમાંથી કોઈપણ ડિફૉલ્ટથી તે પ્રભાવિત થતી નથી.

#### વર્ણન આઉટપુટ મર્યાદા (`modalityBridgeVisionMaxChars`)

| કી                             | ડિફૉલ્ટ | શ્રેણી             |
| ------------------------------ | ------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`     | `0` અથવા 100–50000 |

`0` (ડિફૉલ્ટ)નો અર્થ **કોઈ મર્યાદા નહીં** — `callVisionModel()` દ્વારા
પરત કરાયેલું વર્ણન કોઈ ફેરફાર વિના પસાર થાય છે, જેથી હાલની વર્તણૂક જળવાઈ રહે.
100–50000ની શ્રેણીમાં કોઈપણ મૂલ્ય વર્ણનને પાછું
`[Image N]: <description>` તરીકે જોડવામાં આવે તે પહેલાં `…` પ્રત્યય સાથે કાપે
છે (`VisionBridgeGuardrail.preCall()` in `src/lib/guardrails/visionBridge.ts`).
વિગતોથી ભરપૂર OCR કાર્યો માટે, જેમાં ડાઉનસ્ટ્રીમ મોડલને સંપૂર્ણ ટ્રાન્સક્રિપ્શન
જરૂરી હોય, આ મૂલ્ય વધારો; વધુ લખાણ આપતા વિઝન મોડલ્સનો ટોકન વપરાશ મર્યાદિત
રાખવા માટે તેને ઘટાડો. ડૅશબોર્ડ ફીલ્ડ Vision ટૅબની Advanced પેનલમાં છે
(`modality-bridge-max-chars` in `ModalityBridgeVisionTab.tsx`) અને 1થી 99 વચ્ચેના
કોઈપણ મૂલ્યને વધારીને ન્યૂનતમ 100 કરે છે, જ્યારે સ્પષ્ટ `0`ને યથાવત્ રાખે છે —
`0` પોતે એક માન્ય Zod મૂલ્ય છે
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), તે માત્ર
"સેટ ન કરેલું" ડિફૉલ્ટ નથી.

#### વર્ણન કૅશ (`modalityBridge/bridgeCache.ts`)

વર્ણન આઉટપુટ માટે ઇન-મેમરી LRU + TTL કૅશ, જે સમગ્ર પ્રોસેસમાં શેર થાય છે.
કી = `sha256(imageRef + composedPrompt + configuredBridgeModel)`, જેમાં
લંબાઈ-પ્રીફિક્સ ફ્રેમિંગ છે (ફીલ્ડ સીમાઓ વચ્ચે કોઈ અથડામણ નહીં). મોડલ ઘટક
**કન્ફિગર કરેલું** બ્રિજ મોડલ છે, ખરેખર જવાબ આપનાર મોડલ નહીં —
`callVisionModel` આંતરિક રીતે ફૉલબૅક કરી શકે છે, અને દરેક પ્રયાસ પ્રમાણે કી
બનાવવાથી કૅશ વિખંડિત થઈ જશે. નિષ્ફળ વર્ણનો ક્યારેય કૅશ થતા નથી. સેટિંગ્સ:

| કી                              | ડિફૉલ્ટ | શ્રેણી  |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### રિમોટ ઇમેજ નોર્મલાઇઝેશન (સેલ્ફ-લૂપ વર્ણન/base64 ફેચ)

જ્યારે બ્રિજ પોતે કોઈ **રિમોટ** ઇમેજ ફેચ કરે છે — Anthropic વર્ણન
સેલ્ફ-કૉલ અને claude-વાયર-ફૉર્મેટ base64 રૂપાંતરણ
(`ensureBase64ImagesForClaudeWire`), બંને `visionBridgeHelpers.ts`માંના
`fetchRemoteImageAsDataUri()` મારફતે — ત્યારે પરિણામી data URIને વિઝન-મોડલ
વિનંતીમાં એમ્બેડ કરતાં પહેલાં `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`)માંથી પસાર કરવામાં આવે છે. વધુ પડતી મોટી
ઇમેજોને **2048px લાંબી ધાર** સુધી ડાઉનસ્કેલ કરવામાં આવે છે (OpenAI/Anthropic
સર્વર-સાઇડ પર પહેલેથી લાગુ કરતા રીસાઇઝ મર્યાદા સાથે મેળ ખાતું), જે વિઝન મોડલ
શું જુએ છે તે બદલ્યા વિના અપલોડ બાઇટ્સ/લેટન્સી ઘટાડે છે. રીસાઇઝિંગ `sharp`નો
ઉપયોગ કરે છે, જે ડાયનૅમિક ઇમ્પોર્ટ દ્વારા લોડ થાય છે: જે પ્લેટફૉર્મ પર તેનું
નેટિવ બાઇનરી લોડ થવામાં નિષ્ફળ જાય ત્યાં `normalizeDataUri()` **ક્યારેય
થ્રો કરતું નથી** — તે મૂળ બાઇટ્સને યથાવત્ પસાર કરવા પર ફૉલબૅક કરે છે, જેથી
વર્ણન/base64-રૂપાંતરણ પાથ હંમેશાં કાર્યરત રહે. નૉન-ઇમેજ બાઇટ્સ (એવું ફેચ જેણે
ડિકોડ કરી શકાય તેવી ઇમેજ પરત ન કરી હોય) પણ કોઈ ફેરફાર વિના પસાર કરવામાં આવે
છે. આ નોર્મલાઇઝેશન ફક્ત બ્રિજ તેના પોતાના સેલ્ફ-કૉલ માટે ફેચ કરેલી ઇમેજ સુધી
મર્યાદિત છે — તે કૉલરના કાચા પાસથ્રૂ પેલોડ પર ક્યારેય લાગુ થતું નથી, જે
ફક્ત ઑપ્ટ-ઇન મ્યુટેશનના સિદ્ધાંત (કઠોર નિયમ #20) સાથે સુસંગત છે.

#### પારદર્શિતા હેડર + આંકડા

વર્ણન દ્વારા રૂપાંતરિત પ્રતિસાદોમાં
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
હોય છે (`modalityBridge/bridgeStats.ts`માં `buildModalityBridgeHeader()` દ્વારા
બનાવેલું અને `src/sse/handlers/chatHelpers.ts`માં
`withModalityBridgeHeader()` દ્વારા સ્ટૅમ્પ કરેલું). રીરાઉટ કરેલી વિનંતીઓને
**કોઈ** હેડર મળતું નથી — પેલોડ અસ્પર્શિત હતું અને મોડલ સ્વૅપ પ્રતિસાદ બૉડીના
`model` ફીલ્ડમાં પહેલેથી જ દેખાય છે.

`GET /api/modality-bridge/stats` (મેનેજમેન્ટ ઑથ, `GET /api/settings` જેવું જ સ્તર) `vision`, `audio`, અને `video` માટે ઇન-મેમરી પ્રતિ-મોડાલિટી કાઉન્ટર્સ
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` પરત કરે છે. `averageLatencyMs` તેના
ભાજક તરીકે તમામ પ્રયાસોને નહીં, પરંતુ `latencySamples` ને વાપરે છે; સમયમાપન વિનાનું
ઑપરેશન શૂન્ય-મિલિસેકન્ડનો નકલી નમૂનો બનાવતું નથી. `bridged` સફળ
રૂપાંતરણો માટેનું બૅકવર્ડ-કમ્પેટિબલ ઉપનામ રહે છે; નિષ્ફળ પ્રયાસો તેને વધારતા નથી.
ડિઝાઇન મુજબ, પ્રોસેસ પુનઃપ્રારંભ થાય ત્યારે કાઉન્ટર્સ રીસેટ થાય છે
(ટેલિમેટ્રી, હિસાબકિતાબ નહીં).

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ઑડિયો ઇનપુટ સ્વીકારતું હોવાનું જાણીતું ન હોય એવા ટાર્ગેટ સુધી પહોંચે તે પહેલાં
ઑડિયો ધરાવતી ચૅટ રિક્વેસ્ટ્સને ઇન્ટરસેપ્ટ કરે છે. તે ક્યારેય ચૅટ રિક્વેસ્ટને ફરી રૂટ
કરતું નથી: ઑડિયો ભાગોનું હાલના OpenAI-કમ્પેટિબલ મલ્ટિપાર્ટ એન્ડપોઇન્ટ મારફતે
ટ્રાન્સક્રિપ્શન થાય છે અને પસંદ કરેલું ચૅટ મોડલ ટેક્સ્ટ ટ્રાન્સક્રિપ્ટ્સ સાથે આગળ વધે છે.

પ્રવાહ:

1. `getResolvedModelCapabilities()` દ્વારા `supportsAudio` રિઝૉલ્વ કરો. સ્પષ્ટ
   પ્રોવાઇડર-રજિસ્ટ્રી મેટાડેટાને પ્રથમ પ્રાધાન્ય મળે છે, પછી સ્ટૅટિક મોડલ મેટાડેટાને અને
   ત્યારબાદ સિંક કરેલા `modalities_input` ને. `audio` વિનાની જાહેર કરેલી ઇનપુટ સૂચિ
   `false` છે; ક્ષમતાનો કોઈ પુરાવો ન હોય તો મૂલ્ય `null` રહે છે. `false` અને `null`
   બંને સંયમી બ્રિજને સક્રિય કરે છે, જ્યારે `true` તેને બાયપાસ કરે છે.
2. `modalityBridgeAudio*` સેટિંગ્સ રિઝૉલ્વ કરો અને શેર કરેલા `detectMediaParts()`
   ડિટેક્ટર દ્વારા દરેક મેસેજમાંથી સ્પ્લાઇસ કરી શકાય તેવા ટૉપ-લેવલ ઑડિયો ભાગો કાઢો.
   સમર્થિત વાયર શેપ્સ OpenAI `input_audio`, `audio_url`, અને
   `source.media_type: "audio/*"` છે. રૂટિંગ માટે નેસ્ટેડ ઑડિયો શોધવામાં આવે છે, પરંતુ
   સ્પ્લાઇસ પાથ દ્વારા તેને દૂર કરવામાં આવતો નથી. કાર્ય `modalityBridgeAudioMaxClips`
   દ્વારા મર્યાદિત છે; પછીના ભાગો યથાવત્ રહે છે.
3. કૉન્ફિગર કરેલા `provider/model` ને માન આપો અથવા `selectAudioBridgeModel()` ને
   સ્થિર કૅટલૉગ ક્રમમાં `AUDIO_TRANSCRIPTION_PROVIDERS` માંથી પસાર થઈ, ઉપયોગ કરી શકાય
   તેવા સક્રિય પ્રોવાઇડર ક્રેડેન્શિયલવાળું પ્રથમ મોડલ પસંદ કરવા દો.
4. `callAudioTranscription()` base64/data-URI ઑડિયોને મલ્ટિપાર્ટ `file` માં રૂપાંતરિત
   કરે છે અથવા DNS પિનિંગ અને 25 MB મર્યાદા ધરાવતા ફક્ત-જાહેર આઉટબાઉન્ડ ગાર્ડ મારફતે
   રિમોટ `audio_url` ડાઉનલોડ કરે છે. ત્યારબાદ તે `resolveSelfLoopBearer()` વડે
   પ્રમાણિત કરીને, ફાઇલ અને પસંદ કરેલું મોડલ સ્થાનિક `/v1/audio/transcriptions`
   સેલ્ફ-લૂપ પર POST કરે છે. હાલનો ટ્રાન્સક્રિપ્શન રૂટ સામાન્ય ક્રેડેન્શિયલ લુકઅપ,
   કૂલડાઉન/રેટ-લિમિટ હેન્ડલિંગ અને પ્રોવાઇડર ડિસ્પૅચ કરે છે.
5. સફળ કૉલ્સ તેમના ભાગોને `[Audio N]: <transcript>` વડે બદલે છે. કૉલ્સ
   `Promise.allSettled` સાથે ચાલે છે: કોઈ વ્યક્તિગત નિષ્ફળતા તે મૂળ ઑડિયો ભાગને
   જાળવી રાખે છે (#4012 કરાર). જો દરેક કૉલ નિષ્ફળ જાય અને ટાર્ગેટ માટે
   `supportsAudio === false` સાબિત થયું હોય, તો ભાગો
   `[Audio N]: (unavailable — no STT provider connected)` બને છે (#8430 કરાર).
   અજ્ઞાત ટાર્ગેટ (`null`) માટે, તમામ કૉલ નિષ્ફળ જાય તો પરિણામ યથાવત્ રહે છે.
   ઉપયોગ કરી શકાય તેવું STT ક્રેડેન્શિયલ ન ધરાવતા સાબિત થયેલા ફક્ત-ટેક્સ્ટ ટાર્ગેટને
   નેટવર્ક કૉલ કર્યા વિના એ જ સ્પષ્ટ સ્ટબ મળે છે.

સફળ ટ્રાન્સક્રિપ્ટ્સ પ્રોસેસ-વ્યાપી Modality Bridge LRU/TTL કૅશનો ઉપયોગ કરે છે.
કી ઑડિયો રેફરન્સ, સ્થિર `audio-transcription` ઑપરેશન લેબલ અને પસંદ કરેલા STT
મોડલને સંયોજિત કરે છે; નિષ્ફળતાઓ ક્યારેય કૅશ થતી નથી. ઑડિયો પ્રયાસો શેર કરેલા
`bridged`, `cacheHits`, `failures`, અને `lastUsedAt` કાઉન્ટર્સને અપડેટ કરે છે.
રૂપાંતરિત રિસ્પોન્સમાં
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` હોય છે;
યથાવત્ રિક્વેસ્ટ્સને Audio Bridge સેગમેન્ટ મળતું નથી.

રનટાઇમ સેટિંગ્સ DB-બૅક્ડ અને Zod-વૅલિડેટેડ છે:

| કી                            | ડિફૉલ્ટ | શ્રેણી          |
| ----------------------------- | ------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —               |
| `modalityBridgeAudioModel`    | `""`    | ઑટો અથવા STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10            |

શેર કરેલી કૅશનું નિયંત્રણ `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, અને `modalityBridgeCacheMaxEntries` દ્વારા જ થાય છે.

### વીડિયો બ્રિજ (`videoBridge.ts`, `videoBridgePipeline.ts`)

જાણીતો મૂળ વીડિયો સપોર્ટ ન ધરાવતા લક્ષ્યને કૉલ કરવામાં આવે તે પહેલાં, Chat Completions
`messages` અને Responses API `input` માંના ટોચના-સ્તરના વીડિયો ભાગોને અવરોધે છે.
સપોર્ટેડ સ્વરૂપો `input_video`, `video_url`, `video_source`, HTTPS URLs,
અને `data:video/*;base64,...` ડેટા URIs છે. ટેક્સ્ટમાં રહેલા સાદા ફાઇલનામોને
વીડિયો તરીકે ગણવામાં આવતા નથી.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) વિનંતીનું ટ્રાવર્સલ,
ક્ષમતા/નીતિ તપાસ, પ્રતિ-વિનંતી એકત્રીકરણ અને પ્રતિસાદ પેલોડ સંભાળે છે.
પ્રતિ-વીડિયો કાર્ય — પ્રાપ્તિ, સમગ્ર-પરિણામની કૅશ, ફ્રેમ
ક્રમનું વર્ણન કરવું (જે કૉલર દ્વારા જાહેર કરાયેલી કોઈપણ ઑડિયો ટ્રાન્સક્રિપ્ટને સંયોજિત કરે છે), અને પ્રતિ-પ્રયાસ
મેટ્રિક્સ/રદ્દીકરણ/સફાઈ — `videoBridgePipeline.ts` માંના `processVideoPart` પાછળ
છુપાયેલું છે, જેને `preCall` ના લૂપમાં દરેક વીડિયો ભાગ માટે એક વાર કૉલ કરવામાં આવે છે.
તે મોડ્યુલ સ્પષ્ટ પોર્ટ સીમાઓ `VideoMediaBrokerPort`
(બાઇટ્સ પ્રાપ્ત કરવા અને નમૂના લેવાયેલી ફ્રેમ્સ કાઢવા), `VideoAudioTranscriptionPort`
(કૉલર દ્વારા જાહેર કરાયેલી ઑડિયો ટ્રાન્સક્રિપ્ટને નમૂના લેવાયેલા કૅપ્શન્સ સાથે સંયોજિત કરવા), અને
`VideoDrilldownPort` (ફ્રેમ ડ્રિલ-ડાઉન સ્થાયિત્વ સીમા; હજુ સુધી
`processVideoPart` સાથે જોડાયેલ નથી — હાલમાં માત્ર અલગ `/api/modality-bridge/video/drilldown`
રૂટ ડ્રિલ-ડાઉન એન્ટ્રીઓ લખે છે) પણ વ્યાખ્યાયિત કરે છે.

સાર્વજનિક `/v1` વિનંતી પાથ ક્યારેય સબપ્રોસેસને ઇમ્પોર્ટ કે આમંત્રિત કરતો નથી. રિમોટ
વીડિયો 50 MiB ની મર્યાદા હેઠળ ડાઉનલોડ થાય છે; ઇનલાઇન base64 વીડિયો માટે પ્રતિ-વીડિયો
ડિકોડ કરેલી સાઇઝની રૂઢિચુસ્ત 36 MiB મર્યાદા છે, જેથી મોડલ/મેસેજિસ/ફ્રેમિંગ એન્વલપ
50 MiB ની સાર્વજનિક JSON વિનંતી સ્વીકૃતિ મર્યાદાની અંદર રહી શકે. ફાળવણી પહેલાં ઇનલાઇન
લંબાઈ અને ડિકોડ કરેલી સાઇઝના અંદાજ તપાસવામાં આવે છે. પ્રારંભિક રિમોટ URL અને દરેક
રીડાયરેક્ટ પર HTTPS આવશ્યક છે, જેમાં DNS પિનિંગ સાથેના હાલના
માત્ર-સાર્વજનિક આઉટબાઉન્ડ ગાર્ડનો ઉપયોગ થાય છે. ત્યારબાદ બાઇટ્સ ચોક્કસ આંતરિક
`POST /api/modality-bridge/video/extract` બ્રોકર સીમા પાર કરે છે. તે રૂટ
`LOCAL_ONLY` અને `SPAWN_CAPABLE` બંને છે, માત્ર પ્રતિ-પ્રક્રિયા પ્રમાણિત,
વિશ્વસનીય-લૂપબૅક વિનંતી સ્વીકારે છે, અને ક્યારેય URL, ફાઇલસિસ્ટમ પાથ, એક્ઝિક્યુટેબલ
અથવા આર્ગ્યુમેન્ટ સૂચિ સ્વીકારતો નથી. API બૉડી-સાઇઝ પાઇપલાઇન અને હૅન્ડલરનું ઇન્ક્રિમેન્ટલ બૉડી
રીડર સ્વતંત્ર રીતે 50 MiB ની બ્રોકર ઇનપુટ મર્યાદા લાગુ કરે છે. તેની મર્યાદિત કતાર એક સમયે
એક એક્સ્ટ્રૅક્શન ચલાવે છે, ચાર બાકી જોબ્સને મંજૂરી આપે છે અને બાકી ઇનપુટને
100 MiB સુધી મર્યાદિત કરે છે.

બ્રોકરની અંદર, `ffprobe` ખાનગી લોકલ ફાઇલ વાંચે છે; નિશ્ચિત ફૉર્મેટ
અનુમતિસૂચિ પ્લેલિસ્ટ અને મૅનિફેસ્ટ ફૉર્મેટ્સને બાકાત રાખે છે. મંજૂર MOV-ફૅમિલી
કન્ટેનર્સ માટે, બાહ્ય MOV ડેટા સંદર્ભો ડિફૉલ્ટ રૂપે અક્ષમ રહે છે અને
નિશ્ચિત કમાન્ડ તેમને સક્ષમ કરવાનું પસંદ કરતી નથી. `ffprobe` અને `ffmpeg` બંને
માત્ર-`file` પ્રોટોકૉલ અનુમતિસૂચિ, એક થ્રેડ, નિશ્ચિત આર્ગ્યુમેન્ટ ઍરે, કોઈ શેલ નહીં,
અને `PATH` માંથી ઉકેલાયેલા એક્ઝિક્યુટેબલ્સનો ઉપયોગ કરે છે. જોડાયેલ-ચિત્ર કવર સ્ટ્રીમ્સ
પ્લે કરી શકાય તેવા ઉમેદવારો નથી. પ્લે કરી શકાય તેવા તમામ સ્ટ્રીમ્સે મર્યાદાઓ સંતોષવી આવશ્યક છે, અને
નિર્ધારિત સૌથી નીચા-ઇન્ડેક્સ ફૉલબૅક પહેલાં સ્પષ્ટ ડિફૉલ્ટ સ્ટ્રીમને પ્રાથમિકતા આપવામાં આવે છે.
વીડિયો 600 સેકન્ડ, પ્રતિ પરિમાણ 8,192 પિક્સેલ અને
33,554,432 સ્રોત પિક્સેલ સુધી મર્યાદિત છે. FFmpeg 1–16 મધ્યબિંદુ JPEG ફ્રેમ્સના નમૂના લે છે,
નાના ઇનપુટ્સને અપસ્કેલ કર્યા વિના લાંબી ધારને વધુમાં વધુ 1,024 પિક્સેલ સુધી ઘટાડે છે અને
ક્યારેય URL પ્રાપ્ત કરતું નથી. ડિફૉલ્ટ રૂપે સૅમ્પલિંગ `uniform` છે. વૈકલ્પિક
`scene_aware` અને પ્રાયોગિક `segment_aware` નીતિઓ પહેલેથી માન્ય કરાયેલી લોકલ સ્ટ્રીમ પર
એક વધારાનો નિશ્ચિત FFmpeg પાસ કરે છે, મર્યાદિત
`showinfo` દૃશ્ય ટાઇમસ્ટૅમ્પ્સ પસંદ કરે છે અને ડિટેક્ટર નિષ્ફળતા, સમયસમાપ્તિ,
ખામીયુક્ત આઉટપુટ અથવા ખાલી ઉમેદવાર સેટની સ્થિતિમાં નિર્ધારિત રીતે એ જ
સમાન મધ્યબિંદુઓ પર ફૉલબૅક કરે છે. સેગમેન્ટ-અવેર મોડ માન્ય કરાયેલા
દૃશ્ય અંતરાલોના પ્રમાણમાં મધ્યબિંદુ નમૂનાઓ ફાળવે છે; સેગમેન્ટ-અવેર પુરાવા અને ફૉલબૅક વર્તનની
વિગતો નીચે આપેલી છે. દરેક નીતિમાં પસંદગી પછી 16-ફ્રેમની કડક મર્યાદા
લાગુ થાય છે. જ્યારે સીન-અવેર વિનંતીમાં માત્ર
એક-ફ્રેમનું બજેટ હોય, ત્યારે તે સક્રિય સંપૂર્ણ-વીડિયો અથવા ફોકસ વિન્ડોના સમાન મધ્યબિંદુનો ઉપયોગ કરે છે
અને `policyEffective: uniform` દર્શાવે છે: પસંદ કરેલી એકમાત્ર દૃશ્ય ફ્રેમ
બંને સમયગત છેડાઓને જાળવી શકતી નથી. કૉલર વૈકલ્પિક રીતે
મર્યાદિત ફોકસ વિન્ડો (`start`/`end` સેકન્ડ) આપી શકે છે; સીમાઓને મીડિયાની
અવધિ સુધી મર્યાદિત કરવામાં આવે છે, ઉલટાવેલી અથવા અમર્યાદિત વિન્ડોઝ નકારવામાં આવે છે અને તમામ સૅમ્પલિંગ
નીતિઓ માત્ર સામાન્યકૃત અંતરાલની અંદર જ અમલમાં મૂકવામાં આવે છે. પરિણામી
વિન્ડો સૅમ્પલિંગ મેટાડેટા અને અવિશ્વસનીય વર્ણન
ઉપસર્ગમાં સામેલ કરવામાં આવે છે, જેથી ડાઉનસ્ટ્રીમ મોડલ્સ ફોકસ કરેલા અંશને સંપૂર્ણ
સમયરેખાથી અલગ ઓળખી શકે.

સિમૅન્ટિક કૅપ્શન ફોકસ એક અલગ, સ્પષ્ટ સેટિંગ છે. ડિફૉલ્ટ `full`
વિશ્લેષણ મોડ હાલના ફ્રેમ પ્રૉમ્પ્ટને જાળવે છે અને ક્યારેય વિનંતીનો ટેક્સ્ટ
કૅપ્શન મોડલને ફૉર્વર્ડ કરતો નથી. `focused` મોડમાં, બ્રિજ એ જ Chat અથવા Responses
કન્ટેનરમાંથી માત્ર નવીનતમ બિન-ખાલી, વપરાશકર્તા-લિખિત `text`/`input_text` વાંચે છે,
તેને NFC મુજબ સામાન્યકૃત કરે છે, નિયંત્રણ અક્ષરો અને વ્હાઇટસ્પેસને સંકોચે છે,
અને તેને 500 Unicode કોડ પોઇન્ટ્સ સુધી મર્યાદિત કરે છે. ખાલી પરિણામ ચોક્કસ
`full` પ્રૉમ્પ્ટ પર ફૉલબૅક થાય છે. ઉપયોગી હિન્ટ સમર્પિત
અવિશ્વસનીય-વપરાશકર્તા-સંદર્ભ બ્લૉકમાં JSON તરીકે સિરિયલાઇઝ થાય છે અને તે માત્ર અવલોકન કરી શકાય તેવી વિગતોને પ્રાથમિકતા આપી શકે છે;
તે મીડિયામાં દૃશ્યમાન અથવા શ્રાવ્ય સૂચનાઓનું પાલન ન કરવાની અલગ ચેતવણીને
ઓવરરાઇડ કરી શકતું નથી. ટેક્સ્ચ્યુઅલ ફોકસ ક્યારેય `start`/`end` નો અનુમાન કરતું નથી કે
ટેમ્પોરલ સૅમ્પલરને બદલતું નથી.

#### FU-07 માળખાકીય સેગમેન્ટ પુરાવા

`segment_aware` પહેલેથી માન્ય કરાયેલ સ્થાનિક વિડિયો સ્ટ્રીમ પર એક મર્યાદિત પૂર્વ-વિશ્લેષણ પાસનો ઉપયોગ કરે છે. નિશ્ચિત ફિલ્ટર ચેઇન પહેલાં પહોળાઈને વધુમાં વધુ 320 પિક્સેલ સુધી સ્કેલ કરે છે, દૃશ્ય પરિવર્તનો અને સ્થિર થયેલા અંતરાલો શોધે છે, અને પછી ધૂંધળાશ, સરેરાશ લ્યુમા તથા અવકાશીય/કાલિક માહિતી માટે પ્રતિ સેકન્ડ 1 ફ્રેમના દરે નમૂના લે છે. આ પાસ 600 સંરચનાત્મક નમૂનાઓ, એક FFmpeg/ફિલ્ટર થ્રેડ, સમાન માત્ર-`file` પ્રોટોકોલ અને કન્ટેનર અનુમતિ-સૂચિઓ, 1 MiB પ્રોસેસ-આઉટપુટ મર્યાદા તથા બ્રોકરની સહિયારી રદબાતલ/સમયમર્યાદાની અંદર વધુમાં વધુ 30 સેકન્ડ સુધી મર્યાદિત છે. તે વિનંતીમાંથી ક્યારેય કોઈ કમાન્ડ, ફિલ્ટર, પાથ અથવા URL સ્વીકારતું નથી.

સંરચનાત્મક મૂલ્યો નિર્ધારિત નમૂનાકરણ પુરાવા છે, વિડિયોની અર્થલક્ષી સમજ નથી. તેઓ વિષયો, ક્રિયાઓ, કૅપ્શન, વાણી અથવા વપરાશકર્તાના આશયનું અનુમાન કરતા નથી. દૃશ્ય અને સ્થિરતા સીમાઓ સેગમેન્ટ બનાવે છે; સ્થિરતા આવરણ, ધૂંધળાશ, એક્સપોઝર, અવકાશીય વિગત અને કાલિક પરિવર્તન ફક્ત હાલના 1–16 ફ્રેમના બજેટની ફાળવણીને પ્રભાવિત કરે છે. સંપૂર્ણપણે સ્થિર સેગમેન્ટને વધુમાં વધુ એક ફ્રેમ સુધી મર્યાદિત કરવામાં આવે છે, જ્યારે સ્થિર ન હોય તેવા સેગમેન્ટ બાકીના બજેટ માટે સ્પર્ધા કરે છે. જ્યારે સીમાઓની સંખ્યા ફ્રેમ કરતાં વધુ હોય, ત્યારે સમયરેખાનું સમાન આવરણ જાળવવામાં આવે છે જેથી શરૂઆતના ઝડપી કટ લાંબા અંતિમ સેગમેન્ટને છુપાવી ન શકે. સ્થિરતા સીમાના 1-સેકન્ડના વિશ્લેષણ રિઝોલ્યુશનની અંદર આવેલી દૃશ્ય સીમાઓને એકત્રિત કરવામાં આવે છે.

ગેરહાજર ફિલ્ટર, વિકૃત/ખાલી પુરાવા, ડિટેક્ટરની ભૂલ અથવા મર્યાદિત પૂર્વ-વિશ્લેષણ સમયસમાપ્તિના કિસ્સામાં ચોક્કસ સમાન મધ્યબિંદુ નીતિ પર ખુલ્લી નિષ્ફળતા થાય છે. કૉલર દ્વારા રદબાતલ અથવા બ્રોકરની સમયમર્યાદા ખુલ્લી નિષ્ફળતા કરતી નથી: તે ચાલી રહેલી સબપ્રોસેસને સમાપ્ત કરે છે, ત્યારપછીનું ફ્રેમ નિષ્કર્ષણ અટકાવે છે અને ખાનગી અસ્થાયી ટ્રીને `finally`માં દૂર કરવામાં આવે છે.

`scripts/perf/video-bridge-fu07-eval.ts` ડિડુપ્લિકેશન પછીની કૅપ્શન-કૉલ બચત, ગીચ-ગતિ બજેટ ફાળવણી, ધૂંધળાશ/એક્સપોઝર/SI-TI પુરાવા, લાંબી પૂંછડીવાળા ઝડપી કટ અને ક્રમિક-ફેડ ખોટા હકારાત્મક પરિણામો માટે નિર્ધારિત વાસ્તવિક FFmpeg ફિક્સ્ચર જનરેટ કરે છે. તે પૂર્વ-વિશ્લેષણનો વાસ્તવિક સમય અને જ્યાં `/usr/bin/time` ઉપલબ્ધ હોય ત્યાં ચાઇલ્ડ CPU તથા પીક RSS નોંધે છે. તેની ગુણવત્તા તપાસો માત્ર સંરચનાત્મક ઓરેકલ છે. વાસ્તવિક કૅપ્શન-મોડેલની ગુણવત્તા `HOLD` જ રહે છે, કારણ કે આ હાર્નેસ પાસે અધિકૃત એન્ડપોઇન્ટ અથવા સ્થિર જજ નથી. નાણાકીય બચત પણ `HOLD` જ રહે છે, સિવાય કે `--caption-cost-per-call-usd` પ્રતિ કૉલનો સ્પષ્ટ હકારાત્મક ખર્ચ અંદાજ પૂરો પાડે; સ્ક્રિપ્ટ ક્યારેય કોઈ પણ પરિણામ બનાવટી રીતે ઉત્પન્ન કરતી નથી.

દરેક ફ્રેમ 4 MiB સુધી, બધી કાચી ફ્રેમ મળીને 23 MiB સુધી અને સિરિયલાઇઝ કરાયેલ બ્રોકર પ્રતિસાદ 32 MiB સુધી મર્યાદિત છે. ખાનગી અસ્થાયી ડિરેક્ટરીને `finally`માં દૂર કરવામાં આવે છે. OmniRoute FFmpegને સાથે બંડલ કરતું નથી અને કસ્ટમ એક્ઝિક્યુટેબલ પાથ સ્વીકારતું નથી. કૅપ્શનિંગ પહેલાં, બ્રિજ સંયમિત દૃશ્ય ડિડુપ્લિકેશન પાસ લાગુ કરે છે: દરેક JPEGને 16×16 ગ્રેસ્કેલ બફરમાં ઘટાડવામાં આવે છે અને તેની તુલના ફક્ત છેલ્લે જાળવી રાખેલી ફ્રેમ સાથે કરવામાં આવે છે. એક ફ્રેમથી વધુના વિનંતી કરાયેલા કૅપ્શન બજેટ માટે, નિષ્કર્ષણ તે બજેટથી બમણા સુધીનો અને ક્યારેય 16 ફ્રેમથી વધુ નહીં એવો મર્યાદિત ઉમેદવાર સમૂહ પૂરો પાડે છે. વિનંતી કરેલી મર્યાદા ફક્ત ડિડુપ્લિકેશન પછી લાગુ કરવામાં આવે છે, અને જ્યારે બજેટ ઓછામાં ઓછું બે હોય ત્યારે અંતિમ છટણી દરમિયાન પ્રથમ અને અંતિમ પસંદ કરાયેલા ઉમેદવારોને જાળવી રાખવામાં આવે છે. વર્ઝન ધરાવતી `grayscale-16x16-mean-cells-v2` નીતિ સરેરાશ લ્યુમા ડેલ્ટા અને એવા થંબનેલ સેલના ગુણોત્તરમાંથી મોટા મૂલ્યનો ઉપયોગ કરે છે, જેમનો નોર્મલાઇઝ કરેલો ડેલ્ટા ઓછામાં ઓછો 0.05 હોય. ડુપ્લિકેટ થ્રેશોલ્ડ સ્થિરાંક 0.04 છે, જેને રનટાઇમ સેટિંગ તરીકે રજૂ કરવાને બદલે પૂર્વાનુમાનક્ષમતા માટે પસંદ કરવામાં આવ્યો છે. આ દ્વિતીય ઉચ્ચ-કોન્ટ્રાસ્ટ સંકેત નાની ગતિ અને દૃશ્યમાન-ટેક્સ્ટના એવા ફેરફારોને જાળવે છે, જેને ફક્ત સરેરાશ આધારિત તુલના છુપાવી શકે છે. કમ્પેરેટર અથવા ડિકોડરની ભૂલો ખુલ્લી નિષ્ફળતા કરે છે અને આવરણ જાળવી રાખે છે. આઉટપુટ મેટાડેટા નિષ્કર્ષિત ઉમેદવારો, સફળતાપૂર્વક વપરાયેલી ફ્રેમ અને દૂર કરાયેલા દૃશ્ય ડુપ્લિકેટને અલગ દર્શાવે છે.

સ્પષ્ટ રીતે ચિહ્નિત વિડિયો ભાગ ટાઇમસ્ટેમ્પવાળી કોન્ટેક્ટ શીટની વિનંતી કરી શકે છે. બ્રિજ વધુમાં વધુ 4-કૉલમ, 16-ફ્રેમની JPEG ગ્રિડ બનાવે છે. દરેક 512-પિક્સેલ સેલ તેના સ્રોત ટાઇમસ્ટેમ્પને ઉચ્ચ-કોન્ટ્રાસ્ટવાળા નીચેના પટ્ટામાં અંકિત કરે છે, જ્યારે એ જ ટાઇમસ્ટેમ્પ અનુગામી જોડાણ અને ઑડિટ માટે ટેક્સ્ટ મેટાડેટામાં જળવાયેલા રહે છે. સંપૂર્ણ JPEG 32 MiB સુધી મર્યાદિત રહે છે. જો `sharp` ગ્રિડને ડિકોડ અથવા કમ્પોઝ ન કરી શકે, તો બ્રિજ વ્યક્તિગત JPEG ફ્રેમ પર પાછો ફરે છે; ક્લાયન્ટની રદબાતલ તેમ છતાં શીટ ઑપરેશનમાં પ્રસારિત થાય છે.

પ્રમોશન પુરાવાને કૃત્રિમ કમ્પોઝિશન માઇક્રોબેન્ચમાર્કથી ઇરાદાપૂર્વક અલગ રાખવામાં આવ્યો છે. `scripts/perf/video-bridge-contact-sheet-eval.ts` વાસ્તવિક OpenAI-સુસંગત વિઝન મોડેલો માટે સ્કીમા-વર્ઝન ધરાવતું A/B હાર્નેસ વ્યાખ્યાયિત કરે છે. તે પ્રદાતા દ્વારા જણાવાયેલા ટોકન, એન્ડ-ટુ-એન્ડ વાસ્તવિક વિલંબતા (શીટ કમ્પોઝિશન સહિત), મોડેલ-કૉલની સંખ્યા અને મેનિફેસ્ટ દ્વારા વ્યાખ્યાયિત તથ્ય જાળવણી માપે છે. કાચા મોડેલ પ્રતિસાદ રિપોર્ટમાં લખવામાં આવતા નથી; ફક્ત SHA-256 ડાઇજેસ્ટ અને મેળ ખાતા તથ્ય ID જાળવી રાખવામાં આવે છે. `--execute-real` પસાર કરવામાં ન આવે અને `--model`, `OMNIROUTE_BASE_URL` તથા `OMNIROUTE_API_KEY` કૉન્ફિગર ન કરેલ હોય ત્યાં સુધી હાર્નેસ કોઈ નેટવર્ક અથવા ચૂકવેલ મોડેલ કૉલ કરતું નથી. એ સ્પષ્ટ વાસ્તવિક રન વિના, તેનો મશીન-વાંચનીય નિર્ણય `HOLD` જ રહે છે; માત્ર કૃત્રિમ પેલોડ/કૉલ-સંખ્યા માપ પ્રમોશન પુરાવો નથી.

કૉલર જ્યારે પહેલેથી સુમેળિત ટેક્સ્ટ ધરાવતા હોય ત્યારે સમર્થિત વિડિયો ભાગ સાથે વૈકલ્પિક `transcript.cues` ઍરે જોડી શકે છે. દરેક ક્યૂમાં `text`, તપાસવામાં આવેલી અવધિની અંદરનો સીમિત `start`/`end` અંતરાલ અને અનુમતિ-સૂચિમાં સમાવિષ્ટ `source` (`client`, `embedded` અથવા `audio-bridge`) હોવા આવશ્યક છે; `confidence`નું ડિફૉલ્ટ મૂલ્ય `1` છે અને તે `0` તથા `1` વચ્ચે જ રહેવું જોઈએ. ચોક્કસ ડુપ્લિકેટ ક્યૂને એકમાં સંકુચિત કરવામાં આવે છે. OmniRoute આ મેટાડેટામાંથી ક્યારેય ટ્રાન્સક્રિપ્શન શરૂ કરતું નથી: માન્ય કરાયેલા ક્યૂને સ્રોત, વિશ્વાસ અને અંતરાલ સાથે વર્ણવાયેલા પરિણામમાં કૉપી કરવામાં આવે છે અને ફ્રેમ કૅપ્શનની સાથે અવિશ્વસનીય અવલોકનો તરીકે રેન્ડર કરવામાં આવે છે. અમાન્ય, શ્રેણીની બહારનું અથવા ઉદ્ભવ-માહિતી વિનાનું ટેક્સ્ટ કૅપ્શન સ્ટ્રીમમાં મિશ્રિત કરવાને બદલે નકારવામાં આવે છે. `source` ફીલ્ડ હાલમાં કૉલર દ્વારા જાહેર કરાયેલું છે, સર્વર દ્વારા ચકાસાયેલું નથી: OmniRoute ખાતરી કરે છે કે મૂલ્ય ત્રણ અનુમત સ્ટ્રિંગમાંથી એક છે, પરંતુ `embedded` અથવા `audio-bridge` લેબલ ખરેખર સર્વર-માલિકીના નિષ્કર્ષણમાંથી આવ્યું હતું કે નહીં તેની હજી ક્રિપ્ટોગ્રાફિક પુષ્ટિ કરતું નથી. તે ચકાસણી ઉપલબ્ધ ન થાય ત્યાં સુધી `source`ને અવિશ્વસનીય સંકેત તરીકે ગણો; તેના આધારે અધિકૃતતાના નિર્ણયો ન લો.

પ્રદાન કરી શકે છે. ફ્યુઝન સીમ વિઝ્યુઅલ અને ઑડિયો અવલોકનોને એક જ સમયમર્યાદા
અને અબૉર્ટ સિગ્નલ હેઠળ ચલાવે છે, તેમને સામાન્ય સમયરેખા પર ક્રમબદ્ધ કરે છે,
ચોક્કસ ડુપ્લિકેટ્સને એકમાં સમાવે છે અને માત્ર એક બાજુ સફળ થાય ત્યારે આંશિક
પરિણામની જાણ કરે છે. અમાન્ય `audioTranscript` તે આંશિક પરિણામ સુધી ડિગ્રેડ
થાય છે — વિઝ્યુઅલ વર્ણન જાળવી રાખવામાં આવે છે અને ઑડિયો બ્રાન્ચ સ્વચ્છ કરેલો
નિષ્ફળતા કોડ નોંધે છે — આખા વિડિયોને નિષ્ફળ બનાવવાને બદલે. દરેક બ્રાન્ચની
ઉપલબ્ધતા, આંશિક ફ્લૅગ અને સ્વચ્છ કરેલા નિષ્ફળતા કોડ્સ વર્ણવેલા પરિણામમાં,
ગાર્ડરેલ મેટાડેટા (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), રિઝલ્ટ-કૅશ મેટાડેટા અને બ્રિજ ફ્યુઝન કાઉન્ટર્સમાં
જાળવવામાં આવે છે. ડિફૉલ્ટ Video Bridge પાથ સ્પીચ-ટુ-ટેક્સ્ટને શરૂ કરતો નથી
અથવા મીડિયાની બીજી નકલ ડાઉનલોડ કરતો નથી; તે સ્પષ્ટ ટ્રૅક વિના, તે માત્ર
વિડિયો પૂરતો જ રહે છે.

પ્રિન્સિપલ સુધી મર્યાદિત કરે છે. કૅશ દરેક એન્ટ્રી દીઠ વધુમાં વધુ 16 ડિરાઇવ્ડ

દરેક પ્રિન્સિપલ 16 એન્ટ્રીઓ અને 64 MiB કૅનોનિકલ JPEG ડેટા સુધી મર્યાદિત છે.

ડિસ્કનેક્ટ થવું `499` પરત કરે છે અને નિશ્ચિત બ્રોકર ડેડલાઇન `504` પરત કરે છે. રૂપાંતરિત પ્રતિસાદો
કેન્દ્રીય `x-omniroute-modality-bridge` હેડરમાંથી Vision અથવા Audio સેગમેન્ટ્સ દૂર કર્યા વિના
તેમાં `video->text;model=<visionModel>;parts=<videos>` ઉમેરે છે.

### PII Masker (`piiMasker.ts`)

**બંને** તબક્કાઓ પર ચાલે છે.

- **`preCall`** પેલોડને ક્લોન કરે છે, `system`, `messages`, `input`, અને
  `prompt` (સાદી સ્ટ્રિંગ આઇટમ્સ સહિત)માંથી પસાર થાય છે, અને સ્ટ્રિંગ
  `content`/`text` ફીલ્ડ્સ પર (`@/shared/utils/inputSanitizer`માંથી)
  `processPII()` લાગુ કરે છે. જ્યારે `PII_REDACTION_ENABLED=true` હોય, ત્યારે
  શોધાયેલ PII આઉટબાઉન્ડ પેલોડમાં રીડેક્ટ કરવામાં આવે છે. આ
  `INPUT_SANITIZER_MODE`થી સ્વતંત્ર છે (જે માત્ર પ્રોમ્પ્ટ-ઇન્જેક્શન નીતિને
  નિયંત્રિત કરે છે). જ્યારે રીડેક્શન બંધ હોય, ત્યારે કૉલ કન્ટેન્ટ ફરી લખ્યા
  વિના શોધની સંખ્યાઓ રેકોર્ડ કરે છે.
- **`postCall`** પ્રતિસાદને ડીપ-ક્લોન કરે છે, `sanitizePIIResponse()` તેમજ
  Responses-API-આકારનું માસ્કર (`maskResponsesOutput` — જે
  `output_text` અને `output[].content[].text`ને આવરી લે છે) ચલાવે છે. જો કોઈ
  રીડેક્શન થાય, તો સુધારેલો પ્રતિસાદ મૂળ પ્રતિસાદને બદલે છે.

ગાર્ડરેલ ક્યારેય બ્લૉક કરતું નથી; તે માત્ર ઍનોટેટ (`meta.detections`,
`meta.redacted`) કરે છે અથવા ફરી લખે છે.

### પ્રોમ્પ્ટ ઇન્જેક્શન (`promptInjection.ts`)

વપરાશકર્તા દ્વારા પૂરા પાડવામાં આવેલા કન્ટેન્ટમાં વિરોધી રચનાઓ શોધે છે અને
કૉન્ફિગર કરેલી નીતિ લાગુ કરે છે. વર્તન એન્વાયરમેન્ટ વેરિએબલ્સ અને કન્સ્ટ્રક્ટર
વિકલ્પો દ્વારા સંચાલિત થાય છે:

| સેટિંગ          | એન્વાયરમેન્ટ વેરિએબલ                                                                                  | ડિફૉલ્ટ | અસર                                                                                                                                                                                                                      |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| સક્ષમ           | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | જ્યારે `false` હોય, ત્યારે ગાર્ડરેલ શૉર્ટ-સર્કિટ થાય છે.                                                                                                                                                                 |
| મોડ             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | ઇન્જેક્શન નીતિ: `block`, `warn`, અથવા `log`. (`redact` બૅકવર્ડ સુસંગતતા માટે સ્વીકારવામાં આવે છે, પરંતુ તે ઇન્જેક્શન ટેક્સ્ટને દૂર **કરતું નથી**; રિક્વેસ્ટ PII રીરાઇટ `PII_REDACTION_ENABLED` દ્વારા નિયંત્રિત થાય છે.) |
| બ્લૉક થ્રેશોલ્ડ | `blockThreshold` વિકલ્પ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ઉપનામ `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | બ્લૉક કરવા માટે જરૂરી ન્યૂનતમ ગંભીરતા. ડિફૉલ્ટ પર મધ્યમ ગંભીરતા માત્ર અવલોકન માટે છે.                                                                                                                                    |

**મોડ પ્રિસિડન્સ** (`getMode`): કૉલર `options.mode` →
`INJECTION_GUARD_MODE` **DB ફીચર-ફ્લૅગ ઓવરરાઇડ** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. તેથી ડૅશબોર્ડ ઓવરરાઇડ env vars પર પ્રાધાન્ય મેળવે છે, જેથી Feature
Flags UI ચાલતા ગાર્ડને લાઇવ નિયંત્રિત કરે છે (રીસ્ટાર્ટ વિના). DB રીડ ફેઇલ-સેફ
છે: જો તેમાં ભૂલ થાય, તો ગાર્ડ env-આધારિત વર્તન પર પાછો ફરે છે, અને જ્યારે કોઈ
ઓવરરાઇડ સેટ ન હોય ત્યારે વર્તન માત્ર-env રિઝોલ્યુશન જેવું જ રહે છે.

શોધના સ્રોતો:

1. `@/shared/utils/inputSanitizer`માંથી `sanitizeRequest()` (પાઇપલાઇનમાં અન્યત્ર
   ઉપયોગમાં લેવાતો શેર કરેલો ડિટેક્ટર સેટ).
2. બિલ્ટ-ઇન `DEFAULT_GUARD_PATTERNS` (હાલમાં `system_override_inline` અને
   `markdown_system_block`, બંને `high` ગંભીરતાવાળા).
3. કન્સ્ટ્રક્ટર વિકલ્પો દ્વારા પાસ કરાયેલા વૈકલ્પિક `customPatterns` (સ્ટ્રિંગ્સ,
   regex, અથવા `{ name, pattern, severity }` રેકોર્ડ્સ).

જ્યારે `mode === "block"` હોય **અને** ઓછામાં ઓછી એક શોધ ગંભીરતાના થ્રેશોલ્ડને
પૂર્ણ કરે, ત્યારે `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` પરત કરે છે. `warn`/`log` મોડ્સમાં ગાર્ડરેલ લૉગ
કરે છે પરંતુ કૉલને મંજૂરી આપે છે. રજિસ્ટ્રીમાંથી પસાર થયા વિના પ્રોમ્પ્ટ્સનું
મૂલ્યાંકન કરવાની જરૂર હોય એવા કૉલર્સ માટે શેર કરેલો હેલ્પર
`evaluatePromptInjection()` પણ એક્સપોર્ટ કરવામાં આવે છે.

**સ્કૅન મર્યાદા (v3.8.20):** ડિટેક્ટર જોડાયેલા પ્રોમ્પ્ટ ટેક્સ્ટના માત્ર
**પ્રથમ 16 KB**નું નિરીક્ષણ કરે છે — `src/shared/utils/inputSanitizer.ts`માં
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 બાઇટ્સ). પેટર્ન લૂપ ચલાવતા પહેલાં
`detectInjection()` અને `evaluatePromptInjection()` બંને
`slice(0, MAX_INJECTION_SCAN_BYTES)` કરે છે. ઇન્જેક્શન ડિરેક્ટિવ્સ ઇનપુટની
શરૂઆતની નજીક હોય છે, તેથી આ શોધને નબળી પાડ્યા વિના અનેક-સો-KB પેલોડ્સ પર regex
CPU/GCને મર્યાદિત કરે છે (જુઓ #3932, #4041).

### ક્રેડેન્શિયલ માસ્કર (`credentialMasker.ts`)

ડિફૉલ્ટ ચેઇનમાં સૌથી છેલ્લે (પ્રાથમિકતા `95`) **બંને** તબક્કાઓ પર ચાલે છે.
આઉટબાઉન્ડ પેલોડ (મેસેજ કન્ટેન્ટ, ટૂલ-કૉલ આર્ગ્યુમેન્ટ્સ, ટૂલ પરિણામો) **અને**
પ્રોવાઇડર પ્રતિસાદમાંથી જાણીતા API-key / secret-token પેટર્ન્સ રીડેક્ટ કરે છે,
જેથી પ્રોમ્પ્ટમાં પેસ્ટ કરેલું ક્રેડેન્શિયલ (અથવા ટૂલ પરિણામ દ્વારા પાછું
ઇકો થયેલું) અપસ્ટ્રીમ પ્રોવાઇડર અથવા ક્લાયન્ટ સુધી લીક ન થાય.

- **માત્ર પસંદગીથી સક્ષમ**, PII રિડૅક્શન જેવી જ પ્રણાલી (Hard Rule #20ને સંલગ્ન):
  `settings.credentialRedactionEnabled === true` **અથવા**
  `CREDENTIAL_REDACTION_ENABLED=true` હોય ત્યારે જ સક્ષમ. તે બંધ હોય ત્યારે, guardrail કોઈ કાર્યવાહી કરતું નથી —
  તે ક્યારેય બ્લૉક કરતું નથી અને ક્યારેય ફરીથી લખતું નથી.
- `redactCredentials()` સંપૂર્ણ payload/response ટ્રીમાં (`walkValue()`,
  prototype-pollutionથી સુરક્ષિત, `WeakSet` દ્વારા cycle-safe) ફરે છે અને મેળ ખાતી વસ્તુઓને
  `[REDACTED:<type>]` placeholderથી બદલે છે તથા માત્ર ખરેખર બદલાયેલી branchesને જ
  clone કરે છે.
- `CREDENTIAL_PATTERNS` LLM provider keys (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS tokens (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), payment keys (Stripe, Square), cloud
  keys (AWS access key, Twilio, SendGrid, Mailgun), private keys / JWTs,
  credentials ધરાવતી connection strings (`mongodb://user:pass@...`, વગેરે), અને
  generic `Authorization`/`x-api-key`/`api-key`/`apikey` header-value
  patternને આવરી લે છે. Header જેવા આકાર ધરાવતી keys (`authorization`, `x-api-key`, `api-key`,
  `apikey`) generic text regex દ્વારા નહીં, પરંતુ માળખાકીય રીતે (ફક્ત value,
  `Bearer `/`Basic ` જેવો scheme prefix જાળવીને) રિડૅક્ટ કરવામાં આવે છે.
- આ guardrail ક્યારેય બ્લૉક કરતું નથી; તે માત્ર ફરીથી લખે છે (`modifiedPayload` /
  `modifiedResponse`) અને annotation ઉમેરે છે (`meta.credentialsRedacted`, `meta.count`).

Regression guard: `tests/unit/credential-masker-guardrail.test.ts`.

## મૂળભૂત કરાર (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ચેઇનને તરત જ અટકાવે છે
  message?: string; // અવરોધિત કરતી વખતે દર્શાવવામાં આવે છે
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // વિનંતીને ફરી લખવા માટે preCall દ્વારા પરત કરવામાં આવે છે
  modifiedResponse?: TValue; // પ્રતિસાદને ફરી લખવા માટે postCall દ્વારા પરત કરવામાં આવે છે
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ગાર્ડરેલ `void`, `{}`, અથવા `{ block: false }` પરત કરીને "કોઈ ફેરફાર નહીં"નો સંકેત આપે છે. `modifiedPayload`/`modifiedResponse` પરત કરવાથી ચેઇનમાં આગળના ગાર્ડરેલ્સ તરફ વહેતું મૂલ્ય બદલાઈ જાય છે.
`signal?: AbortSignal` કૉલરની લાઇફસાઇકલને ગાર્ડરેલ્સ સુધી લઈ જાય છે. વિનંતી રદ થવી એ ઇરાદાપૂર્વકનો fail-open અપવાદ છે: મીડિયા બ્રિજ કામ અટકાવે છે અને જે લક્ષ્ય તેને સપોર્ટ કરતું નથી તે જાણીતું હોવા છતાં તેમાં મૂળ મીડિયા પુનઃસ્થાપિત કર્યા વિના ક્લીનઅપ કરે છે.

## રજિસ્ટ્રી (`registry.ts`)

સિંગલટન `guardrailRegistry` નીચેની સુવિધાઓ પ્રદાન કરે છે:

- `register(guardrail)` — ગાર્ડરેલ ઉમેરે છે (અથવા સામાન્યકૃત નામ દ્વારા બદલે છે) અને
  ચઢતા `priority` મુજબ ફરીથી ગોઠવે છે.
- `clear()` / `list()` — વહીવટી સહાયકો.
- `runPreCallHooks(payload, context)` — સક્રિય ગાર્ડરેલ્સ પર ક્રમશઃ ફરે છે, પેલોડને
  `modifiedPayload` મારફતે આગળ ધપાવે છે અને પ્રથમ `block: true` પર અટકે છે.
- `runPostCallHooks(response, context)` — પ્રતિસાદની બાજુએ સમાન પ્રવાહ.
- `resetGuardrailsForTests({ registerDefaults })` — સ્વચ્છ ટેસ્ટ અલગીકરણ માટે સ્ટેટ સાફ કરે છે અને વૈકલ્પિક રીતે
  ડિફૉલ્ટ્સને ફરીથી રજિસ્ટર કરે છે.

બંને રનર્સ `{ blocked, payload|response, results, guardrail?, message? }`
પરત કરે છે, જ્યાં `results` એ `GuardrailExecutionResult` રેકોર્ડ્સની એરે છે, જેમાં
દરેક ગાર્ડરેલ માટેના `blocked`, `skipped`, `modified`, `error`, અને `meta` ફીલ્ડ્સ
સમાવિષ્ટ હોય છે, જે ટ્રેસિંગ માટે ઉપયોગી છે.

### દરેક વિનંતી માટે ગાર્ડરેલ્સ અક્ષમ કરવા

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` વર્તમાન
વિનંતી માટે છોડવામાં આવનાર ગાર્ડરેલ નામોની ડુપ્લિકેટ-રહિત યાદી એકત્રિત કરે છે.
સ્ત્રોતો (બધા વૈકલ્પિક, બધા મર્જ કરવામાં આવે છે):

- `apiKeyInfo.disabledGuardrails`
- વિનંતી બોડીનું `disabledGuardrails` (ટોચના સ્તરે)
- વિનંતી બોડીનું `metadata.disabledGuardrails`
- હેડર `x-omniroute-disabled-guardrails` (અથવા જૂનું
  `x-disabled-guardrails`)

મૂલ્યો સ્ટ્રિંગ્સની એરે અથવા કૉમાથી અલગ કરેલી સ્ટ્રિંગ હોઈ શકે છે; નામોને
લોઅરકેસ kebab-caseમાં સામાન્યકૃત કરવામાં આવે છે (`pii_masker` → `pii-masker`). પરિણામ
`context.disabledGuardrails` મારફતે રજિસ્ટ્રીને આપવામાં આવે છે, જે
મેળ ખાતા ગાર્ડરેલ્સને છોડી દે છે (`results`માં `skipped: true`).

## અમલીકરણ ક્રમ

`src/sse/handlers/chat.ts` અને
`open-sse/handlers/chatCore.ts`માંથી પસાર થતી દરેક વિનંતી માટે:

1. `resolveDisabledGuardrails(...)` API કી, બોડી અને હેડર્સમાંથી સ્કિપ સૂચિ બનાવે છે.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ચડતા પ્રાથમિકતા ક્રમમાં ગાર્ડરેલ્સ ચલાવે છે:
   - અક્ષમ કરેલા ગાર્ડરેલ્સ `skipped` તરીકે નોંધાય છે.
   - દરેક ગાર્ડરેલનું `preCall`, `modifiedPayload` મારફતે પેલોડને ફરી લખી શકે છે.
   - પ્રથમ `block: true` ચેઇનને શોર્ટ-સર્કિટ કરે છે અને હેન્ડલર
     ગાર્ડરેલ અસ્વીકાર પ્રતિસાદ પરત કરે છે.
3. (સંભવિત રીતે ફરી લખાયેલો) પેલોડ કોમ્બો રાઉટિંગ અને અપસ્ટ્રીમ
   ડિસ્પેચમાં જાય છે.
4. પ્રતિસાદ તૈયાર થયા પછી, `guardrailRegistry.runPostCallHooks(...)`
   પ્રતિસાદ પર એ જ ચેઇન ચલાવે છે. અહીં `block: true` અપસ્ટ્રીમ
   પ્રતિસાદને કાઢી નાખે છે.

જે ગાર્ડરેલ્સ અપવાદ ફેંકે છે તે `error: <message>` સાથે નોંધાય છે અને
`logger.warn` મારફતે લૉગ થાય છે, પરંતુ ચેઇન ચાલુ રહે છે — ડિઝાઇન મુજબ ફેઇલ-ઓપન.

બિલ્ટ-ઇન ગાર્ડરેલ્સ દ્વારા વાંચવામાં આવતા એન્વાયર્નમેન્ટ વેરિએબલ્સ:

| વેરિએબલ                               | આના દ્વારા વપરાય છે        | અસર                                                                                                             |
| ------------------------------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | શોધને સંપૂર્ણપણે અક્ષમ કરવા માટે `false` સેટ કરો.                                                               |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | ઇન્જેક્શન નીતિ: `warn`, `block`, અથવા `log`. લેગસી મૂલ્ય `redact` ઇન્જેક્શન ટેક્સ્ટને ફરીથી લખતું નથી.          |

| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | `MODE=block` દ્વારા અસ્વીકાર થવા માટેની ન્યૂનતમ ગંભીરતા: `high` (ડિફૉલ્ટ), `medium`, અથવા `low`.                |

## કસ્ટમ ગાર્ડરેલ્સ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

પગલાં:

1. `BaseGuardrail`ને વિસ્તૃત કરતી `src/lib/guardrails/myGuardrail.ts` બનાવો.
2. `preCall` અને/અથવા `postCall` અમલમાં મૂકો.
3. કાં તો ઇમ્પોર્ટ સમયે નોંધણી કરો (`registerDefaultGuardrails`માંથી પુશ કરો) અથવા
   રનટાઇમ પર `guardrailRegistry.register(...)` કૉલ કરો — રજિસ્ટ્રી સમાન સામાન્યકૃત
   નામ ધરાવતા કોઈપણ અગાઉના ગાર્ડરેલને બદલી નાખે છે.
4. `tests/unit/` હેઠળ પરીક્ષણો ઉમેરો (હાલનાં ઉદાહરણો:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## પરીક્ષણ

જાણીતી સ્થિતિથી શરૂઆત કરવા માટે પરીક્ષણો વચ્ચે `resetGuardrailsForTests()`નો ઉપયોગ કરો.
ખાલી રજિસ્ટ્રીથી શરૂઆત કરવા માટે `{ registerDefaults: false }` પાસ કરો અને
માત્ર પરીક્ષણ હેઠળના ગાર્ડરેલ્સની નોંધણી કરો. Vision Bridge ડિપેન્ડન્સી
ઇન્જેક્શન (`deps.getSettings`, `deps.callVisionModel`) સ્વીકારે છે; Audio Bridge
સેટિંગ્સ, ક્ષમતાઓ, STT મોડેલ પસંદગી, ક્રેડેન્શિયલ તપાસો અને ટ્રાન્સક્રિપ્શન માટે
સમકક્ષ સીમ્સ ઉપલબ્ધ કરાવે છે. તેથી પરીક્ષણો DB અથવા નેટવર્ક ઍક્સેસ વિના બંને
પ્રવાહોને ચકાસી શકે છે.

## ઇન્જેક્શન-ગાર્ડ રૂટ કવરેજ અને રેડ-ટીમ (તબક્કો 8 · બ્લૉક D)

ઇન્જેક્શન-ગાર્ડ (`createInjectionGuard` / `withInjectionGuard`) વપરાશકર્તા પ્રોમ્પ્ટ્સ
સ્વીકારતા તમામ રૂટ્સને આવરી લે છે. તે `INJECTION_GUARD_MODE`નું પાલન કરે છે (ડિફૉલ્ટ
`warn` = ફક્ત લૉગ; `block` = HTTP 400 `SECURITY_001` પરત કરે છે).

| પ્રકાર           | રૂટ્સ                                                                                                                                                | ડિફૉલ્ટ મોડ |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| ટેક્સ્ટ (હાલનું) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| જનરેટિવ          | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| ડેટા             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

ટેક્સ્ટ નિષ્કર્ષણ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`ને આવરી લે છે.

**રેડ-ટીમ (દરરોજ રાત્રે, `nightly-llm-security.yml`):** promptfoo ચકાસે છે કે દરેક રૂટ
`INJECTION_GUARD_MODE=block`માં OWASP-LLM કોર્પસને બ્લૉક કરે છે; garak પ્રોબ્સ ચલાવે છે
(સિક્રેટ વિના સ્કિપ કરે છે). સુસંગતતા માટે `moderations`નો સમાવેશ કરવામાં આવ્યો છે —
બ્લૉક-મોડમાં ઑપરેટર્સ `resolveDisabledGuardrails` મારફતે તેને મુક્તિ આપી શકે છે.

રાત્રિકાલીન વર્કફ્લો (`.github/workflows/nightly-llm-security.yml`, cron + મેન્યુઅલ
ડિસ્પેચ)માં બે જૉબ્સ છે:

- **`promptfoo-guard` (બ્લૉકિંગ)** — `INJECTION_GUARD_MODE=block` સાથે
  `promptfoo eval -c promptfooconfig.yaml` ચલાવે છે. દરેક પ્રતિકૂળ કેસ (દા.ત. "અગાઉની
  તમામ સૂચનાઓ અવગણો…", DAN-શૈલીના જેલબ્રેક્સ) ખાતરી કરે છે કે પ્રતિસાદમાં
  `error.code === "SECURITY_001"` હોય, એટલે કે ગાર્ડે વિનંતીને ખરેખર નકારી હતી.
- **`garak` (સલાહકારી)** — સ્થાનિક OmniRoute ઇન્સ્ટન્સ
  (`http://localhost:20128/v1`) સામે garak `--probes promptinject,dan,leakreplay`
  ચલાવે છે. તે પ્રોવાઇડર સિક્રેટ (`PROMPTFOO_PROVIDER_KEY`) પર આધારિત છે; સિક્રેટ
  ન હોય તો સરળતાથી સ્કિપ કરે છે અને તેની પાછળ `|| true` જોડાયેલું છે, તેથી તે CIને
  નિષ્ફળ કર્યા વિના રિપોર્ટ કરે છે.

ગાર્ડ હેલ્પર (`createInjectionGuard` / `withInjectionGuard`)નું કવરેજ પ્રોમ્પ્ટ ધરાવતા
દરેક `/v1` રૂટ સુધી વિસ્તરે છે; પ્રોમ્પ્ટ ટેક્સ્ટને
`src/shared/utils/inputSanitizer.ts`માંના `extractMessageContents()` દ્વારા
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`માંથી
લેવામાં આવે છે.
