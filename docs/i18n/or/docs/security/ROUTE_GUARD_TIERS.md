## ସାରାଂଶ

ସମସ୍ତ OmniRoute ପରିଚାଳନା API ରୁଟ୍କୁ ତିନୋଟି ସୁରକ୍ଷା
ସ୍ତର ମଧ୍ୟରୁ ଗୋଟିଏରେ ବର୍ଗୀକୃତ କରାଯାଇଛି। ବର୍ଗୀକରଣ ସ୍ଥିର, ଯାହା `src/server/authz/routeGuard.ts`ରେ
ପରିଭାଷିତ ହୋଇଛି, ଏବଂ ଅନ୍ୟ କୌଣସି ପ୍ରମାଣୀକରଣ ଶାଖା ଚାଲିବା ପୂର୍ବରୁ ଏହାର ମୂଲ୍ୟାଙ୍କନ କରାଯାଏ।

## ସ୍ତରଗୁଡ଼ିକ

### ସ୍ତର 1 — LOCAL_ONLY

**ଏହା ଦ୍ୱାରା ବାଧ୍ୟତାମୂଳକ କରାଯାଏ:** `isLocalOnlyPath(path)` → ଲୁପ୍ବ୍ୟାକ୍ ହୋଷ୍ଟ ଯାଞ୍ଚ  
**ବାଇପାସ୍:** ଡିଫଲ୍ଟ ଭାବରେ କିଛି ନାହିଁ। ଅନୁରୋଧରେ `manage` ସ୍କୋପ୍ ଥିବା ଏକ ବୈଧ API କୀ ଥିଲେ, `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ଅନ୍ତର୍ଗତ ପଥଗୁଡ଼ିକ ପାଇଁ ସୀମିତ ବ୍ୟତିକ୍ରମ ରହିଛି ([Manage-scope ବ୍ୟତିକ୍ରମ](#manage-scope-carve-out) ଦେଖନ୍ତୁ)।

ଏହି ରୁଟ୍ଗୁଡ଼ିକ ଚାଇଲ୍ଡ ପ୍ରୋସେସ୍ ସୃଷ୍ଟି କରନ୍ତି କିମ୍ବା ରନ୍ଟାଇମ୍ କୋଡ୍ ନିଷ୍ପାଦନ କରନ୍ତି। ଏଗୁଡ଼ିକୁ ନନ୍-ଲୁପ୍ବ୍ୟାକ୍ ଟ୍ରାଫିକ୍ ପାଇଁ ଉନ୍ମୁକ୍ତ କଲେ, ଏକ ବୈଧ JWT ହାସଲ କରିଥିବା ଆକ୍ରମଣକାରୀ (ଉଦାହରଣ ସ୍ୱରୂପ, Cloudflared/Ngrok ଟନେଲ୍ ମାଧ୍ୟମରେ) ପ୍ରୋସେସ୍ ସୃଷ୍ଟିକୁ ଟ୍ରିଗର୍ କରିପାରିବେ — ଯାହା ଏକ ଜଣାଶୁଣା CVE ଶ୍ରେଣୀ ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj))।

**GHSA-fhh6-4qxv-rpqj କ’ଣ (ଆକ୍ରମଣ ଶ୍ରେଣୀ):** ଏକ ପରିଚାଳନା/ଏଜେଣ୍ଟ ସର୍ଭର୍ ଏପରି ଏକ ଏଣ୍ଡପଏଣ୍ଟକୁ ଉନ୍ମୁକ୍ତ କରେ, ଯାହା ଏକ ସବ୍ପ୍ରୋସେସ୍ (`npm install`, `node`, ଏକ ବ୍ରାଉଜର୍, ଏକ ପ୍ରକ୍ସି, `git`, `tar`, …) ଆରମ୍ଭ କରେ। ଯଦି ସେହି ଏଣ୍ଡପଏଣ୍ଟ ହୋଷ୍ଟ ବାହାରୁ ପହଞ୍ଚଯୋଗ୍ୟ ହୁଏ — କାରଣ ଅପରେଟର୍ OmniRouteକୁ ଏକ nginx/Cloudflare/Tailscale ଟନେଲ୍ ପଛରେ ରଖିଥିଲେ ଏବଂ ଏକ JWT ଲିକ୍ ହୋଇଥିଲା, କିମ୍ବା ପ୍ରମାଣୀକରଣ ଭୁଲ ଭାବରେ ବିନ୍ୟାସ ହୋଇଥିଲା — ତେବେ ଆକ୍ରମଣକାରୀ "ଏକ API କଲ୍ କରିବା"କୁ "ହୋଷ୍ଟରେ ଏକ କମାଣ୍ଡ ଚଲାଇବା"ରେ ପରିଣତ କରନ୍ତି (ଦୂରସ୍ଥ କୋଡ୍ ନିଷ୍ପାଦନ)। OmniRoute ପ୍ରତ୍ୟେକ ପ୍ରୋସେସ୍-ସୃଷ୍ଟି-ସକ୍ଷମ ରୁଟ୍ରେ **କୌଣସି ପ୍ରମାଣୀକରଣ ଯାଞ୍ଚ ପୂର୍ବରୁ, ବିନା ସର୍ତ୍ତରେ ଲୁପ୍ବ୍ୟାକ୍ ହୋଷ୍ଟ ଯାଞ୍ଚ** ବାଧ୍ୟତାମୂଳକ କରି ଏହାକୁ ବନ୍ଦ କରେ: ଟନେଲ୍ ମାଧ୍ୟମରେ ଲିକ୍ ହୋଇଥିବା ଟୋକନ୍ଟି ମଧ୍ୟ ପ୍ରୋସେସ୍ ସୃଷ୍ଟି ପର୍ଯ୍ୟନ୍ତ ପହଞ୍ଚିପାରିବ ନାହିଁ।

**ସମ୍ପୂର୍ଣ୍ଣ LOCAL_ONLY ସେଟ୍।** ପ୍ରାମାଣିକ ଉତ୍ସ ହେଉଛି `src/server/authz/routeGuard.ts`ରେ ଥିବା `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`; ନିମ୍ନରେ ଥିବା ସାରଣୀ ବର୍ତ୍ତମାନର ସ୍ଥିତିକୁ ପ୍ରତିଫଳିତ କରେ। `check-route-guard-membership` ଗେଟ୍ ପ୍ରୋସେସ୍-ସୃଷ୍ଟି-ସକ୍ଷମ ପ୍ରିଫିକ୍ସଗୁଡ଼ିକ ଅଧୀନରେ ଥିବା ପ୍ରତ୍ୟେକ `route.ts`କୁ ତାଲିକାଭୁକ୍ତ କରେ ଏବଂ କୌଣସିଟିକୁ କେବଳ-ସ୍ଥାନୀୟ ଭାବେ ଶ୍ରେଣୀବଦ୍ଧ କରାଯାଇନଥିଲେ CIକୁ ବିଫଳ କରେ।

#### ଅପରେଟର୍ ମାର୍ଗଦର୍ଶନ ଏବଂ ଅଡିଟିଂ

ଯଦି ଆପଣ OmniRouteକୁ ଏକ ରିଭର୍ସ ପ୍ରକ୍ସି କିମ୍ବା ଟନେଲ୍ (nginx, Caddy, Cloudflare

**ପ୍ରମାଣୀକରଣ ଚାଲିବା ପୂର୍ବରୁ** `403 LOCAL_ONLY` ସହିତ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ, ତେଣୁ ଏକ ଲିକ୍ ହୋଇଥିବା JWT
କୌଣସି ସ୍ପନ୍ରେ ପହଞ୍ଚିପାରିବ ନାହିଁ। ଅପରେଟର୍ଙ୍କ ଦୁଇଟି ଦାୟିତ୍ୱ ବାକି ରହେ:

  `X-Forwarded-For: 127.0.0.1` ସେଟ୍ କରିବା, କିମ୍ବା ଉତ୍ସ ଠିକଣାକୁ
  loopback ଭାବେ ପୁନଃଲେଖନ କରୁଥିବା proxy ବ୍ୟବହାର କରିବା, ଏହି ସ୍ତର ବନ୍ଦ କରୁଥିବା ଠିକ୍ ସେହି RCE ଶ୍ରେଣୀକୁ ପୁଣି ଖୋଲିଦିଏ। Proxy ମାଧ୍ୟମରେ
  dashboard/APIକୁ ଉନ୍ମୁକ୍ତ କରନ୍ତୁ — spawn-ସକ୍ଷମ routeଗୁଡ଼ିକୁ କେବେ ନୁହେଁ।

  `isLocalOnlyBypassableByManageScope` runtimeରେ ସେଗୁଡ଼ିକୁ ଅସ୍ୱୀକାର କରେ (ବହୁସ୍ତରୀୟ ସୁରକ୍ଷା),

  `SPAWN_CAPABLE_PREFIXES` array ଦ୍ୱାରା ନୁହେଁ, ବରଂ
  `src/shared/constants/spawnCapablePrefixes.ts`ରେ ଥିବା regex-ଆଧାରିତ `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` ସହାୟକ ଦ୍ୱାରା ଅନ୍ତର୍ଭୁକ୍ତ — ସେଗୁଡ଼ିକୁ ଧରିବା ପାଇଁ flat arrayକୁ
  ସମ୍ପୂର୍ଣ୍ଣ `/api/providers/` prefix ଅନ୍ତର୍ଭୁକ୍ତ କରିବାକୁ ପଡ଼ନ୍ତା, ଯାହା provider CRUD ପାଇଁ
  remote dashboardଗୁଡ଼ିକ ବୈଧ ଭାବେ ବ୍ୟବହାର କରୁଥିବା route treeକୁ ଅତ୍ୟଧିକ ବ୍ୟାପକ କରିଦେବ।

**ପ୍ରବେଶ ଅଡିଟ୍ କରିବା** — host ବାହାରୁ କୌଣସି ଅନୁରୋଧ ଏହି routeଗୁଡ଼ିକରେ ପହଞ୍ଚୁନାହିଁ ବୋଲି ଯାଞ୍ଚ କରିବା ପାଇଁ:

- `/dashboard/settings/security`ରେ **Authorization Inventory** ଖୋଲନ୍ତୁ: ଏହା
  ସକ୍ରିୟ LOCAL_ONLY prefix ତାଲିକା, କେଉଁ prefixଗୁଡ଼ିକ bypass-ଯୋଗ୍ୟ, ଏବଂ compile-time
  spawn-ସକ୍ଷମ ("bypass-ଯୋଗ୍ୟ କରାଯାଇପାରିବ ନାହିଁ") set ପ୍ରଦର୍ଶନ କରେ।
- ଉପରୋକ୍ତ prefixଗୁଡ଼ିକ ସହିତ non-loopback client ଠିକଣା ଯୋଡ଼ି
  ଆପଣଙ୍କ reverse-proxy / access logଗୁଡ଼ିକରେ Grep କରନ୍ତୁ। ଏପରି କୌଣସି hit ଯଦି
  `403 LOCAL_ONLY` ପରିବର୍ତ୍ତେ `200` ଫେରାଇଥାଏ, ତାହେଲେ proxy ପ୍ରକୃତ client IPକୁ ଲୁଚାଉଛି — proxyକୁ ଠିକ୍ କରନ୍ତୁ।
- ଏହି pathଗୁଡ଼ିକ ମଧ୍ୟରୁ କୌଣସି ଗୋଟିଏ ପାଇଁ OmniRouteର logରେ ଥିବା `403 LOCAL_ONLY`ର ଅର୍ଥ
  guardଟି ଉଦ୍ଦେଶ୍ୟ ଅନୁଯାୟୀ କାମ କରୁଛି; ଏହା ଦମନ କରିବାକୁ ଥିବା କୌଣସି ତ୍ରୁଟି ନୁହେଁ।

### ସ୍ତର 2 — ALWAYS_PROTECTED

**ଏହା ଦ୍ୱାରା ବଳବତ୍ତର କରାଯାଏ:** `isAlwaysProtectedPath(path)` → `requireLogin=false` bypassକୁ ଏଡ଼ାଇଦିଏ
**Bypass:** `requireLogin=false` ଥିବାବେଳେ କିଛି ନାହିଁ; JWT ସର୍ବଦା ଆବଶ୍ୟକ

ଏହି routeଗୁଡ଼ିକ ବିନାଶକାରୀ କିମ୍ବା ଅପରିବର୍ତ୍ତନୀୟ। ଏକ "password-ବିହୀନ"
installationରେ ଏଗୁଡ଼ିକୁ ଅନୁମତି ଦେବାର ଅର୍ଥ, ସମାନ LANରେ ଥିବା ଯେକେହି databaseକୁ ସମ୍ପୂର୍ଣ୍ଣ ମିଟାଇପାରିବେ କିମ୍ବା server processକୁ ବନ୍ଦ କରିପାରିବେ।

`/api/settings/obsidian` ଏହାର `/webdav` childକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରେ: `POST`, WebDAV file serviceକୁ —
ଏହି pipeline ବାହାରେ Next.js ପୂର୍ବରୁ custom Node layer ଦ୍ୱାରା ପରିବେଶିତ — caller ଦ୍ୱାରା ଚୟନିତ root ପ୍ରତି ନିର୍ଦ୍ଦେଶ କରେ
ଏବଂ ସଦ୍ୟ ଜାରି ହୋଇଥିବା Basic credentialକୁ ପୁଣି ଫେରାଏ, `DELETE` ସେଗୁଡ଼ିକୁ ପରିବର୍ତ୍ତନ କରେ, ଏବଂ parent `POST`
Obsidian REST API tokenକୁ ସଂରକ୍ଷଣ କରେ। GHSA-62vw କେବଳ `GET` password ପ୍ରକାଶକୁ ଲୁଚାଇଥିଲା; credential ଜାରି କରିବା
ତଥାପି fail-open ସ୍ତରରେ ଥିଲା (GHSA-7pq4-8pvv-rx7r)। `enableObsidianVaultSync()` ଅତିରିକ୍ତ ଭାବେ
data directory ସହିତ ସମାନ, ତାହା ଭିତରେ ଥିବା, କିମ୍ବା ତାହାକୁ ଧାରଣ କରୁଥିବା vaultକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ।

### ନୂତନ installationର bootstrap କେବଳ loopback ପାଇଁ — ପ୍ରକୃତ peer ଦ୍ୱାରା, `Host` ଦ୍ୱାରା ନୁହେଁ

କୌଣସି management password configure ହୋଇନଥିଲେ (ଏବଂ `INITIAL_PASSWORD` ମଧ୍ୟ ନଥିଲେ),
`src/shared/utils/apiAuth.ts`ରେ ଥିବା `isAuthRequired()` ଅଜ୍ଞାତ bootstrapକୁ **କେବଳ loopback peer ପାଇଁ** ଖୋଲା ରଖେ।
ବିଶ୍ୱସ୍ତ peer signalଗୁଡ଼ିକରୁ ଏହି କ୍ରମରେ loopback ନିର୍ଣ୍ଣୟ କରାଯାଏ: token-stamped ପ୍ରକୃତ TCP peer
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, ଯାହା policy ଦେଖେ), pipelineର ନିଜସ୍ୱ
`AUTHZ_HEADER_PEER_LOCALITY` verdict (ଯାହା route handlerଗୁଡ଼ିକ ଦେଖନ୍ତି, କେବଳ
`OMNIROUTE_PEER_STAMP_TOKEN` ସେଟ୍ ଥିବାବେଳେ ବିଶ୍ୱସ୍ତ), କିମ୍ବା direct caller ପାଇଁ ଏକ ପ୍ରକୃତ socket peer। `Host` /
`nextUrl.hostname`କୁ କେବେବି ବିଚାର କରାଯାଏ ନାହିଁ, ଏବଂ ପ୍ରଥମ-password ଲେଖନ
(`POST /api/settings/require-login`) ପ୍ରତ୍ୟେକ network peer ପାଇଁ ଖୋଲା ରହିବା ପରିବର୍ତ୍ତେ ସେହି ସମାନ ସୀମାବଦ୍ଧତା ଅଧୀନରେ ଅଛି
(GHSA-7pq4-8pvv-rx7r)। `managementPolicy` ନିଜ `peerContext` verdictକୁ
ସ୍ପଷ୍ଟ ଭାବରେ ତଳକୁ ପଠାଏ, ତେଣୁ ORIGINAL (strip ପୂର୍ବର) requestର headerଗୁଡ଼ିକ କେବେବି ଏହା ନିର୍ଣ୍ଣୟ କରନ୍ତି ନାହିଁ।

### ସ୍ତର 3 — MANAGEMENT (ଡିଫଲ୍ଟ)

ଅନ୍ୟ ସମସ୍ତ management route। `requireLogin=false`
configure ହୋଇନଥିଲେ authentication ଆବଶ୍ୟକ। CLI tokenଗୁଡ଼ିକ ଏହି routeଗୁଡ଼ିକୁ authenticate କରିପାରିବ (loopback + valid HMAC)।

## ମୂଲ୍ୟାଙ୍କନ କ୍ରମ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → ପରବର୍ତ୍ତୀ ପଦକ୍ଷେପକୁ ଯାଆନ୍ତୁ
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → ଅନୁମତି ଦିଅନ୍ତୁ (management_key)
     → ଅନ୍ୟଥା                                    → 403 LOCAL_ONLY ସହିତ ପ୍ରତ୍ୟାଖ୍ୟାନ କରନ୍ତୁ
  2. isInternalModelSyncRequest(ctx)?
     → ଅନୁମତି ଦିଅନ୍ତୁ (system)
  3. hasValidCliToken(headers)?
     → ଅନୁମତି ଦିଅନ୍ତୁ (cli) [loopback + timingSafeEqual HMAC ଯାଞ୍ଚ]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → ଅନୁମତି ଦିଅନ୍ତୁ (dashboard_session)
     → bypass କରିହେଉ ନଥିବା ପଥରେ manage-scope Bearer?
        → ଅନୁମତି ଦିଅନ୍ତୁ (management_key)
     → 401/403 ସହିତ ପ୍ରତ୍ୟାଖ୍ୟାନ କରନ୍ତୁ
  5. requireLogin=false?
     → ଅନୁମତି ଦିଅନ୍ତୁ (anonymous)
```

ପଦକ୍ଷେପ 1ର manage-scope ଶାଖା ହେଉଛି ଏକମାତ୍ର ପ୍ରମାଣୀକୃତ ପଥ ଯାହା ଏକ
LOCAL_ONLY ରୁଟ୍କୁ ସନ୍ତୁଷ୍ଟ କରିପାରେ; auth-backend ବିଫଳତା ମୋଡ୍ 503 ଫେରାଏ
(403 ନୁହେଁ), ଯାହାଫଳରେ ଏକ ମିଆଦ ଶେଷ ହୋଇଥିବା DB ନିରବରେ "deny"କୁ
ଡାଉନ୍ଗ୍ରେଡ୍ ହୁଏ ନାହିଁ।

## ଏକ ନୂତନ spawn-ସକ୍ଷମ ରୁଟ୍ ଯୋଡ଼ିବା

1. ପଥ ପ୍ରିଫିକ୍ସକୁ `src/server/authz/routeGuard.ts`ର
   `LOCAL_ONLY_API_PREFIXES`ରେ ଯୋଡ଼ନ୍ତୁ
2. `tests/unit/authz/routeGuard.test.ts`ରେ ଏକ ପରୀକ୍ଷା ଯୋଡ଼ନ୍ତୁ, ଯାହା ନୂତନ
   ପ୍ରିଫିକ୍ସ ପାଇଁ `isLocalOnlyPath()` true ଫେରାଉଥିବା ନିଶ୍ଚିତ କରେ
3. **ଏହି ପଦକ୍ଷେପକୁ କେବେବି ଏଡ଼ାନ୍ତୁ ନାହିଁ** — `CLAUDE.md`ର କଠୋର ନିୟମ #15 ଦେଖନ୍ତୁ
4. ନିଷ୍ପତ୍ତି ନିଅନ୍ତୁ: ଏହି ରୁଟ୍ଟି କ’ଣ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`ରେ
   ମଧ୍ୟ ରହିବା ଉଚିତ? ଡିଫଲ୍ଟ ଉତ୍ତର ହେଉଛି **ନା**। କେବଳ ସେତେବେଳେ opt-in କରନ୍ତୁ,
   ଯେତେବେଳେ ରୁଟ୍ଟିକୁ ଏକ manage-scope ଧାରକଙ୍କ ପାଇଁ ଉନ୍ମୁକ୍ତ କରିବା ସୁରକ୍ଷିତ
   (ଅର୍ଥାତ୍, ଏହା ଇଚ୍ଛାମତେ ବ୍ୟବହାରକାରୀ-ନିୟନ୍ତ୍ରିତ କୋଡ୍ spawn କରେ **ନାହିଁ**)।

## ଏକ manage-scope-bypassable ପଥ ଯୋଡ଼ିବା

1. ରୁଟ୍ଟି ବ୍ୟବହାରକାରୀ-ପ୍ରଦତ୍ତ କୋଡ୍ କିମ୍ବା କମାଣ୍ଡ ଚାଲୁ କରେ ନାହିଁ ବୋଲି
   ନିଶ୍ଚିତ କରନ୍ତୁ। ଯଦି କରେ, ଅଟକି ଯାଆନ୍ତୁ — ଏହି ବ୍ୟତିକ୍ରମ ଏଥିପାଇଁ ଉପଯୁକ୍ତ
   ଉପକରଣ ନୁହେଁ।
2. ପ୍ରିଫିକ୍ସକୁ `src/server/authz/routeGuard.ts`ର
   `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`ରେ ଯୋଡ଼ନ୍ତୁ
3. ସମସ୍ତ ଚାରିଟି ଅନୁରୋଧ ରୂପ ପାଇଁ `tests/unit/authz/management-policy.test.ts`ରେ
   କଭରେଜ୍ ଯୋଡ଼ନ୍ତୁ: Bearer ନାହିଁ (403), manage Bearer (ଅନୁମତି), non-manage Bearer
   (403), ଏବଂ manage Bearer ଥିଲେ ମଧ୍ୟ `/api/cli-tools/runtime/*`
   strict-loopback ରହୁଥିବା ପ୍ରତି-ପ୍ରିଫିକ୍ସ ରିଗ୍ରେସନ୍।

| `ALWAYS_PROTECTED_API_PATHS`       | `x-always-protected: true`    | `requireLogin=false` ଥିଲେ ମଧ୍ୟ ପ୍ରମାଣୀକରଣ ଆବଶ୍ୟକ |
| ଆଭ୍ୟନ୍ତରୀଣ admin/debug ରୁଟ୍        | `x-internal: true`            | ଡିଫଲ୍ଟ ଭାବେ /dashboard/api-endpointsରୁ ଲୁକ୍କାୟିତ |
| କିଛି ନୁହେଁ (ସାର୍ବଜନୀନ / ମାନକ auth) | (କୌଣସି ଆନୋଟେସନ୍ ଆବଶ୍ୟକ ନାହିଁ) | ମାନକ `requireLogin`-ନିୟନ୍ତ୍ରିତ ପ୍ରବେଶ            |

### ବୈଧତା ଯାଞ୍ଚ

ଦୁଇଟି ସ୍କ୍ରିପ୍ଟ YAML ଆନୋଟେସନ୍ ଏବଂ `routeGuard.ts` ମଧ୍ୟରେ ସମନ୍ୱୟକୁ
ବାଧ୍ୟତାମୂଳକ କରେ:

- `scripts/check/check-openapi-coverage.mjs` — କଭରେଜ୍ < 99% ହେଲେ ବିଫଳ ହୁଏ
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` କିମ୍ବା
  `x-always-protected` ଆନୋଟେସନ୍ଗୁଡ଼ିକ compile-time କନ୍ଷ୍ଟାଣ୍ଟଠାରୁ ଭିନ୍ନ ହେଲେ ବିଫଳ ହୁଏ

ଉଭୟ ସ୍କ୍ରିପ୍ଟ pre-commit hook ଏବଂ CIରେ ଚାଲେ।

### ଭୁଲ୍ ସକାରାତ୍ମକ ନିୟମ

ଯଦି `routeGuard.ts` କନ୍ଷ୍ଟାଣ୍ଟରେ ନଥିବା ଏକ ରୁଟ୍ରେ `x-always-protected`
କିମ୍ବା `x-loopback-only` ଆନୋଟେଟ୍ କରାଯାଏ, ତେବେ କଭରେଜ୍ ସ୍କ୍ରିପ୍ଟ ବିଫଳ ହୁଏ।
ସମାଧାନ ହେଉଛି ସର୍ବଦା YAMLକୁ `routeGuard.ts` ପ୍ରକୃତରେ ଯାହା ପ୍ରବର୍ତ୍ତନ କରେ
ତାହା ସହିତ ସମନ୍ୱିତ କରିବା — ପ୍ରବର୍ତ୍ତନ ଲଜିକ୍ ମଧ୍ୟ କାର୍ଯ୍ୟକାରୀ ନକରି କେବଳ
`routeGuard.ts`ରେ ରୁଟ୍ ଯୋଡ଼ିବା ନୁହେଁ।
