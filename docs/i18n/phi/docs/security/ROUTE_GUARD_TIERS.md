## Pangkalahatang-ideya

Ang lahat ng ruta ng API sa pamamahala ng OmniRoute ay inuuri sa isa sa tatlong antas ng
proteksiyon. Hindi nagbabago ang pag-uuri, tinutukoy ito sa `src/server/authz/routeGuard.ts`,
at sinusuri bago tumakbo ang anumang iba pang sangay ng awtentikasyon.

## Mga Antas

### Antas 1 — LOCAL_ONLY

**Ipinapatupad ng:** `isLocalOnlyPath(path)` → pagsusuri sa loopback host  
**Pag-bypass:** Wala bilang default. May limitadong eksepsiyon para sa mga path sa
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` kapag may dalang wastong API key ang
kahilingan na may saklaw na `manage` (tingnan ang [Eksepsiyon para sa saklaw na manage](#manage-scope-carve-out)).

Ang mga route na ito ay lumilikha ng mga child process o nagpapatakbo ng runtime
code. Kung ilalantad ang mga ito sa trapikong hindi loopback, maaaring makapagsimula
ng paglikha ng process ang isang attacker na nakakuha ng wastong JWT (hal.,
sa pamamagitan ng Cloudflared/Ngrok tunnel) — isang kilalang uri ng CVE
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Ano ang GHSA-fhh6-4qxv-rpqj (ang uri ng pag-atake):** naglalantad ang isang
management/agent server ng endpoint na naglulunsad ng subprocess (`npm install`,
`node`, browser, proxy, `git`, `tar`, …). Kung naaabot ang endpoint na iyon mula
sa labas ng host — dahil inilagay ng operator ang OmniRoute sa likod ng isang
nginx/Cloudflare/Tailscale tunnel at may tumagas na JWT, o mali ang pagkaka-configure
ng auth — magagawa ng attacker na gawing “mag-call ng API” ang “magpatakbo ng
command sa host” (remote code execution). Pinipigilan ito ng OmniRoute sa pamamagitan
ng walang-kondisyong pagpapatupad ng **pagsusuri sa loopback host bago ang anumang
pagsusuri sa auth**, sa bawat route na may kakayahang lumikha ng process: hindi pa
rin maaabot ng tumagas na token sa pamamagitan ng tunnel ang paglikha ng process.

**Ang kumpletong hanay ng LOCAL_ONLY.** Ang awtoritatibong source ay
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` sa
`src/server/authz/routeGuard.ts`; ipinapakita ng talahanayan sa ibaba ang
kasalukuyang estado. Inililista ng gate na `check-route-guard-membership` ang bawat
`route.ts` sa ilalim ng mga prefix na may kakayahang lumikha ng process at ibinabagsak
ang CI kung may alinmang hindi naklasipika bilang local-only.

#### Pagbubukod para sa manage scope

Ang isang subset ng mga LOCAL_ONLY path ay MAAARI ring ma-access mula sa non-loopback kung at
kung lamang may dalang `Authorization: Bearer <api-key>` ang kahilingan na ang
metadata ay naglalaman ng `manage` scope (o `admin`). Tahasang nililimitahan
ang pagbubukod kada path sa pamamagitan ng `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` upang ang
default para sa anumang bagong LOCAL_ONLY path ay manatiling mahigpit na loopback lamang. Ang mga hindi napatotohanang
kahilingan at mga kahilingang may mga key na walang manage scope ay tinatanggihan pa rin gamit ang
`403 LOCAL_ONLY`.

Sa kasalukuyan, ang tanging prefix na maaaring lampasan ay `/api/mcp/`. Ang `/api/cli-tools/runtime/` at
`/api/services/` ay sadyang hindi isinama dahil maaari silang mag-spawn ng mga arbitraryong
subprocess (`npm install`, `node`), na siyang eksaktong klase ng CVE na
idinisenyong pigilan ng antas na LOCAL_ONLY.

**#7895 — makitid na scope ng `mcp:connect`:** tinatanggap DIN ng pagbubukod para sa `/api/mcp/`
ang isang Bearer key na may makitid na `mcp:connect` scope
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), na sinusuri sa pamamagitan ng
`hasMcpConnectOrManageScope()` sa `src/server/authz/policies/management.ts`.
Saklaw nito ang `/api/mcp/` LAMANG — walang ibinibigay na pahintulot ang `mcp:connect` sa anumang ibang
management route (kabilang ang bawat iba pang LOCAL_ONLY bypass prefix, sakaling may
maidagdag), at sadya itong hindi isinama sa
`MANAGEMENT_API_KEY_SCOPES`. Ang isang key na may `manage`/`admin` ay pumapasa pa rin sa
pagbubukod gaya ng dati; ang `mcp:connect` ay isang alternatibong may mas mababang pribilehiyo
para sa mga remote na tumatawag para lamang sa MCP na hindi dapat mangailangan ng malawak na management access.

| Kahilingan                                            | Path                       | Resulta                    |
| ----------------------------------------------------- | -------------------------- | -------------------------- |
| Non-loopback, walang Bearer                           | `/api/mcp/*`               | 403 LOCAL_ONLY             |
| Non-loopback, Bearer na may `manage` scope            | `/api/mcp/*`               | Payagan                    |
| Non-loopback, Bearer na may `mcp:connect` scope       | `/api/mcp/*`               | Payagan                    |
| Non-loopback, Bearer na walang `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY             |
| Non-loopback, Bearer na may `mcp:connect` scope       | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY             |
| Non-loopback, Bearer na may `manage` scope            | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY             |
| Loopback, mayroon man o walang Bearer                 | anumang LOCAL_ONLY         | Payagan (nakapasa sa gate) |

#### Patnubay sa operator at pag-audit

Kung pinapatakbo mo ang OmniRoute sa likod ng reverse proxy o tunnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), pinoprotektahan pa rin ng loopback check ang mga route sa itaas
na may kakayahang mag-spawn — ang isang kahilingan na ang client address ay non-loopback ay tinatanggihan gamit ang
`403 LOCAL_ONLY` **bago patakbuhin ang auth**, kaya hindi maaabot ng isang na-leak na JWT ang isang spawn. May natitira pang dalawang
responsibilidad ang operator:

- **Huwag "ayusin" ang isang 403 sa pamamagitan ng pagpapanggap na loopback ang client IP.** Ang pagtatakda ng
  `X-Forwarded-For: 127.0.0.1`, o paggamit ng proxy na muling nagsusulat sa source address bilang
  loopback, ay muling nagbubukas sa mismong klase ng RCE na isinasara ng tier na ito. Ilantad ang
  dashboard/API sa pamamagitan ng proxy — huwag kailanman ang mga route na may kakayahang mag-spawn.
- **Panatilihing minimal ang bypass ng manage scope.** Tanging `/api/mcp/` lamang ang maaaring i-bypass, at
  sa pamamagitan lamang ng API key na may `manage` scope. Ang `SPAWN_CAPABLE_PREFIXES` ay hindi kailanman
  maaaring idagdag sa listahan ng bypass — tinatanggihan ng zod schema ang mga ito at
  ipinagbabawal ng `isLocalOnlyBypassableByManageScope` ang mga ito sa runtime (defence-in-depth),
  na siyang ibig sabihin ng dashboard sa "hindi maaaring gawing bypassable". Inaalis din ng runtime
  snapshot loader ang gayong mga entry mula sa nakaimbak na settings row, at ang
  legacy na pag-import ng JSON (`/api/settings/import-json`) ay hindi kailanman nagsusulat ng mga bypass key.
  Ang bawat entry ng `LOCAL_ONLY_API_PREFIXES` ay dapat nasa deny-list o
  nasuri bilang karapat-dapat sa bypass (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Ang mga route na may
  dynamic segment at static path na may kakayahang mag-spawn sa ilalim ng `/api/providers/` (hal. `/login`,
  `/refresh-cursor`) ay saklaw ng kasamang nakabatay sa regex na `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` sa
  `src/shared/constants/spawnCapablePrefixes.ts`, hindi ng patag na
  array na `SPAWN_CAPABLE_PREFIXES` — kakailanganing saklawin ng patag na array ang
  buong prefix na `/api/providers/` upang matukoy ang mga ito, na labis na magpapalawak sa isang route tree
  na lehitimong ginagamit ng mga remote dashboard para sa CRUD ng provider.

**Pag-audit ng access** — upang tiyaking walang umaabot sa mga route na ito mula sa labas ng host:

- Buksan ang **Authorization Inventory** sa `/dashboard/settings/security`: ipinapakita nito ang
  aktuwal na listahan ng prefix ng LOCAL_ONLY, kung aling mga prefix ang maaaring i-bypass, at ang
  compile-time na hanay na may kakayahang mag-spawn ("hindi maaaring gawing bypassable").
- I-grep ang mga log ng iyong reverse proxy / access para sa mga prefix sa itaas na nakapares sa
  isang client address na hindi loopback. Anumang gayong hit na nagbalik ng `200` sa halip na
  `403 LOCAL_ONLY` ay nangangahulugang itinatago ng proxy ang tunay na client IP — ayusin ang proxy.
- Ang isang `403 LOCAL_ONLY` sa mga log ng OmniRoute para sa isa sa mga path na ito ay nangangahulugang
  gumagana ang guard ayon sa nilalayon, hindi ito isang error na dapat pigilan.

### Tier 2 — ALWAYS_PROTECTED

**Ipinapatupad ng:** `isAlwaysProtectedPath(path)` → laktawan ang bypass na `requireLogin=false`
**Bypass:** Wala kapag `requireLogin=false`; palaging kinakailangan ang JWT

Ang mga route na ito ay mapanira o hindi na maibabalik. Ang pagpapahintulot sa mga ito sa isang installation
na "walang password" ay mangangahulugang maaaring burahin ng sinuman sa parehong LAN ang database o patayin ang
proseso ng server.

| Path                                      | Dahilan                                                          |
| ----------------------------------------- | ---------------------------------------------------------------- |
| `/api/shutdown`                           | Tinatapos ang proseso ng server                                  |
| `/api/settings/database`                  | Pag-export, pag-import, at pagbura ng database                   |
| `/api/db-backups`                         | Access sa buong archive ng backup ng database                    |
| `/api/settings/export-json`               | Ine-export ang buong settings blob (kabilang ang mga lihim)      |
| `/api/settings/import-json`               | Pinapalitan ang buong settings blob                              |
| `/api/providers/health-autopilot/actions` | Isinasagawa ang mga pagkilos sa remediation ng autopilot         |
| `/api/settings/obsidian`                  | Lumilikha ng reusable na WebDAV creds para sa anumang vault root |

**Tugon sa paglabag:** `401 Authentication required`

Saklaw ng `/api/settings/obsidian` ang child nitong `/webdav`: itinuturo ng `POST` ang WebDAV file service —
na inihahatid ng custom na Node layer bago ang Next.js, sa labas ng pipeline na ito — sa isang root na pinili ng tumatawag
at ibinabalik ang mga bagong likhang Basic credential, iniikot ng `DELETE` ang mga ito, at iniimbak ng parent na `POST`
ang Obsidian REST API token. Itinago lamang ng GHSA-62vw ang paglalantad ng password sa `GET`; ang pag-isyu ay
nasa fail-open tier pa rin (GHSA-7pq4-8pvv-rx7r). Bukod pa rito, tinatanggihan ng `enableObsidianVaultSync()`
ang vault na mismong data directory, nasa loob nito, o naglalaman nito.

### Ang bootstrap ng bagong installation ay loopback-only — batay sa tunay na peer, hindi sa `Host`

Kapag walang naka-configure na management password (at walang `INITIAL_PASSWORD`), pinananatili ng `isAuthRequired()` sa
`src/shared/utils/apiAuth.ts` na bukas ang anonymous bootstrap **para lamang sa mga loopback peer**.
Tinutukoy ang loopback mula sa mga pinagkakatiwalaang signal ng peer, sa ganitong pagkakasunod-sunod: ang tunay na TCP peer
na may token stamp (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, na siyang nakikita ng policy), ang sariling
hatol ng pipeline na `AUTHZ_HEADER_PEER_LOCALITY` (na siyang nakikita ng mga route handler, pinagkakatiwalaan lamang habang
nakatakda ang `OMNIROUTE_PEER_STAMP_TOKEN`), o isang tunay na socket peer para sa mga direktang tumatawag. Ang `Host` /
`nextUrl.hostname` ay hindi kailanman isinasaalang-alang, at ang pagsulat ng unang password
(`POST /api/settings/require-login`) ay nasa ilalim ng parehong limitasyon sa halip na bukas sa bawat
network peer (GHSA-7pq4-8pvv-rx7r). Tahasang ipinapasa ng `managementPolicy` ang sarili nitong hatol na `peerContext`
pababa, kaya hindi ito kailanman natutukoy ng mga header ng ORIGINAL (bago i-strip) na request.

### Tier 3 — MANAGEMENT (default)

Lahat ng iba pang management route. Kinakailangan ang auth maliban kung naka-configure ang
`requireLogin=false`. Maaaring gamitin ang mga CLI token upang mag-authenticate sa mga route na ito (loopback + wastong HMAC).

## Pagkakasunod-sunod ng pagsusuri

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → magpatuloy
     → non-loopback, manage-scope Bearer
        AT isLocalOnlyBypassableByManageScope    → payagan (management_key)
     → kung hindi                                → tanggihan 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → payagan (system)
  3. hasValidCliToken(headers)?
     → payagan (cli) [loopback + pagsusuri ng HMAC gamit ang timingSafeEqual]
  4. isAlwaysProtectedPath(path) o requireLogin=true?
     → isDashboardSessionAuthenticated?
        → payagan (dashboard_session)
     → manage-scope Bearer sa isang non-bypassable na path?
        → payagan (management_key)
     → tanggihan 401/403
  5. requireLogin=false?
     → payagan (anonymous)
```

Ang sangay na manage-scope sa Hakbang 1 ang tanging authenticated na path na maaaring tumugon sa isang
LOCAL_ONLY na route; nagbabalik ng 503 (hindi 403) ang failure mode ng auth-backend upang hindi
tahimik na bumaba sa "deny" ang isang expired na DB.

## Pagdaragdag ng bagong route na maaaring mag-spawn

1. Idagdag ang path prefix sa `LOCAL_ONLY_API_PREFIXES` sa
   `src/server/authz/routeGuard.ts`
2. Magdagdag ng test sa `tests/unit/authz/routeGuard.test.ts` na nagpapatunay na
   nagbabalik ng true ang `isLocalOnlyPath()` para sa bagong prefix
3. **Huwag kailanman laktawan ang hakbang na ito** — tingnan ang Mahigpit na Panuntunan #15 sa `CLAUDE.md`
4. Magpasya: kabilang DIN ba ang route na ito sa `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Ang default na sagot ay **hindi**. Mag-opt in lamang kapag ligtas na ilantad ang route sa isang
   may hawak ng manage-scope (ibig sabihin, HINDI ito nag-i-spawn ng arbitraryong code na kontrolado ng user).

## Pagdaragdag ng path na maaaring i-bypass ng manage-scope

1. Kumpirmahing hindi nagpapatupad ang route ng code o command na ibinigay ng user. Kung
   nagpapatupad ito, huminto — hindi tamang kasangkapan ang pagbubukod na ito.
2. Idagdag ang prefix sa `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` sa
   `src/server/authz/routeGuard.ts`
3. Magdagdag ng coverage sa `tests/unit/authz/management-policy.test.ts` para sa lahat ng apat na
   anyo ng request: walang Bearer (403), manage Bearer (payagan), non-manage Bearer
   (403), at ang regression sa bawat prefix na tinitiyak na nananatiling
   strict-loopback ang `/api/cli-tools/runtime/*` kahit may manage Bearer.

## Pagdodokumento ng mga Security Tier sa OpenAPI

Kapag nagdaragdag ng bagong route sa `docs/openapi.yaml`, ilapat ang kaukulang
vendor extension kung inuri ng `routeGuard.ts` ang route:

| Klasipikasyon sa routeGuard.ts      | YAML annotation                  | Pagpapatupad                                          |
| ----------------------------------- | -------------------------------- | ----------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`           | `x-loopback-only: true`          | Walang kondisyong bina-block mula sa non-loopback     |
| `ALWAYS_PROTECTED_API_PATHS`        | `x-always-protected: true`       | Kinakailangan ang auth kahit may `requireLogin=false` |
| Internal na admin/debug route       | `x-internal: true`               | Nakatago sa /dashboard/api-endpoints bilang default   |
| Wala (pampubliko / karaniwang auth) | (walang annotation na kailangan) | Karaniwang access na kinokontrol ng `requireLogin`    |

### Pagpapatunay

Dalawang script ang nagpapatupad ng pagkakapare-pareho sa pagitan ng mga YAML annotation at `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — mabibigo kung < 99% ang coverage
- `scripts/check/check-openapi-security-tiers.mjs` — mabibigo kung naiiba ang mga annotation na `x-loopback-only` o
  `x-always-protected` sa mga compile-time constant

Parehong tumatakbo ang dalawang script sa pre-commit hook at sa CI.

### Panuntunan sa False Positive

Kung inilagay ang annotation na `x-always-protected` o `x-loopback-only` sa isang route na HINDI nasa
constant ng `routeGuard.ts`, mabibigo ang coverage script. Ang tamang pag-aayos ay palaging ihanay ang
YAML sa kung ano ang aktuwal na ipinapatupad ng `routeGuard.ts` — hindi ang pagdaragdag ng mga route sa `routeGuard.ts`
nang hindi rin ipinapatupad ang enforcement logic.
