## ទិដ្ឋភាពទូទៅ

ផ្លូវទាំងអស់នៃ API គ្រប់គ្រង OmniRoute ត្រូវបានចាត់ថ្នាក់ជាកម្រិតការពារ
មួយក្នុងចំណោមបី។ ការចាត់ថ្នាក់នេះមានលក្ខណៈថេរ ដែលបានកំណត់នៅក្នុង `src/server/authz/routeGuard.ts`
ហើយត្រូវបានវាយតម្លៃ មុនពេលសាខាផ្ទៀងផ្ទាត់អត្តសញ្ញាណផ្សេងទៀតដំណើរការ។

## កម្រិត

### កម្រិត 1 — LOCAL_ONLY

**ត្រូវបានអនុវត្តដោយ៖** `isLocalOnlyPath(path)` → ការត្រួតពិនិត្យម៉ាស៊ីន loopback  
**ការរំលង៖** តាមលំនាំដើម មិនមានទេ។ មានការលើកលែងក្នុងវិសាលភាពតូចចង្អៀតសម្រាប់ផ្លូវនៅក្នុង
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` នៅពេលសំណើមាន API key ត្រឹមត្រូវ
ដែលមានវិសាលភាព `manage` (សូមមើល [ការលើកលែងសម្រាប់វិសាលភាព Manage](#manage-scope-carve-out))។

Route ទាំងនេះបង្កើតដំណើរការរង ឬប្រតិបត្តិកូដ runtime។ ការបើកឱ្យចរាចរណ៍
ដែលមិនមែនជា loopback ចូលប្រើពួកវា អាចអនុញ្ញាតឱ្យអ្នកវាយប្រហារដែលទទួលបាន JWT ត្រឹមត្រូវ (ឧ.
តាមរយៈ tunnel របស់ Cloudflared/Ngrok) បង្កឱ្យមានការបង្កើតដំណើរការ — ដែលជា
ប្រភេទ CVE ដែលគេស្គាល់រួចមកហើយ
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj))។

**អ្វីដែល GHSA-fhh6-4qxv-rpqj ជា (ប្រភេទនៃការវាយប្រហារ)៖** ម៉ាស៊ីនមេគ្រប់គ្រង/ភ្នាក់ងារ
បើកឱ្យប្រើ endpoint មួយដែលដំណើរការ subprocess (`npm install`, `node`, កម្មវិធីរុករក,
proxy, `git`, `tar`, …)។ ប្រសិនបើ endpoint នោះអាចចូលប្រើបានពីខាងក្រៅម៉ាស៊ីន — ដោយសារ
ប្រតិបត្តិករបានដាក់ OmniRoute នៅពីក្រោយ tunnel របស់ nginx/Cloudflare/Tailscale ហើយ JWT
បានលេចធ្លាយ ឬការផ្ទៀងផ្ទាត់អត្តសញ្ញាណត្រូវបានកំណត់រចនាសម្ព័ន្ធមិនត្រឹមត្រូវ — អ្នកវាយប្រហារអាចបំប្លែង «ការហៅ API» ទៅជា «ការដំណើរការ
command នៅលើម៉ាស៊ីន» (ការប្រតិបត្តិកូដពីចម្ងាយ)។ OmniRoute បិទចន្លោះនេះដោយអនុវត្ត
**ការត្រួតពិនិត្យម៉ាស៊ីន loopback ដោយគ្មានលក្ខខណ្ឌ មុនការត្រួតពិនិត្យការផ្ទៀងផ្ទាត់អត្តសញ្ញាណណាមួយ** លើគ្រប់
route ដែលអាចបង្កើតដំណើរការ៖ token ដែលលេចធ្លាយតាម tunnel នៅតែមិនអាចចូលដល់ការបង្កើតដំណើរការបានទេ។

**សំណុំ LOCAL_ONLY ពេញលេញ។** ប្រភពយោងផ្លូវការគឺ
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` នៅក្នុង
`src/server/authz/routeGuard.ts`; តារាងខាងក្រោមឆ្លុះបញ្ចាំងពីស្ថានភាពបច្ចុប្បន្ន។ Gate
`check-route-guard-membership` រាយបញ្ជីរាល់ `route.ts` នៅក្រោម
prefix ដែលអាចបង្កើតដំណើរការ ហើយធ្វើឱ្យ CI បរាជ័យ ប្រសិនបើមាន route ណាមួយមិនត្រូវបានចាត់ថ្នាក់ជា local-only។

#### ការណែនាំសម្រាប់ប្រតិបត្តិករ និងការធ្វើសវនកម្ម

- `403 LOCAL_ONLY` ក្នុងកំណត់ហេតុរបស់ OmniRoute សម្រាប់ path មួយក្នុងចំណោម path ទាំងនេះ មានន័យថា guard
  កំពុងដំណើរការតាមការរំពឹងទុក មិនមែនជាកំហុសដែលត្រូវលាក់បំបាត់ទេ។

### កម្រិត 2 — ALWAYS_PROTECTED

**អនុវត្តដោយ៖** `isAlwaysProtectedPath(path)` → រំលង bypass `requireLogin=false`
**Bypass៖** គ្មាន នៅពេល `requireLogin=false`; តែងតែតម្រូវឱ្យមាន JWT

Route ទាំងនេះមានលក្ខណៈបំផ្លិចបំផ្លាញ ឬមិនអាចត្រឡប់ក្រោយបាន។ ការអនុញ្ញាតឱ្យប្រើពួកវាក្នុងការដំឡើង

### Bootstrap សម្រាប់ការដំឡើងថ្មីអនុញ្ញាតតែ loopback ប៉ុណ្ណោះ — ដោយផ្អែកលើ peer ពិតប្រាកដ មិនមែន `Host`

នៅពេលមិនទាន់បានកំណត់ពាក្យសម្ងាត់គ្រប់គ្រង (និងគ្មាន `INITIAL_PASSWORD`) `isAuthRequired()` នៅក្នុង
`src/shared/utils/apiAuth.ts` ទុកឱ្យ bootstrap អនាមិកបើក **សម្រាប់តែ loopback peer ប៉ុណ្ណោះ**។
Loopback ត្រូវបានសម្រេចពីសញ្ញា peer ដែលទុកចិត្តបាន តាមលំដាប់៖ TCP peer ពិតប្រាកដដែលបានបោះត្រា token
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER` ដែល policy មើលឃើញ), សេចក្ដីសម្រេច
`AUTHZ_HEADER_PEER_LOCALITY` របស់ pipeline ផ្ទាល់ (ដែល route handler មើលឃើញ និងត្រូវបានទុកចិត្តតែខណៈពេល
`OMNIROUTE_PEER_STAMP_TOKEN` ត្រូវបានកំណត់) ឬ socket peer ពិតប្រាកដសម្រាប់អ្នកហៅដោយផ្ទាល់។ `Host` /
`nextUrl.hostname` មិនដែលត្រូវបានយកមកពិនិត្យទេ ហើយការសរសេរពាក្យសម្ងាត់ដំបូង
(`POST /api/settings/require-login`) ស្ថិតនៅក្រោមលក្ខខណ្ឌដូចគ្នា ជំនួសឱ្យការបើកចំហដល់គ្រប់
network peer (GHSA-7pq4-8pvv-rx7r)។ `managementPolicy` បញ្ជូនសេចក្ដីសម្រេច `peerContext` ផ្ទាល់របស់វា
ចុះក្រោមយ៉ាងច្បាស់ ដូច្នេះ header របស់ request ដើម (មុនពេល strip) មិនអាចសម្រេចវាបានទេ។

### កម្រិត 3 — MANAGEMENT (លំនាំដើម)

Route គ្រប់គ្រងផ្សេងទៀតទាំងអស់។ តម្រូវឱ្យមានការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ លុះត្រាតែបានកំណត់
`requireLogin=false`។ CLI token អាចផ្ទៀងផ្ទាត់អត្តសញ្ញាណលើ route ទាំងនេះបាន (loopback + HMAC ត្រឹមត្រូវ)។

## លំដាប់នៃការវាយតម្លៃ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → fall through
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → allow (management_key)
     → otherwise                                  → reject 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → allow (system)
  3. hasValidCliToken(headers)?
     → allow (cli) [loopback + timingSafeEqual HMAC check]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → allow (dashboard_session)
     → manage-scope Bearer on a non-bypassable path?
        → allow (management_key)
     → reject 401/403
  5. requireLogin=false?
     → allow (anonymous)
```

សាខា manage-scope ក្នុងជំហានទី 1 គឺជាផ្លូវដែលបានផ្ទៀងផ្ទាត់អត្តសញ្ញាណតែមួយគត់ ដែលអាចបំពេញលក្ខខណ្ឌសម្រាប់ route ប្រភេទ
LOCAL_ONLY បាន។ ក្នុងករណី auth-backend បរាជ័យ វានឹងត្រឡប់ 503 (មិនមែន 403 ទេ) ដូច្នេះ
DB ដែលផុតកំណត់នឹងមិនបន្ទាបស្ថានភាពដោយស្ងៀមស្ងាត់ទៅជា "deny" ឡើយ។

## ការបន្ថែម route ថ្មីដែលអាច spawn បាន

1. បន្ថែមបុព្វបទ path ទៅ `LOCAL_ONLY_API_PREFIXES` ក្នុង
   `src/server/authz/routeGuard.ts`
2. បន្ថែមតេស្តមួយក្នុង `tests/unit/authz/routeGuard.test.ts` ដើម្បីអះអាងថា
   `isLocalOnlyPath()` ត្រឡប់ true សម្រាប់បុព្វបទថ្មី
3. **កុំរំលងជំហាននេះជាដាច់ខាត** — សូមមើល Hard Rule #15 ក្នុង `CLAUDE.md`
4. សម្រេចថា៖ តើ route នេះក៏គួរស្ថិតក្នុង `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ដែរឬទេ?
   ចម្លើយលំនាំដើមគឺ **ទេ**។ ជ្រើសចូលតែក្នុងករណីដែល route នោះមានសុវត្ថិភាពសម្រាប់បើកឱ្យ
   អ្នកកាន់ manage-scope ចូលប្រើប៉ុណ្ណោះ (មានន័យថា វាមិន spawn កូដដែលគ្រប់គ្រងដោយអ្នកប្រើតាមអំពើចិត្តឡើយ)។

## ការបន្ថែម path ដែលអាចរំលងតាម manage-scope បាន

1. បញ្ជាក់ថា route មិនប្រតិបត្តិកូដ ឬ command ដែលផ្តល់ដោយអ្នកប្រើទេ។ ប្រសិនបើវា
   ធ្វើដូច្នោះ សូមឈប់ — ករណីលើកលែងនេះមិនមែនជាឧបករណ៍ត្រឹមត្រូវឡើយ។
2. បន្ថែមបុព្វបទទៅចុងបញ្ជី `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ក្នុង
   `src/server/authz/routeGuard.ts`
3. បន្ថែមការគ្របដណ្តប់ក្នុង `tests/unit/authz/management-policy.test.ts` សម្រាប់ទម្រង់
   request ទាំងបួន៖ គ្មាន Bearer (403), manage Bearer (អនុញ្ញាត), non-manage Bearer
   (403) និង regression តាមបុព្វបទ ដើម្បីធានាថា `/api/cli-tools/runtime/*` នៅតែ
   ទាមទារ loopback យ៉ាងតឹងរ៉ឹង ទោះបីមាន manage Bearer ក៏ដោយ។
