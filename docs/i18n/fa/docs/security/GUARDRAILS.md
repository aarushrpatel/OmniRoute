> **آخرین بهروزرسانی:** 2026-08-29 — v3.8.51 (منشأ رونوشت Video Bridge توسط فراخواننده اعلام میشود،
> اما هنوز در سمت سرور تأیید نمیشود — مطابق #11661 شفافسازی شد)

گاردریلها ایمنی، خطمشیها و تبدیلهای محتوا را در مرز میان
OmniRoute و ارائهدهندگان بالادستی اعمال میکنند. هر گاردریل میتواند محتوای درخواست (`preCall`) و
پاسخهای بالادستی (`postCall`) را بررسی کند (و بهصورت اختیاری رد، تبدیل یا حاشیهنویسی کند).

سیستم از نوع **fail-open** است: اگر یک گاردریل هنگام اجرا خطا ایجاد کند، رجیستری
خطا را ثبت میکند و بهجای ناموفقکردن درخواست، اجرای گاردریل بعدی را ادامه میدهد.
مسدودسازی همیشه یک تصمیم صریح (`block: true`) است، نه یک اتفاق ناخواسته.

## گاردریلهای داخلی

رجیستری هنگام import، شش گاردریل را بهترتیب اولویت بهطور خودکار بارگذاری میکند
(`registry.ts` → `registerDefaultGuardrails()` را ببینید):

| اولویت | نام                 | مرحله(ها)      | فایل                  |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

اعداد اولویت پایینتر **زودتر** اجرا میشوند.

### پل بینایی (`visionBridge.ts`) — پل وجهی PR-1

درخواستهای حاوی تصویر را که برای **مدلهای فاقد قابلیت بینایی** ارسال شدهاند رهگیری میکند و یا
کل درخواست را به یک مدل دارای قابلیت بینایی هدایت میکند، یا پیش از
فراخوانی بالادستی، بخشهای تصویری را با توضیحات متنی تولیدشده توسط یک مدل بینایی قابلپیکربندی
جایگزین میکند. این کار به ارائهدهندگان صرفاً متنی امکان میدهد payloadهای
چندوجهی را بهصورت شفاف مدیریت کنند.

جریان:

1. اگر مدل مقصد از قبل از قابلیت بینایی پشتیبانی میکند، از پردازش صرفنظر کنید (مگر اینکه در
   فهرست پل اجباری `isVisionBridgeForcedModel` قرار داشته باشد).
2. بخشهای تصویری را از طریق `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`) استخراج کنید؛ این تابع پردازش را به **تشخیصدهنده یکپارچه رسانه**
   یعنی `detectMediaParts()` در `open-sse/utils/mediaParts.ts` واگذار میکند — تنها
   منبع حقیقت مشترک با فیلتر سازگاری combo.
   استخراج فقط برای بخشهای سطح بالایی مجاز است که شکل آنها بهگونهای باشد که
   `replaceImageParts` بتواند دوباره آنها را درج کند (قرارداد extract↔replace):
   `image_url` در OpenAI، مقدار base64 در Anthropic با `source.type:"base64"`، آدرس URL
   در Anthropic با `source.type:"url"` و `input_image` در Responses API. موارد تودرتو و
   شکلهایی که صرفاً نقش نشانگر دارند، متعلق به فیلتر combo هستند و هرگز استخراج نمیشوند.
   اگر موردی پیدا نشد، از پردازش صرفنظر کنید.
3. پیکربندی زمان اجرا را از طریق `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`) تعیین کنید: کلیدهای جدید تنظیمات
   `modalityBridge*` اولویت دارند؛ کلیدهای قدیمی `visionBridge*` همچنان بهعنوان یک
   **گزینه بازگشت یکچرخهای** (بازه rollback) باقی میمانند. وقتی پل غیرفعال است، پیش از هرگونه
   پیمایش رسانهای از پردازش صرفنظر کنید.
4. انتخابگر حالت (`modalityBridgeVisionMode`، جدول زیر را ببینید) بین
   هدایت مجدد و توصیف تصمیم میگیرد. هدایت مجدد، `modifiedPayload` را برمیگرداند که در آن فقط
   `model` تعویض شده است، بههمراه متادیتای `{ rerouted, fromModel, toModel, imagesKept }`.
5. مسیر توصیف: تعداد تصاویر را به `maxImages` محدود میکند، prompt آگاه از وظیفه را میسازد،
   cache توصیف را بررسی میکند، مدل بینایی را **بهصورت موازی**
   (`Promise.allSettled`) فراخوانی میکند و بخشهای متنی `[Image N]: <description>` را
   بهجای تصاویر درج میکند. توصیف ناموفق مقدار `null` تولید میکند و بخش تصویری اصلی
   **حفظ میشود** (#4012) — بهجز در مسیر توصیف combo، وقتی همه
   توصیفها ناموفق باشند؛ در این حالت، یک upstream تأییدشده فاقد قابلیت بینایی بهجای تصویر
   stub با متن `(unavailable — no vision-capable provider connected)` دریافت میکند (#8430).
6. `modifiedPayload` را بههمراه متادیتا (`imagesProcessed`، `descriptions`،
   `processingTimeMs`، `visionModel`) برگردانید.

#### انتخابگر حالت (`modalityBridgeVisionMode`)

| حالت       | پیشفرض | رفتار                                                                                                                                                                                                                                                                |
| ---------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔      | روش اکتشافی قدیمی، بدون تغییر (#6640/#7204): مدلهای غیر combo/`auto/` به بهترین مدل بینایی هدایت میشوند، مگر اینکه مدل اصلی از قبل اعتبارنامههای قابلاستفاده داشته باشد (در این صورت توصیف انجام میشود)؛ مقصدهای combo همیشه توصیف میشوند.                           |
| `describe` |        | همیشه توصیف میکند — بلوک هدایت مجدد بهطور کامل نادیده گرفته میشود؛ مدل انتخابشده توسط کاربر همیشه پاسخ میدهد.                                                                                                                                                        |
| `reroute`  |        | هدایت مجدد اجباری: گارد حفظ مدل دارای اعتبارنامه دور زده میشود. گارد اعتبارنامه مقصد **هدایت مجدد** همچنان اعمال میشود — وقتی هیچ مقصد بینایی قابلاستفادهای وجود نداشته باشد، درخواست به مسیر توصیف میرود تا تصاویر خام هرگز به یک backend صرفاً متنی نرسند (#8430). |

حالتهای اجباری، **پیش از** اجرای روش اکتشافی خودکار، آن را short-circuit میکنند؛ رفتار `auto`
از نظر بایتبهبایت با گاردریل پیش از PR-1 یکسان است.

#### محدوده کلید API (`visionBridgeKeyScope.ts`)

وقتی کلید API فراخواننده، `allowedConnections`، استخرهای سهمیه
(`allowedQuotas`) یا مدلها (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) را محدود میکند، پل فقط
مدلهای هدایت مجدد و توصیفی را انتخاب میکند که کلید اجازه استفاده از آنها را دارد و فقط از اتصالهایی
استفاده میکند که برای کلید مجاز هستند. سپس فراخوانی توصیف همیشه از self-loop متعلق به
OmniRoute و با header‏ `x-omniroute-self-loop-key-id` عبور میکند تا درخواست chat دریافتکننده،
سیاست اتصال و مدل آن کلید را دوباره اعمال کند. `enforceApiKeyPolicy()`
آن header را تنها همراه با bearer مربوط به self-loop میپذیرد؛ بنابراین فقط میتواند
دسترسی را محدودتر کند و شناسهای که resolve نشود رد خواهد شد.

اگر هیچ مدل بینایی برای کلید مجاز نباشد، مسیر توصیف کنار میرود و
درخواست بدون تغییر عبور میکند؛ همان رفتار fail-open که برای گاردریل غیرفعال وجود دارد
(متادیتای `{ skipped: true, reason: "no_permitted_vision_model" }`).
درخواستهای بدون کلید و کلیدهای فاقد این محدودیتها دقیقاً مانند قبل
رفتار میکنند.

#### prompt توصیف آگاه از وظیفه (`modalityBridgeVisionTaskAware`)

پیشفرض **true** است. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) متن **آخرین پیام کاربر** را (با کوتاهسازی تا 500 نویسه) به پرامپت پایهٔ توصیف اضافه میکند؛ به این ترتیب، توصیف را به سمت چیزی هدایت میکند که کاربر واقعاً درخواست کرده است (الگوی codex-vision-proxy) و از مدل بینایی میخواهد متن قابلمشاهده را رونویسی کند. با غیرفعال بودن این پرچم — یا در نبود متن کاربر — پرامپت پایه بدون تغییر استفاده میشود.

درخواست سازگار با OpenAI متعلق به حلقهٔ خودارجاعی توصیف (`callVisionModelSingle()`
در `visionBridgeHelpers.ts`) همیشه `image_url.detail: "high"` را درخواست میکند —
بدون قیدوشرط، برای هر فراخوان/ارائهدهنده، و بدون وابستگی به هیچ سیگنال کلاینتی.
نمونهبرداری با جزئیات پایین، دقت OCR را دقیقاً برای همان وظیفهٔ رونویسی متن
که این پرامپت درخواست میکند کاهش میدهد؛ بنابراین خود فراخوانی توصیف، صرفنظر
از سطح جزئیاتی که درخواست ورودی اصلی استفاده کرده است، همیشه جزئیات بالا را
درخواست میکند. این فقط بر بدنهٔ درخواست داخلی توصیف اثر میگذارد؛ نحوهٔ
ارسال `image_url.detail` خود فراخواننده توسط OmniRoute در درخواست اصلی را تغییر
نمیدهد — آن مقدار پیشفرض بهصورت جداگانه و فقط برای کلاینتهای OpenCode
شناساییشده، در `defaultImageDetail()`
(`open-sse/handlers/chatCore/upstreamBody.ts`) اعمال میشود. شاخهٔ قالب سیمی
Anthropic در حلقهٔ خودارجاعی توصیف، فیلد `detail` ندارد و از هیچیک از این
مقادیر پیشفرض تأثیر نمیپذیرد.

#### سقف خروجی توصیف (`modalityBridgeVisionMaxChars`)

| کلید                           | پیشفرض | محدوده           |
| ------------------------------ | ------ | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`    | `0` یا 100–50000 |

`0` (پیشفرض) به معنی **بدون سقف** است — توصیف بازگرداندهشده توسط
`callVisionModel()` بدون تغییر عبور داده میشود و رفتار موجود را حفظ میکند.
هر مقداری در محدودهٔ 100–50000، پیش از جایگذاری مجدد توصیف بهشکل
`[Image N]: <description>`، آن را با پسوند `…` کوتاه میکند
(`VisionBridgeGuardrail.preCall()` در `src/lib/guardrails/visionBridge.ts`).
برای وظایف OCR با جزئیات زیاد که مدل پاییندستی به رونویسی کامل نیاز دارد، این
مقدار را افزایش دهید؛ برای محدود کردن مصرف توکن در مدلهای بینایی پرحرف، آن را
کاهش دهید. فیلد داشبورد در پنل پیشرفتهٔ زبانهٔ Vision قرار دارد
(`modality-bridge-max-chars` در `ModalityBridgeVisionTab.tsx`) و هر مقدار بین
1 و 99 را تا کف 100 بالا میبرد، درحالیکه `0` صریح را دستنخورده باقی
میگذارد — `0` بهخودیخود یک مقدار معتبر Zod است
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`)، نه اینکه
صرفاً مقدار پیشفرض «تنظیمنشده» باشد.

#### کش توصیف (`modalityBridge/bridgeCache.ts`)

کش درونحافظهای LRU + TTL برای خروجیهای توصیف که در سراسر فرایند بهاشتراک
گذاشته میشود. کلید = `sha256(imageRef + composedPrompt + configuredBridgeModel)`
با قاببندی مبتنی بر پیشوند طول (بدون برخورد در مرز فیلدها). مؤلفهٔ مدل،
مدل پل **پیکربندیشده** است، نه مدلی که واقعاً پاسخ داده است —
`callVisionModel` ممکن است در داخل به مدل جایگزین برگردد و کلیدگذاری برای هر
تلاش، کش را تکهتکه میکند. توصیفهای ناموفق هرگز کش نمیشوند. تنظیمات:

| کلید                            | پیشفرض | محدوده  |
| ------------------------------- | ------ | ------- |
| `modalityBridgeCacheEnabled`    | `true` | —       |
| `modalityBridgeCacheTtlMinutes` | `60`   | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`  | 10–5000 |

#### نرمالسازی تصویر راهدور (واکشی توصیف خودارجاعی/base64)

هنگامی که پل خودش یک تصویر **راهدور** را واکشی میکند — فراخوانی داخلی توصیف
Anthropic و تبدیل base64 با قالب سیمی claude
(`ensureBase64ImagesForClaudeWire`)، که هر دو از طریق
`fetchRemoteImageAsDataUri()` در `visionBridgeHelpers.ts` انجام میشوند — URI
دادهٔ حاصل، پیش از تعبیه شدن در درخواست مدل بینایی، از `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) عبور داده میشود. تصاویر بیشازحد بزرگ
به **ضلع بلند 2048px** کوچکمقیاس میشوند (مطابق با سقف تغییر اندازهای که
OpenAI/Anthropic از قبل در سمت سرور اعمال میکنند)؛ این کار بدون تغییر آنچه
مدل بینایی میبیند، حجم بایتهای آپلود/تأخیر را کاهش میدهد. تغییر اندازه از
`sharp` استفاده میکند که از طریق import پویا بارگذاری میشود: روی پلتفرمی که
باینری بومی آن بارگذاری نشود، `normalizeDataUri()` **هرگز خطا پرتاب نمیکند** —
بلکه به عبور مستقیم بایتهای اصلی برمیگردد تا مسیر توصیف/تبدیل base64 همیشه
به کار خود ادامه دهد. بایتهای غیرتصویری (واکشیای که تصویر قابل رمزگشایی
برنگردانده است) نیز بدون تغییر عبور داده میشوند. این نرمالسازی فقط به
تصاویری محدود است که پل برای فراخوانی داخلی خودش واکشی میکند — هرگز بر
محمولهٔ عبوری خام فراخواننده اعمال نمیشود، که با اصل تغییر صرفاً با انتخاب
صریح سازگار است (قانون سختگیرانهٔ شمارهٔ 20).

#### شِمای تنظیمات + مهاجرت

کلیدهای جدید `modalityBridge*` در `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`) با Zod اعتبارسنجی میشوند:
`modalityBridgeVisionEnabled`،
`modalityBridgeVisionMode`، `modalityBridgeVisionModel`،
`modalityBridgeVisionTaskAware`، `modalityBridgeVisionPrompt`،
`modalityBridgeVisionTimeout`، `modalityBridgeVisionMaxImages`،
`modalityBridgeVisionMaxChars`، سهتایی `modalityBridgeCache*` و گروه
`modalityBridgeAudio*` که توسط Audio Bridge استفاده میشود. مهاجرت
`141_modality_bridge_settings.sql` مقادیر قدیمی موجود `visionBridge*` را به
کلیدهای جدید متناظر کپی میکند (همتوان، و هرگز مقدار `modalityBridge*`
تنظیمشده توسط اپراتور را بازنویسی نمیکند)؛ کلیدهای قدیمی برای یک چرخهٔ
انتشار همچنان بهعنوان گزینهٔ جایگزین هنگام خواندن پذیرفته میشوند.

#### هدر شفافیت + آمار

پاسخهای تبدیلشده توسط توصیف، هدر
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
را حمل میکنند (ساختهشده توسط `buildModalityBridgeHeader()` در
`modalityBridge/bridgeStats.ts` و درجشده توسط
`withModalityBridgeHeader()` در `src/sse/handlers/chatHelpers.ts`).
درخواستهای مسیریابیمجددشده **هیچ** هدری دریافت نمیکنند — محموله دستنخورده
بوده و تعویض مدل از قبل در فیلد `model` بدنهٔ پاسخ قابلمشاهده است.

`GET /api/modality-bridge/stats` (با احراز هویت مدیریتی، در همان سطح
`GET /api/settings`) شمارندههای درونحافظهای هر وجه را برای `vision`، `audio` و
`video` با ساختار
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` برمیگرداند. `averageLatencyMs` از
`latencySamples`، و نه همه تلاشها، بهعنوان مخرج استفاده میکند؛ عملیاتی که زمانسنجی
نشده است، یک نمونه جعلی صفر میلیثانیهای ایجاد نمیکند. `bridged` همچنان نام مستعار
سازگار با نسخههای پیشین برای تبدیلهای موفق است؛ تلاشهای ناموفق آن را افزایش
نمیدهند.
طبق طراحی، شمارندهها با راهاندازی مجدد فرایند بازنشانی میشوند
(تلهمتری، نه حسابداری).

#### پیکربندی داشبورد

صفحه اختصاصی داشبورد در
`/dashboard/settings/modality-bridge` قرار دارد. زبانههای آدرسپذیر با URL شامل
`Vision`، `Audio` و `Video`، هنگام تغییر مقدار `tab` پارامترهای کوئری را حفظ
میکنند. زبانه Vision امکان فعالسازی، حالت، انتخاب مدل (از جمله پیشفرض خودکار)،
پرامپتگذاری آگاه از وظیفه، محدودیتهای پیشرفته زمانانتظار/تصویر/طول توضیحات/کش،
شمارندههای زمان اجرا و یک درخواست نمونه محافظتشده را ارائه میکند. زبانه Audio
نیز فعال است: این زبانه امکان فعالسازی، انتخابگر مدل مختص STT همراه با Auto،
محدودیتهای زمانانتظار/حداکثر طول کلیپ، شمارندههای صوتی و یک آزمون نمونه
`input_audio` را ارائه میکند. زبانه Video کاربردی است: وضعیت زمان اجرای
FFmpeg/ffprobe را گزارش میدهد — یکی از چهار وضعیت صریح رابط کاربری (`unknown`
هنگامی که بررسی در حال انجام است یا نتوانسته تکمیل شود، `restricted` روی میزبان
داشبورد غیر-loopback که بررسی در سمت کلاینت رد میشود، `unavailable` پس از انجام
بررسی و تأیید فقدان ابزار، یا `available` همراه با نسخههای FFmpeg/ffprobe) —
محدودیتهای فعالسازی/مدل/فریم/ویدئو/زمانانتظار را ماندگار میکند، انتخابگر مدل
را به مدلهای دارای قابلیت بینایی محدود میکند و شمارندههای ویدئو را نمایش
میدهد.

کارت پیشین Vision Bridge در تنظیمات AI اکنون پیوندی سازگار با نسخههای پیشین به
صفحه جدید است؛ این کارت دیگر مالک نسخه دومی از فرم نیست. Media Providers نیز
گردشکارهای Image-to-Text و Speech-to-Text را به زبانههای متناظر Modality Bridge
پیوند میدهد، بدون آنکه محیط آزمایشی موجود Speech-to-Text را حذف کند.

**دور زدن پذیرش در حلقه خودی:** هنگامی که فراخوانی describe از طریق حلقه خودی
`/v1` متعلق به OmniRoute مسیریابی میشود (مدل ارائهدهنده غیراستاندارد)،
زیردرخواست، هدر `x-omniroute-admission-bypass: internal` را ارسال میکند و با
اعتبارنامه حلشده حلقه خودی احراز هویت میشود — مقدار نگهبان محلی
`sk_omniroute` در حالت محلی، یا کلید محیطی پیکربندیشده توسط اپراتور یعنی
`OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350)، تا استقرارهای دارای
`REQUIRE_API_KEY=true` همچنان بتوانند فراخوانی describe را اجرا کنند. دور زدن
فقط برای همان اعتبارنامههای دقیق پذیرفته میشود؛ بنابراین کلاینتهای خارجی
نمیتوانند با استفاده از این هدر مرحله پذیرش را دور بزنند.

پیشفرضهای قدیمی در `src/shared/constants/visionBridgeDefaults.ts` قرار دارند؛
پیشفرضهای جدید حالت/آگاهی از وظیفه/کش و حلکننده تنظیمات در
`src/shared/constants/modalityBridgeDefaults.ts` قرار دارند. سازوکار محافظتی یک
گزینه سازنده `deps` ارائه میکند تا آزمونها بتوانند پیادهسازیهای جعلی
`getSettings` و `callVisionModel` را تزریق کنند.

### پل صوتی (`audioBridge.ts`) — Modality Bridge PR-3

درخواستهای چت حاوی صدا را پیش از رسیدن به مقصدی که پذیرش ورودی صوتی برای آن
شناختهشده نیست، رهگیری میکند. این سازوکار هرگز درخواست چت را مجدداً مسیریابی
نمیکند: بخشهای صوتی از طریق نقطه پایانی multipart موجود و سازگار با OpenAI
رونویسی میشوند و مدل چت انتخابشده با متن رونویسیها ادامه میدهد.

جریان:

1. مقدار `supportsAudio` را از طریق `getResolvedModelCapabilities()` حل کنید.
   فراداده صریح رجیستری ارائهدهنده اولویت دارد، سپس فراداده ایستای مدل و پس از
   آن `modalities_input` همگامشده قرار میگیرد. فهرست ورودی اعلامشدهای که
   شامل `audio` نباشد، `false` است؛ نبود هرگونه شاهد قابلیت، مقدار `null` را
   باقی میگذارد. هر دو مقدار `false` و `null` پل محافظهکارانه را فعال
   میکنند، درحالیکه `true` آن را دور میزند.
2. تنظیمات `modalityBridgeAudio*` را حل کرده و بخشهای صوتی سطحبالا و قابل
   اتصال را از تمام پیامها از طریق آشکارساز مشترک `detectMediaParts()`
   استخراج کنید. قالبهای سیمی پشتیبانیشده عبارتاند از `input_audio`،
   `audio_url` و `source.media_type: "audio/*"` متعلق به OpenAI. صوت تودرتو
   برای مسیریابی شناسایی میشود، اما مسیر اتصال آن را حذف نمیکند. حجم کار با
   `modalityBridgeAudioMaxClips` محدود میشود؛ بخشهای بعدی بدون تغییر باقی
   میمانند.
3. از `provider/model` پیکربندیشده پیروی کنید، یا اجازه دهید
   `selectAudioBridgeModel()` به ترتیب پایدار کاتالوگ در
   `AUDIO_TRANSCRIPTION_PROVIDERS` پیمایش کرده و نخستین مدل دارای اعتبارنامه
   فعال و قابلاستفاده ارائهدهنده را انتخاب کند.
4. `callAudioTranscription()` صدای base64/data-URI را به یک `file` از نوع
   multipart تبدیل میکند، یا یک `audio_url` راه دور را از طریق محافظ خروجی
   فقطعمومی، با تثبیت DNS و سقف 25 MB دانلود میکند. سپس فایل و مدل انتخابشده
   را با POST به حلقه خودی محلی `/v1/audio/transcriptions` ارسال میکند و با
   `resolveSelfLoopBearer()` احراز هویت میشود. مسیر رونویسی موجود، جستوجوی
   معمول اعتبارنامه، مدیریت دوره انتظار/محدودیت نرخ و ارسال به ارائهدهنده را
   انجام میدهد.
5. فراخوانیهای موفق، بخشهای خود را با `[Audio N]: <transcript>` جایگزین
   میکنند. فراخوانیها با `Promise.allSettled` اجرا میشوند: خرابی هر مورد،
   همان بخش صوتی اصلی را حفظ میکند (قرارداد #4012). اگر همه فراخوانیها شکست
   بخورند و برای مقصد ثابت شده باشد که `supportsAudio === false` است، بخشها
   به `[Audio N]: (unavailable — no STT provider connected)` تبدیل میشوند
   (قرارداد #8430). برای مقصد ناشناخته (`null`)، نتیجه شکست کامل بدون تغییر
   باقی میماند. مقصدی که متنمحور بودن آن ثابت شده و فاقد اعتبارنامه STT
   قابلاستفاده است، بدون صدور فراخوانی شبکه همان جایگزین صریح را دریافت
   میکند.

رونویسیهای موفق از کش LRU/TTL سراسری فرایند Modality Bridge استفاده میکنند.
کلید، مرجع صوتی، برچسب پایدار عملیات `audio-transcription` و مدل STT انتخابشده
را ترکیب میکند؛ شکستها هرگز کش نمیشوند. تلاشهای صوتی شمارندههای مشترک
`bridged`، `cacheHits`، `failures` و `lastUsedAt` را بهروزرسانی میکنند.
پاسخهای تبدیلشده دارای
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` هستند؛
درخواستهای دستنخورده یک بخش Audio Bridge دریافت نمیکنند.

تنظیمات زمان اجرا با پشتوانه DB ذخیره و با Zod اعتبارسنجی میشوند:

| کلید                          | پیشفرض  | محدوده              |
| ----------------------------- | ------- | ------------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —                   |
| `modalityBridgeAudioModel`    | `""`    | خودکار یا شناسه STT |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000         |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10                |

کش مشترک همچنان توسط `modalityBridgeCacheEnabled`،
`modalityBridgeCacheTtlMinutes` و `modalityBridgeCacheMaxEntries` کنترل میشود.

### پل ویدئو (`videoBridge.ts`، `videoBridgePipeline.ts`)

پیش از فراخوانی مقصدی که پشتیبانی بومی شناختهشدهای از ویدئو ندارد، بخشهای ویدئویی سطحبالا را در `messages` مربوط به Chat Completions و `input` مربوط به Responses API رهگیری میکند.
قالبهای پشتیبانیشده عبارتاند از `input_video`، `video_url`، `video_source`، نشانیهای HTTPS و URIهای دادهای `data:video/*;base64,...`. نام فایلهای ساده در متن بهعنوان ویدئو در نظر گرفته نمیشوند.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) مسئول پیمایش درخواست، بررسی قابلیت/سیاست، تجمیع در سطح هر درخواست و بار پاسخ است.
کارهای مربوط به هر ویدئو — دریافت، کشِ نتیجه کامل، توصیف توالی فریمها (که هر رونوشت صوتی اعلامشده از سوی فراخواننده را ادغام میکند) و سنجهها/لغو/پاکسازی مربوط به هر تلاش — پشت `processVideoPart` در `videoBridgePipeline.ts` پنهان شدهاند؛ این تابع در حلقه `preCall` برای هر بخش ویدئویی یکبار فراخوانی میشود.
این ماژول همچنین مرزهای صریح پورت `VideoMediaBrokerPort` (دریافت بایتها و استخراج فریمهای نمونهبرداریشده)، `VideoAudioTranscriptionPort` (ادغام رونوشت صوتی اعلامشده از سوی فراخواننده با زیرنویسهای نمونهبرداریشده) و `VideoDrilldownPort` (مرز ماندگارسازی واکاوی عمیق فریم؛ هنوز به `processVideoPart` متصل نشده است — در حال حاضر فقط مسیر مستقل `/api/modality-bridge/video/drilldown` ورودیهای واکاوی عمیق را مینویسد) تعریف میکند.

مسیر عمومی درخواست `/v1` هرگز یک زیرفرایند را وارد یا فراخوانی نمیکند. ویدئوهای راهدور با سقف 50 MiB بارگیری میشوند؛ ویدئوهای base64 درونخطی دارای سقف محافظهکارانه 36 MiB برای اندازه رمزگشاییشده هر ویدئو هستند تا پوشش مدل/پیامها/قالببندی بتواند درون محدودیت پذیرش درخواست JSON عمومیِ 50 MiB باقی بماند. طول درونخطی و تخمینهای اندازه رمزگشاییشده پیش از تخصیص بررسی میشوند. HTTPS برای URL اولیه راهدور و تمام تغییرمسیرها الزامی است و از محافظ خروجیِ موجودِ محدود به مقصدهای عمومی همراه با تثبیت DNS استفاده میشود. سپس بایتها دقیقاً از مرز کارگزار داخلی `POST /api/modality-bridge/video/extract` عبور میکنند. آن مسیر هم `LOCAL_ONLY` و هم `SPAWN_CAPABLE` است، فقط درخواست احراز هویتشده در سطح هر فرایند و از loopback مورد اعتماد را میپذیرد و هرگز URL، مسیر سیستم فایل، فایل اجرایی یا فهرست آرگومانها را قبول نمیکند. خط لوله اندازه بدنه API و خوانشگر افزایشی بدنه در کنترلکننده، هر یک بهطور مستقل سقف 50 MiB را برای ورودی کارگزار اعمال میکنند. صف محدود آن در هر لحظه یک استخراج را اجرا میکند، چهار کار در انتظار را مجاز میداند و ورودی در انتظار را به 100 MiB محدود میکند.

درون کارگزار، `ffprobe` یک فایل محلی خصوصی را میخواند؛ فهرست ثابت قالبهای مجاز، قالبهای فهرست پخش و مانیفست را کنار میگذارد. برای محفظههای مجاز خانواده MOV، ارجاعهای خارجی داده MOV بهطور پیشفرض غیرفعال باقی میمانند و فرمان ثابت آنها را فعال نمیکند. هر دو ابزار `ffprobe` و `ffmpeg` از فهرست سفید پروتکلِ فقط `file`، یک رشته، آرایههای ثابت آرگومان، بدون پوسته و فایلهای اجرایی یافتشده از `PATH` استفاده میکنند. جریانهای تصویر جلدِ پیوستشده، نامزد قابل پخش نیستند. همه جریانهای قابل پخش باید محدودیتها را برآورده کنند و پیش از جایگزین قطعی با کمترین شاخص، یک جریان پیشفرض صریح ترجیح داده میشود. ویدئوها به 600 ثانیه، 8,192 پیکسل در هر بُعد و 33,554,432 پیکسل مبدأ محدود میشوند. FFmpeg از 1 تا 16 فریم JPEG در نقاط میانی نمونهبرداری میکند، لبه بلند را بدون بزرگنمایی ورودیهای کوچکتر حداکثر به 1,024 پیکسل کاهش میدهد و هرگز URL دریافت نمیکند. روش نمونهبرداری بهطور پیشفرض `uniform` است. سیاستهای اختیاری `scene_aware` و آزمایشی `segment_aware` یک گذر ثابت دیگر FFmpeg را روی جریان محلیِ از قبل اعتبارسنجیشده اجرا میکنند، برچسبهای زمانی صحنه `showinfo` را بهصورت محدود انتخاب میکنند و در صورت شکست آشکارساز، پایان مهلت، خروجی معیوب یا خالی بودن مجموعه نامزدها، بهصورت قطعی به همان نقاط میانی یکنواخت بازمیگردند. حالت آگاه از قطعه، نمونههای نقطه میانی را متناسب با بازههای صحنه اعتبارسنجیشده تخصیص میدهد؛ شواهد حالت آگاه از قطعه و رفتار بازگشت در ادامه تشریح شدهاند. سقف سخت 16 فریم پس از انتخاب در همه سیاستها اعمال میشود. هنگامی که درخواست آگاه از صحنه فقط بودجه یک فریم دارد، از نقطه میانی یکنواختِ پنجره فعالِ کل ویدئو یا تمرکز استفاده میکند و `policyEffective: uniform` را گزارش میدهد: یک فریم صحنه انتخابشده نمیتواند هر دو انتهای زمانی را حفظ کند. فراخواننده میتواند بهصورت اختیاری یک پنجره تمرکز متناهی (`start`/`end` بر حسب ثانیه) ارائه کند؛ کرانها به مدت رسانه محدود میشوند، پنجرههای معکوس یا نامتناهی رد میشوند و همه سیاستهای نمونهبرداری فقط درون بازه نرمالسازیشده اجرا میشوند. پنجره حاصل در فراداده نمونهبرداری و در پیشوند توصیف نامطمئن گنجانده میشود تا مدلهای پاییندستی بتوانند یک گزیده متمرکز را از خط زمانی کامل تشخیص دهند.

تمرکز معنایی زیرنویس، تنظیمی جداگانه و صریح است. حالت تحلیل پیشفرض `full`، اعلان فریم موجود را حفظ میکند و هرگز متن درخواست را به مدل زیرنویس ارسال نمیکند. در حالت `focused`، پل فقط جدیدترین `text`/`input_text` غیرخالیِ نوشتهشده توسط کاربر را از همان محفظه Chat یا Responses میخواند، آن را به NFC نرمالسازی میکند، نویسههای کنترلی و فاصلههای سفید را فشرده میسازد و آن را به 500 نقطه کد Unicode محدود میکند. نتیجه خالی دقیقاً به اعلان `full` بازمیگردد. یک راهنمای قابل استفاده بهصورت JSON در بلوکی اختصاصی برای زمینه نامطمئن کاربر سریالسازی میشود و فقط میتواند جزئیات قابل مشاهده را اولویتبندی کند؛ این راهنما نمیتواند هشدار جداگانه درباره پیروی نکردن از دستورالعملهای قابل مشاهده یا شنیدن در رسانه را نادیده بگیرد. تمرکز متنی هرگز `start`/`end` را استنباط نمیکند یا نمونهبردار زمانی را تغییر نمیدهد.

#### شواهد ساختاری قطعه FU-07

`segment_aware` یک گذر پیشتحلیل محدود را روی جریان ویدیوی محلیِ ازپیشاعتبارسنجیشده اجرا میکند. زنجیرهٔ ثابت فیلتر ابتدا عرض ویدیو را حداکثر به 320 پیکسل مقیاس میدهد، تغییرات صحنه و بازههای ثابت را تشخیص میدهد و سپس با نرخ 1 فریم در ثانیه، تاری، میانگین درخشندگی و اطلاعات مکانی/زمانی را نمونهبرداری میکند. این گذر به 600 نمونهٔ ساختاری، یک رشتهٔ FFmpeg/فیلتر، همان فهرستهای مجاز پروتکل صرفاً `file` و کانتینر، سقف 1 MiB برای خروجی فرایند، و حداکثر 30 ثانیه در محدودهٔ لغو/مهلت مشترک کارگزار محدود است. این گذر هرگز فرمان، فیلتر، مسیر یا URL را از درخواست نمیپذیرد.

مقادیر ساختاری، شواهد نمونهبرداری قطعی هستند، نه درک معنایی ویدیو. آنها سوژهها، کنشها، زیرنویسها، گفتار یا قصد کاربر را استنباط نمیکنند. مرزهای صحنه و انجماد، قطعهها را تشکیل میدهند؛ پوشش انجماد، تاری، نوردهی، جزئیات مکانی و تغییرات زمانی فقط بر نحوهٔ تخصیص بودجهٔ موجود 1 تا 16 فریمی اثر میگذارند. یک قطعهٔ کاملاً ثابت حداکثر به یک فریم محدود میشود، درحالیکه قطعههای غی ثابت برای بودجهٔ باقیمانده رقابت میکنند. وقتی تعداد مرزها از تعداد فریمها بیشتر باشد، پوشش یکنواخت خط زمانی حفظ میشود تا برشهای سریع ابتدایی نتوانند یک قطعهٔ طولانی انتهایی را پنهان کنند. مرزهای صحنهای که در محدودهٔ تفکیکپذیری تحلیلی 1 ثانیهای یک مرز انجماد قرار دارند، با آن ادغام میشوند.

نبود فیلترها، شواهد ناقص/خالی، خطای آشکارساز یا پایان مهلت پیشتحلیل محدود، بهصورت باز به سیاست دقیق نقطهٔ میانی یکنواخت بازمیگردد. لغو از سوی فراخواننده یا رسیدن به مهلت کارگزار بهصورت باز ادامه نمییابد: این وضعیت زیرفرایندِ در حال اجرا را خاتمه میدهد، مانع استخراج فریمهای بعدی میشود و درخت موقت خصوصی در `finally` حذف میشود.

`scripts/perf/video-bridge-fu07-eval.ts` برای صرفهجویی در فراخوانیهای زیرنویس پس از حذف موارد تکراری، تخصیص بودجه برای حرکت متراکم، شواهد تاری/نوردهی/SI-TI، برشهای سریع با دنبالهای طولانی و مثبتهای کاذب ناشی از محوشدن تدریجی، نمونههای آزمایشی واقعی و قطعی FFmpeg تولید میکند. این اسکریپت زمان سپریشدهٔ پیشتحلیل و، در صورت موجود بودن `/usr/bin/time`، CPU فرزند و بیشینهٔ RSS را ثبت میکند. بررسیهای کیفیت آن فقط معیارهای ساختاری هستند. کیفیت واقعی مدل زیرنویس همچنان `HOLD` میماند، زیرا این ابزار آزمایشی هیچ نقطهٔ پایانی مجاز یا داور تثبیتشدهای ندارد. صرفهجویی مالی نیز `HOLD` باقی میماند، مگر آنکه `--caption-cost-per-call-usd` یک برآورد مثبت و صریح برای هزینهٔ هر فراخوانی ارائه کند؛ اسکریپت هیچیک از این نتایج را جعل نمیکند.

هر فریم به 4 MiB، مجموع همهٔ فریمهای خام به 23 MiB و پاسخ سریالشدهٔ کارگزار به 32 MiB محدود است. یک پوشهٔ موقت خصوصی در `finally` حذف میشود. OmniRoute همراه با FFmpeg عرضه نمیشود و مسیر اجرایی سفارشی را نمیپذیرد. پیش از زیرنویسگذاری، پل یک گذر محافظهکارانه برای حذف تکرارهای بصری اعمال میکند: هر JPEG به یک بافر خاکستری 16×16 کاهش مییابد و فقط با آخرین فریم نگهداشتهشده مقایسه میشود. برای بودجهٔ درخواستی زیرنویس بیش از یک فریم، استخراج یک مجموعهٔ کاندیدای محدود تا حداکثر دو برابر آن بودجه و هرگز بیشتر از 16 فریم فراهم میکند. سقف درخواستی فقط پس از حذف موارد تکراری اعمال میشود و هنگامی که بودجه حداقل دو فریم باشد، نخستین و آخرین کاندیدای انتخابشده در تنکسازی نهایی حفظ میشوند. سیاست نسخهبندیشدهٔ `grayscale-16x16-mean-cells-v2` مقدار بزرگتر از میانگین اختلاف درخشندگی و نسبت سلولهای بندانگشتی را به کار میگیرد که اختلاف نرمالشدهٔ آنها حداقل 0.05 است. آستانهٔ تکراریبودن، ثابت 0.04 است که بهمنظور پیشبینیپذیری انتخاب شده، نه اینکه بهعنوان تنظیم زمان اجرا در معرض استفاده قرار گیرد. این سیگنال ثانویهٔ با کنتراست بالا، حرکتهای کوچک و تغییرات متن قابلمشاهدهای را حفظ میکند که مقایسهٔ صرفاً مبتنی بر میانگین ممکن است پنهان کند. خطاهای مقایسهگر یا رمزگشا بهصورت باز ادامه مییابند و پوشش را حفظ میکنند. فرادادهٔ خروجی میان کاندیداهای استخراجشده، فریمهای استفادهشده با موفقیت و موارد تکراری بصری حذفشده تمایز قائل میشود.

یک بخش ویدیویی که صراحتاً علامتگذاری شده باشد میتواند یک برگهٔ تماس دارای مُهر زمانی درخواست کند. پل یک شبکهٔ JPEG با حداکثر 4 ستون و 16 فریم میسازد. هر سلول 512 پیکسلی، مُهر زمانی منبع خود را در یک نوار پایینی با کنتراست بالا درج میکند و همان مُهرهای زمانی برای ارتباطدهی و ممیزی در فرادادهٔ متنی باقی میمانند. JPEG کامل همچنان به 32 MiB محدود است. اگر `sharp` نتواند شبکه را رمزگشایی یا ترکیب کند، پل به فریمهای JPEG جداگانه بازمیگردد؛ لغو از سوی کلاینت همچنان در سراسر عملیات برگه منتشر میشود.

شواهد ارتقا عمداً از ریزآزمون کارایی ترکیب مصنوعی جدا نگه داشته شدهاند. `scripts/perf/video-bridge-contact-sheet-eval.ts` یک ابزار آزمایشی A/B با طرحوارهٔ نسخهبندیشده برای مدلهای بینایی واقعی و سازگار با OpenAI تعریف میکند. این ابزار تعداد توکنهای گزارششده توسط ارائهدهنده، تأخیر سرتاسری برحسب زمان واقعی سپریشده ــ شامل ترکیب برگه ــ تعداد فراخوانیهای مدل و حفظ واقعیتهای تعریفشده در مانیفست را اندازهگیری میکند. پاسخهای خام مدل در گزارش نوشته نمیشوند؛ فقط چکیدههای SHA-256 و شناسههای واقعیت تطبیقیافته نگهداری میشوند. این ابزار آزمایشی هیچ فراخوانی شبکهای یا مدل پولی انجام نمیدهد، مگر آنکه `--execute-real` ارسال شده باشد و `--model`، `OMNIROUTE_BASE_URL` و `OMNIROUTE_API_KEY` پیکربندی شده باشند. بدون چنین اجرای واقعی و صریحی، حکم ماشینخوان آن `HOLD` باقی میماند؛ اندازهگیریهای مصنوعیِ حجم داده/تعداد فراخوانی بهتنهایی شاهدی برای ارتقا نیستند.

فراخوانندگان میتوانند در صورتی که از قبل متن همترازشده در اختیار دارند، یک آرایهٔ اختیاری `transcript.cues` را به یک بخش ویدیویی پشتیبانیشده پیوست کنند. هر نشانه باید شامل `text`، یک بازهٔ متناهی `start`/`end` درون مدتزمان بررسیشده و یک `source` از فهرست مجاز (`client`، `embedded` یا `audio-bridge`) باشد؛ مقدار پیشفرض `confidence` برابر `1` است و باید بین `0` و `1` باقی بماند. نشانههای کاملاً تکراری ادغام میشوند. OmniRoute هرگز بر اساس این فراداده رونویسی را آغاز نمیکند: نشانههای اعتبارسنجیشده همراه با منبع، اطمینان و بازهٔ زمانی در نتیجهٔ توصیفشده کپی میشوند و در کنار زیرنویسهای فریم بهصورت مشاهدات نامطمئن نمایش داده میشوند. متن نامعتبر، خارج از محدوده یا فاقد منشأ بهجای ترکیبشدن با جریان زیرنویس رد میشود. فیلد `source` در حال حاضر توسط فراخواننده اعلام میشود و سرور آن را تأیید نمیکند: OmniRoute اجبار میکند که مقدار یکی از سه رشتهٔ مجاز باشد، اما هنوز بهصورت رمزنگاریشده تأیید نمیکند که برچسب `embedded` یا `audio-bridge` واقعاً از استخراج تحت مالکیت سرور آمده است. تا زمان فراهمشدن این تأیید، `source` را یک نشانهٔ نامطمئن در نظر بگیرید؛ تصمیمهای مجوزدهی را بر مبنای آن بنا نکنید.

(هرگز با تجزیهٔ متن تختشده ساخته نمیشود، بنابراین هیچ محتوایی از نشانه —
چه خصمانه و چه عادی، ازجمله بدنههایی شامل `]` مانند
`[inaudible]`/`[music]` — نمیتواند باقی بماند). بدنهٔ درخواستِ گزارش تماس
ذخیرهشده، هر بخش متنی مشتقشده از ویدئو را با همان نسخهٔ سایهٔ ویرایششده
جایگزین میکند و تطبیق بر اساس برابری محتوا انجام میشود؛ لنگر `fullText`
از محمولهٔ تکمیلشدهٔ حفاظتیِ پیش از فراخوانی دوباره خوانده میشود، بنابراین
تطبیق حتی پس از آنکه سامانههای حفاظتی بعدی زنجیره (پوشانندههای PII و
اعتبارنامه، با اولویتهای 10/95) متن توصیف را درجا بازنویسی میکنند و پس از
آنکه تزریق اعلان سیستم/تحویل زمینه/حافظه آرایهٔ پیام را تغییر شکل میدهد، همچنان
موفق میشود. بدنهٔ ارسالشده به مدل بالادستی بدون تغییر باقی میماند. یک درخواست
مشاهدهشده همچنین هیچ Memory پایداری را پر نمیکند (استخراج مشتقشده از درخواست
و پاسخ هر دو نادیده گرفته میشوند)، بنابراین پاسخ خود مدل نمیتواند متن رونوشت
را در Memory بازتاب دهد.

**فیلدهای خام ویدئو (#12430).** هنگامی که پل فعال باشد و پشتیبانی بومی از ویدئو
نامشخص یا موجود نباشد، فیلدهای تعریفشدهٔ `transcript`/`audioTranscript` نیز
`videoBridgeObserved` را فعال میکنند، حتی پس از شکست توصیف یا اعمال محدودیت
`maxVideos`. مقدار `null` و رشتههای خالی محسوب میشوند؛ فیلدهای غایب و
فرادادههای غیرمرتبط با ویدئو محسوب نمیشوند. نسخههای نگهداریشده این فیلدها
را ویرایش میکنند یا درخواست را کنار میگذارند و کشها/Memory دور زده میشوند.
محمولهٔ ارائهدهنده بدون تغییر باقی میماند.

نسخههای نگهداریشدهٔ اضافی از همان سیگنال درخواست مشاهدهشده استفاده میکنند.
نمای فوری خام درخواست کلاینت پیش از سامانهٔ حفاظتی، درخواست معلق درونحافظهای
و گزارش درخواست ردشدهٔ اولیه، فیلدهای رونوشت را بهصورت ساختاری در بخشهای
ویدئویی جایگزین میکنند؛ اعلانهای رشتهای ساختهشده توسط مراحل خط لوله و
تحویل زمینه در مقصد بدنهٔ درخواست ذخیرهشده ویرایش میشوند. نشانگر ذخیرهشدهٔ
`video_content_removed` باعث میشود ادامهدادن با `previous_response_id`
بهصورت بسته و ایمن شکست بخورد، نه اینکه متنی را که عمداً حذف شده است بازسازی
کند. اگر یک درخواست مشاهدهشده پیش از ثبت گزارش، نسخهٔ سایهٔ ویرایششدهٔ
مربوط به هر بخش خود را از دست بدهد، یا حتی یکی از چندین نسخهٔ سایهٔ ویدئو پس
از تغییرات بعدی درخواست تطبیق پیدا نکند، بدنهٔ درخواست نگهداریشده بهطور کامل
کنار گذاشته میشود تا از نگهداشت یک رونوشت ناقصویرایششده جلوگیری شود.

برای یک درخواست مشاهدهشده، پاسخ مدل ممکن است هر بخشی از رونوشت را بدون مرز
ساختیافتهٔ نشانه نقلقول کند. بنابراین `responseBody` در گزارش تماس ذخیرهشدهٔ
آن با یک نشانگر حذف جایگزین میشود؛ مصنوع خط لولهٔ تفصیلی (که میتواند شامل
بدنههای بالادستی/کلاینت و قطعههای جریان باشد) نگهداری نمیشود. کشهای معنایی،
همتوانی و بازپخش استدلال برای آن درخواست، خواندن و نوشتن را دور میزنند.
درخواست ارائهدهنده و پاسخ قابلمشاهده برای کلاینت بدون تغییر باقی میمانند.
هنگامی که مصنوع تفصیلی حذف میشود، بایتهای اولیهٔ keepalive از بافر موقت
تخلیه میشوند. هشدار EventStream معیوب Kiro فقط تعداد بایتهای محموله را گزارش
میکند و هرگز محتویات آن یا خطای خام تجزیهگر JSON را گزارش نمیکند.
این متن ادعا نمیکند که همهٔ عیبیابیهای نامرتبط ارائهدهندگان/افزونهها ممیزی
شدهاند؛ بررسی گستردهتر مقصدهای نگهداشت در #11658 پیگیری میشود.

چرخهٔ حیات داخلی `/api/modality-bridge/video/drilldown` یک زیرلایهٔ کش جداگانه
با احراز هویت loopback/token است. هر عملیات همچنین به یک شناسهٔ اصلیِ کدر و
کانونی نیاز دارد. پیش از فعالشدن یک فراخوانندهٔ عملیاتی، باید آن شناسه را از
مستأجر احرازشده استخراج کند و هرگز مقداری انتخابشده توسط کلاینت را ارسال
نکند. کلیدهای کش، آن شناسهٔ اصلی را به شناسههای کانونی نشست و مرجع ویدئو
متصل میکنند، فقط کلیدهای مشتقشده از SHA-256 آنها را ذخیره میکنند و دامنهٔ
خواندن و حذف را به همان شناسهٔ اصلی محدود میسازند. کش در هر ورودی حداکثر 16
فریم JPEG مشتقشده ذخیره میکند، آنها را پس از ده دقیقه منقضی میکند و از
خواندنهای محدودشده با `start`/`end` یا حذف صریح نشست پشتیبانی میکند.

هر شناسهٔ اصلی به 16 ورودی و 64 MiB دادهٔ کانونی JPEG محدود است. این محدودیتها
از سقف سراسری 64 ورودی/256 MiB مستقلاند: فشار سهمیهٔ یک شناسهٔ اصلی، پیش از
بررسی تخلیهٔ سراسری LRU، فقط ورودیهای دارای کمترین استفادهٔ اخیرِ همان شناسه
را تخلیه میکند. هنگام فعالیت کش، ورودیهای منقضی از حسابداری هر شناسهٔ اصلی
و حسابداری سراسری پاک میشوند، درحالیکه لغو و شکست اعتبارسنجی یک جایگزینی
جزئی را ثبت نمیکنند.

کش ورودیهای Base64 غیرمتعارف، padding اضافی، رسانههای غیر-JPEG، فایلهای JPEG معیوب یا
ناقص، و فایلهای JPEG را که هنگام decode کامل و کراندار تصویر با `sharp`
هشداری ایجاد میکنند، رد میکند. هر تصویر پذیرفتهشده را دوباره بهصورت یک JPEG متعارف encode میکند، عرض و ارتفاع را
بهجای اعتماد به فیلدهای فراخواننده از بایتهای decodeشده به دست میآورد، و هرگونه
بایت چندقالبی انتهایی را بهجای نگهداشتن دور میریزد. فقط بافر فشرده متعارف و کراندار
در هر دو سهمیه محاسبه میشود. محدودیت انتقال JSON، سربار Base64 برای سقف ورودی decodeشده 32 MiB
را نیز شامل میشود. هر
مشتق ذخیرهشده، فرمت/وضوح JPEG اعتبارسنجیشده، سیاست نمونهبرداری،
نسخه مشتقسازی، زمان ایجاد، هش محتوای محاسبهشده توسط سرور، و ارجاع والد
هششده بههمراه هش محتوای والدِ فراخواننده مورداعتماد را ثبت میکند. لغو عملیات
بین مراحل ناهمگام decode/hash و پیش از commit اتمیک کش بررسی میشود.

این بخش هنوز یک تولیدکننده عملیاتی را به route متصل نمیکند و
انتخاب variant چندوضوحی را ارائه نمیدهد. بنابراین مسیر درخواست شفاف Video Bridge
هیچ کار اضافی تحمیل نمیکند، درحالیکه مشتقسازی principal مقید به tenant و
چرخه عمر کامل چندوضوحی FU-08 همچنان بهصراحت بهعنوان کارهای بعدی باقی میمانند،
نه اینکه بهعنوان رفتاری کامل مستند شده باشند.

فریمها بهترتیب با مدل Video پیکربندیشده captionگذاری میشوند. یک override خالی
برای Video تنظیم Vision را به ارث میبرد؛ اگر هر دو خالی باشند، auto-router مربوط به Vision
مدل مؤثرِ دارای قابلیت بینایی را انتخاب میکند. captionهای موفق
بخش اصلی را با پیشوند پایدار `[Video description:` جایگزین میکنند که همچنین
متن را بهعنوان مشاهدهای نامطمئن و مشتقشده از رسانه علامتگذاری میکند و به مدلهای
پاییندستی میگوید دستورالعملهای موجود در رسانه را دنبال نکنند. کلیدهای کش caption فریم
شامل بایتهای JPEG، prompt، timestamp و مدل مؤثر هستند؛ فقط captionهای موفق
کش میشوند. ورودیهای کش، مدل تولیدکننده واقعاً موفق را، از جمله یک مدل fallback،
حفظ میکنند؛ وقتی فریمهای مختلف توسط مدلهای متفاوت تولید شده باشند، bridge مقدار `mixed`
را گزارش میکند. cache hit بهجای برچسبگذاری مجدد آن بهعنوان طرح مسیریابی درخواستی،
هویت همان تولیدکننده را دوباره استفاده میکند. کش نتیجه کل ویدئو بر اساس تمام ورودیهایی
کلیدگذاری میشود که خروجی را تغییر میدهند — prompt، مدل مؤثر،
سیاست نمونهبرداری، تعداد فریم، حالت تحلیل معنایی، fingerprint مبتنی بر SHA-256
از focus hint نرمالشده، focus window، `transcript`،
`audioTranscript` و پرچم contact-sheet — بنابراین تغییر هرکدام از این
ابعاد، cache miss است و هرگز باعث استفاده مجدد از داده کهنه نمیشود. نسخه سیاست
حذف تکرار بصری، آستانه و تعداد کراندار فریمهای کاندید نیز صراحتاً در
کلید و metadata کش نتیجه قرار دارند؛ بنابراین تغییر سیاست نمیتواند توضیح
کهنه کل ویدئو را دوباره استفاده کند. metadata نسخه v4 کش نتیجه، mode و
fingerprint را نگه میدارد و هرگز task خام کاربر را ذخیره نمیکند. metadata مربوط به guardrail هر دو
حالت تحلیل درخواستی و مؤثر را گزارش میکند؛ حالت `focused` درخواستی بدون
متن قابلاستفاده کاربر، عملاً بهصورت `full` گزارش میشود.

guardrail تمام بخشهای ویدئویی پشتیبانیشده را استخراج میکند، اما بیش از
`modalityBridgeVideoMaxVideos` مورد را توصیف نمیکند. برای مقصدی که ثابت شده
`supportsVideo === false` دارد، ویدئوهای ناموفق و بیشازحد مجاز به markerهای متنی امن و صریح
تبدیل میشوند تا هیچ ویدئوی خامی باقی نماند. وقتی قابلیت نامشخص است، آن بخشها
بدون تغییر باقی میمانند. مقصدهایی با `supportsVideo === true`، bridge را دور میزنند.
سیگنال لغو درخواست کلاینت در دانلود، صف broker،
subprocessها و فراخوانیهای caption منتشر میشود؛ لغوها پردازش را بین ویدئوها متوقف میکنند و هرگز
با بازگذاشتن مسیر عبور رسانه خام از خطا عبور نمیکنند.

تنظیمات زمان اجرا در DB ذخیره میشوند و با Zod اعتبارسنجی میشوند:

| کلید                                | پیشفرض      | محدوده / رفتار                                                                                          |
| ----------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | زمان اجرای اختیاری، نیازمند فعالسازی صریح                                                               |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` captionهای عمومی را حفظ میکند؛ `focused` از context کراندار و نامطمئنِ آخرین کاربر استفاده میکند |
| `modalityBridgeVideoModel`          | `""`        | مدل Vision Bridge را به ارث میبرد                                                                       |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                    |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`، `scene_aware`، یا `segment_aware` متناسب؛ خرابی detector به `uniform` بازمیگردد              |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                     |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                          |

مقادیر قدیمی و ذخیرهشده timeout مربوط به Video که بیش از 120 ثانیه باشند، به
deadline مربوط به broker محدود میشوند؛ نوشتن تنظیمات جدید بالاتر از این حد رد میشود.
`GET /api/modality-bridge/video/runtime` پیش از احراز هویت یا بررسی زمان اجرا،
به locality مورداعتماد و مهرشده loopback نیاز دارد و سپس احراز هویت
مدیریتی را الزامی میکند. این endpoint فقط `available`، نسخههای پاکسازیشده FFmpeg/ffprobe و یک
دلیل ثابت در صورت در دسترس نبودن زمان اجرا را برمیگرداند. endpoint داخلی استخراج
یک API عمومی آپلود نیست: اشباع صف، `503` بههمراه `Retry-After` را برمیگرداند، قطع اتصال
فراخواننده `499` را برمیگرداند، و deadline ثابت broker مقدار `504` را برمیگرداند. پاسخهای تبدیلشده،
`video->text;model=<visionModel>;parts=<videos>` را بدون حذف segmentهای Vision یا Audio
به header مرکزی `x-omniroute-modality-bridge` اضافه میکنند.

### پوشاننده PII (`piiMasker.ts`)

در **هر دو** مرحله اجرا میشود.

- **`preCall`** از payload یک کپی میسازد، در `system`، `messages`، `input` و
  `prompt` پیمایش میکند (از جمله آیتمهایی که رشتهٔ ساده هستند) و `processPII()` را
  (از `@/shared/utils/inputSanitizer`) روی فیلدهای رشتهای `content`/`text` اعمال
  میکند. وقتی `PII_REDACTION_ENABLED=true` باشد، اطلاعات PII شناساییشده در
  payload خروجی حذف یا پوشانده میشوند. این رفتار مستقل از `INPUT_SANITIZER_MODE`
  است (که فقط سیاست تزریق prompt را کنترل میکند). وقتی پوشاندن غیرفعال باشد،
  فراخوانی تعداد موارد شناساییشده را بدون بازنویسی محتوا ثبت میکند.
- **`postCall`** یک کپی عمیق از پاسخ میسازد و `sanitizePIIResponse()` را بههمراه
  پوشانندهٔ ساختار Responses API (`maskResponsesOutput` — شامل
  `output_text` و `output[].content[].text`) اجرا میکند. اگر هرگونه پوشاندنی
  انجام شود، پاسخ اصلاحشده جایگزین پاسخ اصلی میشود.

این guardrail هرگز مسدود نمیکند؛ فقط حاشیهنویسی (`meta.detections`،
`meta.redacted`) یا بازنویسی انجام میدهد.

### تزریق Prompt (`promptInjection.ts`)

ساختارهای خصمانه را در محتوای ارائهشده توسط کاربر شناسایی میکند و سیاست
پیکربندیشده را به اجرا میگذارد. رفتار آن توسط متغیرهای محیطی و گزینههای
constructor تعیین میشود:

| تنظیم             | متغیر محیطی                                                                                                | پیشفرض | اثر                                                                                                                                                                                           |
| ----------------- | ---------------------------------------------------------------------------------------------------------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| فعال بودن         | `INPUT_SANITIZER_ENABLED`                                                                                  | `true` | وقتی `false` باشد، guardrail بدون ادامهٔ پردازش بازمیگردد.                                                                                                                                    |
| حالت              | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                            | `warn` | سیاست تزریق: `block`، `warn` یا `log`. (`redact` برای سازگاری با نسخههای قبلی پذیرفته میشود، اما متن تزریق را **حذف نمیکند**؛ بازنویسی PII درخواست توسط `PII_REDACTION_ENABLED` کنترل میشود.) |
| آستانهٔ مسدودسازی | گزینهٔ `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (نام مستعار `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high` | حداقل شدت لازم برای مسدودسازی. با تنظیمات پیشفرض، شدت متوسط فقط تحت نظارت قرار میگیرد.                                                                                                        |

**اولویت حالت** (`getMode`): مقدار `options.mode` متعلق به فراخواننده →
**بازنویسی feature flag پایگاهداده** برای `INJECTION_GUARD_MODE` (Dashboard → Settings →
Feature Flags) → متغیر محیطی `INJECTION_GUARD_MODE` → متغیر محیطی
`INPUT_SANITIZER_MODE` → `warn`. بنابراین، بازنویسی از طریق dashboard نسبت به
متغیرهای محیطی اولویت دارد و رابط کاربری Feature Flags میتواند guard در حال اجرا
را بهصورت زنده کنترل کند (بدون راهاندازی مجدد). خواندن از پایگاهداده fail-safe
است: اگر خطایی رخ دهد، guard به رفتار مبتنی بر متغیرهای محیطی بازمیگردد و وقتی
هیچ بازنویسیای تنظیم نشده باشد، رفتار آن با وضوحیابی صرفاً مبتنی بر متغیرهای
محیطی یکسان است.

منابع شناسایی:

1. `sanitizeRequest()` از `@/shared/utils/inputSanitizer` (مجموعهٔ مشترک
   تشخیصدهندهها که در بخشهای دیگر pipeline نیز استفاده میشود).
2. `DEFAULT_GUARD_PATTERNS` داخلی (در حال حاضر `system_override_inline` و
   `markdown_system_block`، هر دو با شدت `high`).
3. `customPatterns` اختیاری که از طریق گزینههای constructor ارسال میشود (رشتهها،
   عبارتهای منظم یا رکوردهای `{ name, pattern, severity }`).

وقتی `mode === "block"` باشد **و** حداقل یک مورد شناساییشده به آستانهٔ شدت
برسد، `preCall` مقدار `{ block: true, message: "Request rejected:
suspicious content detected" }` را برمیگرداند. در حالتهای `warn`/`log`،
guardrail رویداد را ثبت میکند اما اجازهٔ انجام فراخوانی را میدهد. تابع کمکی
مشترک `evaluatePromptInjection()` نیز برای فراخوانندگانی که نیاز دارند promptها
را بدون عبور از registry ارزیابی کنند، export شده است.

**محدودهٔ اسکن (v3.8.20):** تشخیصدهنده فقط **اولین 16 KB** از متنهای
prompt بههمپیوسته را بررسی میکند — `MAX_INJECTION_SCAN_BYTES = 16 * 1024`
(16 384 بایت) در `src/shared/utils/inputSanitizer.ts`. هر دو تابع
`detectInjection()` و `evaluatePromptInjection()` پیش از اجرای حلقهٔ الگوها،
`slice(0, MAX_INJECTION_SCAN_BYTES)` را اجرا میکنند. دستورالعملهای تزریق نزدیک
ابتدای ورودی قرار میگیرند، بنابراین این کار مصرف CPU/GC ناشی از regex را برای
payloadهای چندصد KB محدود میکند، بدون آنکه قابلیت شناسایی را تضعیف کند (رجوع
کنید به #3932، #4041).

### پوشانندهٔ اطلاعات احراز هویت (`credentialMasker.ts`)

در **هر دو** مرحله اجرا میشود و در زنجیرهٔ پیشفرض آخرین مورد است (اولویت `95`).
الگوهای شناختهشدهٔ کلید API / توکن محرمانه را از payload خروجی (محتوای پیام،
آرگومانهای فراخوانی ابزار و نتایج ابزار) **و نیز** پاسخ ارائهدهنده حذف یا
میپوشاند؛ بنابراین، اطلاعات احراز هویتی که در یک prompt جایگذاری شدهاند (یا
توسط نتیجهٔ یک ابزار بازتاب یافتهاند)، به ارائهدهندهٔ بالادستی یا مجدداً به
کلاینت نشت نمیکنند.

- **فقط با فعالسازی صریح**، مطابق همان قرارداد حذف اطلاعات PII (در مجاورت قانون سختگیرانهٔ #20):
  غیرفعال است، مگر اینکه `settings.credentialRedactionEnabled === true` **یا**
  `CREDENTIAL_REDACTION_ENABLED=true` باشد. وقتی غیرفعال است، این محافظ هیچ عملی انجام نمیدهد —
  هرگز مسدود نمیکند و هرگز بازنویسی نمیکند.
- `redactCredentials()` کل درخت محموله/پاسخ را پیمایش میکند (`walkValue()`،
  ایمن در برابر آلودگی prototype و ایمن در برابر چرخهها با استفاده از `WeakSet`) و موارد منطبق را با
  جاینگهدار `[REDACTED:<type>]` جایگزین میکند؛ در عین حال فقط شاخههایی را کپی میکند که واقعاً
  تغییر کردهاند.
- `CREDENTIAL_PATTERNS` کلیدهای ارائهدهندگان LLM (OpenAI، OpenAI-proj،
  Anthropic، Google، Hugging Face، Replicate)، توکنهای VCS/SaaS (GitHub، Slack،
  Linear، Notion، npm، Postman، Discord)، کلیدهای پرداخت (Stripe، Square)، کلیدهای
  ابری (کلید دسترسی AWS، Twilio، SendGrid، Mailgun)، کلیدهای خصوصی / JWTها،
  رشتههای اتصال حاوی اعتبارنامه (`mongodb://user:pass@...` و غیره)، و
  یک الگوی عمومی برای مقدار هدرهای `Authorization`/`x-api-key`/`api-key`/`apikey`
  پوشش میدهد. کلیدهایی با ساختار هدر (`authorization`، `x-api-key`، `api-key`،
  `apikey`) بهصورت ساختاری حذف میشوند (فقط مقدار؛ پیشوند طرحی مانند
  `Bearer `/`Basic ` حفظ میشود)، نه با استفاده از عبارت منظم عمومی متن.
- این محافظ هرگز مسدود نمیکند؛ فقط بازنویسی (`modifiedPayload` /
  `modifiedResponse`) و حاشیهنویسی (`meta.credentialsRedacted`، `meta.count`) میکند.

محافظ رگرسیون: `tests/unit/credential-masker-guardrail.test.ts`.

## قرارداد پایه (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // مقدار true زنجیره را بلافاصله متوقف میکند
  message?: string; // هنگام مسدودسازی نمایش داده میشود
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // توسط preCall برای بازنویسی درخواست بازگردانده میشود
  modifiedResponse?: TValue; // توسط postCall برای بازنویسی پاسخ بازگردانده میشود
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

یک گاردریل با بازگرداندن `void`، `{}` یا
`{ block: false }` وضعیت «بدون تغییر» را اعلام میکند. بازگرداندن یک `modifiedPayload`/`modifiedResponse`
مقداری را که برای گاردریلهای پاییندستی در زنجیره جریان دارد، جایگزین میکند.
`signal?: AbortSignal` چرخهٔ حیات فراخواننده را به گاردریلها منتقل میکند. لغو درخواست، استثنای عمدیِ بازماندن در هنگام خطا است: پلهای رسانهای کار را متوقف کرده و پاکسازی میکنند، بدون آنکه رسانهٔ خام را برای مقصدی که مشخص است از آن پشتیبانی نمیکند، بازیابی کنند.

## رجیستری (`registry.ts`)

نمونهٔ یکتای `guardrailRegistry` موارد زیر را ارائه میدهد:

- `register(guardrail)` — یک گاردریل را اضافه میکند (یا بر اساس نام نرمالشده جایگزین میکند) و
  بر اساس `priority` صعودی دوباره مرتب میکند.
- `clear()` / `list()` — ابزارهای کمکی مدیریتی.
- `runPreCallHooks(payload, context)` — روی گاردریلهای فعال پیمایش میکند، payload را
  از طریق `modifiedPayload` عبور میدهد و در اولین `block: true` متوقف میشود.
- `runPostCallHooks(response, context)` — همین جریان را در سمت پاسخ اجرا میکند.
- `resetGuardrailsForTests({ registerDefaults })` — وضعیت را پاک میکند و در صورت نیاز
  مقادیر پیشفرض را برای جداسازی تمیز تستها دوباره ثبت میکند.

هر دو اجراکننده، `{ blocked, payload|response, results, guardrail?, message? }`
را بازمیگردانند که در آن `results` آرایهای از رکوردهای `GuardrailExecutionResult` است که
فیلدهای `blocked`، `skipped`، `modified`، `error` و `meta` را برای هر گاردریل شامل میشود
و برای ردیابی مفید است.

### غیرفعالکردن گاردریلها برای هر درخواست

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` فهرستی بدون موارد تکراری
از نام گاردریلهایی را گردآوری میکند که باید برای درخواست فعلی نادیده گرفته شوند.
منابع (همگی اختیاری و همگی ادغامشده) عبارتاند از:

- `apiKeyInfo.disabledGuardrails`
- `disabledGuardrails` در بدنهٔ درخواست (سطح بالا)
- `metadata.disabledGuardrails` در بدنهٔ درخواست
- هدر `x-omniroute-disabled-guardrails` (یا نسخهٔ قدیمی
  `x-disabled-guardrails`)

مقادیر میتوانند آرایهای از رشتهها یا رشتهای با مقادیر جداشده با ویرگول باشند؛ نامها
به kebab-case با حروف کوچک نرمالسازی میشوند (`pii_masker` → `pii-masker`). نتیجه
از طریق `context.disabledGuardrails` به رجیستری ارسال میشود و رجیستری گاردریلهای
مطابق را نادیده میگیرد (`skipped: true` در `results`).

## ترتیب اجرا

برای هر درخواستی که از `src/sse/handlers/chat.ts` و
`open-sse/handlers/chatCore.ts` عبور میکند:

1. `resolveDisabledGuardrails(...)` فهرست موارد قابل صرفنظر را بر اساس کلید API، بدنه
   و هدرها ایجاد میکند.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` گاردریلها را بهترتیب صعودی
   اولویت اجرا میکند:
   - گاردریلهای غیرفعال با وضعیت `skipped` ثبت میشوند.
   - متد `preCall` هر گاردریل میتواند محتوای ورودی را از طریق `modifiedPayload` بازنویسی کند.
   - نخستین `block: true` زنجیره را متوقف میکند و هندلر یک پاسخ
     رد درخواست توسط گاردریل برمیگرداند.
3. محتوای ورودیِ (احتمالاً بازنویسیشده) وارد مسیریابی ترکیبی و ارسال
   به سرویس بالادستی میشود.
4. پس از آمادهسازی پاسخ، `guardrailRegistry.runPostCallHooks(...)`
   همان زنجیره را روی پاسخ اجرا میکند. در این مرحله، `block: true` باعث کنار گذاشته شدن پاسخ
   بالادستی میشود.

گاردریلهایی که استثنا ایجاد میکنند با `error: <message>` ثبت و از طریق
`logger.warn` گزارش میشوند، اما زنجیره به اجرای خود ادامه میدهد — این رفتار عمداً بر اساس اصل باز ماندن در صورت خطا طراحی شده است.

## پیکربندی

متغیرهای محیطی خواندهشده توسط گاردریلهای داخلی:

| متغیر                                 | استفادهشده توسط          | اثر                                                                                             |
| ------------------------------------- | ------------------------ | ----------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`       | برای غیرفعال کردن کامل تشخیص، روی `false` تنظیم کنید.                                           |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`       | خطمشی تزریق: `warn`، `block` یا `log`. مقدار قدیمی `redact` متن تزریق را بازنویسی نمیکند.       |
| `INJECTION_GUARD_MODE`                | `prompt-injection`       | حالت گارد تزریق؛ همچنین یک پرچم قابلیت در DB است که متغیرهای محیطی را **لغو میکند** (DB > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`       | حداقل شدت ردشده توسط `MODE=block`:‏ `high` (پیشفرض)، `medium` یا `low`.                         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`       | نام مستعار قدیمی برای `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                        |
| `PII_REDACTION_ENABLED`               | `pii-masker`             | وقتی `true` باشد، اطلاعات شناساییکننده شخصی در درخواست پوشانده میشوند (مستقل از حالت تزریق).    |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (پاییندستی) | رفتار پوشاننده در سمت پاسخ را کنترل میکند.                                                      |

گاردریلهای Modality Bridge پیکربندی زمان اجرا را از مخزن تنظیمات
مبتنی بر DB (`getSettings()`) میخوانند، نه از متغیرهای محیطی. کلیدهای اصلی Vision عبارتاند از
`modalityBridgeVisionEnabled`، `modalityBridgeVisionMode`،
`modalityBridgeVisionModel`، `modalityBridgeVisionTaskAware`،
`modalityBridgeVisionPrompt`، `modalityBridgeVisionTimeout`،
`modalityBridgeVisionMaxImages`، `modalityBridgeVisionMaxChars`،
`modalityBridgeCacheEnabled`، `modalityBridgeCacheTtlMinutes` و
`modalityBridgeCacheMaxEntries`. کلیدهای قدیمی
`visionBridge*` فقط بهعنوان سازوکار جایگزین خواندن برای یک چرخه، مطابق مستندات، پذیرفته
میشوند؛ نوشتن از طریق داشبورد از کلیدهای اصلی استفاده میکند. مقادیر پیشفرض و تحلیلگر
سازوکار جایگزین در `src/shared/constants/modalityBridgeDefaults.ts` قرار دارند و ثابتهای قدیمی
در `src/shared/constants/visionBridgeDefaults.ts` نگه داشته شدهاند.

Audio از `modalityBridgeAudioEnabled`، `modalityBridgeAudioModel`،
`modalityBridgeAudioTimeout` و `modalityBridgeAudioMaxClips` بههمراه تنظیمات مشترک
`modalityBridgeCache*` استفاده میکند. Audio هیچ سازوکار جایگزینی برای کلیدهای قدیمی ندارد، زیرا این
کلیدها همراه با طرحواره Modality Bridge معرفی شدهاند.

Video از `modalityBridgeVideoEnabled`، `modalityBridgeVideoAnalysisMode`،
`modalityBridgeVideoModel`،
`modalityBridgeVideoFrameCount`، `modalityBridgeVideoSamplingPolicy`،
`modalityBridgeVideoMaxVideos` و
`modalityBridgeVideoTimeout` بههمراه تنظیمات مشترک `modalityBridgeCache*` استفاده میکند.
این قابلیت بهطور پیشفرض غیرفعال است، زیرا FFmpeg/ffprobe وابستگیهای عملیاتی
اختیاری هستند و تولید شرح برای فریمها باعث افزایش تأخیر و هزینه مدل میشود.

## گاردریلهای سفارشی

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

مراحل:

1. فایل `src/lib/guardrails/myGuardrail.ts` را با ارثبری از `BaseGuardrail` ایجاد کنید.
2. `preCall` و/یا `postCall` را پیادهسازی کنید.
3. یا هنگام import ثبت کنید (از `registerDefaultGuardrails` اضافه کنید) یا
   در زمان اجرا `guardrailRegistry.register(...)` را فراخوانی کنید — رجیستری هر
   گاردریل قبلی با همان نام نرمالشده را جایگزین میکند.
4. تستها را در `tests/unit/` اضافه کنید (نمونههای موجود:
   `tests/unit/guardrails-registry.test.ts`،
   `tests/unit/prompt-injection-guard.test.ts`،
   `tests/unit/guardrails/visionBridge.test.ts`).

## تست

برای شروع از یک وضعیت مشخص، بین تستها از `resetGuardrailsForTests()` استفاده کنید.
برای شروع با یک رجیستری خالی، `{ registerDefaults: false }` را ارسال کنید و
فقط گاردریلهای تحت آزمایش را ثبت کنید. Vision Bridge از تزریق وابستگی
(`deps.getSettings`، `deps.callVisionModel`) پشتیبانی میکند؛ Audio Bridge نیز
نقاط اتصال معادل را برای تنظیمات، قابلیتها، انتخاب مدل STT، بررسی اطلاعات
اعتبارسنجی و رونویسی ارائه میدهد. بنابراین تستها میتوانند هر دو جریان را
بدون دسترسی به DB یا شبکه اجرا کنند.

  منوط به وجود یک secret ارائهدهنده (`PROMPTFOO_PROVIDER_KEY`) است؛ در صورت نبود آن،
  بدون خطا از اجرا صرفنظر میکند و پسوند `|| true` دارد، بنابراین بدون شکست CI گزارش میدهد.

پوشش helper گارد (`createInjectionGuard` / `withInjectionGuard`)
تمام مسیرهای `/v1` دارای پرامپت را در بر میگیرد؛ متن پرامپت از
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` توسط
`extractMessageContents()` در `src/shared/utils/inputSanitizer.ts` استخراج میشود.
